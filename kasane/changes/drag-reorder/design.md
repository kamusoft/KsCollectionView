# Design: drag-reorder

## Context

D&D 並べ替えの契約と両プラットフォームの実装方式は、phase-6 の議論で core/ADR-0026〜0033・ios/ADR-0011・android/ADR-0007 (いずれも proposed) に確定した。本 design はそれを両プラットフォームの公開 API と実装に落とす。

今のコードの前提 (提案時の調査で確認):

- iOS の `KsCollectionView` (SwiftUI の View) は modifier ごとに `KsCollectionConfiguration` (internal struct) を書き換えたコピーを返し、`KsCollectionRepresentable` が `KsCollectionViewController` の `update(configuration:)` を毎回呼ぶ。ページングは `KsCollectionView+Paging.swift` の extension と internal の `KsPaging` に分けてある。`update` は直前の値を控えてから `apply(items:...)` を呼び、`apply` が差分データソースの snapshot を「グループ × 内部の塊」のセクションで組む (ios/ADR-0009・0010)。塊の区切りは `KsGroupChunkTable` が持ち、IndexPath から配列の位置を直接引く関数は無い (`sectionItemRanges[section].lowerBound + item` で組み立てる)
- iOS の長押しは、コレクションビューに付けた 1 つの `UILongPressGestureRecognizer` (`isEnabled = onItemLongTap != nil`) で、`update` のたびに有効 / 無効を更新している。`dragDelegate` / `dropDelegate` は未設定。スクロール命令は `pendingCommands` に溜めて `apply` の完了で実行する (core/ADR-0007)
- Android の `KsCollectionView` は Composable 1 本に引数を平らに並べ、ページングは `KsPaging` クラス 1 つを引数で渡す。項目には外側から `ksAnimateItem` (`animateItem`) → 見た目 → 幅 → 間隔 → 区切り線 → `combinedClickable` (タップのハンドラがあるときだけ、`onLongClick = onItemLongTap`) → `ksAnimatedHeight` の順に修飾が付く。グリッドには「ルートのヘッダー → (見出し → 項目) × グループ → ルートのフッター」の順に出し、見出しは固定するとき `stickyHeader`。lazy の index と項目の添字の対応は `KsGroupPlan` が持つ。`LazyGridState` は内部で持ち、スクロール命令・ページングの判定 (`snapshotFlow`)・末尾への追従 (`KsPositionKeeper`)・スクロールインジケータが読む
- 読み上げのカスタム操作は、両プラットフォームとも既存の使用が無い

## Goals / Non-Goals

**Goals:** core/ADR-0026〜0034 の決定を、両プラットフォームで同じ観察可能な振る舞いとして実装する。並べ替えのスイッチが無効の一覧 (既定) の振る舞いを変えない。既存の位置の対応 (iOS のセクション・Android の lazy index) とアニメーション (差分・高さの補間・端の留め方) を壊さずにドラッグを足す。

**Non-Goals:** proposal.md の Non-Goals のとおり。

## Decisions

### Decision 1: 公開 API の形

**採用案:** 語彙は両プラットフォームで 1 対 1 に揃え、記法は各流儀とする (core/ADR-0002)。ページングと同じく、Swift は 1 つの modifier、Kotlin は 1 つの設定クラスを引数で渡す形にまとめる。

| 語彙 | Swift | Kotlin |
|---|---|---|
| 並べ替えの設定 | `.reorder(isEnabled: Bool, canMove: ((Item) -> Bool)? = nil, canDrop: ((KsReorderMove<Item>) -> Bool)? = nil, accessibilityActions: KsReorderAccessibilityActions? = nil, onMove: @escaping @MainActor (KsReorderMove<Item>) -> Bool)` | `KsCollectionView(..., reorder: KsReorder<Item>? = null)` / `public class KsReorder<Item>(enabled: Boolean, onMove: (KsReorderMove<Item>) -> Boolean, canMove: ((Item) -> Boolean)? = null, canDrop: ((KsReorderMove<Item>) -> Boolean)? = null, accessibilityActions: KsReorderAccessibilityActions? = null)` |
| 知らせ | `public struct KsReorderMove<Item> { item: Item; destination: KsReorderDestination<Item>; group: AnyHashable? }` | `public class KsReorderMove<Item>(item: Item, destination: KsReorderDestination<Item>, group: Any?)` |
| 行き先 | `public enum KsReorderDestination<Item> { case before(Item); case end }` | `public sealed interface KsReorderDestination<out Item>` と `Before<Item>(item)` / `data object End` |
| 読み上げの文言 | `public struct KsReorderAccessibilityActions { init(previous: String, next: String) }` | `public class KsReorderAccessibilityActions(previous: String, next: String)` |

- `isEnabled` / `enabled` が並べ替えのスイッチ (core/ADR-0031)。`.reorder` を付けない (Kotlin は `reorder = null`) 一覧と、付けて無効にした一覧は同じ振る舞い (長押しの知らせは今までどおり)
- `onMove` は置いたときに 1 回呼ばれ、受け入れたかを返す (core/ADR-0026・0027)。Swift は MainActor の同期のクロージャ、Kotlin はメインスレッドで呼ぶ普通の関数
- `group` はグループを宣言していれば行き先のグループの値 (`.groups(by:)` / `KsGroups.by` が返した値)、宣言していなければ nil / null。`end` はグループを宣言していればそのグループの末尾、していなければ一覧の末尾 (core/ADR-0028)
- `canDrop` はドラッグ中に行き先の候補ごとに呼ぶ。`onMove` と同じ形の知らせを受ける (core/ADR-0030)
- Kotlin の `KsReorder` / `KsReorderMove` / `KsReorderAccessibilityActions` は `KsPaging` と同じく普通の public class (data class にしない)。`KsReorderDestination.Before` も同じ。`End` は data object
- Kotlin の `reorder` 引数は `paging` / `onRefresh` の後ろ、`content` の前に置く
- 移動を配列に当てはめる補助関数は用意しない。VM の書き方 (動かした項目を取り除き、グループの値を書き換え、行き先の前か末尾へ入れる) はガイドに載せる

**理由:** ページングと同じ置き方にし、並べ替えの設定がひとまとまりで読める。Kotlin はクラス 1 つを渡す形にしないと、`KsCollectionView` の引数が 5 つ増える。グループの値は、`.groups` と `.reorder` が別の modifier (Kotlin は別の引数) で、グループの宣言が任意のため、知らせの型ではグループの値の型を持てない (型を消して渡す)。

**代替案:**
- **A: 知らせの型にグループの値の型を持たせる (`KsReorderMove<Item, Group>`)** — グループを宣言していない一覧で型が決まらず、`.groups` と `.reorder` の宣言を結び付ける仕組みが要る。VM はグループの値を自分のモデルの型に戻すだけで済むため、型を消す負担は小さい
- **B: Swift はスイッチ・判定・文言を別々の modifier にする (`.reorderCanMove { }` 等)** — Kotlin の 1 クラスと 1 対 1 にならず、スイッチを付けずに判定だけ付けた宣言が書けてしまう
- **D: 移動を配列に当てはめる補助関数を用意する (`move.apply(to:)` 等)** — グループの値の書き換えは利用者のモデル次第で、補助関数は並びしか動かせない。主な利用者の VM は KMP の共通のコード (commonMain) にあり、Android のライブラリにも Swift の関数にも依存できないため、いちばん使いたい利用者が使えない
- **C: 知らせを受ける処理の名前を `onReorder` にする** — 設定の名前 (`reorder`) と重なり、何が起きたときの処理かが読みにくい。`onMove` は SwiftUI の List の並べ替えの処理と同じ名前で、「動かしたときの処理」と読める (引数と戻り値は違うことを DocC / KDoc に書く)

### Decision 2: 行き先の求め方と、知らせない場合

**採用案:** 両プラットフォームで同じ規則で、置いた位置 (ドラッグ中の仮の並び) から行き先を求める。

| 置いた位置 | 行き先 | `group` |
|---|---|---|
| 同じグループの中で、後ろに項目がある | `before(後ろの項目)` | その項目のグループの値 |
| グループの最後 (後ろが見出し・グループの間の間隔・一覧の末尾) | `end` | 置いたグループの値 |
| グループを宣言していない一覧の最後 | `end` | nil |

- 境目では、見出し (見出しが無ければグループの間の間隔) より上なら前のグループの末尾、下なら次のグループの先頭 (agenda の導出)。先頭は `before(そのグループの最初の項目)` になる
- 動かした項目自身は後ろの項目に数えない
- 元の位置に置いたとき (行き先を求めると移動の前と同じ並びになるとき)、ドラッグが取りやめになったとき (システムによる中断・スイッチの無効化・layout 値かグループの宣言の変化 — Decision 7)、置けない場所の上で指を離したとき (Decision 3・4) は、`onMove` を呼ばずに元の位置へ戻す
- `canDrop` は、候補の位置ごとに同じ規則で求めた知らせを渡す。元の位置は判定しない (いつでも戻せる)

**理由:** 「この項目の前」は後ろの項目で表すと、グループの境目 (前のグループの末尾と次のグループの先頭) を必ず区別できる。元の位置への「移動」を知らせないのは、VM に保存を走らせないため。

**代替案:**
- **A: 行き先を「この項目の後ろ」で表す** — core/ADR-0028 で「前 / 末尾」と決めた。先頭へ置くときに「後ろ」の相手がいなくなる

### Decision 3: iOS — UIKit のドラッグ & ドロップの組み込み

**採用案:** `KsCollectionViewController` に drag delegate と drop delegate を付ける (ios/ADR-0011)。

- **スイッチ**: 有効の間は `dragInteractionEnabled = true` にし、長押しの認識器を無効にする。無効の間はドラッグを無効にし、長押しの認識器は今までどおり `onItemLongTap` の有無で決める。`update` のたびに更新する。有効の間は `onItemLongTap` をハンドラに数えず、`onItemTap` が無い項目はタップしても強調しない (`shouldHighlightItemAt`)
- **持ち上げ**: `itemsForBeginning` で `canMove` が偽の項目は空の配列を返して持ち上げない。ドラッグの項目にはアプリの中だけの目印 (項目の識別子) を持たせ、`dragSessionIsRestrictedToDraggingApplication` を真にして iPad でもアプリの外へ持ち出させない。ドラッグのセッションには持ち上げた一覧の目印 (ローカルの文脈) を付け、drop delegate は目印が自分でないセッション (同じアプリの別の一覧からのもの) を受けない
- **ドラッグ中**: `dropSessionDidUpdate` で UIKit の行き先 (内部の塊のセクションと番号) を Decision 2 の行き先に読み替え (`KsGroupChunkTable` から配列の位置を組み立てる補助を足す)、`canDrop` が偽なら禁止、真なら `.move` + `insertAtDestinationIndexPath` を返す。自動スクロールと持ち上げの見た目は UIKit 標準のまま
- **置いたとき**: `performDropWith` で知らせを求めて `onMove` を呼ぶ。受け入れたら、差分データソースの今の snapshot の中で項目だけを動かした snapshot を当て (グループの組み直しはしない — 項目のグループの値はまだ変わっていないため、組み直すと離れた同じ値の不正入力になる)、`coordinator.drop` で置く。配列の並び (`appliedIdentifiers` / `appliedItems`) と塊の表 (各塊の件数・セクションの範囲・グループの項目の範囲) を、項目だけを動かした並びと仮の所属 (動かした項目は行き先のグループ) で組み直す (塊の区切り直しはしない。ページングの判定・スクロール命令・位置の控えが位置で引くため、VM の配列が届くまでの間もずれないようにする)。見出しの中身に渡す項目も、グループの値ではなくこの表から組む。項目が無くなったグループは、セクションと見出しをこの時点で取り除く (固定の見出しの位置の計算は、グループに最初と最後の項目があることを前提にしているため)。受け入れなければ置かずに終え、UIKit が元の位置へ戻す
- **確定**: 受け入れた後に、置いた時点の配列と違う配列が届いたら、通常の `apply` で当てる (グループと内部の塊をその配列から組み直す)。置いた時点の配列と同じ配列での `update` (ほかの状態の変化による再描画。`update` は毎回呼ばれる) では当てずに待つ
- **読み上げ**: UIKit がドラッグ & ドロップに付ける標準の読み上げの操作はそのまま残し、加えて Decision 6 の操作をセルに付ける

**理由:** 仮の並び・置けない場所・自動スクロール・持ち上げの見た目を UIKit 標準に任せられ、契約にいちばん素直に当てはまる (ios/ADR-0011)。置いた直後はモデルのグループの値が古いため、通常の組み立て (グループの値からグループを組む) は通せず、差分データソースの snapshot の中で項目だけを動かす。空になったグループを受け入れた時点で取り除くのは、agenda の導出 (確定して配列が届いた時点で消える) より早めた形で、受け入れた後はもう元のグループへ戻せず見出しを残す理由 (ドラッグ中に戻せる・表示が跳ねない) が無くなる一方、残すと固定の見出しが項目の無いグループを扱う壊れやすい状態を通るため (相方の提案レビューで検出)。

**代替案:**
- **A: 置いたときに、仮の並びの配列を通常の `apply` で当てる** — 動かした項目のグループの値はまだ元のグループのままなので、グループをまたいだ移動が「離れた同じ値」になり、debug では assertion で止まる
- **B: 置いた直後は何も当てず、VM の配列を待つ** — `insertAtDestinationIndexPath` で置くには差分データソースを更新する必要があり、当てないと UIKit のプレースホルダが外れて一度元の位置に戻って見える

### Decision 4: Android — 自前のドラッグ

**採用案:** ラッパーの中に並べ替えの状態 (internal) を持ち、Compose の公開 API の上で組む (android/ADR-0007)。

- **スイッチと長押し**: 有効の間は、項目の `combinedClickable` の `onLongClick` を外し (長押しの知らせを呼ばない)、長押しでドラッグを始める検出を項目に付ける (`canMove` が偽の項目には付けない)。有効の間は `onItemLongTap` をタップのハンドラに数えず、`onItemTap` が無ければ `combinedClickable` を付けない (フィードバックを出さない)。無効の間は今までどおり
- **仮の並び**: ドラッグ中は、表示の並びを「配列 + ドラッグ中の項目の今の位置と所属グループ」から作る。グループの計画 (`KsGroupPlan`) にドラッグ中の項目の所属の上書きを渡せるようにし、空になった元のグループの見出しも残す。ドラッグ中の項目の中心がほかの項目の範囲に入ったら、Decision 2 の知らせを求めて `canDrop` を確かめ、真なら仮の並びの中で動かす (ほかの項目は `animateItem` で動く)。偽なら動かさず、その場所の上にいる間は「置けない場所の上」と控える
- **持ち上げ**: ドラッグ中の項目は指に付いて動かし (graphicsLayer の平行移動)、ほかの項目と固定の見出しより手前に描く。その項目だけ配置のアニメーションを外す
- **自動スクロール**: 指が一覧の外枠 (安全領域は使わない — core/ADR-0017) の上端か下端の近くにある間、端からの距離に応じた速さでスクロールを続け、スクロールした分だけドラッグ中の項目の位置を補正する。速さと範囲は iOS の標準に近い既定値を内部の定数に持つ (公開しない)
- **先頭の位置飛び**: 仮の並びで先頭の可視項目が入れ替わったときは、スクロール位置を入れ替わる前の見え方に合わせ直す (LazyGridState は先頭の可視項目の key に位置を追従させるため)
- **置いたとき**: 置けない場所の上で離したら元の位置に戻して知らせない。それ以外は知らせを求めて `onMove` を呼び、受け入れたら項目が無くなったグループを見出しごと取り除いて (iOS の Decision 3 と同じ時点) 仮の並びのまま VM の配列を待ち、受け入れなければ元の位置へアニメーションで戻してから、配列を保留していれば最新の配列を当てる (Decision 5)。ドラッグは項目を持ち上げた一覧のジェスチャの中で完結するため、ほかの一覧には置けない
- **確定**: 受け入れた後に、置いた時点の配列と違う配列が届いたら仮の並びを捨て、通常どおりグループを組み直す。置いた時点の配列と同じ配列での再コンポジションでは捨てない

**理由:** 契約 (仮の並び・見出しまたぎ・置けない場所・保留) を最初から作り込める (android/ADR-0007)。グループの計画に所属の上書きを渡すのは、動かした項目のグループの値がまだ古いまま、ドラッグ中だけ行き先のグループに見せるため (iOS の Decision 3 と同じ事情)。

**代替案:**
- **A: ドラッグ中の項目をグリッドの外の重ね描きで指に付け、グリッドの中には隙間だけを置く** — ドラッグ中の項目のセルがグリッドの中に残らず、スクロールで作り直されて状態を失う心配はないが、テンプレートの中身を 2 か所に描くことになり、描画の費用と見え方の一致の手当てが増える。グリッドの中の項目を持ち上げる形は、Compose の Lazy 系の並べ替えで知られた形

### Decision 5: ドラッグ中の配列・ページング・スクロール命令

**採用案:** 両プラットフォームで同じ扱いにする。

- **配列の保留**: ドラッグ中 (持ち上げてから、置いて受け入れの結果が出るまで) に届いた配列は当てずに、最新の 1 つを控える。受け入れたら捨てて、置いた時点の配列と違う配列が届くまで待つ (同じ配列での描き直しでは待ち続ける)。受け入れなかったとき・取りやめたとき・元の位置に置いたときは、項目を元の位置に戻してから控えた最新の配列を当てる (最後の表示は最新の配列。控えていなければ元の並びのまま) (core/ADR-0033)。iOS は `update` の中の `apply` の手前、Android は表示の並びを作るところで控える
- **ページング**: ドラッグ中は追加読み込みの判定をしない (頼まない)。ドラッグが終わったら (置いた・取りやめた後に) 判定し直す (core/ADR-0034、amends core/ADR-0020)
- **スクロール命令**: ドラッグ中に受けた命令は溜め、ドラッグが終わって配列を当てた後に順に実行する (core/ADR-0007 の「データ反映後に実行」を、ドラッグの終わりまで延ばす)

**理由:** 配列を保留したまま追加読み込みを判定すると、頼んだページが表示に出ないまま状態が変わり、頼んだ後の待ち (core/ADR-0022: 処理が終わり、かつ状態か配列が変わるまで) が解けて、次のページを連鎖して頼む。ドラッグ中のスクロール命令をすぐ実行すると、指の下の一覧が指と関係なく動く。

**代替案:**
- **A: ドラッグ中も追加読み込みを頼み、配列の保留だけで扱う** — 上の連鎖が起きる
- **A': core/ADR-0020 のとおりドラッグ中も判定し、判定で数える配列を保留した最新の配列に切り替えて連鎖を防ぐ** — 指を離したときに次のページが読み込み済みになるが、数え方を保留の有無で切り替える仕組みが両プラットフォームに要り、ドラッグ中に下端で読み込み中の表示が出て消えるのに項目が増えない見え方になる (提案の自己レビューでオーナーに諮り、改訂案 (本採用案) を選んだ)
- **B: ドラッグ中に受けたスクロール命令を捨てる** — 命令は取りこぼさない (core/ADR-0007)

### Decision 6: 読み上げの移動操作

**採用案:** スイッチが有効で、`accessibilityActions` を渡した一覧の、動かせる項目に 2 つの操作を付ける (core/ADR-0032)。

- 「前へ移動」(`previous` の文言): 配列の並びで 1 つ前へ。グループの先頭の項目なら前のグループの末尾へ (`end` + 前のグループの値)
- 「後ろへ移動」(`next` の文言): 1 つ後ろへ。グループの最後の項目なら次のグループの先頭へ (`before(次のグループの最初の項目)`)
- 一覧の先頭の項目には「前へ移動」、最後の項目には「後ろへ移動」を出さない。行き先の知らせを `canDrop` に渡して偽なら、その操作を出さない
- 操作で動かすと、ドラッグと同じく `onMove` を呼び、受け入れたら動かして VM の配列を待ち、受け入れなければ動かさない。移動の後、読み上げの焦点は動かした項目に残す
- iOS はセルの `accessibilityCustomActions`、Android は項目の semantics の `customActions` に付ける。操作の有無は、配列・スイッチ・判定が変わるたびに付け直す

**理由:** 1 つずつ動かす操作はドラッグの 1 段と同じ規則 (Decision 2) で行き先を求められ、グループの境目も同じに扱える。

**代替案:**
- **A: 「先頭へ移動 / 末尾へ移動」も足す** — 長い一覧では役立つが、グループを宣言した一覧で「先頭」が一覧の先頭かグループの先頭かの決めごとが増える。まず 2 つで出し、要望が出たら足す (後から足しても書き方を壊さない)

### Decision 7: ドラッグ中にスイッチ・layout・グループの宣言が変わったとき

**採用案:** ドラッグを取りやめ、元の位置へ戻して `onMove` を呼ばない。そのうえで変わった設定と、控えていた配列があればそれを当てる。iOS はドラッグのセッションを取り消し、Android はドラッグの状態を捨てる。対象はスイッチの無効化と、配置を組み直す設定 (layout 値・グループの宣言) の変化。

**理由:** スイッチが無効 = 並べ替えを受け付けない状態なので、途中の移動も成立させない (proposal でオーナーの承認済み)。layout 値やグループの宣言が変わると、両プラットフォームとも配置 (iOS はレイアウト、Android はグループの計画) を組み直し、仮の並びと行き先の対応が崩れる (相方の提案レビューで検出)。

**代替案:**
- **A: そのドラッグは最後まで続けさせ、次から受け付けない** — スイッチを切った VM に知らせが届き、VM が受け入れの判断で弾く必要が出る

### Decision 8: Sample「並べ替え」

**採用案:**

- ルートメニューの「ページング」の次に「並べ替え」を両プラットフォーム同じ位置・同じ文言で追加する
- データ: 全 10,000 件 (「Item 1」〜「Item 10000」、ID は整数)。グループの値は「グループ 1」〜「グループ 100」で、初めは 100 件ずつ。10 の倍数の項目は動かせない項目にし、「Item 10 (移動不可)」のように表示する
- VM: 項目の配列 (グループの値を書き換えられるモデル) を持ち、知らせを受けたら動かした項目を取り除き、グループの値を行き先のグループに書き換え、行き先 (`before` の項目の前 / グループの末尾) に入れて受け入れる。グループをオフにしている間 (知らせの `group` が無い) は、行き先の隣の項目 (`before` ならその項目、`end` なら最後の項目) のグループの値に書き換える。オフの間に動かした項目のグループの値を変えないと、オンに戻したときに同じグループの値が離れた位置に現れ、不正入力 (core/ADR-0015) になるため。iOS は `@Observable @MainActor final class`、Android は Compose の状態を持つ class を画面で remember する (「ページング」と同じ)
- 操作 (背景が透けるフローティングのパネル。handbook/cross/sample-debug-controls): 「並べ替え」のスイッチ (初期はオン)、list / 2 列グリッドの切り替え、「グループ」の有無 (初期はオン)、「グループをまたがせない」(初期はオフ。オンなら `canDrop` で行き先のグループが元と同じときだけ置ける)、「置いても受け入れない」(初期はオフ。オンなら `onMove` が受け入れないと返し、「並べ替えを受け入れませんでした」を画面上の帯で出す)
- 長押し: `onItemLongTap` で「長押し: Item N」を画面上の帯で出す (スイッチが無効の間だけ出ることを確かめる)。帯は「ページング」の「更新できませんでした」と同じ出し方
- 読み上げの文言: 「前へ移動」「後ろへ移動」を渡す
- 画面の置き方は「ページング」と同じ (一覧を画面の下端まで広げる)。操作のパネルの部品は「ページング」の画面専用の部品を Sample の共通部品に切り出して両画面で使う
- 見え方は承認 mock に従う (ui/brief.md)

**理由:** 決めた契約 (スイッチと長押し・判定 2 つ・受け入れと戻り・グループをまたぐ移動・読み上げ) を 1 画面で目で確かめられるようにする。10,000 件は性能の体感ゲートの土俵の決まり (cross/ADR-0006)。パネルの部品を共通に切り出すのは、同じ見た目の部品を 2 つの画面で二重に持たないため。

**代替案:**
- **A: ソートの切り替えも付ける** — ソート中の扱いはライブラリの契約ではなく VM の書き方 (phase-6 agenda の決定) で、確かめるライブラリの振る舞いが無い
- **B: パネルの部品を「並べ替え」の画面に写して持つ** — 同じ見た目の部品が 2 組になり、片方だけ直す食い違いが起きる

### Decision 9: 検証

**採用案:**

- 自動テスト: デルタスペックの Scenario ごとに、iOS は SwiftPM のテスト (行き先の求め方の単体、ドラッグ & ドロップの delegate を直接呼ぶ結合テスト、読み上げの操作、公開 API)、Android は Robolectric + compose ui-test (長押しからのドラッグの操作を合成する)。Sample は Android の単体テスト (メニューの一致・VM・画面) と iOS の UI テスト (実際のドラッグの操作で並べ替え・受け入れない・グループをまたがせない・スイッチを切ったときの長押し)
- 性能: 「並べ替え」画面でスイッチをオンにした状態の基準機の体感ゲート (handbook/cross/scroll-performance-gate.md) を両プラットフォームで 1 回行う。Android の相対計測は行わない (並べ替えは既定では無効)
- 目視: 持ち上げ・端での自動スクロール (長い距離を運ぶ)・受け入れないときの戻り・グループをまたぐ移動・固定の見出しとの重なり・「前へ / 後ろへ移動」の読み上げを、オーナーが基準機で確かめる。動きの過程の不具合は静止画では判定しない (lessons/code-review.md の昇格済みの教訓)
- UI: 承認 mock との視覚照合 (ksn-ui) を両プラットフォームで行う

**理由:** 行き先と保留の組み合わせは自動テストで網羅し、動きの見え方と滑らかさはオーナーの目で確かめる。Android の自前のドラッグは合成の操作で経路を通せるが、iOS の UIKit のドラッグ & ドロップはライブラリのテストからは合成できないため、delegate を直接呼ぶ結合テストと Sample の UI テストで挟む。

**代替案:**
- **A: 性能の体感ゲートを行わない (並べ替えは有効にした一覧だけで動くため)** — スイッチを有効にすると全項目に長押しの検出 (Android) とドラッグ (iOS) が付く。新しい経路なので 1 回の体感で確かめる

## Risks / Trade-offs

- 固定の見出し (iOS のレイアウトの位置の上書き・Android の stickyHeader) と、ドラッグ中の隙間・持ち上げた項目の重なり順が干渉しないかは未確認。実装の最初に両プラットフォームで確かめ、干渉するなら止めて諮る (tasks 0.1)
- iOS: 置いた直後に項目だけを動かした snapshot を当てると、内部の塊の件数が一時的に 500 からずれる。確定の配列で塊を組み直すとき、塊の件数が変わる差し替えはアニメーションを切る経路 (ios/ADR-0009・0010) を通る。並びは同じなので見た目は変わらないはずだが、目視で確かめる
- iOS: 全画面に広げた一覧 (core/ADR-0017) で、UIKit の自動スクロールがバーの裏の範囲で反応するか (指がバーの上にあるときにスクロールするか) は未確認。自然な形かを実機で確かめる
- Android: 自前の長押しの検出と `combinedClickable` (タップ) の同居、ドラッグとスクロールのジェスチャの取り合い、高さの補間中は配置のアニメーションを止める作り (android/ADR-0006) とドラッグ中の配置のアニメーションの組み合わせ
- Android: ドラッグ中の項目がスクロールで見えている範囲の外に出てコンポジションから外れると、持ち上げが切れる (Compose の Lazy 系の並べ替えで知られた問題)。自動スクロールで長く運ぶ操作で確かめ、起きるならドラッグ中の項目を見えている範囲に留める
- 端の留め方 (core/ADR-0018・0021) と保留の組み合わせ: ドラッグの終わりに控えた配列を当てるとき、端を表示中の端への挿入の判定が働く。直前の状態を正しく控えているかを試験で確かめる
- 読み上げ: iOS は UIKit 標準のドラッグの操作と「前へ / 後ろへ移動」が並んで出る。重複して紛らわしくないかをオーナーが確かめる
- 読み上げ: iOS はセル (`UIHostingConfiguration`) の中の SwiftUI の要素に、Android はテンプレートの中の要素に読み上げの焦点が当たるため、セル / 項目の入れ物に付けたカスタム操作が焦点の要素で出るとは限らない。どこに付ければ出るかを実装の最初に確かめる (tasks 3.6・4.6)
