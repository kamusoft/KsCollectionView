# Design: performance-criteria-review

## Context

探索の決定事項と証跡は `exploration.md` と `evidence/` にある。要点:

- 完了判定はオーナーの体感、数値は証跡 (cross/ADR-0006、proposed)
- iOS「大量件数」の主因は compositional layout の estimated 高さの solver。Sample の行は detail の有無で高さが 2 種類あり、直近 32 件の実測平均 (`KsEstimatedHeight`) はどちらとも一致しないため、新しく可視になる全セルが preferred ≠ original を返して solver を起こす。画像グリッド (全セル同じ高さ) では solver が 0% で体感も合格
- Apple の文書: `shouldInvalidateLayout(forPreferredLayoutAttributes:withOriginalAttributes:)` は preferred が original と同じなら invalidate 不要
- Android の Macrobenchmark には相対 10% の判定コードが無く、人が結果を突き合わせている。絶対基準は文書上の合格線だけ

## Goals / Non-Goals

Goals: 規約を体感ゲートに書き換える / iOS の solver 起動を「推定と高さが違うセル」だけに絞る (最頻値化) / Android の相対基準の判定と計測成立の確認を機械化する / 新手順で再計測して証跡を揃える。
Non-Goals: proposal.md のとおり (画像の表示待ち・スクロールバー・対策 C / D・CI 自動駆動・phase-4 の設計)。

## Decisions

### Decision 1: 推定高さは「直近の実測の最頻値」にし、一致するセルの自己サイズがレイアウトを無効化しないようにする (最頻値化)

**採用案:** `KsEstimatedHeight.value` を、直近 32 件 (幅ごと) の実測のうち出現回数が最も多い値にする。同数なら新しい方を採る。実測が 1 件も繰り返さないうちは平均のまま (未計測は 44pt)。**標本の単位はセル** (`KsHostingCell` が自己サイズで返した高さ。複数列でも行ではなくセルごと) — invalidation の判定は item (セル) の preferred と original の比較で行われるため、一致させる相手はセルの実測。標本は画面のピクセル格子 (1 / scale pt) に量子化してから数える (微小な測定差で同じ見た目の高さが別値に散らないため)。推定値として返すのも量子化後の値。`KsHostingCell.preferredLayoutAttributesFitting` の戻り値は変えないが、Debug 構成のみ「自己サイズを返したセル数」と「推定と不一致だった回数」を `KsCollectionViewController` の診断カウンタに数える (テストと計測の seam。既存の同時生存セル数と同じ扱いで Release には載せない)。

**理由:** 行の高さが少数の種類に集中する画面 (リストの typical、Sample の 2 種類) では、多数派の行が推定値と完全一致して invalidation が起きず、solver が走るのは少数派の行だけになる。画像グリッドの実測 (全行一致で solver 0%) がこの効果の上限を示している。実装は `KsEstimatedHeight` に閉じ、公開 API・レイアウト定義に触れない。

**代替案:**
- **平均のまま (現状)** — 合計高さの見積もりには最良だが、行高が 2 種類以上ある画面では推定値がどの行とも一致せず、全セルが solver を起こす (実測: 主スレッドの 55%)。却下
- **attributes 抑制 (`KsHostingCell` で「推定との差が小さい行は original の attributes をそのまま返す」)** — 差が本当にある行を推定高さで置いてしまい表示が崩れる。差ゼロの行は UIKit が既に invalidate しないので上乗せの効果が無い。却下
- **テンプレートキーごとに推定値を持つ** — `.estimated` は item 定義単位で index path ごとに変えられず、単一セクションでは 1 値しか渡せない (`KsEstimatedHeight` の設計時に確認済み)。却下
- **平均と最頻値のハイブリッド (最頻値の占有率が閾値未満なら平均)** — 切り替えの閾値がもう 1 つの調整点になる。初版では最頻値一本にし、Decision 2 の再検証で合計高さの見積もりが崩れたときの再訪案として残す

### Decision 2: 最頻値化の効果は事前に固定した数値基準で判定し、平均が担っていた保証も数値で再検証する

**採用案:** 判定は次の 4 つで、いずれも実装前に固定する (値は Sample「大量件数」fixture = 高さ 2 種類が 6 : 1 の前提)。
1. **不一致率**: 診断カウンタの「推定と不一致だった回数 / 自己サイズを返したセル数」が、推定が多数派の高さに達した後の区間で **0.20 以下** (少数派の割合 1/7 ≈ 0.14 に余裕 0.05)
2. **件数比例**: Sample の起動引数 `--large-count` で 2,000 件と 10,000 件を開き、同じ固定操作列 (Decision 9) で手動フリックした Instruments の time profile で、`_UICollectionLayoutSectionEstimatedSolver` の主スレッド占有率が **10,000 件 ≤ 2,000 件 × 1.5**。占有率は「操作列の区間」の標本で計算する
3. **合計高さ**: 既存のエンジンテストの形で、初回表示のコンテンツ高さの実測に対する誤差が **±5% 以内**、末尾までスクロールする間の contentSize 変化回数が **3 回以下** (平均での実測は 0% / 1 回)
4. **体感**: Decision 9 の操作列で合格

**理由:** 「同程度」「無視できる」では同じ結果から合格と不合格の両方を主張できる (相方レビュー)。占有率だけでは操作量に左右されるため、不一致率 (件数と操作に依らない) を主指標にし、占有率は比例性の確認に限る。

**代替案:**
- **10,000 件の体感と占有率だけで判定** — 対策後の値が件数に依存しないことを示せない。却下
- **solver の呼出回数と 1 回あたりの費用を直接測る** — UIKit 内部の呼出は数えられない (標本ベースの time profile では回数が出ない)。セル側の不一致回数が呼出回数の上界になるのでそれで代替
- **自動駆動で比例性を測る** — 足場が主スレッドを汚す。却下

### Decision 3: 本 change の実装は最頻値化までとし、不合格なら実装を止めて提案を改訂してから内部セクション分割に進む

**採用案:** Decision 2 の判定で不合格 (不一致率・件数比例・体感のいずれか) なら、実装フェーズはそこで NEEDS_DISCUSSION として止まり、内部セクション分割 (`KsSectionID` を列数の倍数の塊に分けて snapshot を組む) の Requirement / Scenario (塊の境界で不完全な行を作らない・先頭行の区切り線・ルートヘッダー / フッターが先頭と末尾の塊にだけ付く・先頭挿入で塊の所属が変わるときの差分更新と位置維持・スクロール命令の ID 解決) をこの change の提案に追加して再レビューしてから実装する。足場の凍結は保ち、追加は提案の改訂として行う。試作に入る前に phase-4 の agenda に「利用者の論理セクションと内部の分割単位の責務」と 3 条件 (sticky ヘッダが内部分割の末尾で止まらない / 列数に合わない分割で不完全な行を作らない / 先頭挿入時の差分更新と位置維持) を論点として追記する。採用時は ADR 候補として捕捉する。

**理由:** 内部セクション分割は snapshot・区切り線・ヘッダー / フッター・アンカー保持に及ぶのに、今のデルタスペックにはそれを拘束する Requirement が無い (相方レビュー)。使わないかもしれない仕様を先に書くより、必要になった時点で提案を改訂する方が安い。change を分けないのはオーナー判断 (対策の効果測定に新手順を使うため)。

**代替案:**
- **最初から内部セクション分割を実装** — 最頻値化 (小コスト) で足りる可能性が画像グリッドの対照で高い。却下
- **内部セクション分割の spec を今書く** — 塊の件数・ヘッダーの扱い・phase-4 との責務が未決で、推測で書くことになる。却下
- **内部セクション分割を別 change にする** — 効果測定の手順が本 change の成果物で、切り離すと相互待ちになる。却下 (オーナー判断)

### Decision 4: Android の相対基準の判定と計測成立の確認は、Macrobenchmark の結果 JSON を事後検証するスクリプトで行う

**採用案:** `samples/android/benchmark/scripts/verify-fling-results.py` (Python 3、標準ライブラリのみ) を置く。契約:
- 入力: `build/outputs/connected_android_test_additional_output/` 配下の最新 1 実行の JSON だけを読む (古い結果ディレクトリが混在したら入力不正)。`benchmarks[].name` (テスト名) でライブラリ側と比較対象側を対応付け、片側しか無ければ入力不正
- 環境照合: JSON の `context` (機種・OS・ビルド構成) が両側で一致しなければ入力不正
- 計測成立: 各試行の `frameCount` が **90 以上** (基準機 60 Hz × 3 秒のフリック = 理論上限 180 の 50%。結果を見て動かさない固定値)。割れた試行があれば「未判定」
- 相対判定: `frameDurationCpuMs` の P90 / P99 (3 試行の集計値) の劣化が 10% 以内で「合格」、超えたら「不合格」
- 終了コード: 合格 0、不合格・未判定・入力不正はいずれも非 0 (種別ごとに別の値)。欠損 metric・破損 JSON・重複も入力不正
- `ImageGridBenchmark` は比較対象が無いので計測成立だけ判定し、相対・絶対の判定はしない
- 比較対象には、ライブラリの既定機能 (現時点では行の高さ変化のアニメーション、android/ADR-0004) と同じ機能を同じ位置に付ける (現行規約から引き継ぐ。付けないと相対の差が既定機能そのものの費用になる)
- `LargeDataMemoryBenchmark` / `ImageGridBenchmark` の 1,000 件の試行 (件数比) は削除する

**理由:** 相対 10% は現状人が突き合わせており判定の所在が無い。計測ブロック内から集計値は読めないが、結果 JSON には `frameCount` を含む集計が残る (公式の `FrameTimingMetric`)。下限を実装時に校正すると合否線を結果観測後に動かせるため、理論値からの固定にする (相方レビュー)。

**代替案:**
- **試行ごとに `dumpsys gfxinfo` を読んで下限を assert** — 試行間のリセット・対象 window・取得失敗の定義が要り、計測区間と一致しない。却下
- **判定を人手のまま** — 「未判定が緑」の穴が残る。却下
- **下限を実装時の実測で校正** — 事前の受け入れ基準にならない。却下

### Decision 5: メモリの「件数比」系統を「保持対象の寿命と解放」の確認に差し替え、観測できる対象に要件を絞る

**採用案:** 要件が対象にする保持は、ライブラリが**項目単位**で持つもの: iOS はセルとそのホスティング (Debug 構成の同時生存セル数で観測)、Android は項目のコンポジション (Sample debug 構成のテンプレート呼び出しカウンタで観測)。`KsEstimatedHeight` の標本は項目単位ではなく上限 32 件の固定長で、置換時に捨てる必要は無い (幅が変わったときだけ捨てる現行の規則を維持)。画像の要求と台帳は image-loading の spec (取り消し・メモリ保持) が担い、ここでは扱わない。
観測方法: iOS はエンジンテストで (a) 2,000 件往復 → 別の 2,000 件に置換 → 同時生存セルが可視の 4 倍未満に戻る、(b) コレクションを解放 → controller への弱参照が nil になる (破棄後に同じインスタンスのカウンタは読めないため、弱参照プローブで「破棄された」ことを確かめる)。Android は計測用の入口の自動走査に「置換 → 離脱」の段階を足し、離脱後の同時生存はプロセス全体のカウンタ (debug ソースセット、画面に属さない) を離脱先の結果画面の進捗の印から読む。メモリの往復定常化 (10,000 件) の手順は維持する。

**理由:** 10 倍の件数比は「定常値が件数に比例しない」ことしか示さず、項目単位の保持を全件分抱えたまま定常化する場合を見逃す。一方で要件を「保持する対象すべて」と書くと、カウンタが観測しない対象 (訪問済み ID・画像要求・購読) が残っても Scenario が通る (相方レビュー)。観測できる対象に要件を絞り、他は各能力の spec に任せる。

**代替案:**
- **件数比を残す (1,000 vs 10,000)** — 10,000 件の生成と往復の時間が残り、上記の見逃しも残る。却下
- **定常化だけで済ませる** — 全件保持のまま定常化する場合を判別できない。却下
- **保持対象すべてを要件にする** — 観測手段が無い対象が要件に混ざる。却下

### Decision 6: 規約は「共通の判定規則」を cross に置き、platform 別の文書は道具と手順に絞る

**採用案:** `handbook/cross/scroll-performance-gate.md` (rule) を新設し、体感ゲート・証跡に残す項目 (操作条件・体感を先に記録・数値・参考スケールの扱い・比較不能の明示・悪化時の記載義務)・合図の手順・画像の表示待ちが別の観測点であること・自動駆動の再訪条件を書く。`handbook/ios/performance-verification.md` と `handbook/android/performance-verification.md` は、fixture・機材・計測器の接続手順・数値の取り出し方・メモリの手順 (iOS: Simulator の自動往復、Android: Macrobenchmark + 事後検証スクリプト + 相対基準) に絞って全面的に書き直す。旧基準・旧値には言及せず、経緯は cross/ADR-0006 の Context に委ねる (handbook から ADR へリンクする)。

**理由:** 判定規則は両プラットフォームで同一であり、2 本に同じ文を書くと片方だけ直る。道具は platform で違う。

**代替案:**
- **A: platform 別 2 本に同じ規則を書く** — 重複と乖離。却下
- **B: cross 1 本に全部書く** — 計測器の手順が長く、platform の index から引けなくなる。却下

### Decision 7: iOS の自動フリックの計測ドライバは退役し、メモリの自動往復は維持する

**採用案:** `PerformanceDriverUITests` の「3 秒間連続フリック」2 本と、区間の印 (`ScrollWindowSignpost`、起動引数 `--signpost-scroll-window`) を削除する。メモリの自動往復 (`test大量件数を全件通過で2往復してメモリを表示する`、計測専用 launch 経路) は残す。

**理由:** 規約から自動駆動が消えるのに駆動テストだけ残すと使われない足場になる。git の履歴に残るので CI 再訪時に戻せる。メモリの往復は足場の問題が無く、Simulator で自動実行できる。

**代替案:**
- **A: スキーム除外のまま残す** — コンパイルされ続けるだけの死んだコード。却下

### Decision 8: 手動計測の証跡は固定の雛形に書く

**採用案:** `evidence/` の手動計測は探索で書いた 4 本 (`manual-*-2026-09-08.md`) の構成を雛形にする: 環境 (機種・OS・構成・fixture・駆動・記録・熱状態) / オーナーの体感 (数値を見る前に聞き取り。初回・再訪・連続・ムラ・画像の出方) / 数値 (証跡。合否ではない) / 判定 (体感の合否、数値との一致・不一致、前回との比較可否) / 限界。雛形は cross の規約に載せる。

**理由:** 比較可能性は同じ項目が残っているかで決まる。探索で 4 本書いて形が安定した。

**代替案:**
- **A: 自由記述** — 次回との比較ができない。却下

### Decision 9: 体感ゲートは固定の操作列と 3 状態の判定で運用する

**採用案:** 手動計測の操作は次の固定列とする (cross の規約に載せる): (1) 初回: 先頭から下向きに 10 秒連続フリック、(2) 休止 3 秒、(3) 再訪: 上向きに 5 秒、(4) 連続: 下向きに 10 秒 (未訪問の範囲へ)。速度は「いつもの感覚」でよいが、各段階の体感を段階ごとに聞き取り、数値を見る前に記録する。判定は **合格 / 不合格 / 未判定** の 3 状態で、未判定のままでは性能面の完了を報告できない。オーナーが迷った場合、または体感と数値が食い違った場合は、計測器を接続せずに同じ操作列を 1 回行って対照とし、それでも迷えば未判定。独立試行は 1 回を基本とし、再試行は上記の条件でのみ行う。

**理由:** 「10 秒以上フリック」だけでは速度・開始位置・方向・休止が自由で、同じ実装でも判定が揺れる。「未判定」が無いと迷った結果が合格に寄る (相方レビュー)。操作列は探索で 4 本の証跡を取ったときの実際の操作 (初回 → 再訪 → 連続) を固定したもの。

**代替案:**
- **自由な操作 + 条件の記録だけ** — 比較不能を説明できるが判定の再現性は担保しない。却下
- **自動駆動で操作を固定** — 足場の汚染 (探索の結論)。却下

## Risks / Trade-offs

- 最頻値で合計高さの見積もりが崩れ、初回表示のコンテンツ高さや末尾スクロールの安定性が退行する可能性 → Decision 2 の再検証で担保。崩れたら Decision 1 の代替 (ハイブリッド) へ
- 行の高さが多種類 (3 種類以上) の画面では最頻値化の効果が限定的 → Decision 3 で内部セクション分割へ (提案の改訂を経る)
- 体感ゲートはオーナー 1 人の主観 → Decision 8 の雛形と「比較不能」の明示で補う
- Macrobenchmark の JSON の形式が版で変わる → スクリプトは `metrics` の名前で引き、無ければ未判定を返す

## Migration Plan

1. 規約 3 本 (cross 新設 + platform 2 本書き換え) と証跡の雛形
2. iOS: `KsEstimatedHeight` の最頻値化 + 診断カウンタ + エンジンテストの再検証 + `--large-count` + ドライバの退役
3. Android: 事後検証スクリプト + 件数比の試行の削除 + 解放確認の自動走査
4. iOS: 解放確認のエンジンテスト
5. 再計測 (iOS 大量件数 2,000 / 10,000、画像グリッド。Android 画像グリッドは探索の証跡を雛形に揃える) と Decision 2 の判定。不合格なら Decision 3 (提案の改訂)
6. cross/ADR-0006 を実装後の視点で見直す

## Open Questions

- 最頻値化で不合格だった場合の内部セクション分割の塊の件数 (200〜500 の中で列数の倍数) — 提案の改訂で決める

## ADR 候補

- Decision 3 で内部セクション分割を採った場合のみ (ios ドメイン。ios/ADR-0003 との関係と phase-4 の 2 段 ID)
- Decision 1 (最頻値) は concepts (collection-engine の「推定高さは実測平均」) の改訂で足りる。覆すコストは低く境界も越えないため ADR にしない
- cross/ADR-0006 は起票済み (探索で捕捉)。Decision 6 の規約の構成は ADR ではなく handbook の編成
