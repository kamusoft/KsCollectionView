# Exploration: performance-criteria-review

## 課題 / 動機

性能検証の規約 (`kasane/handbook/ios/performance-verification.md` / `kasane/handbook/android/performance-verification.md`) のスクロール性能の基準と固定 fixture を見直す。`image-loading` (L 級) の実機計測 (2026-09-08) で次が判明し、オーナー判断で「規約を見直してから判定する」(選択肢 B) と決めた。

- **iOS の基準「3 秒窓 × 5 ms/s 未満 × 3 試行すべて」は「3 秒間フレーム落ち 0」と同値** (60 Hz で 1 リフレッシュ = 16.7 ms → 5.56 ms/s)。画像グリッドは改善した駆動でも 0.00 / 3.94 / 5.54 ms/s で、落ちた 1 回はいずれも 1 フレーム (合成側の render / 自動化オーバーレイ / hosting のレイアウト) で画像ロードの実装は主因ではない
- **画像を出さない「大量件数」(10,000 件・2 列・可変行高混在) が基準機 iPhone 11 で 108 / 136 / 125 ms/s、窓内 hitch 17〜19 件**と桁違いに超える。アーカイブ済みの過去計測 (iPhone 15・20 秒窓・0.0 ms/s) は hitch を検出できない手順 (プロセス指定の接続が成立していなかった) の値で、基準機・現手順の値としては使えない。主スレッドは窓内サンプルの 94% を占めて飽和 (CA commit 19〜22%、XCTest の走査 20〜24%、`_updateVisibleCells` / hosting のレイアウト等)。原因は未特定
- **Android の絶対基準「frameOverrun P99 が 0.0 ms 以下」**も画像グリッドではディスク 6.2〜6.4 ms、メモリ 4.4〜4.6 ms で不合格。warm でも 7.4 ms で cold の取得が原因ではなく、画像 1 枚ごとの subcomposition 等の描画側の費用
- **計測の足場が主スレッドの 20〜37% を占める** (XCUITest のアクセシビリティ走査・自動化オーバーレイ)。座標駆動に変えても、指を離した後の静止待ちのため区間中もランナーが走査し続け、3 秒の区間に入るフリックの投入は 1 回で「連続フリック」を投入回数の意味では満たしていない
- **オーナー指示: 固定 fixture の「大量件数」に 10,000 件は要らない**。件数を減らす方向で見直す

発見の文脈と一次情報: `kasane/changes/image-loading/` の `evidence/image-grid-measurement-ios.md` (立て直した手順・3 試行・対照・「次に必要なこと」)、`evidence/image-grid-measurement-android.md`、`deviation.md` の 2026-09-08 の項 (iOS 7.1 の切り分けと再解析・大量件数の発見・warm の参考値) (archive 後は `kasane/changes/archive/*-image-loading/`)。`kasane/changes/ios-separator-update-guard/` (区切り線更新の無駄。大量件数の超過との関係は未確認)。

## 検討した選択肢 (却下案と理由を含む)

(未探索。起票時点の材料)

- 窓の長さ: 3 秒 → 10 秒 (1 フレーム落ちが 1.67 ms/s になり閾値 5 ms/s と整合する) 等
- 数え方: hitch time ratio のまま / 「連続 2 フレーム以上の落ちだけ数える」/ 自動化オーバーレイと XCTest の走査を除いた帰属
- Android の絶対基準: P99 0.0 ms 以下 → 何 ms まで許すか、P90 との組み合わせ
- fixture の件数: 10,000 → 1,000〜3,000 等。件数を減らすと「メモリ定常化の件数比 (1,000 対 10,000)」の系統も再定義が要る
- 駆動: 静止待ちをしない入力手段 (XCTest 以外) か、静止待ちを許容して窓を伸ばすか
- image-loading の証跡が「次に必要なこと」に挙げた計測: 改善後 trace の A/B (自動化なしの対照)、`thread-state` での待ちの確認、trace の実行ごとの退避

### 相談役の助言 (2026-09-08、出典: advisor (counterpart / codex)、ksn-advise)

決定 1〜8 を渡して助言を受けた。全体の推奨は「1 つの L change を維持し、**体感の合否・計測の成立・原因対策の検証を別々の完了条件**として提案に渡す」。数値の自動不合格には戻さない。決定を覆す指摘は無く、条件と訂正が付いた:

- **決定 1・2 (条件付き支持)**: 弱点は主観そのものより毎回の負荷が変わること。証跡に「初めて通る範囲 / 再訪 / 連続 / 休止後」の区別、操作時間・開始位置・到達範囲・向き・文字サイズ・キャッシュ状態・熱状態を残す。**体感コメントは数値を見る前に記録**し、迷う場合の再試行を手順化する。「前回と同等」は同条件でなければ「比較不能」と書き、主観の一致と数値の一致を分けて記述。悪化が見えたら原因仮説・再確認・受容理由の記載を必須にする (ゲートの復活ではなく形骸化防止)
- **決定 3 (訂正)**: 5 / 10 ms/s は WWDC20「Eliminate animation hitches with XCTest」(developer.apple.com/videos/play/wwdc2020/10077) の推奨値として引用でき、Good は「5 未満」。Xcode Organizer 向けの説明 (developer.apple.com/documentation/xcode/understanding-hitches-in-your-app) は別の目安を掲げるので「Apple の目安」と一括せず資料を特定する。「3 秒で 1 フレームも落とせない」は 60 Hz・約 16.7 ms の hitch が全量入る条件に限った説明
- **決定 4 (訂正)**: 探索文書の `frameOverrunMs` (期限からの超過) と Android 証跡の gfxinfo のフレーム時間 (時間分布) は別物で比較できない。取得源・単位・集計対象を固定する。参考スケールを置かない理由は「出所が無い」より「固定時間だけでは端末の期限や体感を説明しきれない」が堅い
- **決定 5 (条件付き支持)**: 10,000 件は典型画面の代表ではなく「大規模データ対応の負荷条件」として正当化する。件数比の系統を廃止するなら、代わりに**保持対象 (訪問済み ID・画像・購読・サイズキャッシュ) の寿命・上限と、データ置換 / 画面破棄後の解放**を確認する項目が要る。入力データ自体の O(N) メモリは分けて考える
- **決定 6 (支持 + 条件)**: solver が支配的という判断は強く支持。ただし 10,000 件・1 回の profile では件数比例までは確定しない → 件数を変えて solver の呼出回数と 1 回あたりの費用を分けて確認する。hosting 7.5% は直接費用で、サイズ通知が solver を起動する因果を否定する値ではない。B は短い実験として支持だが、少数の長文が残れば O(N) の再解決も残り、item と group に同じ推定値を使う現実装では最頻値が複数列の行高に適切とは限らない。平均推定で得た contentSize 誤差・末尾移動・位置の安定性も再検証対象。**A に進むなら phase-4 全体の確定は不要だが、「利用者の論理セクション」と「内部の分割単位」の責務は先に決める**: 列数に合わない分割で不完全な行を作らない / 先頭挿入で分割所属が大量に変わるときの差分更新と位置維持 / sticky ヘッダが内部セクション末尾で止まらず論理セクション全体を覆う (2 段 ID だけでは解けない。最小試作で確認)
- **決定 7 (支持)**: ADR-0006 で無効な過去計測を具体的に指し、handbook から ADR へリンクすればアーカイブ改変なしで誤用を防げる
- **決定 8 (再検討)**: `LargeDataScrollBenchmark.kt` には相対 10% の判定が無い (計測と生存確認のみ。比較は人が結果を突き合わせている)。「唯一の自動ゲート」という前提が不正確。公式の `FrameTimingMetric` には `frameCount` があるので、**同じ計測区間の結果 (JSON) を事後検証する案**を優先する。gfxinfo を使うなら試行間リセット・対象 window・取得失敗の定義とスクロール到達の確認が要る
- **反対案**: 「規約改訂 → エンジン修正」の直列 2 change。新手順を先に確定できるので必ず相互待ちになるわけではない。ただし同梱のオーナー判断を覆すほどの理由は無い。C・D や phase-4 の公開契約が必要になった時点を分割・ロードマップ化の再訪条件にする
- **見落とし**: Android の 3,941 フレームを「ほぼ毎 vsync」と書くには記録窓の実長 (reset と取得の時刻差) を確かめる (60 Hz × 60 秒 = 3,600 を超えているので窓は約 66 秒)。「thermal override なし」は熱制限なしと同義ではない。自動駆動を外しても計測器の負荷は残るので、体感と数値が食い違うときの非接続の対照手順が要る。`prefetch-display-size` は体感以外に同期縮小と `allowHardware(false)` 回避の独立した動機があり、本 change の体感合格でその課題が解消した扱いにはできない

## 決定事項

探索 (2026-09-08、prefetch-display-size との順序決めから開始):

- **順序**: `prefetch-display-size` とは統合せず、本 change を先に進める。prefetch の完了条件が実機計測なので、基準が壊れたまま実装すると image-loading と同じ「計測して基準に合わず deviation」を再演するため。大量件数 (108〜136 ms/s) の原因究明も別 change に切り出さず本 change で扱う。前提条件からゼロベースで見直す
- **論点 1 (基準の目的)**: 完了判定が保証するのは「基準機でその種類の画面をフリックしてもカクつきを感じないこと」(利用者体感)。foundation 時点の実測値への退行検出はゲートにせず、同一 fixture の前回証跡との比較を記録するに留める。Android の相対基準 (ラッパーの薄さ) は目的が別なので別系統として残す
- **論点 2 (計測の足場)**: オーナーが基準機を手動でフリックして合否を下す。操作中に計測器 (Instruments / Perfetto 等) をプロセス指定で接続し、数値は証跡 (合否の説明と次回との比較材料) として残す。worker はビルド・接続・trace 回収・証跡記述を担う。**記録の開始はオーナーの「準備できた」の合図を待ってから** (2026-09-08 の Android 計測で、起動と同時に記録を始めたため 1 回目の窓が空振りした。準備 → 合図待ち → 記録開始 → 開始と記録時間を伝える、の順を handbook の手順に書く)。自動駆動は CI の受け皿ができた時点で再訪
- **論点 3・4 (証跡に残す数値と参考スケール)**: 合格線は置かない。iOS は Instruments で操作全体の hitch time ratio・hitch 件数・最長 hitch・主スレッドの帰属を残し、Apple の目安 (5 ms/s 以下 Good / 5〜10 Warning / 10 以上 Critical) を参考として添える。手動操作は 10 秒以上を目安。Android は frameOverrunMs の P50 / P90 / P99・期限超過フレームの割合・描画フレーム数を残し、公式の出所が無いので参考スケールは添えない。**Android の絶対基準 (P99 0.0 ms 以下) は廃止**。相対基準 (素の Compose に対する薄さ、Macrobenchmark、10%) は目的が別なので現状維持 (自動駆動の汚染は両側に等しく乗る)。参考スケールを合否に読み替えないことを規約に明記する
- **論点 5 (fixture)**: スクロール性能の fixture は機能ごとの Sample デモ画面そのもの (エンジンの土台に触る変更は「大量件数」、機能の変更はその機能のデモ画面、両方に触るなら両方。セクション・ページングも各デモ画面が fixture になる)。**件数は 10,000 件のまま保持** (当初「2,000 件に統一」と決めたが、論点 6 で主因が「セクション内の件数に比例する solver の費用」と分かり、件数を減らすと問題が隠れるためオーナーが 2026-09-08 に改めた)。メモリの自動往復は足場の問題が無いので手順・件数とも維持。**「1,000 件と 10,000 件の定常値が件数比に比例しない」系統は廃止**し、仮想化の証明はテンプレート呼び出しカウンタ (Android) と 2,000 件の自動テスト (iOS、同時生存セルが可視の 4 倍未満) に任せる。ADR は分けず ADR-0006 の帰結に書く
- **論点 6 (大量件数の原因)**: 分岐は「体感 NG = エンジンの土台の問題」。cross/ADR-0006 の手順を初適用した手動計測 (iPhone 11、`evidence/manual-largeData-ios-2026-09-08.md`) で、自動化なしでも hitch time ratio 638 ms/s・描画 7〜15 回/秒の秒が多く、体感は「初めて通る部分は少し重い / 連続すると重くなる / 止めると戻る / 操作のたびにムラ」。**主因は compositional layout の estimated 高さの solver** (`_UICollectionLayoutSectionEstimatedSolver` が主スレッドの 55%、うち offsets 再構築 16%)。新しく可視になったセルが preferred size を返すたびに 1 セクション 10,000 件の解決が走り、解決済みの範囲では走らない。hosting (SwiftUI) の計測は 7.5% で `UIHostingConfiguration` 方式は主因ではない。熱状態は Nominal。エンジン修正は本 change に含める (別 change に切らない)。対策の候補は scout の調査 (2026-09-08) より:

  | 候補 | 効果の見込み | コスト | ADR / 概念との関係 |
  |---|---|---|---|
  | A. セクションを内部で N 分割 (200〜500 件/塊) | 高 (推測。solver の費用がセクション内件数に比例するなら線形に減る。比例の裏は未取得) | 中〜大 (`KsSectionID` の複数化、snapshot の塊分け、先頭行の区切り線判定、sectionProvider の余白・ヘッダの index 条件、phase-4 の利用者セクションとの 2 段 ID) | ios/ADR-0003 とは非衝突。phase-4 の設計と座を取り合う |
  | B. 推定値を平均から最頻値に寄せ、多数派の行で preferred == estimated にして invalidation を消す | 中〜高だが未検証 (UIKit が一致時に再解決しない前提が未確認、pt 単位一致が要る) | 小 (`KsEstimatedHeight` のみ) | concepts/ios の「推定高さは実測平均」(contentSize 誤差の理由) と正面衝突 |
  | C. `.absolute` 併用 (テンプレート単位で高さ宣言) | 高 (自己サイズを止めた行は solver を起こさない) | 大 (`.estimated` は item 定義単位で index path 別にできず、DSL の語彙拡張かテンプレート種別ごとのセクション分けが要る) | 公開 DSL の拡張なので core の決定が要る |
  | D. FlowLayout / 完全自前レイアウト (高さを自前キャッシュ) | 高 | 特大 | ios/ADR-0003 と衝突 (改訂が要る) |
  | E. 周辺最適化 (区切り線更新の間引き等) | 低 (profile 上 solver 55% に対し小さい) | 小 | なし |

  追加の材料 (scout 2 本目、2026-09-08): Sample の行は detail の有無で高さが 2 種類あり、コレクション全体で 1 つの平均推定値はどちらの行とも一致しないため、**新規に可視化される全セルが preferred ≠ original を返して solver を起こす**構造 (profile と整合する推論。A/B 実測は未実施)。Apple の文書は `shouldInvalidateLayout(forPreferredLayoutAttributes:withOriginalAttributes:)` で「preferred が original と同じなら invalidate 不要」と明言 (B の前提の出所: developer.apple.com/documentation/uikit/uicollectionviewlayout/1617746-shouldinvalidatelayout)。B の亜種として `KsHostingCell.preferredLayoutAttributesFitting` 側で「推定と一致する行は元の attributes をそのまま返す」抑制も候補。Apple Forums thread/764092 では回避策として「セクション数を絞る」「`.absolute` 固定高」が挙がる。A と「chunk ごとに異なる推定値を渡す」の組み合わせは仕様上可能なはずだが未検証。C は core/ADR-0006 (レイアウト指定は layout 値 1 つ) と DSL の語彙の面でも衝突する
  Web の裏取り: solver の費用が件数に比例するという一次資料や、セクション分割を推奨する出典は見つからず (Apple Forums に「件数が増えるほど全セクションが再計算される」報告 developer.apple.com/forums/thread/764092 と、「推定値の精度を上げると軽減するが解消しない」という Apple の回答 thread/671054 がある)。**効果は実機の A/B 計測で確かめる**。scout の推奨順: B (小コスト) を実験として先に試し、効かなければ A を 200〜500 件の塊で試作して比例性を実測する。**注意: 対策の効果は「件数に比例して増えない形になったか」で見る** (件数を減らせば数字は勝手に良くなる)
- **Android の手動計測 (2026-09-08、Pixel 4a、`evidence/manual-largeData-android-2026-09-08.md`)**: 60 秒で 3,941 フレーム・janky 2 件 (0.05%)・P99 17 ms。体感は「とてもスムーズで引っかかりもムラもない」。文字だけの大量件数では土台の問題は iOS 側だけ。Android の再計測は画像グリッドを対象にする。付随して「Android でスクロールバーが表示されない」(Compose の Lazy 系に標準実装が無く、ライブラリにも無い。パリティの穴) を発見、別 change の候補
- **論点 7 (過去証跡の扱い)**: handbook は合格線と手順を新しい内容に書き換えるだけで、旧基準・旧値への言及は残さない (handbook は今の決まりだけを書く場所)。アーカイブの証跡は触らない。経緯 (foundation の iOS の値が代替機・hitch を検出できない手順だったこと、Android の 0.0 ms が校正値だったこと) は cross/ADR-0006 の Context が持つ。drift の乖離メモも作らない。比較は同じ fixture・同じ手順の前回証跡とだけ行う
- **論点 8 (Android のフレーム数下限)**: Macrobenchmark の役割が相対基準だけになり唯一の自動ゲートになるため、「未判定が緑になる」穴を塞ぐ。試行ごとに計測側から `dumpsys gfxinfo <package>` の「Total frames rendered」を読んで下限を assert する (下限の値は実測から決める。手動計測で gfxinfo がそのまま使えることは確認済み)
- **相談役の助言の採用 (2026-09-08、オーナー確定)**: 決定は覆さず、次の条件を足す。(5) 件数比の系統の代わりに「保持対象 (訪問済み ID・画像・購読・サイズキャッシュ) の寿命・上限と、データ置換 / 画面破棄後の解放」を確認する項目をメモリ系統に置く。入力データ自体の O(N) は分けて扱う。(6) 対策 A を試作する前に「利用者の論理セクション」と「内部の分割単位」の責務を決め、sticky ヘッダが内部分割の末尾で止まらない・列数に合わない分割で不完全な行を作らない・先頭挿入時の所属変化の差分更新と位置維持、の 3 条件を phase-4 の agenda に先に書いて最小試作で確かめる。B の実験は先行してよい。(8) フレーム数下限は gfxinfo ではなく Macrobenchmark の結果 JSON の `frameCount` を事後検証するスクリプトで判定し、相対 10% の突き合わせ (現状は人手) も同じスクリプトに載せる。加えて提案では「体感の合否」「計測の成立」「対策の検証」を別々の完了条件にし、証跡に操作条件を残して体感を数値の前に記録する。訂正 (WWDC20 の出所・Android の指標の取得源と単位・記録窓の実長・熱状態の表現) は提案の清書で直す
- **画像グリッドの手動計測 (2026-09-08、両基準機、`evidence/manual-imageGrid-*.md`)**: iOS は体感「常にスムーズ、初回と再訪で差なし」、**solver は 75 秒で 0%** (正方形セルで推定と実測が一致するため。対策 B の決定的な対照)。残る費用はセル生成 44% と hosting 30% で、最速の連続フリック区間だけ 2 フレーム落ちが集中。Android は体感「スクロールはスムーズ」で滑らかさは合格だが、gfxinfo は 20 ms の山と janky 2.14% (数値と主観の不一致の実例)。画像の表示待ち (止めて少し待つと揃う) は体感不良で、`prefetch-display-size` に観測として引き継いだ。**体感ゲートは「滑らかさ」を判定するもので、画像の表示待ちは別の観測点** — handbook の書き直しで観測点を分けて書く
- 今の基準の正体 (ゼロベースの出発点): iOS 5 ms/s は Apple の Animation Hitches の目安を 3 秒窓に当てたもので「1 フレームも落とさない」と同値、基準機での有効な値は未存在。Android 0.0 ms は foundation の文字だけのグリッドの実測に合わせた退行検出線で体感の閾値ではない。10,000 件は仮想化・メモリ用の件数でスクロールの滑らかさとは無関係

## 変更級の推奨: L

理由:
- 触る能力が多い: 性能検証規約 2 本 (handbook/ios・android) の全面書き換え、Android の計測モジュール (絶対基準の削除・フレーム数下限の追加)、iOS エンジンの estimated solver 対策 (B → A の順で A/B 計測。A なら `KsSectionID`・snapshot・区切り線判定・sectionProvider に及ぶ)、両プラットフォームの再計測 (iOS: 大量件数 + 画像グリッド、Android: 画像グリッド)

- 公開 API 変更: 無し (対策 C を採る場合のみ DSL の語彙が増えるが、初手では採らない)
- UI: 無し (Sample の画面は変えない)

1 change に収める理由: 規約の書き換えと iOS の対策は「体感ゲートで合格する土台」を作る同じ目的で、対策の効果測定に新しい手順を使うため切り離すと相互に待ちが生じる。オーナー判断 (2026-09-08) でも別 change に切り出さないと決めた。
