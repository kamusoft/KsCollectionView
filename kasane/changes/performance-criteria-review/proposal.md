# Proposal: performance-criteria-review

## Why

スクロール性能の完了判定が「壊れた基準」で行われ、新機能を足すたびに不合格が deviation に残る構造になっていた。iOS の合格線 (3 秒窓で hitch time ratio 5 ms/s 未満) は「1 フレームも落とさない」と同値で、基準機で有効に測った値は一度も存在しない。Android の合格線 (`frameOverrunMs` P99 0.0 ms 以下) は foundation 時点の文字だけのグリッドの実測に合わせた退行検出線で、画像グリッドでは到達点 disk でも満たせない。さらに自動駆動 (XCUITest) が主スレッドの 20〜37% を占め、体感を測る土俵そのものを汚していた。

探索 (2026-09-08) で基準の目的を「基準機で、その種類の画面をフリックしてもカクつきを感じないこと」(利用者体感) に定め直し、オーナーの手動フリックを合否に、計測器の数値を証跡にする方針を cross/ADR-0006 (proposed) として起票した。この手順を初めて適用した実機計測で、iOS の「大量件数」(文字だけ・10,000 件) は体感不合格で、主因は compositional layout の estimated 高さの solver (新しく可視になるセルが preferred size を返すたびに 1 セクション 10,000 件を再解決。主スレッドの 55%) と判明した。画像グリッド (正方形セル) では推定と実測が一致して solver が一度も走らず、体感も合格だった。Android は文字グリッド・画像グリッドとも滑らかさは体感合格。

## What Changes

1. **性能検証規約の全面書き換え** (`handbook/ios/performance-verification.md` / `handbook/android/performance-verification.md`): 合否はオーナーの体感、数値は証跡。合格線は置かず、参考スケール (WWDC20 の hitch time ratio の推奨値) は合否に読み替えないと明記。fixture は機能ごとの Sample デモ画面 (件数 10,000 は据え置き)。手順は「準備 → オーナーの合図 → 記録開始 → 固定の操作列 → 回収」で、記録の開始は合図を待つ。判定は合格 / 不合格 / 未判定の 3 状態で、迷いや数値との食い違いは非接続の対照で再確認する。証跡には操作条件を残し、体感は数値を見る前に記録する。メモリの「件数比」系統を廃止し、項目単位の保持 (セル・ホスティング・コンポジション) の解放の確認に差し替える。画像の表示待ちは滑らかさとは別の観測点として書き分ける。旧基準・旧値には言及しない
2. **iOS エンジンの estimated 高さの solver 対策** (能力: collection-layout): 推定高さを直近の実測の最頻値にし、推定と同じ高さに測られたセルの自己サイズがレイアウトを無効化しないようにする (**最頻値化**)。効果は事前に固定した数値基準 (不一致率・件数比例・合計高さの見積もり) と体感で判定する。不合格なら実装を止め、内部セクション分割の Requirement を提案に追加して再レビューしてから進む (design Decision 3)。その前提 (論理セクションと内部分割の責務、sticky ヘッダ・不完全行・先頭挿入の 3 条件) は phase-4 の agenda に先に書く
3. **Android 計測モジュールの整理** (能力: samples): 絶対基準 (P99 0.0 ms 以下) の廃止、相対基準 (素の Compose に対する劣化 10% 以内) の判定と描画フレーム数の下限 (固定値) を、Macrobenchmark の結果 JSON を事後検証するスクリプトに載せる (現状は人が突き合わせている。不合格・未判定・入力不正は非 0 終了)。比較対象にライブラリの既定機能を付ける条件は維持する。1,000 件の件数比の試行を廃止する
4. **iOS 計測ドライバの整理** (能力: samples): 自動フリックの UI テスト 2 本は CI 再訪まで使わないため退役し、メモリの自動往復 (Simulator の計測 launch 経路) は維持する
5. **再計測と証跡**: 対策後に iOS「大量件数」「画像グリッド」を新手順で計測し、Android「画像グリッド」の証跡も新手順の形式に揃える。「体感の合否」「計測の成立」「対策の検証」を別々の完了条件にする
6. **ADR の確定準備**: cross/ADR-0006 を実装後の視点で見直す (accepted への昇格は蒸留時)。内部セクション分割を採った場合は ADR 候補として捕捉する

影響する能力: collection-layout (iOS の自己サイズと推定高さ)、collection-core (保持対象の寿命)、samples (計測モジュール・計測ドライバ)。

## Non-Goals

- **画像の表示待ち (Android で止めてから画像が揃うまでのテンポ)**: 滑らかさとは別の軸で、到達点 memory の方式変更が要る。`prefetch-display-size` の責務 (観測は引き継ぎ済み)
- **Android のスクロールバー非表示**: パリティの穴で性能と無関係。`android-scrollbar-parity` に起票済み
- **`.absolute` 併用と自前レイアウトへの切替**: 前者は DSL の語彙拡張 (core/ADR-0006 と衝突)、後者は ios/ADR-0003 の改訂が要る。最頻値化 / 内部セクション分割で足りない場合の再訪条件として残す
- **内部セクション分割の仕様**: 最頻値化で不合格だった場合に提案の改訂として追加する (今は書かない)
- **iOS の区切り線・タッチ色の毎レイアウト更新の無駄**: 周辺最適化 (profile 上は solver に比べ小さい)。`ios-separator-update-guard` の責務
- **CI での自動駆動**: 実機の受け皿ができた時点で再訪 (cross/ADR-0006)
- **phase-4 (セクション / グループ化) の設計そのもの**: 内部セクション分割の前提 3 条件を agenda に書くに留める
- **concepts の追随** (collection-engine の「推定高さは実測平均」、image-loading / compose-wrapper の「規約の見直し待ち」): 蒸留 (ksn-distill) で行う

## Impact

- 破壊的変更: 公開 API には無し。Sample の画面・件数も変えない
- 規約の変更: 性能検証規約 2 本が全面的に置き換わる。以後のフェーズ (セクション・ページング) の完了判定にはオーナーの手動操作が要る
- iOS エンジン: 推定高さの決め方が変わる (平均 → 一致を狙う値)。concepts の「推定高さは実測平均」(初回表示のコンテンツ高さの誤差 −27% → 0%、末尾へのスクロール中の contentSize 変化 25 回 → 1 回) の効果を損ねないことを再検証する。行の高さが 3 種類以上混在する画面では最頻値化の効果が限定的で、内部セクション分割に進む可能性がある (変更級 L の理由)
- Android: 計測モジュールのコード変更は事後検証スクリプトの追加と件数比の試行の削除に留まる。ライブラリ本体は変えない
- リスク: 体感ゲートはオーナー 1 人の主観に依存する。固定の操作列・3 状態の判定・非接続の対照で再現性を補い、証跡の操作条件と数値で「比較不能」を明示する

## 級: L

規約 2 本の全面書き換え + iOS エンジンの solver 対策 (内部セクション分割に進めば `KsSectionID`・snapshot・区切り線判定・sectionProvider に及ぶ) + 両プラットフォームの計測モジュールと再計測。完了判定のゲートを変える不可逆性が高い。
