# UI Brief: paging-indicator-color

## 画面と状態

対象は両プラットフォームのデモ画面「ページング」。画面の構造・操作のパネル・失敗 / 終端 / 空の表示は `paging-state-machine` で承認済みのまま変えない。変えるのは、ライブラリが出す読み込み中の表示 3 つの色だけである。

- 構造 (変更なし): ナビゲーション → 全画面の一覧 → その上に浮いた操作のパネル
- 色が変わる表示と、その表示が出る状態:
  - ① 最初の読み込み中 — 項目が 0 件で、一覧の真ん中に出る
  - ② 次のページの読み込み中 — 項目があり、見えている範囲の下端に重なって出る
  - ③ Pull to Refresh のインジケータ — 先頭で引っ張って取り直している間に出る。iOS はバーのすぐ下のくるくる、Android は丸い下地の上の矢印
- 3 つとも同じ色で出す。Android の ③ は矢印だけがその色になり、丸い下地はテーマの色のまま
- 外観 (ライト / ダーク) のそれぞれで、選んだ外観の配色の色になる
- 一覧に渡す配置の入力 (余白・安全領域の扱い) は変えない (handbook/cross/sample-debug-controls)

mock で決めないもの: 3 つの表示の形・大きさ・動き・位置。各プラットフォームの標準の部品と、`paging-state-machine` で決めた置き場のままで、mock の絵は近似である。mock と照合するのは色だけにする。

## デザイントークン参照

concepts/ に UI トークンは未登録。Sample 共通の配色 `SampleTheme` (ライト / ダークの 2 組、両プラットフォーム同値 — cross/ADR-0007) を使う。

- 読み込み中の表示の色: 既存のトークン「テキスト副」(`SampleTheme` の `secondaryText`) を、両プラットフォームで同じ名前で参照する。新しいトークンは足さない
- 下地・行・区切り線・アクセント・操作のパネル: 既存のトークンのまま

視認性の基準: 読み込み中の表示の色は、その表示が重なる 2 つの面 (下地の色・行の色) のどちらに対しても、ライト / ダークの両方でコントラスト比 3 以上とする (文字ではない部品の基準)。テキスト副は 4 つの組み合わせすべてで基準を満たす (計算で確認、2026-10-04)。

Android では、Sample の Material のテーマが「補助の色」にテキスト副を、「Pull to Refresh の下地」に行の色を割り当て済みである (`SampleAppTheme.kt`)。そのため Android の ③ は今の見え方 (矢印がテキスト副、下地が行の色) のままで、① ② がアクセントの青からテキスト副に変わる。

## 承認モック

案 A を採用 (`mock/indicator-color-a-secondary-text.html`、ライト / ダークの 2 段を撮った `mock/approved.png`。2026-10-04 オーナー承認)。

案 B (`mock/indicator-color-b-neutral-gray.html` — 前の変更の承認 mock のくるくるの色を、新しいトークンとして足す案) は採らない。ライトの下地の色の上でコントラスト比が基準に届かず、Sample の配色に新しい色を足すことになり、ダークの紺の下地と色みが合わないためである。

approved.png に個人情報が写っていないことを確認した (架空の時刻と「Item N」の行だけ)。

## 合意済み妥協

- iOS の ③ Pull to Refresh のインジケータ: mock では ① ② と同じ濃さのテキスト副、実装は色みがテキスト副で、濃さは色を指定しない標準の Pull to Refresh と同じ (① ② より薄い)。理由: iOS の標準の引っ張りの部品は、渡した色を薄めて描き、公開の手段では濃さを変えられない。標準の部品を保つことを優先し、ライブラリが補正した色を渡す (2026-10-04 オーナー合意)
- iOS・ダークの ③ のコントラスト比: 「視認性の基準」では 3 以上、実装は約 2.9 (最も濃い部分が下地に対して)。理由: 上と同じ (標準の部品の濃さの上限) (2026-10-04 オーナー合意)
- iOS・ライトの ③ のコントラスト比: 「視認性の基準」では 3 以上、実装は約 2.1 (最も濃い部分が下地に対して)。理由: 濃さを標準の Pull to Refresh と同じにすると決めた結果で、標準の部品もライトではこの薄さである (2026-10-04 オーナー合意)

## 照合結果

verification/ の各画像と approved.png を照合し 2026-10-04 最終承認。合意済み妥協は 3 件。

照合した画像は `verification/` の 24 枚 (`<ios|android>-paging-<状態>-<light|dark>.png`) である。照合したのは色だけである。撮影は作業専用に作ったシミュレータ (iPhone 17・iOS 27.0) とエミュレータ (API 36) で行い、終わってから削除した。24 枚に個人情報が写っていないことを確認した (架空の時刻と「Item N」の行だけ)。

読み込み中の表示 3 つ (インジケータの最も濃い部分の色を画像から読んだ値。期待する色はライトがテキスト副のライトの値、ダークがテキスト副のダークの値):

| 表示 (状態の名前) | Android ライト | Android ダーク | iOS ライト | iOS ダーク |
|---|---|---|---|---|
| ① 最初の読み込み中 (`first-loading`) | 一致 (指定した色そのもの) | 一致 (同左) | 一致 (色みが同じ) | 一致 (色みが同じ) |
| ② 次のページの読み込み中 (`appending`) | 一致 (指定した色そのもの) | 一致 (同左) | 一致 (色みが同じ) | 一致 (色みが同じ) |
| ③ Pull to Refresh (`pull-to-refresh`) | 一致 (矢印が指定した色、下地は行の色のまま) | 一致 (同左) | 合意済み妥協のとおり (色みが同じで薄い、コントラスト比 約 2.1) | 合意済み妥協のとおり (色みが同じで薄い、コントラスト比 約 2.9) |

- iOS の ① ② は、標準のくるくるが線ごとに透け方の違う部品のため、最も濃い線でも指定した色の 8 割前後の濃さで出る。色みは指定どおりで、mock と一致と判断した
- iOS の ③ は、ライブラリが補正した色を渡す版で撮り直した。同じ版で ① ② の色と、空の表示・0 件での失敗の表示 (ダーク) が撮り直しの前と変わらないことを確かめた

ほかの表示 (変更前と同じ見え方であること):

- 失敗の表示 (末尾 `failed-footer`・0 件 `failed-placeholder`)・空の表示 (`empty`)・操作のパネル: 色の指定を外した版と画素単位で比べて差が無い (Android はライト / ダーク、iOS はダーク)
- iOS・ライトのほかの表示は、変更後だけを目視で確かめた (変更前の版との比較はしていない)
- 終端の表示は撮っていない。全 10,000 件を読み切らないと出ず、手の操作では到達できないためである。Sample が自分で描く表示で、この変更で変えた箇所を通らない
