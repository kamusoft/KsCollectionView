# Deviation: paging-indicator-color

- Requirement「読み込み中の表示の色」(Scenario: Pull to Refresh のインジケータに効く / ページングを付けない一覧でも効く / 表示中に色を変える): spec では iOS の Pull to Refresh のインジケータも「指定した色で描かれる」 → 指示により、iOS の Pull to Refresh のインジケータは「色みは指定した色、濃さは色を指定しない標準の Pull to Refresh のインジケータと同じ」で描く (差し替えていない 2 つの読み込み中よりは薄い)。ライブラリは標準の引っ張りの部品のまま、OS の描き方を打ち消すように補正した色 (成分ごとの平方根) を渡す。理由: iOS の標準の引っ張りの部品は、渡した色を 2 回掛けた色を最大で約 57% の不透明度で描く (iOS 18.6・27.0 で実測、26.0 も同じ構成。公開の手段では濃さを変えられない)。色をそのまま渡すと指定より暗く薄く出て、Sample のダークでは下地とのコントラスト比が約 1.7 になる。標準の部品を保つこと (core/ADR-0023) を優先し、ライブラリが自前のくるくるを描く案・そのまま受け入れる案は採らない (2026-10-04)
- ui/brief.md「視認性の基準」(コントラスト比 3 以上): brief では 4 つの組み合わせすべてで基準を満たす → 指示により、iOS・ダークの Pull to Refresh のインジケータだけは補正後で約 2.9 (実測 #565F73、下地 #0D1321) となることを受け入れる。理由: 上の行と同じ (標準の部品の濃さの上限) (2026-10-04)
- ui/brief.md「視認性の基準」(コントラスト比 3 以上): brief では 4 つの組み合わせすべてで基準を満たす → 指示により、iOS・ライトの Pull to Refresh のインジケータも補正後で約 2.1 (実測 #A8A9AF、下地 #F2F2F7) となることを受け入れる。理由: 濃さを標準の Pull to Refresh と同じにすると決めた結果で、標準の部品もライトではこの薄さで出る (実測 #A5A5AA) (2026-10-04)
- proposal.md の Impact (Android の引数の互換): proposal では「引数を位置で渡している既存の呼び出しもそのままコンパイルできる」 → 指示により、一覧の中身のブロック (`content`) まで含めて全引数を括弧の中に位置で並べて渡す呼び出しだけは、`loadingIndicatorColor` を足したことでコンパイルできなくなることを受け入れる (中身のブロックを括弧の外に書く呼び出し・名前で渡す呼び出しは壊れない)。互換用の別の入口 (オーバーロード) は足さない。理由: 配布前で該当する利用者がいない。ページング・取り直しの処理・並べ替えの引数を足した過去の変更も同じ位置に足していて、互換用の入口は作っていない。入口を足すと公開 API に同じ名前の関数が並ぶ (2026-10-04)
- 蒸留時に反映: concepts・`kasane/concepts/core/core-model/collection-paging.md` — iOS の Pull to Refresh のインジケータは、標準の部品の描き方に合わせて補正した色を渡すため、色みは指定どおり・濃さは標準の Pull to Refresh と同じ (読み込み中の 2 つより薄い) になること。補正は OS の文書に無い描き方 (2 回掛け) に依存し、iOS 16・17 は未確認であること
- 蒸留時に反映: decisions・core/ADR-0035 — accepted に昇格するとき、iOS の Pull to Refresh は標準の部品を保ったまま補正した色を渡すと決めたこと、却下した案 (自前のくるくるを描く / そのまま渡す) を Consequences に足す
