# 利用者向け Skill の追従

この文書は、利用者向け Skill (`skills/`) を、源泉 (`kasane/concepts/`・ビルドの設定・本体の公開の宣言) の変更に追従させるときの流れをまとめる。どの道具をどの順に呼ぶか、出力をどう読むか、どこでオーナーの承認を得るか、記録をいつ更新するかを書く。Skill の文面の書き方は、[利用者向け Skill と README の書き方](user-docs-writing.md) にある。

追従は、オーナーが頼んだときにだけ行う。検証 CI は、Skill が源泉からずれていることを検査しない。前回追従した commit からの差分をもとに直すと決めた理由は、[cross/ADR-0017](../../decisions/cross/0017-user-skill-refresh-on-request-by-commit-diff.md) にある。

## 用意してあるもの

| もの | 場所 | 役割 |
|---|---|---|
| 追従の記録 | `skills/.manifest.json` | 前回追従したときに見た commit の ID (`syncedCommit`)、差分を出す対象のパスと掛かる Skill の 1 枚 (`sources`)、Skill に載せないと決めた公開の宣言の名前 (`apiExclusions`) を持つ。利用者がコピーするのは `skills/{en,ja}/<名前>/` なので、このファイルは利用者の手元に行かない |
| 変わった源泉を出す道具 | `scripts/docs/skills-refresh.py` | `status` (変わった源泉の一覧) と `record` (記録の更新) の 2 つの使い方を持つ |
| 公開の宣言の名前の漏れを出す道具 | `scripts/docs/check-api-coverage.py` | 本体のソースの公開の宣言の名前のうち、Skill に一度も現れないものを出す |
| Skill 自身の整合の検査 | `scripts/ci/check-skills.py` | 英語版と日本語版の一致・frontmatter・Skill の外へのリンク・URL・内部の言葉を確かめる。検証 CI でも、スクリプトのテストを通して毎回流れる |
| README の例の検査 | `scripts/ci/check-readme-examples.py` | README の最小コード例と、README・`SKILL.md` のインストール例を確かめる。検証 CI でも毎回流れる |

道具は、どれも Skill を書き換えない。git の commit・add・push も行わない。`record` だけが、記録のファイルの中の commit の ID を書き換える。

記録の形は、`scripts/docs/skills_manifest.py` の冒頭に書いてある。

## 流れ

1. 変わった源泉を出す
2. 出たものを読んで、Skill を直す (英語版と日本語版を同じ回に)
3. 公開の宣言の名前の漏れを見る
4. 検査を流す
5. コード例を変えたときは、コンパイルして確かめる
6. オーナーの承認を得る
7. 記録を更新する

1 から 5 は、作業ツリーの上で行う。commit は、6 の承認の後に、指揮側かオーナーが行う。

### 1. 変わった源泉を出す

```bash
python3 scripts/docs/skills-refresh.py status
python3 scripts/docs/skills-refresh.py status --diff
```

`status` は、記録の commit から今の作業ツリーまでの間に変わったものを出す。commit していない変更と、まだ追跡していない新しいファイルも数える。`--diff` を付けると、変わった源泉の差分の本文も出す。

| 終了コード | 意味 |
|---|---|
| 0 | 一覧を出した。変わった源泉があっても 0 である |
| 1 | 失敗した。一覧は出ない。記録の commit が手元の履歴に無い (浅い取得・別のリポジトリ)、記録を読めない、のどちらか。理由は標準エラー出力に出る |
| 2 | 引数の誤り |

終了コードは、変わった源泉の有無を表さない。出力を読む。

### 2. 出たものを読んで、Skill を直す

`status` は、次の 5 つを分けて出す。

| 出るもの | 意味 | すること |
|---|---|---|
| 変わった源泉 | 記録の `sources` にあるパスの内容が変わった。掛かる Skill の 1 枚が添えてある | `--diff` の差分を読み、添えてある 1 枚の該当の場所を直す。片方のプラットフォームの Skill にだけ掛かる源泉は、そう添えてある。差分が利用者に見える内容を変えていなければ、Skill は直さなくてよい (直さなかった源泉と理由を、作業の報告に書く) |
| 対応の決まっていない源泉 | `kasane/concepts/` の下に、記録に無い概念の文書がある | 記録の `sources` に、掛かる 1 枚 (`pages`) か、掛からない理由 (`excluded`) のどちらかを足す。どの 1 枚に掛かるかは、[利用者向け Skill と README の書き方](user-docs-writing.md) の 5 枚の分け方で決める |
| 名前の変わった源泉 | 記録にあるパスが無くなり、前の内容と半分以上が同じ文書が、対応の決まっていない文書の中にある。前の名前と今の名前が出る | 記録の `path` を今の名前に直す。内容も変わっていれば、変わった源泉と同じに扱う |
| 無くなった源泉 | 記録にあるパスが無くなり、名前の変わった先も見つからない | 源泉が消された理由を確かめる。Skill の該当の記述を消すか残すかを決め、記録からその項目を消す |
| 公開の宣言の増減 | 本体のソースの公開の宣言の行が、足された・消えた | 足された宣言は、Skill のどこに載せるかを決める。消えた宣言は、Skill に残っている名前とコード例を消す。1 行の宣言の引数や型を変えると、前の行が消えた行、今の行が足された行として出るので、Skill のコード例と説明を新しい形に合わせる |

直すときに守ることは、[利用者向け Skill と README の書き方](user-docs-writing.md) にまとめてある。特に次の 2 つは、追従で外しやすい。

- 英語版と日本語版を、同じ回に直す。片方だけを直すと、検査が落ちるか、落ちない形でずれる (本文だけの直しは、検査が見ない)
- 源泉の文書に書いてあっても、Skill に書く前に、本体のコードで確かめる

### 3. 公開の宣言の名前の漏れを見る

```bash
python3 scripts/docs/check-api-coverage.py
python3 scripts/docs/check-api-coverage.py --list
```

各プラットフォームのソースから公開の宣言の名前を拾い、そのプラットフォームの Skill の英語版と日本語版のそれぞれに、一度も現れない名前を漏れとして出す。`--list` は、拾った名前の一覧も出す。

| 終了コード | 意味 |
|---|---|
| 0 | 漏れが無い。古い項目 (外す一覧にあるのに、宣言が無くなった名前) だけがあるときも 0 で、出力には出る |
| 1 | 漏れがある |
| 2 | 引数の誤り |
| 3 | 確かめられなかった (公開の宣言を 1 つも拾えない・Skill が無い・記録を読めない)。漏れが 0 件とは出ない |

| 出たもの | すること |
|---|---|
| 漏れ (利用者が使う名前) | その機能を説明している 1 枚に、名前を足す。英語版と日本語版の両方に足す |
| 漏れ (利用者向けでない名前) | 候補の一覧にして、オーナーに諮る。載せないと決まった名前と理由を、記録の `apiExclusions` に書く。書いた名前は、次から報告されない |
| 古い項目 | 記録の `apiExclusions` から、その項目を消す |

載せるか外すかの基準は、[利用者向け Skill と README の書き方](user-docs-writing.md) の「公開の宣言の名前」にある。

今の一覧: 【蒸留のときに、`apiExclusions` の実物に合わせて書く。書いた時点では空で、iOS の 2 つの名前をオーナーに諮っている】

### 4. 検査を流す

```bash
python3 scripts/ci/check-skills.py .
python3 scripts/ci/check-readme-examples.py .
python3 scripts/ci/run-tests.py
python3 scripts/local-path-lint.py
python3 scripts/identity-lint.py
python3 scripts/comment-policy-lint.py
```

- 上の 2 本は、違反が無ければ終了コード 0 で終わる。違反は「ファイル: 内容」の形で出る
- スクリプトのテストは、2026-10-10 時点で 504 件。上の 2 本の検査を今のリポジトリに流すテストを含むので、これが通れば、検証 CI の lint も通る ([検証 CI](verification-ci.md))
- 追従の道具そのもの (`scripts/docs/`) を変えたときも、スクリプトのテストを流す。道具のテストは `scripts/ci/tests/` にある

### 5. コード例を変えたときは、コンパイルして確かめる

Skill の `references/` のコード例は、どの検査もビルドしない。コードブロックか、本文の中の 1 行の断片を変えた・足したときは、リポジトリの外の作業用の置き場でコンパイルして確かめる。やり方は、[利用者向け Skill と README の書き方](user-docs-writing.md) の「コード例を確かめる」にある。

`SKILL.md` の最小の動く例は、利用者役の画面のファイルと同じ内容である。利用者役の画面を変えたときは、README の最小コード例と、4 つの `SKILL.md` を同時に直す ([利用者の立場のビルドの確認](consumer-build-check.md))。README の直し漏れは検査が見つけるが、`SKILL.md` の直し漏れは検査が見ないので、`status` の「変わった源泉」に利用者役の画面のファイルが出たら、必ず見る。

### 6. オーナーの承認を得る

直した Skill をオーナーに見せて、承認を得る。見せるものは次のとおり。

- `status` が出した一覧と、それぞれをどう扱ったか (直した場所・直さなかった理由)
- 公開の宣言の名前の漏れの結果と、外す候補 (あれば)
- 流した検査と結果
- コードで確かめられなかったこと (書かなかったことと、その理由)

### 7. 記録を更新する

```bash
python3 scripts/docs/skills-refresh.py record
python3 scripts/docs/skills-refresh.py record <commit>
```

`record` は、記録の `syncedCommit` を、渡した commit (渡さなければ今の先頭の commit) に書き換える。書き換えるのは、記録のファイルの中のこの ID だけである。

| 終了コード | 意味 |
|---|---|
| 0 | 記録を書き換えた |
| 1 | 書き換えなかった。渡した commit が手元の履歴に無い、または、対象のパスに commit していない変更がある。理由は標準エラー出力に出る |
| 2 | 引数の誤り |

**`record` は、源泉の変更が commit された後に流す。** 対象のパス (記録の `sources` のパスと、`kasane/concepts/` の下の概念の文書) に、commit していない変更や、追跡していない新しいファイルがあると、`record` は書き換えずに失敗で終わる。記録する commit に入っていない変更が、追従済みの扱いになるのを防ぐためである。

- 記録する commit は、追従のときに見た源泉の状態を持つ commit にする。追従の途中で源泉がさらに変わったときは、`status` を流し直してから記録する
- `record` は commit を作らない。`record` の後に、直した Skill と記録のファイルを、指揮側かオーナーが commit する (Skill の直しを先に commit してから `record` を流し、記録だけを続けて commit してもよい)
- `syncedCommit` を手で書き換えない。初回の制作では、利用者役の画面のファイルがまだ commit されていなかったので `record` が失敗し、仮に手で値を入れた。手で入れた値は、対象のパスに未 commit の変更が無いことを誰も確かめていない

## 初回と同じ確かめ方をする場面

初回の制作では、オーナーの検収の前に、配った先を再現した確認を行った。Skill の 1 ディレクトリだけをコピーした空の作業用の置き場で、リポジトリを知らない新しいエージェントに、読ませる (分からない言葉・足りない説明を挙げさせる) ことと、使わせる (課題の画面を Skill だけを頼りに書かせ、利用者役と同じ形でビルドする) ことである。リポジトリの中で読むレビューでは、Skill の外の知識で補って読めてしまい、欠けに気付けない。

追従では、変えた量で決める。

| 追従で変えたもの | 読ませる確認 | 使わせる確認 |
|---|---|---|
| 文の直し・約束ごとの箇条の追加・1 行の断片の追加 | しない | しない (断片はコンパイルして確かめる) |
| 1 枚の中に、見出しを足した・コードブロックを足した / 書き直した | 変えた 1 枚を持つ Skill を、変えた言語ごとに 1 回 | その 1 枚に当たる課題を、変えたプラットフォームで 1 回 |
| 1 枚を新しく足した・1 枚を大きく書き直した・`SKILL.md` の構成を変えた | 4 回 (2 つの Skill × 2 言語) | 5 つの課題 × 変えたプラットフォーム |
| 新しい機能 (公開 API の追加) を載せた | 載せた 1 枚を持つ Skill を、言語ごとに 1 回 | その機能を使う課題を 1 つ作り、両プラットフォームで 1 回ずつ |

進め方:

- 回ごとに、空の作業用の置き場 (リポジトリの外) を作り、Skill の 1 ディレクトリだけを写す。エージェントには、リポジトリのパスも、ほかの文書も渡さない
- 使わせる確認は、英語版で行う。コードブロックは英日で同じなので、ビルドで確かめられる内容は変わらない
- 使わせる確認では、課題と一緒に、利用者役とつなぐための条件を渡す: 画面の名前は `ItemListScreen`・引数を取らない・1 つのファイルに収める・Android は package の宣言を書かない・Android のモジュールは Material に依存していない。これはライブラリの知識ではなく、ビルドの入口とつなぐための条件である
- 書かれたファイルは、本リポジトリの作業ツリーを写した作業用の写し (使い捨ての git のリポジトリ) の中で、利用者役の画面と入れ替えて、確認のスクリプトを `local` で流す。本リポジトリの利用者役は入れ替えない
- Android の作業用の写しには、SDK の場所を書いた設定ファイル (`local.properties`。git の管理の外) を 3 つ足す (`android/`・`samples/android/`・`verification/android/`)。足さないと、画面のファイルをコンパイルする前の、本体の発行で止まる
- ビルドが落ちたら、原因を仕分ける。Skill に書かれていない・誤っているのなら Skill を直してやり直す。Skill に正しく書いてあるのにエージェントが違う書き方をしたのなら、書き損じとして記録し、1 回だけやり直す。ライブラリの側の不足や不具合は、追従では直さず、オーナーに諮る
- ビルドが通った回でも、エージェントに「推測が要ったところ」を挙げさせる。初回の制作では、10 回のすべてがビルドに通った上で、8 件の分かりにくいところが挙がった
- 確かめられるのは、書かれた画面がビルドできることまでである。起動して動きを見てはいない

回数・課題・渡した条件・結果・仕分けは、追従を行った変更の証跡に残す。初回の記録は、`kasane/changes/archive/` の下の変更 `user-docs` の `evidence/` (`dist-read-dispositions.md`・`dist-use.md`) にある。

## 道具の拾い方の限界と、人が本体の差分を見る場面

道具は、文法を解かずに、宣言の行を 1 行ずつ拾う。拾い方の細部は、`scripts/docs/public_api.py` の冒頭に書いてある。次の変更は、道具に現れない。

| 道具に現れない変更 | 人がすること |
|---|---|
| 複数行にわたる宣言の、続きの行だけを変えた (引数の追加・削除・型や既定値の変更)。`KsCollectionView` の初期化と modifier、Android の `KsPaging` などのコンストラクタが当たる | 記録の commit からの、本体の公開の型のファイルの差分を、目で見る (下のコマンド) |
| 宣言は変えずに、挙動だけを変えた (既定の色・呼ばれる時点・不正入力の扱いなど) | 源泉の概念の文書が同時に直されていれば、「変わった源泉」に出る。蒸留を通さずに直した変更 (hotfix) は出ないので、記録の commit からの commit の一覧を読む |
| 公開の宣言のコメントだけを変えた | コメントが利用者への約束を変えていないかを、差分で見る |
| 初期化の宣言 (名前を持たない) の追加 | 行としては増減に出るが、名前の漏れには出ない。Skill に載っている呼び方を、差分と見比べる |
| 短い一般の言葉と同じ名前 (`end`・`all`・`key`・`body` など) の漏れ | 名前は、Skill の文面のどこかに同じ字面で現れれば、載っていると数える。英語の本文の同じ言葉でも現れたことになるので、こういう名前を足した・変えたときは、Skill のコードの中に現れることを目で確かめる |
| 利用者役・README・Skill の索引の変更 | README と `SKILL.md` の例は検査が見る。索引 (`skills/README.md`・`skills/README_ja.md`) は、Skill を足した・名前を変えたときに、手で直す |

本体の差分を見るコマンド (`<記録の commit>` は、`status` の出力の 1 行目にある):

```bash
git log --oneline <記録の commit>..HEAD -- ios/Sources android/kscollectionview/src/main
git diff <記録の commit> -- ios/Sources android/kscollectionview/src/main
```

次のときは、`status` の出力にかかわらず、本体の差分を見る。

- 公開の型のファイルを変えた変更が、記録の commit の後にある
- 蒸留を通さずに本体を直した変更がある
- 依存しているライブラリ (画像ローダー・Compose) の版を上げた。Skill が、依存しているライブラリの動きに頼って書いている箇所がある

## 追従で直さないもの

- インストール例の版。例には `{version}` を置いていて、リリースのたびに書き換えない ([cross/ADR-0018](../../decisions/cross/0018-install-examples-without-concrete-version.md))
- 最新の版の確かめ先の URL。変えるのは、リリースの工程が別の場所に決めたときだけで、例のある 6 か所 (README の 2 枚と 4 つの `SKILL.md`) と、許可する URL の一覧 (`scripts/ci/user-docs-rules.json`) を同時に直す
- ライブラリの公開 API と挙動。追従の途中で不足や不具合を見つけたら、直さずにオーナーに諮る
