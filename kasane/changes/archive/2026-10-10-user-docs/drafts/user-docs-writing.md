# 利用者向け Skill と README の書き方

この文書は、利用者向けの文書 (`skills/` の Agent Skill と、ルートの `README.md`・`README_ja.md`) を書く・直すときに守ることを定める。源泉が変わったときに Skill を追従させる流れは、[利用者向け Skill の追従](user-skill-refresh.md) にある。

利用者向けの文書をこの 2 つで提供すると決めた理由は、[cross/ADR-0005](../../decisions/cross/0005-user-docs-as-agent-skills-and-root-readme.md) にある。Skill の主な読み手は、利用者の手元の AI エージェントである。エージェントの手元には、Skill の 1 ディレクトリしか無い。この文書の決まりの多くは、その前提から出ている。

守れたかどうかの一部は、検査が確かめる (`scripts/ci/check-skills.py`・`scripts/ci/check-readme-examples.py`。検証 CI でも毎回流れる)。各節の終わりに、検査が見るものと、見ないものを分けて書く。

## 構成

### Skill

```
skills/
├── README.md / README_ja.md          索引
├── .manifest.json                    追従の記録
└── {en,ja}/kscollectionview-{ios,android}/
    ├── SKILL.md
    └── references/
        ├── basics.md                 一覧を出す
        ├── layout.md                 並べ方と見た目
        ├── paging.md                 ページングと Pull to Refresh
        ├── reorder.md                並べ替え
        └── images.md                 画像
```

- 4 つの Skill のディレクトリは、同じ 6 枚を持つ。ファイルを足す・名前を変えるときは、4 つに同じ変更をする
- `references/` は、利用者のやりたいことで 5 枚に分ける。源泉の概念の文書の分け方には合わせない。新しい機能は、今の 5 枚のどれかに入れる。どれにも入らないときだけ、1 枚を足す (足したら、`SKILL.md` の表と一覧・Skill の索引・追従の記録の `sources` を同時に直す)
- `SKILL.md` の節は、順に 5 つ: 何のライブラリか (見出しの直下の 1 段落)・できること (やりたいことから `references/` の 1 枚への表)・導入・最小の動く例・`references/` の一覧
- `SKILL.md` の冒頭の 1 段落だけを読んで、これが何のライブラリかが分かるように書く
- `references/` の各 1 枚は、やりたいことを見出しにして、動くコードと約束ごとを並べる
- `SKILL.md` の frontmatter は、`name` (ディレクトリの名前と同じ)・`description`・`license` (`MIT`)・`metadata.language` (`en` か `ja`)・`metadata.source` (本リポジトリの URL) の 5 項目だけにする
- **frontmatter の値は、項目ごとに 1 行で書く** (検査は、複数行の値と折り返しを読めず、違反にする)。日本語版の `description` は、日本語の本文に英語のキーワードを添える
- iOS の Skill と Android の Skill の見出しは、同じ機能なら同じ言い方にする。違えてよいのは、プラットフォームの固有の名前 (読み上げの機能の名前・画像ローダーの名前) と、片方にしか無い手順の節だけである

### README

ルートの README は、英日とも次の 9 つの節 (深さ 2 の見出し) を、この順で持つ。見出しの文面は、スクリプトのテストが持つ一覧と同じにする。

| 順 | `README.md` | `README_ja.md` |
|---|---|---|
| 1 | Overview and key features | 概要と特徴 |
| 2 | Screenshots | スクリーンショット |
| 3 | Supported platforms | 対応プラットフォーム |
| 4 | Installation | インストール |
| 5 | Minimal code examples | 最小コード例 |
| 6 | Skills | Skill |
| 7 | Repository structure | リポジトリ構成 |
| 8 | Contributing | 貢献 |
| 9 | License | ライセンス |

- **最小コード例の節の見出しの文面 (`Minimal code examples`・`最小コード例`) を変えない。** 検査は、この文面で節を見つける。変えるときは、検査 (`scripts/ci/check-readme-examples.py`) とテストの一覧を同時に直す
- Skill への導線の節は、自分の言語の 2 つの `SKILL.md` と、自分の言語の索引だけを指す
- 対応プラットフォームの表の値は、ビルドの設定 (`ios/Package.swift`・`android/gradle/libs.versions.toml`・`android/kscollectionview/build.gradle.kts`) から拾う。Android は、利用者に求める下限と、ライブラリのビルドに使った版を分けて書く。覚えている値で書かない

検査が見るもの: 4 つの Skill のファイルの集合が英日で同じこと・frontmatter の 5 項目・README の 9 つの節の並び・導線のリンクの先の実在。
検査が見ないもの: 4 つの Skill が同じ 6 枚であること (iOS と Android の間)・`SKILL.md` の節の並び・対応プラットフォームの値が今のビルドの設定と合っていること。

## 英語版と日本語版を同じ回に直す

- **1 枚を直すときは、英語版と日本語版を同じ回に直す。** 片方を先に仕上げてから訳さない。新しく書くときも、1 枚ごとに 2 言語を一緒に書く
- 見出しの深さの並びを、英日で同じにする。片方にだけ見出しを足さない
- コードブロックの中身 (言語の名前を含む) と順番を、英日で同じにする
- 本文は、同じ事実を同じ順で書く。片方にだけ注意書きを足さない
- iOS と Android で同じ書き方をしている箇所を直すときは、もう片方のプラットフォームの同じ箇所も見て、当たるなら直す

検査が見るもの: 見出しの深さの並び・コードブロックの中身と順番。
検査が見ないもの: 見出しの文面の対応・本文の内容。本文だけを片方で直しても、検査は落ちない。

## コード例

- **コード例には、原則としてコメントを書かない。** 要るときは英語で書く。日本語版のコードブロックにも、日本語のコメントを書かない (英日でコードブロックが同じでなくなり、片方だけを直したことを機械で見つけられなくなる)
- 説明は、コードブロックの前後の本文に書く
- 例の中の文字列 (画面に出す文言・読み上げの文言) も、英日で同じにする (英語で書く)
- Android の `references/` の例は `import` を省いている。省いた import のうち、推測しにくいものは、本文に書く (初回の制作では、`by mutableStateOf` に要る `getValue`・`setValue` と、取り消しの例外の import が推測になった)
- 例が、利用者のモジュールに無いかもしれない依存 (Android の Material 3 など) を使うときは、無いモジュールでの読み替え方を `SKILL.md` に書く
- 見本の URL は `https://example.com/` で始める。ほかのホストを例に書かない

### 最小コード例は、利用者役の画面のファイルと同じにする

README の最小コード例と、各 `SKILL.md` の最小の動く例は、利用者役の画面のファイルの全体と同じ内容にする。

| プラットフォーム | 利用者役の画面のファイル |
|---|---|
| iOS | `verification/ios/Sources/VerificationApp/ItemListScreen.swift` |
| Android | `verification/android/app/src/main/kotlin/ItemListScreen.kt` |

- 例を変えるときは、利用者役の画面のファイルを先に変え、README の 2 枚と 4 つの `SKILL.md` に同じ内容を写す。利用者役のファイルは、検証 CI の利用者の立場のビルドの確認がビルドする ([利用者の立場のビルドの確認](consumer-build-check.md))
- 利用者役の画面のファイルには、コメントと、利用者に関係の無い行 (package の宣言・`public`) を書かない。そのまま README に載るためである

### コード例を確かめる

`references/` のコード例と、本文の中の 1 行の断片は、どの検査もビルドしない。コードブロックか断片を変えた・足したときは、リポジトリの外の作業用の置き場でコンパイルして確かめる。リポジトリのファイルは変えない。

| プラットフォーム | やり方 |
|---|---|
| iOS | 本体 (`ios/` のマニフェストとソース) の写しに依存する作業用の Swift パッケージを作り、英語版のコードブロックを取り出して置く (先頭に `import SwiftUI` と `import KsCollectionView` を足す)。行き先を機種を決めない形 (`generic/platform=iOS Simulator`) にしてビルドする。Swift 6 の言語モードで確かめる |
| Android | 本体 (`android/`) の写しに、本体のモジュールに依存する作業用のモジュールを足し、英語版のコードブロックを取り出して置く (1 枚を 1 つの package にする)。Kotlin のコンパイルのタスクを流す |
| どちらも (1 つの画面で確かめたいとき) | 作業ツリーを作業用の置き場に写して使い捨ての git のリポジトリにし、写しの中の利用者役の画面のファイルを入れ替えて、確認のスクリプトを `local` で流す。利用者と同じ依存の届き方で確かめられる |

- 日本語版のコードブロックは、検査が英語版と同じ内容だと確かめているので、英語版だけをビルドすればよい
- 本文の中の 1 行の断片も、コンパイルできる形にして一緒に通す
- ビルドが例のソースを読んでいることを、最初に 1 回確かめる (存在しない名前を呼ぶファイルを足すと落ち、消すと通る)
- 確かめられるのは、コンパイルが通ることまでである。例を起動して動きを見てはいないことを、作業の報告に書く

検査が見るもの: README の最小コード例が利用者役の画面のファイルと同じこと・コードブロックが英日で同じこと・一覧に無い URL が無いこと。
検査が見ないもの: `SKILL.md` の最小の動く例が利用者役と同じこと (追従の道具が、利用者役の変更を「変わった源泉」として出す)・`references/` の例がコンパイルできること・コメントの有無と言語。

## 相手のプラットフォームとの差

- 相手のプラットフォームとの動きの差と、片方にしか無い指定は、**その機能を説明している場所に 1〜2 文で書く。** 差をまとめた節や 1 枚を作らない
- 相手のプラットフォームのコードを載せない。iOS の Skill に Kotlin のコードブロックを、Android の Skill に Swift のコードブロックを置かない。本文の中でも、相手のプラットフォームの modifier や関数の呼び出しを書かない
- 相手の Skill に触れるときは、名前 (`kscollectionview-ios`・`kscollectionview-android`) だけを書く。リンクを張らない。触れるのは `SKILL.md` の冒頭の 1 か所で足りる
- 片方のプラットフォームにだけ当たる約束ごと (iOS の起動時のディスクキャッシュの有効化・Android の自動の初期化の前提など) は、そのプラットフォームの Skill にだけ書く
- 相手のプラットフォームの動きを書くときは、相手の本体のコードか、相手の Skill の文面と突き合わせて、合っていることを確かめる。初回の制作では、iOS の Skill が Android の動きに触れる 16 行を、Android の実物と突き合わせた

検査が見るもの: Skill の外へのリンクが無いこと。
検査が見ないもの: 相手のプラットフォームのコードブロックが無いこと・差の記述が合っていること。

## Skill の外への参照

Skill は、1 ディレクトリを単体でコピーして使われる。Skill の外への参照は、何のための参照かで分ける ([cross/ADR-0019](../../decisions/cross/0019-skill-external-references-by-purpose.md))。

| 参照 | 扱い |
|---|---|
| 知識を Skill の外に委ねる参照 (README・Skill の索引・相手の Skill・リポジトリの中の文書へ、続きをそちらで読ませるもの) | 書かない。Skill の外のファイルへのリンクは、すべてこれに当たる |
| 操作の対象になる URL (依存に書く Package URL・最新の版の確かめ先・不具合の報告先・frontmatter の配布元) | 書いてよい。許可する URL の一覧にあるものだけ |
| 同じ Skill の中の 1 枚へのリンク | 書いてよい。リンクの先が実在すること |
| 依存しているライブラリの文書への誘導 | URL は書かない。「そのライブラリの文書に従う」と言葉で書き、Skill が扱わない範囲であることを明記する |

- Skill だけで読み切れるように書く。Skill の外を見ないと分からないことを残さない
- リポジトリの内部の言葉を書かない。ADR の番号・開発の記録の言葉・利用者役など、利用者の知らない言葉が当たる。内部の言葉の一覧は `scripts/ci/user-docs-rules.json` の `internalTerms` にある

### URL と内部の言葉の一覧に足すとき

許可する URL と内部の言葉は、`scripts/ci/user-docs-rules.json` に置いてある。

| 項目 | 中身 | 足すとき |
|---|---|---|
| `allowedUrls` | 完全一致で許可する URL。役割 (`role`)・URL・何の URL か (`note`) を持つ。今は 4 つ (Package URL・本リポジトリ・最新の版の確かめ先・不具合の報告先) | 操作の対象になる URL だけを足す。知識を委ねる先 (文書のページ・ブログ) は足さない。役割 `latest-version` の URL は、インストール例の検査が「最新の版の確かめ先」として読むので、役割の名前を変えない |
| `sampleUrlPrefixes` | 前方一致で許可する、見本の URL の前置き。今は `https://example.com/` | 原則として足さない。例は、今の前置きで書く |
| `internalTerms` | Skill に現れてはいけない言葉。大文字と小文字を区別せずに探す。言葉の端が英数字のときは、ほかの単語の一部を数えない | 新しい内部の言葉 (ハーネスの道具の名前・内部のディレクトリやターゲットの名前) が Skill に入り得ると分かったときに足す。足す前に、その言葉が Skill の正しい文面に現れないことを、4 つの Skill で探して確かめる (一般の英単語と重なる言葉を足すと、正しい文面が落ちる) |

一覧を変えたら、スクリプトのテストを流す (`python3 scripts/ci/run-tests.py`)。

検査が見るもの: Skill の外へ出るリンク・一覧に無い URL・内部の言葉 (本文とコードブロックの両方)。
検査が見ないもの: 言葉だけで Skill の外へ誘導する文・Skill だけで読み切れるか。

## インストール例

インストール例は、README の 2 枚と、4 つの `SKILL.md` の 6 か所にある。

- **版の位置には `{version}` を置く。具体の版を書かない** ([cross/ADR-0018](../../decisions/cross/0018-install-examples-without-concrete-version.md))。リリースのときにも、書き換えない
- 例のそばに、`{version}` を使う版に置き換えること・置き換えないと依存の解決に失敗すること・最新の版の確かめ先の URL を、同じファイルの中に書く
- **依存の宣言の行は、コードブロックの中に、次の形で書く。** 検査は、コードブロックの中のこの形の行だけを数える。文の中に書いた同じ字面は数えない

  ```text
  .package(url: "<Package URL>", exact: "{version}")
  .product(name: "<product>", package: "<package>")
  implementation("<group>:<artifact>:{version}")
  ```

- Package URL・package の名前・product の名前・Maven の座標は、[公開識別子と配布座標](public-identifiers.md) の値を書く。検査は、利用者役が公開済みの配布物を取るときに使う値と比べる
- README は SwiftPM と Gradle の両方の例を、iOS の `SKILL.md` は SwiftPM の例を、Android の `SKILL.md` は Gradle の例を持つ。英語版と日本語版で、例の種類と数を同じにする
- 配布物をまだ公開していないことの 1 文は、README のインストールの節の冒頭にだけ書く。Skill には書かない (利用者が Skill を手にするのは、公開の後である)
- Skill の索引 (`skills/README.md`・`skills/README_ja.md`) には、ライブラリの版を書かない

検査が見るもの: 値が利用者役の値と同じこと・版が `{version}` であること・最新の版の確かめ先の URL が同じファイルにあること・例の種類と数。
検査が見ないもの: 置き換えの説明の文面・文の中に書いた版。

## 公開の宣言の名前

- **本体の公開の宣言の名前 (型・関数と修飾子・プロパティ・列挙の値) は、外すと決めたものを除いて、そのプラットフォームの Skill の英語版と日本語版のそれぞれに、一度は現れるようにする**
- 名前は、その機能を説明している 1 枚に、使い方と一緒に載せる。名前だけを並べた一覧の節を作って数を合わせない
- 外してよいのは、利用者が自分のコードに書かない名前だけである (コンパイラが呼ぶ関数・DSL の組み立てに使う印など)。利用者が書けるが勧めない名前は、外さずに、勧めない理由と一緒に載せる
- 外す名前は、書き手が決めない。候補と理由を一覧にして、オーナーに諮る。決まった名前と理由を、追従の記録 (`skills/.manifest.json`) の `apiExclusions` に、プラットフォームごとに書く
- 外す名前を、文書の表だけに書かない。道具が読む記録に書かないと、毎回報告され、同じ判断を聞き直すことになる
- 提供していない機能は、`SKILL.md` の「できること」の表の下に、1 か所にまとめて書く。書く前に、公開の宣言を読んで、無いことを確かめる

今、外している名前: 【蒸留のときに、`apiExclusions` の実物に合わせて書く】

確かめ方: `python3 scripts/docs/check-api-coverage.py` (漏れが無ければ終了コード 0)。検証 CI では流れない。追従のときと、Skill から名前を消したときに流す ([利用者向け Skill の追従](user-skill-refresh.md))。

## 書くときの勘どころ

初回の制作で、リポジトリの中のレビューをすべて通った後に、Skill だけを渡したエージェントの確認 (読ませる・使わせる) で挙がったことから拾った。

- **事実は、本体のコードで確かめてから書く。** 源泉の概念の文書や、覚えている動きから書かない。宣言の形 (引数の型・既定値・付いている属性)・呼ばれるスレッド・既定の色・依存の届き方は、宣言とビルドの設定の実物を読む
- **コードから決められないことは、書かない。** 掛かる時間・依存しているライブラリの内部に任せている動き・テストも決まりも無い入力の扱いが当たる。書かなかったことと理由を、作業の報告に残す
- 実行して確かめていないことを、確かめたように書かない。コードを読んで決めた動きは、読んで決めたと報告に書く
- **提供していない機能を、明記する。** エージェントは、書かれていない API を探し続けるか、推測で書く。「ライブラリに API が無い」と書けば、そこで止まる
- **例を写したときの落とし穴を、例の直後に断る。** 例が簡単のために省いたこと (保存の間の変更を巻き戻す・ソートへ戻す手段が無い・例の例外の型は代わりである、など) を書く。エージェントは、例をそのまま写す
- **例のどの部分が任意かを書く。** 複数の機能を受け持つ例 (状態を持つモデルなど) は、機能ごとに要る部分を 1 文で示す
- 型の宣言の事実と、実行時の事実を分けて書く。「メインスレッドで呼ばれる」は実行時の話で、クロージャの宣言に何が付いているかは、別に書かないと分からない (Swift 6 の言語モードでは、宣言が分からないと書き方が決まらない)
- 二通りに読める言い回しを避ける。同じものを指す言葉は、Skill の中で 1 つに決め、`SKILL.md` に言葉の説明を置く
- 「できること」の表の行から、行き先の 1 枚の見出しが見つけられるように書く。表から辿れない見出しを作らない
- 1 枚が膨らむ直しは、足す前に量を見る。例を別の書き方でもう 1 つ足すより、読み替え方を 1〜2 文で書く

## スクリーンショット

README のスクリーンショットは、`assets/` の 6 枚である。3 つの画面 (リスト・グリッド (固定列)・グループ化) を、両プラットフォームで撮る。

| 画面 (Sample の名前) | ファイル |
|---|---|
| リスト | `assets/ios-list.png`・`assets/android-list.png` |
| グリッド (固定列) | `assets/ios-grid.png`・`assets/android-grid.png` |
| グループ化 | `assets/ios-grouping.png`・`assets/android-grouping.png` |

### 撮り方

- Sample の今の画面を撮る。**撮るために Sample を変えない**
- 作業専用の Simulator とエミュレータを新しく作って使い、終わったら削除する。操作のたびに、作った端末の識別子を指定する。既存の Simulator・AVD・つながっている実機には触らない
- ライトの表示で撮る。開いた直後 (スクロールしていない・操作していない) の状態で撮る
- ステータスバーを固定の表示にする (時刻 9:41・電波と電池は固定・通知のアイコンなし)
- 画面は、Sample の起動の引数で直接開く
- 両プラットフォームで、同じ画面を同じ状態で撮る
- 外から取得した画像が写る画面 (画像グリッド) は撮らない。権利の確認が別に要る

### 保存する前と後に確かめること

- **保存する前に、1 枚ずつ開いて、外から取得した画像と、個人を特定する情報 (端末の名前・アカウント・通知・通信事業者の名前) が写っていないことを確かめる。** 画像のファイルに、位置や機種の名前の埋め込みが無いことも確かめる
- 撮った後に、Sample のビルドが追跡しているファイルを変えていないことを確かめる
- README からは、相対パスで参照する。ブランチの名前を含む URL で参照しない
- 環境と、写っているものの確かめの結果を、撮った変更の証跡に残す。初回の記録は、変更 `user-docs` の `evidence/readme-and-screenshots.md` にある

### 撮り直すきっかけ

スクリーンショットが古くなったことは、機械では分からない。次の変更をしたときに、撮り直すかを判断する。

- 撮っている 3 つの画面の、Sample のデモデータ・文言・並べ方を変えた
- ライブラリの既定の見た目 (区切り線・間隔・グループの見出しの固定) を変えた
- Sample の画面の上のバー・操作のパネルの見た目を変えた
- README に載せる画面を足す・入れ替える

撮り直すときは、6 枚を同じ回に撮る (片方のプラットフォームだけを撮り直すと、機種と OS の版がずれる)。

検査が見るもの: README のスクリーンショットの節が、`assets/` の 6 枚を 1 回ずつ指し、6 枚が実在すること。
検査が見ないもの: 画像の中身・大きさ・今の画面と合っているか。

## してはいけないこと

- 英語版か日本語版の片方だけを直して終える
- インストール例に、具体の版を書く
- Skill に、Skill の外のファイルへのリンク・一覧に無い URL・内部の言葉を書く
- 相手のプラットフォームのコードを載せる
- コードで確かめていない動きを、事実として書く
- 外す名前を、オーナーに諮らずに `apiExclusions` に足す
- 検査を通すために、検査の一覧 (`user-docs-rules.json`) や、検査が読む見出しの文面を、理由を残さずに変える
- 追従の途中で見つけた、ライブラリの不足や不具合を、Skill の文面で取り繕う (オーナーに諮る)
