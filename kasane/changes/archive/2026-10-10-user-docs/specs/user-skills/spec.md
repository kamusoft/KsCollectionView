## ADDED Requirements

### Requirement: 利用者向け Skill の構成

利用者向け Skill は、`skills/{en,ja}/kscollectionview-ios/` と `skills/{en,ja}/kscollectionview-android/` の 4 つのディレクトリに置かなければならない (SHALL)。各ディレクトリは、`SKILL.md` と、`references/` の 5 枚 (`basics.md`・`layout.md`・`paging.md`・`reorder.md`・`images.md`) を持ち、ほかのファイルを持たない。

同じ Skill の英語版と日本語版は、同じファイルの集合・同じ見出しの深さの並び・同じコードブロックを持つ。iOS の Skill と Android の Skill は、同じ 5 枚の分け方を持つ。

**Side Effects**: なし

#### Scenario: 4 つのディレクトリが同じ 6 枚を持つ
- **GIVEN** 制作が終わった `skills/`
- **WHEN** 4 つの Skill のディレクトリのファイルの一覧を比べる
- **THEN** どのディレクトリも、`SKILL.md` と `references/` の 5 枚だけを持つ

#### Scenario: 英語版と日本語版が同じ構成である
- **GIVEN** 同じ Skill の英語版と日本語版
- **WHEN** 同じ名前のファイルどうしで、見出しの深さの並びとコードブロックを比べる
- **THEN** どちらも一致する

### Requirement: SKILL.md の中身

各 `SKILL.md` は、frontmatter に `name`・`description`・`license`・`metadata.language`・`metadata.source` の 5 項目だけを持たなければならない (SHALL)。`name` はディレクトリの名前と同じで、英語版と日本語版で同じとする。`metadata.language` は、置き場の言語と合う。

本文は、順に次の 5 つを持つ: このライブラリが何かを説明する段落 (見出しの直下)・できること (やりたいことから `references/` の 1 枚への表)・導入 (インストール例と必要な環境)・最小の動く例・`references/` の一覧。

できることの表は、`references/` の 5 枚のすべてを指す。導入のインストール例は、ルートの README と同じ書き方 (版の位置は `{version}`。置き換えの説明と、最新の版の確かめ先を添える) にする。最小の動く例は、ルートの README の、同じプラットフォームの最小コード例と同じコードである。

**Side Effects**: なし

#### Scenario: 冒頭でライブラリが何かが分かる
- **GIVEN** Skill の 1 ディレクトリだけを手にした読み手
- **WHEN** `SKILL.md` の見出しの直下の段落を読む
- **THEN** このライブラリが何をするものかと、この Skill がどのプラットフォームを扱うかが、ほかの文書を見ずに分かる

#### Scenario: できることの表が 5 枚をすべて指す
- **GIVEN** 各 `SKILL.md`
- **WHEN** できることの表のリンクの先を数える
- **THEN** `references/` の 5 枚のすべてが、少なくとも 1 回指されている

#### Scenario: 導入に必要な環境がある
- **GIVEN** iOS の `SKILL.md`
- **WHEN** 導入の節を読む
- **THEN** 最低の OS の版と、要る Xcode の版が書かれている

#### Scenario: 最小の動く例が README の例と同じである
- **GIVEN** 各 `SKILL.md` と、ルートの README
- **WHEN** `SKILL.md` の最小の動く例と、README の同じプラットフォームの最小コード例を比べる
- **THEN** コードが同じである

### Requirement: references の中身

`references/` の各 1 枚は、利用者のやりたいことを見出しにして、動くコードと、守る約束ごとを並べなければならない (SHALL)。各 1 枚は、design.md の Decision 2 の表が、その 1 枚に割り当てた申し送りを、そのプラットフォームに当たる分だけすべて載せる。

コード例には、原則としてコメントを書かない。書くときは英語で書く。

**Side Effects**: なし

#### Scenario: 割り当てた申し送りがすべて載っている
- **GIVEN** design.md の Decision 2 の表と、フェーズの agenda の申し送り
- **WHEN** ある 1 枚に割り当てた申し送りを、1 件ずつその 1 枚と突き合わせる
- **THEN** そのプラットフォームに当たる申し送りが、すべてその 1 枚に書かれている

#### Scenario: 片方のプラットフォームだけの申し送りは、そのプラットフォームにだけ載る
- **GIVEN** iOS だけに当たる申し送り (親の状態を渡す指定・起動時のディスクキャッシュの有効化)
- **WHEN** 両方の Skill を読む
- **THEN** iOS の Skill には手順として書かれ、Android の Skill には手順として書かれていない

### Requirement: 相手のプラットフォームとの差の書き方

相手のプラットフォームとの動きの差と、片方にしか無い指定は、その機能を説明している場所に短く書かなければならない (SHALL)。相手のプラットフォームのコードを載せてはならない。差をまとめた節を作ってはならない。

**Side Effects**: なし

#### Scenario: 動きの差が、その機能の場所に書かれている
- **GIVEN** 両プラットフォームで動きが違う機能 (並べ替えの動き・Pull to Refresh が失敗したときの位置)
- **WHEN** その機能を説明している 1 枚を読む
- **THEN** 相手のプラットフォームでは動きが違うことが、その説明の場所に書かれている

#### Scenario: 相手のプラットフォームのコードが無い
- **GIVEN** iOS の Skill
- **WHEN** すべてのコードブロックを見る
- **THEN** Kotlin のコードが無い (Android の Skill では、Swift のコードが無い)

### Requirement: Skill の外への参照

`SKILL.md` と `references/` は、知識を Skill の外に委ねる参照を持ってはならない (SHALL NOT)。Skill の外のファイルへのリンク・ルートの README や Skill の索引へのリンク・本リポジトリの中の文書への URL が、これに当たる。相手のプラットフォームの Skill に触れるときは、名前だけを書く。

操作の対象の URL (依存に書く Package URL・最新の版の確かめ先・不具合の報告先・配布元を示す frontmatter の項目) は、書いてよい。

リポジトリの内部の言葉 (ADR の番号・開発の記録の言葉) を書いてはならない。

**Side Effects**: なし

#### Scenario: 相手の Skill は名前だけで触れる
- **GIVEN** 相手のプラットフォームの Skill に触れている箇所
- **WHEN** その箇所を見る
- **THEN** Skill の名前が書かれていて、リンクが無い

#### Scenario: Skill だけで読み切れる
- **GIVEN** Skill の 1 ディレクトリだけを手にした読み手
- **WHEN** `SKILL.md` と `references/` を通して読む
- **THEN** 説明の続きを、Skill の外の文書で読むように求められる箇所が無い

### Requirement: 公開の宣言の名前の掲載

各プラットフォームの公開の宣言の名前は、載せないと決めた名前を除いて、そのプラットフォームの Skill のどこかに、少なくとも 1 回現れなければならない (SHALL)。英語版と日本語版のそれぞれで満たす。

**Side Effects**: なし

#### Scenario: 載せないと決めた名前のほかに、漏れが無い
- **GIVEN** 制作が終わった `skills/` と、載せないと決めた名前の一覧
- **WHEN** 公開の宣言の名前の網羅を報告する道具を流す
- **THEN** 漏れの報告が 0 件である

### Requirement: Skill の索引

`skills/README.md` と `skills/README_ja.md` は、Skill の一覧・導入の手順・片方の言語だけを使うときの案内を持たなければならない (SHALL)。2 枚は、同じ見出しの並びを持つ。

**Side Effects**: なし

#### Scenario: 索引から導入の手順が分かる
- **GIVEN** 索引だけを読んだ利用者
- **WHEN** 導入の手順に従う
- **THEN** どのディレクトリを、自分のプロジェクトのどこへコピーすればよいかが分かる

#### Scenario: 索引が 4 つの Skill をすべて挙げる
- **GIVEN** 索引の 2 枚
- **WHEN** 一覧を見る
- **THEN** 英語版は `skills/en/` の 2 つ、日本語版は `skills/ja/` の 2 つの Skill を挙げている

### Requirement: 配った先を再現した確認

オーナーの検収の前に、Skill の 1 ディレクトリだけを手にした、リポジトリを知らない読み手 (エージェント) で、Skill を確かめなければならない (SHALL)。確かめるのは、読むだけで分かること (読ませる確認) と、Skill だけを頼りに書いたコードがビルドできること (使わせる確認) の 2 つである。

使わせる確認は、design.md の Decision 9 の 5 つの課題を、両プラットフォームで行う。ビルドは、利用者役と同じ形 (公開の前の成果物を、利用者と同じ書き方で参照する) で行う。ビルドが落ちたときは、原因を Skill の欠け・読み手の書き損じ・ライブラリの側の問題のどれかに仕分けて記録する。

確認の作業 (読ませる・書かせる・ビルドする) は、本リポジトリの追跡しているファイルを変えてはならない。ビルドは、作業用の写しの中だけで行う。確認で見つかった Skill の欠けを直すのは、確認とは別の作業で、この Requirement の外にある (直した Skill は、ほかの Requirement を満たし続ける)。

**Side Effects**:
- 一時の作業用のディレクトリ (Skill の写し・リポジトリの写し・ビルドの出力): 作成
- 変更のディレクトリの証跡: 作成

#### Scenario: 読ませる確認の指摘に、すべて結末が付いている
- **GIVEN** 4 つの Skill のそれぞれに対する、読ませる確認の指摘の一覧
- **WHEN** 証跡を見る
- **THEN** どの指摘にも、直したか、直さない理由が書かれている

#### Scenario: 5 つの課題が、両プラットフォームでビルドできる
- **GIVEN** Skill の 1 ディレクトリだけを渡された読み手が、課題ごとに書いた画面のファイル
- **WHEN** そのファイルを作業用の写しの利用者役の画面と入れ替えて、利用者の立場のビルドの確認を流す
- **THEN** 10 回 (5 つの課題 × 2 プラットフォーム) のすべてで、確認が成功している

#### Scenario: 落ちた回には、仕分けが残っている
- **GIVEN** 使わせる確認で、ビルドが落ちた回
- **WHEN** 証跡を見る
- **THEN** 原因の仕分けと、その後に行ったこと (Skill を直してやり直した・書き損じとしてやり直した・オーナーに諮った) が書かれている

#### Scenario: 確認の作業は、追跡しているファイルを変えない
- **GIVEN** 使わせる確認の 1 回を始める前の、本リポジトリの作業ツリー
- **WHEN** 書かせたファイルを作業用の写しに入れてビルドし、その回を終える
- **THEN** 本リポジトリの作業ツリーが、その回の前と同じである (利用者役のソースも変わっていない)
