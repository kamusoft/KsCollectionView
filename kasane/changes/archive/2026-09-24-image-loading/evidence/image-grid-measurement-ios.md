# iOS 画像グリッドの計測 (tasks 7.1)

## 状態

**2 系統のうち、メモリは合格、スクロール性能は不合格。** 合意済みの乖離 (区間の投入回数・窓の閉じ方) を含む立て直し手順で 2 系統とも計測を
済ませており (スクロール性能は 2026-09-08 に手順を立て直し、さらに同日、駆動を改善して測り直した)、
**計測としては完了、性能の合否としては不合格**である。

| 系統 | 状態 |
|---|---|
| メモリ (`phys_footprint` の往復推移) | **合格**。規約が求める独立 2 回の実行を行い、両方で定常化を確認した (2026-09-07。手順立て直しの対象外のため測り直していない) |
| スクロール性能 (hitch time ratio) | **不合格**。駆動を改善した手順で基準機の独立 3 試行を記録し、3 試行中 1 試行が合格線 (5 ms/s 未満) を超えた (0.00 / 3.94 / 5.54 ms/s) |
| プリフェッチの開始・取消件数 | Simulator で計測 (件数は挙動の量であり実機性能とは独立) |

この表の「実行した / していない」は下の各節の記述と一致させる。片方だけを合格と読める書き方を
しないこと (測っていないものを測ったことにしないため)。

**次に必要なことは「次に必要なこと」の節にまとめてある。**

## 固定 fixture

- 画面: Sample「画像グリッド」と、同じデータ・同じ配置を描く計測専用の起動経路
- 件数: 10,000 件、3 列、セル間と外周の余白は Sample と同じ
- セル: 正方形の `KsImage` (fill) と ID の文言
- 取得元: ID から決まる公開プレースホルダー画像サービスの URL (400 × 400)
- プリフェッチ: 到達点はディスクまで (Sample の初期選択と同じ)

要素・配置・外周の余白・セル・プリフェッチの宣言は、デモ画面と計測用の画面が同じ宣言元
(`ImageGridFixture`) から取る。コレクションの組み立てそのものを 1 箇所に集めているため、
両者の土俵が食い違う書き方ができない (Android は宣言元の共有に加えて、両画面を実際に描いて
一致を確かめるテストを持つ。iOS は組み立てが 1 本なのでテストでの確認を持たない)。

取得はネットワークに依存するため、この土俵の結果は実行時の回線状態を含む。
「大量件数」の土俵 (固定高・可変行高混在の 2 列) とは別の土俵であり、値を比較しない。

## メモリ

手順は iOS 性能検証の規約どおり。Release 構成の app を Simulator に入れ、計測専用の起動経路を
自動実行で走らせる (走査・記録・終了まで app 自身が行う)。1 往復は可視範囲の高さの半分ずつ
content offset を送って先頭から末尾、そして先頭へ戻る走査で、各段階は「目的の位置に到達し、
その位置のセルが載った」ことを条件に待つ。

環境: iPhone 17 Pro Simulator (iOS 26.5) / Release 構成。規約はメモリの計測を Simulator で行うと
定めており、判定は定常化 (往復を重ねても増え続けないこと) に限る — Simulator のメモリ絶対値は
実機と異なるため、この土俵の値を絶対量の判定に使わない。

2 回の実行は独立している。実行ごとに app を削除して入れ直し、画像のキャッシュを空の状態から
始めている。

### 実行 1

| 往復 | `phys_footprint` | 1 往復後に対する増分 | 通過項目 |
|---|---:|---:|---:|
| 1 往復後 | 38,455,432 bytes | — | 10,000 / 10,000 |
| 2 往復後 | 39,471,240 bytes | +2.64% | 10,000 / 10,000 |
| 3 往復後 | 40,241,288 bytes | +2.00% | 10,000 / 10,000 |
| 4 往復後 | 40,683,656 bytes | +1.15% | 10,000 / 10,000 |
| 5 往復後 | 41,437,320 bytes | +1.96% | 10,000 / 10,000 |

判定: **定常化を確認した**。4・5 往復目の増分が 1 往復後の値の 2% 以内 (+1.15% / +1.96%) で
2 往復連続して収まり、上限の 10 往復に達する前に打ち切っている。走査は毎往復 10,000 件すべてを
通過した。3 往復目の増分 (+2.00%) は許容差をわずかに上回っており、そこでは定常と判定していない。

### 実行 2

| 往復 | `phys_footprint` | 1 往復後に対する増分 | 通過項目 |
|---|---:|---:|---:|
| 1 往復後 | 38,471,840 bytes | — | 10,000 / 10,000 |
| 2 往復後 | 39,569,568 bytes | +2.85% | 10,000 / 10,000 |
| 3 往復後 | 40,093,856 bytes | +1.36% | 10,000 / 10,000 |
| 4 往復後 | 40,519,840 bytes | +1.11% | 10,000 / 10,000 |

判定: **定常化を確認した**。3・4 往復目の増分が許容差以内 (+1.36% / +1.11%) で 2 往復連続して
収まっている。走査は毎往復 10,000 件すべてを通過した。

### 実行間のばらつき

| 見る値 | 実行 1 | 実行 2 | 差 |
|---|---:|---:|---:|
| 1 往復後の値 | 38,455,432 bytes | 38,471,840 bytes | +0.04% |
| 定常と判定した往復 | 5 往復目 | 4 往復目 | 1 往復 |
| 定常と判定した時点の値 | 41,437,320 bytes | 40,519,840 bytes | 2.26% |

系統としての判定: **合格**。規約が求める独立 2 回の実行のいずれでも、上限の 10 往復に達する前に
定常化した。実行間のばらつきは 1 往復後の値で 0.04%、定常時の値で 2.26% であり、定常化の成否は
どちらの実行でも変わらない。

ただし増分は 0 にはならず、定常と判定した往復でも 1 往復あたり 0.4〜0.8 MB の増加が残っている
(規約の合格線は「増分が 1 往復後の値の 2% 以内」であって「増分が 0」ではない)。この土俵の値は
実行ごとの回線状態を含むため、回線の違う日の値どうしは比較できない。

なお、この変更の以前の便で 1 回だけ実行した記録 (1 往復後 82,168,976 bytes、4 往復目で定常) が
あるが、Simulator の版を記録しておらず、上の 2 回とは環境が揃っていない。合格の判定材料には
使わない。

## プリフェッチの開始・取消件数

Sample「画像グリッド」(プリフェッチはディスクまで) を iPhone 17 Pro Simulator (iOS 26.5) の
Debug 構成で開き、app を削除して入れ直した状態から 4 回の速いフリックを行ったときの件数。
観測手段と限界は `image-behavior-observation.md` に書いたとおりで、到達点がディスクまでの先読みは
ローダー自身の計測記録の側で数えている。

| 対象 | 開始 | 取り消し | 完了 |
|---|---:|---:|---:|
| 元データの取得 (先読みを含む) | 200 | 41 | 159 |
| 表示要求 | 165 | 43 | 122 (失敗 0) |

フリング中に窓から外れた取得が実際に取り消されている。デコードは開始・終了とも 124 件で、
取り消された取得はデコードまで進んでいない。

この表は、`image-behavior-observation.md` の 7.4 に載せた取り消しの観測とは**別の実行**である
(あちらは同じ土俵の以前の実行で、元データの取得 183 / 48 / 135、表示要求 254 / 53 / 201)。
件数はフリックの速さと回線状態で変わるため、2 つの表の数字は一致しない。どちらの実行でも
「開始した取得の一部が取り消され、残りが完了する」という読み取りは同じである。

元データの取得 (200) が表示要求 (165) を上回るのは、この差に先読みが含まれるためである
(到達点がディスクまでの先読みは表示要求として現れない)。ただし**両者の差がそのまま先読みの
件数になるわけではない** — 同じ URL への表示要求と先読みは 1 本の取得にまとめられるため、
この観測から先読みの件数だけを取り出すことはできない。

### この表の集計規則

観測ログの種別 (`kind=`) は、要求から本当に分かることだけを名乗る。上の表の行との対応は次のとおり。

| ログの種別 | 意味 | 上の表での扱い |
|---|---|---|
| `display` | `KsImage` の表示要求。表示枠から決めた縮小の指定を持つのはこれだけ | 「表示要求」の行 |
| `prefetch-or-loader-display` | 到達点がメモリまでの先読みか、ローダー付属のビュー (`LazyImage`) の直接表示のいずれか。**要求からは区別できない** | どちらの行にも数えない (下記) |
| (ログに現れない) | 到達点がディスクまでの先読み。元データの取得として走り割り込み処理へ通知が来ない | 「元データの取得」の行 — ローダー自身の計測記録の側で数える |

この土俵は到達点がディスクまでで、画面もローダー付属のビューを使わない。したがって曖昧な種別に
入る要求は構成上生まれないはずであり、上の表の「表示要求」は `display` の件数だけで足りる。
**この計測では、その曖昧な種別の件数を実際に数え上げて 0 件であることを確かめている** (構成から
導いた推論だけに頼っていない)。**この種別が出る土俵 (到達点をメモリまでにする / 検証画面の
ローダー付属ビューを使う) で数えるときは、その件数を先読みとも表示とも読んではならない。**

完了した表示要求 122 件の取得元は、この実行ではすべてネットワークだった。app を入れ直した直後で
ディスクにもメモリにも何も無い状態から始めているため、この数字を「先読みが効いていない」根拠に
してはならない — 先読みと表示が同じ取得にまとまった場合、その表示は先読みの完了を待って成功し、
取得元はネットワークとして記録される。プリフェッチが効いていることの判定は
`image-behavior-observation.md` の 7.3 の観測 (先読み済みの ID に要求が出ないこと) で行っている。

## スクロール性能 (hitch time ratio)

環境: iPhone 11 (基準機) / iOS 18.7.8 / Release 構成 / 実機。記録は Instruments の Animation
Hitches テンプレート (`os_signpost` を併用)。3 試行は独立している (試行ごとに app を削除して
入れ直し、画像のキャッシュが空の状態から始める)。Android の実機計測便と同じ Mac で並走して
取得した (下記「並走の影響」)。

**手順は 2026-09-08 に 2 度動いている。** 前半に窓の取り方を立て直し、後半に駆動そのものを
改善して測り直した。**本文の値は後半 (駆動改善後) のもの**で、前半の値は末尾に履歴として残す。
窓の長さと計測の足場の費用が違うため、前半・後半の値は比較しない。

### 計測手順

1. Debug のテストランナーを先に走らせ、駆動テストを待たせる (`KS_PERF_PRELAUNCH_HOLD`)
2. その間に、測る対象である Release 構成の app を削除して入れ直す (キャッシュが空になる)
3. 待ちが明けた駆動テストが、その app を `--screen <画面> --signpost-scroll-window` で起動する
4. 起動したプロセスに記録を接続する
   (`xctrace record --template 'Animation Hitches' --instrument os_signpost --attach <アプリのプロセス>`)。
   駆動テストは接続のために `KS_PERF_RECORD_WAIT` 秒待つ
5. 駆動テストが区間の外で 1 回空打ちしたあと、始まりの印を送って 3.000 秒フリックし続ける。
   区間の印は **app 自身が** Points of Interest (`scroll-window`) として記録に残す
6. 記録から `scroll-window` の区間を取り、その中に始まる hitch の長さの合計を区間の実測長で割る

駆動は `samples/ios/KsCollectionViewSamplesUITests/PerformanceDriverUITests.swift` の
「画像グリッドを3秒間連続フリックスクロールする」(対照は「大量件数を3秒間連続フリック
スクロールする」)、区間の印は `samples/ios/KsCollectionViewSamples/ScrollWindowSignpost.swift`。

### 駆動の改善 (2026-09-08 後半)

前半の計測では区間が 3.0〜6.0 秒とばらつき、比を薄める向きに働いた。また駆動が毎フリックで
一覧の要素を解決しており、その走査が測る側の主スレッドの 11〜17% を占めていた。次の 3 点を
改めた。

| 改めたこと | 狙い |
|---|---|
| ループの中で要素を解決しない。座標をフリックの前に 1 度だけ確定し、以後はアプリ原点からの絶対座標として押下 → ドラッグする | 毎回のアクセシビリティ走査を区間から外す。静止を待つ `swipeUp` も使わない |
| 区間を閉じるのを「最後のフリックの終了」ではなく**締切**にする。終わりの印は別スレッドの時計で 3.000 秒後に送る | 区間の実測長を 3.00 秒にそろえる |
| 区間の外で 1 回空打ちする | 自動化の初期化にかかる一度きりの費用と、一覧が止まった状態から動き出す分を区間へ持ち込まない |

**改善の過程で分かったこと**: 座標による押下 → ドラッグも、`swipeUp` と同じく**指を離した後の
静止まで待って戻る**。1 回の呼び出しに 3.0〜3.3 秒かかるため、3.000 秒の区間に入る**フリックの
投入は 1 回**になる。区間の大半は指を離した後の慣性スクロールであり、画面は動き続けている
(下記「区間内でフリックした回数と画面の更新」)。「連続フリック」を投入回数で満たすには、静止
待ちを迂回する別の入力手段が要る — 今回はそこまで踏み込んでいない。

### 結果 (画像グリッド)

| 試行 | 区間の長さ | 区間内の hitch | hitch time の合計 | hitch time ratio | 判定 |
|---|---:|---:|---:|---:|---|
| 1 | 3.02 s | 0 件 | 0.00 ms | **0.00 ms/s** | 合格 |
| 2 | 3.04 s | 1 件 | 11.99 ms | **3.94 ms/s** | 合格 |
| 3 | 3.01 s | 1 件 | 16.67 ms | **5.54 ms/s** | **不合格** |

系統としての判定: **不合格**。規約は「3 回すべて 5 ms/s 未満」を求め、平均で合格にしないと定める。
試行 3 が合格線を超えている。**合格を拾うために試行を足すことはしていない** (規約どおり 3 試行で
止めた)。

区間内の hitch の内訳:

| 試行 | 区間の先頭からの位置 | 長さ | 種別 |
|---|---:|---:|---|
| 1 | — | — | (区間内に無し) |
| 2 | +1.03 s | 11.99 ms | Expensive Commit(s) |
| 3 | +1.66 s | 16.67 ms | Commit to Render latency - Delay Frame Swap |

**hitch は多くても 1 件で、長さは 1 リフレッシュ (16.7 ms) 以内である。** 3 秒窓に対する
5 ms/s の合格線は 15 ms 相当なので、この土俵では **「3 秒間フレーム落ち 0」でなければ合格
しない**基準として働いている (試行 3 は落ちたフレームが 1 枚)。

### 区間内でフリックした回数と画面の更新

駆動が出力する印 (`KS71`) と、記録側の画面更新 (surface swap) の件数。

| 試行 | 空打ち (区間外) | 区間内のフリック | 各回の所要 | 区間内の画面更新 | 平均 | 60 Hz 換算で更新が無かった時間 |
|---|---:|---:|---:|---:|---:|---:|
| 1 | 3.134 s | 1 回 | 3.045 s | 137 回 | 45.4 fps | 0.74 s |
| 2 | 3.130 s | 1 回 | 3.210 s | 130 回 | 42.8 fps | 0.87 s |
| 3 | 3.123 s | 1 回 | 3.015 s | 143 回 | 47.5 fps | 0.63 s |

**窓に含まれる無操作時間の見積もり**: 指が画面に触れているのは押下 (0.05 s) とドラッグ
(可視高の約 6 割 ÷ 2500 pt/s ≒ 0.2 s) だけで、区間の残り約 2.7 秒は慣性スクロールである。
そのうち**画面がまったく更新されない時間は 0.6〜0.9 秒** (上表の右端。60 Hz で埋まるはずの
181 枚に対する不足を時間に直した値)。この時間は空打ちの慣性が尽きてから次のフリックが
届くまでの間と、区間末で慣性が尽きた後に生じる。**比の分母には入るが hitch は起きない**ため、
合格側に薄める向きに働く。前半の手順 (区間 3.0〜6.0 秒) より薄まりは小さいが、0 ではない。

### 対照: 画像を出さない土俵 (「大量件数」)

同じ改善後の駆動・同じ機材・同じ窓で、Sample「大量件数」(10,000 件・2 列・固定高と可変行高の
混在・ネットワークを含まない) も独立 3 試行を取った。**画像グリッドの残り 1 件が計測の足場や
基準の側に共通の原因を持つのか**を切り分けるための対照である。

| 試行 | 区間の長さ | 区間内の hitch | hitch time の合計 | hitch time ratio |
|---|---:|---:|---:|---:|
| 1 | 3.03 s | 17 件 | 329.21 ms | 108.65 ms/s |
| 2 | 3.08 s | 19 件 | 419.90 ms | 136.33 ms/s |
| 3 | 3.03 s | 18 件 | 379.23 ms | 125.16 ms/s |

区間内の hitch の種別の内訳は、試行 1 が Commit to Render latency 9 / Pre-Commit(s) latency 5 /
Expensive Commit(s) 3、試行 2 が 10 / 7 / 2、試行 3 が 12 / 4 / 2 である。

対照側も、画像グリッドと同じ列で駆動の印 (`KS71`) と画面更新を記録した。

| 試行 | 空打ち (区間外) | 区間内のフリック | 各回の所要 | 区間内の画面更新 | 平均 | 60 Hz 換算で更新が無かった時間 |
|---|---:|---:|---:|---:|---:|---:|
| 1 | 3.295 s | 1 回 | 3.201 s | 134 回 | 44.2 fps | 0.80 s |
| 2 | 3.252 s | 1 回 | 3.281 s | 130 回 | 42.2 fps | 0.91 s |
| 3 | 3.255 s | 1 回 | 3.187 s | 133 回 | 43.9 fps | 0.81 s |

読み取り: **同じ駆動・同じ窓でも、fixture によって hitch の件数が大きく異なった** (画像グリッドは
0〜1 件、大量件数は 17〜19 件)。画面の更新回数は両者ほぼ同じ (130〜143 回) なので、走った量の違い
ではない。自動化の負荷は両方の土俵に共通して掛かっている (改善後の trace で主スレッドの 20〜37%) が、
大量件数の側は主スレッドが窓内サンプルの 94% を占めて飽和しており、**共通要因だけでは 0〜1 件と
17〜19 件の差を説明できない可能性が高い**。ただし共通の足場の費用が画面の中身との相互作用で違う
大きさになる余地は残る — **自動化を掛けない条件の対照が無いため、共通要因の分離は未確認である**。

同時に、この対照は**「大量件数」の土俵が基準機で合格線を大きく超える**ことを示している。区間内の
hitch は Pre-Commit(s) latency と Commit to Render latency が中心である。これは本 change の
判定対象 (画像グリッド) の外にあり、**この証跡では原因を特定していない**。アーカイブ済みの
「大量件数」の計測 (iPhone 15 で 3 試行とも 0.0 ms/s) は代替機かつ 20 秒の保守的な窓で取った値で、
基準機の値としても今の手順の値としても使えないため、この 3 試行と比較していない。

### 記録が成立していることの確かめ (陽性対照)

- 各試行の記録に**区間の印が入っている**。印が無い記録は窓を含んでいないので使わない
- 区間内が 0 件だった試行 1 でも、**同じ記録の区間の外**に hitch が 1 件 (起動直後の読み込み中、
  15.51 ms Expensive Rendering) 記録されている。区間内 0 件が「記録が成立していないため」では
  ないことを、同じ記録の中で示せる
- 区間内の画面更新が 130〜143 回あり、区間中に実際にスクロールが進んでいる (静止した画面を
  測ったのではない)

### 並走の影響

Android の実機計測便と同じ Mac で並走して取得した。記録は端末側で行われ、ホストは記録の開始・
停止と書き出しだけを行うため影響は小さいと考えるが、**並走しない条件との比較は取っていない**。
なお 3 試行と対照 3 試行のビルドは、いずれも計測を始める前に済ませてある (試行中にホスト側で
ビルドを走らせていない)。

### この結果の読み方 (限界)

- 区間内の hitch は多くても 1 件で、**この計測は原因を特定していない**。trace の解析で分かった
  範囲は下記「次に必要なこと」にまとめてある (改善後の trace では試行 3 で画像ロードの経路が
  不在、試行 2 は不在とは言えない)
- 「自動化」の分類は、スタックに `XCTAccessibilityFramework` / `XCTest` 系、および `AXRuntime` /
  `AccessibilityViewGraph` のフレームを含むサンプルとする (UIKit のアクセシビリティ呼び出し
  `UIViewAccessibility` は含めない。含めると同じ trace で約 10 ポイント振れる)。改善前 (19〜24%) と
  改善後 (34〜37%) は同じ定義で数えている。対照 b1 の窓内 hitch time の合計は 1 行 (+1.190 s) の扱いで
  312.59〜329.21 ms の幅があるが結論は不変
- **駆動改善後も自動化の負荷は減っていない**。改善前の trace で主スレッドの 19〜24% だった自動化
  (XCTest / アクセシビリティ走査) は、改善後の trace では 34〜37% に増えている。座標による
  press-drag も指を離した後の静止まで待って戻るため、区間中もランナーがアクセシビリティの
  スナップショットを取り続けているものと推測する (推測であり、切り分けは取っていない)。
  改善で区間から外れたのは「毎フリックの要素解決」であって、自動化の費用そのものではない
- **サンプリングの取りこぼし**。time profile は 1 ms 刻みのため、1 ms 未満で終わるデコードは
  サンプルに現れないことがある。また render 側の費用にデコード後のテクスチャが効いていないことは、
  この記録からは否定できていない
- 1 件が 12〜17 ms と短いため、**区間の長さと分母の取り方が合否をそのまま動かす**。区間は
  3.01〜3.04 秒にそろったので、前半の手順にあった「区間が長い試行だけ合格する」形は消えた
- 土俵はネットワークからの画像取得を含み、各試行はキャッシュが空の状態から始まる。したがって
  この値は回線状態を含む。「大量件数」の土俵の値と絶対値を比べる意味はない (対照は hitch の
  **件数の桁**を見るために取った)
- 区間内のフリックの投入は 1 回である。規約の「3 秒間の連続フリック」を投入回数で満たしては
  いない (画面は区間を通して動いている)

## 次に必要なこと

この節は、この証跡だけを読む人に「ここで止まっている理由」と「次の一手」を示す。

**分かっていること (どこまで切り分けたか)**

- **`KsImage` の経路は、少なくとも試行 3 の hitch には不在である**。ここは**どの trace を見た話か
  で結論が変わる**ので分けて書く。
  - *改善前の trace (前半の 3 試行、1.47 / 5.53 / 5.78 ms/s)*: `KsImage` の準備・縮小・デコード・
    先読みは窓全体の 1% 未満で、hitch の時刻には走っていなかった。**この結論は前半の値に対する
    ものであり、後半の試行にそのまま持ち越せない** (hitch の時刻・長さ・種別が変わっているため)
  - *改善後の trace・試行 3 (5.54 ms/s、Commit to Render latency - Delay Frame Swap)*: commit
    1.5 ms / render 12.2 ms で、フレームの寿命 50 ms の内側に `KsImage` / ローダー / 先読み /
    通信のサンプルは 1 つも無い。**画像ロードの実装は不在 (自信度 高)**
  - *改善後の trace・試行 2 (3.94 ms/s、Expensive Commit(s))*: commit 17 ms の内側に
    `KsImageRequestFactory.makeContext` が 1 サンプル (約 1 ms、commit の 6%) ある。したがって
    **「不在」とは言えない**。commit の内側のサンプルは 5 件で、内訳は区切り線の更新
    (`updateVisibleCellSeparators` → `configureTouchFeedback`。スタックに現れる UIKit の
    アクセシビリティ呼び出しを含む) 2 / 画像の要求準備 1 / SwiftUI 1 / 空 1。駆動側 (XCTest) の
    サンプルは 0 件。commit 17 ms の間に走行中として記録されたサンプルはこの 5 件だけで
    (他スレッド 0)、残りの時間の帰属は 1 ms 刻みの time profile では示せない。この commit で識別できる最大の費用は足場ではなくライブラリ自身の
    区切り線更新の経路だが、commit 17 ms の残りの帰属は示せておらず、**主因は未特定**
  - *窓全体 (改善後)*: `KsImage` の準備は主スレッドの 0.5%。デコードと通信は全スレッドで 9〜10%
    あるが**すべてバックグラウンドで、主スレッドは 0.0%** である
- **hitch は 1 件 = 1 リフレッシュ**。3 秒窓に 5 ms/s という合格線は 15 ms 相当で、
  1 リフレッシュ (16.7 ms) より短い。つまりこの窓では **「フレーム落ち 0」と同値**の基準に
  なっている。基準そのものが土俵に対して妥当かは、規約 (窓の長さ・閾値) の側の問題である
- **計測の足場のうち「毎フリックの要素解決」は外れたが、自動化の負荷そのものは減っていない**。
  前半の駆動は毎フリックで要素を走査しており、その走査は測る側の主スレッドの 11〜17% を占めて
  いた。改善後は座標を先に確定するためこの走査は区間から外れたが、自動化 (XCTest /
  アクセシビリティ) 全体の占有は改善前 19〜24% → 改善後 34〜37% に**増えている** (上記「限界」)
- **同じ駆動でも fixture により hitch の件数が桁で違う**。対照 (「大量件数」) は 17〜19 件、
  画像グリッドは 0〜1 件。自動化は両方に共通して掛かっているが、大量件数側は主スレッドが
  窓内サンプルの 94% を占めて飽和しており、共通要因だけでは差を説明できない可能性が高い。
  **自動化を掛けない対照が無いため、共通要因の分離は未確認**である

**次の一手 (オーナー判断が要るもの)**

1. **規約 (窓の長さ・閾値) の改訂の要否**。現行の組み合わせが「3 秒間フレーム落ち 0」を要求して
   いることを踏まえ、窓を延ばす / 閾値を見直す / この土俵を別基準にする、のいずれを取るか
2. **「大量件数」の土俵の超過** (対照で 108〜136 ms/s)。本 change の判定対象ではないが、基準機での
   値としては初めて取れたものである。別途の調査・起票が要るかの判断
3. **駆動から自動化の負荷を外すか** (静止待ちをしない入力手段の調査)。同じ調査が 2 つの問題を
   まとめて解く — 投入回数の意味での「連続フリック」が成立し (現状は 3 秒の区間にフリック 1 回 +
   慣性)、区間中に走り続けるアクセシビリティのスナップショット (主スレッドの 34〜37%) も外れる。
   自動化なしの条件が取れれば、上の「共通要因の分離は未確認」も解ける
