# Android 回帰計測 (tasks 7.2)

## 状態

**実施済み・合格。** 3 系統 (相対 P90/P99・絶対 frameOverrun P99・メモリ定常化と件数比) をすべて
基準機で計測し、いずれも合格基準を満たした。**先読み窓の追加によるラッパーの上乗せの増加は
見られない。**

環境: Pixel 4a / Android 13 (SDK 33) / benchmark 構成 (release と同じ最適化 + profileable、
debug 鍵で署名) / Compose BOM 2026.06.01 (compose 1.11.4) / compileSdk 36。
土俵は既存の固定 fixture (「大量件数」と同じ内容を描く計測用の入口、10,000 件・2 列・
行間 / 列間 1dp・固定高と可変行高の混在、プリフェッチの宣言なし)。

前回 (この便の前) の記録は途中で端末側の確認画面に阻まれ、2 列のライブラリ側が欠けていた。
今回はその 1 件を含め、**4 つの土俵を同じ実行内で連続して測り直している** (別々の日に採った値を
突き合わせないため)。

## スクロール性能

`FrameTimingMetric` の 3 試行の集計値。暖機 1 回 + `CompilationMode.Partial`、実座標のフリック
3 秒 × 独立 3 試行。4 つの土俵はすべて同一実行内で連続して計測した。
サーマルスロットリングによる待機は全土俵で 0 秒。

| 土俵 | `frameDurationCpuMs` P50 / P90 / P99 | `frameOverrunMs` P50 / P90 / P99 |
|---|---:|---:|
| ライブラリ 2 列 (`ksCollectionView`) | 4.38 / 6.81 / 8.39 ms | -8.71 / -6.96 / -5.26 ms |
| 比較対象 2 列 (`LazyVerticalGrid`) | 4.42 / 7.26 / 8.78 ms | -8.05 / -6.89 / -4.76 ms |
| ライブラリ 1 列 (`ksCollectionViewList`) | 4.14 / 5.63 / 6.62 ms | -9.82 / -7.44 / -6.50 ms |
| 比較対象 1 列 (`LazyColumn`) | 4.19 / 6.03 / 7.52 ms | -8.95 / -7.12 / -6.40 ms |

### 相対 (ラッパーの上乗せ) — 合格

| 列数 | P90 の比 | P99 の比 | 判定 (劣化 10% 以内) |
|---|---:|---:|---|
| 2 列 | **-6.2%** | **-4.4%** | 合格 (ライブラリ側が速い) |
| 1 列 | **-6.7%** | **-11.9%** | 合格 (ライブラリ側が速い) |

両列とも符号がライブラリ有利側で固まっているため、規約が求める「符号が固まらないときの
独立 2 回実行」には当たらない。なお 2 列のライブラリ側は、この連続計測の直前に単独でも 1 回
実行しており (P90 6.92 / P99 8.40 ms、`frameOverrunMs` P99 -5.64 ms)、上表の値と同じ水準だった。

比較対象には規約どおり既定機能 (行の高さ変化のアニメーション) を `animateContentSize` として
同じ位置に付けてある。したがってこの 10% は「ラッパーの上乗せ」より緩い側の基準であり、
薄さそのものの主張には使わない (規約の注意書きどおり)。**この便の目的は回帰の有無の確認**
であり、対等条件の対照計測は採っていない。

### 絶対 (フレーム落ち) — 合格

`frameOverrunMs` P99 はライブラリ 2 列 -5.26 ms、ライブラリ 1 列 -6.50 ms で、いずれも
合格基準 (0.0 ms 以下) を満たす。

### 前回値との比較

前回計測 (この変更の前) の同じ土俵の値は
`../../archive/2026-09-05-android-wrapper-foundation/evidence/performance-measurement.md` にある。
1 列の前回値は P90 5.70〜5.76 ms / P99 6.53〜7.01 ms で、今回の 5.63 / 6.62 ms はその範囲の内側。
先読み窓の追加による上乗せは、宣言なしの土俵では現れていない (宣言が無いときは `LazyGridState`
の観測そのものを起動しないため、期待どおりの結果)。

## メモリ

往復ごとの PSS 合計 (アプリ自身の記録)。暖機と本計測をそれぞれ独立した実行として記録した。
`通過` はその往復で載った項目の数で、件数と一致していることが走査の空振りが無かった証拠になる。

| 件数 | 実行 | 往復 1 | 往復 2 | 往復 3 | 増分 (1→2 / 2→3) | 通過 | 判定 |
|---|---|---:|---:|---:|---|---:|---|
| 10,000 | 実行 A | 110,000 KB | 110,867 KB | 110,945 KB | +0.79% / +0.07% | 10,000 | 3 往復で定常 |
| 10,000 | 実行 B | 102,954 KB | 103,059 KB | 103,379 KB | +0.10% / +0.31% | 10,000 | 3 往復で定常 |
| 1,000 | 実行 A | 108,456 KB | 102,277 KB | 103,559 KB | -5.70% / +1.25% | 1,000 | 3 往復で定常 |
| 1,000 | 実行 B | 100,309 KB | 94,066 KB | 94,361 KB | -6.22% / +0.31% | 1,000 | 3 往復で定常 |

判定: **定常化を確認した**。4 実行すべてが上限 10 往復のうち 3 往復で定常に達し、往復ごとに
全項目を通過している。減少は「増え続けていない」として定常に含める規約どおりの読みである。

件数比の判定: 定常値の比は 10,000 件 / 1,000 件で **実行 A が 1.07 倍、実行 B が 1.10 倍**。
件数比 (10 倍) に比例していない (仮想化が効いている)。

計測の枠組み側の記録 (走査終了時点、`MemoryUsageMetric` Last):

| 件数 | heap | RSS(anon) | RSS(file) | GPU |
|---|---:|---:|---:|---:|
| 10,000 | 8,081 KB | 57,428 KB | 101,544 KB | 61,988 KB |
| 1,000 | 5,629 KB | 51,776 KB | 98,548 KB | 61,996 KB |

## 判定

Android 性能検証の規約が求める 3 系統をすべて満たしたため、**この変更は「大量件数」の土俵で
性能面の回帰を起こしていない**と判定する。

生の結果ファイル (Macrobenchmark の JSON と Perfetto トレース) は手元保管であり、ここには
判定に使った集計値だけを載せている。
