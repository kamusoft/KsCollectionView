# 画像の挙動の観測 (プリフェッチの共有・取り消し・戻り・既定表示)

tasks 7.3 / 7.4 の証跡。性能ではなく**挙動**の確認であり、判定は数値ではなく
「どの層から取得したか」「要求が起きたか / 取り消されたか」で行う。

**確認できている範囲**: ローダー付属ビューとのキャッシュ共有、画面外へ出た読み込みの取り消し、
読み込み中と失敗の既定表示、消去後の再取得。
戻ってきたときに読み込み中を経由しないことは、**両プラットフォームの基準機で確認済み**
(Android 2026-09-08 / iOS 2026-09-08。計数の基準点機構による。下記「戻ってきたときの再表示」)。
**限界**: iOS では、基準点の時点で画面の外にあった要素 (ID 13〜15) が送りの途中で 1 回ずつ
読み込み中を経由した。判定の対象は「戻った範囲」であり、この 3 件は戻りではなく送りで起きて
いる (下記 iOS の節に区間ごとの内訳を残した)。

## 観測手段 (これを選んだ理由)

静止画では読み込み中・取り消し・再取得のような一瞬の出来事を捉えられないため、
**要求の一生をログで観測できる手段**を先に用意してから判定した。

| プラットフォーム | 手段 | 分かること | 限界 |
|---|---|---|---|
| iOS | Sample の起動引数 `--observe-image-loading` で共有パイプラインに観測用の割り込み処理を付け、あわせてローダー自身の計測記録を有効にする。`log stream` で 2 系統を収集 | 表示要求の開始 / 取り消し / 成功 (メモリ・ディスク・ネットワークのどこから来たか)、元データ取得の開始 / 取り消し / 完了 | 到達点がディスクまでの先読みは**元データの取得として走り、割り込み処理に通知が来ない**。この経路の件数はローダーの計測記録側で数える。到達点がメモリまでの先読みと、ローダー付属のビューの直接表示は**互いに区別できない** (どちらも縮小の指定を持たない素の要求になる) |
| Android | Sample の計測構成で共有インスタンスの ImageLoader に観測用の通知を付ける (`installImageLoadingObserver`)。`logcat` のタグ `KsImageObserve` を数える | 開始 / 取り消し / 成功 (どの層から来たか) と、要求に付いた指定 (メモリキャッシュ方針・寸法一致の指定) | 到達点がメモリまでの先読み・表示要求・ローダー付属のビューの直接表示は、要求に付く指定が同じで**互いに区別できない**。**ディスクまで**の先読みだけが `mem=DISABLED` で見分けられる |

ログの種別 (`kind=`) は、この限界をそのまま名前に出す。区別できる要求だけが `prefetch-disk`
(Android) / `display` (iOS) のように単独の名前を持ち、区別できない組み合わせは
`display-or-memory-prefetch` (Android) / `prefetch-or-loader-display` (iOS) という曖昧な名前で
記録される。**曖昧な種別の件数を、どちらか一方の件数として集計してはならない** — 土俵の作りから
片方しか生まれないと言える場合に限り、その旨を書いたうえで一方として読む (計測資料の集計規則を
参照)。

観測用のコードの入り方はプラットフォームで非対称である。**iOS は release の Sample にも
含まれる**が、起動引数 (`--observe-image-loading` / `--verify-image-behavior`) を渡さない限り
到達せず不活性である。**Android は計測用のソースセット限定**で、配布する構成 (release) の
成果物には含まれない。

環境: iPhone 17 Pro Simulator (Debug 構成) / Android エミュレータ API 35 (Debug 構成)。
いずれも挙動の確認であり、性能値はここでは測らない (性能は
[iOS 性能検証の手順と合格基準](../../../handbook/ios/performance-verification.md) と
[Android 性能検証の手順と合格基準](../../../handbook/android/performance-verification.md) の手順に従う)。

## 7.3 ローダー付属ビューとキャッシュを共有する

手順は両プラットフォームで同じ。アプリを入れ直して (Android は保存領域を消して) キャッシュを空にし、
検証画面を開き、先読み (到達点はメモリまで) が走った ID を記録してから、同じ URL を
**ローダー付属のビューだけで組んだ表示**に切り替え、その要求がどの層から返ったかを見る。

この観測ではログの種別を切り分けに使っていない (先読みもローダー付属のビューも同じ曖昧な種別に
入るため)。切り分けは**切り替えの前後という時間の順序と取得元の URL** で行い、判定に使うのは
「どの層から返ったか」だけである。

### iOS (`LazyImage`)

先読みが走った ID: 16〜27 (12 件、すべて完了)。切り替え後にローダー付属のビューが要求した ID は
13〜36。

| 切り替え後の要求 | 件数 | 取得元 |
|---|---:|---|
| ID 13〜15 (先読みではなく直前に表示した ID) | 3 | ディスク |
| ID 16〜27 (先読み済み) | **0** | 要求そのものが起きない (メモリ上の画像を同期で返すため) |
| ID 28〜30 (先読みも表示もしていない ID) | 3 | ネットワーク |

判定: **共有されている**。先読みで取り込んだ 12 件は、ローダー付属のビューから要求が 1 件も
出ていない。ネットワークへ出たのは先読みしていない ID だけである。

### Android (`AsyncImage`)

先読みが走った ID: 13〜24 (12 件)。切り替え後にローダー付属のビューが要求した ID は 13〜36。

| 切り替え後の要求 | 件数 | 取得元 |
|---|---:|---|
| ID 13〜24 (先読み済み) | 12 | **メモリキャッシュ** |
| ID 25 以降 (先読みしていない) | 12 | ネットワーク |

判定: **共有されている**。再ダウンロードは起きていない。

## 7.4 画面外へ出た読み込みの取り消しと、戻ってきたときの再表示

土俵は Sample「画像グリッド」(10,000 件・3 列・プリフェッチはディスクまで)。

### 取り消し

| プラットフォーム | 操作 | 開始 | 取り消し | 完了 |
|---|---|---:|---:|---:|
| iOS | 3 秒相当の速いフリック 4 回 | 元データ取得 183 / 表示要求 254 | 元データ取得 48 / 表示要求 53 | 元データ取得 135 / 表示要求 201 |
| Android | 速いフリック 5 回 (取得を遅くするため回線を絞った) | 先読み 42 / 表示要求 36 | 先読み 8 / 表示要求 3 | 先読み 3 / 表示要求 12 |

判定: **取り消されている**。iOS の表示要求の失敗は 0 件で、取り消し以外の理由で終わった要求はない。

Android は回線が速いままだと窓が動く前に取得が終わってしまい取り消しが観測できなかったため、
エミュレータの回線速度を落として観測した (この操作はエミュレータのコンソール指定で行い、
観測後に元へ戻している)。「取り消しが観測できない = 起きていない」ではなく、
**取り消しが起きる状況を作ってから観測した**。

### 戻ってきたときの再表示 — **両プラットフォームとも合格**

土俵は Sample「画像グリッド」相当の計測用の経路 (10,000 件・3 列)。判定は
**基準点からの差分 `Δsized == 0`** で行う (下記「判定の手順」)。

環境 (この観測のみ): Pixel 4a / Android 13 (SDK 33) / Sample の debug 構成 /
Compose BOM 2026.06.01 / compileSdk 36。基準機であり代替機ではない。この節の値は
エミュレータではなく実機で取っている (他の節はエミュレータ / Simulator)。

#### 手順 (実施した通り)

1. 数えることを要求して起動する (`ks_count_image_loading_slots` を立て、
   `ks_reset_image_cache` でキャッシュを空にする)。経路は
   `measurement/image/10000/disk` と `measurement/image/10000/memory`
2. 初回表示の収束を待つ (印が `session=0` で `items=15` に落ち着く)
3. 印を叩いて基準点を切る (`session=1` に進み、差分がすべて 0 になることを画面で確認)
4. 縦のドラッグ 3 回で送る (可視の先頭が ID 1 → 28。9 行 = 約 2.2 画面)。同じ操作を逆向きに
   3 回行って戻す (可視の先頭が ID 1 に復帰。表示サイズは終始同じ)
5. 印とログを突き合わせて判定する

#### 結果 (到達点ディスク)

| 時点 | 印 (`slots …`) | 可視 ID |
|---|---|---|
| 初回表示の収束後 | `session=0 items=15 sized=15 unsized=0 lines=15 total=15/0/15` (ID 1〜15 が各 `1/0`) | 1〜12 |
| 基準点を切った直後 | `session=1 items=15 sized=0 unsized=0 lines=0 total=15/0/15` (ID 1〜15 が各 `0/0`) | 1〜12 |
| 2 画面送った後 | `session=1 items=45 sized=30 unsized=0 lines=30 total=45/0/45` (ID 16〜45 が各 `1/0`) | 28〜39 |
| **同じサイズで戻した後** | `session=1 items=45 sized=30 unsized=0 lines=30 total=45/0/45` (**変化なし**) | 1〜12 |

logcat (タグ `KsImageLoadingSlot`) との突き合わせ:

| 確認 | 値 |
|---|---|
| `session=1` の行数 | 30 (印の `lines=30` と一致) |
| `session=1` に現れる要素 ID | 16〜45 が各 1 行のみ (飛びなし) |
| **対象 ID (1〜15) の `sized` が増えた行** | **0 行** |
| `unsized` の行 | 0 行 |

判定: **合格**。戻った範囲の対象 ID (可視 1〜12 を含む構成済み 1〜15) はすべて
`Δsized == 0` であり、読み込み中の表示を経由せずに再表示されている。
**空振りでないことの裏付け**は、同じ観測区間で初めて構成された ID 16〜45 が
`Δsized == 1` を記録していること (計数はこの区間で生きている)。

#### 結果 (到達点メモリ) — 先読みの `allowHardware(false)` 撤去後

オーナー判断 C で先読みからハードウェア支援を切る指定を外した現行コードで取り直した値
(2026-09-08 後半)。撤去前の値は下の「[前回 (暫定回避適用中)](#前回-暫定回避適用中-の到達点メモリ)」に残す。

| **同じサイズで戻した後** | `session=1 items=39 sized=24 unsized=0 lines=24 total=39/0/39` (**変化なし**) | 1〜12 |

|---|---|
| `session=1` の行数 | 24 (印の `lines=24` と一致) |

判定: **合格**。戻った範囲の対象 ID (可視 1〜12 を含む構成済み 1〜15) はすべて `Δsized == 0` で
あり、読み込み中の表示を経由せずに再表示されている。**空振りでないことの裏付け**は、同じ観測
区間で初めて構成された ID 16〜39 が `Δsized == 1` を記録していること (撤去前と違い、この区間の
中で陽性対照が成立しているため、印を叩き直した別区間は要らなかった)。

**撤去前と変わった点**: 到達点メモリでも**送り先の初出の要素は読み込み中を経由するようになった**
(撤去前は 0 行、撤去後は 24 行)。オーナー判断 C の帰結 — 先読みが載せた元寸は実機ではグラフィックス
側に置かれて画素を読めないため、初回の描画に使わずローダーの縮小デコードを待つ — がそのまま

判定に使う「戻った範囲」の要求 (メモリキャッシュにあれば経由しない) は満たしている — 戻る先の
表示鍵の項目は表示サイズでメモリに載っているためである。

送り出しの距離はこの実行で可視の先頭 ID 1 → 22 (7 行) で、撤去前の実行 (1 → 28、9 行) より
わずかに短い。ドラッグの操作量は同じ 3 回だが、実座標の操作のため到達位置は実行ごとに揺れる。
判定対象 (ID 1〜15) が完全に画面外へ出ている条件は満たしている。

一連の操作の間に `FATAL EXCEPTION` は 0 件で、プロセスは生存したままだった
(到達点メモリのクラッシュ修正が実機で保たれていることの再確認。
`image-grid-memory-prefetch-crash-fix-android.md` の A/B と同じ向き)。

#### iOS の観測 (2026-09-08、実機)

環境 (iOS のこの観測のみ): iPhone 11 / iOS 18.7.8 / Sample の Debug 構成。基準機であり代替機
ではない。この節の値は Simulator ではなく実機で取っている (iOS の他の節は Simulator)。
Android の実機計測便と同じ Mac で並走して取得した (計数であり時間の計測ではないため、
並走は値に影響しない)。

手順は Android と同じ 5 段で、操作だけ画面の大きさに合わせている。数えることを要求して起動し
(`--screen 画像グリッド --count-image-loading-slots`、到達点は `--prefetch` で与える)、
試行ごとにアプリを入れ直してキャッシュを空から始める。初回表示の収束を待ってから印を叩き、
縦のドラッグ 3 回で送り (可視の先頭が ID 1 → 22。約 2 画面)、同じ操作を逆向きに 3 回行って戻す
(表示サイズは終始同じ)。操作は計測用の駆動テスト
(`samples/ios/KsCollectionViewSamplesUITests/PerformanceDriverUITests.swift` の
「画像グリッドで基準点を切り送って戻す」) が実座標のドラッグで行う。

**ログの採り方が Android と異なる**。iOS の実機のログは手元の道具では `log stream` で追えず
(端末を指す口が無い)、`log collect` は root を要求するため、**Instruments の記録**
(`xctrace record --template Logging --attach <アプリのプロセス>`) から取り出した。
プロセスを絞らずに端末全体を記録すると**行が落ちる** (同じ手順で 45 行のうち 19 行しか残らない
実行があった)。落ちた分はそのまま合格側に倒れるため、**印の `lines` と行数が一致した記録だけを
判定に使う**。下の 2 つはいずれも一致している。

##### 判定

**合格** (両到達点)。戻った範囲の対象 ID (可視 1〜12) はすべて `Δsized == 0` であり、読み込み中の
表示を経由せずに再表示されている。**空振りでないことの裏付け**は、同じ観測区間で送り先の
初出要素 (ID 16〜45 の 30 件) が**すべて** `Δsized >= 1` を記録していることである。

行数の帰属は次のとおり (印の `lines` と突き合わせる「`session=1` の全行数」と、送り先の初出要素の
行数は別の数である)。

| 数える対象 | ディスク | メモリ |
|---|---:|---:|
| `session=1` の全行数 (印の `lines` と一致) | 45 行 | 39 行 |
| うち ID 13〜15 (基準点の時点で構成済み・画面外) | 3 行 | 3 行 |
| うち **送り先の初出要素 (ID 16〜45)** | **42 行** | **36 行** |
| うち ID 1〜12 (判定対象) | 0 行 | 0 行 |

送り先の初出要素は 30 件だが行数がそれを上回るのは、同じ要素が観測区間の中で 2 回構成されて
いるためである (ディスクは ID 19〜30 の 12 件、メモリは ID 19〜21 と 28〜30 の 6 件が 2 行ずつ)。

**判定に含めなかったもの**と、その理由:

- **ID 13〜15 (各 `Δsized == 1`)**: 基準点の時点で構成されてはいたが画面の外にあり、絵が
  メモリに載りきったことを確かめていない。判定の手順 1 が求める「対象がメモリキャッシュに
  あることを確認してから送る」を満たすのは、実際に表示されていた 1〜12 である。行が出た位置も
  戻りではなく**送りの始め**であり、「戻ってきたときの再表示」の観測ではない
- **ID 19〜21 (戻す区間で 2 回目)**: 送りの途中を通り過ぎただけの中間帯で、絵が届く前に画面外へ
  出た可能性がある (この土俵では画面外へ出た取得が取り消されることを別の節で観測している)。
  **どちらだったかはこの計測では確かめていない** — 手順 5 の「メモリから追い出されていた場合は
  別条件として記録する」に倣い、戻った範囲の判定には入れずに記録だけ残す

なお、iOS では到達点をメモリにしても送り先の初出の要素 (ID 16〜45) は読み込み中を経由する
(ディスクの 45 行に対しメモリで 39 行と減りはするが 0 にはならない)。この点は**暫定回避の
撤去後の Android と同じ形**である (撤去前の Android だけが、送り先の初出も経由しない状態だった)。
spec はこの点を要求していない (要求は「メモリキャッシュにあれば経由しない」であり、
先読みが表示に間に合うことまでは求めていない) ため、判定には影響しない。

#### 前回の観測 (2026-09-07、判定に使えない)

| プラットフォーム | 操作 | 戻った範囲の表示要求 | 取得元 | 静止画 |
|---|---|---:|---|---|
| iOS | 2 画面送って 2 画面戻す | **0 件** | 要求が起きない | `image-grid-after-return-ios.png` |
| Android | 2 画面送って 2 画面戻す | 36 件 | メモリキャッシュ 33 / ディスク 3 / ネットワーク **0** | `image-grid-after-return-android.png` |

**測れているのはネットワークへ出ていないことだけ**であり、「読み込み中の表示を経由しない」は
この観測からは言えない。理由は 2 つある。

- **Android の数値が結論に反している。** 読み込み中を省略できるのは、表示の組み立てと同時に
  メモリから同期で画像を引き当てられた場合だけである。ディスクから返る 3 件は非同期の
  デコードを待つため、読み込み中の表示を経由する。つまり同じ表の「ディスク 3」が、
  同じ表の判定を否定している
- **静止画は過程を写せない。** 一瞬だけ挟まる読み込み中は、収束後の静止画には残らない。
  「静止画に読み込み中が無い」は非発現の根拠にならない

#### 判定の手順 (測っていないことを測ったことにしないため、条件を先に固定する)

1. 最初の表示が完了し、対象がメモリキャッシュにあることを確認してから画面外へ送る
2. 送る直前に**画面の印を叩いて観測区間を切る** (基準点)。初回表示の分を判定に混ぜないため。
   印の `session=` が 1 つ進むことで、切れたことを確かめる
3. 同じ表示サイズで戻す (サイズが変わると別の鍵になり、条件が変わる)
4. **読み込み中スロットの構成回数が、基準点からの差分で 0 であること** (`Δsized == 0`) を直接
   数える (取得回数やネットワーク件数では代用しない)。累計では判定できない — 初回表示で
   `sized` は通常 1 以上になるため
5. メモリから追い出されていた場合は別条件として記録し、ディスクから再デコードする際の
   読み込み表示と混同しない

証跡には**対象の要素 ID ごとに基準点の前後の値**を残す。すなわち、基準点を切る直前の印
(累計 `total=`) と、戻した後の印 (差分 `sized` / `unsized` と要素ごとの内訳
`<ID>:<Δsized>/<Δunsized>`) の両方を、同じ `session=` の logcat / `log stream` の行と
突き合わせたうえで記録する。合格の条件は、戻った範囲の対象 ID がすべて `Δsized == 0` で
あること。**空振りでないことの裏付け**として、同じ区間で `Δsized >= 1` になる範囲
(追い出された範囲、または初めて構成された範囲) を併せて記録する。それが同じ区間に無いときは、
印を叩き直した別区間で陽性対照を取る (上の到達点メモリの `session=2` がその例)。

突き合わせの注意 (下の `log show` / `log stream` は **Simulator の話**である。実機のログは
これらでは追えないため、上の iOS の節に書いた Instruments の記録から取り出す。落ちる向きは
どちらも同じで、行が減れば合格側に倒れる): iOS の計数ログは `Logger.info` のため
`log show` / `log stream` に `--info` が要る
(落とすと 0 行になり合格側に倒れる)。また `log show --info` は起動直後の行を落とすことがあるため、
**基準点より前の値は印の `total=` から取り、ログから数え直さない**。判定する区間 (基準点以後) は、
その `session=` の行数が印の `lines` と一致することを先に確かめてから読む。印の要素別内訳は
上限 20 件で溢れるため、溢れた対象 ID はログ側で `sized` が増えた行が無いことを見る
(上の到達点ディスクの記録がこの形になっている — 判定対象の ID 1〜15 は差分 0 のため
内訳の 20 件に入らず `more=25` に回っており、ログ側で 0 行を確かめている)。

なお、戻り以外の経路については自動テストで構成回数 0 を直接数えているものがある
(Android の `KsImageTest.loadingSlotIsNeverComposedWhenTheImageIsAlreadyInMemory`)。

#### 測り直しに足りていなかったもの (Android、2026-09-07 の便で判明。**現在は解消済み**)

以下は当時の記録である。現在は両プラットフォームの Sample に、計測できる構成だけで読み込み中
スロットを差し込んで数える仕組み (`ImageLoadingSlotCounter`、画面の印 `ImageLoadingSlotMark` と
基準点機構) があり、上の手順 4 の「基準点からの差分を直接数える」はそれで行う。

当時: 手順 4 (当時の手順 3) の「読み込み中スロットの構成回数を直接数える」を実機で行う手立てが、
当時の Sample に無かった。デモ画面と計測用画面が共有するセル (`ImageGridCell`) は `KsImage` に読み込み中の
スロットを渡しておらず、既定の表示に任せている。数を取るには、計測できる構成だけで
読み込み中のスロットを差し込んで数える仕組み (テンプレート呼び出しカウンタに相当するもの) を
新たに置く必要がある — セルは配布する構成と共有しているため、置き方はその共有を壊さない形を
選ぶ判断が要る。この便では計測だけを担当範囲としたため、その追加は行っていない。
