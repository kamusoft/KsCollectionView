# 「並べ替え」(iOS) の手動フリック計測: 変更前と「番号を付けずに入れ物を使い回す形」 — 2026-10-04

> **この記録と最終の形の関係。** 最終の形は「iOS 18 以降だけ入れ物を使い回す。iOS 18 より前の版は変更前のまま作り直す」(ios/ADR-0012)。この記録の「変更後」は、最終の形が決まる前に作った「番号を付けずに入れ物を使い回す」変種で、基準機 (iOS 18.7.8) では最終の形と同じ動きをする (中身を外さない・何も付けない)。ただし最終の形のソースからビルドしたバイナリではない。本文の「作業ツリーの案 A (番号を付ける形)」は記録した時点の作業ツリーのことで、いまの作業ツリーではない。

セルの中身のホスティング (入れ物) を再利用で使い回すと、基準機で何が変わるかを見るための記録である。変更前と変更後を同じ日に 1 走行ずつ採った。Simulator での計測は perf-hosting-reuse-stage1.md にある。体感の合否はオーナーの判定で、「判定」の節に書いた。

比べた 2 つ:

| 記号 | 中身 |
|---|---|
| 変更前 | HEAD。再利用のたびに `prepareForReuse` で中身を外し、入れ物を作り直す |
| 変更後 | 作業ツリーから、テンプレートの中身に付ける番号 (`.id`) だけを外した変種。再利用で中身を外さず、入れ物を使い回す。内部 state を戻す処理はライブラリに無く、OS まかせ。**作業ツリーの案 A (番号を付ける形) そのものではない** |

## 数値 (証跡。合否ではない)

取得源: 2 つの trace を `xctrace export --xpath` で書き出した表 (hitches-summary / display-surface-swap / device-thermal-state-intervals / device-display-info / time-profile / potential-hangs)。区間は display-surface-swap の hid-time 列を使い、入力の空白 3 秒で切った。hitch はその開始時刻で区間に入れた。主スレッドの稼働率は、time-profile の主スレッドの標本 (1 標本 1 ms) を区間の長さで割った値。

## 判定

- 体感の合否: 合格 (オーナーの判定。「変更前・変更後とも特に問題なし。2 つで変わらない」。変更前より悪くなっていない)。判定の対象は「並べ替え」の 1 走行ずつで、変更後は識別の値を付けない変種のビルドである (冒頭の断り書き)
- 数値との一致・不一致 (観測): 体感は 2 つで変わらないが、数値は違う。変更後は hitch がすべて 1 フレームで High が 0 件、入力の遅れの候補が 0 件、入れ物の解放の帰属が 9.8 % → 0.1 %。両方をそのまま残す
- 前回との比較可否: 変更前と変更後は、同じ日・同じ端末・同じ fixture の記録だが、**操作の量が揃っていない** (上の「操作の量」)。件数・合計の hitch 時間・hitch time ratio は、差の向きを見る材料にとどめる。2026-09-30 の記録 (drag-reorder の体感ゲート) とは別の走行で、比べない

### 読み取れること (観測)

- 入れ物の解放と生成は、変更後の主スレッドの標本からほぼ消えた (解放 972 → 8 標本、生成 252 → 9 標本)。変更前に解放が載っていた `objc_autoreleasePoolPop` も 10.0 % → 0.5 % になった。Simulator の計数 (生成と解放が 0 になる) と合う
- セルの生成の経路の比が 40.9 % → 25.7 % に下がった。下がった内訳は、解放 (−9.7 ポイント)、中身の設定 (10.7 % → 3.0 %)、セルの取り出し (12.4 % → 6.4 %)、`prepareForReuse` (5.0 % → 1.4 %) である
- hosting の `layoutSubviews`・自己サイズ・SwiftUI の graph の更新の比は、下がっていない (34.4 → 36.9 %、16.9 → 14.8 %、37.7 → 43.7 %)。入れ物を使い回しても、中身の組み立てと計測の仕事は残っている
- hitch 1 件の長さは短くなった。変更前は 2〜4 フレームの hitch が混ざる (最長 66.66 ms)。変更後はすべて 1 フレーム (最長 16.68 ms)
- 主スレッドの稼働率が近い窓どうしでも、変更後のほうが hitch time ratio が小さい (最初の 5 秒: 50.9 % で 145.5 ms/s に対し 41.1 % で 13.3 ms/s。最後の窓: 71.7 % で 508.9 ms/s に対し 66.0 % で 165.7 ms/s)。ただし窓の長さと稼働率は揃っていない

### 読み取れないこと

- hitch の件数・合計時間が減った分のうち、どれだけが変更の効果で、どれだけが操作の違い (速さ・距離・休止の入り方) によるかは分けられない。変更後のほうが swap と入力は多いが、通った項目の数は分からない
- 段階ごと (初回 / 再訪 / 連続) の比較。どちらの記録も、入力の時刻から 3 つの段階を切り出せない
- **作業ツリーの案 A (番号を付けて state を戻す形) の基準機での値。** この記録の「変更後」は番号を付けない変種である。Simulator (iOS 18.6) では、案 A は番号を付けない形より主スレッドの CPU 時間が中央値で 5〜33 % 重かった (perf-hosting-reuse-stage1.md)。案 A が基準機でどこまで効くかは、この記録からは言えない
- キャッシュ状態の違い (上書きインストールと入れ直し) と、間の 30 分に別の作業が端末を使ったことの影響

### 推測

- 変更前の 2〜4 フレームの hitch は、次の項目のセルを用意する最中に前の入れ物を解放する仕事 (1 項目あたりの固定の上乗せ) が、コミットを 1 フレームの枠から押し出していたためと読む。変更後に hitch が 1 フレームに収まったことと合う。ただし操作が違うので、確かめたとは言えない

## 限界

- 記録は変更前・変更後とも 1 走行ずつ。計測器なしの対照は行っていない
- 操作の量が 2 つの記録で揃っていない。依頼した操作列と、記録の入力の時刻の対応も取れていない。向きと到達した項目の番号は記録に残らない。初回で末尾に着かなかったことはオーナーの回答による
- 体感は「2 つで変わらない・どちらも特に問題なし」だけで、段階ごとの体感とムラの有無は聞き取れていない
- キャッシュ状態の揃え方が 2 つで違う (変更前は上書き、変更後は入れ直し)。2 つの記録の間に約 30 分あり、別の作業が同じ端末を使っていた
- 文字サイズ (端末の設定) は記録していない
- 「変更後」は番号 (`.id`) を付けない変種で、内部 state を戻す処理を OS に任せる。作業ツリーの案 A とは別の形である。iOS 18 系より前の版での state の動きは確かめていない
- 不一致率 (Debug 構成) とメモリは採っていない
- 帰属は関数名の一致で数えた (例: 名前に `_UIHostingView` と `layoutSubviews` を含むフレーム)。Instruments の画面の集計とは数え方が違いうる
- thread-info の書き出しで、XML に表せない 1 文字を飛ばした通知が出た (この証跡で使った表は書き出せた)
- 生の trace と表の全件の書き出しは evidence に置いていない (スクラッチにのみ置いた)
