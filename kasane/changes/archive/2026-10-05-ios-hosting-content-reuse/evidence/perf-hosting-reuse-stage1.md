> **この記録と最終の形の関係。** 最終の形は「iOS 18 以降だけ入れ物を使い回す。iOS 18 より前の版は変更前のまま作り直す」(ios/ADR-0012)。この記録が測ったのは、最終の形が決まる前の 3 つの変種である: H (変更前)、A (どの版でも番号を付ける案。採らなかった)、F (番号を付けずに使い回す)。iOS 18 以降での最終の形の動きは F と同じで、A ではない。本文の「案 A = 作業ツリー」「やめる基準」は記録した時点の話で、経緯として残している。最終の形の確認は verify-hosting-reuse-stage2.md と verify-hosting-reuse-ios17.md の末尾にある。

## 結論 (先に)

- **入れ物 (hosting) の生成と解放は減った。** 案 A では、スクロール中の生成が最初のセルの数だけ (9)、解放が 0 になった。上限の参考と同じ計数である
- **主スレッドの CPU 時間は、案 A の範囲が「今のまま」の範囲と重なった。** 2 つの OS × 2 つの一覧 × 2 つの向きの 8 区画すべてで重なった。中央値は 8 区画すべてで案 A のほうが小さい (−1.5 〜 −8.0 %) が、走行ごとのばらつきと区別できない
- したがって、やめる基準の 2 つ目 (「案 A の CPU 時間の範囲が今のままの範囲と重なる」) に当たる
- **1 回目は iOS 18.6 で測れていない。** 1 回目の時点では、この Mac に iOS 18.6 のランタイムが無かった (入っていたのは iOS 26.0 と 27.0 だけ)。測れたのはテストの既定の版 (iOS 27.0) で、iOS 26.0 は代わりの参考として測った。iOS 18.6 は後から測り足した (末尾の「測り足し: iOS 18.6」)。そこでも案 A の範囲は「今のまま」と 4 区画すべてで重なった

## 読み (推測)

- 入れ物の生成と解放を無くした分の節約は、この土俵 (軽い 1 行の文字だけの行、Mac の Simulator) では主スレッドの CPU 時間の数 % で、走行ごとのばらつきより小さいと読む。切り分けのときの「−4〜8 %、1 走行ずつ、ばらつきの内側」という見立てと同じ水準である
- 案 A が状態を戻すために足した組み立て直し (`.id` の変化) の費用は、F との比較では読み取れなかった。A と F の差に一貫した向きが無い (iOS 27.0 では A が軽く、iOS 26.0 の none では F が軽い)
- 基準機 (iPhone 11 の実機) では、入れ物の解放が主スレッドの標本の 10.5 % を占めていた。Simulator の数 % より大きく出る可能性はあるが、この計測からは言えない
- 走行ごとの値には 1200〜1400 ms 台の低い値が散発的に混ざる (観測: 1450 ms 未満は A に 4 区間、F に 10 区間。H には無く、H の最小は 1500)。A と F の範囲が下へ広いのはこのためである。入れ物を使い回す形でだけ起きる軽い走行なのか、たまたまの揺れなのかは確かめていない

## テスト (観測)

- 作業ツリー (案 A) で iOS 本体のテスト全件: `Executed 530 tests, with 0 failures` (148.5 秒)。Simulator は iPhone 17・iOS 27.0 (この作業のために作った `ksn-hosting-reuse-27`。計測の後に削除した)、Debug 構成
- 既存の `KsCollectionScenarioTests` の「セルの再利用が起きる距離を往復するとテンプレートの state は初期値へ戻る」は、変えずに通った
- **同じテストは、上限の参考 F (識別の値を付けず、中身も外さない) でも iOS 27.0 と iOS 26.0 の両方で通った。** この 2 つの版では OS 自身が再利用のときに状態を初期値へ戻している。したがってこのテストは、この 2 つの版では「ライブラリが付けた識別の値で状態が戻ること」を確かめていない (識別の値を外しても通る)

## 限界

- ここまでの節は iOS 18.6 (基準機と同じ系統) を含まない。iOS 26.0 の値は代わりの参考で、iOS 18.6 の結果の代用にはならない。iOS 18.6 の値は末尾の「測り足し: iOS 18.6」にある
- Simulator の値は Mac の上のもので、基準機の hitch は再現できない。比べたのは主スレッドの CPU 時間と計数だけ
- 自動スクロールは一定の速さで送っており、オーナーのフリックとは速さも慣性も違う (診断用)
- 計測の間、この作業のものではない Simulator が 3 台起動していた (ほかの作業のもので、止めていない)。ばらつきの一因になりうる
- 行はどれも 1 行の文字だけで軽い。利用者が重いセルを書いたとき、状態を戻すための組み立て直しと入れ物の作り直しの差がどうなるかは測っていない
- 状態を戻す処理が二重になっている (OS とライブラリ) かどうかの費用は、切り分けていない。iOS 16・17 のランタイムも無く、OS が戻さない版での動きは確かめていない
- 前の見た目・高さ・`onAppear` と `.task`・メモリは、この段階では確かめていない (第 2 段階)
- プローブ・複製・ビルドの生成物はスクラッチにだけ置いた。作業ツリーの `ios/` と `samples/` にプローブは入れていない

### 読み (推測)

- iOS 18.6 では、入れ物を使い回すこと自体の効果 (F) は主スレッドの CPU 時間の 1〜3 割ある。しかし案 A は、状態を戻すために中身を別物として作り直すので、その効果の大半を使ってしまうと読む。残るのは数 % で、ばらつきと区別できない
- 識別の値の位置 (内側 / 外側) では差が出なかった。作り直しの費用は、利用者のテンプレートの中身の側にあると読む
- iOS 26.0・27.0 で F の効果が小さかったのは、OS の側の再利用の費用が版で違うためかもしれない。確かめていない
