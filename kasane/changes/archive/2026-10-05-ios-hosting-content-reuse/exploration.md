# Exploration: ios-hosting-content-reuse

## 課題 / 動機

iOS エンジンで、セル (`KsHostingCell`) そのものは再利用されているが、`prepareForReuse` で `contentConfiguration = nil` にしているため (`ios/Sources/KsCollectionView/KsHostingCell.swift:171`)、表示に入る項目ごとにセルの中身の hosting (`UIHostingConfiguration` の中身) が作られて捨てられている。

`drag-reorder` (L 級) の tasks 6.2 (基準機 iPhone 11 の体感ゲート、2026-09-30) で、「並べ替え」画面の hitch の数値がページング画面より大きく悪かったため原因を切り分けて見つかった (`kasane/changes/archive/2026-10-01-drag-reorder/evidence/perf-diag-ios-reorder-cells.md`)。

- 基準機の trace: 主スレッドのコミット中の処理の内訳はセルの生成 42%・hosting の layoutSubviews 37%・自己サイズ 18%・hosting view の解放 10.5%。解放は、次のセルを用意する最中の `objc_autoreleasePoolPop` の中で、再利用で捨てた前の中身の解放 (`tearDown` → `GraphHost.invalidate`) として起きていた
- Simulator の計数 (iPhone 11 / iOS 18.6、10,000 件・100 件ずつのグループ・見出しの固定・下向き 450 フレーム): セルの生成は 9 件だけ、hosting の生成 / 解放は表示した項目 1 件ごとに 1 回 (399 / 390)。変更前のコード (HEAD) でも同じ計数で、drag-reorder の変更で入ったものではない
- 参考の変種 (`contentConfiguration = nil` を外したもの、1 走行ずつ): hosting の生成・解放が 0 になり、主スレッドの CPU 時間が 4〜8% 下がった
- 体感ゲート (cross/ADR-0006) はオーナーの体感で合格しており、実害は数値の側だけ

オーナー判断で別 change として簡易起票した (drag-reorder のスコープ外で、nil にしている前提の確認が要るため)。

### 探索で確かめたこと (2026-10-04)

コードとテスト:

- 中身を外している理由は ios/ADR-0002 (accepted)。「セル再利用時はホスティングを作り直し、セル内の SwiftUI の状態は保持しない」と決めており、`contentConfiguration = nil` はその手段である
- 高さの計測の受け口 (`onMeasuredSize = nil`) と読み上げの移動操作 (`reorderAccessibility.clear()`) は `prepareForReuse` の別の行で外している。中身を外すのをやめても、この 2 つは今のまま外せる
- 契約を固定しているテストがある: `ios/Tests/KsCollectionViewTests/KsCollectionScenarioTests.swift:342` (再利用が起きる距離を往復するとテンプレートの state は初期値へ戻る)
- 表示中のセルの作り直し (ios/ADR-0006・0008、`reconfigureVisibleCells`) は `prepareForReuse` を通らず、同じセルに中身を当て直している。この change の影響をほぼ受けない
- 補助ビュー (グループの見出し・ルートのヘッダー / フッター) にも、再利用で中身を捨てる同じ作りがある (`ios/Sources/KsCollectionView/KsHostingSupplementaryView.swift:38`)
- テンプレートの中身は型を消して (`AnyView`) 渡り、セルの再利用はテンプレートキーごとの列で起きる。中身の型は、読み上げの移動操作の部品を付ける構成と付けない構成の 2 種類で、構成で決まりスクロール中は変わらない
- 利用者向けドキュメント (`skills/`) はまだ無い。ADR-0002 が求める「状態は保持されない」の明記はこれから (ロードマップ v1-foundation の phase-7)

外部の事実 (ksn-scout の Web 調査。公式資料と二次情報を分けて記す):

- 公式: iOS 18 のリリースノート (SwiftUI の Resolved Issues、125100960) に、`UIHostingConfiguration` のルートの状態を、セルが表示される前にリセットするよう直したとある (https://developer.apple.com/documentation/ios-ipados-release-notes/ios-ipados-18-release-notes)
- 解釈: 裏返すと iOS 16・17 では、使い回すと前の項目の状態が次の項目に残りうる。旧挙動を説明した Apple の明文は見つかっていない
- 公式: 識別の値 (`.id`) が変わると状態は初期値で作り直される (WWDC21「Demystify SwiftUI」)。入れ物 (hosting view) が残るかと、丸ごと作り直す場合との費用の比較は見つかっていない
- 二次情報: 使い回すと、前の項目の画像が一瞬出る・大きさの変化がアニメーションして見える。中身に `.id` を付けると消える (https://lucasvandongen.dev/swiftui_uitableviewcell_reuse_id.php)
- 二次情報: iOS 18 以降は、同じ項目でも上下にスクロールすると状態が消えるという報告がある (https://developer.apple.com/forums/thread/767006)
- 見つからず: 使い回したときの `onAppear` / `onDisappear` / `.task` の時機。`prepareForReuse` で nil にすることの是非を述べた公式資料
- iOS 18 の修正が状態を消す時機 (再利用のたびか、表示のたびか) は資料が無い

効果の数値の確からしさ:

- 参考の変種 (nil を外したもの) の −4〜8% は 1 走行ずつで、Mac のばらつき (±10% 程度) の内側にある
- 基準機では計測していない。基準機の trace の帰属では、入れ物の解放が主スレッドの 10.5% を占める

## 検討した選択肢 (却下案と理由を含む)

進めるかどうか:

- 進める (採用): 入れ物の解放だけで主スレッドの 1 割を占め、利用者が重いセルを書いたときや遅い端末での余裕になる
- 閉じる (今のまま作り直す): 却下。体感ゲートは合格しているので正当な選択だが、オーナー判断で「軽いにこしたことはない」(2026-10-04)。ただし効果が薄いと分かったら、ここへ戻る

状態の扱い (論点 1):

- 案 A (採用): 入れ物だけ使い回し、状態は再利用のたびに初期値へ戻す。利用者から見た契約は今と同じで、ADR-0002 は手段の部分だけ一部改訂になる。効果は未計測
- 案 B (却下): 中身を外すのをやめるだけで、状態は OS まかせにする。効果はいちばん大きい見込みだが、iOS 16・17 では前の項目の状態が次の項目に残りうる。手元に iOS 16・17 のランタイムが無く確かめられず、ADR-0002 の契約そのものの改訂になる

状態を戻す仕組み (案 A の中の設計):

- 再利用の回数を識別の値にする (採用): 状態が戻るのが「再利用を通ったとき」と一致し、今の動きと同じになる
- 項目の ID を識別の値にする (却下): 同じ項目がたまたま同じセルへ戻ったときだけ状態が残り、残るかどうかがセルの巡り合わせで変わる
- iOS 18 以降は OS 自身の戻しに任せ、iOS 16・17 だけライブラリが戻す (却下): 手元で確かめられない版だけが別の経路になる。計測で二重の戻しが効果を食っていると分かったときに、オーナーと改めて相談する

範囲 (論点 3):

- セルだけを対象にする (採用)
- 補助ビュー (グループの見出し・ルートのヘッダー / フッター) も対象にする (却下): 見出しの生成は基準機の「グループ化」で主スレッドの 2.1% で、再利用の頻度も低い。セルで効果を確かめてから、必要なら別 change で検討する

## 決定事項

論点 1 までは対話で決めた。論点 2〜5 は、オーナーの指示 (2026-10-04) で推奨どおりに決めた。S 級のため、この節が実装へ渡すスコープになる。

### 進め方

- 進める。最初に効果を測り、薄ければ閉じる (オーナー判断、2026-10-04)

### 状態の扱い (論点 1: 案 A、ios/ADR-0012)

- セルの再利用のときに中身を外さない (`prepareForReuse` の `contentConfiguration = nil` をやめる)。入れ物 (hosting) は使い回す
- セルは再利用の回数を持ち、再利用のとき (`prepareForReuse`) だけ進める
- 利用者のテンプレートの中身に、この回数を識別の値として付ける (`.id`)。回数が進むと SwiftUI が中身を別物として扱い、状態が初期値に戻る
- 表示中のセルの作り直し (同値配列の更新・観測する値の変化) は再利用を通らないので回数が進まず、状態は残る (今と同じ)
- OS の版で経路を分けない
- 識別の値を付ける位置は、利用者のテンプレートの中身を既定にする。ライブラリが足す配置の部品 (`KsRowContentPlacement`) と読み上げの部品の内側である。ライブラリの部品は状態を持たないので使い回す。最初の計測で外側に付ける形のほうが軽いと分かれば、そちらにしてよい (契約はどちらでも同じ)

### 次の項目へ持ち越さないもの (論点 2)

| もの | 扱い |
|---|---|
| 高さの計測の受け口 | 今のまま。再利用のときに外し、中身を当てるときに付け直す |
| 読み上げの移動操作 | 今のまま。再利用のときに空にし、中身を当てる前に入れ直す |
| 高さ | 再利用されたセルは、次の項目の中身の高さで測られる。前の項目の高さが残らない |
| 見た目 | 再利用されたセルが表示に入るとき、前の項目の中身が見えず、前の見た目から動いて (アニメーションして) 見えない。差分のアニメーションの最中に表示へ入るセルを含む |
| `onAppear` と `.task` | 再利用で表示に入る項目で、今と同じく動く |

再利用の列で待つ間の中身の寿命とメモリは変わらない。今も、前の中身が捨てられるのは次の項目のために取り出す時点である (基準機の trace で、解放は次のセルを用意する最中に起きていた)。

### 範囲 (論点 3)

- 対象はセル (`KsHostingCell` と、中身を当てる処理) だけ
- 対象外: 補助ビュー (`KsHostingSupplementaryView`)、公開 API、Android、Sample、利用者から見た挙動
- 実態に合わなくなるソースコメントは直す (中身を当てる処理の「`prepareForReuse` で内容と一緒に解除される」など)
- `ios-prefetched-cell-content-refresh` とは独立で、どちらを先にしてもよい。この change はテンプレートを呼ぶ時機を変えないので、先に組み立てたセルの中身が古いままになりうる問題は良くも悪くもならない
- `ios-self-sizing-layout-loop` とも独立。この change は高さの測り方を変えない

### 確かめ方とやめる基準 (論点 4)

次の順で進める。Simulator は作業専用のものを作り、最後に削除する。

1. **効果の計測** (進めるかの判断材料。合否ではない)
   - 土俵は切り分けのときと同じにする (`kasane/changes/archive/2026-10-01-drag-reorder/evidence/perf-diag-ios-reorder-cells.md` の 2 節: Release、診断用の一覧、自動スクロールで下向き・上向きに 450 フレームずつ、プローブはスクラッチの複製だけに入れる)
   - 変種は 3 つ: 今のまま / 案 A / 中身を外すのをやめるだけ (効果の上限の参考)。交互に回して各 5 走行以上
   - 一覧は 2 つ: 並べ替えを付けない一覧と、並べ替えのスイッチがオンの一覧。OS は iOS 18.6 (基準機と同じ系統) と、テストの既定の版
   - 取り出す値: 入れ物の生成と解放の回数、主スレッドの CPU 時間の中央値と範囲
   - **やめる基準**: 案 A で入れ物の生成と解放が減らない、または案 A の CPU 時間の範囲が今のままの範囲と重なる (ばらつきと区別できない) なら、そこで止めて数値をオーナーへ報告する。既定は閉じる。案 B には乗り換えない
   - 案 A が上限の参考より明らかに重いときは、識別の値を付ける位置を変えて測り直してよい
2. **テスト** (既定の版と iOS 18.6 の両方で通す)
   - 既存: 再利用が起きる距離を往復すると状態が初期値へ戻る (変えずに通る)
   - 新規: 再利用の前後で、セルの中身のビュー (入れ物) が同じである
   - 新規: 高さの違う項目へ再利用されたセルが、新しい項目の高さになる
   - 新規: 再利用で表示に入った項目で `onAppear` と `.task` が動く
   - 新規: 表示中のセルの作り直しでは状態が残る (同じ確認が既にあれば足さない)
   - 既存の全件 (読み上げの移動操作・同時生存セル・自己サイズを含む) が通る
   - iOS 16 か 17 のランタイムを入手できれば、状態が初期値へ戻るテストをその版でも流す。入手できなければ、未確認として証跡の限界に書く
3. **前の見た目が残らないことの確認**: Simulator で、項目の追加・削除のアニメーションの最中に表示へ入るセルを見る
4. **完了の判定** (`kasane/handbook/cross/scroll-performance-gate.md`・`kasane/handbook/ios/performance-verification.md`)
   - 基準機 iPhone 11・Release・固定の操作列で、オーナーが手動でフリックする。合否は体感 (前より悪くなっていないこと)
   - fixture は「大量件数」(エンジンの土台に触る変更の規定) と「並べ替え」(見つかった画面)。変更前と変更後を同じ回に 1 走行ずつ採る。以前の記録とは条件が違うので比べない
   - 数値は証跡として並べる: hitch の指標と、time profile の帰属 (セルの生成・入れ物の解放・hosting の計測と描画)
   - 不一致率は「大量件数」の Debug 構成で読む。メモリは Simulator の自動往復で定常化を確かめる

### 蒸留時に反映

- 蒸留時に反映: concepts `kasane/concepts/ios/architecture/collection-engine.md` — `KsHostingCell` の責務 (「再利用時のホスティング破棄」) と「してはいけないこと」(「再利用でホスティングを作り直す」) を、入れ物を使い回して状態だけを戻す形に書き換える。性能の節に計測の結果を足す

## ADR 候補 (作成済み: ADR-NNNN / 未起票: ...)

- 作成済み: ios/ADR-0012 (proposed、amends ios/ADR-0002) — セル再利用では中身のホスティングを使い回し、SwiftUI の内部 state だけを再利用のたびに初期値へ戻す
- 効果が薄くて閉じる場合は、このドラフトを破棄する

## 未決の論点

対話で決める論点は残っていない。次は実装の中で決まる。

- 識別の値を付ける位置 (利用者の中身 / ライブラリの部品の外側) は、最初の計測で軽いほうにする
- iOS 18 以降は OS 自身も表示の前に状態を戻すため、戻す処理が二重になって効果が減る可能性がある。最初の計測で分かる
- iOS 16・17 での確認は、ランタイムを入手できるかによる

## 変更級の推奨: S / M / L (理由)

S

- 触る能力は 1 つ (iOS エンジンのセル)。公開 API の変更なし。利用者から見た挙動の変更なし
- 可逆で局所的 (セルと、中身を当てる処理の数行。戻せば元どおり)
- 重要判断は ios/ADR-0012 に残した
- エンジンの土台に触れ、accepted の決定を一部改訂するため、M に上げて提案・デルタスペック・相方レビューを付ける選択もある
