# 性能の食い違いの切り分け: iOS「並べ替え」画面のセルの作り直し (診断) — 2026-09-30

基準機の体感ゲート (perf-ios-reorder.md) で、体感は合格だったのに数値 (hitch 284 件・操作中 175〜329 ms/s) がページング画面の記録 (3.8 ms/s) より大きく悪かった。この食い違いの原因を切り分けるための診断の記録である。**合否の判定には使わない。** 自動スクロールは体感ゲートでは使わない (handbook/cross/scroll-performance-gate.md)。ここでは原因の切り分けのためだけに使った。

## 1. 基準機の trace の帰属 (観測)

材料は perf-ios-reorder.md と同じ trace の time-profile。範囲は操作区間 23.332〜57.830 s の主スレッドの標本 17,627 で、比は inclusive。

- **セルの生成** (`_createPreparedCellForItemAtIndexPath`、42.3 %) の呼び出し元は次の 2 つ
  - コミット中のレイアウト (`CA::Transaction::commit` → `UICollectionView layoutSubviews` → `_updateVisibleCellsNow` → `_createVisibleViewsForAttributes`): 6,052 標本
  - アイドル時の先読み (`_updatePrefetchedCells`): 1,394 標本
  - つまり「セルを作り直している」のではない。表示に入る項目ごとに、UIKit が通常の経路でセルを用意しているだけである
- **hosting view の解放** (`_UIHostingView.__deallocating_deinit`、10.5 %) は、1,851 / 1,858 標本がセルの用意の中の `objc_autoreleasePoolPop` から呼ばれている。中身は `UIHostingViewBase.tearDown` → `GraphHost.invalidate` (1,197 標本)
  - 再利用に回ったセルの `prepareForReuse` で `contentConfiguration = nil` とし、前の項目の hosting の中身を捨てている。その解放が、次の項目のセルを用意する最中に走っている (仕組みは Simulator の計数で確かめた。2 節)
- セルを用意する処理の中身: 自己サイズ (`KsHostingCell.preferredLayoutAttributesFitting`) 3,015 標本、`cellForItem` (中身の設定) 2,272 標本、前の hosting の解放 約 1,850 標本
- 読み上げに関わるフレームは全体の 16.2 %。ただし大半 (`EnableDeferredAccessibilityAttachmentModifier` などの `_makeView`、約 10.9 %) は、SwiftUI が中身の view graph を組むたびに必ず通る包みのフレームである。この change の modifier の分だけを取り出すことはできない。この change のコードそのもの (`updateReorderAccessibility`・`KsReorderAccessibilityModel`・`KsReorderAccessibilityModifier.body`) は、合わせても 2 % 未満

## 3. 読み (観測と推測を分けて書く)

- **観測**: 仮説「スクロール中にセルが作り直され続けている」は、**セルそのものについては否定**。セルは再利用されている。作り直されているのはセルの中身の hosting view で、表示に入る項目ごとに作られ、捨てられている。原因は `KsHostingCell.prepareForReuse` の `contentConfiguration = nil` (ios/Sources/KsCollectionView/KsHostingCell.swift:161)。これは HEAD にもある既存の作りで (HEAD では 158 行目)、Simulator の計数は HEAD と作業ツリーで同じだった。**hosting の作り直し・解放・自己サイズ・hosting の layoutSubviews という大きな帰属は、この change 由来ではない**
- **観測**: この change の上乗せは、主スレッドの CPU で約 +5〜9 % (a と d の比較、Simulator)。上乗せは、読み上げの移動操作の modifier を外すと消える (e は d と同じ水準)
- **推測 (コードを読んだ結果。計数は取っていない)**: 上乗せの仕組みは 2 つ
  1. ios/Sources/KsCollectionView/KsCollectionViewController.swift:644-648 で、`KsReorderAccessibilityModifier` (`@ObservedObject` + `.accessibilityActions { ForEach … }`) を**並べ替えの有無やスイッチによらず、すべての行の中身に付けている**。中身の hosting は項目ごとに作り直されるので、この modifier の graph も項目ごとに組まれる。c (`.reorder` を付けない一覧) が d より少し重いのはこのため。並べ替えを使わない一覧にも負担がかかっている
  2. スイッチがオンのときは、:691 の `updateReorderAccessibility` が中身の設定の**後で** `KsReorderAccessibilityModel.update` を呼ぶ。直前の `prepareForReuse` の `clear()` (KsHostingCell.swift:165、KsReorderAccessibilityModel.swift:31) で操作が空に戻っているので、動かせる項目 (9 割) では毎回 `actions` が変わる (:23)。すると `objectWillChange` が出て、作ったばかりの hosting がもう一度描き直される。a が c より重いのはこのためだと読む
- **推測**: ページング画面 (3.8 ms/s) との桁違いの差は、この change の上乗せ (1 割弱) では説明できない。hosting を項目ごとに作り直す作りはページング画面でも同じだった (Simulator で、ページング画面の上向きの区間でも表示した 321 件すべてで作り直しを確認)。差の多くは、fixture と操作の違いによると読む。違いは、100 件ずつのグループと見出しの固定、行の数と長さ、オーナーのフリックの速さ (記録では約 45 swaps/s で送られる行の量) である。この読みは、同じ構成を HEAD で実機計測しない限り確かめられない

## 4. 直し方の見当 (直していない)

- この change の分
  - modifier は並べ替えが有効で、読み上げの文言が渡されている構成のときだけ付ける (構成が変わるときは中身を作り直す)。modifier を付けないときの主スレッドの CPU は e と同じ水準になる見込み
  - 操作を中身の設定より**前に**モデルへ入れる。あるいは、操作を `UIHostingConfiguration` の中身へ値として渡し、`ObservableObject` の通知で描き直させない。これで設定直後の 2 度目の描き直しを避けられる。スクロール中に操作が変わるのは世代が変わったときだけなので、そのときは表示中のセルの中身を設定し直せば足りる
- 既存の分 (この change の範囲外。簡易起票の候補): `prepareForReuse` で `contentConfiguration = nil` にするのをやめ、同じ型の `UIHostingConfiguration` を当て直して hosting を使い回す。fW / fH で hosting の生成・解放が 0 になり、主スレッドの CPU は 4〜8 % 下がった (1 走行)。ただし nil にしているのには理由がある (中身と計測のハンドラを一緒に外す。core/ADR や concepts の前提を確かめる必要がある) ので、別の change で検討する

## 限界

- Simulator の値は Mac 上のもので、基準機の hitch は再現できなかった。比べたのは主スレッドの CPU 時間と計数だけ
- 自動スクロールは一定の速さで送っており、オーナーのフリックとは速さも慣性も違う (診断用)
- CPU 時間の走行数は a / c / d / e が 6 回、b / real が 2 回、fW / fH が 1 回。Mac のばらつきは ±10 % 程度ある
- Simulator で Time Profiler (`xctrace record --launch`) を採ろうとしたが、記録が終わらずに止まった。そのため Simulator での帰属は採れていない。帰属は基準機の trace (1 節) だけによる
- 同じ構成を HEAD で基準機にのせた計測は無い。ページング画面との差の原因 (3 節の最後の推測) は確かめていない
- プローブ・複製・trace はスクラッチにだけ置いた。作業ツリーの ios/ と samples/ は書き換えていない

## 修正後 (2026-09-30)

4 節の「この change の分」の 2 つを作業ツリーに入れた後の、同じ手順での再計測である。合否の判定には使わない (診断用の自動スクロール)。

### 入れた修正

- 読み上げの移動操作の部品 (`KsReorderAccessibilityModifier`) は、並べ替えを付けて文言を渡した構成のときだけ中身に付ける。並べ替えを付けない一覧・文言を渡さない一覧には付けない。スイッチのオン / オフでは付け外しせず、オフの間は操作を空にする。付け外しは中身の型が変わるので、切り替えのたびに表示中のセルの hosting が作り直され、テンプレートも呼び直されるためである。文言の有無が変わったときは、作ってあるセルの中身を作り直す
- 操作は中身を設定する**前に**モデルへ入れる。中身を設定した後に操作が入れ替わらないことを結合テストで確かめた (`testスクロールで表示に入る項目は中身を作った後に操作を入れ替えない`。修正前の順番に戻した複製では失敗する)

### 環境

- Simulator の iPhone 11 (iOS 18.6)。この計測のために新しく作った `ksn-drag-reorder-fix-perf`。2 節の計測とは別の機体なので、絶対値を 2 節の表とは比べない
- W は修正後の作業ツリーの複製 (プローブ入り)。H は 2 節と同じ HEAD のビルド。駆動・一覧・取り出した値は 2 節と同じ
- 変種は 2 節の a (オン)・b (オフ)・c (付けない)・d (HEAD)。1 周で d → a → c → b の順に回し、5 周した (走行の順番の偏りを避けるため)

### 計数

どの変種でも 2 節と同じだった (下向き: セルの生成 9・hosting の生成 399・中身の設定 399、上向き: 0・393・393)。

### 読み (観測と推測を分けて書く)

- **観測**: 並べ替えを付けない一覧 (c) とスイッチがオフの一覧 (b) の上乗せは消え、HEAD と同じ水準になった
- **観測**: スイッチがオンの一覧 (a) には約 +5〜8 % が残った。2 度目の描き直しを無くしても a の値は修正前 (2 節の +9.0 % / +5.5 %) とほとんど変わらなかった。操作の一覧を空にすると (g、b) HEAD と同じ水準になる
- **推測**: 残りの上乗せは、中身の hosting を項目ごとに作るたびに、中身の読み上げの操作 (ボタン 2 つ) を組み立てる費用である。2 節の e (操作をモデルへ入れる計算はそのまま、部品だけを外す) が HEAD と同じ水準だったので、操作を求める計算の費用ではない。また、修正前の 2 度目の描き直しは、hosting が最初に描かれる前に起きていたので、ほとんど費用になっていなかったと読む
- g の形は、支援技術が無効の間は操作を出さない。spec の「スイッチが有効で文言を渡した一覧では、動かせる項目に操作を出す」の読み方に関わるため、作業ツリーには入れていない
