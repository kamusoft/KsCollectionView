# 体感ゲート: iOS「並べ替え」画面、並べ替えのスイッチがオン (tasks 6.2 の iOS 分) — 2026-09-30

並べ替えのスイッチを有効にした一覧で、スクロールの滑らかさが基準機で保たれているかを確かめる手動フリック計測 (design Decision 9)。Android 分は別の記録にする。

## 環境

| 項目 | 値 |
|---|---|
| 機種 / OS | iPhone 11 (基準機)、iOS 18.7.8。表示 60 Hz |
| 構成 | Release (samples/ios を実機向けにビルド、Release 用に分けた DerivedData) |
| fixture | Sample「並べ替え」: 全 10,000 件、100 件ずつのグループ、見出しの固定あり、リスト表示、並べ替えのスイッチはオン (既定)、10 の倍数の項目は動かせない。起動引数 `--screen 並べ替え` (devicectl の `--` の後ろに渡した) |
| 駆動 | オーナーの手動フリック (自動化なし)。並べ替えのドラッグはしていない |
| 記録 | Instruments Animation Hitches を `xctrace record --template 'Animation Hitches' --attach KsCollectionViewSamples --device <UDID> --time-limit 10m` で接続し、操作列の終了の合図の後に停止 (Stop で終了、Deferred 記録)。接続は 2 回「Timed out waiting for device to boot」で失敗し、`devicectl device info details` の後の 3 回目で「Starting recording」。記録窓の実長 69.578 s |
| 熱状態 | device-thermal-state-intervals で、記録窓の全体 (0〜69.578 s) が 1 区間で「Nominal」、Is Induced は No |

## 操作条件

| 項目 | 値 |
|---|---|
| 操作列 | 初回 下向き 10 秒 → 休止 3 秒 → 再訪 上向き 5 秒 → 連続 下向き 10 秒 |
| 開始位置 / 到達範囲 | 先頭 (起動直後、グループ 1 の Item 1)。初回の 10 秒の間に末尾には到達していない (オーナーの回答)。そのほかの段階の到達範囲は記録していない |
| 起動引数の確認 | 起動直後にオーナーが画面 (タイトル・先頭のグループ 1 と Item 1・並べ替えのボタンがオン) を確かめ、スクロールせずに待った |

## オーナーの体感 (合否の主語。数値を見る前に聞き取り、2026-09-30)

- 初回 / 再訪 / 連続 / ムラ: 4 つとも「問題なし」
- 画像の出方 (別の観測点): 対象外 (この画面に画像はない)
- 体感とは別の観測 (合否に入れない): 「見出しを下から上へ押し出すとき、安全領域の外で見出しの高さが伸びる。その状態で上から下へ戻すと高さが変わったままになる」。静止画 2 枚で、グループ 86 の見出しがバーの裏で縦に伸び、戻した後にグループ 87 の見出しの上に余分な高さが残っている。原因は **調査中** (この記録では事実だけを残す)

## 数値 (証跡。合否ではない)

取得源: Animation Hitches の trace を `xctrace export --xpath` で書き出した表 (hitches-summary / display-surface-swap / device-thermal-state-intervals / device-display-info / thread-state / time-profile / potential-hangs)。区間は display-surface-swap の hid-time 列を使い、入力の空白 3 秒で切った。hitch はその開始時刻で区間に入れた。

### 区間の切り方

入力の空白 3 秒で切ると **2 区間** に分かれた (空白は 36.814→40.198 s の 3.38 s の 1 か所だけ)。

- 区間 1 (初回): 23.332〜36.814 s。区間の中に 29.515→30.382 s (0.87 s) と 30.648→31.482 s (0.83 s) の入力の切れ目がある
- 区間 2 (再訪 + 連続): 40.198〜57.830 s。再訪から連続への折り返しに 3 秒以上の空白が無く、入力の時刻だけでは 2 つを分けられない。入力の間隔が 47.9 s を境に約 0.43 s から約 0.59 s へ変わるので、参考としてそこで分けた値も載せる (向きの記録は無く、推測)

## 判定

- 体感の合否: **合格** (オーナー)。初回 / 再訪 / 連続 / ムラの 4 つとも「問題なし」
- 数値との一致・不一致: **食い違う**。体感は迷いなく合格だが、数値は hitch 284 件 (High 88)、操作区間の hitch time ratio 175〜329 ms/s、最長 50 ms (3 フレーム)、操作中の swaps/s 約 45 (60 Hz の表示に対して) で、hitch が連なって出ている。scroll-performance-gate の規則 (体感が迷いなく合格で数値だけが悪いときは対照を行わない) により、計測器なしの対照は行っていない。体感と数値の両方をここにそのまま残す
- 数値の読み (原因は未確定): hitch の 85 % は Commit to Render latency で、主スレッドは操作区間の半分以上で動いており、その標本の 8 割強がコミット中のレイアウト (セルの生成・hosting の layoutSubviews・自己サイズ) に帰属する。並べ替えの有効化で加わる処理 (読み上げの移動操作の更新) の比は 1 % 未満。この記録だけでは、並べ替えのスイッチ・100 件ずつのグループと見出しの固定・hosting view の解放のどれが効いているかは切り分けられない
- 前回との比較可否: **比較不能**。前回の iOS の記録 (paging-state-machine の「ページング」画面、archive の evidence/perf-ios-paging.md) とは fixture が違う (並べ替え画面・100 件ずつのグループ・見出しの固定あり・並べ替えのスイッチがオン)。数値の水準は前回と大きく違うが、fixture が違うので悪化とは言えない
- 見出しの高さが伸びる観測: 判定に入れない。原因は調査中

## 限界

- 区間と操作列の対応は推測を含む。入力の空白 3 秒で 2 区間にしか分かれず、再訪と連続を入力の時刻では分けられない。区間 1 の中の 29.5〜31.5 s の短い切れ目 (0.87 s + 0.83 s、間に 0.27 s の入力) を休止と読む別の読み方 (初回 23.332〜29.515 s、再訪 30.382〜36.814 s、36.8〜40.2 s の空白が再訪から連続への折り返し、連続 40.198〜57.830 s) も否定できない。その読み方での値は、初回 6.183 s で hitch 32 件・137.67 ms/s、再訪 6.432 s で 35 件・142.90 ms/s (最長はどちらも 50.00 ms)
- 記録にスクロールの向きと到達した項目の番号は残らない。初回で末尾に届かなかったことはオーナーの回答による
- 記録回数は 1 回。対照 (計測器なし) は行っていない (体感が迷いなく合格のため)
- 同じ端末・同じ土俵で並べ替えのスイッチをオフにした記録は無く、スイッチの有無による差はこの記録からは言えない
- 文字サイズ (端末の設定) は記録していない
- trace の保存時に NSSQLiteErrorDomain 1032 の警告が出たが、この証跡で使った表 (hitches-summary・display-surface-swap・device-thermal-state-intervals・device-display-info・thread-state・time-profile・potential-hangs) と、試したそのほかの表はすべて書き出せた (thread-info で XML に表せない 1 文字を飛ばした旨の通知が出ただけ)。大きい低水準の表 (kdebug・syscall・context-switch・cpu-state・tick・time-sample など) は使わないので書き出しを試していない
- 生の trace と表の全件の書き出しは evidence に置いていない (スクラッチにのみ置いた)

## 追記: 数値の食い違いの切り分けと修正 (2026-09-30)

体感 (合格) と数値 (hitch 284 件・操作中 175〜329 ms/s) の食い違いを受け、オーナー判断で原因を Simulator で切り分けた (診断用の自動スクロール。体感ゲートの判定には使わない)。詳細は [perf-diag-ios-reorder-cells.md](perf-diag-ios-reorder-cells.md)。

- 数値の大半は、この change 由来ではない: セルは再利用されているが、`prepareForReuse` で中身を外すため表示のたびにセルの中の hosting を作り直す、変更前からの作り (別 change `ios-hosting-content-reuse` として簡易起票)
- この change 由来の上乗せ (主スレッドの CPU 約 +5〜9%) は、読み上げの移動操作の部品を全一覧の全行に付けていたことによる。修正で、部品は並べ替えを付けて文言を渡した一覧だけに付くようにし、並べ替えを使わない一覧と並べ替えが無効の一覧は HEAD と同じ水準に戻った
- 並べ替えが有効で文言を渡した一覧には、操作 (ボタン 2 つ) を組み立てる費用として約 +5〜8% が残る。支援技術が無効の間は組み立てない形 (SwiftUI の `accessibilityEnabled`) なら HEAD と同じ水準になるが、公式の説明がどの支援技術で真になるかを定めておらず、VoiceOver 以外の支援技術で移動の操作が消えるおそれがあるため、オーナー判断で今の形のまま受容した (2026-09-30)
- 基準機での測り直しはしていない: 体感は上乗せを含んだ状態で合格で、修正は負荷を減らす向きのため合否が変わらない。この記録の数値は修正前のビルドのもの
- 測り直しをしない理由 (2026-10-01、verify-002 の問いへの判断): この記録の後に iOS の並べ替えを reorder-capable な形に組み替え、置く絵の見た目を直したが、変わったのはドラッグして置く経路で、体感ゲートの操作列 (ドラッグしないフリック) の経路は変わっていない。読み上げの部品の修正はフリックの負荷を減らす向き。いずれも合否を悪い向きに変えないため、基準機での測り直しはしない
