## 判定

- 0.1 (iOS): 固定の見出しとの重なり順、自前の見出しの固定 (レイアウトの位置の上書き) と UIKit の隙間の計算の干渉は、**見つからなかった** (#1・#2)
- 0.2: 10,000 件・内部の塊をまたぐ移動・全画面の一覧での持ち上げ・隙間・下端の自動スクロールは標準どおりに動いた (#6)。上端はバーの上に指があると自動スクロールしない (#7。バーは一覧の上に重なる別の表示で、指の下が一覧ではなくなるためと見られる)
- **標準どおりでは spec と合わない点を 1 つ検出した**: UIKit の隙間の位置は、境目の前後で spec の「見出し (見出しが無ければグループの間の間隔) より上なら前のグループの末尾」にならない (#3・#4)。下のグループから上へ運ぶとき、前のグループの末尾には置けず、見出しより上でも次のグループの先頭になる。隙間の位置を変える delegate は、ドラッグ & ドロップでは呼ばれない (#5)。design の Risks の定めに従い、ここで止めて諮る

# 再確認 (公式の差し替え口と、隙間の位置の読み直し) — 2026-09-30

## 前回までの読み違い

前回までは、`dropSessionDidUpdate` に渡る `destinationIndexPath` を「いま隙間が空いている位置」とみなして読んでいた。今回、実際に隙間が動いたときに呼ばれるレイアウトのフック (`invalidationContext(forInteractivelyMovingItems:...)` の `targetIndexPaths`) と、置いたときの `coordinator.destinationIndexPath` を併せて記録したところ、両者は一致した。一方、`dropSessionDidUpdate` の値とは一致しない場面があった (例: `1,4` と渡された直後に隙間は `1,5` へ動く、指が隙間の上にあると元の位置 `2,1` が渡される)。このため、前回の「下から運ぶと前のグループの末尾には置けない」(上の #3・#4 の判定と 1-a・1-b) は**誤り**だった。前回の 1-a・1-b はまっすぐ見出しの上へ運んで止めた操作と `dropSessionDidUpdate` の値からの判定で、前のグループの最後の項目の上を通ってから戻る操作は含んでいなかった。

## 手順

- 環境: iOS 26.5 (`ksn-drag-reorder-impl`、iPhone 17) と iOS 18.6 (`ksn-drag-reorder-ios18`、iPhone 16)。iOS 16・17 のランタイムは入っていないため**未確認**
- ハーネスは前回と同じ (グループ 5 件、置き先の提案は `.insertAtDestinationIndexPath`)。本体に一時的に次のログを入れ、確認後に取り除いた
  - レイアウト (`KsCompositionalLayout`) の `targetIndexPath(forInteractivelyMovingItem:withPosition:)`・`layoutAttributesForInteractivelyMovingItem(at:withTargetPosition:)`・`invalidationContext(forInteractivelyMovingItems:withTargetPosition:previousIndexPaths:previousPosition:)` (super をそのまま返す)
  - delegate の `collectionView(_:targetIndexPathForMoveOfItemFromOriginalIndexPath:atCurrentIndexPath:toProposedIndexPath:)` と旧版 `collectionView(_:targetIndexPathForMoveFromItemAt:toProposedIndexPath:)`
  - `dropSessionDidUpdate` の `destinationIndexPath` と `session.location(in:)`、`performDrop` の `coordinator.destinationIndexPath`
- 座標 (list): Item 10 (グループ 2 の最後) 484〜527、グループの間の間隔 527〜544、グループ 3 の見出し 544〜580、Item 11 (グループ 3 の先頭) 580〜624。セクション 1 = グループ 2、2 = グループ 3。グループ 2 の末尾は `1,5`

# review-001 の指摘の修正: 置かずに終えるときの見え方 (iOS) — 2026-09-30

## 変えたこと

- 置いたときの処理を受け入れないとき・元の位置で離したとき・取りやめた後に離したときは、`coordinator.drop(_:to: UIDragPreviewTarget(container: 一覧, center: 元の位置の中心))` で、持ち上げた項目のプレビューを元の位置へ動かして置く。元の位置の中心は持ち上げたときに控える
  - 根拠: UICollectionView.h の `UICollectionViewDropCoordinator` の `dropItem:toTarget:` (「UIDragPreviewTarget で指定した位置へ drag item を動かす」)。`dropItem:toItemAtIndexPath:` は「新しく挿入した項目へ動かす」もので、配列を変えない場合には当たらない。何もせずに返すと UIDropInteraction.h の「nil なら drag item をその場で薄くして縮める」既定の置き方になる
- 戻る動きの間は、元の位置のセルをレイアウトの属性で透明にして、動いているプレビューと 2 つ同時に見せない。動きが終わったら (`UIDragAnimating` の完了) 戻す。セルの `alpha` を直接変えても UIKit がレイアウトの属性で当て直すため効かなかった
- 取りやめた後の提案は、置けない (`.cancel`) ではなく、隙間を空けない置ける提案 (`.move` + `.unspecified`) にした。指を離すと置く処理が呼ばれ、上と同じ戻し方になる。取りやめてから離すまでの間は、直前の隙間が残るのは変わらない
- 置けない行き先の上で離したときは、最後の提案が置けない (`.forbidden`) なので置く処理は呼ばれず、UIKit 標準の取り消しの動き (UIDragInteraction.h の「既定の preview は元の場所へ戻す」) で元の位置へ戻る

## review-004 の Minor の修正後の確認 (送り始めの待ち・iOS 18 の曲がり方・フレームの上限・UIKit の帯との重なり)

測った条件と値は `ios-r4-autoscroll-speed.log` の冒頭と「review-004 の後の測り直し (r5)」。

- **送り始めの待ち**: iOS 18.6 の UIKit 標準の上端は、指が帯に入ってから 0.765 秒待って送り始め、帯を出て入り直すと待ち直した (0.764 秒)。iOS 26.5 の UIKit 標準には待ちが無い (帯に入って約 0.03 秒で送る)。自前は iOS 26 より前にだけ 0.75 秒の待ちを持たせ、帯を出たら (一覧の外へ出た・帯の下へ出た・UIKit の帯へ入った) 数え直す。直した後の自前の実測は 0.715・0.730 秒 (1〜2 フレーム早いのは、表示のリンクの最初のフレームを時間の基準にしている分)
- **iOS 18 の曲がり方**: 深い側 (45pt) で UIKit 約 122pt/秒に対し、比例の式は 82 だった。`1 - 深さ / 65pt` の 1.6 乗 × 830pt/秒 (帯の幅は 50pt のまま) に変え、深さ 1・25・45pt で 810・382・126 (実測 811・381・122)。直した後の自前の実測は 45pt で 121、24pt で 408pt/秒
- **フレームの上限**: 1 回に進める時間の上限を 1/30 秒から 0.1 秒に広げた。単体テストで、フレームの間隔が 1/60・1/30・45ms・1/15 秒のどれでも 1 秒あたりの送りが式の値と一致することを確かめた
- **UIKit の帯との重なり**: 一覧の枠を画面の上端から下げてバーを隠し、安全領域の上を UIKit の帯より短くした (26.5 で 22pt、18.6 で 29pt)。直す前 (26.5) は、重なる所 (枠の上端から 40pt) の送りが 613pt/秒で、自前だけの見込み (約 430) と UIKit だけ (180) の和になり、**両方が送っていた**。UIKit の帯 (内側の余白 `adjustedContentInset.top` から帯の幅) に入る所では自前で送らないようにし、直した後は重なる所が 179pt/秒 (26.5)・161pt/秒 (18.6) で UIKit だけの値と一致した。重ならない所 (UIKit の帯より下で自前の帯の中) は自前だけが送る (26.5 で 79、18.6 で 223pt/秒)
- この置き方では、UIKit の帯の下の端 (UIKit はほぼ 0) のすぐ下から自前の帯が続くため、指を下げていくとそこで速さが上がる (26.5・安全領域 22pt なら UIKit の端で約 20 から自前の約 200 へ)。バーのある置き方 (Sample・安全領域の上が帯より長い) では起きない
