# Exploration: ios-launch-failure-uitests

## 課題 / 動機

iOS Sample の UI テスト `samples/ios/KsCollectionViewSamplesUITests/LargeDataCountUITests.swift` のうち、起動を止めることを確かめる 2 本 (`test件数に0を指定すると起動しない`・`test件数に数値でない値を指定すると起動しない`) が失敗し、実行ごとに成否が揺れる。`prefetch-display-size` の実装中 (2026-09-23〜24) に発見。変更前 (HEAD 3e4a918) のコードでも同じく失敗することを、別の作業ツリーで確かめたため、その change の起因ではない (2026-09-24、オーナー指示で起票)。

- 症状: `Expected failure '受け取れない件数では起動が止まる' but none recorded` (約 80 秒で失敗)
- アプリ側は正しく止まっている: `simctl launch` で直接起動すると `samples/ios/KsCollectionViewSamples/LargeDataCount.swift` の `fatalError` で意図どおり止まる。XCTest がアプリの異常終了を失敗として記録していない
- 環境: Xcode 26.5、iOS 26.5 Simulator (iPhone 17 / 17e / Air / 17 Pro Max で再現)。以前の verify (iOS 26 系の別機種) では通っていた。同じ日の別の実行では 2 本とも、または 1 本だけ通ったこともある
- `samples/ios/KsCollectionViewSamplesUITests/ImageGridCountUITests.swift` (`prefetch-display-size` で追加) は、同じ形の検出の揺れを避けるため、不正な値で起動が止まるかのテストを持っていない

### 探索での観測 (2026-09-26)

- **XCTest が起動中の異常終了に気づく経路は、Simulator のクラッシュレポートの到着だけ。** 通った実行の記録では、失敗は `KsCollectionViewSamples at static LargeDataCount.failIfInvalid()` (添付は診断レポート) として「Setting up automation session」の中で記録されていた。1 本目はレポートの到着まで約 15 秒、2 本目以降は約 1 秒
- テストは `XCTExpectFailure` を既定の厳格モードで使っており、期待した失敗が記録されなければそれだけで落ちる。当時の症状はこの 1 行だけなので、`app.state` の検査 (起動していないこと) は通っていたと読める。**落ちていたのは「起動してしまったこと」ではなく「クラッシュの記録が届かなかったこと」**
- 今日は再現しなかった: iPhone 17e (iOS 26.5、起動し直した直後) で 2 本を単独 8 周ずつ → 16 tests / 0 failures、通常スキーム全件 → 18 tests / 0 failures。ホストの負荷平均 48 の状況でも通った。9/25〜26 の `sections-grouping` の verify 2 回 (iPhone 17 Pro) も通っている
- 当時 (9/23〜24) の Sample UI テストの結果ファイルは残っておらず、落ちたときに約 80 秒のあいだ何を待っていたかはたどれない。ホストのクラッシュレポートは失敗していた時間帯 (9/24 02:40〜02:54) にも書かれており、「レポートが作られない」より「到着が XCTest の待ちに間に合わない」可能性が高い (未確定)
- Android の Sample には件数の起動引数が無く、この課題は iOS だけで閉じる。handbook・concepts に「クラッシュで止める」ことを前提にした記述は無い

## 検討した選択肢 (却下案と理由を含む)

### 対応するか

- **直す (採用)**: テストだけの小さな修正。全件実行の緑 (完了判定の根拠) の信用を戻し、起動を止める検査も残す
- 2 本を消す (却下): 揺れは確実に消えるが、「受け取れない件数で黙って既定の 10,000 件で開く」退行に計測まで誰も気づけなくなる
- 何もしない (却下): Sample に触る変更のたびに verify とレビューで除外の弁明が続き (`prefetch-display-size` の verify-002・review-008 で実例あり)、「いつもの揺れ」として本物の退行も流される

### 起動の失敗を何で判定するか (論点 1)

| 判断軸 | A: 判定は「起動後にアプリが動いていないこと」、クラッシュの記録は届いても届かなくてもよい (採用) | B: クラッシュさせずに理由を出す画面で止め、テストはその画面を確かめる | C: 起動を試す UI テストをやめ、件数の読み取り規則だけを単体テストで確かめる |
|---|---|---|---|
| 当時の落ち方が消えるか | 消える | 消える | 消える |
| 黙って既定件数で開く退行を捕まえられるか | 捕まえられる | 捕まえられる | 起動時に検査を呼ばなくなる退行は捕まえられない |
| 止まった理由まで確かめられるか | 確かめられない (現状と同じ) | 確かめられる | 規則は確かめられる |
| 速さ | 記録が届かない環境では 1 本約 80 秒のまま (通るようにはなる) | 数秒 | 数秒 |
| 変更の範囲 | テスト 1 ファイル | Sample の振る舞い (計測の足場の止め方) が変わる | Sample に単体テストのターゲットを追加 |

- B を却下: 理由まで確かめられるが、計測の足場の止め方を変えることになり、テストの揺れという課題に対して変える範囲が大きすぎる
- C を却下: アプリが実際に止まることを確かめなくなり、器の追加も要る

## 決定事項

- 対応する。ただしテストだけを小さく直し、原因の深追いはしない (2026-09-26、オーナー判断)
- 論点 1: A を採用。「受け取れない件数では起動しない」の判定を起動後のアプリの状態 (動いていないこと) に置き、クラッシュの記録は届けば吸収、届かなくても失敗にしない。アプリ側の止め方 (`fatalError`) は変えない
- 論点 2 (揺れる条件の切り分け): 打ち切り。原因が分かっても直し方は変わらず、現在は再現しないため
- 論点 3 (`--image-count` にも同じ検査を入れるか): 見送り。「小さく直すだけ」の方針に合わせる

### 実装への申し送り

- 修正対象は `samples/ios/KsCollectionViewSamplesUITests/LargeDataCountUITests.swift` の起動失敗の確かめ方だけ。一致条件 (issue の拾い方) は、記録が届いた場合に別の失敗として漏れないよう残す
- 起動できてしまった場合の検査の失敗は、吸収されずに失敗として残ること (一致条件に当たらない文言のまま)
- 再現しない環境で効き目を確かめる手順: アプリ側の止め方を一時的に「クラッシュレポートの出ない終了」に差し替えて記録が届かない状態をわざと作り、(1) 現行の書き方では落ちる・修正後は通ること、(2) 止める処理を一時的に外すと修正後のテストも落ちること、を確かめる。一時的な差し替えは戻してから全件を実行する
- 完了判定は通常スキームの全件実行 (件数を併記。handbook `cross/test-execution.md`)
