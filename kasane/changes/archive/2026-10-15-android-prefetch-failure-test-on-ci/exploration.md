# Exploration: android-prefetch-failure-test-on-ci

## 課題 / 動機

検証 CI の `android / verify` で、Android 本体のテスト `KsImageCacheContractTest > failedMemoryPrefetchLeavesInFlight` が、ランナーの上でだけ落ちる。2026-10-15 に `develop` へ 119662f (変更 `release-pipeline` の実装) を push したときの run (https://github.com/kamusoft/KsCollectionView/actions/runs/38711686655) で、試行 1 と、失敗したジョブだけを再実行した試行 2 の両方で、同じ行 (`android/kscollectionview/src/test/kotlin/jp/kamusoft/kscollectionview/KsImageCacheContractTest.kt:823`) の `AssertionError` で落ちた。512 件中 1 件。

落ちた行は、未対応の形式の URL (`ks-unsupported://...`) の先読みを、メモリへの先読みとして要求した直後に、`assertEquals(1, KsImageMemoryIndex.shared.fetchesInFlightCount)` で「取得中が 1 件」を確かめる行である。テストの意図は、その後の `awaitCondition` で「失敗の時点で取得中から外れる」を確かめること。

分かっていること (簡易起票の時点):

- 同じコードで、手元の `./gradlew :kscollectionview:testDebugUnitTest --rerun-tasks` は 512 件・失敗 0 (2026-10-15。`kasane/changes/archive/2026-10-15-release-pipeline/evidence/local-tests-001.md`)
- 119662f が Android で変えたのは `android/kscollectionview/build.gradle.kts` の公開の設定 (POM の scm の tag と、Maven Central へ送るタスクを止める条件) だけで、テストの設定・依存は変えていない
- 前回の `develop` への push (8a0f7df、2026-10-09) の検証 CI では `android / verify` は成功していた。テストのファイルはその間に変わっていない (最後の変更は `prefetch-display-size` の実装)
- 経緯の記録: `kasane/changes/archive/2026-10-15-release-pipeline/evidence/ci-develop-001.md`

発見の文脈: 変更 `release-pipeline` の tasks 10.1 (実装を `develop` に入れ、検証 CI が緑になることを確かめる) で見つけた。本務とは別の能力 (画像の読み込み) なので、オーナーの判断 (2026-10-15) で別の change として起票した。`main` 宛ての Pull Request では `android / verify` が必須の検査なので、これが直るまで `release-pipeline` の tasks 10.2 以降 (準備の Pull Request・初回のリリース) に進めない。

### 調査 (2026-10-15、起点 0945688)

原因: テストが、要求を出した直後の数を、実行機のスレッドの順番に依存する形で確かめていた。製品の数え方は正しい。

- 画像のローダー (Coil 3.5.0) は、先読みの要求を受けると、呼び出し元 (main スレッド) で URL の解釈とメモリキャッシュの照会までを済ませ、取得を取得用のスレッド (IO) へ渡して待つ。未対応の形式の URL は、取得用のスレッドで取得層を探した時点で即座に失敗する
- 待つ側 (kotlinx.coroutines の `withContext`) は、取得用のスレッドが**待ちに入る前に**終わっていると、待たずにその場で続きを実行する。このとき失敗の結果は、要求を出す呼び出し (`KsCoilImageLoading.enqueue`) の中で main スレッドへ返り、取得中の数はその場で 0 に戻る。取得用のスレッドが後から終われば、失敗は main の looper への投函で届き、テストが looper を回すまで数は 1 のまま
- どちらになるかは、取得用のスレッドが起きて走るのと、main スレッドが待ちに入るのと、どちらが先かで決まる。CPU が混んでいて main スレッドが割り込まれると、取得用のスレッドが先に終わる

確かめたこと (手元の macOS arm64・JDK 21.0.12.1。実験用のテストは一時的なもので、commit していない):

| 確かめたこと | 結果 |
|---|---|
| 未対応の形式の要求を 1 回出して、失敗の通知が届くスレッドと時点を記録 | 通知は main スレッドに、looper を回した時点で届いた。要求の直後と 200 ms 待った後の数は 1 |
| 同じ要求を 3000 回繰り返し、毎回、要求の直後の数を記録 | 静かな状態では 3000 回とも 1。`yes` を 40 本走らせて CPU を混ませると、3000 回中 7 回が 0 で、7 回とも失敗の通知が要求の呼び出しの中で main スレッドに届いていた |
| 取得を呼び出し元のスレッドでその場で走らせる設定 (`fetcherCoroutineContext(Dispatchers.Unconfined)`) にして、元のテストを流す (取得用のスレッドが先に終わった場合と同じ流れになる) | 元のテストは、CI と同じ assert で `expected:<1> but was:<0>` で落ちる。ただしこの設定では、ネットワーク経由の取得も保留の前に呼び出し元のスレッドで失敗し終えるので、保留を使う形の確かめには使えない |
| 取得用のスレッドで先に走らせ、最初の待ちに入るか終わるまで呼び出し元を待たせる dispatcher (検証用に一時的に作ったもの) を取得に差し込み、取得中を確かめる 7 件を直す前・直した後で流す | 直す前: `failedMemoryPrefetchLeavesInFlight` だけが `expected:<1> but was:<0>` で落ちる (CI と同じ形)。直した後: 7 件とも通る |
| 同じ dispatcher を取得とデコードの両方に差し込んで流す (実際の構成では取得とデコードが同じ IO の dispatcher で、成功までを待たずに走り切れる) | 直す前: 失敗・成功・取り消しの 3 件とも、要求の直後の確かめで落ちる。直した後: 7 件とも通る |
| テストのクラスの順番の影響 (Gradle はクラスをファイルシステムが返す順に流すので、ランナーが変わると順番が変わる) | 他の 30 クラスをそれぞれ直前に置いた 30 組と、全 31 クラスをランダムに並べた 6 通りで流し、すべて 512 件・失敗 0。順番では再現しない |
| 9 日の成功と今回の失敗の、ランナーの条件の差 | JDK (Temurin 21.0.12.1+1)・Gradle 9.7.0・依存のキャッシュ (同じ鍵から復元)・カーネル (6.17.0-1022-azure) は同じ。違うのはランナーのイメージの版 (20261004.327 → 20261012.334) で、更新の中身 (Kotlin・Gradle の同梱版・各種の道具) にこのテストの実行に効くものは無い |

未決の論点 3 つへの答え:

- **取得中は 0 件か 2 件以上か**: 0 件と判断した。CI のログには期待値と実際の値が出ていないので直接は見ていないが、2 件以上になる経路が無い (テストの前に索引を空にしており、取得中の数を増やすのは要求の呼び出しだけで、テストはそれを 1 回しか呼ばない) のに対し、0 件になる経路は上のとおり実物で再現した
- **9 日の成功から何が変わったか**: 落ちる条件を作るものは見つからなかった。競争はテストを足したときからあり、結果が実行機の混み具合で変わる。それまでの CI の成功 6 回は、取得用のスレッドが後になった回だったと考える。今回の 2 回 (同じ版のイメージのランナー) がそろって逆になった理由は特定していない (確かめる手段が手元に無い。ランナーの CPU の割り当てなど)
- **直すのはテストか製品か**: テスト。製品は、失敗がどの時点で分かっても、その時点で取得中から外す (呼び出しの中で失敗が分かれば、呼び出しから戻る時点で 0)。契約「失敗の時点で取得中から外れる」はどちらの順番でも満たしている。崩れていたのは、テストが「要求の直後はまだ失敗していない」を前提にしていたことだけである

同じ形の前提を持つテストがほかに 2 件ある (`memoryPrefetchIsInFlightOnlyUntilItCompletes`・`cancelledMemoryPrefetchLeavesInFlightImmediately`。どちらも要求の直後に「取得中」を確かめる)。こちらは取得 (スタブのネットワーク・ディスクへの書き込み・デコード) を経て成功するまでの処理が長いので、呼び出しから戻る前に終わる見込みはずっと小さいが、取得とデコードが同じ IO の dispatcher で走るので、取得用のスレッドが先に走り切れば同じ形で落ちる (上の表の最後の行で再現した)。

## 検討した選択肢 (却下案と理由を含む)

- **採用: 要求の直後の数を確かめるテストは、取得を保留してから要求を出す** — テストのネットワーク層 (`CountingNetworkClient`) の保留の口 (`isHeld`) は既にあり、保留している間は取得が終わらないので、直後の数が実行機によらず決まる。失敗のテストは、保留を解いた後にネットワーク層を失敗させる口を足して作る
- 却下: 要求の直後の `assertEquals(1, ...)` を消し、最後に 0 になることだけを確かめる — 取得中として数えていなくても (数え漏れでも) 通ってしまい、テストが空振りする
- 却下: 失敗を確かめるテストを、未対応の形式の URL のまま、looper を回さずに数を見る形で残す — 競争の結果に依存したままなので直らない
- 却下: 製品の側で、失敗の通知を必ず looper への投函で届ける (呼び出しの中では外さない) — 製品の挙動を変える。数え方は正しく、遅らせる理由が無い
- あわせて採用: 呼び出しの中で失敗し終えた場合 (CI で起きた側の流れ) を、取得をその場で走らせる設定で確実に作り、取得中に残らないことを確かめるテストを足す — 取得中として数え始める処理を要求を出した後に動かす、といった変更で、この流れの数え漏れ (取得中に 1 件残り続けて表示を遅らせる) が起きるのを捕まえる

## 決定事項

- 製品のコードは変えない
- `KsImageCacheContractTest` だけを直す:
  - テストのネットワーク層に、保留を解いた後に失敗させる口を足す。あわせて、失敗した要求を記録する (成功した要求の記録と同じ形)
  - `failedMemoryPrefetchLeavesInFlight`: 取得を保留して失敗させる設定で、ネットワーク上の URL の先読みを要求し、直後に取得中が 1 件、保留を解くと失敗し、取得中が 0 件に戻ることを確かめる (失敗したことを、失敗の記録で確かめる)
  - 新しいテスト (呼び出しの中で失敗し終えた先読み): 取得を呼び出し元のスレッドでその場で走らせる設定のローダーで、未対応の形式の URL の先読みを要求し、呼び出しから戻った時点で失敗が届いていて、取得中が 0 件であることを確かめる
  - `memoryPrefetchIsInFlightOnlyUntilItCompletes`・`cancelledMemoryPrefetchLeavesInFlightImmediately`: 要求の直後の確かめを、取得を保留した状態で行う (保留を解いてからの確かめはそのまま)
- テストの件数は 1 件増える (512 → 513)
- 直しが空振りしていないことは、元のテストが「取得用のスレッドが先に走る」条件 (上の表の、検証用の dispatcher を差し込んだ 2 行) で CI と同じ形で落ち、直した後のテストが同じ条件でも通ることで示す。検証用の dispatcher はテストに残さない (取得の順番を変える口を本体のテストに常設するほどの理由が無く、呼び出しの中で失敗し終える側は新しいテストが確かめる)
- 蒸留時に反映: `kasane/handbook/cross/test-execution.md`「収束を待つアサーション」 — 「要求の直後」の状態を確かめるテストは、確かめたい状態を保留などで作ってから確かめる (別のスレッドが先に終えると直後の状態が変わり、手元で通っても CI で落ちる)。反映するかは蒸留で判断する
