# UI Brief: sample-dark-mode-toggle

## 画面と状態

- ルートメニュー (両プラットフォーム)
  - 見出し「外観」の項目群 (「システム / ライト / ダーク」) をメニューの先頭に置き、その下に既存のデモ画面・検証画面の項目を今と同じ順で並べる
  - 状態: 選択中の項目に印がある (3 項目のうち常に 1 つ)。初回は「システム」
  - 外観: ライト / ダークの 2 状態 (「システム」は端末の表示モードに応じてどちらかになる)
- ルートメニューから開ける全画面 (デモ画面・検証画面): ライト / ダークの 2 状態。画面ごとの状態 (loading / empty / error) は既存のまま
- OS が描く部品 (iOS のナビゲーションバー・ステータスバー・segmented の Picker、Android のステータスバー): Sample の配色で塗り替えず、外観の上書きで Sample の配色と表示モードを揃える
- Android の上部バー: 今と同じく Sample の下地の色で塗る (ダークでは下地のダークの色)

## リファレンス注釈

画像のリファレンスは無い。形の参考は `../KsSettingsView/` の Sample (オーナー指定):

- 採用: ルートメニューの「外観」グループと 3 択・選択中の印と読み上げ「選択中」・初期値「システム」・再起動後の保持
- 採用: ダークの配色を OS のダークの灰色と見分けられる色味にする考え方 (KsSettingsView は暖色案を採用し、中立色の案をライブラリ既定色のダークと見分けにくいとして却下した)
- 対象外: KsSettingsView の配色そのもの (MAUI 互換の琥珀色のアクセント)。KsCollectionView はライトの組を今の値のまま残し、ダークの組はこの change の mock で決める

## デザイントークン参照

concepts/ にデザイントークンの定義は無い。Sample の配色のトークンは Sample 共通の配色定義 (`samples/ios/KsCollectionViewSamples/SampleTheme.swift` / `samples/android/app/src/main/kotlin/jp/kamusoft/kscollectionview/samples/android/SampleTheme.kt`) が正で、両プラットフォームで同じ RGBA を持つ (handbook/cross/sample-parity・cross/ADR-0007)。

- ライトの組: 今の値のまま (accent / background / cell / text / secondaryText / separator)
- ダークの組: 承認 mock の値を両プラットフォームの配色定義に写す
- 色見本 (グリッドのセルの項目の色): 項目の内容を表す色のため、ライト / ダークで同じ値を使う
- アクセントの上の色 (アクセントで塗った部品の上に載せる文字・印・つまみ。今は Android の `Color.White` の直書き): 配色定義に足す。ライトは白 (今の値)、ダークは下地のダークの色 (紺)。ダークのアクセントは承認 mock で明るめの青にしたため、白ではコントラストが足りない (second-opinion-spec-001 の指摘 2)

### 視認性の基準

デルタスペックの「読める」「背景に埋もれない」の判定に使う。対象はダークの組だけ (ライトの組は今の値のまま変えないため、「変更前と同じ」で判定する。今のライトの値はアクセント / 下地が約 4.1:1、補助の文字 / 下地が約 4.4:1 で、下の文字の基準に届かない組を含む):

- 文字と、その背景の組 (文字 / 下地、文字 / 行、補助の文字 / 下地、補助の文字 / 行、アクセント / 下地、アクセント / 行、アクセントの上の色 / アクセント): コントラスト比 4.5:1 以上 (WCAG 2.x の AA)
- 選択の印・操作部品の塗りと、その背景の組: 3:1 以上
- 区切り / 行: ライトの今の比 (約 1.4:1) と同程度 (1.3:1 以上)。区切りは飾りの線のため文字・部品の基準は当てない
- OS の標準部品とライブラリの既定の色は対象外 (後者は完了条件の目視確認で扱う)
- 承認 mock のダークの値と「アクセントの上の色」の紺は、提案時の計算で上の基準を満たす (文字の組は最小でアクセント / 行の約 5.0:1、区切り / 行は約 1.34:1)

## 承認モック

`mock/plan-b-navy.html` を採用 (`mock/approved.png`)。2026-09-26 オーナー承認。

- 採用理由: ダークの下地と行をアクセントの青の色相に寄せた紺にすると、OS のダークの灰色で描かれるライブラリの既定の色 (iOS のタップの反応・画像の読み込み中の色等) と見分けやすく、ダークでのライブラリの既定の色の確認 (完了条件) に向く。KsSettingsView の判断と同じ考え方
- 却下: `mock/plan-a-neutral.html` (中立の灰色のダーク) — ふつうのアプリのダークに近いが、ライブラリの既定の色 (OS の灰色) と見分けにくい
- アクセントはダークで明るめの青にする (mock の値)。構成・文言は 2 案で同じ
- mock の「リスト」の区切り線「既定」は、ライブラリ既定の固定色のまま明るく描いている (Non-Goal。ライブラリ側の別 change で直す)。実装でもこの見え方になるのが正しい
- 色の実値は mock の HTML (`plan-b-navy.html` の各フレームの CSS 変数) が正。アクセントの上の色は mock に描いていないため、上の「デザイントークン参照」の定めに従う
- Android のルートメニューのフレームの検証画面の項目名を、実物の「検証: 行の高さ変化 (Android 固有)」に直した (second-opinion-spec-001 の指摘 1。承認画像の範囲外の行のため approved.png は変わらない)
