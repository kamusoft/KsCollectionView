### Requirement: 確かめるだけの使い方

追従の Skill は、確かめるだけの使い方で呼ばれたとき、変わった源泉の一覧を出す道具を流し、その出力から、追従が要るかどうかと、見直す利用者向け Skill の 1 枚を報告しなければならない (SHALL)。追従が要るのは、道具の出力に、変わった源泉・対応の決まっていない源泉・名前の変わった源泉・無くなった源泉・公開の宣言の増減のどれかがあるときである。

あわせて、記録の commit の後に本体のソースを変えた commit の一覧を報告する。本体のソースの変更には、道具に現れないもの (複数行の宣言の続きの行・挙動だけの変更) があるため、一覧があるときは、人が本体の差分を見る必要があると添える。

この使い方は、利用者向け Skill・記録・作業ツリー・履歴のどれも変えず、ワーカーも起動しない。

**Requires**:
- 変わった源泉の一覧を出す道具が、成功で終わること (記録の commit が手元の履歴にあり、記録が読める)

**Side Effects**: なし

#### Scenario: 変わっていなければ、追従は要らないと報告する
- **GIVEN** 記録の commit の後に、源泉も本体のソースも変わっていない
- **WHEN** 確かめるだけの使い方で呼ぶ
- **THEN** 追従は要らないと報告する

#### Scenario: 変わった源泉があれば、源泉と見直す 1 枚を報告する
- **GIVEN** 記録の commit の後に、ページングの概念の文書を変えて commit した
- **WHEN** 確かめるだけの使い方で呼ぶ
- **THEN** 追従が要ることと、その文書と、見直す 1 枚 (両プラットフォームのページングの 1 枚) を報告する

#### Scenario: 本体のソースを変えた commit があれば、一覧と、人が差分を見る必要を報告する
- **GIVEN** 記録の commit の後に、本体のソースの公開の宣言でない行だけを変えて commit した
- **WHEN** 確かめるだけの使い方で呼ぶ
- **THEN** 変わった源泉が無いことと、本体のソースを変えた commit の一覧と、人が本体の差分を見る必要があることを報告する

#### Scenario: 道具が失敗すると、理由を報告し、要らないとは言わない
- **GIVEN** 記録の commit の ID が、手元の履歴に無い
- **WHEN** 確かめるだけの使い方で呼ぶ
- **THEN** 道具が出した理由を報告し、追従が要らないとは報告しない

#### Scenario: 何も変えない
- **GIVEN** 変わった源泉がある作業ツリー
- **WHEN** 確かめるだけの使い方で呼ぶ
- **THEN** 作業ツリー・記録・履歴が変わらず、ワーカーが起動されない

### Requirement: 書き直しの任せ方

追従の Skill は、追従の使い方で呼ばれたとき、変わった源泉の一覧 (差分の本文は含めない) を出し、見直す 1 枚を持つ利用者向け Skill ごと (1 つのプラットフォームの英語版と日本語版の組ごと) に、器 ksn-scribe のワーカーへ書き直しを任せなければならない (SHALL)。ワーカーへは、見直す 1 枚と、それに掛かる変わった源泉と、差分を出す仕方と、従う決まり (handbook の `cross/user-docs-writing.md` と、`cross/user-skill-refresh.md` の該当の節) を渡す。対応の決まっていない源泉・名前の変わった源泉・無くなった源泉・公開の宣言の増減も、掛かるプラットフォームのワーカーに渡す。記録の commit の後に本体のソースを変えた commit があるときは、その差分を見る仕方もそのプラットフォームのワーカーに渡し、道具に現れない変更 (`cross/user-skill-refresh.md` の「道具の拾い方の限界と、人が本体の差分を見る場面」) を探させる。ワーカーは、コード例を変えた・足したときは、`cross/user-docs-writing.md` の「コード例を確かめる」でコンパイルして確かめ、結果を報告する。

メインは、概念の文書の本文と差分の本文を読み込まず、利用者向け Skill の文面を自分で書き直さない。差分の本文は、ワーカーが自分で出して読む。ワーカーが決められずに報告した箇所 (新しい内容を載せる 1 枚・載せない名前の候補・源泉と本体のコードの食い違いなど) は、メインがオーナーに諮り、決まった内容を添えて、もう一度ワーカーに任せる。

記録の対象の書き足し・直し (対応の決まっていない源泉の行き先、名前の変わった源泉のパス、無くなった源泉の削除、載せないと決めた名前) も、決まった内容でワーカーに任せる。

**Requires**:
- 器 ksn-scribe のワーカーを起動できること
- 変わった源泉の一覧を出す道具が、成功で終わること

**Side Effects**:

- `skills/.manifest.json` の `sources` と `apiExclusions`: 更新 (記録の対象の書き足し・直しがあるとき)

#### Scenario: 両プラットフォームに掛かる源泉が変わると、Skill ごとにワーカーへ任せる
- **GIVEN** 記録の commit の後に、両プラットフォームに掛かるページングの概念の文書を変えて commit した
- **WHEN** 追従の使い方で呼ぶ
- **THEN** iOS の Skill と Android の Skill のそれぞれについて、英語版と日本語版のページングの 1 枚を、1 つのワーカーに任せる

#### Scenario: 片方のプラットフォームにだけ掛かる源泉なら、その Skill だけを任せる
- **GIVEN** 記録の commit の後に、iOS にだけ掛かる概念の文書を変えて commit した
- **WHEN** 追従の使い方で呼ぶ
- **THEN** iOS の Skill だけを、ワーカーに任せる

#### Scenario: 本体のソースを変えた commit があると、その差分を見させる
- **GIVEN** 記録の commit の後に、Android の本体のソースの、複数行にわたる公開の宣言の続きの行だけを変えて commit した。源泉は変えていない
- **WHEN** 追従の使い方で呼ぶ
- **THEN** Android の Skill のワーカーを起動し、その commit の差分を見る仕方を渡す

#### Scenario: コード例を変えたワーカーは、コンパイルの結果を報告する
- **GIVEN** ワーカーが、ページングの 1 枚のコードブロックを書き直した
- **WHEN** ワーカーが報告する
- **THEN** 報告に、そのコード例をコンパイルして確かめた結果がある

#### Scenario: ワーカーが決められなかった箇所は、オーナーに諮ってから任せ直す
- **GIVEN** ワーカーが、新しい内容を載せる 1 枚を決められないと報告した
- **WHEN** メインがその報告を受ける
- **THEN** メインは、その箇所をオーナーに諮り、自分では書かず、オーナーが決めた内容を添えて、もう一度ワーカーに任せる

#### Scenario: 変わった源泉が無ければ、ワーカーを起動せずに終わる
- **GIVEN** 道具の出力に、追従が要るものが無く、記録の commit の後に本体のソースを変えた commit も無い
- **WHEN** 追従の使い方で呼ぶ
- **THEN** 追従は要らないと報告して終わり、ワーカーを起動しない

#### Scenario: 器を起動できないと、何も書かずに止まる
- **GIVEN** 実行環境に、器 ksn-scribe が置かれていない
- **WHEN** 追従の使い方で呼ぶ
- **THEN** 器を起動できないことと、器を置く手順の案内を出して止まり、メインが代わりに利用者向け Skill を書き換えることも、器を指定しない起動もしない

#### Scenario: 道具が失敗すると、何も書かずに止まる
- **GIVEN** 記録が読めない
- **WHEN** 追従の使い方で呼ぶ
- **THEN** 道具が出した理由を報告して止まり、ワーカーを起動しない

### Requirement: 検査とオーナーの承認

追従の Skill は、ワーカーの書き直しの後、公開の宣言の名前の漏れを出す道具と、handbook の `cross/user-skill-refresh.md` が決めた検査を流し、漏れと違反を、掛かるプラットフォームのワーカーに戻して直させなければならない (SHALL)。漏れた名前は、ワーカーが宣言を読んで、利用者が使う名前なら 1 枚に載せ、利用者向けでないと判断した名前は、載せない候補として報告する (前の Requirement の、決められなかった箇所と同じに扱う)。同じ違反が、2 回戻しても残るときは、残った違反を添えてオーナーに諮る。名前の漏れを出す道具が、確かめられずに終わったとき (公開の宣言を拾えない・記録を読めない) は、漏れが無いとは扱わず、理由を添えてオーナーに諮る。追従の範囲の外のファイルの違反は、ワーカーに戻さず、「追従の範囲」の Requirement で扱う。

漏れと違反が無くなったら、`cross/user-skill-refresh.md` が決めた見せるもの (変わった源泉の一覧とそれぞれの扱い・人が本体の差分を見た結果・配った先を再現した確認の判断と結果・名前の漏れの結果と外す候補・流した検査と結果・コードで確かめられなかったこと) をオーナーに見せて、承認を待つ。承認を得る前に、commit も、記録の commit の ID の更新もしない。オーナーが承認しなかったときは、指摘をワーカーに戻し、検査からやり直してから、もう一度見せる。

**Side Effects**:
- 利用者向け Skill の、見直す 1 枚 (英語版と日本語版): 更新 (漏れ・違反・オーナーの指摘を、ワーカーに戻して直させるとき)
- `skills/.manifest.json` の `apiExclusions`: 更新 (オーナーが載せないと決めた名前を、ワーカーに書き足させるとき)

#### Scenario: 名前の漏れを確かめられないと、漏れが無いとは扱わない
- **GIVEN** 名前の漏れを出す道具が、公開の宣言を 1 つも拾えずに終わった
- **WHEN** メインがその結果を受ける
- **THEN** 漏れが無いとは扱わず、理由を添えてオーナーに諮る

#### Scenario: 検査が落ちると、ワーカーに戻す
- **GIVEN** ワーカーが、日本語版だけに見出しを足した
- **WHEN** 検査を流す
- **THEN** 英語版と日本語版の食い違いの違反を、そのプラットフォームのワーカーに戻し、オーナーには、まだ見せない

#### Scenario: 2 回戻しても残る違反は、オーナーに諮る
- **GIVEN** 同じ違反を、2 回ワーカーに戻しても、検査が同じ違反を出す
- **WHEN** 3 回目の検査の結果を受ける
- **THEN** 残った違反を添えて、オーナーに諮る

#### Scenario: 違反が無くなると、決めたものを見せて止まる
- **GIVEN** 検査と名前の漏れの報告が、違反なし・漏れなしで終わった
- **WHEN** メインが次へ進む
- **THEN** 決めた見せるものをオーナーに見せて、承認を待ち、commit も、記録の commit の ID の更新もしていない

#### Scenario: 承認されないと、直してから見せ直す
- **GIVEN** オーナーが、直した 1 枚の言い回しに指摘を出した
- **WHEN** メインが指摘を受ける
- **THEN** 指摘をワーカーに戻し、検査を流し直してから、もう一度見せる

### Requirement: 配った先を再現した確認の判断

追従の Skill は、ワーカーが報告した変えたものを、`cross/user-skill-refresh.md` の「初回と同じ確かめ方をする場面」の表の行に当て、読ませる確認と使わせる確認の回数を決めなければならない (SHALL)。複数の行に当たるときは、回数の多い方の行を採る。回数が 1 回以上なら、同じ節の進め方で、器 ksn-scribe のワーカーに、リポジトリの外の作業用の置き場で行わせ、挙がった指摘を書き直しのワーカーに戻す。回数が 0 なら行わない。どちらでも、当てた行と理由をオーナーに見せる。

**Side Effects**:
- 利用者向け Skill の、見直す 1 枚 (英語版と日本語版): 更新 (挙がった指摘を、書き直しのワーカーに戻して直させるとき)

作業用の置き場はリポジトリの外に作り、確認が終わったら消す。

#### Scenario: 文の直しだけなら、確認を行わない
- **GIVEN** ワーカーが、1 枚の文を直しただけだと報告した
- **WHEN** 確かめ方を決める
- **THEN** 読ませる確認も使わせる確認も行わず、当てた行 (文の直し) と理由をオーナーに見せる

#### Scenario: コードブロックを書き直したら、その 1 枚の確認を行う
- **GIVEN** ワーカーが、iOS の Skill の並べ方の 1 枚の、英語版と日本語版のコードブロックを書き直したと報告した
- **WHEN** 確かめ方を決める
- **THEN** iOS の Skill を言語ごとに 1 回読ませ、並べ方の課題を iOS で 1 回使わせ、挙がった指摘を書き直しのワーカーに戻す

### Requirement: 追従の範囲

追従の Skill が追従の中で直すのは、利用者向け Skill の既存の 1 枚と、記録の `sources`・`apiExclusions` に限らなければならない (SHALL)。次の 2 つは追従の中で行わず、ワーカーにも行わせない。

- 範囲の外のファイル (ルートの README・Skill の索引・利用者役の画面など) の直し。範囲の外のファイルの直しが要るとワーカーが報告したとき、または範囲の外のファイルに検査の違反が出たときは、ワーカーに戻さず、その箇所と、別の作業で直す必要があることをオーナーに伝える
- 利用者向け Skill の構成の見直し (1 枚の追加・名前の変更・分け方の変更)。今の 1 枚のどれにも入らない内容があるとワーカーが報告したときは、構成の見直しが要ることと、それを変更の実装で行う必要があることをオーナーに伝える

どちらかが残ったまま承認されたときは、範囲の中の直しは commit してよいが、記録の commit の ID は更新しない (残った源泉の変更を、次の追従でも見つけられるようにするため)。

**Requires**:
- 追従に要る直しが、利用者向け Skill の既存の 1 枚と、記録の `sources`・`apiExclusions` に収まること

**Side Effects**: なし (範囲の中の直しの commit は、「承認の後の commit と記録の更新」で数える)

#### Scenario: README の検査の違反は、ワーカーに戻さずにオーナーに伝える
- **GIVEN** 利用者役の画面のファイルが変わり、README の最小コード例が古いままで、README の例の検査が違反を出した
- **WHEN** メインが検査の結果を受ける
- **THEN** その違反をワーカーに戻さず、README を別の作業で直す必要があることをオーナーに伝える。ワーカーは README を書き換えていない

#### Scenario: 1 枚の追加が要ると報告されたら、構成の見直しとしてオーナーに伝える
- **GIVEN** ワーカーが、新しい内容が今の 5 枚のどれにも入らないと報告した
- **WHEN** メインがその報告を受ける
- **THEN** 1 枚を足さず、構成の見直しを変更の実装で行う必要があることをオーナーに伝える

#### Scenario: 範囲の外が残ったまま承認されると、記録の commit の ID を更新しない
- **GIVEN** README を別の作業で直す必要が残ったまま、オーナーが範囲の中の直しを承認した
- **WHEN** メインが承認を受ける
- **THEN** 範囲の中の直しを commit し、記録の commit の ID は更新せず、その理由をオーナーに伝える

### Requirement: 承認の後の commit と記録の更新

オーナーが承認したら、追従の Skill は、追従で変えたファイル (利用者向け Skill の 1 枚と、記録の `sources`・`apiExclusions`) だけを 1 つの commit にし、続けて記録の更新の道具を流し、書き換わった記録のファイルだけを、もう 1 つの commit にしなければならない (SHALL)。追従で変えたファイルが無いとき (変わった源泉のどれも利用者に見える内容を変えておらず、直す 1 枚が無かったとき) は、1 つ目の commit を作らず、記録の commit だけを作る。追従の要約 (扱った源泉・直した 1 枚・直さなかった源泉と理由・流した検査と結果・配った先を再現した確認の判断) は、最初に作る commit のメッセージに書く。追従で変えていないファイルは commit しない。push はしない。範囲の外が残っているときの記録の扱いは、「追従の範囲」の Requirement に従う。

**Requires**:
- 源泉のパスに、commit していない変更が無いこと

**Side Effects**:
- git の履歴: commit の作成 (追従で変えたファイルの commit と、記録のファイルの commit)
- `skills/.manifest.json` の、前回追従したときに見た commit の ID: 更新

#### Scenario: 承認の後、2 つの commit ができ、追従は要らない状態になる
- **GIVEN** オーナーが、直した Skill を承認した。源泉に commit していない変更は無い
- **WHEN** メインが承認を受ける
- **THEN** 直した 1 枚の commit と、記録の commit がこの順にでき、その後に確かめるだけの使い方で呼ぶと、変わった源泉は無いと出る

#### Scenario: 直す 1 枚が無かったときは、記録の commit だけを作る
- **GIVEN** ワーカーが、変わった源泉はどれも利用者に見える内容を変えていないと報告し、オーナーがその扱いを承認した
- **WHEN** メインが承認を受ける
- **THEN** 記録の commit だけができ、そのメッセージに、扱った源泉と、直さなかった理由がある。その後に確かめるだけの使い方で呼ぶと、変わった源泉は無いと出る

#### Scenario: 源泉に commit していない変更があると、記録を更新しない
- **GIVEN** 源泉の概念の文書に、commit していない変更が残っている状態で、オーナーが承認した
- **WHEN** メインが承認を受ける
- **THEN** 記録を更新せず、その源泉の一覧と、オーナーがそれを commit してから記録を更新する必要があることを伝える。源泉の変更を、メインが commit することはしない

#### Scenario: 追従で変えていないファイルは commit しない
- **GIVEN** 作業ツリーに、追従と関係の無い Sample のソースの変更が残っている
- **WHEN** 承認の後に commit する
- **THEN** その変更は、どちらの commit にも入らない

#### Scenario: push しない
- **GIVEN** 承認の後の 2 つの commit ができた
- **WHEN** 追従の Skill が終わる
- **THEN** リモートの履歴は変わっていない

### Requirement: 追従の入口の案内

AGENTS.md は、利用者向け Skill の追従を、オーナーが頼んだときに追従の Skill `docs-refresh` で行うことを示さなければならない (SHALL)。利用者向け Skill の構成の見直し (1 枚の追加・名前の変更・分け方の変更) は、追従ではなく変更の実装で行うことも示す。

**Side Effects**: なし

#### Scenario: AGENTS.md から追従の入口が分かる
- **GIVEN** 今の AGENTS.md
- **WHEN** 利用者向け Skill の追従について読む
- **THEN** 追従の Skill の名前と、頼まれたときにだけ使うことが書いてある
