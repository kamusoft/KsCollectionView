# 利用者向け Skill の追従

この文書は、利用者向け Skill (`skills/`) を、源泉 (`kasane/concepts/`・ビルドの設定・本体の公開の宣言) の変更に追従させるときの、手順の中身をまとめる。道具の出力の読み方・終了コード・直し方・確かめ方の基準・commit と記録の更新の順を書く。Skill の文面の書き方は、[利用者向け Skill と README の書き方](user-docs-writing.md) にある。

追従は、オーナーが頼んだときにだけ行う。検証 CI は、Skill が源泉からずれていることを検査しない。追従は、プロジェクト内の追従の Skill `docs-refresh` (`.agents/skills/docs-refresh/`) から始める。前回追従した commit からの差分をもとに、専用の Skill から追従すると決めた理由は、[cross/ADR-0020](../../decisions/cross/0020-user-skill-refresh-via-dedicated-skill.md) にある。

追従の Skill とこの文書は、役目で分けてある。

| 置き場 | 持つもの |
|---|---|
| 追従の Skill `docs-refresh` | 入口と指揮。2 つの使い方 (確かめるだけ・追従)、メインの進め方、ワーカーへの任せ方とその指示のひな形、オーナーに見せる時点、commit のメッセージの形 |
| この文書 | 手順の中身。道具の出力の読み方・終了コード・直し方・確かめ方の基準・追従の範囲 |

追従の Skill は、この文書の節を名前で指して読ませる。節の名前を変えるときは、追従の Skill の本文とひな形の参照も同じ回に直す。

2026-10-10 時点で、追従を通しで行ったことはまだ無い。この文書の流れは、道具の実物と、初回の制作 (Skill を最初に作った変更 `user-docs`) で行ったことから組み立てた。

codex から追従の使い方 (器 `ksn-scribe` を指定したワーカーの起動を含む) を通しで動かしたことは、まだ無い (未確認)。codex から確かめたのは、Skill の名前と説明が一覧に出ることと、確かめるだけの使い方までである。codex で初めて追従するときに、ワーカーを起動できることを確かめる。

公開 API や利用者に見える挙動を変えた変更の後に、この文書を開いたときは、その場では Skill を直さない。追従はオーナーが頼んだときに、変わった分をまとめて行う。その変更の報告に、Skill に関わる変更があったこと (変えた公開の宣言・利用者に見える挙動) を書いて、オーナーに知らせる。

## この文書の言葉

| 言葉 | 意味 |
|---|---|
| 源泉 | Skill の内容の元になるもの。概念の文書 (`kasane/concepts/`)・ビルドの設定・本体の公開の宣言・利用者役の画面のファイルなど。追従の記録の `sources` に並べてある |
| 1 枚 | Skill のディレクトリの中のファイル 1 つ。`SKILL.md` と、`references/` の下の 5 つ (`basics.md`・`layout.md`・`paging.md`・`reorder.md`・`images.md`) のどれかを指す |
| 源泉が 1 枚に掛かる | その源泉が変わったら、その 1 枚を見直す、という対応。1 つの源泉が、複数の 1 枚に掛かることがある (記録の `pages` に、すべてを書く) |
| 利用者役 | 配布物を利用者と同じ書き方で取る、最小のプロジェクト (`verification/ios/`・`verification/android/`)。画面のファイルが、README の最小コード例と `SKILL.md` の最小の動く例の元になっている ([利用者の立場のビルドの確認](consumer-build-check.md)) |
| オーナー | リポジトリの持ち主である開発者。追従を頼み、直した Skill を承認する |
| メイン | オーナーの依頼を受けて、追従の Skill を読み込んだセッション。道具を流し、ワーカーに任せ、結果をオーナーに見せて、承認の後に commit と記録の更新を行う。概念の文書の本文と差分の本文を読まず、利用者向け Skill の文面を自分で書き直さない |
| ワーカー | メインが器 `ksn-scribe` を指定して起動するエージェント。利用者向け Skill の書き直し (1 プラットフォームの英語版と日本語版の組ごとに 1 つ)・読ませる確認・使わせる確認を行う。commit はしない。決められない箇所は埋めずに報告で戻す |
| 器 | ワーカーの起動の型。ワーカーのモデルと effort は、器の定義が決める。メインは器を選ぶだけである |
| 蒸留 | 終わった変更から、長く残す知識 (決定・規約・概念の文書) を取り出す、ハーネスの工程。概念の文書は、蒸留で直される |
| 公開の型のファイル | 本体のソース (`ios/Sources/`・`android/kscollectionview/src/main/`) のうち、公開の宣言を持つファイル |

## 用意してあるもの

| もの | 場所 | 役割 |
|---|---|---|
| 追従の Skill | `.agents/skills/docs-refresh/` (`.claude/skills/docs-refresh` は、そこへの相対のリンク) | 追従の入口。名前 `docs-refresh` で呼ぶ。実体を 1 つにし、2 つの CLI の置き場から同じものを読ませる。置き場の形は、スクリプトのテストが確かめる |
| 追従の記録 | `skills/.manifest.json` | 前回追従したときに見た commit の ID (`syncedCommit`)、差分を出す対象のパスと掛かる Skill の 1 枚 (`sources`)、Skill に載せないと決めた公開の宣言の名前 (`apiExclusions`) を持つ。利用者がコピーするのは `skills/{en,ja}/<名前>/` なので、このファイルは利用者の手元に行かない |
| 変わった源泉を出す道具 | `scripts/docs/skills-refresh.py` | `status` (変わった源泉の一覧) と `record` (記録の更新) の 2 つの使い方を持つ |
| 公開の宣言の名前の漏れを出す道具 | `scripts/docs/check-api-coverage.py` | 本体のソースの公開の宣言の名前のうち、Skill に一度も現れないものを出す |
| Skill 自身の整合の検査 | `scripts/ci/check-skills.py` | 英語版と日本語版の一致・frontmatter・Skill の外へのリンク・URL・内部の言葉 (ADR の番号や利用者役など、利用者の知らない言葉。一覧は `scripts/ci/user-docs-rules.json`) を確かめる。検証 CI でも、スクリプトのテストを通して流れる |
| README の例の検査 | `scripts/ci/check-readme-examples.py` | README の最小コード例と、README・`SKILL.md` のインストール例を確かめる。検証 CI でも流れる |

道具は、どれも Skill を書き換えない。git の commit・add・push も行わない。`record` だけが、記録のファイルの中の commit の ID を書き換える。

記録の形は、`scripts/docs/skills_manifest.py` の冒頭に書いてある。`sources` と `apiExclusions` を手で書き足すときは、次の形にする (今の記録からの抜き書き)。

```json
{"path": "kasane/concepts/core/core-model/collection-items.md", "pages": ["references/basics.md", "references/layout.md"]}
{"path": "ios/Package.swift", "pages": ["SKILL.md"], "platforms": ["ios"]}
{"name": "buildBlock", "reason": "テンプレートを並べて書くブロック (KsTemplateBuilder) を、コンパイラが組み立てるときに自動で呼ぶ関数。利用者は自分のコードに書かない"}
```

1 行目と 2 行目が `sources` の 1 件、3 行目が `apiExclusions` の `ios` か `android` の一覧の 1 件である。`platforms` は、片方のプラットフォームの Skill にだけ掛かるときに書く。Skill に掛からない源泉は、`pages` の代わりに `excluded` (掛からない理由の文字列) を書く。

## 流れ

| 流れ | 行う側 |
|---|---|
| 1. 変わった源泉を出す | メイン (`--diff` を付けずに流す) |
| 2. 出たものを読んで、Skill を直す (英語版と日本語版を同じ回に) | ワーカー (差分の本文は、ワーカーが自分で出して読む) |
| 3. 公開の宣言の名前の漏れを見る | メインが道具を流し、漏れはワーカーに戻す |
| 4. 検査を流す | メインが流し、違反はワーカーに戻す |
| 5. コード例を変えたときは、コンパイルして確かめる | ワーカー (結果を報告に書く) |
| 6. オーナーの承認を得る | メインが見せ、オーナーが決める |
| 7. 記録を更新する | メイン (承認の後) |

流れの番号に入っていない作業が 2 つある。どちらも、結果を 6 でオーナーに見せる。

| 作業 | 行う時点 | 書いてある節 |
|---|---|---|
| 人が本体の差分を見る | 2 の中。記録の commit の後に本体のソースを変えた commit があるときに、道具に現れない変更が無いかを、そのプラットフォームのワーカーが見る | 「道具の拾い方の限界と、人が本体の差分を見る場面」 |
| 配った先を再現した確認 (読ませる・使わせる) | 5 の後、6 の前。変えた量が、表の当たる行のとき。ワーカーに行わせる | 「初回と同じ確かめ方をする場面」 |

追従の Skill には、追従が要るかを確かめるだけの使い方もある。1 を流し、記録の commit の後に本体のソースを変えた commit の一覧 (下の「道具の拾い方の限界と、人が本体の差分を見る場面」のコマンドの 1 行目) と合わせて報告する。何も書き換えず、ワーカーも起動しない。

### commit と記録の更新の順

1 から 5 は、作業ツリーの上で行う。ワーカーは commit しない。commit と `record` は、6 の承認の後に、メインが次の順で行う。初回の制作も、この順だった。

1. 追従で変えたファイル (利用者向け Skill の 1 枚と、記録の `sources`・`apiExclusions`) だけを、1 つの commit にする。作業ツリーと index に追従と関係の無い変更が残っていても、その変更は入れない (パスを名指しして `git add` し、`git commit --only -- <パス…>` で commit すると、前から stage されている別の作業の変更も入らない)。直した 1 枚が無く、記録の `sources`・`apiExclusions` だけを直したときも、この commit を作る。`record` は記録のファイルの変更では止まらないので、作らないと、対応表の直しが 3 の commit に混ざる
2. `record` を流す。対象のパスに commit していない変更があると止まるので、1 より前には流せない
3. 書き換わった記録のファイル (`skills/.manifest.json`) だけを、続けて commit する (`git commit --only -- skills/.manifest.json`)

push はしない。

| 場面 | すること |
|---|---|
| 追従で変えたファイルが無かった (変わった源泉のどれも、利用者に見える内容を変えておらず、利用者向け Skill の 1 枚にも、記録の `sources`・`apiExclusions` にも変更が無い) | 1 の commit を作らず、2 と 3 だけを行う。3 の commit のメッセージに、追従の証跡を書く |
| 源泉に commit していない変更が残っている | 2 が止まる。記録を更新せず、commit していない源泉の一覧と、オーナーがそれを commit してから記録を更新する必要があることを伝える。源泉の変更を、メインもワーカーも commit しない。1 の commit も無く、commit が 1 つもできないときは、6 でオーナーに見せた内容と、ここで伝えた内容をその回の追従の証跡とする |
| 追従の範囲の外の直しか、構成の見直しが残っている | 1 の commit は作ってよいが、2 と 3 は行わない (「追従の範囲」)。範囲の中の直しも無く、commit が 1 つもできないときは、6 でオーナーに見せた内容をその回の追従の証跡とし、commit を作らないことを伝える |

追従を始めるときに、源泉に commit していない変更があってもよい。`status` は、commit していない変更も数えて出す。

### 追従の証跡

追従は、変更のフローの外で頼まれることがあり、変更のディレクトリ (`kasane/changes/<変更の名前>/`) が無い。そのため、追従の証跡は、承認の後に最初に作る commit のメッセージに要約して残す。書くものは次のとおり。

- 扱った源泉 (`status` が出したもの)
- 直した 1 枚 (英語版と日本語版)
- 直さなかった源泉と、その理由
- 流した検査と結果
- 配った先を再現した確認の判断 (当てた表の行と理由。行ったなら、回数と結果)

変更の中で追従を行ったときは、変更のディレクトリの `evidence/` にも残してよい。

### 1. 変わった源泉を出す

```bash
python3 scripts/docs/skills-refresh.py status
python3 scripts/docs/skills-refresh.py status --diff
```

`status` は、記録の commit から今の作業ツリーまでの間に変わったものを出す。commit していない変更と、まだ追跡していない新しいファイルも数える。`--diff` を付けると、変わった源泉・名前の変わった源泉・無くなった源泉の、差分の本文も出す。無くなった源泉は、記録の commit の時点の内容の全行が、消えた行として出る。

| 終了コード | 意味 |
|---|---|
| 0 | 一覧を出した。変わった源泉があっても 0 である |
| 1 | 失敗した。一覧は出ない。記録の commit が手元の履歴に無い (浅い取得・別のリポジトリ)、記録を読めない、などである。理由は標準エラー出力に出る |
| 2 | 引数の誤り |

終了コードは、変わった源泉の有無を表さない。出力を読む。

終了コード 1 で終わったときは、追従を進めない。標準エラー出力の理由を読んで直す。記録の commit が手元の履歴に無いときは、履歴をすべて持つ clone で流し直す。記録を読めないときは、記録のファイルの形を直す。

### 2. 出たものを読んで、Skill を直す

`status` は、次の 5 つを分けて出す。

| 出るもの | 意味 | すること |
|---|---|---|
| 変わった源泉 | 記録の `sources` にあるパスの内容が変わった。掛かる Skill の 1 枚が添えてある | `--diff` の差分を読み、添えてある 1 枚の該当の場所を直す。片方のプラットフォームの Skill にだけ掛かる源泉は、そう添えてある。差分が利用者に見える内容を変えていなければ、Skill は直さなくてよい (直さなかった源泉と理由を、ワーカーの報告に書く) |
| 対応の決まっていない源泉 | `kasane/concepts/` の下に、記録に無い概念の文書がある (前回の追従の後に足された文書) | 文書を読み、利用者に関わる内容を、その回に Skill の当たる 1 枚へ書く。そのうえで、記録の `sources` に、掛かる 1 枚 (`pages`) か、掛からない理由 (`excluded`) のどちらかを足す。記録に足すだけで、追従済みにしない (下の「新しい概念の文書の扱い」) |
| 名前の変わった源泉 | 記録にあるパスが無くなり、前の内容と半分以上が同じ文書が、対応の決まっていない文書の中にある。前の名前と今の名前が出る | 記録の `path` を今の名前に直す。内容も変わっていれば、変わった源泉と同じに扱う |
| 無くなった源泉 | 記録にあるパスが無くなり、名前の変わった先も見つからない。掛かっていた Skill の 1 枚が添えてある | `--diff` で消えた内容を読み、源泉が消された理由を確かめる。Skill の該当の記述を消すか残すかを決め、記録からその項目を消す |
| 公開の宣言の増減 | 本体のソースの公開の宣言の行が、足された・消えた | 足された宣言は、Skill のどこに載せるかを決める。消えた宣言は、Skill に残っている名前とコード例を消す。1 行の宣言の引数や型を変えると、前の行が消えた行、今の行が足された行として出るので、Skill のコード例と説明を新しい形に合わせる |

Skill に掛からない源泉 (記録で `excluded` にした源泉) は、「見直す 1 枚」か「掛かっていた 1 枚」が `Skill に掛からない (理由: …)` と出る。変わった源泉に出たときは、Skill も記録も直さない。名前の変わった源泉・無くなった源泉に出たときは、見直す 1 枚が無くても、記録の `path` を直すか項目を消す。`record` は `sources` を直さずに記録の commit の ID だけを書き換えるので、直さないと、次の `status` でも出続ける。消した源泉は「無くなった源泉」のまま、改名した源泉は「無くなった源泉」と「対応の決まっていない源泉」に形を変えて出る (2026-10-14 に使い捨ての写しで、`excluded` の源泉を消す・改名して commit し、確かめた)。

#### 新しい概念の文書の扱い

- どの 1 枚に掛かるかは、利用者のやりたいことで決める。`references/` の 5 枚の分け方は、[利用者向け Skill と README の書き方](user-docs-writing.md) の「構成」にある
- 「掛からない」(`excluded`) にしてよいのは、利用者に関わる記述 (公開 API の使い方・利用者に見える挙動・分かっている限界・してはいけないこと) を 1 つも持たない文書だけである。内部の仕組みが中心の文書でも、利用者に関わる記述を持つなら、同じ主題の 1 枚に掛ける。初回の制作では、プラットフォーム別の内部の仕組みの文書 8 件を、この理由で外さずに掛けた

#### 直すときに外しやすいこと

`status` の出力のほかに、道具に現れない変更が無いかを、ここで見る (「道具の拾い方の限界と、人が本体の差分を見る場面」)。

直すときに守ることは、[利用者向け Skill と README の書き方](user-docs-writing.md) にまとめてある。特に次の 2 つは、追従で外しやすい。

- 英語版と日本語版を、同じ回に直す。片方だけを直すと、検査が落ちるか、落ちない形でずれる (本文だけの直しは、検査が見ない)
- 源泉の文書に書いてあっても、Skill に書く前に、本体のコードで確かめる

### 3. 公開の宣言の名前の漏れを見る

```bash
python3 scripts/docs/check-api-coverage.py
python3 scripts/docs/check-api-coverage.py --list
```

各プラットフォームのソースから公開の宣言の名前を拾い、そのプラットフォームの Skill の英語版と日本語版のそれぞれに、一度も現れない名前を漏れとして出す。`--list` は、拾った名前の一覧も出す。

| 終了コード | 意味 |
|---|---|
| 0 | 漏れが無い。古い項目 (外す一覧にあるのに、宣言が無くなった名前) だけがあるときも 0 で、出力には出る |
| 1 | 漏れがある |
| 2 | 引数の誤り |
| 3 | 確かめられなかった (公開の宣言を 1 つも拾えない・Skill が無い・記録を読めない)。このとき、道具は「漏れ 0 件」とは出力しない |

| 出たもの | すること |
|---|---|
| 漏れ (利用者が使う名前) | その機能を説明している 1 枚に、名前を足す。英語版と日本語版の両方に足す |
| 漏れ (利用者向けでない名前) | 候補の一覧にして、オーナーに諮る。載せないと決まった名前と理由を、記録の `apiExclusions` に書く。書いた名前は、次から報告されない |
| 古い項目 | 記録の `apiExclusions` から、その項目を消す |

漏れた名前が、利用者が使う名前か、利用者向けでない名前かは、道具は見分けない。そのプラットフォームのワーカーが、宣言を読んで判断する。利用者向けでないと判断した名前は、載せない候補として報告させ、メインがオーナーに諮る。終了コード 3 で終わったときは、漏れが無いとは扱わず、出力の理由 (記録の形・ソースや Skill の置き場) を添えてオーナーに諮る。

載せるか外すかの基準と、今、外している名前は、[利用者向け Skill と README の書き方](user-docs-writing.md) の「公開の宣言の名前」にある。2026-10-10 時点の出力は、漏れ 0 件 (載せないと決めた名前は iOS 2 個・Android 0 個) である。

### 4. 検査を流す

```bash
python3 scripts/ci/check-skills.py .
python3 scripts/ci/check-readme-examples.py .
python3 scripts/ci/run-tests.py
python3 scripts/local-path-lint.py
python3 scripts/identity-lint.py
python3 scripts/comment-policy-lint.py
```

- 上の 2 本は、違反が無ければ終了コード 0 で終わる。違反は「ファイル: 内容」の形で出る
- 違反は、掛かるプラットフォームのワーカーに戻して直させる。同じ違反が、2 回戻しても残るときは、残った違反を添えてオーナーに諮る。追従の範囲の外のファイル (ルートの README・Skill の索引・利用者役の画面など) の違反は、ワーカーに戻さない (「追従の範囲」)
- ワーカーが何も書き換えなかったとき・ワーカーを起動しなかったときも、3 とこの検査を流す。README の例の検査は、源泉 (利用者役の画面など) の変更だけでも結果が変わりうる
- スクリプトのテストは、上の 2 本の検査を今のリポジトリに流すテストを含む。同じテストが、検証 CI の lint の `CI script tests` で流れる ([検証 CI](verification-ci.md))
- 追従の道具そのもの (`scripts/docs/`) を変えたときも、スクリプトのテストを流す。道具のテストは `scripts/ci/tests/` にある

### 5. コード例を変えたときは、コンパイルして確かめる

Skill の `references/` のコード例は、どの検査もビルドしない。コードブロックか、本文の中に書いたコードの断片 (文の中の、1 行に収まるコード) を変えた・足したときは、リポジトリの外の作業用の置き場でコンパイルして確かめる。やり方は、[利用者向け Skill と README の書き方](user-docs-writing.md) の「コード例を確かめる」にある。

`SKILL.md` の最小の動く例は、利用者役の画面のファイルと同じ内容である。利用者役の画面を変えたときは、README の最小コード例と、4 つの `SKILL.md` を同時に直す ([利用者の立場のビルドの確認](consumer-build-check.md))。README の直し漏れは検査が見つけるが、`SKILL.md` の直し漏れは検査が見ない。`status` の「変わった源泉」に利用者役の画面のファイルが出たら、4 つの `SKILL.md` の例を見る。

### 6. オーナーの承認を得る

追従の範囲の中の漏れと違反が無くなったら、直した Skill をオーナーに見せて、承認を得る。範囲の外のファイルの違反は、残ったままでよく、下の見せるものの最後の項目として伝える (残ったまま承認されたときの扱いは「追従の範囲」)。承認を得る前に、commit も、記録の更新もしない。承認が得られなかったときは、指摘をワーカーに戻して 2 からやり直させ、3 から 5 を流し直してから、もう一度見せる。見せるものは次のとおり。

- `status` が出した一覧と、それぞれをどう扱ったか (直した場所・直さなかった理由)
- 人が本体の差分を見た結果 (見た範囲と、道具に現れなかった変更のうち Skill に反映したもの)
- 配った先を再現した確認を行ったか。行ったなら、回数・結果・指摘の扱い。行わなかったなら、表のどの行に当たると判断したか
- 公開の宣言の名前の漏れの結果と、外す候補 (あれば)
- 流した検査と結果
- コードで確かめられなかったこと (書かなかったことと、その理由)
- 追従の範囲の外の直しや、構成の見直しが要るとき、その箇所と、別の作業で行う必要があること (「追従の範囲」)

### 7. 記録を更新する

```bash
python3 scripts/docs/skills-refresh.py record
python3 scripts/docs/skills-refresh.py record <commit>
```

`record` は、記録の `syncedCommit` を、渡した commit (渡さなければ今の先頭の commit) に書き換える。書き換えるのは、記録のファイルの中のこの ID だけである。流す時点は、上の「commit と記録の更新の順」の 2 である。

commit は、ふつうは渡さない (今の先頭の commit が、追従で見た源泉の状態を持っている)。渡すのは、追従で見た源泉の状態を持つ commit が、今の先頭でないときだけである (追従の commit の後に、追従していない源泉の変更が別の commit で積まれたとき)。

| 終了コード | 意味 |
|---|---|
| 0 | 記録を書き換えた |
| 1 | 書き換えなかった。渡した commit が手元の履歴に無い、または、対象のパスに commit していない変更がある。理由は標準エラー出力に出る |
| 2 | 引数の誤り |

**`record` は、源泉の変更が commit された後に流す。** 対象のパスは、記録の `sources` のパスと、`kasane/concepts/` の下の概念の文書である。ここに commit していない変更があると、`record` は書き換えずに失敗で終わる。記録する commit に入っていない変更が、追従済みの扱いになるのを防ぐためである。

| `record` を止める変更 (対象のパスにあるもの) | 補足 |
|---|---|
| 作業ツリーの内容が、今の先頭の commit と違う | — |
| 追跡していない新しいファイルがある | 無視の指定に当たるものは数えない |
| index にだけ残っている変更がある | 変更を index に載せた後で、作業ツリーだけを commit の内容に戻した形。作業ツリーと commit の比較には出ない |

- 記録する commit は、追従のときに見た源泉の状態を持つ commit にする。追従の途中で源泉がさらに変わったときは、`status` を流し直す。新しい差分が出たら、2 へ戻って Skill を直し、承認を得てから記録する
- `record` は commit を作らない。書き換わった記録のファイルは、メインが commit する
- `syncedCommit` を手で書き換えない。手で入れた値は、対象のパスに commit していない変更が無いことを誰も確かめていない

初回の制作では、記録のファイルを作った時点で、利用者役の画面のファイルがまだ commit されておらず、`record` が失敗した。そのため、仮の値を手で入れた。これは、記録を最初に作るときだけの事情で、追従では繰り返さない。仮の値は、実装の commit の後に `record` を流し直して置き換えた (2026-10-10)。書き換わったのは `syncedCommit` の 1 行だけで、その直後の `status` は「変わった源泉は無い」「公開の宣言の増減は無い」だった。

## 初回と同じ確かめ方をする場面

初回の制作では、オーナーの検収 (できあがった Skill と README を、オーナーが見て受け入れる確認) の前に、配った先を再現した確認を行った。Skill の 1 ディレクトリだけをコピーした空の作業用の置き場で、リポジトリを知らない新しいエージェントに、読ませる (分からない言葉・足りない説明を挙げさせる) ことと、使わせる (課題の画面を Skill だけを頼りに書かせ、利用者役と同じ形でビルドする) ことである。リポジトリの中で読むレビューでは、Skill の外の知識で補って読めてしまい、欠けに気付けない。

追従では、変えた量で決める。行うのは、流れの 5 の後、6 の前である。メインが、ワーカーの報告した変えたものを下の表の行に当てて回数を決め、確認は、器 `ksn-scribe` のワーカーに、リポジトリの外の作業用の置き場で行わせる。挙がった指摘は、そのプラットフォームの書き直しのワーカーに戻し、直した後に 3 と 4 を流し直す。作業用の置き場は、確認が終わったら消す。

| 追従で変えたもの | 読ませる確認 | 使わせる確認 |
|---|---|---|
| 文の直し・約束ごと (その機能を使うときに守ること) を書いた箇条の追加・文の中のコードの断片の追加 | しない | しない (断片はコンパイルして確かめる) |
| 1 枚の中に、見出しを足した・コードブロックを足した / 書き直した | 変えた 1 枚を持つ Skill を、変えた言語ごとに 1 回 | その 1 枚に当たる課題を、変えたプラットフォームで 1 回 |
| 1 枚を新しく足した・1 枚を大きく書き直した・`SKILL.md` の構成を変えた | 4 回 (2 つの Skill × 2 言語) | 5 つの課題 × 変えたプラットフォーム |
| 新しい機能 (公開 API の追加) を載せた | 載せた 1 枚を持つ Skill を、言語ごとに 1 回 | その機能を使う課題を 1 つ作り、両プラットフォームで 1 回ずつ |

変えたものが複数の行に当たるときは、回数の多い方の行を採る。「大きく書き直した」の線は、決めていない。どの行か迷ったら、回数の多い方の行を採り、どの行と判断したかを 6 でオーナーに見せる。

### 5 つの課題

使わせる確認の課題は、`references/` の 1 枚に 1 つずつある。両プラットフォームで、同じ課題を使う。

| 課題 | 当たる 1 枚 | 書かせる画面 |
|---|---|---|
| 1 | `basics.md` | 型でテンプレートを切り替える一覧。行のタップを受け、ボタンで先頭へスクロールする |
| 2 | `layout.md` | 向きで列の数が変わるグリッド。グループの見出しを固定し、ルートのヘッダーを持つ |
| 3 | `paging.md` | 続きを読み込む一覧。失敗したときの再試行の表示と、空のときの表示を持ち、Pull to Refresh で取り直す |
| 4 | `reorder.md` | グループをまたいで並べ替えられる一覧。置けない場所の判定と、読み上げの移動操作の文言を持つ |
| 5 | `images.md` | 画像のグリッド。先読みを宣言し、URL が変わる画像に任意キーを使う |

### 読ませる確認

Skill の 1 ディレクトリだけを写した置き場で、新しく起動したワーカーに Skill を通して読ませ、次の 4 つを挙げさせる: 意味の分からない言葉・足りない説明・Skill の外を見ないと分からないこと・冒頭でこれが何かが分かるか。置き場の外を読まない・Web を使わない・このライブラリの事前の知識を使わない、と指示する。

挙がった指摘は、すべて直すか、直さない理由を追従の証跡に残す。直すときは、事実を本体のコードで確かめ、英語版と日本語版を同じ回に直す。初回の制作では、4 回で 211 件が挙がり、182 件を直し、17 件は一部を直し、12 件は直さなかった。

### 使わせる確認の進め方

| 場面 | 進め方 |
|---|---|
| 置き場 | 回ごとに、空の作業用の置き場 (リポジトリの外) を作り、Skill の 1 ディレクトリだけを写す。確認のワーカーには、リポジトリのパスも、ほかの文書も渡さない |
| 使わせる確認の言語 | 英語版で行う。コードブロックは英日で同じなので、ビルドで確かめられる内容は変わらない |
| 課題と一緒に渡す条件 | 利用者役とつなぐための条件を渡す: 画面の名前は `ItemListScreen`・引数を取らない・1 つのファイルに収める・Android は package の宣言を書かない・Android のモジュールは Material に依存していない。これはライブラリの知識ではなく、ビルドの入口とつなぐための条件である |
| ワーカーへの指示 | 置き場の中だけを読んで、課題の画面を 1 つのファイルで書かせる。置き場の外を読まない・Web を使わない・このライブラリの事前の知識を使わない・ビルドしない、と指示する。書いたファイルと一緒に、「推測が要ったところ」を報告させる |
| 作業用の写し | 本リポジトリの今の作業ツリー (追跡しているファイルと、追跡していない新しいファイル) を、リポジトリの外の作業用の置き場に写し、使い捨ての git のリポジトリにする。本リポジトリの作業ツリーは変えない |
| ビルド | メインが行う。書かれたファイルを、作業用の写しの中の、利用者役の画面のファイルと入れ替える (iOS は `verification/ios/Sources/VerificationApp/ItemListScreen.swift`、Android は `verification/android/app/src/main/kotlin/ItemListScreen.kt`)。写しの中で、確認のスクリプトを流す (`python3 scripts/ci/verify-consumer-ios.py --mode local`・`python3 scripts/ci/verify-consumer-android.py --mode local`)。回が終わるたびに、写しの画面のファイルを元に戻す。本リポジトリの利用者役は入れ替えない |
| Android の作業用の写し | SDK の場所を書いた設定ファイル (`local.properties`) は git の管理の外にあり、写しには入らない。初回は、`android/`・`samples/android/`・`verification/android/` の下の 3 つの `local.properties` を、写しの同じ場所に足した。足す前は、画面のファイルをコンパイルする前の、本体の発行で止まった |
| ビルドが落ちたとき | ビルドの出力と書かれたファイルを、そのプラットフォームの書き直しのワーカーに渡して、原因を仕分けさせる。Skill に書かれていない・誤っているのなら、Skill を直してやり直す。Skill に正しく書いてあるのに確認のワーカーが違う書き方をしたのなら、書き損じとして記録し、1 回だけやり直す。ライブラリの側の不足や不具合は、追従では直さず、オーナーに諮る |
| ビルドが通ったとき | ワーカーが報告した「推測が要ったところ」を、読ませる確認の指摘と同じに扱う (直すか、直さない理由を追従の証跡に残す。Skill が正しく書いていて、課題の文面の側の言い方が原因のものは直さない)。初回の制作では、10 回のすべてがビルドに通った上で、8 件の分かりにくいところが挙がった |
| 確かめられる範囲 | 書かれた画面がビルドできることまでである。起動して動きを見てはいない |

回数・課題・結果・仕分けは、追従の証跡 (「追従の証跡」) に要約して残す。初回の記録は、`kasane/changes/archive/2026-10-10-user-docs/evidence/dist-read-dispositions.md` と `kasane/changes/archive/2026-10-10-user-docs/evidence/dist-use.md` にある。

## 道具の拾い方の限界と、人が本体の差分を見る場面

ここに書く確かめは、流れの 2 の中で、そのプラットフォームの書き直しのワーカーが行う。確かめるだけの使い方では、メインが下のコマンドの 1 行目で commit の一覧だけを出し、一覧があれば、人が本体の差分を見る必要があると報告に添える。道具は、文法を解かずに、宣言の行を 1 行ずつ拾う。拾い方の細部は、`scripts/docs/public_api.py` の冒頭に書いてある。次の変更は、道具に現れない。

| 道具に現れない変更 | 人がすること |
|---|---|
| 複数行にわたる宣言の、続きの行だけを変えた (引数の追加・削除・型や既定値の変更)。`KsCollectionView` の初期化と modifier、Android の `KsPaging` などのコンストラクタが当たる | 記録の commit からの、本体の公開の型のファイルの差分を、目で見る (下のコマンド) |
| 宣言は変えずに、挙動だけを変えた (既定の色・呼ばれる時点・不正入力の扱いなど) | 源泉の概念の文書が同時に直されていれば、「変わった源泉」に出る。蒸留を通さずに直した変更 (hotfix) は出ないので、記録の commit からの commit の一覧を読む |
| 公開の宣言のコメントだけを変えた | コメントが利用者への約束を変えていないかを、差分で見る |
| 初期化の宣言 (名前を持たない) の追加 | 行としては増減に出るが、名前の漏れには出ない。Skill に載っている呼び方を、差分と見比べる |
| 短い一般の言葉と同じ名前 (`end`・`all`・`key`・`body` など) の漏れ | 名前は、Skill の文面のどこかに同じ字面で現れれば、載っていると数える。英語の本文の同じ言葉でも現れたことになるので、こういう名前を足した・変えたときは、Skill のコードの中に現れることを目で確かめる |
| 利用者役・README・Skill の索引の変更 | README と `SKILL.md` の例は検査が見る。索引 (`skills/README.md`・`skills/README_ja.md`) は、Skill を足した・名前を変えたときに、手で直す。README と索引の直しは、追従の範囲の外である (「追従の範囲」) |

本体の差分を見るコマンド (`<記録の commit>` は、`status` の出力の 1 行目にある):

```bash
git log --oneline <記録の commit>..HEAD -- ios/Sources android/kscollectionview/src/main
git diff <記録の commit> -- ios/Sources android/kscollectionview/src/main
```

次のときは、`status` の出力にかかわらず、本体の差分を見る。

- 公開の型のファイルを変えた変更が、記録の commit の後にある
- 蒸留を通さずに本体を直した変更がある
- 依存しているライブラリ (画像ローダー・Compose) の版を上げた。Skill が、依存しているライブラリの動きに頼って書いている箇所がある

## 追従の範囲

追従の中で直すのは、利用者向け Skill の既存の 1 枚と、記録の `sources`・`apiExclusions` だけである。次の 2 つは、追従の中で行わず、ワーカーにも行わせない。

| 範囲の外のもの | 見つけたときにすること |
|---|---|
| 範囲の外のファイルの直し (ルートの README・Skill の索引・利用者役の画面など) | ワーカーが直しが要ると報告したとき、または範囲の外のファイルに検査の違反が出たときは、ワーカーに戻さない。その箇所と、別の作業で直す必要があることを、オーナーに伝える |
| 利用者向け Skill の構成の見直し (1 枚の追加・名前の変更・分け方の変更) | 今の 1 枚のどれにも入らない内容があるとワーカーが報告したときは、構成の見直しが要ることと、それを変更の実装で行う必要があることを、オーナーに伝える |

どちらかが残ったまま承認されたときは、範囲の中の直しは commit してよいが、記録の `syncedCommit` は更新しない。残った源泉の変更を、次の追従でも `status` が見つけられるようにするためである。その理由を、オーナーに伝える。

## 追従で直さないもの

- インストール例の版。例には `{version}` を置いていて、リリースのたびに書き換えない ([cross/ADR-0018](../../decisions/cross/0018-install-examples-without-concrete-version.md))
- 最新の版の確かめ先の URL。変えるのは、リリースの工程が別の場所に決めたときだけで、例のある 6 か所 (README の 2 枚と 4 つの `SKILL.md`) と、許可する URL の一覧 (`scripts/ci/user-docs-rules.json`) を同時に直す
- ライブラリの公開 API と挙動。追従の途中で不足や不具合を見つけたら、直さずにオーナーに諮る
