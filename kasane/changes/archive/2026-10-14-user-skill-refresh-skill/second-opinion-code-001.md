## 指摘事項

### [🟠 Major] 掛からない源泉の改名・削除で、対応表の修正を飛ばす

**該当箇所**: `.agents/skills/docs-refresh/SKILL.md:81`

**問題点**: 「Skill に掛からない源泉だけが変わった」場合はワーカーを起動せず、承認と記録更新へ進みます。しかし、`excluded` の源泉にも改名・削除は起こり、その場合は `sources` のパス変更・項目削除が必要です。この分岐では、対応表を直せるワーカーへ処理が渡りません。

例えば、`excluded` の文書を削除して commit すると、`record` は `syncedCommit` だけを更新します。古い `sources` の項目は残るため、次の `status` でも「無くなった源泉」が出続けます。改名の場合も旧パスが残り、追従済みの状態になりません。草稿の「2. 出たものを読んで、Skill を直す」が要求する対応表の修正とも食い違います。

**推奨修正**: ワーカーを省略できる条件から、対応表の修正が必要な改名・削除を除いてください。見直すページが無い場合でも、記録の修正を担当する ksn-scribe ワーカーへ渡せる手順を設けてください。

### [🟠 Major] 記録の対応表だけを直した場合に、最初の commit を省略する

**該当箇所**: `.agents/skills/docs-refresh/SKILL.md:141`、`drafts/user-skill-refresh.md:113`

**問題点**: 最初の commit を省略する条件が「直す1枚が無かったとき」になっています。ページの変更が無くても、新しい概念文書への `excluded` の追加、源泉の改名、古い `apiExclusions` の削除などで、`sources`・`apiExclusions` だけが変更される場合があります。

その場合、この手順は対応表の変更を commit せずに `record` を流し、次の commit に対応表の変更と `syncedCommit` の更新をまとめます。「追従で変えたファイルを先に commit し、その後に記録の ID を更新して別 commit にする」という Requirement を満たしません。範囲外の課題が残る場合には、対応表の変更を保存する最初の commit も省略され得ます。

**推奨修正**: 省略条件を「ページにも `sources`・`apiExclusions` にも、追従による変更が無い場合」にしてください。記録の対応表だけを変更した場合も、ID 更新前の commit を作ることを Skill と草稿の両方に明記してください。

### [🟡 Minor] 範囲外の違反を報告する経路と、承認へ進む条件が矛盾している

**該当箇所**: `.agents/skills/docs-refresh/SKILL.md:112`、`drafts/user-skill-refresh.md:225`

**問題点**: 直前の手順では、README など範囲外の違反はワーカーへ戻さず、手順6でオーナーへ伝えるとしています。一方、この行は「漏れと違反が無くなるまで、オーナーには見せない」と無条件に定めています。

README の例の検査だけが失敗している場合、追従の中では直せず、違反も消えないため、手順6へ進めません。仕様が認める「範囲外の課題を伝え、残ったまま承認されたら範囲内だけ commit する」経路が曖昧になります。

**推奨修正**: 承認へ進む条件を、追従の範囲内の漏れ・違反についての条件と明記してください。範囲外の違反は残件として手順6へ渡し、承認後も `syncedCommit` を更新しない経路につなげてください。

## アクションプラン

1. 掛からない源泉の改名・削除でも、対応表の修正をワーカーへ渡す。
2. 最初の commit の省略条件を、ページと対応表の両方に変更が無い場合へ修正する。
3. 範囲外の違反を残したまま、報告・承認へ進める条件を明記する。
4. 上記の分岐を、使い捨ての写しで確認する。特に「対応表だけ変更」「excluded の改名・削除」「README の違反を残して範囲内だけ承認」を含める。
