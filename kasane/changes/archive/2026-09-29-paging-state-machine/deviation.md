# Deviation: paging-state-machine

- ui/brief.md「ページングの表示」の項目があるとき (次のページの読み込み中 / 失敗 / 終端): brief では「一覧の全幅で置く」→ 指示により、一覧の左右の余白 (contentPadding) の内側に置き、利用者のルートのフッターと同じ幅にそろえる (両プラットフォーム。「全幅」はグリッドの全列にまたがる意味とする)。理由: 実装で iOS が端から端まで・Android が余白の内側と分かれたため、利用者のフッターとそろう側に統一する (2026-09-27)
- design Decision 9 (Sample の VM): design では iOS の VM を `@Observable @MainActor final class` → 実装では `ObservableObject` の `@MainActor final class`。理由: Sample の配布先の下限が iOS 16 で `@Observable` (iOS 17 以上) を使えないため。既存の Sample の画面の状態と同じ扱い。オーナーへ報告済み (2026-09-27)
- samples の Requirement「取り直しの実演」: spec では「項目があるときに取り直しが失敗したら、VM は状態を取り直しの前に戻す」→ 指示により、取り直しの前の状態が追加読み込み中 (または取り直し中) だった場合は待機に戻す (両プラットフォーム)。理由: 取り直しを始めた時点で先に始めた読み込みの結果を捨てるため、追加読み込み中に戻すと読み込みが終わらず先へ進めなくなる (2026-09-27)
- samples の Requirement「取り直しの実演」と ui/brief.md (承認 mock ④): brief / mock では「更新できませんでした」を操作のパネルの説明の一行に太字で出す → 指示により、操作のパネル (デバッグ用の操作) から出し、画面の上 (バーのすぐ下) の帯として出して 3 秒で消す (両プラットフォーム)。理由: パネルは Sample のデバッグ操作であり、利用者のアプリの見本としての知らせとは切り分ける。Pull to Refresh の直後に見ている位置で失敗に気づけ、一覧の上を隠し続けない (2026-09-27)
- ライブラリの「次のページの失敗」の表示の置き場 (ADR-0024 の 6 つの表示): オーナーの確認により、既定オフのまま残す (spec どおり。変更なし) (2026-09-27)
- collection-core の Requirement「取り直しの結果は先頭から表示する」(core/ADR-0021): spec では「差し替えの直前の状態が取り直し中なら、差し替えと同時に先頭を表示する」だけ → 指示により、Pull to Refresh で始めた取り直し (ライブラリが取り直しの処理を呼んでから、インジケータを出し終えるまで) の間に届いた差し替えは、直前の状態によらず先頭を表示する規則を足す (両プラットフォーム)。VM が自分で始める取り直しは従来どおり直前の状態で決め、取得がすぐ終わって「取り直し中」と差し替えが 1 回の描画にまとまると先頭へ送られない条件を、公開 doc と phase-7 のガイドに書く (「取り直し中が一覧に届いてから差し替える」か「先頭へのスクロール命令を一緒に出す」)。Sample の VM の「取り直し中が一覧に届いたと画面が知らせてから取得する」手順は、この条件を満たす見本として残す。理由: 独立レビュー (review-001.md) で、取得が速いと 2 つの書き換えが 1 回の描画にまとまり規則が効かないと分かった。Pull to Refresh はライブラリが取り直しの間を知っているため確実にでき、VM 起点はライブラリから見分けられない。ADR-0021 の本文と負の帰結への反映は蒸留時に行う (2026-09-27)
- collection-core の Requirement「取り直しの結果は先頭から表示する」(上の項目で足した Pull to Refresh の規則の端): Pull to Refresh で始めた取り直しのインジケータを出している間に利用者が下へスクロールし、取り直しが失敗して配列を変えずに状態を戻したとき、iOS はインジケータを出し終えるときに先頭へ戻り、Android はスクロールした位置に残る → 指示により、両プラットフォームの差として受け入れる。理由: iOS は配列を中身で比べるため「失敗して配列がそのまま」と「前と同じ中身の成功」を見分けられず、後者で先頭を表示する手当てが前者にも効く。Android は配列の参照で比べるため差し替えが無かったと分かる。そろえるには公開 API に合図を足す必要があり、起きるのは取り直しの最中にスクロールして失敗したときだけで項目や操作は壊れない (review-002.md の Minor、2026-09-27)
- collection-paging の Requirement「ページングの表示」(次のページの読み込み中) と design Decision 2・ui/brief.md (承認 mock ②): spec / design / brief では、項目があるときの次のページの読み込み中の表示を「いちばん下の項目のすぐ下」(ルートのフッターの枠の中) に置く → 指示により、次のページの読み込み中の表示だけは、一覧の見えている範囲の下端 (下の余白 contentPadding の下と下端の安全領域の上) に止めて重ね、項目はその裏を流れるようにする。状態が追加読み込み中の間だけ出す (両プラットフォーム)。「次のページの失敗」と「終端」の表示は従来どおりフッターの枠の中に置く。0 件のときの表示 (最初の読み込み中など) は変えない。理由: 基準機の体感ゲートで、速いフリックで末尾に追いつくと読み込み中の表示が項目と一緒に流れてくることが分かり、オーナーが「くるくるが一緒に流れる UI なんて見たことない。ありえないので直す」と判断した (2026-09-28)
- 上の項目 (次のページの読み込み中の表示を見えている範囲の下端に重ねる) の縦の位置: 直した当初は「下端の安全領域 + contentPadding の下 + 8」だけ上に置いていた → 指示により、「下端の安全領域 + 8」だけで決め、contentPadding を見ない (両プラットフォーム)。理由: Sample がパネルのために入れた下の余白でくるくるがパネルの上まで押し上げられ、オーナーが「本体以外の影響で位置がずれるのは重大な欠点」と判断した。contentPadding は中身と一緒にスクロールする中身の周りの余白で、中身の外に重ねる表示の置き場を決めるものではない。一覧の上に重なるバーを避ける仕組みは安全領域が担う (2026-09-28)
- ui/brief.md (Sample の画面・承認 mock) と samples の Requirement「操作を畳める」: brief では「一覧の下の余白 (contentPadding の下) に、パネル (畳んだときは丸いボタン) の高さと余白の分を入れ、畳む / 広げるで余白も変える」→ 指示により、一覧の下の余白にパネル・丸いボタンの分は入れない (全画面の一覧として本来入れる下端の安全領域の分だけにする)。かわりにパネルと丸いボタンを画面の下端から上げて浮かせ、広げたままでもパネルの下に一覧の底 (次のページの読み込み中の表示・失敗と「再試行」・終端の表示) が見えるようにする (両プラットフォーム同じ値)。理由: パネルは本体の本来の動きと表示を見るためのデバッグ操作で、背景が透けるフローティングにしているのはそのため。デバッグ操作の都合で本体の余白を変えるのは本末転倒 (オーナー) (2026-09-28)
- [付随修正] iOS のルートのフッター / ヘッダーの枠が、上下の余白 (contentPadding の上 / 下) の変化で測り直されない: 末尾 (または先頭) を表示したまま余白を変えると、中身から高さを決める枠が前の高さのまま残り、空白が残る (大きくしたときは伸びない)。ページングを付けた一覧では本変更でフッターの枠を中身から高さを決める形にしたことで入り、利用者のフッター / ヘッダーがある一覧では本変更より前からあった。直し方は同じ (余白が変わったとき、見えている枠の中身を作り直して名指しで測り直させる) ため、本変更で両方を直す。Android には無い見込み (2026-09-28)
- 上の項目 (パネルを上げて浮かせる) の上げる量: sample-parity では寸法を両プラットフォームで一致させる → 指示により、iOS 100pt・Android 128dp の差を受け入れる。理由: どちらも「末尾の失敗の表示 (「読み込めませんでした」と「再試行」) が丸ごとパネルの下に入る高さ」という同じ決め方で、Android はボタンの押せる範囲 (48dp) の分だけ失敗の表示の背が高い (iOS 約 88pt、Android 約 113dp)。あわせて、背の低い画面では 0 件のときの真ん中の表示にパネルが少しかかることがある (Pixel 4a で計算上数 dp) ことを受け入れる。パネルは畳めるデバッグ操作のため (2026-09-28)
- design Decision 1 (公開 API の形) と tasks 1.1 / 1.2: design では次のページの読み込み中の表示の差し替え口を iOS `.pagingAppendingFooter { }`・Android `KsPaging(appendingFooter = { })` → 実装では iOS `.pagingAppendingIndicator { }`・Android `KsPaging(appendingIndicator = { })`。理由: 上の項目で表示をフッターの枠から外し、見えている範囲の下端に重ねる形にしたため、名前を置き場に合わせた。配布前のため互換は付けない。改名はオーナーへ報告済み (2026-09-28)
- 上の項目 (次のページの読み込み中の表示を下端に重ねる) の出入り: 表示は 0.2 秒のフェードで出入りする (両プラットフォーム)。失敗・終端に変わった直後は、消えていく読み込み中の表示とフッターの枠の失敗・終端の表示が一瞬重なって見える。承認した照合の画像は止まった状態のため、動きは tasks 7.2 の基準機の目視で確かめる (2026-09-28)
- 上の項目 (次のページの読み込み中の表示を下端に重ねる) の既定の見た目: 直した当初は標準の読み込み中を直径 40 の円の下地 (iOS .regularMaterial と影、Android surfaceContainerHigh と影) に載せていた → 指示により、下地を外して標準の読み込み中だけを同じ位置に出す (両プラットフォーム)。理由: オーナーが基準機の体感ゲートで「読み込みインジケータに背景がついてるのが気になる (背景はなくてよい)」と判断した (2026-09-29)
