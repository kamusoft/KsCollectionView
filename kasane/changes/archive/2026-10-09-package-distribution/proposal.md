# Proposal: package-distribution

## Why

リポジトリは公開したが、利用者がライブラリを入れる手段がまだ無い。SwiftPM は git のリポジトリのルートにあるマニフェストしか解決できず、マニフェストが `ios/` の下にある今の形では配れない。Android は Maven の公開の設定を持たない。

Sample は両プラットフォームとも本体のソースを直接参照している。Sample のビルドが通っても、配布物として正しいこと (写しにファイルが揃っている・発行物の依存の宣言が足りている・配信用リポジトリのルートでマニフェストが解決できる) は言えない。配布物だけが壊れても、今はどの検査も気付かない。

フェーズの議論で、SwiftPM を配信用の別リポジトリから配ること (cross/ADR-0015)、配布物の中身、対応する Xcode の宣言、配布物を専用の利用者役で確かめること (cross/ADR-0016) を決めた。本変更は、その決定を実物にする。

## What Changes

- **iOS のマニフェスト**: `ios/Package.swift` の宣言を、確かめている版に合わせて Swift 6.4 のツールに上げる
- **SwiftPM の写しを作る道具**: `ios/` の本体から、配信用リポジトリのルートに置く写しを作るスクリプトを足す
  - 写しに入れるのは、マニフェスト・本体のソース・テストのソース・`LICENSE`・配信用の README (このリポジトリへ案内する固定文) の 5 点。マニフェストは書き換えない
  - 道具は git を操作しない。行き先の中身を消す前に、行き先が意図した場所であることを確かめる
- **Android の公開の設定**: 本体のモジュールに、Maven の発行の設定を足す
  - 出すのは release の 1 種類で、sources jar を付け、javadoc jar は空で置く。POM に名前・説明・ライセンス・開発者・リポジトリの場所を入れる
  - 署名は鍵を外から受け取り、鍵が無ければ署名を飛ばす。版が `-SNAPSHOT` のときは、Maven Central 向けのタスクを失敗させる
- **利用者役**: `verification/` に、iOS と Android の最小のプロジェクトを置く
  - 利用者が書くのと同じ書き方 (package の名前 `KsCollectionView-SPM`、Maven の座標 1 行) で、公開の前の成果物を参照してビルドする。iOS は写しのディレクトリ、Android は手元の Maven リポジトリに発行したものを使う
  - iOS は Simulator 向けと実機向けの両方をビルドする。Android はコード縮小 (R8) を有効にして、リリース用に組み立てる。どちらも起動はしない
  - 公開済みの配布物を取りに行く形にも切り替えられる。切り替えた形での取得の実行は、公開物がまだ無いので本変更では確かめない
- **検証 CI**: 利用者役をビルドする再利用 workflow を 2 本足し、入口から `main` 宛ての Pull Request のときだけ呼ぶ。検査の名前は `consumer-ios / verify`・`consumer-android / verify`
- **`main` の保護**: 上の 2 つを必須の検査に足す (3 つから 5 つになる)。`develop` から `main` 宛ての Pull Request で 2 つの検査が報告されるのを見てから登録する
- **手元での起動の確認**: コード縮小を有効にした Android の利用者役を、手元で 1 回起動して一覧が表示されることを確かめる
- **GitHub への操作** (`main` 宛ての Pull Request の作成とマージ・保護の変更) は外向きの操作なので、オーナーの承認を得てから行い、実行したコマンドと設定の読み直しを証跡に残す

提案の段階で、作業用の写しを使って次を確かめた (2026-10-09。値と環境は design に書く)。

- 兄弟ライブラリと同じ公開のプラグインが、今のビルドの構成 (AGP 9.4.0・Gradle 9.7.0) で発行物を作れる
- 宣言を Swift 6.4 に上げた写しを参照する利用者役が、Simulator 向けと実機向けの両方でビルドできる

影響する能力: package-distribution (新規。配布物の形と、それを作る道具) / consumer-verification (新規。配布物を利用者の立場でビルドして確かめる) / verification-ci (検査が 2 つ増え、lint が流すテストが増える) / repository-publication (`main` の必須の検査が増える)

- 蒸留時に反映: decisions — cross/ADR-0015・0016 を実装の形で確かめて accepted に昇格する
- 蒸留時に反映: handbook — cross に、配布物の形の文書を新設する (写しの作り方・手元での発行のしかた・利用者役の流し方・失敗したときの見方)
- 蒸留時に反映: handbook — `kasane/handbook/cross/verification-ci.md` に、利用者の立場の確認 (走る時点・構成・検査の名前・緑が保証する範囲・既知の制限) を足す
- 蒸留時に反映: handbook — `kasane/handbook/cross/branch-and-github-settings.md` の必須の検査を 5 つに直し、足したときの手順と読み直した値を足す
- 蒸留時に反映: handbook — `kasane/handbook/cross/public-identifiers.md` に、SwiftPM の Package URL と、利用者がマニフェストに書く package の名前を足す
- 蒸留時に反映: handbook — 「マニフェストの宣言を、確かめている Xcode の版に合わせる」ことを規約にするかを判断する (フェーズの議論の決定事項)

## Non-Goals

- **実際に公開する workflow・鍵の受け渡し・Maven Central への送信・tag** — 別の能力で、phase-7-4-release-pipeline が扱う
- **配信用リポジトリ `KsCollectionView-SPM` の作成と設定 (Issue と Pull Request を閉じる)、写しを送る工程** — 書き込み用の鍵と公開の工程と一緒に作るので、phase-7-4-release-pipeline で扱う。本変更の確認は手元の写しを参照するので、本物の配信用リポジトリは要らない
- **リリースの workflow が作った成果物そのものを利用者役に渡す形と、公開の後の確認の実行** — リリースの工程の設計に属するので、phase-7-4-release-pipeline で扱う
- **README のインストール例と、利用者役のソースを README の例と一致させる検査** — 別の能力で、phase-7-3-user-docs が扱う
- **コード縮小を有効にした利用者役の起動を、リリースの節目ごとに確かめる決まり** — リリースの基準の判断を要するので、phase-7-4-release-pipeline で扱える。本変更が行うのは 1 回の確認だけ
- **Xcode 26 でビルドできることの確認** — フェーズの議論でオーナーが行わないと決めた
- **利用者役を CI の上で起動すること** — cross/ADR-0013 で、検証 CI では Simulator・エミュレータを使わないと決めている
- **API の文書の生成 (Dokka)** — フェーズの議論で javadoc jar を空にすると決めた

## Impact

- 破壊的変更: 公開 API とライブラリの挙動は変えない。マニフェストの宣言を上げるので、Xcode 26 以前のツールでは依存を解決できなくなる (まだ配布していないので、影響を受ける利用者はいない)
- `main` 宛ての Pull Request の必須の検査が 3 つから 5 つに増え、macOS のランナーを使うジョブが 1 本増える
- Android のビルドに、公開のプラグインが加わる
- リスク: 本ライブラリをコード縮小に通すのは初めてなので、利用者役の組み立てで不整合が見つかる可能性がある。規則の同梱が要ると分かったら、フェーズの議論の既定 (同梱しない) を改めることになるので、実装を止めてオーナーに諮る
- リスク: 利用者役のビルドは外部の依存の取得 (Nuke・Maven の依存) に頼る。ランナー `xcode-27` は public preview で、稼働の保証が無い
- 公開済みの配布物を取りに行く形は、取得の実行までは確かめられない。最初のリリースで確かめる必要がある
