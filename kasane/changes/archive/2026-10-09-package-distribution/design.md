# Design: package-distribution

## Context

フェーズの議論で決まったことは、次のとおりである (`kasane/roadmaps/v1-foundation/phases/phase-7-2-package-distribution/agenda.md` の決定事項)。

- SwiftPM の配布物は、配信用の公開リポジトリ `KsCollectionView-SPM` に本体の写しを置いて配る (cross/ADR-0015、proposed)
- 配布物の中身は、兄弟ライブラリ KsSettingsView と同じ形にする
- `ios/Package.swift` の宣言を Swift 6.4 のツールに上げる
- 配布物は、専用の利用者役を `main` 宛ての Pull Request のときだけビルドして確かめ、必須の検査にする。確かめるのはビルドまでで、Android はコード縮小を有効にする (cross/ADR-0016、proposed)

今のコードは次の状態である。

| 対象 | 状態 |
|---|---|
| `ios/Package.swift` | Swift 6.2 のツールを要求する。product は 1 本で、Nuke に依存する。ソースの場所は既定のまま |
| `android/` | 公開の設定が無い。版は `-Pversion` を優先し、無ければカタログの `0.1.0-SNAPSHOT` を使う |
| 検証 CI | 入口 `ci.yml` が lint を持ち、`verify-ios.yml`・`verify-android.yml` を呼ぶ。検査のロジックは `scripts/ci/` の Python のスクリプトで、テストは `scripts/ci/tests/` にあり、lint が毎回流す |
| `main` の保護 | 必須の検査は `lint`・`ios / verify`・`android / verify` |

兄弟ライブラリの実物 (写しを作る道具 `../KsSettingsView/scripts/spm-snapshot/`、公開の設定 `../KsSettingsView/android/kssettingsview/build.gradle.kts`、利用者役 `../KsSettingsView/verification/`、workflow `../KsSettingsView/.github/workflows/verify-consumer-*.yml`) を参考にする。兄弟は Bash で書いているが、本リポジトリの形 (Python のスクリプトとテスト) に合わせて作り直す。

### 提案の段階で試して確かめたこと (2026-10-09)

リポジトリの外の作業用の写しで試した。リポジトリのファイルは変えていない。

| 試したこと | 環境 | 結果 |
|---|---|---|
| `com.vanniktech.maven.publish` 0.37.0 を本体のモジュールに足し、release の 1 種類・sources jar・空の javadoc jar の設定で、手元のディレクトリへ発行する | AGP 9.4.0・Gradle 9.7.0・Kotlin 2.4.10 (AGP の組み込み) | 鍵なしで成功。`.aar`・`-sources.jar`・`-javadoc.jar`・`.pom`・`.module` の 5 点ができた |
| 発行された POM の依存 | 同上 | `api` の依存は compile、`implementation` の依存は runtime の範囲。Compose BOM は依存の管理の節に import で入る。AAR に R8 の規則のファイルは入らない |
| `ios/` のマニフェスト (宣言を Swift 6.4 に書き換えたもの)・`Sources/`・`Tests/`・`LICENSE` を `KsCollectionView-SPM` という名前のディレクトリに置き、パスで参照する SwiftPM のパッケージから、product `KsCollectionView` を package `KsCollectionView-SPM` の名前で指してビルドする | Xcode 27.0 (Swift 6.4) | `generic/platform=iOS Simulator` と `generic/platform=iOS` (署名を無効にする指定つき) の両方で、リリースの構成のビルドが成功。実機向けは、Simulator 向けの後で 13 秒 |
| 写しの大きさ | — | 展開した状態で約 1.7 MB |

確かめていないこと: 宣言を Swift 6.4 に上げた状態での iOS のテストの全件通過 (実装の最初に流す)。コード縮小を有効にした Android の利用者役の組み立てと起動 (実装で確かめる)。

## Goals / Non-Goals

Goals:

- 配布物を作る設定と道具が揃い、手元で配布物を作って中身を確かめられる
- 配布物だけが壊れたことに、`main` 宛ての Pull Request の検査で気付ける
- 同じ利用者役と同じ再利用 workflow を、後のリリースの workflow がそのまま呼べる

Non-Goals は proposal.md のとおり。

## Decisions

### Decision 1: 写しを作る道具は、行き先を写しの 5 点に置き換え、git を操作しない

**採用案:** `scripts/distribution/sync-spm-snapshot.py` を置く。行き先のディレクトリを受け取り、`.git` を除く中身を消してから、次の 5 点を置く。

| 写しの中の場所 | 元 |
|---|---|
| `Package.swift` | `ios/Package.swift` (内容を変えない) |
| `Sources/` | `ios/Sources/` のうち、git が追跡しているファイル |
| `Tests/` | `ios/Tests/` のうち、git が追跡しているファイル |
| `LICENSE` | ルートの `LICENSE` |
| `README.md` | `scripts/distribution/spm-readme.template.md` (このリポジトリへ案内する英語の固定文) |

消す前に、次を確かめる。1 つでも外れたら、何も消さずに失敗で終わる。

- 元の 5 点がすべてある
- 行き先が、このリポジトリの中でも、このリポジトリを含むディレクトリでもない
- 行き先が、まだ無いパスか、空のディレクトリか、配信用リポジトリの作業コピー (git の最上位で、`origin` が `kamusoft/KsCollectionView-SPM` を指す) である。無いパスは、作ってから写す

道具は commit も push も tag もしない。テストは `scripts/ci/tests/` に置き、lint の中のスクリプトのテストで毎回流す。

**理由:** 行き先の中身を消す道具なので、意図しない場所を消さないことを道具の側で保証する。追跡しているファイルだけを写せば、手元のビルドの出力が配布物に混ざらない。git の操作を分けておけば、書き込み用の鍵を持つ工程 (後のリリースの workflow) と、鍵の要らない確認の両方から同じ道具を使える。

**代替案:**
- **A: 兄弟の Bash のスクリプトをそのまま持ってくる** — 却下。本リポジトリの検査のスクリプトとテストは Python の標準のライブラリに揃えてあり、同じ入口でテストを流せる形にしたい。兄弟は、行き先が空のときにも git の初期化と `origin` の設定を先に行う必要があり、確認の側に準備が要る。
- **B: 道具が commit・push・tag まで行う** — 却下。確認には git の操作が要らない。書き込み用の鍵を持つ工程を、鍵の要らない道具から分けておく。
- **C: 行き先を消さずに上書きだけする** — 却下。本体から消したファイルが、配信用リポジトリに残り続ける。

### Decision 2: Android の公開の設定は、兄弟と同じプラグインで release の 1 種類を出す

**採用案:** 本体のモジュールに `com.vanniktech.maven.publish` を足す。版はバージョンカタログに置く。

- 出すのは release の 1 種類。sources jar を付け、javadoc jar は空で置く
- POM に、名前・説明・開始年・URL・MIT License・開発者 (名義は `kamusoft`)・リポジトリの場所を入れる
- 署名は、鍵をプロパティ (`signingInMemoryKey` など) で受け取る。鍵のプロパティが無いときは、署名を必須にしない
- 版が `-SNAPSHOT` で終わるときは、名前に `MavenCentral` を含むタスクを実行の最初で失敗させる (取り下げ用のタスクだけは除く)

`group` と `version` の決め方 (ルートの `build.gradle.kts`) は変えない。今 `api` で宣言している依存 (Compose の BOM・runtime・ui・foundation-layout と、Coil の Compose 連携) は、そのまま compile の範囲で届ける。Coil の Compose 連携は、公開 API に型が現れないが、利用者が直接使ってキャッシュを共有する前提で届けている (core/ADR-0012)。

**理由:** 提案の段階の試作で、今のビルドの構成のまま発行物を作れることを確かめた。署名・空の javadoc jar・Maven Central への送信の入口を 1 つのプラグインが持ち、兄弟と設定の形が揃う。タスクの名前で歯止めを掛けるのは、プラグインが送信のタスクを増やしたときに素通りしないためである (兄弟の実装の理由と同じ)。

**代替案:**
- **A: Gradle 標準の `maven-publish` と `signing` だけで組む** — 却下。空の javadoc jar の用意・署名の配線・Maven Central への送信を自前で組むことになり、兄弟と手順が分かれる。
- **B: Dokka で API の文書を作って javadoc jar に入れる** — 却下。IDE は sources jar からコメントを表示できるので、差は Web で読む文書の有無だけである (フェーズの議論の記録)。

### Decision 3: 利用者役は、参照の行だけを差し替えて、公開の前と公開済みを切り替える

**採用案:** 利用者役のソースは 1 つだけ持ち、配布物をどこから取るかだけを切り替える。切り替えの名前は `local` (公開の前の成果物) と `published` (公開済みの配布物) にする。

| プラットフォーム | 利用者が書くのと同じ部分 | `local` | `published` |
|---|---|---|---|
| iOS | target の依存が、package `KsCollectionView-SPM` の product `KsCollectionView` を指す | `KsCollectionView-SPM` という名前の写しのディレクトリを、パスで参照する | 配信用リポジトリの URL を、版の完全一致で参照する |
| Android | 依存が `jp.kamusoft:kscollectionview:<版>` の 1 行 | `jp.kamusoft` の取得元を、作業用の Maven リポジトリ (ディレクトリ) だけにする | `jp.kamusoft` の取得元を、Maven Central だけにする |

- iOS は `verification/ios/Package.swift.template` に依存の行を差し込んでマニフェストを作る。差し込みは、利用者役を写した作業用のディレクトリで行い、リポジトリの作業ツリーを変えない
- Android は `verification/android/` を独立した Gradle のビルドにし、取得元と版をプロパティで受け取る。`jp.kamusoft` の取得元は 1 つに固定し、ほかの取得元へ黙って切り替わらないようにする。本体のビルドを取り込まない (ソースへの置き換えを持たない)。バージョンカタログは本体のものを共有する
- Android の `local` の成果物は、作業用のディレクトリに発行する。利用者の既定の手元の Maven リポジトリ (`~/.m2`) には書かない

ビルドと成功の条件は、切り替えに関わらず同じにする。切り替えで変わるのは成果物の準備だけで、`published` では写しの作成も手元への発行も行わない。

`published` での取得の実行は、公開物がまだ無いので本変更では確かめない。確かめるのは、切り替えたときの参照の書き方と、準備を飛ばして同じビルドを始めることまでとする (コマンドを差し替えたテストで確かめる)。

**理由:** 利用者役のソースが 1 つなら、公開の前に確かめたものと、公開の後に確かめるものが食い違わない。取得元を 1 つに固定すれば、確かめたつもりの配布物と違うものをビルドする経路が無くなる。

**代替案:**
- **A: 公開の前と公開済みで、別々の利用者役を持つ** — 却下。ソースが 2 つになり、食い違う。
- **B: 公開の前の形だけを作り、公開済みの形は後のリリースの変更で足す** — 却下。フェーズの議論で、同じ利用者役を両方の形で使えるようにすると決めた。切り替えは差し込む行と取得元の違いだけで済む。
- **C: Android の公開の前の成果物を、既定の手元の Maven リポジトリに置く** — 却下。手元の環境に発行物が残り、前の回の発行物を誤って参照し得る。

### Decision 4: iOS の利用者役は SwiftPM のパッケージにして、Simulator 向けと実機向けをビルドする

**採用案:** 利用者役は、ライブラリの target を 1 つ持つ SwiftPM のパッケージにする。ソースは、一覧を 1 つ表示する最小の利用例とする。リリースの構成で、`generic/platform=iOS Simulator` と `generic/platform=iOS` (署名を無効にする指定つき) の 2 つの行き先をビルドする。どちらかが失敗すれば、確認は失敗で終わる。Simulator は選ばず、起動もしない。

**理由:** 実機向けのビルドは、今どの検査も確かめていない (`kasane/handbook/cross/verification-ci.md` の「緑では言えないこと」)。試作で、署名なしで通り、時間もほとんど増えないことを確かめた。起動しないので、アプリの体裁は要らない。

**代替案:**
- **A: Simulator 向けだけをビルドする (兄弟と同じ)** — 却下。実機向けのビルドを確かめる検査が、無いままになる。
- **B: Xcode のアプリのプロジェクトにする** — 却下。起動しないのでアプリの体裁は要らず、プロジェクトのファイルの維持が増える。

### Decision 5: Android の利用者役はアプリにして、コード縮小を有効にしたリリースを組み立てる

**採用案:** `verification/android/` に、アプリのモジュール `:app` を 1 つ持つ Gradle のビルドを置く。画面は、一覧を 1 つ表示する最小の利用例とする。

- リリースの組み立てで、コード縮小 (R8) を有効にする。規則は Android の既定の最適化の規則だけを使い、利用者役の側に、本ライブラリのための規則を書かない
- リリースの組み立てに、デバッグ用の鍵で署名を付ける (手元で端末に入れて起動できるようにするため)
- 確認では `:app` のリリースを組み立て、実行時の依存の一覧に `jp.kamusoft:kscollectionview` が、指定した版で現れることを確かめる

**理由:** 利用者のアプリはリリースでコード縮小を有効にするのがふつうで、本ライブラリはコード縮小を通したことが無い。利用者役の側に規則を書くと、配布物に規則が足りないことが隠れる。

**代替案:**
- **A: コード縮小を無効のまま組み立てる (兄弟と同じ)** — 却下。コード縮小の途中で見つかる不整合に、CI で気付けない (フェーズの議論の記録)。
- **B: 利用者役の側に規則を足して通す** — 却下。配布物に規則が足りないことが隠れる。

### Decision 6: 確認のロジックはプラットフォームごとに 1 つのスクリプトにし、workflow はそれを呼ぶだけにする

**採用案:** `scripts/ci/verify-consumer-ios.py` と `scripts/ci/verify-consumer-android.py` を置く。どちらも、切り替え (`local`・`published`) と版を引数で受け取り、成果物の準備からビルドまでを行う。

- 引数が範囲の外 (知らない切り替え・`published` で版が無い) なら、何も始めずに失敗で終わる
- 準備とビルドの子プロセスの出力は、加工せずにそのまま流す。子プロセスが失敗したら、その時点で失敗で終わる
- git が追跡しているファイルを変えない。iOS は、一時のディレクトリに利用者役を写して作業する。Android のビルドの出力は、利用者役の下の、追跡の対象外の場所に置く
- 手元でも、workflow と同じコマンドで流せる

テストは `scripts/ci/tests/` に置く。引数の検査・差し込んだ参照の書き方・失敗の伝わり方を、ビルドを実際には走らせない形で確かめる。

**理由:** 検査のロジックを workflow に直に書かず、テストの付いたスクリプトにする決まりに従う (`kasane/handbook/cross/verification-ci.md` の「検査を足すときの注意」)。兄弟は、準備の出力の最後の行だけを取っていたため、失敗の理由が CI の記録に残らなかった。出力をそのまま流す形にして、先に防ぐ。

**代替案:**
- **A: 準備とビルドを workflow の step に直に書く** — 却下。手元で同じ確認を流せず、テストも付けられない。
- **B: 準備とビルドを別々のスクリプトにする (兄弟と同じ)** — 却下。本変更の範囲では、準備だけを単独で呼ぶ場面が無い。後のリリースの変更で必要になったら、そのときに分ける。

### Decision 7: 再利用 workflow を 2 本足し、入口から `main` 宛ての Pull Request のときだけ呼ぶ

**採用案:** `verify-consumer-ios.yml` と `verify-consumer-android.yml` を足す。

- どちらも、ほかの workflow から呼ばれる形だけを持つ。入力は切り替え (必須) と版 (任意)。ジョブの名前は `verify`
- ランナー・Xcode・JDK・action の指定のしかた、権限 (内容の読み取りだけ)、時間の上限は、既存の検証の workflow と同じ決まりに従う。iOS は、決めた版の Xcode が無ければ、ビルドを始める前に失敗で終わる
- 入口 `ci.yml` に `consumer-ios`・`consumer-android` のジョブを足し、Pull Request で起動したときだけ、切り替えを `local` にして呼ぶ。検査の名前は `consumer-ios / verify`・`consumer-android / verify` になる
- 時間の上限は、暫定で 15 分を置き、ランナーでの所要時間を見て決め直す

**理由:** 入口を 1 本に保ち、検査の名前を固定する (cross/ADR-0014)。ジョブの条件で絞れば、`develop` への push ではランナーを起こさない。後のリリースの workflow が、同じ workflow を切り替えを変えて呼べる。

**代替案:**
- **A: 入口のジョブを常に走らせ、ジョブの中で起動の種類を見て何もせずに終わる** — 却下。`develop` への push のたびに、macOS のランナーを起こす。
- **B: Pull Request だけで起動する入口の workflow を、もう 1 本持つ** — 却下。入口を 1 本にする決定 (cross/ADR-0014) から外れ、同時実行と権限の定義が二重になる。

### Decision 8: `main` の保護には、検査の名前が報告されるのを見てから登録する

**採用案:** 次の順で行う。GitHub への操作は、それぞれオーナーの承認を得てから行う。

1. 実装を `develop` に push し、検証 CI が 3 つの検査だけを走らせる (利用者の立場の確認は走らない) ことを確かめる
2. `develop` から `main` 宛ての Pull Request を作り、5 つの検査が報告されることと、名前が決めたとおりであることを確かめる
3. `main` の保護の必須の検査を 5 つに更新し、読み直して確かめる。ほかの保護の値は変えない
4. 5 つの検査が成功した状態で、Pull Request を merge commit でマージする

実行したコマンドと、読み直した値は、変更の証跡に残す。

**理由:** 検査の名前が食い違ったまま保護に登録すると、登録した名前の検査が報告されず、Pull Request をマージできなくなる。報告された名前を見てから登録する決まりに従う (`kasane/handbook/cross/branch-and-github-settings.md` の「設定を入れる順」)。

**代替案:**
- **A: 先に保護へ登録してから Pull Request を作る** — 却下。名前が食い違っていたとき、Pull Request が止まる。
- **B: Pull Request を作らず、保護の登録を次のリリースの節目に送る** — 却下。検査が走るところを見ないまま変更が終わる (提案の方向の確認で、オーナーが本変更の中で行うと決めた)。

## Risks / Trade-offs

- **コード縮小で不整合が見つかる**: 本ライブラリをコード縮小に通すのは初めてである。配布物に規則の同梱が要ると分かったら、フェーズの議論の既定 (同梱しない) を改めることになるので、実装を止めてオーナーに諮る。本ライブラリと関係の無い依存 (Compose・Coil・OkHttp) に由来する不整合で、利用者役の側の規則が要ると分かったときも、同じく止めて諮る
- **利用者役が確かめられる範囲は、利用者役が触る API に限られる**: 最小の利用例が触らない型の、依存の宣言の漏れは見つからない。公開 API に現れる型の依存の宣言の過不足は、実装で 1 回洗って確かめる (tasks)
- **`published` の形は取得まで確かめられない**: 公開物が無い。参照の書き方までをテストで確かめ、取得の実行は最初のリリースで確かめることを申し送る
- **外部の依存の取得に頼る**: Nuke と Maven の依存を取得できないと、利用者の立場の確認は落ちる。必須の検査が、コードの誤りではない理由で止まり得る。管理者は保護を迂回できる
- **異常系を公開リポジトリで確かめない**: 壊れた commit を push したり、確かめるための Pull Request を作ったりしない。スクリプトのテストと、一時のツリーで確かめる (`kasane/handbook/cross/verification-ci.md` の「確かめ方の限界」と同じ扱い)
- **`main` 宛ての Pull Request で、`develop` の内容がすべて `main` に入る**: 本変更のほかに、前の変更で決め直した時間の上限と、開発の記録が入る

## Migration Plan

1. iOS のマニフェストの宣言を上げ、iOS のテストを流す
2. 写しを作る道具と Android の公開の設定を入れ、手元で配布物を作って中身を確かめる
3. 利用者役と確認のスクリプトを入れ、手元で確認を流す。コード縮小を有効にした Android の利用者役を、手元で 1 回起動する
4. workflow を入れ、手元の完了判定 (テスト 4 系統の全件・スクリプトのテスト・workflow の定義の検査) を通す
5. Decision 8 の順で、公開リポジトリでの確認と保護の更新を行う

戻し方: 保護の必須の検査を 3 つに戻せば、`main` 宛ての Pull Request は前の条件でマージできる。入口の 2 つのジョブを外せば、利用者の立場の確認は走らなくなる。マニフェストの宣言と Android の公開の設定は、配布を始めるまでは利用者に届かないので、戻しても影響が無い。
