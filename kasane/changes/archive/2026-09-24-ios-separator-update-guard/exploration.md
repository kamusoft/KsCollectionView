# Exploration: ios-separator-update-guard

## 課題 / 動機

iOS エンジンで、レイアウト確定のたび (`viewDidLayoutSubviews`) に走る可視セルの再構成 (`KsCollectionViewController.updateVisibleCellSeparators()` → `configure(cell:at:)`) が、スクロール中の毎フレーム・全可視セルに対して**変化の有無に関わらず**タッチ時の背景色を代入している (`KsHostingCell.configureTouchFeedback(color:)` に変化ガードが無い。区切り線側の `configureSeparators` はガードを持つ)。代入のたびにアクセシビリティ差し替え済みの `setBackgroundColor` → 色の比較 → 動的色の trait 解決が走り、CA レイヤも dirty になる。さらにグリッド (区切り線を出さない構成) では `indexPathsForVisibleItems` の走査とセルごとの `cellForItem(at:)` 自体が毎レイアウト空回りしている。

`image-loading` (L 級) の tasks 7.1 (iOS 画像グリッドの hitch 計測) の不合格の切り分け (trace 解析、2026-09-08) で本務と無関係に発見した既存経路の無駄。オーナー判断で別 change として積んだ (image-loading への同梱は「画像ロードと無関係の既存経路」のため見送り)。

観測値 (iPhone 11 / iOS 18.7.8 / Release、3 秒〜6 秒のフリック窓): 背景色代入系のスタックが窓あたり 7〜15 サンプル (1 ms 刻み、主スレッド稼働率で 1〜2 pt)。グリッドでの走査の空回りが追加 4〜14 サンプル/窓。**hitch (1 フレーム落ち) を消す保証は無い**規模で、主スレッド費用の削減に留まる見込み。詳細は `kasane/changes/image-loading/deviation.md` の「iOS 7.1 の不合格の切り分け」の項 (archive 後は `kasane/changes/archive/*-image-loading/`)。

該当箇所: `ios/Sources/KsCollectionView/KsCollectionViewController.swift` (`viewDidLayoutSubviews` / `configure(cell:at:)` / `updateVisibleCellSeparators`)、`ios/Sources/KsCollectionView/KsHostingCell.swift` (`configureTouchFeedback(color:)` / `configureSeparators`)。

### 現状の把握 (探索で確認、2026-09-24)

可視セルを揃える処理 (`updateVisibleCellSeparators`) の呼び出しは 3 か所あり、役目が違う:

| 契機 | 役目 |
|---|---|
| ① レイアウト確定 (`viewDidLayoutSubviews`)。スクロール中は毎フレーム | 差分適用後の位置依存の表示 (先頭行の上端の線) を揃える |
| ② 構成の差し替え (`update(configuration:)` で区切り線の表示・色・表示形態が変わったとき) | 変更を可視セルへ届ける |
| ③ 差分の適用完了 (`apply` の完了ハンドラ) | 位置が変わったセルを揃える。**配列が変わる更新で、作り直されずに残った可視セルへ新しいタッチ色を届けるのもここ** (同値配列の更新では `reconfigureVisibleCells` が届ける) |

## 検討した選択肢 (却下案と理由を含む)

### 論点 1: タッチ色の変化ガードの比べ方

- **採用 A**: セルが最後に書いた色を控え、同じオブジェクト (`===`) なら書かない。既定のタッチ色 (`.systemFill`) は定数 (`static let`) に固定して毎回同じオブジェクトにする。区切り線の色の比較も同じ形に揃える
  - 取りこぼしが無い (別オブジェクトなら必ず書く。UIColor は不変)、比較が最安、2 つのガードが同じ形になる
  - 利用者指定の色 (`UIColor(color)`) は構成更新のたびに新しいオブジェクトになるが、スクロール中は同じオブジェクトのままなのでガードは効く
- 却下 B: タッチ色だけ A の形、区切り線は今の値比較 (`!=`) のまま — リストで区切り線を出す構成では毎フレーム・全セルの動的色の値比較が残る
- 却下 C: タッチ色も値比較 (`!=`) — 動的色の比較そのものの費用が毎フレーム残り、比較が外れれば書き込みも起きる

補足: `.systemFill` が呼ぶたびに同じオブジェクトを返す保証は無い。固定しないと `===` のガードが素通りになる (壊れはしないが効かない)。

### 論点 2: 区切り線を出さない構成での毎レイアウトの走査の省き方

- **採用 A**: ① (レイアウト確定) の呼び出しだけを「リスト、かつ区切り線を表示」のときに限る。②③ はそのまま
  - 無駄の本体 (毎フレームの ①) だけを止め、②③ が担う反映経路に触れない
- 却下 B (起票時の見立て): 関数そのもの (`updateVisibleCellSeparators`) を早期リターン — グリッドで配列の変更とタッチ色の差し替えが同時に届くと、③ が止まって残った可視セルが古い色のままになる。現状は ① が毎フレーム全セルを上書きしているため、この穴が表に出ていないだけ
- 却下 C: A に加えてリストでも先頭の項目が可視のときだけ ① を走らせる — 先頭への挿入で元の先頭が 2 番目に下がる場面など、上端の線の取り残しの再点検が要る。論点 1 のガードでリストの 1 セルあたりの費用は十分小さくなるため、踏み込む差が無い

グリッドで位置依存の表示が崩れる心配 (起票時の疑問): グリッドは区切り線を出さず、ヘッダ・フッタは補助ビューとして別経路 (`updateVisibleSupplementaryViews`) で揃えるため、① を省いても崩れる表示は無い。

### 論点 3: 効果の確かめ方

- **採用 A**: ユニットテストだけで確かめる (実機計測なし)。hitch の改善は主張せず「主スレッドの無駄な仕事を減らした」と書く
- 却下 B: A に加えて実機で 1 回プロファイル (Time Profiler) を取り、スタックが 0 件になるのを確かめる — A のテストと同じことを確かめるだけで、結果で決まることがほぼ無い
- 却下 C: hitch の A/B を 3 試行 — 起票時の見積もりで差が測定誤差に埋もれる規模。`image-loading` の 7.1 は完了済みで、hitch の主因も別に切り分け済みのため、結果で決まることが無い

## 決定事項

1. **タッチ色・区切り線の色のガード**: セルが最後に書いた色を控え、同じオブジェクト (`===`) なら書かない。既定のタッチ色を定数に固定する。区切り線の色の比較も同じ形に揃える (論点 1 = A)
2. **毎レイアウトの揃え直しの限定**: レイアウト確定 (`viewDidLayoutSubviews`) からの揃え直しは「リスト、かつ区切り線を表示」のときだけ行う。構成の差し替え時と差分の適用完了時の揃え直しは変えない (論点 2 = A)
3. **確かめ方**: ユニットテストだけ。実機計測はしない (論点 3 = A)。押さえる点:
   1. 同じ構成で揃え直しても、タッチ色・区切り線の色を書き直さない (既定色を含む)
   2. グリッドおよび区切り線なしのリストでは、レイアウト確定で可視セルを揃え直さない
   3. グリッドで配列の変更とタッチ色の差し替えが同時に届いても、残った可視セルに新しい色が届く (論点 2 の穴の回帰防止)
   4. タッチ色・区切り線の色の差し替えが可視セルに届く (既存テストが通る)
4. 証跡には hitch の改善を主張せず、主スレッド費用の削減として書く

いずれも ADR の選別基準 (覆すコスト高 / 境界を越える / 将来を制約) に当たらない内部の小変更のため ADR は起票しない。
