- **Major (余白で端に届かない)**: 解消。`indicatorReachesBothEndsWithContentPadding` は上 50 / 下 60 の余白で、末尾で下端、先頭で上端に 1px 以内で届くことを画素で確かめている。KDoc の「先頭では上端、末尾では下端に届く」も、行の高さが揃った画面では実装どおりになった

### 位置の補正 (`ksAlignedScrollOffset`) の正しさ

公式の実装を foundation 1.11.4 の aar から逆アセンブルして読んだ。値は次のとおり求められている。

- `scrollOffset` = 可視行の平均 × `visibleItemsInfo.first().row` + `firstVisibleItemScrollOffset`
- `contentSize` = 平均 × ceil(総件数 / maxSpan) − 行間 + 前後の余白

KDoc の説明はこれと一致する。`visibleItemsInfo` は、見えている範囲の番号の項目 (と sticky の項目) を番号順に並べたもので、固定 (pinned) の項目は含まれない (`updatedVisibleItems` で絞られる)。KsCollectionView は sticky を使っていない。したがって「先頭の要素 = 画面に見えている最初の行」「同じ行の項目は同じ y」という前提が成り立つ。

探針は、作業ツリーの複製の上で素の `LazyVerticalGrid` を 7px ずつ末尾まで送り、補正後の割合と公式の割合を毎回記録する形で行った。リポジトリは変更していない。

| 条件 | 逆戻りの回数 (補正後 / 公式) | 末尾の割合 (補正後 / 公式) |
|---|---|---|
| リスト・高さ一定・余白なし | 0 / 0 | 1.000 / 1.000 |
| リスト・高さ一定・余白 50 / 60 | 0 / 53 | 1.000 / 1.000 |
| リスト・高さばらつき・余白なし・header / footer | 16 / 16 | 1.0007 / 1.0007 |
| リスト・高さばらつき・余白 250 / 10・header / footer | 16 / 67 | 1.0006 / 0.962 |
| 3 列・高さ一定・余白 45 / 25・行間 8・header / footer | 0 / 16 | 1.069 / 1.003 |
| 3 列・高さばらつき・余白なし・行間 8・header / footer | 13 / 13 | 1.058 / 1.058 |
| 3 列・高さばらつき・余白 45 / 25・行間 8・header / footer | 13 / 25 | 1.057 / 1.057 |

- **高さが揃った画面**: 余白があっても逆戻りは 0 で、末尾でちょうど 1 に届く
- **高さがばらつく画面**: 補正後の逆戻りは、余白なしの公式の値と同じ回数・同じ種類である。原因は、先頭の行が入れ替わるたびに「平均 − その行の実際の高さ」だけずれる誤差で、補正が新しく持ち込んだものではない。決定事項 (公式の値を使い、揺れはオーナーが目視で判定する) の範囲内。補正は、余白の境目で起きていた 1 行分の逆戻りだけを消している
- **範囲外**: 割合は `coerceIn(0f, 1f)` で丸められ、トラックの外には出ない
- **0 除算**: `contentSize <= viewportSize` で先に抜けるため起きない
- **可視項目が空**: `firstOrNull` で公式の値に戻る。空配列にしても例外は出ない。基準の項目が可視項目に無い場合と、基準の行が先頭以下の場合も、公式の値に戻る
- **データの差し替え直後**: 末尾までスクロールした状態で 60 件を 10 件に縮め、さらに空にした。いずれも破綻は無かった (縮めた直後は末尾の割合 1.0、空ではスクロールできない扱いになり描かない)。`firstVisibleItemIndex` と `layoutInfo` は同じ計測の結果として同時に反映されるため、描画時に食い違わない
- **高さのアニメーション中**: 補正は各フレームの実際の `offset` の差を使い、行の高さを覚えないため、古い値が残らない。平均が毎フレーム変わることによる揺れは公式の値の性質で、決定事項の目視判定の範囲内
- **グリッドと header / footer**: 全幅の header は行 0 として `row` に反映され、番号順の並びも崩れない。行の中の項目は同じ `offset.y` を持つ

### 描画フェーズの費用

- 表示中 (濃さ > 0) の描き直し 1 回あたりに行うのは次の 3 つ。いずれも可視項目の数 (数十) に比例する小さな走査で、加えて `Rect` の割り当てが 1 回ある
  - `scrollIndicatorState` の getter 3 つ。平均の計算が 2 回走る
  - `firstVisibleItemIndex` の読み取り
  - `visibleItemsInfo` の `firstOrNull` 2 回
- 非表示の間は `layoutInfo` を読む前に抜けるため、スクロールしても描き直しの依存が生じない
- `LazyGridMeasuredItem` は項目を `placeWithLayer` / `placeRelativeWithLayer` で置く (逆アセンブルで確認)。そのため、グリッドの節点を描き直しても項目の中身は記録し直されず、フェードの 250ms の間の描き直しも安い。毎フレームの描画として過大ではない

## 指摘事項

### 🟡 Minor 補正の行の扱いがグリッド (複数列)・header のある構成でテストされていない

**該当箇所**: `android/kscollectionview/src/main/kotlin/jp/kamusoft/kscollectionview/KsScrollIndicator.kt:163-172`、`android/kscollectionview/src/test/kotlin/jp/kamusoft/kscollectionview/KsScrollIndicatorTest.kt:252-310`

**問題点**: 補正は「番号」ではなく「行 (`row`)」を比べ、行の先頭どうしの `offset.y` の差を足す。この区別が意味を持つのは、1 行に複数の項目が並ぶグリッドと、全幅の header が行 0 を占める構成である。しかし、余白を扱う 2 件の結合テストは、どちらも 1 列・header なしのリストで書かれている。たとえば行ではなく番号で比べる形に崩れても、リストのテストは通り続ける。探針では 3 列・header / footer つきで正しく動くことを確かめたが、回帰を捕まえるテストは無い。

**推奨修正**: 次のどちらかを足す (優先度は低い)。
- `ksAlignedScrollOffset` は純関数で、`LazyGridItemInfo` はインターフェースなので、偽の項目で直接テストする。3 列で、余白の領域に前の行の 3 項目、基準が次の行の先頭という配置で、`officialOffset + 行の間の距離` を返すことを確かめる
- 既存の余白のテストの 1 件を `KsLayout.Grid(columns = KsColumns.Fixed(3))` + header で書いた版を足す

### 🔵 Suggestion グリッド + header / footer では、末尾の約 1 行手前でバーが下端に着く (公式の全長の数え方に由来)

**該当箇所**: `android/kscollectionview/src/main/kotlin/jp/kamusoft/kscollectionview/KsScrollIndicator.kt:26-33` (「末尾では下端に届く」)、exploration.md の未決の論点「公式の推定が全幅の header / footer を 1 行として数えるか」

**問題点**: 公式の `contentSize` は行数を ceil(総件数 / 列数) で数えるため、全幅の header / footer を 1/列数 行として数える。探針では推測どおりで、3 列 + header / footer では全長が約 1 行短く出た。その結果、末尾に着く前に割合が 1 を超え (1.058〜1.069)、最後の約 1 行はバーが下端に留まる。これは公式の値の誤差で、余白なしでも同じだけ起きる。

ただし、余白ありの 3 列 + header / footer (高さ一定) では、補正前は 2 つの誤差 (位置が 1 行少ない・全長が 1 行短い) が打ち消し合って 1.003 に収まっていた。補正で位置が正しくなったため、全長の誤差だけが表に出る (1.069)。補正そのものは正しく、退行ではない。バーはトラックの外にも出ない。

完了条件の目視の対象 (「大量件数」「テンプレート切り替え」) には、グリッド + header / footer の画面が無い。Sample の header / footer のデモはリストで、リストでは全幅の項目も 1 行と数えるためずれない。そのため、この誤差はオーナーの目に触れないまま残る。

**推奨修正**: コードの修正は不要 (決定事項 a の範囲で、独自推定 c の判断材料)。基準機確認でオーナーへ deviation を報告するときに、この未決の論点の答え (全幅の項目は 1/列数 行と数えられ、グリッド + header / footer では末尾の約 1 行手前で下端に着く) を添える。気になるかどうかの判定をオーナーに委ねること。
