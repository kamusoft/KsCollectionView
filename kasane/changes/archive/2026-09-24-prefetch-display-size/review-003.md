## 指摘事項

### 🟠 Major 取得を始めたアイテムが外れた・可視範囲へ移った後は、残りのアイテムの署名がすべて変わっても古い URL の取得が続く

**該当箇所**: `ios/Sources/KsCollectionView/KsImagePrefetcher.swift:210-215`、`android/kscollectionview/src/main/kotlin/jp/kamusoft/kscollectionview/KsImagePrefetchWindow.kt:279-284`(Android は `:113` と `:228-234` の `releaseStale` 経路も関わる)

**問題点**: 共有中の単位を始め直す条件は `state.request.url == abandonedURL`、つまり「進行中の取得が、このアイテム自身が今手放した URL を使っている」ことである。進行中の取得の URL は、その単位を最初に始めたアイテムの URL である。そのため、始めたアイテムがその URL を手放した後に参照数が 0 にならなければ、他のどのアイテムの URL が変わっても条件は成り立たない。次の 2 つの場合をプローブで再現した (スクラッチに複製した上で台帳を直接呼ぶ単体テスト。本体は触っていない)。

1. 両プラットフォーム: 同じ `key` を 3 件 (A: `sig=a`, B: `sig=b`, C: `sig=c`) が共有し、A の URL で始まった。A が対象から外れる (参照数 2)。その後、署名の更新で B・C の URL がそれぞれ `b2`・`c2` に変わる → 取り消しも開始も無く、進行中の取得は `sig=a` のまま。どのアイテムも宣言していない URL である。iOS: `started=["sig=a"] cancelled=[]`、Android: `started=[s?a, …] disposed=[] active=[s?a, …]`
2. Android のみ: 同じ 3 件で、A の行が可視範囲へ移る。窓の外・可視範囲の中にいるので台帳には残る。その後、A・B・C の 3 件すべての署名が変わる → A は `releaseStale` で古い宣言を手放すだけで、新しい宣言は確保しない。B・C の `acquire` では進行中の URL (`sig=a`) が自分の手放した URL と違うので、始め直さない。結果は `started=[s?a] disposed=[] active=[s?a]` で、配列のすべての要素の URL が変わったのに古い URL の取得が続く。iOS は可視のアイテムも `retain` で宣言を合わせ直すので、A 自身の変更で始め直され、この形では起きない

Requirement「画像の任意キー」は「`key` が同じでも URL が変わった要素は、進行中の取得を取り消して新しい URL で出し直す (失効した URL の取得が失敗したままにならないため) (SHALL)」と定めている。どちらの場合も、URL が変わった要素の単位の取得は取り消されず、出し直されない。Scenario「署名だけが変わった配列の差し替えでは新しい URL で出し直す」(旧 URL の取得は取り消され、新しい URL で取得が開始される) にも反する。

どちらも起きやすい形である。署名の更新は配列全体に一斉に来るのが普通で、そのとき最初に始めた行が窓の外や可視範囲にいることは、スクロール中なら珍しくない。失効した `sig=a` の取得は失敗し、共有するアイテムが残る間は出し直されないので、その `key` の先読みは効かないままになる。表示は `KsImage` 自身の要求 (`key` で新しい URL) で出るので壊れはしない。ただし、これは相方 code-001 が Major として挙げ採用された症状 (共有中のキーで署名を差し替えても取得が更新されない) と同じもので、それがサイクル 2 の条件の絞り込みで一部の形に戻っている。突き合わせで採った方針「同じアイテムが自分の URL を変えたときだけ始め直す」から見ても、B・C は自分の URL を変えているので、始め直す対象である。

**推奨修正**:
- 始め直す条件を「このアイテムがこの単位の URL を変えた (`abandonedURL != nil`) うえで、進行中の取得の URL を、いまこの単位を持つどのアイテムも宣言していない」に変える。単位の状態に「持ち主が宣言している URL → 件数」を持ち、`acquire` / `release` で増減すれば判定できる
  - review-002 の場合 (別のアイテムが違う署名で加わる): `abandonedURL == nil` なので始め直さない
  - code-001 の場合 (片方・両方が変わる): 最初に変わったアイテムの時点で進行中の URL の持ち主が 0 になるので 1 回だけ始め直し、2 件目では新しい URL に持ち主がいるので始め直さない
  - 上の場合 1・2: 最初に URL を変えたアイテムで始め直す
- 上の 2 つの場合を両プラットフォームの台帳テストに足す (場合 2 は Android の可視範囲の経路。iOS は場合 1)。既存の `anotherItemJoiningWithADifferentSignedUrlDoesNotRestartTheSharedRequest` / `test別のアイテムが同じキーを違う署名で共有しても進行中の取得を始め直さない` の途中の確認 (後から加わったアイテムの署名が変わっても触らない) は、始めたアイテムがまだ `a` を宣言しているので、新しい条件でも成り立つ

### 観察 (指摘ではない)

- iOS の `@State private var retainedMatch = KsImageRetainedMatch()` は、`KsImage` の値が作られるたびに初期値の参照型を 1 つ確保して捨てる (SwiftUI の `@State` は最初の 1 回しか使わないため)。確保は小さく、描画経路の性能に効く大きさではないので、指摘にはしない。完了時の計測 (tasks 8.x) でセルの組み立て費用が問題になったときの見直し候補として残す
