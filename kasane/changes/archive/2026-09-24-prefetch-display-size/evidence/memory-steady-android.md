# 到達点 memory (幅なし / 列幅) のメモリ定常化と索引 (Android) — 2026-09-23

> **採ったビルドと、その後の修正について (後からの注記)**
>
> - この証跡の数値は、Android の表示経路の 2 つの修正より**前のビルド**で採った。1 つは、まだ引き当てていない `KsImage` が画面に出る時点でもう一度引き当てを試す修正 (修正サイクル 5)、もう 1 つは、先読みが未完了のときだけ表示要求の開始を遅らせる修正 (修正サイクル 6) である。本文は採った時点の値のまま残す
> - **修正で変わりうる値**: 索引の鍵の件数 (10,000 件の往復の 18,769、600 件の往復の 615〜638 など) は、表示要求が鍵を登録する時点と回数に依るため、修正後は変わりうる。これらは修正前のビルドの値として読む
> - **結論が修正に依らない理由**: 結論の (1) (列幅で元寸が載らない)・(3) (索引が鍵以外を持たない、離脱後 `left:0`)・(4) (充足) を決めているのは、先読みの項目の寸法、索引の持ち物の型、要求を出すたびに鍵を登録する経路で、2 つの修正はどれも変えていない (修正が触ったのは表示要求を出すかどうかと、その開始の時点。review-008 の確認による)。そのため結論が覆る見込みは低いが、修正後のビルドでは測り直していない
> - 同じ時期に採った「止めてから揃うまで」の証跡 (`disk-wait-android.md`) は、最終ビルドで採り直す予定がある (同ファイルの冒頭の注記)

tasks 8.3 (Android 分)。到達点 `memory` の幅なし / 列幅で、Android 性能検証の手順 (kasane/handbook/android/performance-verification.md の「メモリの手順」「保持対象の解放の確認」) により、(1) 列幅では元寸を載せない分の減少、(2) 索引込みで定常化すること、(3) 画面離脱後に索引がコレクションやセルを保持しないこと、(4) 索引の充足 (キャッシュにある項目が索引に残っている率) を確かめる。iOS 分は別の証跡。

## 結論

| 観点 | 結果 |
|---|---|
| (1) 列幅では元寸を載せない | **spec どおり。** 列幅の走行ではメモリキャッシュに元寸 (400×400) の項目が 1 件も無く、先読みの項目はすべて 330×330 (列幅)。キャッシュの上限に届かない件数 (60 件) では、キャッシュの大きさが 50.6 MB → 38.0 MB (−12.6 MB、−25%)、PSS が約 133.2 MB → 約 124.2 MB (−9 MB、−7%)。上限に届く件数 (600 件) では大きさは上限 (約 53 MB) で頭打ちになり、差は保持できる件数 (元寸 74 件 → 列幅 105 件、+42%) に出る |
| (2) 索引込みで定常化 | 手順どおりの 10,000 件の往復: 列幅 steady:3、幅なし 1 回目は **未判定 (10 往復で notSteady)**・2 回目 steady:7。索引は 1 往復目で上限 (20,000 件) またはその近くに達し、以後は上限で頭打ち (増え続けない)。読み込みを待つ往復 (600 件・60 件) はすべて steady |
| (3) 離脱後に索引が保持しない | **保持していない。** 離脱まで進んだすべての走行で離脱後の同時生存 `left:0`。索引が持つものを実行時に全件たどり、メモリの鍵 (文字列と文字列どうしの付随情報) 以外を 1 件も持たないこと (`foreign=0`) を確かめた。索引は離脱後も鍵を残す (プロセスで共有する設計) が、鍵はコレクション・セル・画像への参照を持たない |
| (4) 索引の充足 | **すべての計測点で 1.000。** メモリキャッシュにある Sample の画像の項目は、索引が上限に達した 10,000 件の往復でも 100% 索引に残っていた |

## 環境と手順

| 項目 | 値 |
|---|---|
| 機種 / OS | Pixel 4a (基準機) / Android 13 (API 33) |
| 構成 | benchmark ビルド種別 |
| 土俵 | 「画像グリッド」と同じ宣言元 (`ImageGridFixture`: 3 列・正方形セル・リモート画像 400×400)。画像の枠は 330〜331 px、列幅 330 px。メモリキャッシュの上限 53.7 MB (ローダーの既定) |
| キャッシュ状態 | 走行ごとにアプリのデータを消去してから起動し、起動時の指定でも画像キャッシュを空にする。cold |
| 起動 | 計測用の入口の経路を Intent の追加情報で直接開いた (`adb shell am start`)。手順 1 の計測モジュール (Macrobenchmark) は使っていないため `MemoryUsageMetric` は無い。定常判定に使う往復ごとの PSS は手順どおりアプリ自身の記録 |
| 往復 | 手順 2〜5 のとおり (16 項目刻み、到達を条件に進む、全項目の通過を確認、往復ごとに GC 後の PSS 合計、連続 2 往復の増分 2% 以内で定常、上限 10 往復) |
| 解放の確認 | 手順 6 と「保持対象の解放の確認」のとおり、定常の後に識別子の重ならない同件数の配列へ置換し、結果画面へ離脱して同時生存を読む。画像グリッドの自動往復には本 change の計測で置換と離脱の段階を足した |
| 覗き窓 | 往復ごとと離脱後に、メモリキャッシュの項目 (件数・大きさ・寸法の内訳・鍵の形) と本体の索引 (鍵の件数・充足・鍵以外の持ち物) を記録した。索引は本体の内部の型のため、計測用ソースセットから実行時に名前で読んだ (本体の公開面は増やしていない) |
| 生ログ | スクラッチにのみ保管 |

### 読み込み待ちの往復を足した理由

手順どおりの往復 (10,000 件、到達したらすぐ次へ) は取得より速く進むため、画像がほとんどメモリに載らない (往復の終わりのメモリキャッシュは 6〜23 件)。この往復では「元寸を載せない分」も「キャッシュが満ちた状態での索引の充足」も見えない。そこで同じ画面に、1 段階ごとに進行中の読み込みが無くなるまで (上限 10 秒) 待ってから進む往復 (`measurement/image-memory-loaded/<件数>/10/<到達点>`) を足し、キャッシュの上限を超える 600 件と、上限に収まる 60 件で測った。件数を変えた計測のため、10,000 件の結果とは比べない。

## 保持の確認の詳細

- 同時生存: 離脱まで進んだすべての走行 (10,000 件の幅なし 1 回目以外) で走査中の最大 36・最大可視 15・置換後 15・離脱後 0 (`steady:<n> peak:36 visible:15 replaced:15 left:0`)。上限 (可視 × 4 = 60) の内側
- 索引の持ち物: 離脱後の覗き窓で、索引の 2 つの表 (鍵の順序つき集合と、識別子 → 鍵の一覧) の全要素を実行時にたどり、鍵以外 (文字列以外の識別子・文字列以外の付随情報・鍵以外の値) が 0 件であることを確かめた (`foreign=0`)。鍵は URL (または任意キーの識別子) の文字列と、寸法・当てはめ方の文字列だけでできている
- 離脱後も索引には鍵が残る (600 件の往復で 615〜638 件、10,000 件の往復で 18,769 件)。索引はプロセスで共有し、消えるのはキャッシュの消去と件数の上限だけという設計どおり。鍵は文字列だけなので、残ってもコレクションやセルを生かさない
- 索引そのものが占めるメモリは分けて測っていない。上限 20,000 件に達した 10,000 件の往復でも PSS は増え続けていない (1 回目は未判定だが単調増加ではない)

## 限界

- 10,000 件の手順どおりの往復では画像がほとんど載らないため、元寸と列幅の差・キャッシュが満ちた状態の索引の充足は、件数を変えた読み込み待ちの往復で見た。これらは手順どおりの fixture ではなく、過去の結果とは比べない
- 600 件の往復の PSS は揺れが大きく、定常判定は成立しているが比較の材料にしていない
- 取得元は公開の画像サービスで、回線状態は記録していない。読み込み待ちの往復は、1 段階あたり 10 秒を超える取得を待たずに進む
- `MemoryUsageMetric` (計測モジュールの記録) は採っていない
