## 走行 5: 到達点「メモリまで (列幅)」 (修正前のビルド)

### 環境

共通表のとおり。起動引数 `--prefetch memory-column` (先読みの要素に列幅を付ける)。記録窓の指定 120 秒、**実長 120.51 秒**。熱状態は全区間 Nominal (`is-induced` は No)。

### 操作条件

共通表のとおり。

**記録に操作列が入っていない。** trace (接続先は `KsCollectionViewSamples` の 1 プロセス、記録の終了理由は時間切れ) を export すると、対象プロセスの surface swap は 44.55 秒と 104.43 秒の 2 件だけ、HID 入力は 0 件、hitch は 44.43 秒の 1 件 (116.92 ms、High) だけ、主スレッドを含む time profile の標本は 15 行で、スクロールの描画も入力も記録されていない。1 秒ごとの surface swap 数の表も、2 件を除いて全区間 0 である。

オーナーは「Starting recording」の確認後に画面と到達点を確かめて操作列を行い、体感を答えている。記録が操作を捉えなかった理由 (接続先のプロセスと画面のプロセスの食い違い、計測器側の取りこぼしなど) は、trace からは決められない。

### オーナーの体感 (合否の主語。数値を見る前に聞き取り)

- 初回 / 再訪 / 連続 / ムラ: 体感変わらず (問題なし)
- 画像の出方 (別の観測点): (走行 4 と比べて) **よりスムーズに早く感じた**

### 数値 (証跡。合否ではない)

**取得できない。** 記録に操作列が入っていないため、hitch 件数・ratio・主スレッド稼働率・time profile の帰属のいずれも、この走行の値として示せない。上の 2 件の surface swap と 1 件の hitch は操作列のものではなく、数値として使わない。

### 判定

- 体感の合否: **合格** (迷いなく変わらず。非接続の対照は行っていない)。体感ゲートの合否の主語はオーナーの体感で、体感は計測器の記録とは独立に聞き取れている。ただし、この走行で計測器の負荷が操作中のプロセスに掛かっていたかは trace から確かめられない (掛かっていなかったなら負荷は減る向きで、合格の向きは変わらない)
- 数値との一致・不一致: 数値が無いため判断できない
- 画像の出方: 走行 4 よりスムーズに早く感じた
- 前回との比較可否: 到達点「メモリまで (列幅)」は本 change で足した到達点で、before に同じ到達点の記録が無い。**比較不能**

### 限界

- 数値の証跡が欠けている。体感ゲート規約は「記録窓が操作列を収めきれなかった記録は破棄し、判定に使わない」としており、この trace は判定の材料にも数値の証跡にも使わない。数値が要るなら同じ条件で採り直す必要がある (本証跡の作成では端末を使っていないため採り直していない)

#### 悪化している数値とその扱い

- **最終走行 6 (ディスクまで)**: 操作の外枠の hitch time ratio 119.7 (前回) / 116.8 (before) → 133.0 ms/s、High 7 / 11 → 15 件、初回に当たる区間の ratio 133.7 / 120.7 → 161.5 ms/s、連続に当たる区間の ratio 186.9 (前回) → 193.4 ms/s、主スレッド稼働率 (操作の外枠) 38.5% / 34.9% → 39.1%、surface swaps / 秒の中央値 49.5 (前回) → 43、hosting の描画の占有 31.1% / 31.3% → 37.2%・`ViewRendererHost` 全体 53.9% / 54.1% → 57.2%。hitch の総数・HID 区間の外枠の ratio (前回比)・再訪の区間・セルの生成の占有は下がっている
- **最終走行 4 (メモリまで)**: 再訪に当たる区間の主スレッド稼働率 22.9% (before) → 25.2%、hosting の描画の占有 30.9% / 31.1% → 37.0%・`ViewRendererHost` 全体 52.8% / 54.3% → 56.3%、プリフェッチの占有 (上限値) 14.6% / 12.1% → 16.3%
- 原因仮説: (a) 修正で、まだ引き当てていない画像を画面に出る時点の引き当ての包み (`KsImageDeferredLoad`) で包むようになり、表示の組み立てに 1 段の View と状態が加わり、画面に出る時点の引き当ての照会が主スレッドで走る。「ディスクまで」では画面に出る画像のほぼすべてがこの経路を通るため、hosting の描画の占有と主スレッドの費用が増えた可能性。(b) 操作の密度。最終走行 6 の操作の外枠は 3 者で最も短く、同じ段階を短い時間に詰めると区間長を分母にした ratio・稼働率は上がる向きに働く。(c) 走行ごとの揺れ。before の証跡で、コードの変わらない 2 記録の間で「ディスクまで」の初回区間の hitch が 13 件 → 41 件に動いた例がある。time profile の占有は inclusive の比で、他の項目 (セルの生成) が下がると相対的に上がる。どれが効いているかは**確定していない**
- 再確認の有無: 非接続の対照も再走行も行っていない (各 1 試行)。自動フリックによる修正前後の A/B は Android で予定されており、iOS での再確認は未定
- 受容する理由: 合否の主語は体感 (cross/ADR-0006) で、オーナーは 3 走行とも迷いなく合格 (前回と変化なし) とした。体感が迷いなく合格で数値だけが悪いときは対照を行わない規約どおりで、計測器を外せば負荷は減る向きのため合否は変わらない。悪化は ratio で 1 割強・High で数件の幅で、操作量が揃わない記録どうしの差であり、hitch の最長 (33.34 ms) は 3 者で変わらない。修正は Scenario「メモリ到達点の後の表示」を実機で満たすためのもので、滑らかさの数値の悪化を理由に取り下げる根拠は体感側に無い。ただし「ディスクまで」の悪化の帰属は未確定のまま残す

### 8.4: 許容範囲の初期値 (0.5 / 4) の見た目 (最終ビルド)

結論は変わらない。定数は `KsImageMatching` の `lowerBound = 0.5` / `upperBound = 4.0` のまま。最終走行 4〜6 と Android の最終走行 1〜3 でも、オーナーから画像のぼやけ・粗さ・枠との不一致の指摘は無かった。限界は前回の節と同じ (オーナー 1 人の目視、画像ごとの拡大率は未記録、枠は正方形セル 3 列の 1 種類だけ)。

### 3 走行に共通する限界

- 体感はオーナー 1 人・各 1 試行 (最終走行 5 は破棄した 1 回目の後のやり直し)。非接続の対照は行っていない
- 到達範囲 (通過した件数) が取得不能のため、操作量の差を件数で数えられない。区間の長さと HID 入力の長さからの当てに留まる
- 段階の当ては HID の空白で切った当てで断定しない。前回・before の一部 (描画区間の空白で切った記録) と切り方が違う
- time profile の占有率は inclusive のため入れ子の項目は重複して数えられ、合計は 100% にならない。画像の読み込み・デコード系とプリフェッチの占有はシンボル名の部分一致による上限値
- 画像の出方はオーナーの目測で、前回との相対で聞き取った。計時していない。ネットワーク状態・画像の到着タイミングは記録していない
- 取得・デコードの回数 (ローダーの通知) はこの記録には無い (tasks 8.2 の証跡)
- 画像の出方は滑らかさとは別の観測点で、合否に混ぜていない

#### 限界

- **改善後は「ディスクまで」1 回だけで、依頼の回数 (到達点「ディスクまで」と「メモリまで」で各 3 回以上、修正前・最終と交互) に届いていない。** オーナー決定で打ち切った。理由: 原因は前半の A/B で特定済みであり、改善後の「ディスクまで」は包みを通らず修正前と同じ経路に戻る構造であり、滑らかさの合否は最終走行のオーナーの体感で合格済みのため
