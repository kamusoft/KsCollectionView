tasks 8.5 (Android 分)。オーナーの手動計測 (before / after) で、Android の画像グリッドは「スクロールを止めてから画像が揃うまで」が約 5 秒で、到達点 (メモリまで / 列幅 / ディスクまで) による差を感じず、iOS (2〜3 秒) より遅い。この待ちの内訳をローダーの通知の時刻で測り、主因の仮説を証拠付きで書く。改善策は実装しない (本 change の Non-Goals)。

## 結論 (主因の仮説)

**主因は、取得経路 (OkHttp) の同一ホストの同時取得数の上限 5 件である。** フリングを止めた時点で、同じ画像サービスへの要求が 43〜52 件 (先読みの窓 + 可視セルの表示要求 + 同じ画像の二重取得) 取得待ちに積まれ、5 件ずつしか進まない。可視セルの表示要求は先読みの要求と同じ列に並ぶため、揃うまでに 1 画像の取得時間 (約 0.4 秒) の数倍かかる。

- 証拠 1 (対照計測): 上限だけを 5 → 64 に変えると、止めてから揃うまでの時間が **中央値 2.4〜2.8 秒 → 0 秒** (最大 0.9 秒) になる。3 つの到達点すべてで同じ
- 証拠 2 (内訳): 待ちのほぼすべてが「取得の開始から終了まで」(取得経路の順番待ち + 通信) にある。ローダーの中の待ち・合成から要求までの時間・デコードは合わせて数十ミリ秒
- 到達点で差が出ないのはこのため: 到達点が変えるのは取得の後 (デコードしてメモリに載せるか) で、待ちは取得の前 (順番待ち) にある。フリングで先読みの窓を追い越すと、どの到達点でも可視セルは取得から始まる

副因 (上限 5 の下で待ちを増やしているもの):

1. **同じ画像の二重取得。** 取得した画像の 35〜43% (既定の上限で 138〜172 件中 54〜63 件。修正前のビルドの値で、修正後は同時取得数 5 で 36〜38%。冒頭の注記) を、先読みと表示要求が並行してネットワークから取得している。先読みは可視範囲に入っても取り消さず表示側へ引き継ぐ設計だが、表示要求は先読みの完了を待たずに別の取得を始めるため、順番待ちの列が 1.4 倍前後に膨らむ
2. **先読みと表示要求の間に優先度が無い。** 止めた時点の取得待ちの約 6 割 (26〜31 件) は先読みで、可視セルの表示要求 (17〜21 件) と同じ列に並ぶ
3. **(到達点 memory のみ) 先読みの完了後に引き当て直さない。** 画面外で先に組まれた時点で先読みが未完了だったセルは、完了後に画面へ出ても表示要求 (二重取得) のままになる (`loader-counts-android.md` の「フリングでの発見」)。**修正後は解消** (`loader-counts-android.md` の修正後の節)

主因ではないと判断したもの: 画像 1 枚ごとの subcomposition (`BoxWithConstraints`)、ローダー内部のディスパッチ、デコード、cold の取得そのもの (1 画像の通信は約 0.4 秒)。根拠は下の「内訳」。

### 取得経路の同時取得数の上限が 5 件であることの確認

coil-network-okhttp 3.5.0 の実装 (配布物のバイトコード) を読み、取得は `okhttp3.Call.enqueue` (非同期の実行) で行われ、既定の取得経路は引数なしの `OkHttpClient()` で作られることを確かめた。OkHttp の非同期実行は `Dispatcher` の同一ホストの上限 (既定 5) と全体の上限 (既定 64) で絞られる。本 Sample の画像はすべて同じホストから取得する。

### 対照の作り方

計測用ソースセットの観測者に、共有インスタンスを作る時点で「同一ホストの上限だけを変えた取得経路」(`Dispatcher.maxRequestsPerHost = 64`、全体の上限 64) を差し込む指定を足した (経路の最後の引数。0 は既定のまま)。本体のコードと公開面は変えていない。上限 64 の 6 走行すべてで差し込みのログ (`network maxRequestsPerHost=64`) が出ており、上限 5 の 6 走行では出ていない。差し込んだ取得経路が使われたことは、1 画像の取得時間の中央値が 1.86〜2.53 秒から 0.36〜0.50 秒へ変わったことで確かめた (既定の取得経路のままなら変わらない)。

## 手順

1. アプリのデータを消去し、観測用画面を (到達点, 上限) の組ごとに起動する。15 秒待つ
2. 下向きのフリング (`input swipe`、1,500 px を 60 ms) を 0.5 秒間隔で 5 回 (約 2.5 秒の連続フリング)、その後 15 秒静止。これを 3 回
3. 観測用画面がスクロールの停止 (セルの位置が 300 ms 変わらない) を検出し、最後に位置が変わった時刻 (止めた時刻) と、そのとき見える範囲に重なるセルを記録する
4. 見えるセルごとに「絵が出た時刻」を求める: 組まれた後に表示要求を出していなければ組まれた時刻 (メモリの項目を引き当てて読み込み中を経由しない)、出していればその要求の成功の時刻。**止めてから揃うまで = 見えるセルの「絵が出た時刻」の最大 − 止めた時刻** (負なら 0)
5. 各組 2 走行 × 3 回 = 6 標本

オーナーの操作は使っていない。

| 区間 (ローダーの通知の時刻) | 値 |

| 同じ画像の二重取得 (ネットワークからの取得が 2 回以上あった画像) | 54/156・63/172 (ディスク)、60/158・59/157 (メモリ)、60/153・60/138 (列幅) |

- 上限 64 の 1 画像の取得 (中央値 0.36〜0.50 秒) が通信そのものの時間にあたる。上限 5 との差 (約 1.5〜2 秒) は順番待ち
- 止めた時点の取得待ち 43〜52 件を 5 件ずつ、1 件約 0.4 秒で流すと約 3.4〜4.2 秒で、最後に揃ったセルの取得 2.7〜3.8 秒と桁が合う (可視セルの表示要求は列の途中にいるため、全件より早く終わる)
- フリング中の取り消しは多いが、取り消した要求は取得経路で即座に失敗して枠を空ける (上限 64 との比較で、取り消しの量は同程度なのに待ちが消えている)

### 候補ごとの判定

| 候補 | 判定 | 根拠 |
|---|---|---|
| 同一ホストの同時取得数 (OkHttp の上限 5) | **主因** | 上限だけを 64 にすると待ちの中央値が 0 になる (上の表) |
| 同じ画像の二重取得 (先読みと表示要求) | 副因 | 取得した画像の 35〜43% が 2 回取得され、上限 5 の列を膨らませる |
| 先読みと表示要求の優先度の無さ | 副因 | 止めた時点の取得待ちの約 6 割が先読みで、可視セルの要求と同じ列 |
| 先読みの窓の広さ (可視件数と同数) | 副因の一部 | 窓の先読みが上の約 6 割を占める。窓そのものを狭める効果は測っていない |
| 画像 1 枚ごとの subcomposition (`BoxWithConstraints`) | 主因ではない | 組まれてから表示要求まで中央値 1 ms。フレームの負荷の問題で、秒単位の待ちには現れない |
| ローダー内部のディスパッチ | 主因ではない | 要求の開始から取得の開始まで 0〜3 ms |
| デコード | 主因ではない | 1 件 15 ms 前後 |
| cold の取得そのもの | 主因ではない | 1 画像の通信は約 0.4 秒。上限 64 では止めた時点でほぼ揃う |
| 到達点 (メモリ / 列幅 / ディスク) | 差なし | 待ちは取得の前 (順番待ち) にあり、到達点が効くのは取得の後。6 標本の中央値 2.4〜2.8 秒で重なる |

## iOS との差について (仮説、未計測)

本計測は Android だけで、iOS の取得経路の同時取得数は測っていない。iOS (2〜3 秒) が Android より速い理由の候補として、取得経路の同時取得の扱いの違い (Android は OkHttp の同一ホスト 5 件の上限で要求単位に絞られる) を挙げるにとどめる。iOS 側で同じ内訳を取るまで断定しない。

オーナーの手動計測 (約 5 秒) と本計測 (約 2.6 秒) の差は、操作の違い (オーナーは 10 秒の連続フリングで本計測の 2.5 秒より多くのセルを通過し、取得待ちがより多く積まれる) で説明できる見込みだが、確かめていない。

## 別 change で扱うべきこと (簡易起票の材料)

1. **Android の取得の並行度と優先度** — 同一ホストの上限 5 の下で、可視セルの表示要求が先読みの後ろに並ぶ。選択肢の例: (a) 利用者向けの案内 (共有インスタンスの取得経路の上限を上げる。共有インスタンスは利用者のもの、core/ADR-0012) に留める、(b) スクロール停止時に可視範囲の外の先読みを後回しにする・止める、(c) 先読みの窓の広さを取得の並行度に合わせる。上限 64 で待ちが消えることは本証跡で確認済み
2. **同じ画像の二重取得** — 先読みの取得中にセルが見えると、表示要求が別の取得を始める。ローダーの同時要求の統合 (Coil の取得経路の設定) か、表示側が進行中の先読みの完了を待つ形で解消できるかを調べる
3. (本 change の範囲の可能性) **先読みの完了後の引き当て直し** — `loader-counts-android.md` の「フリングでの発見」。iOS で見つかった同型の不具合と同じ扱いにするかはオーナー判断。**本 change で修正済み** (冒頭の注記)

## Perfetto について

Perfetto のトレースは採っていない。ローダーの通知の時刻で要求ごとの区間 (ローダー内の待ち・取得・デコード) と止めた時刻を同じ時計で取れ、主因は上限だけを変えた対照計測で直接確かめられたため。取得経路のスレッドの並行数や主スレッドの負荷をトレースで見る必要が出たら、次の計測で採る。

## 限界

- フリングは `input swipe` による合成の操作で、オーナーの手の速さ・回数とは違う。各組 2 走行 (6 標本)
- 取得元は公開の画像サービス (リダイレクトあり) で、回線状態は記録していない。各反復の中で上限 5 の 3 組を先に、上限 64 の 3 組を後に続けて行った (交互ではない)
- 「絵が出た時刻」は要求の成功の時刻で、その後の描画 1 フレーム分は含まない
- 二重取得の数え方は「同じ画像にネットワーク由来の取得の終了が 2 回以上あった」で、取り消された取得は数えていない

## 最終ビルドでの採り直し — 2026-09-24

冒頭の注記の「採り直しの予定」の実施分。上の節 (修正前のビルド) と同じ観測用画面・同じ手順 (上の「手順」1〜5)・同じ集計で、最終ビルド (review-008 APPROVED / verify-002 VALID の時点の作業ツリー) を採り直した。同じ日の回線状態での差を見るため、比較用ビルド (最終ビルドから Android の修正サイクル 5・6 の変更だけを戻したもの。下の「比較用ビルド」) も上限 5 だけ同じ手順で採った。

### 結論

- **主因 (同一ホストの同時取得数 5) の結論は保てる。** 最終ビルドでも、上限 5 の止めてから揃うまでの中央値は 2.6〜3.2 秒で、上限だけを 64 にすると 3 到達点とも中央値 0 秒 (最大 0.7 秒) になる。待ちのほぼすべてが取得の開始から終了まで (取得経路の順番待ち + 通信) にある点も変わらない
- **副因 1 (同じ画像の二重取得)**: 残っている。取得した画像の 29〜34% (上限 5)。同じ日の比較用ビルドは 34〜40% で、修正で少し減った (画面に出た時点で先読みが完了していれば取得しないため)。残りは、画面に出た時点で先読みがまだ取得中だった画像のもの
- **副因 2 (先読みと表示要求の優先度の無さ)**: 変わらない。止めた時点の取得待ちは先読み 23〜29 件 + 表示要求 15〜21 件 (先頭付近で止まった回を除く) で、可視セルの表示要求が先読みと同じ列に並ぶ
- **副因 3 (先読みの完了後に引き当て直さない)**: 修正済み (`loader-counts-android.md` の修正後の節)。本計測のフリング (2.5 秒で先読みの窓を追い越す) では、止めた時点の可視セルはどのビルドでも先読みが完了しておらず、引き当てられたセルは 0 件で、この計測では差が出ない
- **新しく見えたこと**: 「メモリまで」「メモリまで (列幅)」では、最終ビルドの待ちが同じ日の比較用ビルドより中央値で 0.35〜0.5 秒長い (6 標本ずつで重なりがあり、確定ではない)。最終ビルドは、先読みが未完了の画像の表示要求を画面に出る時点まで遅らせる (修正サイクル 6)。フリング中の表示要求の 67〜71% がこの経路に入り、組み立てから表示要求の開始までが中央値 1 ms → 24〜25 ms (95 パーセンタイル 102〜104 ms。上限 5) に延びている。遅れた分だけ可視セルの表示要求が上限 5 の列の後ろに並ぶ、という仮説と向きが合う。「ディスクまで」は先読みを索引に覚えさせないため遅らせる経路に入らず (0%)、待ちも比較用ビルドと同じ

## 性能改善後 — 2026-09-24

表示中のフレームの再合成を減らす改善 (`manual-imageGrid-android-after.md` の「性能改善後の再確認」) の後で、上の「最終ビルドでの採り直し」と同じ観測用画面・同じ手順・同じ集計で採った。改善の一方は「表示要求を画面に出る時点まで遅らせるのは、その画像の先読みが取得中のときだけにする」(完了・失敗・取り消し・追い出し済みの先読みでは遅らせない) で、上の節の「新しく見えたこと」(遅れた表示要求の割合 67〜71%) を減らす狙いがある。

### 結論

- **遅らせた表示要求は減ったが、待ちの差は縮まっていない。** 画面に出る時点まで遅らせた表示要求の割合 (16 ms 以上遅れた割合) は 65〜70% → **38〜41%**、組み立てから表示要求の開始までの中央値は 24〜25 ms → **12 ms**、95 パーセンタイルは 98〜113 ms → **74〜76 ms** になった (上限 5)。一方、止めてから揃うまでの中央値は、メモリまで 比較用 2,467 / 改善前の最終 2,822 / 改善後 2,707 ms、列幅 2,423 / 2,697 / 2,725 ms で、改善後も比較用より 0.25〜0.3 秒長いまま (6 標本ずつで範囲は重なり、確定ではない)
- 残る遅らせた表示要求は、画面に出る前に組まれた時点で先読みが**まだ取得中**だった画像のもの。フリングでは先読みの取得が同時取得数 5 の列に並んで長く取得中のままになるため、この割合が 4 割残る。取得中の先読みを待つのは、画面に出るまでに完了すれば読み込み中も二重取得も省けるからで (Scenario「メモリ到達点の後の表示」)、これ以上減らすには「取得中でも待たない」の判断が要る
- **主因 (同一ホストの同時取得数 5) の結論は変わらない。** 改善後も上限だけを 64 にすると 3 到達点とも中央値 0 秒 (最大 0.75 秒)
- 「ディスクまで」は遅らせる経路に入らず (0%)、待ちも 3 ビルドで揺れの範囲 (中央値 2,266 / 2,423 / 2,343 ms)
