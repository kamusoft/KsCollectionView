# 先読み後の初回表示でのローダーの要求・取得・デコードの回数 (iOS) — 2026-09-23

tasks 8.2 (iOS 分)。Scenario「メモリ到達点の後の表示」(到達点 `memory` で取得が完了し、載った項目が枠に対して許容範囲の内側にあるとき、`KsImage` はネットワークもデコードのやり直しもなしに、読み込み中を経由せず表示する) を、ローダーの割り込み処理の通知と計測の足場の計数で数えて確かめる。Android 分は `loader-counts-android.md`。修正 (まだ引き当てていない `KsImage` は画面に出る時点でもう一度引き当てを試す、deviation.md 末尾) の後のビルドで測った。

## 結論

- **ゆっくり送り (主計測): spec どおり。** 画面に出た時点で先読みが完了していた項目 138 件 (幅なし) / 138 件 (列幅) のすべてで、`KsImage` の表示の要求 0 件 (= 取得 0 件・デコード 0 件)・画面に描かれた読み込み中 0 件。対照の到達点 `disk` では同じ送りで現れた 147 件すべてが表示の要求を出し、138 件がディスクからデコードしており、数え方が空振りしていないことも確かめた
- **速い送り (先読みが間に合わない項目が混じる): spec どおり。** 画面に出た時点で先読みが完了していた項目 160 件 (幅なし) / 165 件 (列幅) のすべてで、表示の要求 0 件・画面に描かれた読み込み中 0 件。「先読みの完了後に画面に出たのに表示の要求を出した」(修正前の不具合の形・引き当ての失敗) は 0 件。表示の要求を出したのは、画面に出た時点で先読みがまだ完了していなかった項目だけ (spec の GIVEN の外)
- Android の「フリングでの発見」(修正前) と同じ形は、iOS の修正後のどの走行にも現れていない

| 項目 | 値 |

| 起動引数 | `--prefetch <memory | memory-column | disk> --observe-image-loading --count-image-loading-slots`、`--probe-steps <段数>`、速い送りは `--probe-pace <ミリ秒>` (`devicectl device process launch --console` の `--` の後ろ) |
| 土俵 | 「画像グリッド」と同じ宣言元 (`ImageGridFixture`: 10,000 件・3 列・正方形セル・リモート画像 400 × 400)。枠 127.33 pt (表示倍率 2 で約 255 px、列幅 255 px) |
| 数えた通知 | ローダー (Nuke) の共有パイプラインの割り込み処理 (`ImagePipeline.Delegate`) が受ける画像の要求の作成 (`start`)・成功 (`success`、どの層から返ったか)・取り消し (`cancel`)。要求の種別は縮小の指定と優先度で分ける (表示の要求 `display` / 列幅の先読み `width-prefetch` / 幅なしの先読み `prefetch-or-loader-display`)。読み込み中の表示の組み立て (`sized` / `unsized`) と画面に描かれた読み込み中 (`shown`、コレクションの表示範囲で切り取られた表示は数えない) は Sample の足場の計数 |
| 生ログ | スクラッチにのみ保管。change には置かない |

`KsImage` が引き当てたときはローダーへ要求を作らない (メモリにある項目をそのまま描く) ため、「表示の要求が 0」は「その項目の取得もデコードも 0」を意味する。ローダーの取得とデコードは要求 (`ImageTask`) の中でしか起きない。

## 手順

1. 初回表示の後、読み込みの節目が 3 秒静まるまで待ち、読み込み中の計数の基準点を切る
2. 送り: 可視範囲の高さの半分ずつ、アニメーション付きで送る (UIKit はアニメーションの無い位置の書き換えでは先読みの通知を出さない)。段ごとの待ちで速さを変える
   - ゆっくり送り: 20 段。各段の前に取得中の先読みが無くなるまで待つ (`settle`)
   - 速い送り: 40 段。各段の後に 500 ms だけ待つ (取得より速く進み、先読みが間に合わない項目が混じる)
   - 最速: 40 段。待ちなし (1 段 = アニメーション 1 回、約 0.3 秒)
3. 送りで新しく現れた項目 (セルの枠の半分以上が可視範囲に入った項目) ごとに、「先読みの完了」「表示の要求の開始」「セルの組み立て」の時刻を並べて分類する
4. 戻し (同じ刻みで先頭側へ戻す) とメモリのみの消去の後の 1 段の送り戻しも、基準点を切り直して数える

## 結果: ゆっくり送り (各 1 走行)

| 到達点 | 現れた項目 | 画面に出た時点で先読み完了 | その表示の要求 (= 取得・デコード) | その画面に描かれた読み込み中 | その読み込み中の組み立て (画面には出ていない) | 先読みが間に合わなかった項目 (表示の要求 / 描かれた読み込み中) | 先読みが載せた項目の寸法 |
|---|---:|---:|---:|---:|---:|---|---|
| メモリまで (幅なし) | 147 | 138 | **0** | **0** | 136 | 9 (9 / 9) | 元寸 400 × 400 (138) |
| メモリまで (列幅) | 147 | 138 | **0** | **0** | 136 | 9 (9 / 9) | 255 × 255 (138)、元寸無し |
| ディスクまで (対照) | 147 | — (先読みはメモリに載せない) | 147 (ディスク 138 / ネットワーク 9) | 91 | — | — | — |

- 先読みの取得は、幅なし・列幅とも 162 件開始・162 件成功 (ネットワーク 155 / ディスク 7)・取り消し 0 件。メモリからの成功 (同じ画像の要求の出し直しがメモリに当たったもの) は 0 件で、先読みの完了後にその画像の要求が作られた記録は無い
- 先読みが間に合わなかった 9 件は、最初の送りで現れた項目。送りの開始前には UIKit が先読みの通知をまだ出しておらず、先読みと表示の要求が同じ段で始まった (`device-image-match-ios.md` の修正後の節)
- ディスクまでの対照で、表示の要求 147 件に対して画面に描かれた読み込み中が 91 件なのは、画面外で先に組み立てられたセルの要求が画面に出る前に終わる分 (ディスクから p50 11 ms) があるため。Android の対照と同じ性質

## 結果: 速い送り (各 1 走行)

| 到達点 / 段ごとの待ち | 現れた項目 | 画面に出た時点で先読み完了 | その表示の要求 | その描かれた読み込み中 | 先読みの完了後に表示の要求 (引き当ての失敗・修正前の形) | 画面に出た時点で先読み未完了 (表示の要求 / 描かれた読み込み中) |
|---|---:|---:|---:|---:|---:|---|
| メモリまで (幅なし) / 500 ms | 297 | 160 | **0** | **0** | **0** | 137 (137 / 136) |
| メモリまで (列幅) / 500 ms | 297 | 165 | **0** | **0** | **0** | 132 (132 / 132) |
| メモリまで (幅なし) / 待ちなし | 297 | 0 | — | — | 0 | 297 (297 / 297) |
| メモリまで (列幅) / 待ちなし | 297 | 0 | — | — | 0 | 297 (297 / 297) |

- 500 ms の送りで先読みの完了後に画面に出た項目は、幅なしでは元寸 400 × 400 (160 件)、列幅では 255 × 255 (165 件、元寸無し) の項目で表示された。うち幅なし 157 件・列幅 163 件は、セルが先読みの完了より前に組み立てられ、画面に出る時点の引き当てで当たったもの
- 画面に出た時点で先読みが未完了の項目は、画面に出る時点で表示の要求を出す (`KsImage` はそれより前には要求を出さない)。500 ms の送りでは、その表示の要求の取得元はネットワーク (幅なし 137 件、p50 346 / p90 414 / 最大 1,137 ms) と、列幅でディスク 1 件
- 待ちなしの送りでは先読みがどの項目にも間に合わず、全件が表示の要求を出した。表示の要求は 297 件中 245 件 (幅なし) / 255 件 (列幅) がセルが画面から外れて取り消された
- 戻し (待ちなしの走行で 303 件) では、表示の要求・描かれた読み込み中とも 0 件。送りの間に完了した先読みの項目を、画面に出る時点で引き当てている

### 先読みと表示の要求が同じ画像を取った場合

500 ms の送りでは、先読みの成功のうちディスクからのものが幅なし 113 件・列幅 121 件あった。先に始まった表示の要求がネットワークから取って元データをディスクに残した後で、先読みがその画像の番に来たもの (先読みは 2 件ずつしか走らない。`disk-wait-ios.md`)。ネットワークからの取り直しではない。表示の要求と先読みが同じ画像を同時に取りにいった場合は、ローダーが元データの取得を 1 本にまとめる (同じ識別子の要求の統合) ため、割り込み処理の通知ではどちらも「ネットワーク」と記録されるが、通信は 1 回である。通知の数からは両者を区別できないため、二重の通信の有無はこの記録では数えていない。

## 抜粋 (sanitize 済み、ゆっくり送り・幅なし)

```
KS_PROBE_FORWARD appeared=147 matched=138 late=9 builtBefore=0 violation=0 unprefetched=0 noEvent=0 matchedSized=136 matchedUnsized=0 matchedShown=0
KS_PROBE_PIXELS items=138 original=[(key: "400x400", value: 138)] originalAbsent=0 column255=[]
KS_PROBE_PHASE phase=forward items=147 displayStarts=9 displayCancels=0 sized=154 unsized=0 shown=9 waitMs=[network:n=9,p50=353,p90=596,max=600]
```

`matched` = 先読みが完了していて表示の要求が無い項目、`late` = 表示の要求が先読みの完了より前、`builtBefore` = 先読みの完了後に表示の要求が出てセルの組み立ては完了より前 (修正前の形)、`violation` = 先読みの完了後に組み立てられたのに表示の要求が出た (引き当ての失敗)。

## 限界

- 送りは計測用の起動経路によるアニメーション付きのスクロールで、指のフリックではない。「速い送り」はアニメーション 1 回 (半画面) ごとに 500 ms 待つ送りで、Android のフリング (`input swipe`) とは速さも減速の形も違う
- 各形 1 走行。実回線で、取得時間は回線状態に依存する (判定は先読みの完了を確かめた項目だけを数えるため、回線の速さに依らない)
- 先読みの要求がその画像で 1 回しか作られていないことは、開始件数 (162 / 309) と現れた項目の範囲 (先読みの窓 1 画面分先まで) の突き合わせと、メモリからの成功が 0 件であることから読んでいる。画像ごとの要求の回数は集計値に出していない
