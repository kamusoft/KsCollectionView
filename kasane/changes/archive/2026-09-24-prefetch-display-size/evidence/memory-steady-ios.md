# 到達点 memory (幅なし / 列幅) のメモリ定常化と索引 (iOS) — 2026-09-23

tasks 8.3 (iOS 分)。到達点 `memory` の幅なし / 列幅で、iOS 性能検証の手順 (kasane/handbook/ios/performance-verification.md の「メモリの手順」「保持対象の解放の確認」) により、(1) 列幅では元寸を載せない分の減少、(2) 索引込みで定常化すること、(3) 画面離脱後に索引がコレクションやセルを保持しないこと、(4) 索引の充足 (キャッシュにある項目が索引に残っている率) を確かめる。Android 分は `memory-steady-android.md`。

## 結論

| 観点 | 結果 |
|---|---|
| (1) 列幅では元寸を載せない | **spec どおり。** 列幅の走行ではメモリキャッシュに元寸 (400 × 400) の項目が 1 件も無く、先読みの項目はすべて 255 × 255 (列幅)。メモリキャッシュの大きさ (ローダーの見積もり) は 60 件で 42.3 MB → 19.6 MB (−22.7 MB、−54%)、600 件で 387.9 MB → 160.6 MB (−227.3 MB、−59%)。先読みの項目が 400 × 400 から 255 × 255 になった分 (1 件 640,000 B → 260,100 B) と一致する。ただし `phys_footprint` には差が出ない (下の「`phys_footprint` とキャッシュの大きさ」) |
| (2) 索引込みで定常化 | **定常。** 手順どおりの 10,000 件の往復 (Simulator、Release、独立 2 回): 幅なし steady:4・steady:4、列幅 steady:3・steady:3。索引は 10,000 件 (上限 20,000 の内側) で止まり、増え続けない。実機の読み込み待ちの往復 (60 件・600 件) もすべて steady:3〜4 |
| (3) 離脱後に索引が保持しない | **保持していない。** 走行後にコレクションを画面から外すと、コレクションと可視セル 15 件がすべて解放された (Simulator の 10,000 件、実機の 60 件・600 件の全 Debug 走行)。索引は離脱後も鍵を残す (`indexKeysBefore` = `indexKeysAfter`) が、持つのは要求の値 (URL・識別子・縮小の指定) だけでビューへの参照を持たない |
| (4) 索引の充足 | **1.000。** 画像が載る実機の読み込み待ちの往復で、メモリキャッシュにある項目は 60 件 (75/75)・600 件 (615/615) とも全件が索引に残っていた。手順どおりの 10,000 件の往復はキャッシュが空で終わるため、充足を計算できない (下の「結果 1」) |

画像の枠は Simulator で約 370 px (表示倍率 3)、実機で約 255 px (表示倍率 2)。メモリキャッシュの上限はローダーの既定で、Simulator 805 MB、実機 606 MB。

### 読み込み待ちの往復を足した理由

手順どおりの往復は、位置をアニメーション無しで書き換えて取得より速く進む。UIKit はアニメーションの無い位置の書き換えでは先読みの通知を出さない (`device-image-match-ios.md`) ため、この往復では**先読みが 1 件も走らず**、画像もほとんど載らない (往復の終わりのメモリキャッシュは 0 件)。「元寸を載せない分」も「キャッシュが満ちた状態での索引の充足」も見えないので、Android と同じく、段ごとに読み込みを待つ往復を足して 60 件 (キャッシュの上限に十分収まる) と 600 件で測った。件数を変えた計測のため、10,000 件の結果とは比べない。

この往復は、手順どおりの計測用の起動経路 (`PerformanceVerificationView`) に起動引数で足した分岐で、**リポジトリの samples/ios の起動引数で再現できる**。

- `--image-count <件数>`: 「画像グリッド」の土俵の件数を変える (`ImageGridCount`。既定 10,000 件、正の整数以外は起動を止める)
- `--memory-loaded`: 送りをアニメーション付きにし、段ごとに進行中の読み込み (観測の記録で始まって終わっていない要求) と見える範囲の読み込み中が無くなるまで (上限 10 秒) 待ってから進む。判定に観測の記録と読み込み中の印を使うため、`--observe-image-loading --count-image-loading-slots` と併せて指定する (欠けていれば `KS_PERF_ERROR` を出して走らせない)
- 往復ごとのメモリキャッシュの大きさ・件数 (`KS_CACHE` 行) は、画像グリッドの走行では常に出る

Android の計測用ソースセットの `measurement/image-memory-loaded/<件数>/10/<到達点>` に対応する。起動引数を付けない実行 (デモ画面・手順どおりの往復) の挙動は変わらず、本体に計測のための公開面は足していない (索引の突き合わせは従来どおり Debug 構成だけの `ImageMemoryIndexReport`)。

証跡の数値は、同じ内容の足場を Sample の複製 (スクラッチ) に足した版で採った (リポジトリ版との違いは、前提の引数が欠けたときに走らせない検査と、`KS_CACHE` 行を画像グリッドの走行に限ったことだけで、送り・待ち・出力の形は同じ)。その後この足場をリポジトリへ取り込み、リポジトリ版で Simulator (iPhone 17e / iOS 26.5) の 60 件・列幅を Release・Debug 各 1 回走らせ、同じ形の出力 (往復ごとの `KS_PERF_MEMORY_ROUND_<n>` と `KS_CACHE`、判定、Debug の `KS_INDEX_*`) が出ることを確かめた (どちらも 3 往復で定常、`visited=60/60`、Debug は充足 1.0000・コレクションとセル 15/15 の解放。Simulator の値なので上の実機の表とは比べない)。あわせて、`--memory-loaded` だけを付けて前提の引数を欠いた起動が `KS_PERF_ERROR` を出して走らずに終わることも確かめた。実機の数値はリポジトリ版では採り直していない。

### `phys_footprint` とキャッシュの大きさ

`phys_footprint` は、メモリキャッシュの大きさ (ローダーの見積もり 19.6〜387.9 MB) に比例していない。実機で 60 件の幅なしと列幅の定常値はどちらも約 14.6〜15.5 MB、600 件の幅なし (キャッシュ 387.9 MB) でも約 16〜19 MB だった。Simulator でも同じ読み込み待ちの往復 (60 件) の値は幅なし・列幅とも約 30 MB で差が無かった。Nuke は iOS で画像を展開してからキャッシュに置く (`isDecompressionEnabled` の既定が有効) ため、展開した画素の記憶域が `phys_footprint` の数え方の外にある (画像用の記憶域として別に数えられる) と見ているが、確かめていない。

このため、「元寸を載せない分の減少」はキャッシュの大きさと項目の寸法で示し、`phys_footprint` では示さない。定常判定 (`phys_footprint` の往復ごとの増分) は手順どおりに成立しているが、展開した画素の記憶域の増減はこの判定に現れない可能性がある。キャッシュの大きさは往復ごとに一定だったので、この計測の範囲では画像の記憶域も増え続けていない。

## 保持の確認の詳細

- 取り外し: 走行の後、コレクションを画面から外し、コレクションと可視セルへの弱参照が空になるのを待った (上限 10 秒)。全 Debug 走行 (Simulator 2、実機 4) で `collectionReleased=true cellsReleased=15/15`
- 索引の持ち物: 索引 (`KsImageMemoryIndex`) の項目は要求の値 (`ImageRequest`: URL・識別子・縮小の指定) と LRU の前後の鍵だけで、ビューやクロージャを持たない (本体の型を読んで確かめた。本体の要求は加工処理を付けない)。取り外しの後も鍵は残る (`indexKeysBefore` = `indexKeysAfter`) が、コレクションとセルが解放されていることが、索引がそれらを保持していないことを示す
- 規約の「保持対象の解放の確認」のうち、同時生存セル数のカウンタと弱参照プローブによるエンジンテスト (配列の置換後に同時生存が可視セル数の 4 倍未満、コレクションへの強参照を手放すとエンジンへの弱参照が nil) は本体のテストが持ち、本 change の実装の完了時に通っている (本証跡では再実行していない)

## 限界

- 10,000 件の手順どおりの往復では先読みが走らず画像が載らないため、元寸と列幅の差・索引の充足は、件数を変えた読み込み待ちの往復で見た。この往復は手順どおりの fixture ではない。数値は Sample の複製 (スクラッチ) に足した足場で採り、同じ足場をリポジトリへ取り込んだ後は Simulator で出力の形だけを確かめた (実機の数値は採り直していない)
- 索引の充足の測定器 (`ImageMemoryIndexReport`) には盲点がある。メモリキャッシュは鍵を列挙できないため、キャッシュを引く候補の縮小指定を「縮小なし」と「索引のどこかに現れた縮小指定」から集めている。そのため、ある縮小指定の鍵が索引から**すべて**失われた場合、キャッシュに残るその指定の項目は候補に現れず分母に入らないので、充足は 1.000 のまま出る (この欠落を検出できない)。今回の 60 件・600 件の値が誤りだと示すものではないが、充足 1.000 は「索引に現れた縮小指定の範囲で」の値として読む。候補を索引と独立に (fixture の列幅と表示の枠から) 作れば盲点は消えるが、本 change では作っていない
- `phys_footprint` は展開した画像の記憶域を反映していないと見られる (上の節)。iOS の計測手順のメモリ判定が画像キャッシュの増減を捉えるかは、本証跡の範囲では確かめていない
- 取得元は公開の画像サービスで、回線状態は記録していない。読み込み待ちの往復は、1 段階あたり 10 秒を超える取得を待たずに進む
- 読み込み待ちの往復は各形 Release 2 回 + Debug 1 回。10,000 件の往復は Release 2 回 + Debug 1 回
