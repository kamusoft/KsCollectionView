# 画像グリッド (Android) の手動フリック計測 — 2026-09-23 (本実装前の対照)

tasks 1.1 / 1.2 (design Decision 8 (1))。本実装の前に、Sample「画像グリッド」を到達点「メモリまで」(走行 1) と「ディスクまで」(走行 2) で固定の操作列どおりにフリックし、現状の対照を残す。完了時の計測 (Decision 8 (3)) はこの記録と比べる。iOS の対は [manual-imageGrid-ios-before.md](manual-imageGrid-ios-before.md)。

コードは main の本実装前 (提案改訂のコミット時点)。画像まわりのコードは 2026-09-17 の本実装から変わっていない。

## 走行 1: 到達点「メモリまで」

### 環境

| 項目 | 値 |
|---|---|
| 機種 / OS | Pixel 4a (基準機) / Android 13 (API 33) |
| 構成 | benchmark ビルド種別 |
| fixture | Sample「画像グリッド」(10,000 件・3 列・正方形セル、リモート画像)。Intent の追加情報 `ks_start_route=demo/ImageGrid` で直接開き、`ks_reset_image_cache=true` で起動時に画像キャッシュを空にする |
| 到達点 | **メモリまで**。Android Sample には到達点の起動引数が無いため、画面を開いた後にオーナーが画面で選んだ (初期選択「ディスクまで」で開き、「メモリまで」へ切り替え) |
| 駆動 | オーナーの手動フリック (自動化なし) |
| 記録 | 到達点を選んで待機 → `dumpsys gfxinfo <package> reset` → 合図 → 操作 → `dumpsys gfxinfo <package> framestats`。perfetto は採っていない。記録窓の実長 **84.8 秒** (出力の `Uptime` と `Stats since` の差) |
| 熱状態 | 走行の直前に thermalservice の Thermal Status 0、IsStatusOverride false を観測 (熱制限の有無そのものは確かめていない) |
| 生の framestats | スクラッチにのみ保管。change には置かない |

### 操作条件

| 項目 | 値 |
|---|---|
| 操作列 | 固定の操作列 (初回: 下向き 10 秒 → 休止 3 秒 → 再訪: 上向き 5 秒 → 連続: 下向き 10 秒)。速度は「いつもの感覚」 |
| 開始位置 / 到達範囲 | 先頭から / **未記録** |
| 段階ごとの所要 | 未記録 (gfxinfo の集計値からは段階を切れない) |
| 文字サイズ | 端末の既定 |
| キャッシュ状態 | 上書きインストール (`install -r`) + `ks_reset_image_cache=true`。走行前の uninstall が `DELETE_FAILED_INTERNAL_ERROR` で失敗したため、削除からの入れ直しではない (限界を参照) |

### オーナーの体感 (合否の主語。数値を見る前に聞き取り)

- 初回 / 再訪 / 連続 / ムラ: 体感 (滑らかさ) は問題なし
- 画像の出方 (別の観測点): 画像の表示は遅い。スクロールを止めてから **5 秒くらい** かかる

### 数値 (証跡。合否ではない。取得源は `dumpsys gfxinfo` = HWUI の描画フレーム)

| 指標 (取得源・単位) | 値 |
|---|---|
| 描画フレーム数 (gfxinfo、窓 84.8 秒) | 1,383 |
| janky frames (gfxinfo) | 40 (2.89%)。legacy 27 (1.95%) |
| フレーム時間 = 描画 1 フレームの所要時間 P50 / P90 / P95 / P99 (gfxinfo、ms) | 12 / 20 / 20 / 30 |
| 期限超過 (Frame deadline missed、件) | 40 (legacy 16) |
| Missed Vsync / Slow UI thread / Slow issue draw (件) | 0 / 19 / 33 |
| ヒストグラムの山 (gfxinfo、ms = 件) | 主の山 11 ms = 216、12 ms = 214 (10〜13 ms に 709 件)。副の山 **20 ms = 97 (7.0%)** |
| ヒストグラムの裾 (件) | 16 ms 超 255 (18.4%)、26 ms 以上 23 (1.7%)、34 ms 以上 6。最長の区分 44 ms = 1 |
| GPU のフレーム時間 P50 / P90 / P95 / P99 (gfxinfo、ms) | 8 / 12 / 13 / 14 |

### 判定

- 体感の合否: **合格** (オーナーが迷いなく「問題なし」としたため、非接続の対照は行っていない)
- 数値との一致・不一致: 20 ms の副の山 (60 Hz の期限 16.7 ms を越える) と janky 2.9% はあるが、オーナーは引っかかりとして感じていない。体感は合格、数値はこのとおりで、両方をそのまま残す
- 画像の出方: 止めてから約 5 秒。滑らかさとは別の観測点で、合否に混ぜない
- 前回との比較可否: 下の「過去の記録との比較」を参照 (比較不能)

### 限界

- 到達点の切り替え前 (初期選択「ディスクまで」) の間に、先頭付近の先読みが「ディスクまで」で走った可能性がある。走行 1 は純粋な「メモリまで」の cold ではない
- uninstall が失敗し上書きインストールで入れたため、画像キャッシュは起動引数で空にしたが、アプリデータそのもの (画像キャッシュ以外) は消えていない可能性がある
- 記録窓 84.8 秒は操作列 (28 秒) より大幅に長い。無操作の間は描画フレームがほぼ出ないため件数への影響は小さいと見込むが、窓の中の段階ごとの内訳は取れない

- 画像の出方 (別の観測点): メモリの時と変わらない (止めてから約 5 秒)

| 指標 (取得源・単位) | 値 |

| janky frames (gfxinfo) | 23 (2.32%)。legacy 23 (2.32%) |
| フレーム時間 P50 / P90 / P95 / P99 (gfxinfo、ms) | 13 / 20 / 21 / 30 |
| 期限超過 (Frame deadline missed、件) | 23 (legacy 10) |

### 限界

- 記録窓 52.0 秒は走行 1 (84.8 秒) より短く、描画フレーム数も違う (992 / 1,383)。操作量が揃っている保証は無い
- 段階ごとの所要と到達範囲は未記録

## 2 走行の対照 (tasks 1.2: 表示待ちの差)

| 観点 | 走行 1: メモリまで | 走行 2: ディスクまで |
|---|---|---|
| 滑らかさの体感 | 合格 | 合格 (走行 1 と変わらない) |
| 画像の出方 (止めてから揃うまで) | 約 5 秒 | 約 5 秒 (走行 1 と変わらない) |
| janky frames | 40 (2.89%) | 23 (2.32%) |
| P50 / P90 / P95 / P99 (ms) | 12 / 20 / 20 / 30 | 13 / 20 / 21 / 30 |
| 20 ms 区分の割合 | 7.0% | 19.0% |
| 16 ms 超の割合 | 18.4% | 31.7% |

- **表示待ちの差: なし。** 到達点「メモリまで」と「ディスクまで」で、オーナーの観測した画像の出方は同じ (どちらも止めてから約 5 秒)
- **iOS より遅い。** 同日の iOS の対 (走行 3・4) では止めてから 2〜3 秒で、Android の約 5 秒より速い。両 platform とも到達点による差は無い。ローダー・ネットワーク経路・端末が違うため、この記録から原因は言わない
- 滑らかさの体感も差なし。数値では 20 ms 区分の割合が走行 2 で高いが、窓長・フレーム数が違い操作量が揃っていないため、到達点の差に帰属させない
- 所見 (仮説。断定しない):
  - 走行はどちらも cold で、スクロール中に可視になる画像の大半は初回のネットワーク取得を待つ。取得待ちが表示待ちの主因なら、到達点の差 (先読みでデコードしてメモリに載せるか) は表に出にくい
  - 現行の Android では、到達点「メモリまで」で先読みが載せる元寸がハードウェアビットマップになり、表示側の鍵と一致せず再利用されない (本 change の動機。proposal Why)。これも「メモリまで」と「ディスクまで」の差が出ない向きに働く
  - 走行 1 は切り替え前に「ディスクまで」の先読みが走った可能性があり、純粋な対照ではない
  - どの要因が支配的かは、この記録 (gfxinfo のみ、取得・デコードの回数なし) からは切り分けられない。完了時の計測 (Decision 8 (3)) ではローダーの通知による取得・デコード回数を併記する

## 過去の記録との比較

- 2026-09-08 の Android 記録 (archive `2026-09-17-performance-criteria-review/evidence/manual-imageGrid-android-2026-09-08.md`) とは **比較不能**。理由: 固定の操作列の制定前の記録で操作が自由な順の反復であること、端末の OS 版が未記録であること、到達点が未記録であること (デモ画面の初期選択は「ディスクまで」だが、記録に残っていない)
- 同 fixture の Android で固定の操作列を使った記録は本記録が最初であり、完了時の計測はこの 2 走行と比べる
- 画像の出方については、2026-09-08 の記録にも「止めてから少し待つと揃う、iOS より数テンポ遅い」という観測がある。操作条件が揃わないため、遅さの程度を並べて比べはしない

## 両走行に共通する限界

- 体感はオーナー 1 人・各 1 試行
- 到達範囲 (通過した件数) と段階ごとの所要は未記録。gfxinfo の集計値は段階に割れない
- perfetto を採っていないため、20 ms の山や表示待ちの原因帰属 (subcomposition・取得・デコード) はできない
- 画像の出方の「約 5 秒」はオーナーの目測で、計時していない。ネットワーク状態・画像の到着タイミングは記録していない
- 画像の出方は滑らかさとは別の観測点で、合否に混ぜていない
