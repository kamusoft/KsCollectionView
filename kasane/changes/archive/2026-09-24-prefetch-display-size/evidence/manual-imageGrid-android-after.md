- **表示待ちの差: 到達点による差は観測されない。** オーナーの観測した画像の出方は、「メモリまで」「メモリまで (列幅)」「ディスクまで」で変わらない。before と同じく Android では到達点で表示待ちが変わらず、本 change で期待した「メモリまで」で先読みした項目がそのまま表示に使われる効果は、体感の画像の出方には現れていない
- 滑らかさの体感も 3 走行で差なし。数値では「メモリまで」の 2 走行で 19〜20 ms の区分が厚く (18.1% / 21.9%)、「ディスクまで」で薄い (7.3%) が、窓長・フレーム数が大きく違い操作量が揃っていないため、到達点の差には帰属させない。before でも同じ 20 ms の山が「ディスクまで」側で厚く出ており (19.0% / 7.0%)、向きが走行ごとに入れ替わっている
- 所見 (仮説。断定しない):
  - 走行はどれも cold で、スクロール中に可視になる画像の大半は初回のネットワーク取得を待つ。取得待ちが表示待ちの主因なら、到達点の差 (先読みでデコードしてメモリに載せるか) は表に出にくい。before の所見と同じ見立てで、本 change で鍵の不一致を解いても体感が変わらなかったことはこの見立てと矛盾しない
  - iOS の完了時計測 (走行 4・5) では「メモリまで」で画像が早く感じられ、Android では感じられないという platform 差がある。ローダー・ネットワーク経路・Compose の subcomposition の費用が違うため、この記録から原因は言わない。Android の表示待ちの残りの切り分け (subcomposition・cold 取得) は tasks 8.5 が行う
  - 先読みした項目が表示で引き当てられたか (取得・デコードが走らなかったか) の回数は tasks 8.2 の証跡が持つ。体感に差が出ないことが「引き当てが効いていない」ことを意味するのか「効いているが取得待ちが支配的」なのかは、この記録からは切り分けられない

#### 悪化している数値とその扱い

- **janky frames 2.32% → 3.17%、期限超過 23 → 33 件、P99 30 → 32 ms、26 ms 以上 19 → 31 件、最長の区分 57 → 69 ms (2 件)、Slow issue draw 12 → 23 件、Missed Vsync 1 → 5 件。**
- 原因仮説: (a) 本 change で表示側の引き当てを実物の寸法の許容範囲に変え、CPU の同期縮小をやめた。ディスクから表示へ上げる経路で、1 フレームに載る画像の到着・アップロードの重なり方が変わった可能性がある。(b) 走行間の揺れ。cold の走行で画像の到着が重なるタイミング (ネットワーク状態は両記録とも未記録) とフリックの速さ・回数の違いで、裾の数十件は動きうる。before の iOS 側でもコードの変わらない 2 記録の間で初回区間の hitch が 3 倍に動いた例がある。perfetto を採っていないため、どちらかは**確定していない**
- 再確認の有無: 非接続の対照も再走行も行っていない (各 1 試行)。長いフレームの帰属は tasks 8.5 (到達点 `disk` の表示待ちの切り分け) の観測で合わせて見られる
- 受容する理由: 合否の主語は体感 (cross/ADR-0006) で、オーナーは迷いなく合格 (変化は感じない) とした。悪化しているのは裾の数十フレーム (1,040 のうち 26 ms 以上が 12 件増) で、分布の本体は逆に良くなっている。本 change の目的は表示待ち (画像の出方) で、滑らかさの数値の小さな揺れを理由に差し戻す根拠は無い

1. **画面に出た時点の処理を再合成なしで終える。** 部品 (`KsShownNode`) の中で、引き当てた項目はそのまま描き続け、引き当てられなかったときはローダーへの要求も部品から出して結果を描く (状態を書かず、描画の無効化だけで済ませる)。表示中のフレームの再合成の増加 (約 2 秒 / 30 秒) を消す見込み
2. **遅らせる対象を、本当に取得中の先読みに絞る。** 先読みの取得単位の完了・取り消しを索引か先読みの窓で覚え、取り消し・失敗・追い出し済みの画像は遅らせずに組み立て時点で要求を出す。フリング中にこの経路に入る画像が減り、再合成が減る。`disk-wait-android.md` の最終ビルドの節で見えた「表示要求の開始の遅れ」(メモリまでの待ちが 0.35〜0.5 秒長い仮説) も同時に減る

#### 結論

- **「メモリまで」の悪化は解消し、比較用ビルドより良い値になった。** janky の中央値は 比較用 3.63% / 改善前の最終 4.89% / 改善後 **3.19%**。反復ごとの対では、改善後は 5 反復のすべてで改善前の最終と比較用の両方より低い。P99 の中央値は 73 / 81 / **61 ms**、Slow UI thread は 56 / 70 / **50 件**、50 ms 以上は 28 / 41 / **24 件**
- 主スレッドのトレースでは、表示中のフレームの中の再合成 (`Recomposer:recompose`) が記録窓あたり 比較用 0.58 秒 / 改善前の最終 2.67 秒 / 改善後 **0.10 秒** になった。1 フレームの主スレッドの処理 (`Choreographer#doFrame`) の中央値は 3.3〜3.4 / 5.8 / **3.8 ms** で、比較用よりわずかに長い (画面に出た時点の引き当てと要求の開始を配置の中で行う分と見ている。確かめてはいない)
- **「ディスクまで」は 3 ビルドで差が揃わない** (中央値 3.55% / 3.47% / 3.69%、反復ごとの差の向きもまちまち)。ディスクまでは画面に出る時点まで遅らせる経路に入らないため、改善の対象外で、揺れの範囲と読む
- 改善前の最終の「メモリまで」は、今回も上の節と同じ向きの悪化 (janky 中央値 4.89%、上の節では 4.26%) を再現した。比較の土俵は上の節と揃っている

改善の内容 (実装の要約):

1. 画面に出た時点の処理を部品の中で終える。先読みが取得中の画像は、画面に置かれた最初の時点で部品が引き当てをやり直し、当たればその項目を部品がそのまま描く。外れればその場で要求を出し、成功した画像も部品が描く (描画の無効化だけで、組み立て直しをしない)。読み込み中の既定の表示も部品が描く。組み立て直しが残るのは、利用者の読み込み中の表示を外すとき (その表示だけの小さな範囲) と、失敗の表示へ切り替えるときだけ
2. 遅らせる対象を、本当に取得中の先読みに絞る。先読みの要求の完了・失敗・取り消しをローダーの通知と取り消しの取っ手で捉えて、取得中の先読みを索引で数え、取得中のときだけ表示要求の開始を画面に出る時点まで遅らせる。完了・失敗・取り消し・追い出し済みの先読みは遅らせない

#### 手順

上の節の「手順」と同じ (Pixel 4a / Android 13、Wi-Fi、benchmark ビルド種別、走行ごとに入れ直し → `pm clear` → `ks_reset_image_cache=true` で cold 起動、起動 10 秒後に `gfxinfo reset` → 同じ操作列 → 2 秒後に `framestats`、記録窓の実長 29.4〜30.4 秒)。到達点 2 × ビルド 3 × 5 反復 = 30 走行。反復ごとにビルドの順を回した (1・4 反復目は 比較用 → 改善前 → 改善後、2・5 反復目は 改善後 → 比較用 → 改善前、3 反復目は 改善前 → 改善後 → 比較用)。熱状態 (Thermal Status) は 1〜2 反復目が 0、3〜5 反復目が 1 で、同じ反復の 3 走行は同じ状態。トレースは別に「メモリまで」を各ビルド 2 走行 (熱状態はすべて 1)。

生の framestats・トレースはスクラッチにのみ置き、change には集計値だけを載せる。
