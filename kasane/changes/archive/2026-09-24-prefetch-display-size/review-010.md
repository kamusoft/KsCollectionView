# レビュー結果: prefetch-display-size (010 回目)

**日付**: 2026-09-24
**判定**: APPROVED

## サマリー

review-009 の Major (iOS の包みの経路で読み込んだ画像が、メモリのみの消去の後の組み立て直しで `LazyImage` に切り替わり、ディスクから再デコードされる) の修正だけを確認した。修正は、包みを選んだ条件を `KsImageRetainedMatch` が覚え、同じ条件の間は包みを選び続ける形である (review-009 の案 2)。レビュアーのプローブと回帰テストで、指摘の経路と副次の形 (先読みの完了後に LRU で追い出されてから組み立て直す) の両方が直っていることを確かめた。条件が変わったときの選び直しも確かめた。全消去・ソース単位の削除・範囲外への枠の変化では、新しい不具合は見つからなかった。

## 確認したこと

- **ビルド・テスト (レビュアーが自分で実行。DerivedData はスクラッチ、Simulator は iPhone 16e / iOS 26.1)**: iOS パッケージは **276 tests / 0 failures** だった。回帰テスト `test先読みの取得中に待った表示が読み込んだ画像はメモリのみ消去の後に親が組み立て直されても置き換わらない` を含む
- **修正の中身**: `usesDeferredLoad(mayBeLoadingPrefetch:for:)` は、取得中の可能性があれば包みを選んで条件を覚える。可能性が無くても、覚えた条件と同じなら包みを選び続ける。条件が違えば、覚えた条件を捨てて `LazyImage` を選ぶ。条件 (`Condition`) には、ソースの識別子と削除の世代・範囲消去の世代 (`reloadToken`)・枠・表示倍率・当てはめ方が入る。`clear(.memory)` は `globalGeneration` を進めない (`KsImageCache.swift` の `.memory` 分岐) ので、条件は変わらず包みが選ばれ続ける。`.id(condition)` も同じ値なので、包みの `FetchImage` の状態は残る。アセットの経路と枠が決まらない経路では、`discard()` が覚えた条件も捨てる
- **プローブ (作業ツリーの ios パッケージをスクラッチへ複製し、既存の `KsImageCacheContractTests` の道具で 4 本足した)**: 共通の前提は次のとおりである。メモリまでの先読みを取得中に止めたまま `KsImage` を表示して包みの経路に入れる。応答を返し、表示の要求の画像が表示されてデコードが 2 回になるまで待つ

  | プローブ | 操作 | 修正あり | 修正を外した対照 (`usesDeferredLoad` が `mayBeLoadingPrefetch` をそのまま返す) |
  |---|---|---|---|
  | 全消去 | `clear(.memory)` → 組み立て直し → `clear(.all)` | 組み立て直しでデコード 2 → 2。全消去で要求 1 → 2、読み込み中の組み立て 3 → 5 (読み込み中を経由して取り直す) | 組み立て直しでデコード 2 → 3 (失敗) |
  | ソース単位の削除 | `clear(.memory)` → 組み立て直し → `remove(.remote(target))` | デコード 2 → 2。要求 1 → 2、読み込み中 3 → 5 | デコード 2 → 3 (失敗) |
  | 範囲外への枠の変化 | `clear(.memory)` → 組み立て直し (10pt のまま) → 枠を 60pt に広げる | 組み立て直しでデコード 2 → 2。広げた後は新しい枠の要求の項目が保存され、デコード 2 → 3。再ダウンロードは無い (要求 1 のまま) | 組み立て直しの時点でデコード 2 → 3 (失敗) |
  | 副次の形 (LRU) | 先読みの完了で取得中の可能性が消えた後に、ローダーのメモリだけを消す (LRU の追い出しに相当) → 組み立て直し | デコード 2 → 2 | デコード 2 → 3 (失敗) |

  回帰テストも、対照では 2 → 3 で失敗した。組み立て直しのときの読み込み中の組み立て +1 は、review-009 で両方の経路に出る雑音と判定したものと同じで、デコードと要求の回数は変わらない
- **選び直しの範囲**: 覚えるのは条件ごとである。そのため、ソースの切り替え・世代の進行・枠・表示倍率・当てはめ方の変化では選び直す。引き当てた画像 (`resolve`) の判定が先に走るので、引き当ての経路の優先順位は変わっていない。包みの中の挙動は、画面に出る時点の要求の開始で `LazyImage` と同じである。したがって選び続けても、見た目と要求の時点は変わらない
- **足場**: 修正の範囲では proposal / design / specs / tasks は変わっていない
