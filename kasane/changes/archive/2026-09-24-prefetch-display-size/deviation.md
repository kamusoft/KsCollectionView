# Deviation: prefetch-display-size

- tasks 3.4 (iOS の削除の要求): tasks では `imageID = key` / `key#世代` の形 → 実装では識別子を `KsImageIdentity` の 1 か所で求め、key なし = URL の文字列、key あり = `"ks-key " + key`、世代付き = `"ks-gen N " + 識別子` とした (Android も key ありは同じ形。世代は鍵に入れない)。理由: design Decision 9 が「具体的な文字列の形は実装に任せ、衝突しないことを契約テストで固定する」としており、`key#世代` の形は `key: "p1#1"` と衝突するため。衝突しないことは契約テストで固定 (2026-09-23)
- Requirement「Sample のデモ画面「画像グリッド」」の到達点の選択: spec は見せ方を指定していないが、4 択のセグメントでは iOS で「メモリまで (…」と切れるため、オーナー指示により両プラットフォームともメニュー形式 (現在の選択を 1 行で表示し、タップで一覧が開く) にした。文言と順序は spec のまま。理由: 選択肢の文字切れの解消 (2026-09-23)
- [付随修正] samples/android の起動時の到達点指定: Intent の追加情報 `ks_prefetch` (`none` / `disk` / `memory` / `memory-column`) を足し、画像グリッドの初期選択を起動時に決められるようにした (iOS の起動引数 `--prefetch` と対称)。理由: before 計測で到達点を画面で選び直す必要があり、選び直す前の到達点の先読みが観測に混じったため。完了時の計測 (tasks 8.1) の土俵をそろえる (2026-09-23)
- [付随修正] samples/ios の起動引数 `--prefetch` に `memory-column` を追加。理由: tasks 6.6 / 8.1 で「メモリまで (列幅)」から起動するため (2026-09-23)
- design Decision 3 (Android の鍵の形): design では「`ks#scale` は付けない」 → オーナー指示により、`KsImage` が出す**表示の縮小要求の鍵にだけ**当てはめ方 (fit / fill) を付ける。幅つきの先読みの鍵は `coil#size` のまま。理由: 表示の縮小要求の鍵が「識別子 + `coil#size`」だけだと、引き当てで範囲外と退けた先読みの項目や別の当てはめ方の項目がローダーのメモリで同じ鍵に当たり、Scenario「大きすぎる項目は使わない」「小さすぎる項目は使わない」が Android で破れるため (review-001)。先読みの項目の引き当ては索引経由なので影響しない (2026-09-23)
- [付随修正] samples/ios・samples/android の doc コメントに残っていた ADR 参照 (comment-policy-lint の要確認) を整理する。オーナー指示で本 change に同梱。理由: Sample の画像グリッド周辺を本 change で触っており、同じファイル群の規約逸脱を残さないため (2026-09-23)
- [付随修正] samples/ios/KsCollectionViewSamples/ImageGridDemoView.swift の doc コメント冒頭の文のつながり (「プリフェッチの到達点を / 形 (到達点と表示幅) を」) を直した。理由: 本 change で到達点の選択を「形」に広げた際の書き換えの残り (2026-09-23)
- design Decision 3 / tasks 6.4 (索引の刈り込み): design には「消去以外では索引から消さず上限つき LRU に任せる」と「引き当て時にキャッシュに無かった鍵はその場で索引から外す」の両方があり、tasks 6.4 は「キャッシュに無い候補の破棄」 → オーナー指示により**刈り込みをやめ**、索引から消すのは `clear` / `remove` と LRU の上限だけにする (キャッシュに無い候補はその回の引き当ての候補にならないだけで、索引には残す)。理由: 刈り込むと、速いスクロールで先読みの完了前に表示が照会した鍵が外れ、先読みの完了後も引き当てられずディスクから再デコードになる (second-opinion-code-004)。代償の死んだ鍵への問い合わせは URL あたり数件で design の Risks の許容範囲 (2026-09-23)
- Requirement「プリフェッチの表示幅」: spec は有限かつ正の固定幅をすべて有効とする → 実装ではデコードの目標幅を両プラットフォームとも 16384 px で頭打ちにする (不正入力扱いにはしない)。理由: `Int` への変換で停止しないため (second-opinion-code-003)。元寸より大きい指定は拡大しないため、16384 px を超える元画像を 16384 px 以上で宣言した場合だけ、載る項目が宣言より小さくなる (2026-09-23)
- design Decision 2 (範囲内の項目があればローダーへ要求を出さず、その項目を表示の完了状態として描く) の実現時点: design は `KsImage` の組み立て時の引き当てだけを想定 → 実機検証 (evidence/device-image-match-ios.md) で、コレクションが画面外のセルを前もって組み立てる時点 (iOS の UIKit のセル先行組み立て、Android のフリング時の先行合成) では先読みが未完了で外れ、画面に出る時点で試し直さないため Scenario「メモリ到達点の後の表示」が破れていた。オーナー指示 (A) により、**まだ引き当てていない `KsImage` は画面に出る時点でもう一度引き当てを試し、外れたときだけ表示の要求を出す**。利用者から見える差: 引き当てられなかった表示は、要求の開始が画面に出る時点になる (iOS は、同じ識別子の到達点 memory の先読みが取得中の可能性があるときだけ画面に出る時点の再照会の包みを通し、それ以外は組み立て時に直接 `LazyImage` を置く — `LazyImage` はもともと画面に出る時点で開始。Android は、その識別子の到達点 memory の先読みが取得中のときに限り遅らせる (完了・失敗・取り消し済みは遅らせない。性能改善サイクルで索引の条件から取得中の条件へ絞った — evidence/manual-imageGrid-android-after.md の再確認)。画面に出る時点の引き当て・要求の開始・成功の描画は再合成なしで行う)。理由: spec の Scenario を実機で満たすため (2026-09-23)
