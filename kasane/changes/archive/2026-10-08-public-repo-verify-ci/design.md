# Design: public-repo-verify-ci

## Context

フェーズの議論 (`kasane/roadmaps/v1-foundation/phases/phase-7-1-public-repo-verify-ci/agenda.md`) で決めたことを実物にする。方向の決定は ADR にある。

| 決定 | ADR |
|---|---|
| 今の履歴を書き換えずにそのまま公開する | cross/ADR-0009 |
| ブランチを `develop` と `main` の 2 本に分ける | cross/ADR-0010 |
| 貢献は Issue で受け、外部からの Pull Request は受け付けない | cross/ADR-0011 |
| MIT License で提供する | cross/ADR-0012 |
| 検証 CI の緑が保証する範囲 | cross/ADR-0013 |

本書が決めるのは、その方向を実現する形である。下敷きは兄弟ライブラリ KsSettingsView の実物 (`../KsSettingsView/.github/`) と、その変更で実装中に見つかった落とし穴 (`../KsSettingsView/kasane/changes/archive/2026-08-31-add-verification-ci/deviation.md` とレビュー) である。

兄弟ライブラリと違う点が 3 つある。履歴を引き継いで公開する。Sample のビルドとユニットテストを CI に載せる (兄弟ライブラリは載せていない)。ブランチの役割を最初から 2 本で始める (兄弟ライブラリは後から整理した)。

### 置くファイル

| ファイル | 中身 |
|---|---|
| `LICENSE` | MIT License の標準の文面。著作権の行は `Copyright (c) kamusoft` |
| `README.md` / `README_ja.md` | 準備中の案内。ライブラリの 1 行の説明、公開物がまだ無いこと、ライセンス、貢献の案内への導線。2 枚は同じ構成にする |
| `.github/ISSUE_TEMPLATE/bug_report.yml` | バグ報告。必須: 版 / プラットフォーム (iOS・Android から選ぶ) / 再現手順 / 実際の挙動 / 期待した挙動 |
| `.github/ISSUE_TEMPLATE/feature_request.yml` | 提案。必須: 解決したい課題 / 今どう困っているか / 考えた選択肢 |
| `.github/ISSUE_TEMPLATE/question.yml` | 質問。必須: 版 / プラットフォーム / 試したこと / 読んだ文書の箇所 |
| `.github/ISSUE_TEMPLATE/config.yml` | 空の Issue を作れなくする。外部への案内のリンクは置かない |
| `.github/CONTRIBUTING.md` / `CONTRIBUTING_ja.md` | 貢献方針 (外部の Pull Request は受けず、Issue で受ける) と、Issue の書き方 |
| `.github/workflows/ci.yml` | 検証 CI の入口 |
| `.github/workflows/verify-ios.yml` / `verify-android.yml` | プラットフォーム別の再利用 workflow |
| `scripts/ci/` | 検査のスクリプトと、そのテスト (Decision 3) |

Issue のフォームは英語で書き、本文は英語でも日本語でもよいと冒頭で案内する。フォームのラベルは `bug`・`enhancement`・`question` で、GitHub が新しいリポジトリに最初から作るものを使う。

lint のジョブに入れる検査は、secret・ローカル絶対パス・個人を特定する値・コメントの規約と、`main` 宛ての Pull Request の出どころの確認である。文書の構造の検査は入れない (hook にも登録していない検査で、`kasane/` だけの push では CI を起動しないため)。

## Goals / Non-Goals

Goals:

- 公開してよい状態であることを確かめてから公開し、確かめた内容を証跡に残す
- `develop` への push と `main` 宛ての Pull Request で、決めた範囲の検証が走り、失敗が失敗として見える
- 検査が黙って空振りしない (実行 0 件・走査の対象が空・期待した結果のファイルが無い、をすべて失敗にする)
- 検査の異常系を、公開リポジトリに壊れた commit を push せずに確かめられる

Non-Goals: proposal.md の Non-Goals と同じ。

## Decisions

### Decision 1: 検証 CI は、プラットフォーム別の再利用 workflow と入口 1 本で構成し、検査の名前を固定する

**採用案:** iOS と Android の検証を、それぞれ他の workflow から呼べる workflow (`workflow_call`) にする。入口の `ci.yml` がこの 2 本を呼び、lint のジョブを自分で持つ。検査の名前は `lint`・`ios / verify`・`android / verify` の 3 つに固定し、呼ぶ側と呼ばれる側の両方で名前を明示する。

入口が走る時点は 2 つ。`develop` への push と、`main` 宛ての Pull Request である。同じブランチまたは同じ Pull Request の新しい実行は、走っている古い実行を打ち切る。

`develop` への push に限り、`kasane/` 配下・Issue のフォーム・貢献の案内だけを変えた push では起動しない。`main` 宛ての Pull Request では、変更したパスで絞り込まない。

**理由:** リリースの workflow (phase-7-4) が、同じ検証を手順の二重持ちなしで呼べる。検査の名前は `main` の保護の必須の検査が参照するので、名前が変わると保護が壊れる。`main` 宛ての Pull Request でパスを絞ると、必須の検査が走らないまま通る経路ができる。`develop` は必須の検査を持たないので、その心配が無い。

**代替案:**
- **A: 入口 1 本に手順を直に書く** — リリースの workflow から同じ検証を呼べず、手順を写すことになる。
- **B: プラットフォームごとに別の入口を持ち、変更したパスで起動を分ける** — 片方しか走らない Pull Request で、もう片方の必須の検査が満たされない。必須から外すと、検証を通らないまま `main` に入る経路ができる。

### Decision 2: Sample の検証は、プラットフォームの検証と同じジョブの中で、本体のテストの後に走らせる

**採用案:** `ios / verify` は、本体のテスト全件の後に、iOS Sample のビルドとユニットテストを走らせる。`android / verify` も、本体のテスト全件の後に、Android Sample のビルドとユニットテストを走らせる。本体のテストが落ちても Sample の検証は走らせ、どちらかが落ちればジョブを失敗にする。

iOS Sample は、通常の検証のスキームをユニットテストのターゲットだけに絞って実行する。Android Sample は、アプリのモジュールだけを対象にし、計測用のモジュールは対象にしない。

**理由:** 必須の検査を 3 つのまま保てる。macOS のランナーの起動と、依存の取得が 1 回で済む。本体が落ちた回でも Sample の状態が分かる。

**代替案:**
- **A: Sample を別のジョブにして並列で走らせる** — 壁時計は短くなる。しかし必須の検査が 5 つになり、macOS のランナーをもう 1 台起動して、本体のビルドを二重に行うことになる。
- **B: 本体のテストが落ちたら Sample を走らせない** — ランナーの時間は減る。しかし本体と Sample の両方が壊れているとき、片方を直すまでもう片方が見えない。

### Decision 3: 検査のロジックは workflow に直に書かず、スクリプトに置いて手元でテストする

**採用案:** 次の 6 つを `scripts/ci/` のスクリプト (Python) にし、workflow はそれを呼ぶだけにする。スクリプトには、正常と異常の両方を確かめる自動テストを付ける。テストは lint のジョブと手元の両方で流す。スクリプトは Python の標準のライブラリだけで書き、ランナーに追加の導入をしない。

| スクリプトの役割 | 異常として失敗にするもの |
|---|---|
| iOS のテストの実行件数を確かめる | ログが無い / 集計の行が無い / 実行が 0 件 |
| Android のテストの実行件数を確かめる | 期待したタスクの結果のファイルが無い / 実行が 0 件 |
| 使う Simulator を選ぶ | 使える iPhone の Simulator が無い |
| `main` 宛ての Pull Request の出どころを確かめる | 別のリポジトリ (fork) からの Pull Request / `develop` 以外のブランチからの Pull Request |
| workflow の定義を確かめる | commit の ID で指定していない外部の action / 最新を指す名前のランナー / 読み取り以外の権限 |
| コマンドを流して、出力を記録に残す | 流したコマンドの失敗 (失敗をそのまま返す。記録を残す処理に隠れて成功に見えることを防ぐ) |

**理由:** 兄弟ライブラリは、これらを workflow の中に直に書いた。その結果、レビューで件数の抽出の誤り・期待の集合が静かに縮む誤り・異常系が確かめられていない点を指摘されている。公開リポジトリでは、異常系を確かめるために壊れた commit を push したくない。スクリプトにすれば、手元で異常系を確かめられる。

**代替案:**
- **A: workflow に直に書く (兄弟ライブラリの形)** — ファイルが増えない。しかし異常系を確かめるには、CI の上で実際に失敗させるしかない。

スクリプトのテストは数秒で終わる小さなもので、テスト 4 系統 (cross/ADR-0008) とは別に数える。

### Decision 4: 実行件数は、決めた集合について確かめる

**採用案:** iOS は、本体と Sample のそれぞれの実行について、`xcodebuild` の出力の集計の行から件数を読む。Android は、テストの結果のファイルを、workflow が明示して渡す「モジュールとタスクの組」ごとに集計する。組は、本体のデバッグのユニットテストと、Sample のアプリのデバッグのユニットテストの 2 つ。

どちらも、その実行で作られた記録だけを読み、スキップされたテストを除いて数える。Android は実行の前に結果の置き場を空にする。

Android は、テストのソースにあるテストのクラスの集合を導き、結果のファイルに現れないクラスがあれば失敗にする (`kasane/handbook/cross/test-execution.md` が手元の確認に求めていることを、機械で行う)。導いた集合が空のときも失敗にする。iOS は、クラスごとの突き合わせを合否にしない。クラスごとの内訳を出力から読むと、文書に無い書式に頼ることになるためで、内訳は概要に出すだけにする。

**理由:** 手元の完了判定 (`kasane/handbook/cross/test-execution.md`) と同じ読み方なので、CI と手元で件数の意味が揃う。期待の集合を明示すると、集合が縮んだときに失敗として見える。

**代替案:**
- **A: Android の期待の集合を、ビルドの定義から自動で導く (兄弟ライブラリの形)** — モジュールが増えても追随する。しかし導き方を誤ると、集合が静かに縮んだまま緑になる。本リポジトリのモジュールは 2 つで、増える予定が無い。
- **B: iOS の件数を、テスト結果のバンドルから読む** — ログの書式に頼らず、クラスごとの突き合わせもできる。しかし読み出すツールの出力の形が Xcode の版で変わってきた経緯があり、手元の手順とも読み方が分かれる。
- **C: 件数が 0 でないことだけを確かめる (兄弟ライブラリの形)** — 作りが小さい。しかし一部のクラスだけが走った状態と、全件がスキップされた状態を通してしまう。

### Decision 5: Xcode は版を決めて選び、Simulator は実行のときに選ぶ

**採用案:** iOS のジョブは、ランナー `xcode-27` の上で、決めた版の Xcode (27.0) を明示して選ぶ。その版が無ければ失敗にする。Simulator は、使える iPhone のうち OS が最も新しいものを、実行のときに選ぶ。

**理由:** Xcode の版は検証の前提なので、黙って別の版で走ることを防ぐ。Simulator の機種の名前はランナーのイメージの更新で変わるので、名前を固定すると壊れる。

**代替案:**
- **A: Simulator の機種と OS を固定する (手元の手順の形)** — どの機種で走ったかが毎回同じになる。しかしランナーのイメージが更新されると、その機種が無くなって CI が落ちる。

### Decision 6: Android のテストは、デバッグのユニットテストだけを走らせる

**採用案:** Android は、本体と Sample とも、デバッグのユニットテストのタスクを走らせる。Sample はあわせてデバッグのアプリを組み立てる。

**理由:** 手元の完了判定と同じタスクなので、CI の緑と手元の緑の意味が揃う。

**代替案:**
- **A: リリースのユニットテストも走らせる (兄弟ライブラリの形)** — 最適化後の差を拾える可能性がある。しかし時間がおよそ 2 倍になり、手元の完了判定が見ていないものを CI だけが見ることになる。

### Decision 7: 使う道具は版を固定し、権限は読み取りだけにする

**採用案:**

- ランナーは版を指定する (`ubuntu-24.04`・`xcode-27`)。`latest` の付く名前は使わない
- Android の検証は JDK 21 を使う (手元と同じ)
- 外部の action は commit の ID で固定し、対応する版をコメントに書く
- gitleaks は、版と配布物のチェックサムを固定して取得し、チェックサムが合わなければ失敗にする。gitleaks の公式の action は使わない (Organization の下では別途ライセンスの鍵が要るため)
- gitleaks は、追跡中の内容を取り出した先を走査する。取り出しに失敗したら、走査の前に失敗にする
- workflow の権限は、リポジトリの内容の読み取りだけにする
- ジョブには時間の上限を置く。値は、公開後の最初の数回の実測から余裕を取って決める

**理由:** タグは後から付け替えられる。走査の対象が空のまま緑になる経路を塞ぐ。検証 CI は何も書き込まない。

**代替案:**
- **A: action をタグで指定する** — 更新は楽になる。しかしタグが付け替えられると、確かめていないコードが走る。

### Decision 8: 公開の当日は、`main` だけを非公開で push して目で確かめ、public にしてから `develop` を push する

**採用案:** 実装は `develop` (本変更の前の `main` から切る) に載せ、`main` は本変更の前の先端のままにしておく。公開の当日は次の順で進める。

1. 公開前の確認 (Decision 10) がすべて通っていることを確かめる
2. GitHub に非公開でリポジトリを作り、`main` だけを push する
3. オーナーが GitHub の画面で中身を目で確かめる
4. public に切り替える
5. 機能の設定・Pull Request を作れる人の制限・secret の検査と push の保護を入れる (Decision 9)
6. `develop` を push する。検証 CI がここで初めて走る
7. 検証 CI が緑になったら、`main` と `develop` の保護を入れる
8. `develop` から `main` へ Pull Request を作り、必須の検査が緑になったら merge commit でマージする。lint の記録に、出どころを確かめた結果が出ていることを確かめる

2・4・5 と 7・8 は、それぞれ実行の前にオーナーの承認を得る。

**理由:** 非公開の間に push するのは `main` だけで、そこには workflow が無いので、非公開の利用枠を使わない。目で確かめる機会を public の前に持てる。8 の Pull Request が本変更そのものを運ぶので、`main` 宛ての Pull Request の経路を、作り物でない変更で確かめられる。

出どころの確認の異常系 (`develop` 以外からの Pull Request が落ちること) は、GitHub の上では確かめない。確かめるための Pull Request は、閉じても公開リポジトリに残るためである。異常系はスクリプトのテストで確かめ、8 では確認が実際に走ったことを記録で確かめる。

**代替案:**
- **A: 最初から public で作り、2 本のブランチを同時に push する** — 手順が短い。しかし公開の前に目で確かめる機会が無く、`main` と `develop` が同じなので、`main` 宛ての Pull Request の経路を確かめられない。
- **B: 非公開のまま検証 CI まで確かめてから public にする** — 公開の前に CI の不具合を直せる。しかし macOS のランナーが非公開の利用枠を使い、Free プランでは非公開のリポジトリにブランチの保護を入れられない。

### Decision 9: GitHub の設定は `gh` で入れ、入れた直後に読み直して証跡に残す

**採用案:** 設定は指揮側が `gh` のコマンドで入れる。入れた直後に同じ項目を読み直し、下の表と突き合わせて、コマンドと読み直しの結果を証跡 (`evidence/`) に残す。繰り返し適用するための道具は作らない。

| 設定 | 値 |
|---|---|
| 公開の範囲 | public |
| 既定のブランチ | `main` |
| Issues | 有効 |
| Wiki・Discussions・Projects | 無効 |
| Pull Request を作れる人 | 共同作業者だけ |
| secret の検査・push の保護・依存の脆弱性の通知 | 有効 |
| ラベル | `bug`・`enhancement`・`question` がある |
| `main` の保護 | Pull Request を必須にする (承認の必須の数は 0)。必須の検査は `lint`・`ios / verify`・`android / verify` (GitHub Actions が出した検査に限る)。強制 push と削除を禁じる。管理者には強制しない |
| `develop` の保護 | 強制 push と削除を禁じる。必須の検査は持たない |

**理由:** 設定は一度入れれば変わらない。兄弟ライブラリも同じやり方で、手順と値を handbook に持っている。

**代替案:**
- **A: 設定の適用と確認をスクリプトにする** — 後から何度でも確かめ直せる。しかし 1 度しか使わない道具の維持が増える。要るようになった時点で足せる。
- **B: オーナーが GitHub の画面で入れる** — エージェントに権限を渡さずに済む。しかし入れた値の記録が残らず、入れ忘れに気付きにくい。

### Decision 10: 公開前の確認は 5 つで、履歴に残る画像は取り出して目で見る

**採用案:** push の前に、次の 5 つを確かめて証跡に残す。1 つでも通らなければ公開せず、オーナーに諮る。

| 確かめること | 通る条件 |
|---|---|
| 作者とコミッターのメールアドレス | 全 commit で noreply だけ |
| 履歴の中身の、個人を特定する値とローカル絶対パス | 標準の検査 (`scripts/git-gate-lint.py`) で 0 件。この検査は merge commit と最初の commit を数えないので、その 2 つは下の手順で別に確かめる |
| コミットメッセージ | ローカル絶対パスとメールアドレスが 0 件 |
| gitleaks | merge commit を含む全履歴の走査で検出 0 件 |
| 履歴に残る証跡の画像 | 全件を取り出して目で見て、画面内に個人の情報が無い |

merge commit は、どちらの親とも違う内容を持つファイルを、リポジトリの中の一時の場所に取り出して、同じ 2 つの検査に掛ける。個人を特定する値の検査は場所で範囲を決めるので、`kasane/` の下に取り出す。先に、わざと違反を置いたファイルで検出できることを確かめる。取り出したファイルは検査の後に消す。この手順は提案の段階で 1 度試してある (`evidence/proposal-checks.md`)。

画像は、履歴から一時の場所に取り出して見る。証跡には、見た件数・見た観点・結果だけを書き、画像は置かない。見る観点は、端末の名前・通知・アカウントの名前・メールアドレス・位置の情報である。

**理由:** 公開は取り消せない。フェーズの議論の時点で 4 つは 0 件と確かめてあるが、その後も commit が増えるので、公開の直前に掛け直す。

**代替案:**
- **A: 画像の目視を抜き取りで行う** — 手間は減る。しかし見ていない画像に個人の情報が写っていても気付けない。

## Risks / Trade-offs

- **`xcode-27` のランナーは public preview である** → 順番待ちや不調で CI が止まり得る。止まったときに `main` 宛ての Pull Request を進める手段は、管理者による迂回だけになる。正式なラベルが出たら切り替える
- **CI の Simulator の負荷で、iOS の本体のテストが不安定になり得る** → 本体のテストは条件が満たされるのを待つ形で書いてある (`kasane/handbook/cross/test-execution.md`) が、兄弟ライブラリでは 1 度タイムアウトが起きた。起きたらテストの側を直す
- **lint が Linux で初めて走る** → 兄弟ライブラリでは、検査の範囲が Linux と macOS で違って誤検出が出た。公開の前に Linux のコンテナで流して手元と比べる。コンテナを使えないときは、公開の後の最初の実行で確かめて `develop` の上で直す (tasks の 5.3)
- **`kasane/` だけの push では CI が起動しない** → その push に lint の違反があっても、CI が見つけるのは次に起動した回になる。公開リポジトリでは push した時点で公開されるので、本命は手元の commit 時と push 時の検査である
- **依存の版が実行ごとに動き得る** → iOS の依存 (Nuke) は範囲で指定しており、解決の結果のファイルは追跡していない。新しい版が出ると、コードを変えていないのに CI が落ち得る
- **Linux のランナーに、コンパイル対象の Android SDK が入っていない可能性がある** → 入っていなければ取得の手順を足す (tasks の 4.3)
- **管理者は `main` と `develop` の保護を迂回できる** → 開発者が 1 人で、止まったときの逃げ道が要るため受け入れる。デルタスペックも、保護を「入っている設定」として約束し、管理者に対する禁止は約束しない
- **iOS では、一部のクラスだけが走った状態を CI が機械では見つけない** → 件数とスキップの件数が概要に出るので、前の回との差で人が気付ける。手元の完了判定の件数の確認が本命である

## Migration Plan

1. 提案の commit の後の `main` から `develop` を切り、以後の作業を `develop` に載せる
2. ファイル・スクリプト・workflow を `develop` に実装し、手元と Linux で確かめる
3. 公開前の確認を行う
4. Decision 8 の順で公開する
5. 作業用のブランチと worktree の基点を `develop` に切り替える

戻し方: 公開の前なら、`develop` を消して `main` に戻るだけで元に戻る。public に切り替えた後は、公開された内容を取り消せない。検証 CI の不具合は `develop` の上で直す。
