## 指摘事項

### 🔵 Suggestion コードの塊をまとめて貼ると、確かめで止まらず、問いが続く行を値として読む

**該当箇所**: `kasane/changes/release-pipeline/drafts/release-procedure.md:182`〜`:194`
**問題点**: `head -1 "$key_file"` (`:185`) は目で見る確かめで、塊をまとめて端末に貼ると、1 行目が `PUBLIC` でも次の行の `gh secret set SIGNING_KEY` が続けて走る (「PUBLIC なら登録しない」はコメントで、止める仕組みではない)。また、続く `gh secret set SIGNING_KEY_ID` などは問いで値を待つので、まとめて貼ると、貼った残りの行 (`gh secret set SIGNING_PASSWORD …` など) が問いへの入力として読まれ、secret の値として登録されるおそれがある (このレビューでは実物で確かめていない)。後者は直す前の塊にもあった形だが、`:170` で「問いに何行も貼らない」と書いた直後の塊が、まとめて貼ると同じことを起こす形になっている。オーナーが手順を写して貼る使い方をすると、直しの狙い (登録の前に止まる) が効かない。
**推奨修正**: 塊の前に「1 行ずつ打つ (まとめて貼らない)」を 1 文足す。あわせて、確かめを止める形にしたいなら、`:185`〜`:186` を `head -1 "$key_file" | grep -q 'BEGIN PGP PRIVATE KEY BLOCK' && gh secret set SIGNING_KEY … < "$key_file"` のように、1 行目が合うときだけ登録する形にする。

### 🔵 Suggestion 秘密鍵が手元のファイルに書かれ、`trash` の後もゴミ箱に残る

**該当箇所**: `kasane/changes/release-pipeline/drafts/release-procedure.md:183`〜`:187`・`:196`
**問題点**: 直す前の例はパイプで流しており、秘密鍵はディスクに書かれなかった。直した後は `mktemp` のファイルに書かれ、`trash` はゴミ箱へ移すだけなので、ASCII armor の秘密鍵がゴミ箱に残る。鍵はパスフレーズつき (`SIGNING_PASSWORD` を別に登録する) なので害は小さく、deploy key の `trash "$key_dir"` (`:193`。パスフレーズなしの鍵) も同じ形で前からある。ただ、草稿は「登録の後に `trash` で消す」と書いており、消えたと読める。
**推奨修正**: `trash` の後もゴミ箱に残るので、登録が済んだらオーナーがゴミ箱から消す、の 1 文を足す (ゴミ箱を空にするのはオーナーの操作)。または、ファイルに書かずに確かめる形 (`gpg … | head -1` で確かめ、同じパイプで登録する) を例にし、ファイルで確かめるのは控えのファイルから登録するとき (`:196`) に限る。

## アクションプラン

2. (Suggestion) `trash` の後もゴミ箱に残ることを書くか、`SIGNING_KEY` の例をファイルに書かない形に戻す
