# Proposal: library-default-colors-dark-mode

## Why

利用者が色や表示を指定しないときにライブラリが使う色 (既定の色) のうち、ライブラリが自前の値を持つものが、ダークの表示モードに合っていない。Sample にライト / ダークの切り替えを入れたときに見えるようになった (`sample-dark-mode-toggle`)。

- list の区切り線は、両プラットフォームとも固定値 1 つで、ダークでも明るい線のまま残る (core/ADR-0010 がダークを考えていなかった)
- 画像の読み込み中・失敗の既定の表示は、iOS が OS の灰色を借りていてダークに追随し、Android は固定の灰色でダークでも明るいまま残る (オーナーの目視で問題と判断、2026-09-26)。値はライトでも両プラットフォームで違う

あわせて、項目をタップしたときの色の宿題を片づける。同じ値を渡しても両プラットフォームで濃さが違い、Sample「リスト」は両プラットフォームに違う値を渡している。文書には「Android では半透明の色が見えなくなる」と書かれていたが、探索で波紋の実装を読んだところ成り立たないと分かり、提案の段階でエミュレータの画素で確かめた (Android 16 で、不透明な色とその 15% の色を渡したときの押している間の見え方が一致。`evidence/proposal-probes.md`)。統一の方向は後続の変更で決めることになっていた (android/ADR-0003 の帰結)。

## What Changes

- **既定の色をライト / ダーク 2 組にする** (core/ADR-0036。core/ADR-0010 の色の項の一部改訂): ライブラリが自前の値を持つ既定の色を、ライト用とダーク用の 2 組の固定値で持つ。利用者が指定しないときだけ、描くときの表示モードの側の値を使う。値はライト・ダークとも両プラットフォームで同じにする
  - list の区切り線: ライトは今の値のまま。ダークの値を足す
  - 画像の読み込み中・失敗の既定の表示 (読み込み中の無地、失敗の下地と印): 両プラットフォームとも同じ値の 2 組にする。iOS は OS の色を借りるのをやめる。Android はライトの灰色もわずかに変わる
  - 値の正は承認 mock の色の表 (`ui/brief.md`)。出どころは iOS の標準の灰色で、画像の 3 つの値は iOS 17.5〜27.0 のシミュレータで実測して確かめた (`evidence/proposal-probes.md`)
- **表示モードの決め方**: iOS は一覧や画像が置かれた場所の外観 (アプリが上書きした外観を含む) で、OS が解決する。Android は一覧や画像が置かれた画面の構成の夜間モード (`isSystemInDarkTheme()` が返す値) で、スクロールインジケータと同じ判定にする。通常は端末の表示モードに追随し、アプリが画面の構成を上書きしたとき (Sample の外観の切り替えがこの形) はその値になる。Material のテーマの配色は判定に使わない
- **表示中の切り替え**: 表示中に表示モードが切り替わると、既定の色で描いている区切り線と画像の既定の表示はその場で追随する。切り替えだけでは、画像の進行中の取得を取り消さず、取得し直さない
- **利用者が指定したものは変えない**: 指定した区切り線の色と、差し替えた読み込み中・失敗の表示に、ライブラリは手を加えない (iOS で外観で値の変わる色を指定したときの今の挙動も変えない)。公開 API の型・名前・引数は変えない (ライト / ダークの対を表す型は足さない)
- **タップしたときの色** (core/ADR-0037): ライブラリの挙動は変えない。iOS は渡した色をそのまま塗り、Android は標準の波紋に渡す (色みだけが使われ、濃さは標準)。両プラットフォームの濃さをそろえる加工はしない
- **公開 API の説明**: 区切り線の色・画像の既定の表示・タップしたときの色の doc コメントに、既定の色が表示モードで変わること、Android の判定元、タップの色の濃さの決まり方 (両プラットフォームで近い見え方にするには半透明の色を渡す) を書く
- **Sample**: デモ画面「リスト」のタップしたときの色を、両プラットフォームで同じ値 (アクセントに同じ不透明度を掛けた値。不透明度は `ui/brief.md` の承認の記録) にする。ほかの画面は変えない (区切り線「既定」と画像の既定の表示は、ライブラリの変更がそのまま見える)
- **検証**: Scenario ごとの自動テスト (両プラットフォームのライブラリ)。既定の色は、ライト / ダークそれぞれの値をテストに固定する。Sample の見え方は、両プラットフォーム × ライト / ダークで mock と照合する。Android のタップの色は自動テストで描けないため、エミュレータの証跡で確かめる

影響する能力: collection-layout (区切り線の既定の色) / image-loading (画像の既定の表示の色) / collection-interaction (タップしたときの色の濃さの決まり方) / samples (デモ画面「リスト」のタップしたときの色)

## Non-Goals

- **読み込み中のインジケータ・Pull to Refresh の、指定しないときの色** — core/ADR-0035 のまま変えない。却下理由 3 つのうち 2 つ (指定しない一覧の見え方が変わる・色がライブラリ独自になる) が今も成り立つと探索で確かめ、オーナーが従うと判断した
- **タップしたときの色の意味を両プラットフォームでそろえる** (Android を変える / iOS を変える) — core/ADR-0037 で却下した。Sample の目視で濃さの違いが受け入れられないと分かったら、同 ADR の Revisit When に従って決め直す (設計判断を要する)
- **画像の失敗の印の形をそろえる** (iOS は写真のアイコン、Android は四角と丸) — 色ではなく形の話で、別の設計判断を要する
- **Android の並べ替えの持ち上げの影** — 既定の色ではなく持ち上げの見せ方の話で、ダークでの見え方を誰も見ていない。確認の目視のついでに見て、気になれば簡易起票する (別の能力)
- **Android で、利用者が表示モードを渡せる入口** — Android だけの公開 API が増えるため、探索で採らなかった (設計判断を要する。core/ADR-0036 の Revisit When)
- **画像の既定の表示の色だけを変える設定** — 表示ごと差し替える口が既にある。色の設定を足すのは別の機能追加で、設計判断を要する
- **iOS で、外観で値の変わる色を色の設定に渡したときの追随** — 提案の段階の実測で、iOS 17.5 では SwiftUI の色から変換した時点でライトの値に固定されると分かった (iOS 18.6 以降は保たれる。`evidence/proposal-probes.md` の 4)。利用者が指定した色の扱いの話で、直し方に設計判断を要するため、この変更では今の挙動のままにする (別の change `ios-adaptive-color-settings-before-ios-18` に簡易起票した)
- **iOS の「コントラストを上げる」設定への追随** — 固定値にする帰結として受け入れた (core/ADR-0036。区切り線は今も同じ状態)
- **利用者向けドキュメント (Agent Skills)** — まだ存在せず、配布のフェーズで作る。今回は doc コメントだけを書く

## Impact

- 公開 API の型・名前・引数の変更は無い。指定しないときの見え方が変わる: ダークの区切り線 (両プラットフォーム)、ダークの画像の既定の表示 (Android)、ライトの画像の既定の表示の灰色 (Android、わずか)。iOS の画像の既定の表示は、借りていた OS の色と同じ値を自前で持つので見え方は変わらない
- 外部の利用者はまだいない (git の tag は 0 件、配布のフェーズは未着手)。告知や互換の手当てはしない
- 両プラットフォームのライブラリ (区切り線の既定の色、画像の既定の表示) と、両 Sample のデモ画面「リスト」に触る
- Sample の見え方: ダークで、区切り線「既定」が暗い線になり、Android の画像の読み込み中・失敗が暗い灰色になる。「リスト」のタップの色は、iOS が今より少し薄くなり (渡す不透明度を下げるため)、Android は変わらない (渡した色の不透明度が見え方に効かないため)
- 既存のテストのうち既定の色と比べているもの (Android は画素の比較、iOS は同じオブジェクトであることの比較) は、表示モードを明示して比べる形に直す
- リスク: Android の画像の読み込み中の色は 2 か所で描いている (組み立てた表示と、描く段階の処理)。片方だけ直すと、先読みの完了を待つ間だけ明るい色が出る。Scenario とテストで両方を押さえる
- リスク: Android で、画面の構成を変えずに Material の配色だけでダークにするアプリでは、既定の色がアプリの見た目とずれる。スクロールインジケータで受け入れ済みの制限と同じで、doc コメントに書く (画面の構成を上書きするアプリには追随する)
- リスク: Sample のダークは紺寄りの配色で、灰色の区切り線が無彩色に浮いて見える可能性がある。mock の承認で確かめる
- 区切り線のダークの値は、iOS 26 までの OS の区切り線の不透明な値と同じである。実測で、iOS 27 では OS 自身の値が変わっていると分かった。ライブラリは固定値で持つので OS の版には左右されないが、「iOS の今の区切り線と同じ色」にはならない (mock に並べて見比べられるようにした)
- リスク: Android の波紋の実測は Android 16 のエミュレータだけで、最低対応の Android 10・11 では測っていない (システムイメージが無かった)。不透明度を置き換える処理は OS の版によらない Compose の側にあるので結論は変わらない見込みだが、濃さの値は版で違いうる
- 性能検証は今回行わない (オーナー判断の例外、2026-10-06)。handbook/android/performance-verification の適用範囲は「区切り線の経路に触れる変更」を対象にしており、Android の区切り線の既定の色を変えるこの変更は文面どおりなら対象に入る。例外にした理由: 項目ごとの仕事量を変えない (区切り線の色を選ぶのは一覧ごとに 1 回で、一覧が既に読んでいる値を使う。項目ごとに線を描く処理は変えない。画像は、画像ごとに画面の構成を 1 回読んで色を 1 つ渡すだけ) ため、測っても結果で変わる設計の選択肢が無い。歯止め: レビューで項目ごとの仕事量が増えていないことを確かめる。実装でそれが増える形になったら、実装を止めて報告し、規約どおり性能検証を行う。iOS の規約の対象 (セルの生成・再利用・自己サイズ・レイアウト生成・snapshot 適用の経路) には当たらないと判断した (定数の値と、既定の表示の色を変えるだけで、これらの経路の処理は変えない)
- テストの時間: ライブラリのテストを十数件足すだけで、Sample の UI テストは足さない (全系統の合計 10 分以内 — cross/ADR-0008)

## 級: M

型・名前・引数は変えず、指定しないときの見え方だけを変える小変更。能力は 3 つにまたがるが、どれも定数と既定の選び方の変更で、設計書が要る深さではない (2026-10-06 オーナー確定)

domain: cross   # core の契約 (既定の色・タップの色) + iOS / Android 双方の実装と両 Sample。実装時のスキル解決は ios + android を結合

- 性能検証を対象外と書いた判断が、handbook/android/performance-verification の適用範囲 (区切り線の経路に触れる変更は対象) とぶつかっていた。オーナーに諮り、今回は例外として行わないと決まった (Impact に理由と歯止めを書いた)。自己レビューでは handbook の冒頭の適用のきっかけだけを読み、適用範囲の節を読んでいなかった
- 「指定した色は表示モードで変わらない」が、利用者が指定した外観で値の変わる色まで固定する約束にも読めた。約束を書く前にシミュレータで確かめ、iOS 17.5 では変換の時点でライトの値に固定されると分かった (`evidence/proposal-probes.md` の 4)。スペックは「指定した色にライブラリは手を加えない」とだけ約束する形に直し、Scenario を「固定の色を指定すると表示モードで変わらない」に限定した。iOS 17 以前の挙動は Non-Goals に書いた。samples のスペックから、外観の切り替えへの追随の約束と Scenario を外した (この挙動に依存するため)
- 外観の切り替えで画像を取得し直さないことを tasks は求めていたが、スペックに約束が無く、予定のテストでは確かめられなかった。約束と Scenario「取得の途中で表示モードが切り替わる」を足し、要求と取り消しの数を数えるテストを両プラットフォームに足した
