### 最初の「大量件数」の実行で 1 列の P99 が基準を超えた件 (やり直しで再現せず)

最初の「大量件数」の実行 (15:53) では、1 列の P99 がライブラリ 8.489 ms / 比較対象 7.606 ms で **+11.6% (超過、終了コード 1)** だった。2 列は P90 −10.4% / P99 −6.2%、1 列の P90 は −5.4%。超過はライブラリ側の 3 試行のうち 1 試行目だけに出た 13 ms 台のフレーム数枚によるもので (試行別の P99: 13.17 / 6.63 / 6.70 ms)、2・3 試行目は比較対象と同じ水準だった。handbook の「集計値が基準を超えたときは同じ手順を 1 回やり直し、再現するかを見る」に従って同じ手順をやり直した (15:58)。やり直しでは −3.9% で再現しなかったため、上表はやり直しの値で判定した。「グループ化」の最初の実行は、比較対象側の試行の後始末でトレースの記録プロセスを止められずに失敗した (計測の枠組み側の失敗、`Failed to stop perfetto`)。同じ手順を 1 回やり直して得た値を上表に載せた。

### 回帰 (行間を項目の余白に移した影響・`animateItem` を付けた影響)

回帰の判定は相対基準 (上表、すべて 10% 以内) で行った。前回の相対計測 (../../archive/2026-09-17-performance-criteria-review/evidence/relative-fling-android-2026-09-15.md) との並びは参考として載せる。

| 土俵 | 2026-09-15 のライブラリ P90 / P99 | 今回のライブラリ P90 / P99 | 2026-09-15 の劣化 | 今回の劣化 |
|---|---|---|---|---|
| 大量件数 2 列 | 6.655 / 8.251 | 6.918 / 8.501 | −9.2% / −8.6% | −7.9% / −3.8% |
| 大量件数 1 列 | 5.727 / 7.083 | 6.014 / 7.349 | −7.7% / −6.0% | −4.2% / −3.9% |

- **比較不能な点:** 2026-09-15 以後、ライブラリと比較対象の両方にスクロールインジケータ (android-scrollbar-parity) と `animateItem` (この change) が加わっている。前回との絶対値の差は、行間を余白に移した影響だけを表さない
- ライブラリの絶対値は P90 +4〜5% / P99 +3〜4% 上がり、比較対象に対する余裕は縮んだ (1 列の P99 で −6.0% → −3.9%)。ただし `animateItem` を外したライブラリ (下の (c)) は 2 列 7.018 / 8.439 ms、1 列 5.766 / 7.206 ms で、2026-09-15 から 2 列 +5% / +2%、1 列 +1% / +2%。この差にはインジケータの追加も含まれ、行間を余白に移した影響だけを取り出せない。受容する理由: 相対基準の内側であり、差は試行間の揺れ (±数%) と同じ桁

## (c) `animateItem` 自体の費用 — ライブラリのなし / あり

計測のために、ライブラリの配置のアニメーションの修飾 (`KsCollectionView.kt` の `ksAnimateItem`) を一時的に「何も付けない」に差し替えたビルドで、ライブラリ側だけを同じ手順で測った (計測後に元に戻した。下の「後片付け」)。「あり」は上表の値 (同じ手順を 2 回採った土俵は 2 回の平均)。

| 土俵 | あり P90 / P99 | なし P90 / P99 | ありの上乗せ P90 / P99 |
|---|---|---|---|
| グループ化 | 7.383 / 9.815 (2 回: 7.254 / 10.006、7.511 / 9.624) | 6.798 / 9.237 (2 回: 6.769 / 8.807、6.827 / 9.667) | **+8.6% / +6.3%** |
| 大量件数 2 列 | 6.918 / 8.501 | 7.018 / 8.439 | −1.4% / +0.7% |
| 大量件数 1 列 | 6.014 / 7.349 | 5.766 / 7.206 | +4.3% / +2.0% |
| 画像グリッド (ディスク) | 11.067 / 18.328 | 10.441 / 17.577 | +6.0% / +4.3% |
| 画像グリッド (メモリ) | 11.742 / 15.886 | 13.024 / 26.837 | −9.8% / −40.8% (回線の揺れが支配的) |

- 「グループ化」では `animateItem` が P90 で 8〜9% を上乗せする (2 回ずつ採って同じ向き)。比較対象にも同じ修飾が付いているため相対基準には現れない (design の Risks のとおり)
- 「大量件数」では試行間の揺れと区別できない。「画像グリッド」は取得が回線に依存し、cold の試行ではなし / ありの差より回線の揺れが大きい
- `frameOverrunMs` の P99 (同じ `FrameTimingMetric`) はいずれも負 (期限内) だった: グループ化 あり −4.77 / −4.18 ms、なし −5.38 / −5.05 ms
- 合否はこの数値ではなく体感のゲート (tasks 5.5、cross/ADR-0006) で決める

## (d) 高さが変わる土俵での上乗せ (降格した Suggestion の観点)

**既存の土俵では高さの補間はスクロール中に起きない。** 「画像グリッド」のセルは画像の枠を `aspectRatio(1f)` で固定しており、読み込みの前後で高さが変わらない (コード上の確認。実行時に補間の開始を数えてはいない)。「大量件数」「グループ化」の行は内容ごとに高さが決まっていて、再利用時は補間の状態を初期化する (`KsAnimatedHeightNode.onReset`)。したがって上の (c) の「画像グリッド」は、指摘の経路 (補間の開始・終了で可視項目の入れ物が作り直される) を通っていない。

指摘の経路を通すため、計測用に一時的な土俵を足して測った (計測後に取り除いた): 「大量件数」2 列の各項目が、載ってから 150 ms 後に高さを 24dp 伸ばす (画像の読み込みで高さが変わるセルを模したもの)。この土俵ではフリック中に高さの補間が絶えず始まり・終わる。ライブラリの配置のアニメーションの付け方を一時的に 4 通りに差し替えて、各 2 回測った。

| 付け方 | 1 回目 P90 / P99 | 2 回目 P90 / P99 | 平均 P90 / P99 | なしに対する上乗せ P90 / P99 | `frameOverrunMs` P99 (1 回目 / 2 回目) |
|---|---|---|---|---|---|
| なし (`animateItem` を付けない) | 7.074 / 9.489 | 7.095 / 9.184 | 7.085 / 9.337 | — | −4.46 / −4.59 |
| フェードのみ (`placementSpec = null` 固定、補間の状態を読まない) | 7.637 / 9.870 | 7.821 / 9.518 | 7.729 / 9.694 | +9.1% / +3.8% | −4.17 / −4.23 |
| 配置のばね固定 (補間の状態を読まない) | 7.477 / 9.513 | 7.777 / 11.033 | 7.627 / 10.273 | +7.7% / +10.0% | −3.33 / −3.42 |
| **現行** (補間の間だけ配置を止める。補間の状態をコンポジションで読む) | 7.719 / 10.256 | 8.852 / 10.519 | 8.286 / 10.388 | **+17.0% / +11.3%** | −2.72 / **+0.24** |

- 高さが変わる土俵では、現行の付け方は `animateItem` なしに対して P90 +17% / P99 +11% を上乗せし、2 回目は P99 で期限を 0.24 ms 超えた (`frameOverrunMs` P99 > 0)
- 上乗せの大半 (+8〜9%) は補間の状態を読まない付け方でも出ており、`animateItem` を付けること自体の費用にあたる。補間の状態を読むことに帰属しうる分 (現行とフェードのみの差、P90 で約 +7%) は、現行の 1 回目 (7.719) がフェードのみの 2 回目 (7.821) と重なっており、2 回ずつの計測では揺れと切り分けきれていない
- 描画フレーム数はすべて 175〜182 (1 回目の「現行」の 1 試行だけ 202)
- この土俵は一時的なもので、既存の fixture ではない。前回値との比較はしない

## 判定

- **相対 (ラッパーの上乗せ): 合格。** 「グループ化」「大量件数」2 列 / 1 列のいずれも P90 / P99 の劣化が 10% 以内 (事後検証スクリプトの終了コード 0)。「画像グリッド」は計測成立
- **回帰: 相対基準の内側。** 前回 (2026-09-15) から比較対象に対する余裕は縮んだが、比較対象にもインジケータと `animateItem` が加わっており絶対値の差は比較不能。行間を余白に移した影響を単独で取り出す計測は採っていない
- **`animateItem` の費用:** 「グループ化」で P90 +8〜9%、高さが変わる一時的な土俵で P90 +17% (うち `animateItem` 自体が +8〜9%)。合否は体感のゲート (5.5) で決める。体感で不合格なら design の Risks に従い 3.8 に戻って付け方を見直す
- 降格した Suggestion の観点: 既存の土俵では指摘の経路を通らない。通す土俵では現行の付け方の上乗せが最も大きく、P99 の期限超過が 1 回出た。体感のゲートに「高さが変わる画面」は含まれていない
- (d) の体感: Pixel 4a の「検証: 行の高さ変化 (Android 固有)」画面 (list / grid、行の展開・折りたたみとスクロール) で引っかかりなし (2026-09-26、オーナー。記録なしの体感のみ) → `animateItem` の上乗せは受け入れ ([performance-5.5.md](performance-5.5.md))

## 限界

- 各土俵の試行は 1 実行 (独立 3 試行) を基本とし、なし / ありの比較は「グループ化」と高さが変わる土俵だけ 2 回ずつ採った。「大量件数」「画像グリッド」のなし / ありは 1 回ずつ
- なし / ありは別の実行 (15:58〜16:28 の間) で採っており、同じ実行の中で対にしていない。熱による待機は全試行で 0
- 「画像グリッド」は cold (キャッシュを空にした状態) の試行で、取得が回線に依存する
- 高さが変わる土俵で補間の状態を読むことの費用は、2 回ずつの計測では揺れと切り分けきれていない。確かめるには回数を増やすか、Perfetto のトレースで項目の入れ物の作り直し (recomposition) を数える必要がある
- 生の結果 (Macrobenchmark の JSON と Perfetto のトレース) は手元保管。ここには判定に使った集計値だけを載せた
