## sample-parity (Android との操作の規則の一致)

- **切り替え**: Android (`samples/android/app/src/main/kotlin/jp/kamusoft/kscollectionview/samples/android/DiffUpdateDemoScreen.kt:76-81`) は、`onCheckedChange` の中で `model = model.regrouped()` としてから `grouped = isGrouped` にする。iOS の `setGrouped(_:)` と同じ順序で、同じ規則 (グループが初めて現れた順に集め直し、グループ内の順は保つ)。グループなしへの切り替えでは、どちらも並びを変えない
- **状態の持ち方の差**: Android は `grouped` を画面の `rememberSaveable` に、iOS はモデルに置く。これは画面に出ないコード上の差で、sample-parity の「許容される差異」に収まる。移動とシャッフルがグループの有無を受け取る方法も違う (Android は引数、iOS はモデルの `grouped`)。ただし、どちらも表示中のグループの有無を使うので、結果は同じ
- **元に戻す**: iOS の `reset()` は `grouped` に触れない。Android もグループの有無を別の状態に持つので、`reset()` で変わらない。両方の doc コメントの「表示の形とグループの有無は変えない」と一致する
- **文言・見た目**: スイッチの文言「グループ」と modifier (`font` / `foregroundStyle` / `tint` / `fixedSize`) は変わっていない。承認 mock (ui/brief.md の案 B) との見た目の差は生じない

## 指摘事項

### 🟡 Minor (低優先) 追加の UI テストの 2 周目「移動で崩す経路」は配列を崩せておらず、不具合を検知できない
**該当箇所**: `samples/ios/KsCollectionViewSamplesUITests/GroupingDemoUITests.swift:154-155`
**問題点**: 2 周目の崩し方 `["中ほど", "移動", "先頭", "移動"]` は、配列を元に戻してしまう。1 周目の後の配列は 5 件ずつ続いて並んでいる。そこでグループなしの「中ほど」の移動をすると、位置 10 の項目が位置 (10 + 20 / 2) % 20 = 0 へ移る。続く「先頭」の移動で、同じ項目が位置 min((0 + 10) % 20, 19) = 10 へ戻る。このため、グループありに切り替える直前の配列は、グループが続いた並びになる (モデルの単体での確認で、切り替え前に続いて並んでいることを確かめた)。プローブ 2 でも、修正前の実装でこの周だけを回すテストは成功した。コメント (`:154` の「移動で崩す経路」) と、テストの doc コメントの「(シャッフル・移動)」が約束する経路を、実際には確かめていない。不具合そのものは 1 周目 (シャッフル) で検知できるので、今の回帰の防ぎは保たれている。
**推奨修正**: 2 周目を、崩れた状態で切り替えに入る操作列にする。例えば `["中ほど", "移動"]` だけにすれば、中ほどの項目が先頭へ移り、グループの値が離れて現れる。あるいは、どちらの移動も崩す向きになる組み合わせを選ぶ。直した後は、修正前の形でこの周が落ちることを確かめる。

### 🔵 Suggestion (任意) スイッチの `Binding(get:set:)` の扱いの確認
**該当箇所**: `samples/ios/KsCollectionViewSamples/DiffUpdateDemoView.swift:37-40`
**問題点**: swift-ui-impl-skill の data-flow には、本体の中で `Binding(get:set:)` を作るのは強く避け、副作用は `onChange()` で起こすとある。ただしこの画面では、`onChange` で並べ直すこと自体が不具合の原因だった (更新が 2 回に分かれる)。そのため、ここで `Binding(get:set:)` を使うのは妥当と判断する。理由はコメント (`:35-36`) に書かれている。指摘ではなく確認として残す。
**推奨修正**: 不要。スキルの規則に寄せたいなら、`grouped` の `didSet` で (偽から真へ変わったときに) `regroup()` し、`$model.grouped` を渡す形がある。これでも 1 回の変更に収まる。ただし、`setGrouped(_:)` を明示的に持つ今の形のほうが意図は読みやすい。

## 確認した観点

- **仕様充足**: Requirement「デモ画面「差分更新」」の SHALL のうち、「グループの有無を切り替えられる」と「グループありのとき、どの操作の後も同じグループの項目が続いて並ぶよう、データ側でグループ単位に並べ直す」は、切り替えでグループありに入る経路を含めて満たす。Scenario「グループありの操作で不正入力にならない」の趣旨 (debug で assertion が一度も起きない) も、この経路で保たれる。「両プラットフォームで同じ結果」は、切り替えの規則と乱数の消費で Android と一致する
- **足場の不変**: specs / proposal / design / deviation.md / ui/brief.md / tasks.md の更新時刻は、いずれも verify-001 より前。修正の中で足場は書き換えられていない。今回の修正は仕様どおりに直したもので、deviation への記録が要る逸脱はない
- **堅牢性**: `grouped` を `private(set)` にしたので、並べ直しを飛ばしてグループありにする経路はない。空の配列 (全件を削除した後) での切り替えでは、`regroup()` は空のまま返る。スイッチの `set` が同じ値で呼ばれても、`regroup()` は続いて並んだ配列を変えない
- **テスト**: 追加したテストは `continueAfterFailure = false` で、停止の後に失敗を重ねない。見出しが消えるのと出るのを、条件ベースで待つ。検知の力は 1 周目にあり、2 周目にはない (Minor)。iOS Sample にはモデルの単体テストのターゲットがなく、規則は UI テストと Android の `DiffUpdateModelTest` で担保している (verify-001 の所見のとおり。今回の修正の範囲外)
- **SwiftUI / Swift のイディオム** (swift-ui-impl-skill): モデルは値型で、`@State` の 1 つの値にまとまっている。1 ファイル 1 型は守られ、強制アンラップはない。`Binding(get:set:)` については Suggestion のとおり
- **設計品質**: モデルの doc コメントに、切り替えの規則と 1 回の変更で行う理由が書かれている。画面のコメントとも食い違わない
