# Design: performance-criteria-review

## Context

探索の決定事項と証跡は `exploration.md` と `evidence/` にある。要点:

- 完了判定はオーナーの体感、数値は証跡 (cross/ADR-0006、proposed)
- iOS「大量件数」の主因は compositional layout の estimated 高さの solver。Sample の行は detail の有無で高さが 2 種類あり、直近 32 件の実測平均 (`KsEstimatedHeight`) はどちらとも一致しないため、新しく可視になる全セルが preferred ≠ original を返して solver を起こす。画像グリッド (全セル同じ高さ) では solver が 0% で体感も合格
- Apple の文書: `shouldInvalidateLayout(forPreferredLayoutAttributes:withOriginalAttributes:)` は preferred が original と同じなら invalidate 不要
- Android の Macrobenchmark には相対 10% の判定コードが無く、人が結果を突き合わせている。絶対基準は文書上の合格線だけ
- **改訂 (2026-09-16)**: 最頻値化は不一致率 0.032・solver 占有率 55% → 35.9% まで効いたが、10,000 件の体感は不合格で solver の費用は 2,000 件の 4.1 倍と件数に比例したまま (`evidence/manual-largeData-ios-2026-09-15.md`)。Decision 3 の分岐でオーナーが「提案を改訂して内部セクション分割を追加」を選び、Decision 10〜14 を足した

## Goals / Non-Goals

Goals: 規約を体感ゲートに書き換える / iOS の solver 起動を「推定と高さが違うセル」だけに絞る (最頻値化) / iOS の solver の再解決の費用を配列の件数から切り離す (内部セクション分割、改訂で追加) / Android の相対基準の判定と計測成立の確認を機械化する / 新手順で再計測して証跡を揃える。
Non-Goals: proposal.md のとおり (画像の表示待ち・スクロールバー・対策 C / D・CI 自動駆動・phase-4 の設計)。

## Decisions

### Decision 1: 推定高さは「直近の実測の最頻値」にし、一致するセルの自己サイズがレイアウトを無効化しないようにする (最頻値化)

**採用案:** `KsEstimatedHeight.value` を、直近 32 件 (幅ごと) の実測のうち出現回数が最も多い値にする。同数なら新しい方を採る。実測が 1 件も繰り返さないうちは平均のまま (未計測は 44pt)。**標本の単位はセル** (`KsHostingCell` が自己サイズで返した高さ。複数列でも行ではなくセルごと) — invalidation の判定は item (セル) の preferred と original の比較で行われるため、一致させる相手はセルの実測。標本は画面のピクセル格子 (1 / scale pt) に量子化してから数える (微小な測定差で同じ見た目の高さが別値に散らないため)。格子に丸めるのは数えるときだけで、返すのはその格子に入った直近の実測値そのもの (丸めた値を返すと半画素までの差が解き直しを起こさないまま行ごとに積み上がる — 実装で確定、deviation.md)。標本は幅または画面の倍率が変わったときに捨てる (倍率は改訂で追加)。`KsHostingCell.preferredLayoutAttributesFitting` の戻り値は変えないが、Debug 構成のみ「自己サイズを返したセル数」と「推定と不一致だった回数」を `KsCollectionViewController` の診断カウンタに数える (テストと計測の seam。既存の同時生存セル数と同じ扱いで Release には載せない)。

**理由:** 行の高さが少数の種類に集中する画面 (リストの typical、Sample の 2 種類) では、多数派の行が推定値と完全一致して invalidation が起きず、solver が走るのは少数派の行だけになる。画像グリッドの実測 (全行一致で solver 0%) がこの効果の上限を示している。実装は `KsEstimatedHeight` に閉じ、公開 API・レイアウト定義に触れない。

**代替案:**
- **平均のまま (現状)** — 合計高さの見積もりには最良だが、行高が 2 種類以上ある画面では推定値がどの行とも一致せず、全セルが solver を起こす (実測: 主スレッドの 55%)。却下
- **attributes 抑制 (`KsHostingCell` で「推定との差が小さい行は original の attributes をそのまま返す」)** — 差が本当にある行を推定高さで置いてしまい表示が崩れる。差ゼロの行は UIKit が既に invalidate しないので上乗せの効果が無い。却下
- **テンプレートキーごとに推定値を持つ** — `.estimated` は item 定義単位で index path ごとに変えられず、単一セクションでは 1 値しか渡せない (`KsEstimatedHeight` の設計時に確認済み)。却下
- **平均と最頻値のハイブリッド (最頻値の占有率が閾値未満なら平均)** — 切り替えの閾値がもう 1 つの調整点になる。初版では最頻値一本にし、Decision 2 の再検証で合計高さの見積もりが崩れたときの再訪案として残す

### Decision 2: 最頻値化の効果は事前に固定した数値基準で判定し、平均が担っていた保証も数値で再検証する

**採用案:** 判定は次の 4 つで、いずれも実装前に固定する (値は Sample「大量件数」fixture = 高さ 2 種類が 6 : 1 の前提)。
1. **不一致率**: 診断カウンタの「推定と不一致だった回数 / 自己サイズを返したセル数」が、推定が多数派の高さに達した後の区間で **0.20 以下** (少数派の割合 1/7 ≈ 0.14 に余裕 0.05)
2. **件数比例**: Sample の起動引数 `--large-count` で 2,000 件と 10,000 件を開き、同じ固定操作列 (Decision 9) で手動フリックした Instruments の time profile で、`_UICollectionLayoutSectionEstimatedSolver` の主スレッド占有率が **10,000 件 ≤ 2,000 件 × 1.5**。占有率は「操作列の区間」の標本で計算する
3. **合計高さ**: 既存のエンジンテストの形で、初回表示のコンテンツ高さの実測に対する誤差が **±5% 以内**、末尾までスクロールする間の contentSize 変化回数が **3 回以下**。基準値の出典は起票時は foundation の証跡 (一様な 1 列・100 件相当: 平均で 0% / 1 回。`kasane/changes/archive/2026-09-04-ios-engine-foundation/evidence/estimated-height-ab-measurement.md`) で fixture が違ったため、実装で一様な 1 列・2,000 件に校正し直した (最頻値で誤差 0.09〜0.15%、合計の 0.1% を超える変化 1〜2 回、Simulator 5 機種。`deviation.md`)。Scenario はこの校正後の fixture で書いてある
4. **体感**: Decision 9 の操作列で合格

**理由:** 「同程度」「無視できる」では同じ結果から合格と不合格の両方を主張できる (相方レビュー)。占有率だけでは操作量に左右されるため、不一致率 (件数と操作に依らない) を主指標にし、占有率は比例性の確認に限る。

**代替案:**
- **10,000 件の体感と占有率だけで判定** — 対策後の値が件数に依存しないことを示せない。却下
- **solver の呼出回数と 1 回あたりの費用を直接測る** — UIKit 内部の呼出は数えられない (標本ベースの time profile では回数が出ない)。セル側の不一致回数が呼出回数の上界になるのでそれで代替
- **自動駆動で比例性を測る** — 足場が主スレッドを汚す。却下

### Decision 3: 本 change の実装は最頻値化までとし、不合格なら実装を止めて提案を改訂してから内部セクション分割に進む

**採用案:** Decision 2 の判定で不合格 (不一致率・件数比例・体感のいずれか) なら、実装フェーズはそこで NEEDS_DISCUSSION として止まり、内部セクション分割 (`KsSectionID` を列数の倍数の塊に分けて snapshot を組む) の Requirement / Scenario (塊の境界で不完全な行を作らない・先頭行の区切り線・ルートヘッダー / フッターが先頭と末尾の塊にだけ付く・先頭挿入で塊の所属が変わるときの差分更新と位置維持・スクロール命令の ID 解決) をこの change の提案に追加して再レビューしてから実装する。足場の凍結は保ち、追加は提案の改訂として行う。試作に入る前に phase-4 の agenda に「利用者の論理セクションと内部の分割単位の責務」と 3 条件 (sticky ヘッダが内部分割の末尾で止まらない / 列数に合わない分割で不完全な行を作らない / 先頭挿入時の差分更新と位置維持) を論点として追記する。採用時は ADR 候補として捕捉する。

**理由:** 内部セクション分割は snapshot・区切り線・ヘッダー / フッター・アンカー保持に及ぶのに、今のデルタスペックにはそれを拘束する Requirement が無い (相方レビュー)。使わないかもしれない仕様を先に書くより、必要になった時点で提案を改訂する方が安い。change を分けないのはオーナー判断 (対策の効果測定に新手順を使うため)。

**代替案:**
- **最初から内部セクション分割を実装** — 最頻値化 (小コスト) で足りる可能性が画像グリッドの対照で高い。却下
- **内部セクション分割の spec を今書く** — 塊の件数・ヘッダーの扱い・phase-4 との責務が未決で、推測で書くことになる。却下
- **内部セクション分割を別 change にする** — 効果測定の手順が本 change の成果物で、切り離すと相互待ちになる。却下 (オーナー判断)

**結果 (2026-09-15):** Decision 2 の基準 2 (件数比例 4.1 倍) と基準 4 (10,000 件の体感) で不合格。本 Decision のとおり実装を止め、phase-4 の agenda に責務と 3 条件を追記し、本改訂 (Decision 10〜13) で内部セクション分割を追加した。

### Decision 4: Android の相対基準の判定と計測成立の確認は、Macrobenchmark の結果 JSON を事後検証するスクリプトで行う

**採用案:** `samples/android/benchmark/scripts/verify-fling-results.py` (Python 3、標準ライブラリのみ) を置く。契約:
- 入力: `build/outputs/connected_android_test_additional_output/` 配下の最新 1 実行の JSON だけを読む (古い結果ディレクトリが混在したら入力不正)。`benchmarks[].name` (テスト名) でライブラリ側と比較対象側を対応付け、片側しか無ければ入力不正
- 環境照合: JSON の `context` (機種・OS・ビルド構成) が両側で一致しなければ入力不正
- 計測成立: 各試行の `frameCount` が **90 以上** (基準機 60 Hz × 3 秒のフリック = 理論上限 180 の 50%。結果を見て動かさない固定値)。割れた試行があれば「未判定」
- 相対判定: `frameDurationCpuMs` の P90 / P99 (3 試行の集計値) の劣化が 10% 以内で「合格」、超えたら「不合格」
- 終了コード: 合格 0、不合格・未判定・入力不正はいずれも非 0 (種別ごとに別の値)。欠損 metric・破損 JSON・重複も入力不正
- `ImageGridBenchmark` は比較対象が無いので計測成立だけ判定し、相対・絶対の判定はしない
- 比較対象には、ライブラリの既定機能 (現時点では行の高さ変化のアニメーション、android/ADR-0004) と同じ機能を同じ位置に付ける (現行規約から引き継ぐ。付けないと相対の差が既定機能そのものの費用になる)
- `LargeDataMemoryBenchmark` / `ImageGridBenchmark` の 1,000 件の試行 (件数比) は削除する

**理由:** 相対 10% は現状人が突き合わせており判定の所在が無い。計測ブロック内から集計値は読めないが、結果 JSON には `frameCount` を含む集計が残る (公式の `FrameTimingMetric`)。下限を実装時に校正すると合否線を結果観測後に動かせるため、理論値からの固定にする (相方レビュー)。

**代替案:**
- **試行ごとに `dumpsys gfxinfo` を読んで下限を assert** — 試行間のリセット・対象 window・取得失敗の定義が要り、計測区間と一致しない。却下
- **判定を人手のまま** — 「未判定が緑」の穴が残る。却下
- **下限を実装時の実測で校正** — 事前の受け入れ基準にならない。却下

### Decision 5: メモリの「件数比」系統を「保持対象の寿命と解放」の確認に差し替え、観測できる対象に要件を絞る

**採用案:** 要件が対象にする保持は、ライブラリが**項目単位**で持つもの: iOS はセルとそのホスティング (Debug 構成の同時生存セル数で観測)、Android は項目のコンポジション (Sample debug 構成のテンプレート呼び出しカウンタで観測)。`KsEstimatedHeight` の標本は項目単位ではなく上限 32 件の固定長で、置換時に捨てる必要は無い (幅または倍率が変わったときだけ捨てる規則)。画像の要求と台帳は image-loading の spec (取り消し・メモリ保持) が担い、ここでは扱わない。
観測方法: iOS はエンジンテストで (a) 2,000 件往復 → 別の 2,000 件に置換 → 同時生存セルが可視の 4 倍未満に戻る、(b) コレクションを解放 → controller への弱参照が nil になる (破棄後に同じインスタンスのカウンタは読めないため、弱参照プローブで「破棄された」ことを確かめる)。Android は計測用の入口の自動走査に「置換 → 離脱」の段階を足し、離脱後の同時生存はプロセス全体のカウンタ (debug ソースセット、画面に属さない) を離脱先の結果画面の進捗の印から読む。メモリの往復定常化 (10,000 件) の手順は維持する。

**理由:** 10 倍の件数比は「定常値が件数に比例しない」ことしか示さず、項目単位の保持を全件分抱えたまま定常化する場合を見逃す。一方で要件を「保持する対象すべて」と書くと、カウンタが観測しない対象 (訪問済み ID・画像要求・購読) が残っても Scenario が通る (相方レビュー)。観測できる対象に要件を絞り、他は各能力の spec に任せる。

**代替案:**
- **件数比を残す (1,000 vs 10,000)** — 10,000 件の生成と往復の時間が残り、上記の見逃しも残る。却下
- **定常化だけで済ませる** — 全件保持のまま定常化する場合を判別できない。却下
- **保持対象すべてを要件にする** — 観測手段が無い対象が要件に混ざる。却下

### Decision 6: 規約は「共通の判定規則」を cross に置き、platform 別の文書は道具と手順に絞る

**採用案:** `handbook/cross/scroll-performance-gate.md` (rule) を新設し、体感ゲート・証跡に残す項目 (操作条件・体感を先に記録・数値・参考スケールの扱い・比較不能の明示・悪化時の記載義務)・合図の手順・画像の表示待ちが別の観測点であること・自動駆動の再訪条件を書く。`handbook/ios/performance-verification.md` と `handbook/android/performance-verification.md` は、fixture・機材・計測器の接続手順・数値の取り出し方・メモリの手順 (iOS: Simulator の自動往復、Android: Macrobenchmark + 事後検証スクリプト + 相対基準) に絞って全面的に書き直す。旧基準・旧値には言及せず、経緯は cross/ADR-0006 の Context に委ねる (handbook から ADR へリンクする)。

**理由:** 判定規則は両プラットフォームで同一であり、2 本に同じ文を書くと片方だけ直る。道具は platform で違う。

**代替案:**
- **A: platform 別 2 本に同じ規則を書く** — 重複と乖離。却下
- **B: cross 1 本に全部書く** — 計測器の手順が長く、platform の index から引けなくなる。却下

### Decision 7: iOS の自動フリックの計測ドライバは退役し、メモリの自動往復は維持する

**採用案:** `PerformanceDriverUITests` の「3 秒間連続フリック」2 本と、区間の印 (`ScrollWindowSignpost`、起動引数 `--signpost-scroll-window`) を削除する。メモリの自動往復 (`test大量件数を全件通過で2往復してメモリを表示する`、計測専用 launch 経路) は残す。

**理由:** 規約から自動駆動が消えるのに駆動テストだけ残すと使われない足場になる。git の履歴に残るので CI 再訪時に戻せる。メモリの往復は足場の問題が無く、Simulator で自動実行できる。

**代替案:**
- **A: スキーム除外のまま残す** — コンパイルされ続けるだけの死んだコード。却下

### Decision 8: 手動計測の証跡は固定の雛形に書く

**採用案:** `evidence/` の手動計測は探索で書いた 4 本 (`manual-*-2026-09-08.md`) の構成を雛形にする: 環境 (機種・OS・構成・fixture・駆動・記録・熱状態) / オーナーの体感 (数値を見る前に聞き取り。初回・再訪・連続・ムラ・画像の出方) / 数値 (証跡。合否ではない) / 判定 (体感の合否、数値との一致・不一致、前回との比較可否) / 限界。雛形は cross の規約に載せる。

**理由:** 比較可能性は同じ項目が残っているかで決まる。探索で 4 本書いて形が安定した。

**代替案:**
- **A: 自由記述** — 次回との比較ができない。却下

### Decision 9: 体感ゲートは固定の操作列と 3 状態の判定で運用する

**採用案:** 手動計測の操作は次の固定列とする (cross の規約に載せる): (1) 初回: 先頭から下向きに 10 秒連続フリック、(2) 休止 3 秒、(3) 再訪: 上向きに 5 秒、(4) 連続: 下向きに 10 秒 (未訪問の範囲へ)。速度は「いつもの感覚」でよいが、各段階の体感を段階ごとに聞き取り、数値を見る前に記録する。判定は **合格 / 不合格 / 未判定** の 3 状態で、未判定のままでは性能面の完了を報告できない。オーナーが迷った場合、または体感と数値が食い違った場合は、計測器を接続せずに同じ操作列を 1 回行って対照とし、それでも迷えば未判定。独立試行は 1 回を基本とし、再試行は上記の条件でのみ行う。

**理由:** 「10 秒以上フリック」だけでは速度・開始位置・方向・休止が自由で、同じ実装でも判定が揺れる。「未判定」が無いと迷った結果が合格に寄る (相方レビュー)。操作列は探索で 4 本の証跡を取ったときの実際の操作 (初回 → 再訪 → 連続) を固定したもの。

**代替案:**
- **自由な操作 + 条件の記録だけ** — 比較不能を説明できるが判定の再現性は担保しない。却下
- **自動駆動で操作を固定** — 足場の汚染 (探索の結論)。却下

### Decision 10: 配列を固定件数の塊 (内部セクション) に分けて snapshot を組み、レイアウトの再解決の単位を件数から切り離す (改訂 2026-09-16)

**採用案:** `KsSectionID` を「塊の順番」で識別する値にし、snapshot は配列を先頭から塊の件数ずつ区切って各塊に載せる。塊の件数 C は**基準 500 件を、列数の候補の最小公倍数 L の倍数へ切り上げた値** (list: L = 1、固定列数 n: L = n、向き別列数 (portrait, landscape): L = lcm(portrait, landscape)、adaptive: 直近のレイアウトパスで解決した列数。初回で未解決なら 1 で組み、最初のレイアウトで列数が確定したとき C が割り切れなければ組み直す)。lcm はオーバーフロー検査つきで計算し、オーバーフローするか lcm が 2,000 (基準の 4 倍。2,000 件 1 セクションが体感合格だった上限) を超える向き別列数は「現在の列数の倍数」に縮退して adaptive と同じく回転で組み直す (互いに素な大きい列数で塊が消えるのを防ぐ)。塊の数は max(1, ⌈N / C⌉) で、空配列でも 1 塊を載せる (ヘッダー / フッターを表示するため。現行の「初回は section を載せるために必ず適用する」を保つ)。推定高さ (`KsEstimatedHeight`) は 1 コレクション 1 値のまま全塊に同じ値を渡す。塊分けは snapshot 構築の直前に controller 内で行い、`KsSnapshotPlanner` はフラットな identifiers を返すまま変えない。塊の情報は `internal` に閉じ、公開 API・DSL・Android には現れない。

**理由:** solver の費用は「1 セクションの件数」に比例する (2,000 件 8.7% → 10,000 件 35.9%、4.1 倍。`evidence/manual-largeData-ios-2026-09-15.md`)。塊の件数を固定すれば、1 回の再解決の費用の上限が配列全体の件数に依らない。基準 500 は、2,000 件を 1 セクションで解いた実測 (体感合格・solver 8.7%) の 1/4 で余裕を取った値。列数候補の最小公倍数にするのは、向き別列数で表示領域が回転するたびに 10,000 件の差分適用を起こさないため (2 列と 4 列なら C = 500、2 列と 3 列なら 504)。adaptive は候補が無限なので現在の列数で組み、C が新しい列数で割り切れなくなったときだけ組み直す (2 列 → 4 列は 500 のまま組み直さない。Decision 12)。

**代替案:**
- **塊の所属を項目に固定し、件数を可変にする** — 挿入・削除で塊の件数が列数の倍数でなくなり、塊の境界に不完全な行ができる。却下
- **常に現在の列数だけで組み、列数が変わるたびに組み直す** — 向き別列数の回転のたびに全塊が組み直され、回転時のアンカー復元に差分適用が重なる。最小公倍数で回避できる。却下
- **塊 200 件** — 塊の数が 2.5 倍になり境界の処理が増えるが、再解決の上限はさらに下がる。500 で不足なら下げる (Decision 13 の判定で決める)。初版では採らない
- **塊ごとに異なる推定値を渡す** — sectionProvider の仕組み上は可能だが、最頻値化で不一致率が 0.032 まで下がっており必要性が未証明。再訪案 (proposal の Non-Goals)
- **`.absolute` 併用 / 自前レイアウト** — proposal の Non-Goals (ADR の改訂を伴う)。試作で効かなかった場合の再訪条件

### Decision 11: 塊の境界を見た目に出さない

**採用案:** sectionProvider は section index を受け取り、塊の位置で次を切り替える: (a) 内側余白 (`contentPadding`) の top は先頭の塊だけ、bottom は末尾の塊だけに入れ、先頭以外の塊の top には行間 (`rowSpacing`) を入れて塊間の間隔を他の行間と同じにする、(b) ヘッダーの boundary item は先頭の塊、フッターは末尾の塊にだけ付ける (空配列の 1 塊は先頭かつ末尾)、(c) 区切り線の先頭判定は「先頭の塊の先頭の項目」だけを上線ありにする (現行の `indexPath.item == 0` を塊の位置を含む判定に置き換える)。apply 完了後と `viewDidLayoutSubviews` での可視セルの区切り線更新は現行のまま。

**理由:** 塊は利用者に見えない契約 (core/ADR-0006 の単一コンポーネント、phase-4 の申し送り)。compositional layout はセクション間に行間を入れないため、境界の行間だけ 0 になるのを (a) で埋める。

**代替案:**
- **decoration item で境界を埋める** — concepts (iOS コレクションエンジン) が「`NSCollectionLayoutDecorationItem` は将来のセクション装飾と座を取り合うため使わない」としている。却下
- **全塊にヘッダー / フッターを付け、先頭 / 末尾以外を空にする** — 空の supplementary view が塊の数だけ生成され、ホスティングの費用が無駄になる。却下

### Decision 12: 塊の組み直しと位置維持は、既存の項目 ID によるアンカーに任せる

**採用案:** 差分更新は項目 ID ベースのまま。先頭に 1 件挿入すると各塊の末尾の項目が次の塊へ移るが、diffable の差分で移るのは塊の境界の項目だけ (N / C 件。10,000 件・C = 500 なら 20 件) で、塊の所属が変わらない可視セルは作り直されない。**項目だけの追加・削除・並べ替えではアンカーを捕捉しない (現行どおり)**。契約は「塊が無い場合と同じ位置の動き」であり、先頭挿入で表示中の項目が挿入分だけ下がるのは 1 セクションと同じ挙動として許容する (表示位置を項目に固定する契約は本 change では足さない。Android の Lazy 系との差も含めて別の判断)。塊の所属が変わる可視セルが diffable のセクション間移動で作り直されるかは実装で確かめ、結果を deviation に記録する (契約は所属が変わらないセルに限る)。adaptive の列数変化は `viewDidLayoutSubviews` のコンテナサイズ変化で検知し、**塊の件数が変わるときだけ**アンカーを控えて再適用し復元する (layout 値の変更と同じ経路: `captureAnchor` → apply → `restorePendingAnchor`)。layout 値の変更 (list ⇄ grid、列数の指定の変更) で塊の件数が変わるときも、`update(configuration:)` の既存のアンカー捕捉に乗せて同じ経路で組み直す。塊の構造の変化 (件数 C が変わる) は、**同値配列の早期 return (`items == appliedItems`) より前に判定**して snapshot の組み直しへ進め、`hasSnapshotChanges` の条件にも加える。ID へのスクロール命令と末尾への命令は `dataSource.indexPath(for:)` で解決する現行のまま。

**理由:** 現行のアンカー・スクロール命令・prefetch・選択は全て `dataSource.indexPath(for:)` / `itemIdentifier(for:)` を経由し、`indexPath.item` を直接使う箇所は区切り線の先頭判定だけ (Decision 11 で置き換える)。塊に依存しない構造が既にあるので、新しい仕組みを足さない。

**代替案:**
- **塊の組み直しで `reloadData` する** — 位置が飛び、可視セルが作り直される。却下
- **塊の所属を項目に固定して移動を無くす** — Decision 10 の代替案と同じ理由で却下

### Decision 13: 効果の判定は「試作 → 実機計測 → 本実装」の順で行い、Decision 2 の 4 基準を維持する

**採用案:** 段階 1 (試作) は Decision 10 の snapshot の塊分けだけ (Decision 11 の境界の見た目と Decision 12 の組み直しは未実装) を Release で基準機に入れ、tasks 4.1 と同じ手順 (固定の操作列、`--large-count` で 2,000 / 10,000) で solver の占有率の件数比例 (10,000 件 ≤ 2,000 件 × 1.5) と 10,000 件の体感を採る。**比例の比較区間は初回の段階 (先頭から未訪問域へ下向き 10 秒) だけ**にする: 4.1 の証跡では 2,000 件の入力区間が 17 秒で 10,000 件の 36 秒と揃わず、末尾に近づいて推定の対象範囲も狭かった (相方レビュー)。初回区間なら両走行とも先頭から初見のセルを通り、仕事量が揃う。証跡に両走行の初回区間の長さと到達件数を残し、2,000 件が初回区間で末尾に達した場合や区間の長さの差が 3 秒を超える場合は未判定とする。合格なら段階 2 (Decision 11・12・テスト) へ進み、完了後に Decision 2 の 4 基準 (不一致率 0.20 以下・件数比例 1.5 倍以下・合計高さ・体感) で最終判定する。段階 1 で不合格 (solver が全セクションを再解決している等) なら実装を止め (NEEDS_DISCUSSION)、`.absolute` 併用 (core/ADR-0006 の改訂を伴う) と自前レイアウト (ios/ADR-0003 の改訂を伴う) を、従う案と改訂案のコストを並べてオーナーに諮る。

**理由:** 「solver の費用がセクション内の件数に比例する」は profile からの推論で、一次資料は無く、Apple Forums には「件数が増えると全セクションが再計算される」という報告もある。境界の処理とテストを書き切ってから効かないと分かるより、試作 1 回の実機計測で確かめる方が安い (相談役の助言「最小試作で確認」)。試作でも件数比例の判定は「件数を減らせば数字は勝手に良くなる」を避けるため 2,000 / 10,000 の比で見る。

**代替案:**
- **試作を挟まず本実装まで進む** — 効かなかった場合、境界処理・組み直し・テストの実装が無駄になる。却下
- **試作の判定を Simulator で採る** — 実機の solver の費用を再現しない (cross/ADR-0006 の判定は基準機)。却下

### Decision 14: メモリ往復ドライバは定常判定つきの反復にし、往復ごとの footprint を記録に出す

**採用案:** UI テストの駆動 (`test大量件数を全件通過で2往復してメモリを表示する`) は 2 往復固定をやめ、app 側が持つ定常判定 (連続 2 往復の増分が 1 往復後の値の 2% 以内、上限 10 往復) と同じ規則で往復を重ね、往復ごとの `phys_footprint`・通過件数・最終判定 (定常 / 未判定) を `KS` 接頭のテストログに出す。未判定はテストの失敗にする (未判定が緑にならない)。通過件数の記録は `indexPath.item` ではなく項目の全体の順番 (または ID) で数える — 塊分割後は item が塊ごとに 0 から始まり、現行の数え方では全件通過が成立しなくなる (相方レビュー)。画像読み込みの観測駆動 (`test画像グリッドで基準点を切り送って戻す`) は image-loading の証跡取得用で自動フリックではないため残す。

**理由:** `evidence/memory-roundtrip-ios-2026-09-15.md` で、現行のドライバが 2 往復固定で値を残さず Scenario「往復後もメモリが定常化する」を判定できないと分かった (foundation 期の実装のまま)。

**代替案:**
- **app の自動実行モード (走査・記録・終了を app 自身が行う経路) を UI テストから起動し標準出力を読む** — XCUITest からアプリの標準出力は読めない。却下
- **画面表示だけに出してログに残さない** — 証跡に転記する数値が残らず、今回と同じ「数値の無い証跡」になる。却下

### 改訂で取り込む小修正 (Decision を立てない)

- Sample の Xcode プロジェクトの Debug 構成に `SWIFT_ACTIVE_COMPILATION_CONDITIONS = DEBUG` を定義する (不一致率の帯の操作が `#if DEBUG` で、実機の Debug 構成で出なかった)
- `KsEstimatedHeight` の標本を、幅だけでなく画面の倍率が変わったときも捨てる (独立レビュー review-004〜006 の再掲指摘。格子が混ざると最頻値の意味が崩れる)
- `handbook/ios/performance-verification.md` の手順に、実機の起動引数は `xcrun devicectl device process launch` の `--` の後ろに置くこと、合図の前に画面の件数表示で引数が効いていることをオーナーに確かめてもらうことを足す (lessons inbox `confirm-launch-arguments-on-screen-before-measuring`)

### Decision 15: 複数列の合計高さは行の高さの実測で見積もり、セルの一致には最頻値を使い続ける (改訂 2026-09-16、オーナー指示)

**採用案:** compositional layout の item と group (行) には別々の estimated 高さを渡せる。item には現行の最頻値 (セルの自己サイズが一致して再解決を起こさないための値) を渡し、group には**直近の行の高さ (その行のセルの実測の最大値) の平均**を渡す。行の高さはセルの実測を行 (indexPath の塊内の順番 ÷ 列数) ごとにまとめて記録する。1 列ではセル = 行なので現行と同じ値になる。判定は Scenario「混在 2 列でも合計高さの見積もりを損ねない」(一様 1 列と同じ基準: 初回誤差 ±5%、0.1% 超の変化 3 回以下、画面サイズまたは倍率の異なる 2 機種以上) で、**基準は結果を見て動かさない**。item と group の推定を分けても group の推定が行の配置に使われない、または一致したセルの行が group の推定に引き直されて再解決が増える、と分かった場合は実装を止めて (NEEDS_DISCUSSION) オーナーに諮る。基準を緩めて通す選択はしない。

**理由:** 本番 fixture (Sample「大量件数」= 混在 2 列) はライブラリの典型的な使われ方で、テストの対象外にはできない (オーナー指示 2026-09-16)。単一の推定値ではセルの一致 (最頻値) と行の合計 (平均) を同時に満たせないことが実測で分かっている (平均 12.0% / 最頻値 34.5%、`deviation.md`)。item と group で推定を分ければ、それぞれの役割に合った値を渡せる。前提 (group の estimated が未解決の行の配置に使われ、item の一致判定と独立していること) は Apple の文書に明記が無く、実装の A/B で確かめる。

**代替案:**
- **単一の推定値のまま (最頻値)** — 混在 2 列で 34.5% の誤差。却下
- **単一の推定値を平均に戻す** — 一致が崩れて solver が全セルで走る (Decision 1 の却下理由)。却下
- **混在 2 列をテストの対象外にする** — 却下 (オーナー指示)
- **行ごとの高さを自前で全件キャッシュして contentSize を補正する** — 自前レイアウトに踏み込む (ios/ADR-0003 の改訂を伴う)。今は採らない

## Risks / Trade-offs

- **solver の費用がセクション内の件数ではなく全セクションに比例していた場合、塊分割は効かない** → Decision 13 の試作計測で本実装の前に確かめる。効かなければ ADR 改訂を伴う案 (`.absolute` / 自前レイアウト) に戻る
- 塊の境界の見た目 (行間・余白・区切り線・ヘッダー / フッター) を自前で保守する → Decision 11 の Scenario をテストで固定する
- adaptive の列数変化で塊を組み直すとき、差分適用とアンカー復元が重なる → 塊の件数が変わるときだけ組み直し、layout 変更と同じ経路を使う (Decision 12)。固定列数・向き別列数では組み直しが起きない
- 既存テストの `IndexPath(item:section: 0)` 直書きが塊分割で壊れる → 全体の順番から indexPath へ変換するヘルパに置き換える (tasks 6.2)
- 塊分割後に合計高さの見積もり (一様な 1 列 2,000 件 = 4 塊) と 4 倍未満の同時生存が退行する可能性 → tasks 7.6 で再実行し、2 機種以上で通す
- item と group の推定を分ける前提 (Decision 15) が成り立たないと、混在 2 列の合計高さの基準に届かない → 基準は動かさず、届かなければ止めてオーナーに諮る
- 体感ゲートはオーナー 1 人の主観 → Decision 8 の雛形と「比較不能」の明示で補う
- Macrobenchmark の JSON の形式が版で変わる → スクリプトは `metrics` の名前で引き、無ければ未判定を返す (実装済み)
