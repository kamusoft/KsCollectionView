## 指摘事項

### [🟠 Major] 対策 A が発火した場合の仕様が存在しない

**該当箇所**: `design.md:43`、`proposal.md:27`、`tasks.md:29`

**問題点**: 対策 B が不合格なら内部セクション分割を同じ change で実装するとしていますが、sticky header、不完全行、先頭挿入時の位置維持は phase-4 の agenda に論点として書くだけです。現在のデルタスペックには、それらを満たす Requirement / Scenario がありません。

内部セクション分割は snapshot、区切り線、header/footer、アンカー保持へ影響します。agenda への記録は将来の設計材料であり、現在の実装を拘束する受け入れ条件にはなりません。

**推奨修正**: 次のどちらかを提案段階で確定してください。

- 本 change は対策 B までとし、不合格なら `NEEDS_DISCUSSION` で停止して対策 A を別 change にする。
- 対策 A を含めるなら、3 条件と既存の区切り線・header/footer・差分更新・位置維持を現 change のデルタスペックとテストタスクへ追加する。

### [🟠 Major] 対策 B の合否基準が検証不能

**該当箇所**: `specs/collection-layout/spec.md:11`、`specs/collection-layout/spec.md:16`、`design.md:33`、`tasks.md:28`

**問題点**: 「2,000 件と同程度」「件数に比例していない」「誤差が無視できる範囲」「変化が数回以内」は閾値がなく、同じ測定結果から合格・不合格の両方を主張できます。

さらに、探索の完了条件は solver の呼出回数と1回当たり費用を分離することですが、spec と tasks は主スレッド占有率しか要求していません。占有率は操作量、記録時間、他処理の負荷でも変動するため、件数依存性を直接示しません。

**推奨修正**: 次を事前に固定してください。

- solver 呼出回数、新規可視セル数、solver 総時間・1呼出当たり時間の記録方法
- 2,000 / 10,000 件の許容比または許容差
- 初回 contentSize 誤差率と contentSize 変化回数の上限
- 開始位置、方向、操作時間、到達範囲を含む比較手順

### [🟠 Major] 「行の最頻値」と実装が採取する値の単位が一致していない

**該当箇所**: `design.md:21`、`specs/collection-layout/spec.md:3`、`ios/Sources/KsCollectionView/KsHostingCell.swift:83`、`ios/Sources/KsCollectionView/KsCollectionViewController.swift:313`、`ios/Sources/KsCollectionView/KsCollectionViewController.swift:529`

**問題点**: 設計は「行の高さ」の最頻値を前提にしていますが、現在のコールバックが記録するのは個々のセルの fitted size です。一方、その単一推定値は item と複数列を束ねる horizontal group の両方に適用されます。複数列では行高が各セル高の最大値になるため、「セル高の最頻値」と「行高の最頻値」は一致するとは限りません。

また、値を丸めず完全一致だけで頻度を数える設計では、微小な測定差があると同じ視覚的高さでも全て別値となり、平均から最頻値へ移行しません。

`tasks.md:13` が要求する `shouldInvalidateLayout` の非発火についても、現在は `super.preferredLayoutAttributesFitting` を返すだけで、テストから安定して観測できる seam がありません。

**推奨修正**:

- サンプル単位をセルとするのか group/行とするのかを定義する。
- 列数・幅変更時のリセット規則と、同値判定の許容差または量子化規則を定義する。
- 複数列で「各行に高いセルが1つある」ケースと微小誤差ケースを Scenario に追加する。
- invalidation 回数を観測できるテスト seam を設計するか、この部分を実機 profile の受け入れ条件へ明確に分離する。

### [🟠 Major] メモリ要件と予定しているカウンタの観測範囲が一致しない

**該当箇所**: `specs/collection-core/spec.md:4`、`specs/collection-core/spec.md:16`、`specs/collection-core/spec.md:44`、`design.md:63`、`tasks.md:17`

**問題点**: Requirement はセル、ホスティング、自己サイズ実測、Android の項目関連保持全般の解放を要求しますが、計画されているカウンタが観測するのは iOS の生存セルと Android の `DisposableEffect` の生存数だけです。訪問済み ID、画像要求、購読、サイズキャッシュ等が残っていても Scenario は通ります。

特に `KsEstimatedHeight` のサンプルは配列置換時にリセットされず保持されるため、「置換前の項目のための自己サイズ実測が残らない」という要求と設計が整合していません。

また、iOS の `liveCellCount` は controller のインスタンスプロパティなので、controller 破棄後にその値が 0 であることは同じインスタンスから確認できません。Android も画面離脱後は画面内の進捗表示自体が破棄されます。

**推奨修正**:

- プラットフォームごとに保持対象の一覧、上限、置換時・破棄時の寿命を定義する。
- 自己サイズサンプルを配列置換時に維持するか破棄するかを明文化する。
- 外部所有の弱参照プローブまたは非保持の診断カウンタを設け、破棄後にも結果を読めるようにする。
- Android は離脱先の結果画面、プロセス外ログ、またはテスト所有 observer へ最終値を残す。
- 「メモリが件数に比例しない」本体要件をどの検査が証明するか、Scenario 対応を追加する。

### [🟠 Major] 体感ゲートの操作・再判定規則が固定されていない

**該当箇所**: `specs/collection-core/spec.md:6`、`specs/collection-core/spec.md:34`、`design.md:73`、`design.md:90`

**問題点**: 「10秒以上フリック」「引っかかりを感じない」だけでは、速度、開始位置、方向、初見範囲と再訪範囲、休止時間、試行数が自由です。証跡へ条件を書くことは比較不能を説明できますが、同じ実装を誰がどう操作しても同じ判定になる条件にはなりません。

計測器接続による負荷で体感が変わった場合や、体感と数値が食い違った場合の再試行・非接続対照・最終判定規則もありません。「未判定」の状態も定義されていないため、迷った結果を合格へ寄せられます。

**推奨修正**:

- 初回、再訪、連続、休止後を順番・時間・方向・到達範囲付きの固定操作列にする。
- 独立試行回数と、迷いまたは試行間不一致時の再試行条件を定める。
- 計測器負荷が疑われる場合の非接続対照を必須化する。
- 合格・不合格・未判定の3状態と、未判定時に完了できないことを Requirement に置く。

### [🟠 Major] Android の事後検証ゲートが実装時校正に依存し、比較条件も失われる

**該当箇所**: `design.md:53`、`design.md:104`、`design.md:117`、`specs/samples/spec.md:4`、`tasks.md:20`

**問題点**: `frameCount` 下限は実装時に同じ基準機の結果を見て決める未決事項です。これは計測成立の合否線を結果観測後に動かせるため、事前の受け入れ基準になりません。

また、JSON の対象ファイル選択、テスト名の対応付け、古い結果や複数結果、構成・機種・fixture の不一致、欠損 metric、終了コードが未定義です。スクリプトが「未判定」と表示して exit 0 なら、自動ゲートにはなりません。

加えて、現行 Android 規約が要求する「比較対象にもライブラリ既定機能と同等の機能を付ける」という条件が新 spec にはありません。絶対ゲート廃止後に比較対象が軽すぎる／重すぎると、唯一の定量ゲートが別の費用を測ります。

**推奨修正**:

- 下限値または結果から独立した導出式を提案段階で固定する。
- JSON の形式、ファイルの個数、テスト名による対応、環境メタデータ照合、古い結果の拒否を定義する。
- 不合格・未判定・入力不正はいずれも非0終了とする。
- 欠損、破損、重複、片側だけの結果、構成不一致を単体テストへ追加する。
- 比較対象が同等の既定機能を持つことを Requirement / Scenario に戻し、wrapper 単体の薄さを主張する場合の対等条件も区別する。

### [🟡 Minor] `--large-count` の不正値の挙動が未定義

**該当箇所**: `specs/samples/spec.md:23`

**問題点**: 0、負数、数値でない値、引数欠落、複数指定時の挙動が決まっていません。計測専用経路で誤入力が既定 10,000 件へ黙って縮退すると、別 fixture を測っても成功したように見えます。

**推奨修正**: 正の整数だけを受理し、不正値は明示的な起動失敗または計測未判定とする Scenario を追加してください。

### [🟡 Minor] 対策 A/B の記号が文書内で衝突している

**該当箇所**: `design.md:25`

**問題点**: proposal/exploration では A が内部セクション分割、B が最頻値ですが、Decision 1 の代替案では A が現状維持、B がセル側抑制を指します。「Bで不足ならA」の参照先を誤読できます。

**推奨修正**: 「最頻値化」「内部セクション分割」「attributes 抑制」のような固有名を使い、記号を全成果物で統一してください。
