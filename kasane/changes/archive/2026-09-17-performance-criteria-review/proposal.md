# Proposal: performance-criteria-review

## Why

スクロール性能の完了判定が「壊れた基準」で行われ、新機能を足すたびに不合格が deviation に残る構造になっていた。iOS の合格線 (3 秒窓で hitch time ratio 5 ms/s 未満) は「1 フレームも落とさない」と同値で、基準機で有効に測った値は一度も存在しない。Android の合格線 (`frameOverrunMs` P99 0.0 ms 以下) は foundation 時点の文字だけのグリッドの実測に合わせた退行検出線で、画像グリッドでは到達点 disk でも満たせない。さらに自動駆動 (XCUITest) が主スレッドの 20〜37% を占め、体感を測る土俵そのものを汚していた。

探索 (2026-09-08) で基準の目的を「基準機で、その種類の画面をフリックしてもカクつきを感じないこと」(利用者体感) に定め直し、オーナーの手動フリックを合否に、計測器の数値を証跡にする方針を cross/ADR-0006 (proposed) として起票した。この手順を初めて適用した実機計測で、iOS の「大量件数」(文字だけ・10,000 件) は体感不合格で、主因は compositional layout の estimated 高さの solver (新しく可視になるセルが preferred size を返すたびに 1 セクション 10,000 件を再解決。主スレッドの 55%) と判明した。画像グリッド (正方形セル) では推定と実測が一致して solver が一度も走らず、体感も合格だった。Android は文字グリッド・画像グリッドとも滑らかさは体感合格。

実装フェーズで先に試した最頻値化 (推定高さを直近の実測の最頻値にして、多数派のセルが再解決を起こさないようにする) は、不一致率を 0.032 まで下げ solver の占有率を 55% → 35.9% に減らしたが、**10,000 件では依然として体感不合格で、solver の費用は 2,000 件の 4.1 倍と件数に比例したまま**だった (`evidence/manual-largeData-ios-2026-09-15.md`)。少数派 (7 件ごとの長文行) のセルが可視になるたびに 1 セクション 10,000 件を解き直す費用が残る。design Decision 3 に従い実装を止め、オーナー判断 (2026-09-15) で「提案を改訂して内部セクション分割を追加し、再レビュー後にこの change で実装を続ける」と決めた。本文はその改訂版 (2026-09-16)。

## What Changes

1. **性能検証規約の全面書き換え** (`handbook/ios/performance-verification.md` / `handbook/android/performance-verification.md`、共通の判定規則は `handbook/cross/scroll-performance-gate.md` に新設): 合否はオーナーの体感、数値は証跡。合格線は置かず、参考スケール (WWDC20 の hitch time ratio の推奨値) は合否に読み替えないと明記。fixture は機能ごとの Sample デモ画面 (件数 10,000 は据え置き)。手順は「準備 → オーナーの合図 → 記録開始 → 固定の操作列 → 回収」で、記録の開始は合図を待つ。判定は合格 / 不合格 / 未判定の 3 状態で、迷いや数値との食い違いは非接続の対照で再確認する。証跡には操作条件を残し、体感は数値を見る前に記録する。メモリの「件数比」系統を廃止し、項目単位の保持 (セル・ホスティング・コンポジション) の解放の確認に差し替える。画像の表示待ちは滑らかさとは別の観測点として書き分ける。旧基準・旧値には言及しない。**(実装済み。改訂で iOS の手順に、実機の起動引数の渡し方と、合図の前に画面表示で引数が効いていることを確かめる段を足す)**
2. **iOS エンジンの estimated 高さの solver 対策** (能力: collection-layout)。2 段構成:
   - **最頻値化 (実装済み)**: 推定高さを直近の実測の最頻値にし、推定と同じ高さに測られたセルの自己サイズがレイアウトを無効化しないようにする。効果は不一致率 0.032 で確認済み。単独では不合格 (上記)
   - **行の高さによる合計高さの見積もり (改訂で追加、オーナー指示)**: 本番 fixture (混在 2 列) の合計高さの見積もりをテストの対象にする。item の推定は最頻値のまま、行 (group) の推定を直近の行の高さの平均にして、セルの一致と行の合計を別々の値で満たす (design Decision 15)。基準は一様 1 列と同じで、届かなければ基準を緩めずに止めて相談する
   - **内部セクション分割 (改訂で追加)**: 1 つの配列を内部で固定件数の塊 (内部セクション) に分けて snapshot を組み、レイアウトの再解決の単位を塊に閉じる。塊の件数は列数の候補すべての倍数にして不完全な行を作らず、塊の境界は行間・区切り線・余白・ヘッダー / フッターのいずれにも現れない。塊の分け方は利用者の語彙に現れない。列数が変わって塊が合わなくなれば組み直し、表示位置は項目 ID のアンカーで保つ。効果は**試作 → 実機計測 → 本実装**の順で確かめ (design Decision 13)、判定は事前に固定した数値基準 (不一致率・件数比例・合計高さ) と体感 (design Decision 2)。試作で効かなければ実装を止め、`.absolute` 併用または自前レイアウト (いずれも ADR の改訂を伴う) をオーナーに諮る
3. **Android 計測モジュールの整理** (能力: samples): 絶対基準 (P99 0.0 ms 以下) の廃止、相対基準 (素の Compose に対する劣化 10% 以内) の判定と描画フレーム数の下限 (固定値) を、Macrobenchmark の結果 JSON を事後検証するスクリプトに載せる (不合格・未判定・入力不正は非 0 終了)。比較対象にライブラリの既定機能を付ける条件は維持する。1,000 件の件数比の試行を廃止する。**(実装済み。基準機での相対計測は合格、`evidence/relative-fling-android-2026-09-15.md`)**
4. **iOS 計測ドライバの整理** (能力: samples): 自動フリックの UI テスト 2 本は CI 再訪まで使わないため退役 (実装済み)。メモリの自動往復は残すが、**改訂で「定常化まで往復を重ね、往復ごとの footprint と判定を記録に出す」形に改める** (現状は 2 往復固定で値を残さず、Scenario を判定できなかった。`evidence/memory-roundtrip-ios-2026-09-15.md`)。画像読み込みの観測駆動 (image-loading の証跡取得用) は残す
5. **計測の足場の小修正 (改訂で追加)**: Sample の Xcode プロジェクトの Debug 構成に `DEBUG` の compile 条件を定義し、不一致率の帯の操作が Debug 構成で出るようにする。推定高さの標本は幅だけでなく画面の倍率が変わったときも捨てる (独立レビューの再掲 3 回目の指摘)
6. **再計測と証跡**: 本実装後に iOS「大量件数」(2,000 / 10,000) と「画像グリッド」を新手順で計測し、iOS のメモリ自動往復を改めたドライバで採り直す。Android の証跡は揃え済み。「体感の合否」「計測の成立」「対策の検証」を別々の完了条件にする
7. **ADR**: cross/ADR-0006 を実装後の視点で見直す (accepted への昇格は蒸留時)。内部セクション分割は **ios/ADR-0009 (proposed)** として起票済み (探索のハンドオフ「採用時に ADR 候補として捕捉」に従う)。phase-4 の agenda には「利用者の論理セクションと内部の分割単位の責務」と 3 条件を申し送り済み

影響する能力: collection-layout (iOS の自己サイズ・推定高さ・内部セクション分割)、collection-core (保持対象の寿命)、samples (計測モジュール・計測ドライバ・件数指定)。

## Non-Goals

- **画像の表示待ち (Android で止めてから画像が揃うまでのテンポ)**: 滑らかさとは別の軸で、到達点 memory の方式変更が要る。`prefetch-display-size` の責務 (観測は引き継ぎ済み)
- **Android のスクロールバー非表示**: パリティの穴で性能と無関係。`android-scrollbar-parity` に起票済み
- **`.absolute` 併用と自前レイアウトへの切替**: 前者は DSL の語彙拡張 (core/ADR-0006 と衝突)、後者は ios/ADR-0003 の改訂が要る。内部セクション分割の試作で効かなかった場合の再訪条件として残す (その時点で従う案と改訂案をコスト付きで提示する)
- **塊ごとに異なる推定高さを渡す**: sectionProvider の仕組み上は可能だが、最頻値化で不一致率が 0.032 まで下がっており必要性が未証明。本実装後の再計測で少数派の行の費用が残ると分かった場合の再訪案
- **利用者の論理セクション (phase-4)**: 内部分割はその土台になるが、論理セクションの語彙・sticky ヘッダ・境界の装飾は phase-4 の設計。agenda に責務と 3 条件を申し送るに留める
- **Android 側の対応**: Compose の Lazy 系は表示中の項目だけを測るため、iOS の solver に相当する費用が無い。塊分割は iOS 固有の内部最適化で、Android の語彙・実装は変えない
- **iOS の区切り線・タッチ色の毎レイアウト更新の無駄**: 周辺最適化 (profile 上は solver に比べ小さい)。`ios-separator-update-guard` の責務
- **CI での自動駆動**: 実機の受け皿ができた時点で再訪 (cross/ADR-0006)
- **concepts の追随** (collection-engine の「推定高さは実測平均」「section は常時 1 つ」、image-loading / compose-wrapper の「規約の見直し待ち」): 蒸留 (ksn-distill) で行う

## Impact

- 破壊的変更: 公開 API には無し。Sample の画面・件数も変えない。塊の分け方は `internal` に閉じる
- 規約の変更: 性能検証規約 2 本が全面的に置き換わる (実装済み)。以後のフェーズ (セクション・ページング) の完了判定にはオーナーの手動操作が要る
- iOS エンジン: snapshot のセクション構造が「常時 1 つ」から「固定件数の塊の列」に変わる。区切り線の先頭判定・ヘッダー / フッター・余白・行間の sectionProvider が塊の位置を見るようになる。アンカー・スクロール命令・prefetch・選択は項目 ID → indexPath の解決を経由しており塊に依存しないが、既存テストの `IndexPath(item:section: 0)` 直書きは全体の順番からの変換に置き換える。phase-4 のセクション設計は「論理セクション × 内部の塊」の 2 段を前提にする (ios/ADR-0009 の帰結)
- リスク (最大): solver の費用が「セクション内の件数」ではなく「全セクション」に比例していた場合、塊分割は効かない。試作の実機計測を本実装の前に置いて確かめる (design Decision 13)。効かなければ ADR 改訂を伴う案に戻る
- Android: 計測モジュールのコード変更は事後検証スクリプトの追加と件数比の試行の削除に留まる (実装済み)。ライブラリ本体は変えない
- リスク: 体感ゲートはオーナー 1 人の主観に依存する。固定の操作列・3 状態の判定・非接続の対照で再現性を補い、証跡の操作条件と数値で「比較不能」を明示する

## 級: L

規約 2 本の全面書き換え + iOS エンジンの solver 対策 (snapshot のセクション構造・区切り線判定・sectionProvider・アンカーに及ぶ) + 両プラットフォームの計測モジュールと再計測。完了判定のゲートを変える不可逆性が高く、内部分割は phase-4 の設計を制約する。

domain: cross
