# 行の高さ変化のアニメーション (Android / Pixel 4a)

オーナー実機確認で挙がった「行の高さ変化にアニメーションが無い」の解消を、**行高の毎フレームの
数値**で判定した記録。展開前 / 展開後の静止画では中間状態の有無が写らないため、中間フレームの
本数で見る。

さらに、行の高さだけが動いて**中身が枠から離れる** (何も描かれない帯が出る) ことは行高の数値には
写らないため、観測点を 1 つ足して「中身の下端」と「行の下端 (区切り線)」の差でも判定する。

## 手順 (中間フレームの本数)

- 画面: Sample「検証: 行の高さ変化 (Android 固有)」。操作: 1 行目を 1 回タップ
- 端末: Pixel 4a / Android 13。ウィンドウアニメーションの倍率は 1.0
- 採取: 計測用に本体へ毎フレームのログを 1 か所だけ足したビルドで採り、採取後に外した
- 観測値: 先頭可視項目 (タップした行) の高さ。あわせて次の行の上端も採り、押し出される側の
  移動が同じ値で追従することを確かめた

## 結果 (A/B) — 親 state / list / 展開

| ビルド | 変化区間のフレーム数 | 開始高 → 終了高 | 中間フレーム数 |
|---|---:|---|---:|
| 修正前 (アニメーションなし) | 5 | 132 px → 396 px | **0** |
| 修正後 | 28 | 132 px → 396 px | **23** |

修正前の系列は `132, 132, 396, 396, 396` で、1 フレームで飛んでいる。修正後は次のとおり。

```
132, 143, 169, 200, 232, 262, 287, 310, 327, 343, 354, 364, 371, 377, 382,
385, 388, 390, 391, 392, 393, 394, 395, 395, 396
```

同じフレームでの次の行の上端の系列も同一の値を辿る。展開する行自身の高さの変化がそのまま
下の行の移動になっており、押し出される側の動きも段階を踏む。

この採取は debug ビルドのログの出力回数であり、描画されたフレーム数とは一致しない。

## 結果 — 経路とレイアウトの組み合わせ (修正後)

| 経路 | レイアウト | 向き | 中間フレーム数 |
|---|---|---|---:|
| 親 state | list | 展開 | 23 |
| 親 state | list | 折りたたみ | 23 |
| 親 state | grid (2 列) | 展開 | 23 |
| テンプレート内 state | list | 展開 | 23 |
| テンプレート内 state | grid (2 列) | 折りたたみ | 22 |

親の状態で内容が変わる経路と、テンプレート内の `remember` が変わる経路のどちらでもアニメーション
する。list / grid のどちらでも、展開 / 折りたたみのどちらでも同じ本数の中間フレームを通る。

## 中身と枠が離れないこと (帯の有無)

### 観測手順

行高の本数だけでは、行の中身が枠より先に縮んで**中身と区切り線の間にページ背景の帯が出る**ことは
写らない。そこで、**実装に触れない別経路**で次のように採った。

- 端末の `animator_duration_scale` を 10 にして、行の高さの補間を 10 倍に引き伸ばす
  (Compose のアニメーションはこの倍率に従う)。採取後に 1.0 へ戻す
- 折りたたみの操作を実座標のタップで起こし、直後に画面の静止画を連続で取得する
  (1 枚あたり 300〜500 ms。引き伸ばした区間から 7〜9 枚が採れる)
- 静止画の右端の画素列 (テキストに掛からない位置) を上から読み、
  行 1 の上端の区切り線の直後から次の区切り線までの間に
  **ページ背景色 (242, 242, 246) の画素が何 px あるか**を数える。行の中身は白 (255, 255, 255)
- 観測されるのは実際に描画されたフレームであり、利用者が見るものと同じである

### 結果 (A/B) — 親 state / list / 折りたたみ

修正前は `animateContentSize` を項目の箱に付けた実装、修正後は箱の高さの補間と同時に中身も
その高さで測り直す実装。ビルドを入れ替えて同じ手順で採り、採取後にソースを復元して照合した。

| 経過 (連続取得の順) | 修正前: 行 1 の高さ | 修正前: 中身の下端 | 修正前: 帯 | 修正後: 行 1 の高さ | 修正後: 帯 |
|---|---:|---:|---:|---:|---:|
| 1 枚目 | 393 px | y=1081 (固定) | **261 px** | 392 px | **0 px** |
| 2 枚目 | 354 px | y=1081 | **222 px** | 350 px | **0 px** |
| 3 枚目 | 293 px | y=1081 | **161 px** | 283 px | **0 px** |
| 4 枚目 | 238 px | y=1081 | **106 px** | 218 px | **0 px** |
| 5 枚目 | 196 px | y=1081 | **64 px** | 184 px | **0 px** |
| 6 枚目 | 167 px | y=1081 | **35 px** | 160 px | **0 px** |
| 7 枚目 | 151 px | y=1081 | **19 px** | 146 px | **0 px** |
| 8 枚目 | 141 px | y=1081 | **9 px** | 139 px | **0 px** |
| 9 枚目 | 136 px | y=1081 | **4 px** | 134 px | **0 px** |

修正前は**中身の下端が最初のフレームで折りたたみ後の位置 (y=1081) へ飛び**、そこから区切り線が
降りてくるまでの間がページ背景のまま残る。修正後は中身の下端が区切り線の直上にあり続け、
帯の画素は全フレームで 0 である (行の中身は白のまま、タップのフィードバックで
(253, 253, 253) まで沈む区間があるが、ページ背景色には一度もならない)。

### 結果 — 展開と grid (修正後)

| 条件 | 中間フレーム (連続取得) | 帯 |
|---|---|---:|
| 親 state / list / 展開 | 9 枚 (130 → 389 px) | 全フレーム **0 px** |
| 親 state / grid (2 列) / 折りたたみ | 7 枚 (行の下端 y=1344 → 1100) | 行間 (22 px) を除いて全フレーム **0 px** |

grid では行間 (8dp = 22 px) にページ背景が出るのが正しい表示のため、セルが描いた最後の y と
行間の開始 y の差を帯として数えた。差は全フレームで 0 である。

### 残る条件: テンプレートの根が高さを使わない場合

行の枠に追従するのはテンプレートの根までである。根が背景を塗らず内側の要素が塗っている
テンプレートでは、内側までは追従しない (RecyclerView の既定アニメータでも、行のビューの子は
同じように追従しない)。行の高さの制約が根で止まり、その内側で背景を塗っている要素との間に
帯が残るためである。

Sample の「テンプレート内 state」経路のセルは、`clickable` を付けた**背景を塗らない箱**で
本文を包んでおり、この条件に当たっていた (同じ手順で帯 260 → 2 px)。**この箱に高さの制約を通す
指定 (`propagateMinConstraints = true`) を Sample へ恒久的に入れて解消した。** 同じ手順で採ると
帯は全フレームで 0 px になる (392 / 350 / 287 / 231 / 191 / 166 / 150 / 141 / 135 px のいずれでも
中身の下端は区切り線の直上)。原因が本体側ではなくテンプレートの構造にあることの確認でもある。

同じ構造を書く利用者が同じ条件を踏むため、テンプレートの根へ高さの制約を渡すことは利用契約と
して `KsCollectionView` の doc コメントに書いてある。

## 大量件数への副作用 (修正後)

`animator_duration_scale` を 10 にしたまま Sample「大量件数」を開き、初期表示直後とフリック 2 回の
それぞれで静止画を 3 枚ずつ採り、右端の画素列から行の高さを数えた。

| 場面 | 現れた行の高さ |
|---|---|
| 初期表示直後 (3 枚) | 132 px と 303 px の 2 種のみ |
| フリック 1 回目の直後 (3 枚) | 同上 (画面端で切れた分を除く) |
| フリック 2 回目の直後 (3 枚) | 同上 |

同じ場面で連続して採った 3 枚はいずれも同一であり、動いている途中の高さは 1 件も出ない。
再利用時に前の項目の高さから補間が始まる副作用は無い。

## 検証層のテストとの対応

同じ判定を Robolectric でも掛けている (`KsCollectionViewLayoutTest`)。クロックの自動進行を止めて
フレームごとに位置を記録する。

| テスト | 経路 / レイアウト | 観測点 |
|---|---|---|
| `rowHeightChangeFromParentStateAnimates` | 親 state / list | 下の行の上端が中間の位置を通る |
| `rowHeightChangeFromTemplateStateAnimates` | テンプレート内 state / list | 同上 |
| `rowHeightChangeAnimatesInGrid` | 親 state / grid (2 列) | 同上 |
| `headerHeightChangeAnimates` | ヘッダー / list | ヘッダーに押される先頭項目の上端が中間の位置を通る |
| `rowHeightCollapseKeepsContentBottomAtRowBottom` | 親 state / list / 折りたたみ | 中身の下端と行の下端の差が全フレームで 0 |
| `rowHeightAnimationClipsContentIgnoringHeightConstraint` | 親 state / list / 展開 | 制約に従わない content の画素が、補間の中間フレームで行の下端より下に出ない |
| `reusedItemDoesNotInheritPreviousRowHeight` | 親 state / list / 再利用 | 補間中に画面外へ送った項目が、戻したときの最初のフレームから本来の高さで現れる |

アニメーションの修飾を外すと最初の 4 件はいずれも失敗する (中間フレーム 0)。中身へ高さの制約を
渡さない実装に戻すと `rowHeightCollapseKeepsContentBottomAtRowBottom` だけが失敗する (帯 160 px)。
補間中の切り取りをやめると `rowHeightAnimationClipsContentIgnoringHeightConstraint` だけが失敗する。
`reusedItemDoesNotInheritPreviousRowHeight` は再利用の往復での見え方を押さえるものであり、
検証層では項目の破棄で状態が捨てられるため、再利用時の後始末だけを外しても失敗しない。

## 実装の選択

行の高さの補間は自前の修飾 (`ksAnimatedHeight`) で行う。`animateContentSize` は子を新しい自然高で
測ってから外へ報告するサイズだけを補間するため、縮む向きで上の帯が出る。自前の修飾は補間中の
高さで子を測り直すので、中身の背景が枠と同じ量で伸び縮みする。

測り直しても縮まない content (`Modifier.requiredHeight` のように渡した制約に従わないもの) がある
ため、**補間している間は描画を行の高さで一律に切り取る**。測り直した結果の高さは制約へ丸められた
値であり、どれだけはみ出しているかは測定結果からは分からないためである。補間していない通常時は
切り取らない。切り取りは描画時に行い、合成レイヤは作らない (大量件数のスクロールへの上乗せを
避けるため)。

項目の配置アニメーション (`animateItem`) を重ねる案も試したが、無しでも中間フレームは同数
得られ、性能の上乗せだけが残るため採らない (性能の実測は performance-measurement.md の追補を見る)。
