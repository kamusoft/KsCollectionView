# Proposal: prefetch-display-size

## Why

到達点 `memory` の先読みは URL だけの鍵で元寸をメモリに載せ、`KsImage` は「URL + 枠の実サイズ + 当てはめ方」の鍵で縮小済みの画像を探すため、両者は一致しない。いまは表示側がメモリの元寸を同期で枠サイズへ縮小して継いでいるが、Android の実機では先読みが載せる元寸がハードウェアビットマップ (画素を CPU から読めない) になり、この縮小が成立しない。初回表示は読み込み中を経由してディスクから縮小デコードし直し、到達点 `memory` は `disk` に対して元寸のデコードとメモリ保持の費用だけ余分に払う。spec「メモリ到達点の後の表示 (ネットワークもデコードのやり直しもなし)」が実機で破れ、iOS (UIImage は常に読める) との非対称が残っている (image-loading の deviation 2026-09-08 で一時容認、解消は本 change)。ハードウェア支援を切る回避策は描画のたびに画素の転送費用が乗り、基準機で frameOverrun P99 18〜21 ms を出したためオーナー方針で不採用。

同日の手動計測で、Android の画像グリッドは「止めてから画像が揃うまで」が iOS より数テンポ遅い体感が記録されている。ただし到達点が未記録 (デモ画面の初期選択は `disk`) のため、本 change の方式で改善する範囲かはまだ確かめていない。

## What Changes

方針は core/ADR-0013 (proposed。本 proposal の承認で確定し、蒸留で accepted にする) のとおり。2 つの変更を両プラットフォームに入れる。

1. **表示側の引き当てを、鍵の完全一致から許容範囲の照合に変える。** `KsImage` は同じ URL でメモリにある項目の実物の寸法と枠を比べ、許容範囲 (下限・上限) の内側なら CPU で縮小せずそのまま初回描画に使い、描画時に枠へ合わせる。範囲内の項目があればローダーへの取得要求は出さない。範囲外の項目しか無ければ、従来どおり枠の実サイズで縮小デコードする。ハードウェアビットマップのままで成立するため、Android の `Unreadable` 分岐 (CPU の同期縮小) は不要になる。鍵から当てはめ方 (`ks#scale`) が外れる。
2. **先読み宣言の要素を `KsResource` (URL + 任意の幅) にする。** 幅は `KsWidth` の「列幅」(ライブラリが画面幅・列数・余白から解く) と「固定値」(pt / dp の 1 値) の 2 種類で、省略すると元寸。先読みは幅のある要素をその幅に縮小デコード (元が小さければそのまま、拡大しない) してメモリに載せ、幅のない要素は到達点 `memory` で従来どおり原寸を載せる (表示は 1. の引き当てで原寸を使う)。入口は `prefetchResources` 1 本のままで、URL だけの配列 (`[URL]` / `List<String>`) は廃止する。

付随して:

- 先読み台帳を URL 単位から「要求 (URL + 幅) 単位」にする。列幅は回転・列数変更で変わるため、以後の先読みは新しい幅で出す
- ライブラリが URL ごとに「メモリに載せた項目の鍵」の索引を持つ (Nuke に近似の引き当てが無く、Coil の `Precision.INEXACT` は下限 1.0・上限なしで本 change の許容範囲と一致しないため)。索引は引き当ての手掛かりで、実在と寸法の正はローダーのキャッシュ。索引は上限つきで、外れた項目は引き当てず通常の縮小要求に落ちる (契約はこの限定を含む)
- 先読みの取得単位は到達点で決まる: `disk` は URL 単位 (幅を使わない)、`memory` は URL + 幅 px 単位 (幅なしは URL のみ)。幅の無効値 (0 以下・非有限) は不正入力 (core/ADR-0011)、列幅が 0 以下に解ける間は列幅の先読みを開始しない
- Sample「画像グリッド」に列幅の選択肢を足し、`KsResource` の形に書き換え、両プラットフォームの文言をそろえる (sample-parity)
- 実機テスト `KsImageDeviceDecodeTest` の前提 (元寸が URL 鍵に載り、読めないと初回描画に使わない) を新しい契約に書き換える

影響する能力: image-loading (先読み宣言 (破壊的)・到達点・`KsImage` の縮小デコードと表示状態・読み込み取り消しとメモリ保持・Sample のデモ画面)。

## Non-Goals

- **表示から学んで先読みに使う方式 (A-2)** — 学習表・レイアウト世代・窓の再評価が要り重い。宣言で書けない実例が出たときに別 change で足す (ADR-0013 Revisit When)
- **到達点 `disk` の初回表示の速さ** — 取得 → 表示時の縮小デコードは本方式で変わらない。画像 1 枚ごとの subcomposition (`BoxWithConstraints`) や cold の取得は別要因で、本 change の計測で切り分けた結果を申し送る
- **ローダー付属ビュー (`LazyImage` / `AsyncImage`) の直接使いでの縮小済み項目の利用** — 引き当てはライブラリの `KsImage` の中にあるため対象外。共有キャッシュによる再ダウンロードなしは維持
- **高さ・縦横比・当てはめ方の宣言** — 当てはめ方は View の仕事 (ADR-0013 で却下)
- **image-loading の deviation の書き換え** — 足場は凍結。本 change の完了で「解消は prefetch-display-size」の記述が事実になるだけで、蒸留時に concepts へ反映する

## Impact

- 公開 API: **破壊的変更あり (配布前)**。`prefetchResources` の戻り値が `[URL]` / `List<String>` から `[KsResource]` / `List<KsResource>` に変わる。新設の公開型は `KsResource` と `KsWidth`。`KsImage` の引数は変えない。phase-7 (配布) より前なので影響は Sample と自社の試用コードに限られる
- 挙動の変更 (既存利用者に見える): `KsImage` が枠と違う寸法のメモリ項目を許容範囲で使うようになる。枠より大きい項目は描画時に縮むだけで見た目は変わらない。枠より小さい項目 (下限以上) は軽く拡大されるため、概算を小さく書いた場合にわずかに甘くなりうる。到達点 `memory` + 幅なしの実機挙動は「読み込み中を経由」から「原寸を即描画」に改善
- spec: image-loading の Requirement「プリフェッチ宣言」「プリフェッチの取り消し」「プリフェッチの到達点」「KsImage の縮小デコード」「KsImage の読み込み取り消しとメモリ保持」「KsImage の表示状態」「Sample のデモ画面「画像グリッド」」を MODIFIED (7 本)、「プリフェッチの表示幅」「KsImage のメモリ項目の引き当て」を ADDED (2 本)
- リスク: (1) 許容範囲の値 (下限・上限) の妥当性は実機の見た目で決める。(2) 索引とローダーのキャッシュの整合 (LRU 追い出し・`clear` / `remove` の世代) — 索引の項目をキャッシュで検証してから使う設計で吸収する。(3) 「同じ鍵にすれば表示待ちの体感が良くなる」は未証明 — 先頭の工程で到達点 `memory` の手動計測を行い、対象範囲を確かめてから本実装に入る
- 決定との関係: core/ADR-0013 (proposed) が core/ADR-0008 を amends。phase-8 agenda「サイズヒント付き宣言は却下」と image-loading design Decision 5 の却下案 A / C の前提は ADR-0013 で改訂 (蒸留時に参照を残す)。agenda「縮小の既定は自身のレイアウトサイズ」は「範囲内のメモリ項目が無いときの縮小の目標」として維持し、範囲内の項目を優先する規則が前に付く。agenda「`KsImage` は縮小サイズの手動指定を持たない」は維持 (許容範囲は公開 API にしない)
