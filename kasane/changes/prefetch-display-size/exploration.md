# Exploration: prefetch-display-size

## 課題 / 動機

先読み到達点 `memory` の方式を「元寸をメモリに載せ、表示側 (`KsImage`) が枠に合わせて同期縮小する」から「先読みの時点で表示サイズを知り、表示と同じ鍵 (URL + 表示サイズ + 当てはめ方) で縮小デコードして載せる」に改める (案 A)。

`image-loading` (L 級) の実装フェーズ (tasks 7.5、Android 画像グリッドの実機計測) で発見した方式の帰結。2026-09-08 にオーナーが別 change として積むと判断した。

発見の文脈と根拠 (詳細は `kasane/changes/image-loading/` の evidence / deviation。archive 後は `kasane/changes/archive/*-image-loading/`):

- 基準機 Pixel 4a で到達点 `memory` の frameOverrun P99 が 18〜21 ms (絶対基準 0.0 ms 以下、再現済み)。到達点 `disk` は 6.2〜6.4 ms
- 原因 (コード読解ベース。trace は成果物として残っていない): ①表示側の composition 内で新規セルごとに走る同期縮小 (元寸の画素数に比例) ②ハードウェア支援ビットマップは画素を読めず同期縮小で落ちるため、先読みに `allowHardware(false)` を付けた結果、載る画像も縮小結果もソフトウェアビットマップになり描画のたびにテクスチャアップロードが乗る
- **オーナー方針: ハードウェア支援を切る回避策は採らない**。緩和策 (縮小の閾値緩和) や到達点 `memory` の基準の別扱いも却下
- 設計の系譜: image-loading の design Decision 5 で「先読み時点で枠サイズが要る案」を却下 (`KsImage` がセル全体を占めるとは限らないため) → その帰結として「元寸を載せて表示側で縮小」に至った (deviation 2026-09-07「到達点メモリの先読みと表示の継ぎ目」)。本 change はその判断の再訪

現行との対比資料: 先読み・初回表示・2 回目の 3 局面の対比を image-loading の実装フェーズで HTML にまとめた (claude.ai の artifact「先読みを表示サイズで出す案」。ローカルには残していない)。要点: 差が出るのは到達点 `memory` の先読みと初回表示だけで、到達点 `disk` と 2 回目 (戻り) はどちらの案でも同じ。サイズが分からない / 一致しないケースは壊れるのではなく到達点 `disk` と同じ動き (読み込み中を経由) に落ちる。

### 追加の観測 (2026-09-08、performance-criteria-review の手動計測より)

cross/ADR-0006 (proposed) の手順で Pixel 4a の「画像グリッド」を cold からオーナーが手動フリックした体感: スクロール自体はスムーズだが、**画像のレスポンスが iOS と比べて数テンポ遅れ、止めて少し待つと画像が揃う**。体感としてよくない。iPhone 11 では「一度読み込んだ画像はすぐに表示される」で差が無い。gfxinfo はフレーム時間 20 ms の山 (735 フレーム) と janky 2.14% を示すが、滑らかさの体感は合格。証跡: `../performance-criteria-review/evidence/manual-imageGrid-android-2026-09-08.md`。本 change の合否は「止めてから画像が揃うまで」の体感で見る必要があり、滑らかさのゲートとは別の観測点になる。

## 検討した選択肢 (却下案と理由を含む)

(未探索。以下は起票時点の材料)

サイズをどう知るかの取り方:

| 取り方 | 動き | 起票時点の見立て |
|---|---|---|
| A-1 宣言で受け取る | 先読み宣言で URL と一緒に表示サイズ (pt / dp) と当てはめ方を返してもらう | 予測可能だが公開 API が変わり利用者負担 |
| A-2 表示から学ぶ | 同じコレクションで `KsImage` が要求した (サイズ, 当てはめ方) を覚え、以後の先読みに使う | API は不変。最初の 1 画面は学習前。混在レイアウトで曖昧になる |
| A-3 併用 | 宣言があれば A-1、無ければ A-2、どちらも無い間は `disk` 到達点として振る舞う | **オーナーの推し**。相方相談役も推奨 (下記) |

相談役 (counterpart / codex、ksn-advise、2026-09-08) の助言の要点 — 出典: advisor (counterpart / codex):

- **A-3 を推奨。ただし自動学習は「対応が一意に絞れる場合だけ」に限定し、曖昧なら `disk` に落とす**。観測した全サイズを全 URL に掛け合わせる設計は不採用
- 優先順: 宣言された表示条件 → 同じ「表示用途」で学習した条件 → 未学習・対応不明・複数候補なら `disk` まで → 表示側は常に実測サイズを正とし、完全一致の項目が無ければ通常の非同期縮小デコード
- 学習キーは「コレクションのインスタンス × レイアウト世代 × テンプレートの値キー × 画像用途 (avatar / cover 等)」。テンプレートだけでは同じセル内のアイコンと本文画像を区別できない。URL や配列順序も用途の代替にはならない
- 自動学習の最小構成は「対象 URL と `KsImage` の対応が一意で、同じテンプレート内の観測条件も一致する」場合のみ。同じ世代・用途で違うサイズを観測したら「曖昧」にして推測を止める (直近 N 個の多数決は初版に不要)
- 寿命: セル破棄では忘れず、コレクション破棄で全消去。配置条件の変更 (幅・列数・表示倍率・文字サイズ) でレイアウト世代を進める。学習表は件数上限つき LRU でよい (消去保証を担う台帳とは別物)。学ぶのは成功画像の寸法ではなく**レイアウト確定時の要求寸法**。観測の通知は composition / body 評価中の直接更新ではなく確定後に差分通知
- 公開 API: 既存の URL 配列を返す軽量形は残し、詳細形として `{url, role?, target?}` (用途キー、幅・高さ・当てはめ方) を返せるようにする。戻り値型だけでオーバーロードせず引数ラベル等で区別。表示側 (`KsImage`) にも任意の用途キーを渡せる形を設ける。UI 宣言の戻り値なので KMP 共有モデル無改造・単一型配列・モデル純粋性の 3 軸は守れる (core/ADR-0004・0008 と整合)。明示寸法は Swift pt / Kotlin dp とし表示側と同じ変換・丸めで整数 px に正規化。セル幅から画像枠を一律推定する便利機能は Decision 5 の問題を再導入するので避ける
- 反対案: A-1 のみ (学習の複雑さを許容できないなら有力)、A-2 のみ (可変枠・未登場テンプレートを解決できない)

## 決定事項

- 探索 (2026-09-22) 論点 1「達成したいこと」: **1-c = 契約の回復を本体にし、Android の表示待ちは計測して確かめる**。本体は「到達点 `memory` を選んだら実機でも初回表示が読み込み中もデコードのやり直しも経由しない (spec の SHALL を両プラットフォームで満たす)」。Android の表示待ちの体感不良 (2026-09-08 の手動計測) はデモ画面の初期選択が「ディスクまで」で到達点が未記録のため、**到達点 `memory` で手動計測をやり直して本 change の対象かを確かめる工程を先頭に置く**。`disk` の初回表示 (取得 → 表示時の縮小デコード) は本方式では変わらないので、そこで残る分は本 change の対象外と明記する
- 論点 2「先読みが表示サイズを知る取り方」(2026-09-22): **A-1 (宣言) を採り、A-2 (学習) は見送り** (却下ではない。宣言で書けない実例が出たら追加)。オーナーの「ジャストサイズでなくてよい」を起点に、次の形に収束:
  - 宣言は URL ごとの**概算の幅だけ**。種類は「列幅」(ライブラリが画面幅・列数・余白から解く) と「固定値」(pt / dp の 1 値) の 2 つ。高さ・縦横比・当てはめ方は持たない (当てはめ方は View の仕事)
  - 先読みはその幅に縮小デコード (元が小さければそのまま、拡大しない) してメモリに載せる。概算は大きめに書く運用
  - **表示は鍵の完全一致をやめ、同じ URL の項目の実物の寸法と枠を比べて許容範囲 (下限・上限) の内側なら使い、描画時に枠へ合わせる**。下限は拡大ぼやけ、上限は GPU 縮小のざらつきとテクスチャ上限の回避。範囲外なら枠の実サイズで縮小デコード
  - **素の配列 (URL だけ) は残し、到達点 memory では原寸を載せる**。表示は同じ許容範囲の引き当てで原寸を使う。CPU の同期縮小 (`Unreadable` 分岐) は不要になり、Android 実機でも成立する
  - 外形 (propose で確定 2026-09-22): 入口は `prefetchResources` 1 本のまま、要素を `KsResource(url, width:)` に。幅は `KsWidth` (`.column` / `.fixed(40)`、Kotlin は `KsWidth.Column` / `Fixed(40.dp)`)、省略で元寸。`[URL]` / `List<String>` は廃止 (配布前)。別名の入口 (`prefetchImages`: 区別がつかない)・オーバーロード (Kotlin で Composable の複製)・ファクトリ混在・`Dp` 番兵はオーナー判断で却下
  - 却下: バケット化 (刻みをまたぐと外れる)、下限なし (ぼやけ事故)、下限 1.0 (大きめを強いる)、上限なし (巨大原寸)、幅+高さ+当てはめ方の宣言
- 追加探索 (2026-09-23) 論点 1「任意キーを指定する場所」: **A = 先読みの要素 `KsResource` と `KsImage` の画像ソース (`KsImageSource.remote` / `Remote`) の両方に同じ任意キーを持たせる**。動機はオーナーの追加要望「署名付き URL のように毎回変わる URL は鍵に使えないので、`KsResource` で任意のキーを指定し、キーがあればキー文字列を基に鍵を作る」。`KsResource` だけ (B) では表示側が URL で鍵を作るため先読みが当たらない。引数名は `cacheKey` ではなく **`key`** (オーナー判断)。書き口: `KsResource(url, width: .column, key: photo.id)` / `.remote(url, key: photo.id)`、Kotlin `KsResource(url, width = KsWidth.Column, key = photo.id)` / `KsImageSource.Remote(url, key = photo.id)`。既定値は省略 (nil / null) で、既存の `.remote(url)` / `Remote(url)` はそのまま通る
  - 却下: C「URL → キー変換をアプリ全体で 1 つ登録」(URL から作れないキーを書けない・大域状態。署名がクエリだけの場面の手軽さは Revisit When で A に足す余地)、D「`KsResource` にだけ書き、先読み宣言から URL → キーの対応を覚える」(先読みは画面内のアイテムを宣言対象にしない — Android の窓は可視範囲の先だけで起動直後のセルは窓の更新より先に作られる、iOS の `prefetchItemsAt` は初期表示のセルに来ない — ため起動直後の 1 画面が URL の鍵になる)、D'「D + セル表示時にも宣言を評価して登録」(コレクション外・先読み未宣言の `KsImage` で黙って URL の鍵へ戻る見えない結合、実装も重い)
- 追加探索 (2026-09-23) 論点 2「キーが効く範囲」: **取得 (ネットワーク) 以外のすべてでキーを URL の代わりに使う** — メモリの鍵 (幅・枠サイズの付け足しはそのまま)、ディスクの鍵 (iOS は `imageID`: Nuke の `makeDataCacheKey` とメモリ鍵の両方に効くことを checkout で確認、Android は `diskCacheKey`)、削除の世代、鍵の索引、先読みの取得単位と `fence`、`KsImageCache.remove(source)` (画像ソースにキーがあればキーで消す)。ローダー付属ビューを URL で直接使う場合とは項目を共有しない (壊れない)。キーは画像の中身を一意に特定する文字列であることを利用者向けの注意書きに含める
- 前提の更新: 起票の直接の動機だった到達点 `memory` の frameOverrun P99 18〜21 ms は、オーナー判断 C (`allowHardware(false)` の撤去) 後に 4.4〜4.6 ms (`disk` の 6.2〜6.4 ms より軽い) まで下がっている。滑らかさは動機から外れ、残るのは「実機で `memory` が `disk` に対して費用だけ余分に払う (spec 違反・iOS との非対称)」と表示待ちの体感

## 未決の論点

探索 2026-09-22 で論点 1〜2 を決定。方式の骨格は決まり、以下は propose / 実装で詰める残り (起票時の疑問のうち A-2 学習に関するもの — 学習完了時の窓の再評価・学習世代 — は見送りに伴い消えた):

- 許容範囲の下限・上限の値 (例: 下限 0.5、上限 4 倍)。上限を超える原寸は使わず縮小デコードし直す
- Android の引き当ての実現: Coil の `Precision.INEXACT` で下限側が得られるか、上限は自前判定になるか (実物での裏取り)。自前の `coil#size` / `ks#scale` extras を鍵から外す
- iOS の引き当ての実現: Nuke に近似の引き当てが無いため、URL ごとに載っている寸法の索引をライブラリが持つ設計 (寿命・消去との同期)
- 列幅の解決の置き場: iOS は `KsLayoutMetrics` + bounds、Android は `resolveGridCells` + 可視情報。回転・列数変更後の先読みは新しい幅で出す
- 詳細形の名前 (Swift の引数ラベル / Kotlin の引数名) と型名 (`KsPrefetchResource` / 幅の enum)

追加探索 (2026-09-23、任意キー) の残り — propose の改訂 (2026-09-23) で解決し design Decision 9 に反映:

- `key` を持てる画像ソース → リモートだけ (ファイル・アセットには持たせない)
- 空文字の `key` → 不正入力 (core/ADR-0011。release は警告して `key` なし)
- 同じ `key` で URL が違う同時取得 → 統合しない (Nuke はネットワーク取得を `originalImageID` = 元の URL で統合するため別取得になり、同じ鍵へ保存される)
- 便宜形 `KsImage(url, key:)` も足す。先読みの宣言の突き合わせは当初「識別子で行い取り直さない」としたが、相方 spec レビュー 002 #3 (失効した URL の先読みが回復しない) を受けてオーナー判断で「URL も含め、URL が変われば新しい URL で出し直す (取得済みならキャッシュに当たる)」に改めた

起票時からの残り:

- spec の改訂範囲: image-loading の Requirement「プリフェッチの到達点」は memory 完了後の同じ URL の表示に再デコード不要を要求している。「有効な表示条件が得られれば memory、得られなければ disk」「同じ表示条件の項目が残っていれば即時」に書き換える必要がある。「メモリにあれば読み込み中なし」も「利用可能な同一要求の項目」を指すと明確化する。Requirement「縮小デコード」の「元寸を保持しない (到達点 memory は対象外)」の但し書きは不要になる
- 学習完了時の窓の再評価: Android は初期表示時から次の可視件数分を先読みする。学習が完了しても既に `disk` で出した窓は自動で memory に昇格しない。**学習更新時に現在の窓を一度だけ再評価して画面外の対象を昇格**する処理が要る (無駄な取消・再取得にならない接続を実ローダーで確認)
- 先読み台帳の単位: 現在の URL 台帳 (URL → 参照数) では同じ URL の小枠用と大枠用を独立管理できない。アイテムが所有する要求集合と、要求ごとの参照数・開始時のハンドルを保持する。取消時に学習値から要求を作り直すと開始時と違う鍵を消す
- 学習世代と画像削除世代 (`KsImageCache` の世代) は別物。回転で学習を忘れても共有キャッシュは消さない。`remove` / `clear` は全サイズの旧要求を止める
- 鍵一致だけでなく要求全体の共通化: サイズ・当てはめ方・precision・世代・キャッシュ識別を先読みと表示で共通化し、表示時は同期のキャッシュ参照だけを残す。現行の手動書き込み (`memory.set`) に依存せず、**実ローダーの先読みが書いた項目**で初回から成功表示できることが検証対象。Android の `coil#size` のようなローダー依存部分も採用版で確認
- ローダー付属ビュー (`LazyImage` / `AsyncImage`) をサイズなしで直接使う利用者は、元寸のメモリ項目に当たらずディスクへ落ちる。「再ダウンロード無し」は維持されるが表示待ち時間は退行。「共有キャッシュ」と「同じデコード済み画像へのヒット」を分けて説明する
- **同じ鍵にすれば性能基準を満たす、までは未証明**。到達点 `disk` の 6 ms も別要因 (画像 1 枚ごとの `BoxWithConstraints` の subcomposition、cold でフリング中に取得・デコードが走る取り決め) で残る。正しいヒット・学習前・サイズ不一致・混在配置・回転・削除中の取得について、取得 / デコード回数と実機 trace を対応させて確認する計測計画が要る (trace を実行ごとに退避する手順も含む)
- `BoxWithConstraints` (画像 1 枚あたり subcomposition 1 段) は「初回 composition で枠を同期に読む」ために残るのか、`rememberConstraintsSizeResolver()` に戻せるのか
- image-loading 側の扱い: 到達点 memory の性能不合格と `allowHardware(false)` の暫定回避を deviation に残したまま完了扱いにするか、本 change と一体で閉じるか

## 変更級の推奨

**L** (オーナー確定 2026-09-22)。材料: 公開 API の追加 (先読み宣言の詳細形、core/ADR-0008 の amends)・先読み台帳の要求単位化・`KsImage` の引き当てを鍵の完全一致から許容範囲へ・列幅の解決・spec の Requirement 3 本の改訂・両プラットフォームで引き当ての実現手段が違う (Coil `INEXACT` の裏取り / Nuke は自前の索引)・実機計測 (先頭に到達点 memory の手動計測、最後に合否)・実機テスト 4 本の前提書き換え。UI 変更なし。M と迷う材料が 2 つあるため「迷ったら 1 段上」で L。

追加探索 (2026-09-23、任意キー) を同梱しても **L のまま** (公開型 `KsResource` / `KsImageSource.remote` の形がさらに変わり、鍵の基準の切り替えが両プラットフォームのメモリ・ディスク・世代・索引・台帳・消去にまたがる。級を上げる要素はあっても下げる要素はない)。
