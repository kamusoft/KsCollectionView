# 独立 spec レビュー: prefetch-display-size

**判定: CHANGES_REQUESTED**（Major 3 件）

今回追加された `key` には、別画像の取り違えと、削除後に古い画像が戻る可能性があります。実装前に識別子と再取得の契約を決める必要があります。

### 🟠 Major: `key` と URL が同じ鍵空間で衝突する

**該当箇所:** `specs/image-loading/spec.md:84`、`specs/image-loading/spec.md:310`、`design.md:144-157`  
**問題点:** 識別子を「`key` があればその文字列、なければ URL」とすると、画像 A の `key` が画像 B の URL と同じ場合、両者が同じキャッシュ項目・先読み台帳・削除対象になります。これは「`key` なしのソースでは `key` 付き画像を消さない」という Scenario にも反します。さらに iOS の `key#世代` は、別画像の通常の `key` と衝突し得ます。  
**推奨修正:** `key`、URL、世代を衝突しない形で符号化する規則を仕様化し、この二種類の衝突を Scenario に追加してください。`key` なしの既存ローダーとの共有も維持できる規則が必要です。

### 🟠 Major: Android の削除後に旧要求がキャッシュを書き戻せる

**該当箇所:** `design.md:157`、`specs/image-loading/spec.md:288`、`tasks.md:24`  
**問題点:** Android の提案は削除前後とも `memoryCacheKey`・`diskCacheKey` に同じ `key` を使います。削除前に始まった表示要求が `remove` の復帰後に完了すると、旧画像を同じ鍵へ書き戻せます。索引の削除や表示の再構築だけでは、「削除前の項目に当たらない」という SHALL を保証できません。提案本文の「削除の世代にも `key` を使う」と、Android の鍵への写像も揃っていません。  
**推奨修正:** 進行中の表示・先読み要求を含め、削除後の書き戻しをどう防ぐかを定めてください。削除と完了が競合する Scenario を両プラットフォームの契約テストに加えてください。

### 🟠 Major: 署名 URL の更新後、失敗した先読みを回復できない

**該当箇所:** `specs/image-loading/spec.md:101-104`、`specs/image-loading/spec.md:137`、`design.md:85-89`  
**問題点:** 同じ `key` の URL 差し替えでは進行中の要求を出し直さない契約です。旧署名 URL が失効して要求が失敗した場合、新しい有効な URL が宣言されても、アイテムが先読み窓に残る間は再試行の条件がありません。署名付き URL を支えるという追加目的に対する穴です。  
**推奨修正:** 旧要求が失敗したとき、新 URL で再試行するか、窓への再入場まで先読みを諦めるかを明記してください。前者を選ぶなら、URL 更新中の失敗と再試行を Scenario にしてください。

**照合した規約:** Sample のプラットフォーム間一致、実行時挙動の検証規約、スクロール性能の体感ゲート、iOS／Android の性能検証手順。静的レビューのため、ビルド・テストは実行していません。前回レビューの証跡は判断材料にしていません。
