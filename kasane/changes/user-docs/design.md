# Design: user-docs

## Context

フェーズの議論で決まったことは、次のとおりである (`kasane/roadmaps/v1-foundation/phases/phase-7-3-user-docs/agenda.md` の決定事項)。

- 利用者向け Skill は、プラットフォーム別の 2 つを英語と日本語で持つ (cross/ADR-0005)。`references/` は、利用者のやりたいことで 5 枚に分ける
- 追従は、オーナーが頼んだときにだけ行う。前回追従した commit からの源泉の差分で見分け、手順は handbook、機械で行う部分は `scripts/` に置く (cross/ADR-0017、proposed)
- インストール例には版を書かず `{version}` を置く (cross/ADR-0018、proposed)
- Skill の外への参照は、知識を委ねるものを持たず、操作の対象の URL は書いてよい (cross/ADR-0019、proposed)
- README の最小コード例は、利用者役の画面のファイル全体と一致させる。README にスクリーンショットを載せる
- Skill 自身の整合の検査は、検証 CI のスクリプトのテストでも毎回流す。公開 API の名前の漏れは、コードの公開の宣言と比べる。初回の制作は、配った先を再現して確かめる

今のリポジトリは次の状態である。

| 対象 | 状態 |
|---|---|
| `skills/` | 無い |
| ルートの README | 英日 2 枚。「準備中」の案内・ライセンス・貢献の 3 つの節 |
| 源泉 | 利用者向けの契約を書いた concepts は core の 6 枚 (合計 1,312 行)。プラットフォーム別の concepts 8 枚は内部の仕組みが中心で、利用者に関わる記述を一部に持つ |
| 利用者役 | `verification/ios/` は画面とモデルの 2 ファイル、`verification/android/` は画面 1 ファイルと入口。どれも日本語の説明のコメントを持つ |
| 検証 CI | lint のジョブが `scripts/ci/tests/` のテストを毎回流す (`scripts/ci/run-tests.py`)。README の英日の見出しの一致と導線を見るテストが既にある (`scripts/ci/tests/test_repository_files.py`) |
| 公開の宣言 | iOS は 90 個ほど。Android は公開の宣言に必ず `public` と書く設定 (explicitApi) で、70 個ほど |

兄弟ライブラリの実物 (`../KsSettingsView/skills/`・`../KsSettingsView/README.md`・`../KsSettingsView/scripts/readme-example-lint.py`・`../KsSettingsView/scripts/install-example-lint.py`) を、書き方の参考にする。追従の道具 (`../KsSettingsView/.agents/skills/docs-refresh/`) は、形が違うので写さない。

### 提案の段階で試して確かめたこと (2026-10-10)

リポジトリの外の作業用の写しで試した。リポジトリのファイルは変えていない。

| 試したこと | 結果 |
|---|---|
| iOS の利用者役の画面とモデルを 1 ファイルにまとめ、コメントと `public` を外して、確認のスクリプトを `local` で流す | Simulator 向けと実機向けの両方が成功した |
| Android の利用者役の画面を、package の宣言を持たないファイルに置き、宣言を持つ入口からそのまま呼ぶ | コンパイルが失敗した (呼ぶ側から名前を解決できない) |
| 上の入口に、画面の名前だけを書いた import を 1 行足して、確認のスクリプトを `local` で流す | コード縮小を有効にした組み立てと、依存の確認が成功した |

確かめていないこと: 書き直した Android の利用者役の起動 (実装で 1 回確かめる)。公開の宣言から名前を拾う処理の誤検出の量 (実装で、外す一覧を作りながら確かめる)。

## Goals / Non-Goals

Goals:

- 利用者が、README を読んで何ができる部品かが分かり、Skill を自分のプロジェクトにコピーして使い始められる
- README に載っている例が、検証 CI でビルドされているコードそのものである
- `skills/` と README を手で直したときの崩れ (片方の言語だけの更新・Skill の外へのリンク・具体の版) に、その push の回で気付ける
- オーナーが追従を頼んだときに、どの源泉が変わり、どの Skill の 1 枚を見直すかが、道具で分かる

Non-Goals は proposal.md のとおり。

## Decisions

### Decision 1: Skill のファイルの置き方と、1 枚の中の並び

**採用案:** 4 つの Skill のディレクトリは、同じ 6 枚を持つ。

```
skills/
├── README.md / README_ja.md          索引
├── .manifest.json                    追従の記録 (Decision 7)
└── {en,ja}/kscollectionview-{ios,android}/
    ├── SKILL.md
    └── references/
        ├── basics.md                 一覧を出す
        ├── layout.md                 並べ方と見た目
        ├── paging.md                 ページングと Pull to Refresh
        ├── reorder.md                並べ替え
        └── images.md                 画像
```

- `SKILL.md` の frontmatter は `name` (ディレクトリの名前と同じ)・`description`・`license` (`MIT`)・`metadata.language` (`en` か `ja`)・`metadata.source` (本リポジトリの URL) の 5 項目にする。日本語版の `description` は、日本語の本文に英語のキーワードを添える
- `SKILL.md` の節は、順に 5 つ: 何のライブラリか (見出しの直下の 1 段落)・できること (やりたいことから `references/` の 1 枚への表)・導入 (インストール例と必要な環境)・最小の動く例・`references/` の一覧
- 導入のインストール例は、README と同じ書き方にする (版は `{version}`。置き換えの説明と、最新の版の確かめ先を添える)
- `references/` の各 1 枚は、やりたいことを見出しにして、動くコードと約束ごとを並べる
- コード例には、原則としてコメントを書かない。要るときは英語で書く。英語版と日本語版のコードブロックを同じ内容にするためである
- 各 Skill の「最小の動く例」は、README の最小コード例 (Decision 4) と同じコードにする

**理由:** 両プラットフォームが同じ 6 枚を持てば、能力の対応が見出しで分かる (cross/ADR-0005 が求める、同じ能力マップ)。コードブロックを英日で同じにすれば、一致を機械で確かめられる。

**代替案:**
- **A: 日本語版のコード例に、日本語のコメントを書く** — 却下。英日でコードブロックが一致しなくなり、片方だけを直したことを機械で見つけられなくなる。
- **B: ファイルの名前を、源泉の concepts の名前に合わせる** — 却下。源泉は 6 枚で、Skill の 5 枚と 1 対 1 にならない。利用者のエージェントが読むのはファイルの名前なので、やりたいことの言葉にする。

### Decision 2: 各 1 枚に載せる事項と、相手のプラットフォームとの差の書き方

**採用案:** 載せる事項の出どころは、源泉の concepts と、フェーズの agenda の申し送りである。申し送りの行き先を、次の表で決める。

| 1 枚 | 源泉の concepts | 載せる申し送り (agenda の節) |
|---|---|---|
| `basics.md` | `core/core-model/collection-items.md`・`collection-interaction.md` | 不正入力のリリースビルドでの挙動 (core/ADR-0011)。iOS だけ: 親の状態を渡す指定 (ios/ADR-0008)・セルの再利用で内部の状態が残らないこと (ios/ADR-0002)・表示中にキーパスやテンプレートの登録を差し替えても反映されないこと (ios/ADR-0006) |
| `layout.md` | `core/styling/collection-layout.md` (グループの宣言は `collection-items.md`) | phase-4 からの申し送りの 4 件 (グループの宣言と並びの責任・全画面に広げた一覧の安全領域・Android のグループの値の型・グループの値の取り出し方の切り替え) |
| `paging.md` | `core/core-model/collection-paging.md` | phase-5 からの申し送りの 9 件 |
| `reorder.md` | `core/core-model/collection-reorder.md` | phase-6 からの申し送りの 10 件 |
| `images.md` | `core/core-model/image-loading.md` | phase-8 からの申し送りの 2 つの表 (7 項目) |

- 片方のプラットフォームにだけ当たる申し送り (iOS の起動時のディスクキャッシュの有効化・Android の自動の初期化の前提・Android の持ち上げた項目の影など) は、そのプラットフォームの Skill にだけ載せる
- 相手のプラットフォームとの動きの差と、片方にしか無い指定は、その機能を説明している場所に 1〜2 文で書く。相手のプラットフォームのコードは載せない。差をまとめた節は作らない
- 相手の Skill に触れるときは、名前だけを書く (リンクを張らない)
- 公開の宣言の名前は、外すと決めたものを除いて、Skill のどこかに一度は現れるようにする (Decision 8 の道具で確かめる)
- リポジトリの内部の言葉 (ADR の番号・開発の記録の言葉・利用者役など) は書かない

**理由:** 申し送りは 5 つのフェーズに分かれて積まれている。行き先を表で決めておけば、書き手が拾い漏らしたかどうかを、1 枚ごとに確かめられる。

**代替案:**
- **A: 申し送りの行き先を、書き手に任せる** — 却下。兄弟ライブラリで、源泉から移すときに公開 API の名前が脱落した。行き先が決まっていないと、漏れを確かめる単位が無い。

### Decision 3: ルートの README と、Skill の索引

**採用案:** ルートの README は、英日とも次の 9 つの節を、この順で持つ。概要と特徴は 1 つの節にする (フェーズの議論で、スクリーンショットを概要の次に置くと決めた。兄弟ライブラリも同じ並びである)。

| 節 | 中身 |
|---|---|
| 概要と特徴 | 何のライブラリか (今の冒頭の段落を引き継ぐ) と、できることの箇条書き |
| スクリーンショット | 両プラットフォームの画面 (下の表) |
| 対応プラットフォーム | 表 1 枚。iOS は最低の OS と Xcode の版、Android は利用者に求める下限と、ライブラリのビルドに使った版を分けて書く |
| インストール | SwiftPM と Gradle の依存の宣言。版は `{version}`。置き換えることと、置き換えないと依存の解決に失敗することの説明。最新の版の確かめ先の案内。配布物をまだ公開していないことの 1 文 |
| 最小コード例 | 両プラットフォームに 1 つずつ (Decision 4) |
| Skill への導線 | 各プラットフォームの `SKILL.md` と、索引へのリンク。英語版は `skills/en/`、日本語版は `skills/ja/` を指す |
| リポジトリ構成 | ルートのディレクトリの役割の表 |
| 貢献 | Issue で受け、外部からの Pull Request は受けない。今の文面と、貢献の案内への導線を引き継ぐ |
| ライセンス | MIT License。本ライブラリが依存するライブラリのライセンスの案内 |

スクリーンショットは、次の 6 枚にする。Sample の今の画面を、ライトの表示で撮る。

| 画面 (Sample の名前) | 見せるもの | ファイル (`assets/`) |
|---|---|---|
| リスト | 基本の一覧と区切り線 | `ios-list.png`・`android-list.png` |
| グリッド (固定列) | グリッドの並び | `ios-grid.png`・`android-grid.png` |
| グループ化 | グループの見出しと固定 | `ios-grouping.png`・`android-grouping.png` |

- 画像は README から相対パスで参照する
- 画像グリッドの画面は撮らない。外から取得した画像が写り、権利の確認が別に要る
- 撮るときは、作業専用の Simulator とエミュレータを作って使い、終わったら削除する。保存する前に、写り込み (個人を特定する情報) が無いことを確かめる
- 対応プラットフォームの値は、ビルドの設定 (`ios/Package.swift`・`android/gradle/libs.versions.toml`・`android/kscollectionview/build.gradle.kts`) から拾う。Android の利用者に求める下限は、発行物のメタデータと、利用者役のビルドの設定から確かめる
- 「ライセンス」の節を書く前に、Sample に第三者の通知が要る素材 (同梱の画像・フォント) が無いことを確かめる
- 配布物をまだ公開していないことの 1 文は、README だけに書く。Skill には書かない

Skill の索引 (`skills/README.md`・`skills/README_ja.md`) は、Skill の一覧・導入の手順 (取得する・ディレクトリごとコピーする・エージェントを開き直す)・片方の言語だけ使うときの 3 つの節を持つ。

**理由:** 節の並びは cross/ADR-0005 が挙げたものに、フェーズの議論で決めたスクリーンショットを足した形である。相対パスなら、どのブランチで見ても、その commit の画像が表示される。

**代替案:**
- **A: 画像を、ブランチの名前を含む絶対 URL で参照する (兄弟ライブラリの形)** — 却下。URL にブランチの名前が入り、見ているブランチと違う commit の画像が表示され得る。
- **B: 配布物をまだ公開していないことを書かない** — 却下。README が `main` に入ってから初回の公開までの間、インストールの手順がそのまま読めて、依存の解決に失敗する理由が分からない。

### Decision 4: 利用者役の画面のソースを、README の最小コード例にする

**採用案:** 利用者役の画面のソースを、次の形に書き直す。README の最小コード例は、このファイルの全体と同じ内容にする。

| プラットフォーム | ファイル | 形 |
|---|---|---|
| iOS | `verification/ios/Sources/VerificationApp/ItemListScreen.swift` | モデルと画面を 1 ファイルに置く。コメントと `public` を持たない。今の 2 ファイルは消す |
| Android | `verification/android/app/src/main/kotlin/ItemListScreen.kt` | package の宣言を持たない。コメントを持たない。今の画面のファイルは消す |

- Android の入口 (`MainActivity.kt`) は、今の package のまま残し、画面の名前だけを書いた import を 1 行足して呼ぶ (上の試作のとおり、import が無いと名前を解決できない)
- 例の中身は、今と同じ「行を縦に並べた一覧を 1 つ表示する」にする。Android の例は、Material に依存しない書き方のままにする
- 確認のスクリプト・ひな形・ビルドの定義・成功の条件は変えない
- 書き直した後に、コード縮小を有効にした Android の利用者役を、手元で 1 回起動して、一覧が表示されることを確かめる

**理由:** ファイルの全体を README に載せれば、利用者が貼ったコードが、import まで含めてビルドで確かめたものになる。比べ方は文字列の一致だけで済む。

**代替案:**
- **A: Android の例に、利用者役の package の宣言を残す** — 却下。README の例の先頭に、利用者役のアプリの package が載る。利用者には関係の無い行である。
- **B: 入口も package の宣言を持たないファイルにする** — 却下。マニフェストの入口の名前の書き方まで変わり、変える範囲が広がる。import の 1 行で済む。

### Decision 5: 検査のロジックはスクリプトに置き、実物への適用はスクリプトのテストから行う

**採用案:** 検査を 2 つのスクリプトに分け、どちらも Python の標準のライブラリだけで書く。

| スクリプト (`scripts/ci/`) | 確かめること |
|---|---|
| `check-readme-examples.py` | README の最小コード例と利用者役の画面のファイルの一致。インストール例 (README の 2 枚と、各 `SKILL.md`) |
| `check-skills.py` | Skill 自身の整合 (5 つ) |

- どちらも、リポジトリのルートを引数で受け取り、違反を 1 件ずつ出して、違反があれば失敗で終わる。手元でも、追従の手順の中でも、そのまま呼べる
- 実物への適用は、`scripts/ci/tests/` のテストが、今のリポジトリのルートを渡して呼ぶ。lint のジョブの step は増やさない
- 検査のロジックのテストは、一時のディレクトリに作った正常と異常のひな形に対して流す
- 黙って空振りする経路を作らない。次はどれも失敗にする: `skills/` が無い・Skill が 1 つも無い・最小コード例の節やコードブロックが見つからない・対象のファイルにインストール例が無い
- 許可する URL と、内部の言葉の一覧は、データとして `scripts/ci/user-docs-rules.json` に置く。一覧を変える差分が、レビューで見える

最小コード例の検査は、README の英日 2 枚の、最小コード例の節の中の Swift と Kotlin のコードブロックを 1 つずつ取り出し、利用者役の 2 つのファイルと比べる。節は見出しの文面で見つける (英語版と日本語版の見出しの文面を、スクリプトが持つ)。

インストール例の検査が確かめることは、次のとおり。

| 確かめること | 相手 |
|---|---|
| SwiftPM の依存の 2 行 (Package URL の行と、product と package の名前の行) | iOS の確認のスクリプトが、公開済みの配布物を取るときに差し込む行と、ひな形の product の行。版の位置は `{version}` |
| Gradle の依存の 1 行 | Android の利用者役の依存の行の座標。版の位置は `{version}` |
| 例の中に、具体の版が書かれていない | — |
| 最新の版の確かめ先の URL が、同じファイルにある | 一覧のデータ |
| どのファイルに、どの例があるか | README は両方、iOS の Skill は SwiftPM、Android の Skill は Gradle |
| 英語版と日本語版で、例の種類と数が同じ | — |

Skill 自身の整合の検査が確かめることは、次のとおり。

| 確かめること | 判定 |
|---|---|
| 英語版と日本語版の一致 | Skill の集合・ファイルの集合・見出しの深さの並び・コードブロックの中身と順番が同じ |
| frontmatter | 5 項目だけを持つ。`name` がディレクトリの名前と同じ。`metadata.language` が置き場と合う |
| Skill の外のファイルへのリンク | 相対のリンクの先が、その Skill のディレクトリの中に実在する。外へ出るリンクは失敗 |
| URL | 一覧にある URL (完全一致) か、見本の URL の前置き (前方一致) に当たるものだけ |
| 内部の言葉 | 一覧にある言葉が、本文にもコードブロックにも現れない |

URL の一覧の最初の値は、Package URL・本リポジトリの URL・最新の版の確かめ先・不具合の報告先の 4 つと、コード例の見本に使う `https://example.com/` の前置きにする。知識を委ねる参照 (本リポジトリの中の文書への URL) は、完全一致の一覧に無いので失敗になる。

**理由:** ロジックをスクリプトに置けば、追従の手順からも同じ検査を呼べる。実物への適用をテストに置けば、検査の名前も step も増えず、`main` の保護を変えずに済む。今の README の検査と同じ形になる。

**代替案:**
- **A: lint のジョブに、検査の step を足す** — 却下。フェーズの議論で、検査の名前を増やさず、今のスクリプトのテストに足すと決めた。step を足すと、workflow のテストと文書の step の表も直すことになる。
- **B: URL を、本リポジトリの URL の前方一致で許可する** — 却下。本リポジトリの中の文書への URL (知識を委ねる参照) まで通ってしまう。
- **C: 一覧をスクリプトの中に直に書く** — 却下。一覧に足すときに人が判断する決まりなので、ロジックの変更と分けて差分で見えるほうがよい。

### Decision 6: 検査しないものの線引き

**採用案:** 検証 CI に足すのは、`skills/` と README と利用者役の中だけで合否が決まる検査に限る。次は検証 CI に置かない。

- Skill が源泉からずれていること (cross/ADR-0017)。スクリプトのテストは、追従の記録の commit と、源泉の今の内容を比べない
- 公開の宣言の名前の網羅 (Decision 8)。公開の宣言を足した push が、Skill を直すまで落ち続けることになるためである
- 各 Skill の「最小の動く例」と `references/` のコード例のビルド

**理由:** 源泉を変えた push を、Skill を直すまで止めないためである。

**代替案:**
- **A: 公開の宣言の名前の網羅も、スクリプトのテストで流す** — 却下。源泉 (コード) とのずれを検証 CI で止めることになり、cross/ADR-0017 と食い違う。

### Decision 7: 追従の記録と、変わった源泉を出す道具

**採用案:** 追従の記録を `skills/.manifest.json` に持つ。利用者がコピーするのは `skills/{en,ja}/<名前>/` なので、このファイルは利用者の手元に行かない。

| 項目 | 中身 |
|---|---|
| `version` | 記録の形の版 |
| `syncedCommit` | 前回追従したときに見た commit の ID (40 桁) |
| `sources` | 差分を出す対象のパスと、その源泉が掛かる Skill の 1 枚 (言語とプラットフォームを抜いた相対パス。複数の 1 枚に掛かる源泉は、すべてを書く)。Skill に掛からない源泉は、理由を添えて「外す」と書く |
| `apiExclusions` | Skill に載せないと決めた公開の宣言の名前と、その理由 (プラットフォームごと。Decision 8) |

差分を出す対象は、次の 4 つにする。概念の文書は、どれも「どの 1 枚に掛かるか」か「外す理由」のどちらかを持つ。

- `kasane/concepts/` の下の概念の文書のすべて
- ビルドの設定の 3 つ (Decision 3 の対応プラットフォームの値の出どころ)。掛かる先は `SKILL.md`
- 依存の書き方を決めている文書 (`kasane/handbook/cross/public-identifiers.md`)。掛かる先は `SKILL.md`
- 利用者役の画面のファイルの 2 つ (Decision 4)。掛かる先は `SKILL.md` (最小の動く例)。README の側は、検証 CI の検査が直し漏れを見つけるが、`SKILL.md` の最小の動く例は検証 CI が見ないので、追従で拾う

道具は `scripts/docs/skills-refresh.py` の 1 本で、2 つの使い方を持つ。

| 使い方 | 行うこと |
|---|---|
| `status` | `syncedCommit` から今の作業ツリーまでの、対象のパスの差分を git で出し、変わった源泉と、見直す Skill の 1 枚 (複数に掛かる源泉は、そのすべて) を一覧にする。対応の決まっていない源泉 (新しい概念の文書) と、改名された源泉は、別に分けて報告する。本体のソースの、公開の宣言の行の増減も、別に分けて報告する。差分の本文も出せる。何も書き換えない |
| `record` | `syncedCommit` を、渡した commit (渡さなければ今の HEAD) に書き換える。書き換えるのは、このファイルだけ |

- `status` は、commit していない変更も数える。対象のパスの下に足した、まだ追跡していない新しいファイルも数える
- 公開の宣言の行の増減は、本体のソース (Decision 8 が名前を拾うのと同じ置き場) の差分のうち、公開の宣言の行が足された・消えたものだけを拾って出す。宣言を消した・名前を変えた・引数や型や既定値を変えた、が 1 行の宣言なら現れる。内部の変更は出さない
- 公開の宣言の行の増減には、限界がある。複数行にわたる宣言の、続きの行だけを変えたとき (引数の並びの途中の行など) は現れない。限界は handbook の草稿に書き、追従のときに人が本体の差分を見る場面を決めておく
- `status` は、`syncedCommit` が履歴に無いとき (浅い取得・別のリポジトリ) は、理由を出して失敗で終わる
- `record` は、対象のパスに commit していない変更 (追跡していない新しいファイルを含む) があるときは、書き換えずに失敗で終わる (記録する commit に入っていない変更が、追従済みの扱いになるのを防ぐ)
- 道具は Python の標準のライブラリだけで書き、テストを `scripts/ci/tests/` に置く (Decision 8 の道具も同じ)
- 最初の記録は、制作が見た源泉の commit にする。実装の最後に `record` で書く
- 追従のときの流れ (どの順に道具を呼び、どこで承認を得るか) は、handbook の草稿に書く (蒸留のときに配置する)

**理由:** 覚えるものが commit の ID 1 つなら、源泉を分割・改名しても、記録を手で合わせる作業が起きない (cross/ADR-0017)。対応を記録の中に持てば、変わった源泉から見直す 1 枚を、道具が引ける。

**代替案:**
- **A: `record` が、Skill の変更と一緒に commit まで行う** — 却下。道具は git の履歴を変えない (写しを作る道具と同じ決まり)。commit は、呼ぶ側の工程が行う。
- **B: 対応を記録に持たず、道具が変わった源泉だけを出す** — 却下。見直す 1 枚を毎回人が引くことになり、新しい概念の文書がどの 1 枚にも掛かっていないことに気付けない。
- **C: 本体のソースのファイルを、そのまま差分を出す対象に入れる** — 却下。内部の変更まで毎回出て、見直す対象が埋もれる。公開の宣言の行の増減だけを拾えば、宣言を消した・変えたことは出せる。
- **D: 本体のソースの変更は道具で拾わず、Decision 8 の道具だけに任せる** — 却下。Decision 8 の道具が見るのは、今ある名前が Skill に現れるかだけである。宣言を消した・引数を変えたことは、概念の文書を同時に直していなければ、どの道具にも現れない。

### Decision 8: 公開の宣言の名前の網羅を報告する道具

**採用案:** `scripts/docs/check-api-coverage.py` が、各プラットフォームのソースから公開の宣言の名前を拾い、そのプラットフォームの Skill (英語版と日本語版のそれぞれ) に一度も現れない名前を報告する。

| 拾う名前 | iOS (`ios/Sources/`) | Android (`android/kscollectionview/src/main/`) |
|---|---|---|
| 型 | `public` の struct・enum・class・protocol・typealias | `public` の class・object・interface・typealias |
| 関数と修飾子 | `public` の func | `public` の fun |
| プロパティ | `public` の var・let | `public` の val・var |
| 列挙の値 | `public` の enum の case | `public` の enum の値と、sealed の型の中の `public` の宣言 |

- 引数の名前と、初期化の宣言は拾わない。引数の名前は短い一般の言葉が多く、名前だけの照合では意味が無い
- iOS の、計測用として公開している宣言 (利用者向けでない印の付いたもの) は拾わない
- `apiExclusions` にある名前は報告しない。`apiExclusions` にあるのに宣言が無くなった名前は、古い項目として報告する
- 結果は報告だけで、Skill を書き換えない。漏れがあれば、漏れがあったと分かる終了コードで終わる
- 公開の宣言を 1 つも拾えなかったときは、失敗で終わる (置き場の移動などで、黙って空振りしないため)
- 文法を解く道具は使わず、宣言の行を拾う。拾い方の細部 (複数行の宣言・拡張の中の宣言) は、実装で今のソースに当てて決める

最初の `apiExclusions` は、実装で道具を流して出た名前のうち、利用者向けでないもの (DSL の組み立てに使う型の名前など) を、オーナーに諮って決める。

**理由:** 利用者向けの concepts は両プラットフォームの名前が 1 枚に混ざるので、concepts と比べると、相手のプラットフォームの名前が誤って漏れに数えられる。コードから拾えば、プラットフォームごとの一覧が取れ、concepts に書き漏らした名前も拾える。

**代替案:**
- **A: concepts に書かれた名前と比べる (兄弟ライブラリの形)** — 却下。フェーズの議論で退けた。
- **B: 引数の名前まで拾う** — 却下。`id`・`key`・`width` のような名前は、説明の文のどこかに必ず現れ、漏れの検出にならない。
- **C: 外す名前を、文書の表だけに書く (兄弟ライブラリの形)** — 却下。道具が読まないと、外すと決めた名前が毎回報告され、同じ判断を聞き直すことになる。

### Decision 9: 配った先を再現した確認の進め方

**採用案:** オーナーの検収の前に、指揮側が次の 2 つを行う。どちらも、Skill の 1 ディレクトリだけをコピーした空の作業用のディレクトリで、リポジトリを知らない新しいエージェントに行わせる。エージェントには、リポジトリのパスも、ほかの文書も渡さない。

| 確認 | 回数 | 行うこと |
|---|---|---|
| 読ませる | 4 回 (2 つの Skill × 2 言語) | Skill を通して読ませ、次を挙げさせる: 意味の分からない言葉・足りない説明・Skill の外を見ないと分からないこと・冒頭でこれが何かが分かるか |
| 使わせる | 10 回 (下の 5 つの課題 × 2 プラットフォーム。英語版で行う) | 課題の画面を、Skill だけを頼りに 1 ファイルで書かせる。書いたファイルを、作業用の写しの利用者役の画面と入れ替えて、確認のスクリプトを `local` で流す |

| 課題 | 当たる 1 枚 | 書かせる画面 |
|---|---|---|
| 1 | `basics.md` | 型でテンプレートを切り替える一覧。行のタップを受け、ボタンで先頭へスクロールする |
| 2 | `layout.md` | 向きで列の数が変わるグリッド。グループの見出しを固定し、ルートのヘッダーを持つ |
| 3 | `paging.md` | 続きを読み込む一覧。失敗したときの再試行の表示と、空のときの表示を持ち、Pull to Refresh で取り直す |
| 4 | `reorder.md` | グループをまたいで並べ替えられる一覧。置けない場所の判定と、読み上げの移動操作の文言を持つ |
| 5 | `images.md` | 画像のグリッド。先読みを宣言し、URL が変わる画像に任意キーを使う |

- 使わせる確認の作業用の写しは、提案の段階の試作と同じ作り方にする (追跡しているファイルを作業用のディレクトリに取り出し、使い捨ての git のリポジトリにして、画面のファイルだけを入れ替える)。本リポジトリの作業ツリーは変えない
- 使わせる確認では、課題と一緒に、利用者役とつなぐための条件を渡す: 画面の名前は `ItemListScreen`・引数を取らない・1 つのファイルに収める・Android は package の宣言を書かない。これはライブラリの知識ではなく、ビルドの入口とつなぐための条件である (条件を渡さないと、Skill が正しくても入口とつながらずに落ちる)
- 確認の作業 (読ませる・書かせる・ビルドする) は、本リポジトリの追跡しているファイルを変えない。確認で見つかった欠けを直すのは、確認とは別の作業で、変えるのは Skill の文書だけである
- 読ませる確認の指摘は、すべて直すか、直さない理由を記録する
- 使わせる確認でビルドが落ちたら、原因を仕分ける。Skill に書かれていない・誤っているのなら Skill を直し、その課題をやり直す。Skill に正しく書いてあるのにエージェントが違う書き方をしたのなら、書き損じとして記録し、その課題を 1 回だけやり直す。やり直しても落ちるときは、Skill の書き方が伝わっていないものとして扱う
- 落ちた原因が、ライブラリの API の不足や不具合のときは、本変更では直さず、オーナーに諮る
- 回ごとに、課題・書かれたファイル・ビルドの結果・仕分けを証跡に残す

**理由:** Skill の主な読み手は AI エージェントで、利用者の手元には Skill の 1 ディレクトリしか無い。兄弟ライブラリの最初の制作は、リポジトリの中で読むレビューをすべて通った後に、検収で落ちた。`references/` のコード例は、ほかのどの検査もビルドしない。

**代替案:**
- **A: 確認のスクリプトに、画面のソースを差し替える引数を足す** — 却下。確認のスクリプトは、検証 CI とリリースの工程が呼ぶ道具で、入力を 2 つに決めてある。1 回の確認のために入力を増やさない。
- **B: 使わせる確認を、日本語版でも行う** — 却下。コードブロックは英日で同じなので、ビルドで確かめられる内容は変わらない。日本語の文面は、読ませる確認で見る。

## Risks / Trade-offs

- **文書の量が多い**: Skill の文書は 24 枚で、レビューが 1 回で見る量が大きい。フェーズの議論で、分けずに 1 つの変更でやりきると決めた。Decision 2 の表と、Decision 5・8 の道具で、1 枚ごとに確かめられるようにする
- **使わせる確認の結果が揺れる**: エージェントの書き損じでも落ちる。仕分けを人が読める形で残す。課題が触らない API のコード例の誤りは、この確認では見つからない
- **内部の言葉の一覧は、誤って止め得る**: 一般の言葉と重なる語を一覧に入れると、正しい文面で落ちる。一覧には、ほかの意味で使われない言葉だけを入れる
- **公開の宣言を行で拾うので、拾い漏れがあり得る**: 文法を解かない。拾った名前の数を証跡に残し、目で数えた数と突き合わせる。公開の宣言の行の増減も同じ拾い方なので、複数行にわたる宣言の続きの行の変更は現れない
- **スクリーンショットは古くなる**: 見た目を変えても、機械は気付かない。撮り直すきっかけを、書き方の決まりの草稿に書く
- **最新の版の確かめ先は仮の値**: phase-7-4-release-pipeline が別の場所に決めたときは、例のある 6 か所と、URL の一覧を直す。検査が、直し漏れを見つける
- **未公開の間、インストール例は解決できない**: README の 1 文で知らせる。外すのは初回のリリースの作業である

## Migration Plan

1. 利用者役の画面のソースを書き直し、確認のスクリプトを `local` で流す。コード縮小を有効にした Android の利用者役を、手元で 1 回起動する
2. README の検査のスクリプトとテストを入れ、ルートの README とスクリーンショットを作る
3. Skill 自身の整合の検査のスクリプトとテストを入れ、Skill の文書と索引を作る
4. 追従の道具と記録を入れ、公開の宣言の名前の網羅を流して、外す名前をオーナーに諮る
5. 配った先を再現した確認を行い、指摘と落ちた課題を直す
6. 草稿を書き、手元の完了判定を通して、オーナーの検収を受ける

戻し方: `skills/`・`assets/`・足したスクリプトとテストを消し、README と利用者役のソースを前の内容に戻せば、変更の前の状態になる。配布物の確認の合否の条件は、変えていない。
