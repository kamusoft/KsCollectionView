# Proposal: user-docs

## Why

リポジトリは公開したが、利用者がこのライブラリの使い方を知る手段がまだ無い。ルートの README は「準備中」の短い案内だけで、利用者向けの Agent Skill (`skills/`) は 1 枚も無い。

利用者向けの文書は、Agent Skill とルートの README 2 枚で提供すると決めてある (cross/ADR-0005)。Skill は `kasane/` とコードから翻訳した派生物なので、源泉が変わったときに追従させる仕組みが要る。cross/ADR-0005 は、その仕組みの具体を後の決定に委ねていた。

兄弟ライブラリ KsSettingsView は、同じ方式を先に運用して、いくつかの手戻りを経験している。最初の制作がレビューをすべて通った後にオーナーの検収で落ちた・源泉から Skill へ移すときに公開 API の名前が脱落した・インストール例に実在しない版が残った・片方の言語だけを直した、の 4 つである。

フェーズの議論で、Skill の構成、追従の仕組み (cross/ADR-0017)、インストール例の版の書き方 (cross/ADR-0018)、Skill の外への参照の扱い (cross/ADR-0019)、README の中身、守り方を決めた。本変更は、その決定を実物にする。

## What Changes

- **利用者向け Skill**: `skills/{en,ja}/kscollectionview-ios/` と `skills/{en,ja}/kscollectionview-android/` を作る
  - 各 Skill は `SKILL.md` と、利用者のやりたいことで分けた `references/` の 5 枚 (一覧を出す・並べ方と見た目・ページングと Pull to Refresh・並べ替え・画像) を持つ。英語版と日本語版は、同じ構成・同じコードブロックにする
  - 相手のプラットフォームとの動きの差と、片方にしか無い指定は、その機能を説明している場所に短く書く。相手のプラットフォームのコードは載せない
  - フェーズの agenda に積まれた申し送り (各機能のフェーズと ADR が「利用者ドキュメントに書く」とした約束ごと) を載せる
  - Skill の索引 (`skills/README.md` と日本語版) を置く
- **ルートの README**: 英日 2 枚を、利用者の入口として書き直す
  - 節は、概要と特徴・スクリーンショット・対応プラットフォーム・インストール・最小コード例・Skill への導線・リポジトリ構成・貢献・ライセンスの 9 つ
  - スクリーンショットは、両プラットフォームの代表の画面を Sample から撮って `assets/` に置く
  - 対応プラットフォームは表 1 枚で案内する (iOS は Xcode 27 以上を含む。Android は、利用者に求める下限と、ライブラリのビルドに使った版を分ける)
- **インストール例**: README と各 `SKILL.md` の例は、版の位置に `{version}` を置き、置き換えの説明と、最新の版の確かめ先を同じファイルで案内する。案内先は、本リポジトリの Release の一覧を仮の値として書く (下の Impact)
- **利用者役のソース**: `verification/` の画面のソースを、README の最小コード例としてそのまま載せられる形に書き直す。ビルドして確かめる内容と、成功の条件は変えない
- **README と Skill の検査**: 検証 CI のスクリプトのテスト (lint のジョブが毎回流す) に、次を足す。検査の名前と step は増えない
  - README の最小コード例が、利用者役の画面のファイル全体と一致すること
  - インストール例の値が利用者役の使う値と同じで、版が `{version}` であり、最新の版の確かめ先の案内があること
  - Skill 自身の整合 (英語版と日本語版の一致・frontmatter・Skill の外のファイルへのリンクが無い・許可した一覧に無い URL が無い・決めた内部の用語が無い)
- **追従の道具**: オーナーが頼んだときに使う道具を `scripts/` に足す
  - 前回追従した commit から今までの、源泉のパスの差分を出す。前回追従した commit の ID を 1 つ、リポジトリの中に記録する
  - 各プラットフォームのコードの公開の宣言から名前を拾い、Skill に一度も現れない名前を報告する。外すと決めた名前は一覧に残し、次からは報告しない
- **配った先を再現した確認**: オーナーの検収の前に、Skill の 1 ディレクトリだけを渡した新しいエージェントで確かめる
  - 読ませる確認 (分からない言葉・足りない説明・冒頭に「これは何か」があるか)
  - 使わせる確認 (決めた課題を Skill だけを頼りに書かせ、利用者役と同じ形でビルドが通るか)

影響する能力: user-skills (新規。利用者向け Skill の構成と中身) / user-readme (新規。ルートの README と Skill の索引) / user-docs-consistency (新規。README と Skill の検査) / user-docs-refresh (新規。追従の道具) / consumer-verification (利用者役の画面のソースが、README の最小コード例と同じ内容になる)

- 蒸留時に反映: decisions — cross/ADR-0017・0018・0019 を、実装の形で確かめて accepted に昇格する。cross/ADR-0019 を上げるときに、cross/ADR-0005 の側へ、一部が改められたことの印を付ける
- 蒸留時に反映: handbook — cross に、利用者向け Skill の追従の手順を新設する (頼まれたときの流れ・差分の出し方・検査・承認・記録の進め方)。`skills/` を触る作業で必ず読まれるように、適用のきっかけにパスを書く
- 蒸留時に反映: handbook — cross に、利用者向け Skill と README の書き方の決まりを新設する (公開 API の名前を載せる基準と外す名前の扱い・相手のプラットフォームとの差の書き方・Skill の外への参照の線引き・インストール例の書き方・コード例のコメント・英語版と日本語版の同時更新・スクリーンショットの撮り方と撮り直すきっかけ)
- 蒸留時に反映: handbook — `kasane/handbook/cross/verification-ci.md` に、lint が流すテストへ README と Skill の検査が加わったこと・落ちたときの見方を足す
- 蒸留時に反映: handbook — `kasane/handbook/cross/consumer-build-check.md` に、利用者役の画面のソースが README の最小コード例と同じ内容であること・変えるときに README も同時に直すことを足す
- 蒸留時に反映: handbook — `kasane/handbook/cross/public-identifiers.md` の、依存の書き方を変えるときに同時に直すものに、README と Skill のインストール例を足す

## Non-Goals

- **Release の作り方と、最新の版の案内先の確定** — リリースの工程の設計に属するので、phase-7-4-release-pipeline が決める。本変更は、案内先を仮の値で書く
- **リリースの手順の中で Skill の追従を確かめる決まり** — リリースの基準の判断を要するので、phase-7-4-release-pipeline で扱える (フェーズの議論の申し送りの候補)
- **Skill が源泉からずれていることを、検証 CI で検査すること** — cross/ADR-0017 で、検査しないと決めた。検証 CI に足すのは、`skills/` と README の中だけで合否が決まる検査に限る
- **リリースのたびに README と Skill の版を書き換える仕組み** — cross/ADR-0018 で、持たないと決めた
- **各 Skill の「最小の動く例」と `references/` のコード例を、ビルドして確かめる検査** — フェーズの議論で、README の最小コード例だけを利用者役と一致させると決めた。Skill のコード例は、配った先を再現した確認で確かめる
- **公開 API とライブラリの挙動の変更** — 別の能力である。配った先を再現した確認で API の不足や不具合が見つかったときは、本変更では直さず、オーナーに諮って起票する
- **Sample の変更** — スクリーンショットは今の Sample の画面を撮るだけにする。撮るために Sample を変えると、両プラットフォームの一致の確認が別に要る
- **画像の同時取得数の案内** — 簡易起票 `image-fetch-concurrency-priority` で、利用者への案内に留めるかどうかが未決である。決まった後に、追従で載せる
- **MAUI 向けの記述・旧ライブラリからの移行の Skill・章立ての `docs/`** — cross/ADR-0005 で、作らないと決めた
- **兄弟ライブラリと共通の追従の道具を、ハーネスの側に持つこと** — このリポジトリの変更では作れない (cross/ADR-0017 の見直しのきっかけに書いてある)

## Impact

- 破壊的変更: 無い。公開 API とライブラリの挙動は変えない
- 利用者役の画面のソースを書き直すが、配布物を確かめる内容と成功の条件は変えない。`main` 宛ての Pull Request の必須の検査は、5 つのまま変わらない
- lint のジョブが流すスクリプトのテストが増える。`skills/` や README を触った push は、整合の検査で落ち得る。触らない push では落ちない
- リポジトリに、Skill の文書 24 枚・索引 2 枚・画像 (`assets/`) が増える
- 最新の版の案内先は、本リポジトリの Release の一覧を仮の値として書く。phase-7-4-release-pipeline が別の場所に決めたときは、例のある 6 か所と、許可する URL の一覧を直す
- 配布物はまだ公開していない。本変更の README は、インストールの節の冒頭に「まだ公開していない」ことを 1 文で書き、初回のリリースのときに外す (外す作業は phase-7-4-release-pipeline へ申し送る)。Skill には、この注記を書かない (利用者が Skill を手にするのは公開の後である)
- リスク: Skill の文書は量が多く (24 枚)、書くのがエージェントなので、コード例の誤りが入り得る。配った先を再現した確認で落ちたときは、Skill の欠けか、エージェントの書き損じかの仕分けが要る
- リスク: 利用者役の画面のソースを README に載せる形に変えると、Android では package の宣言を持たないファイルを、宣言を持つファイルから呼ぶことになる。コード縮小を有効にしたビルドが通ることを、設計の段階で確かめる
- リスク: スクリーンショットは、見た目を変えても機械では古さに気付けない
