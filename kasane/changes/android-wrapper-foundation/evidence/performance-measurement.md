# Android 性能計測 (スクロール性能とメモリ)

## 状態

実施済み。**現行構成 (Compose 1.11.4 / compileSdk 36) で基準機 Pixel 4a により測り直した**結果を
本文の「計測結果」に置く。スクロール性能は、行の高さ変化のアニメーションをライブラリ既定に
した後、比較対象にも同じ既定機能を持たせ、さらに高さの補間を自前の修飾に置き換えた条件での
再計測 (同じ手順を独立に 2 回) が最新である。それ以前の計測 (`animateContentSize` による補間・
条件を揃える前・初回構成) は参考と経緯の節に残す。代替機による計測ではないため、基準機の
保証を欠く旨の但し書きは不要。

計測は Sample と同じビルドルートの Macrobenchmark モジュールが自動実行する。人の操作を挟まない
ため、同じ手順を何度でも再現できる。

| 対象 | 環境 | app |
|---|---|---|
| スクロール性能 (`FrameTimingMetric`) | Pixel 4a / Android 13 (SDK 33) | benchmark 構成 (release と同じ最適化 + profileable、debug 鍵で署名) |
| メモリ (`MemoryUsageMetric` + アプリ自身の往復記録) | Pixel 4a / Android 13 (SDK 33) | 同上 |

## 固定 fixture

iOS 側の規約と同じ土俵にそろえる。

- 画面: Sample「大量件数」と同じ内容を描く計測用の入口
- 件数: 10,000 件 (メモリの件数比較では 1,000 件も使う)
- 配置: 2 列グリッド、行間 / 列間 1dp。1 列の比較では 1 列リスト、行間 1dp
- 行高: 固定高と、7 件ごとの長文による可変行高の混在
- 生成: 整数 ID 1〜件数 による決定的なデータ。同じバイナリでは項目ごとの内容が常に一致する
- 比較対象: まったく同じ件数・間隔・行の見た目を、ライブラリを通さず素の Compose で描いた画面 (多列は `LazyVerticalGrid`、1 列は `LazyColumn`)

**件数ごとに、その件数分だけを生成して保持する。** 最大件数を作り置きして先頭から切り出すと、
1,000 件の計測でも 10,000 件分の入力データが保持され、件数間の差を測れなくなる。

## 手順

### スクロール性能

1. 計測モジュールが、計測用の入口へ直接遷移する指定つきでアプリを起動する。
2. **目的の画面が載ったこと** (画面ごとに別の印を付けた semantics の出現) を実時間の上限つきで
   待ってから計測に入る。起動の完了だけで測り始めると、メニューや遷移の途中のフレームが混ざる。
3. 実行時コンパイルの状態を試行間でそろえる (`CompilationMode.Partial`、暖機 1 回)。起動時間は測らない。
4. 実座標のフリックを 3 秒間続ける試行を、独立に 3 回行う。
5. 同じ手順をライブラリ側と比較対象側の両方で行い、結果を突き合わせる。

### メモリ

1. 計測モジュールが自動往復の画面へ直接遷移する指定つきでアプリを起動し、画面が載ったことを
   待ってから計測に入る。走査・記録・停止まで画面自身が行う。
2. 1 往復は、先頭から末尾まで可視範囲の半分ずつ (16 項目 = 8 行刻み) 位置を送り、同じ刻みで
   先頭へ戻る走査とする。可視範囲より粗い刻みでは間の項目が作られず、コストが計上されない。
3. **1 段階ごとに、送り先の項目が実際に載ったことを条件に次へ進む** (実時間の上限つき)。
   フレーム数で進めると、実行機が混んでいるときに命令が追い越されて間の項目が作られず、
   「メモリが増えない = 合格」という向きに誤る。
4. 往復のたびに、通過した項目の識別子を数えて**全項目を通過したことを確かめる**。両端 (先頭と
   末尾) には刻みと別に明示して到達する。
5. 往復ごとに使用メモリ (PSS 合計) を記録し、**連続する 2 往復の増分がいずれも 2% 以内**に
   なった時点で定常とみなして止める。上限 10 往復で止まらなければ未判定とする。
6. 往復の終了時点で、計測の枠組みからも使用メモリを記録する。
7. 同じ手順を 1,000 件でも行い、定常値を件数間で突き合わせる。

到達できなかった (`unreached`)・間の項目を飛ばした (`missedItems`)・上限まで定常にならなかった
(`notSteady`) はいずれも未判定であり、計測側が実測値つきでテストを失敗させる。緑にはならない。

## 合格基準と、比率で測れない指標の扱い

| 系統 | 指標 | 基準 |
|---|---|---|
| 相対 | フレーム時間 (P90 / P99) の比較対象に対する劣化 | 10% 以内 |
| 絶対 | フレーム超過時間の P99 | 0.0 ms 以下 (初回計測で校正) |
| メモリ | 往復ごとの PSS 合計 | 連続 2 往復の増分が 2% 以内で定常。定常値が件数比 (10 倍) に比例しない |

比率での比較はフレーム超過時間 (`frameOverrunMs`) には使えない。実測がほぼ全域で負 (= 期限に
対して余裕がある) であり、負値どうしの比は劣化の大小を表さないためである。そこで**相対の判定は
フレームの CPU 時間 (`frameDurationCpuMs`) で行い、フレーム超過時間は絶対値で判定する**。

判定は 3 試行の集計値に対して行う。試行ごとの P90 / P99 は、差が 1 ミリ秒に満たない領域では
±14% ほど揺れる。試行 1 つの比を合否にすると、実装の差ではなく揺れを測ることになる。

定常判定は増分を符号つきで見るため、**減少も「増え続けていない」として定常に含める**。判定の
意図は増加が止まったことの確認であり、実行ごとの揺れによる減少を未定常とは扱わない。

### 相対基準の比較対象の条件

**比較対象の項目にも、ライブラリの既定機能と同じ高さ変化のアニメーション (`animateContentSize`) を
同じ位置 (項目の content を包む箱) に付ける** (deviation 7 件目)。行の高さ変化をアニメーション
させることをライブラリの既定にした結果、素のままの比較対象と並べると、相対の差が「ラッパーの
上乗せ」ではなく既定機能そのもののコストを表してしまう。相対 10% 以内はラッパーの薄さの検証と
して維持し、機能そのもののコストは絶対上限 (フレーム超過時間の P99 ≤ 0.0 ms) で担保する。

比較対象のそれ以外の条件 (件数・列数・間隔・行の見た目・安定 ID・再利用種別) はライブラリ側と
同一のまま変えない。

**「同じ既定機能」は機能で揃え、実装は揃えない。** 比較対象は Compose 標準の `animateContentSize`
で高さ変化をアニメーションさせ、ライブラリ側は自前の高さ補間 modifier を使う。機能としては同等
(高さの補間 + 補間中のはみ出しの切り取り) だが実装は異なるため、**この相対基準が測るのは
「標準の Compose で同じ機能を組んだ場合に対するラッパーの上乗せ」**である。ラッパーそのものの
純粋な上乗せは、両側からアニメーションを外した対照計測 (後方の経緯節: P90 +2.3% / P99 +6.0%) で
別途押さえている (deviation 7 件目の補足)。

## 計測結果: スクロール性能 (Pixel 4a / Compose 1.11.4 / compileSdk 36)

値は 3 試行を通した集計。ライブラリ・比較対象ともに高さ変化のアニメーションを持つ条件で測った
(上記「相対基準の比較対象の条件」)。ライブラリ側は自前の高さ補間、比較対象は Compose の
`animateContentSize` である。比較対象の条件は「同じ既定機能を持つこと」であり、実装をそろえる
必要はない。

**同じ手順を独立に 2 回実行した。** 差が 1 ms に満たない領域では試行別の百分位が揺れるため、
1 回の実行だけでは相対の符号が固まらない。これが現行の正式な結果であり、条件を揃える前の計測と、
高さの補間を `animateContentSize` で行っていたときの計測は後方の節に残す。

### 多列 (2 列グリッド) — ライブラリ vs `LazyVerticalGrid`

| 指標 | ライブラリ (1 回目 / 2 回目) | 比較対象 (1 回目 / 2 回目) | 相対 (1 回目 / 2 回目) | 判定 |
|---|---:|---:|---:|---|
| `frameDurationCpuMs` P90 | 6.85 / 7.09 ms | 7.53 / 7.40 ms | -9.1% / -4.2% | 合格 |
| `frameDurationCpuMs` P99 | 8.40 / 8.03 ms | 10.95 / 8.50 ms | -23.2% / -5.6% | 合格 |
| `frameOverrunMs` P90 | -6.73 / -7.34 ms | -6.54 / -6.85 ms | — | 合格 (絶対) |
| `frameOverrunMs` P99 | -5.87 / -6.25 ms | 0.04 / -4.75 ms | — | 合格 (絶対) |

相対はどちらの実行でも負 (ライブラリ側が速い) である。1 回目の比較対象の P99 (10.95 ms /
超過 +0.04 ms) は 2 回目には出ておらず、比較対象側に散発する外れ値と読む。判定に使う絶対上限は
ライブラリ側に掛かるもので、両実行とも 5.8 ms 以上の余裕がある。

## 計測結果: メモリ (Pixel 4a / Compose 1.11.4 / compileSdk 36)

高さ変化のアニメーションは項目ごとの保持構造を変えないため、アニメーション導入とその後の
比較対象の条件揃えに際してメモリの測り直しは行っていない。以下は導入前の計測である。

往復ごとの PSS 合計 (アプリ自身の記録)。暖機と本計測をそれぞれ独立した実行として記録した。
`通過` はその往復で載った項目の数で、件数と一致していることが走査の空振りが無かった証拠になる。

| 件数 | 実行 | 往復 1 | 往復 2 | 往復 3 | 増分 (1→2 / 2→3) | 通過 | 判定 |
|---|---|---:|---:|---:|---|---:|---|
| 10,000 | 暖機 | 104,866 KB | 105,097 KB | 105,237 KB | +0.22% / +0.13% | 10,000 | 3 往復で定常 |
| 10,000 | 本計測 | 101,391 KB | 102,057 KB | 102,092 KB | +0.66% / +0.03% | 10,000 | 3 往復で定常 |
| 1,000 | 暖機 | 104,145 KB | 98,274 KB | 99,369 KB | -5.64% / +1.11% | 1,000 | 3 往復で定常 |
| 1,000 | 本計測 | 100,274 KB | 92,287 KB | 94,031 KB | -7.97% / +1.89% | 1,000 | 3 往復で定常 |

4 実行すべてが上限 10 往復のうち 3 往復で定常に達し、往復ごとに全項目を通過した。往復を重ねても
メモリは増え続けない。1,000 件側の往復 1→2 の大きな減少は、開いた直後の一時的な確保が回収された
もので、増加ではないため定常の判定を妨げない (上記「合格基準」の読み)。

往復の終了時点で計測の枠組みから見た値 (本計測の実行):

| 指標 | 1,000 件 | 10,000 件 | 差 |
|---|---:|---:|---:|
| `memoryRssAnonLastKb` | 51,768 KB | 57,888 KB | +6,120 KB (+11.8%) |
| `memoryHeapSizeLastKb` | 5,518 KB | 8,324 KB | +2,806 KB (+50.9%) |
| `memoryRssFileLastKb` | 98,152 KB | 101,944 KB | +3,792 KB (+3.9%) |
| `memoryGpuLastKb` | 61,996 KB | 61,988 KB | -8 KB (-0.0%) |

件数は 10 倍だが、いずれの指標も 10 倍にはならない。今回は 1,000 件側が 1,000 件分の入力データ
しか保持していないため、この差は**入力データ 9,000 件分そのものの大きさ**として読める
(1 件あたり約 0.7 KB。7 件ごとの長文を含む)。項目ごとの描画物が件数分保持されていれば現れる
はずの桁の増加はない。

同じ fixture を別の実行で測った差 (10,000 件の暖機 105,237 KB と本計測 102,092 KB = 3,145 KB) は、
件数を 10 倍にした差 (6,120 KB) より小さい。件数差はこの実行間のばらつきを超えて観測できている。

## 判定

- **相対**: 2 回の実行を通して、2 列グリッドは P90 -9.1% / -4.2%、P99 -23.2% / -5.6%。1 列リストは P90 -1.3% / -6.6%、P99 +2.5% / -10.1%。劣化はいずれも 10% 以内
- **絶対**: P99 のフレーム超過時間はライブラリ側で 2 列 -5.87 / -6.25 ms、1 列 -6.50 / -6.51 ms。上限 0.0 ms を満たす (5.8 ms 以上の余裕)
- **メモリ**: 4 実行すべてが 3 往復で定常。各往復で全項目を通過。定常値は件数比に比例せず、差は入力データ分で説明できる

`memoryRssAnonLastKb` で +5,220 KB) を入力データ分として読むことはできない。現行構成の計測は
件数ごとに生成する形へ直してある。

## 生ログの扱い

数値は計測モジュールの結果ファイルとアプリのログから採った。本文へ載せた抜粋は
`scripts/log-sanitize.py` を通し、端末の個体識別子・ローカル絶対パス・生のトレースは含めない。

## 経緯: 行の高さ変化のアニメーション導入直後の再計測 (比較対象は素のまま、Pixel 4a)

行の高さの変化をライブラリ既定でアニメーションさせる修正 (項目ラッパーへの `animateContentSize`)
を入れた後、相対指標 `frameDurationCpuMs` を測り直した。手順・fixture は本文と同じ。

| 実装 | 土俵 | ライブラリ P90 / 比較対象 / 相対 | ライブラリ P99 / 比較対象 / 相対 |
|---|---|---|---|
| アニメーションなし (対照) | 2 列 | 6.73 / 6.58 ms / +2.3% | 8.33 / 7.86 ms / +6.0% |
| アニメーションなし (対照) | 1 列 | 5.82 / 5.51 ms / +5.6% | 6.50 / 6.98 ms / -6.9% |
| `animateContentSize` のみ (採用) | 2 列 | 7.06 / 6.49 ms / +8.8% | 8.60 / 7.78 ms / **+10.6%** |
| `animateContentSize` のみ (採用、再実行) | 2 列 | 7.28 / 6.66 ms / +9.4% | 8.84 / 7.83 ms / **+12.9%** |
| `animateContentSize` のみ (採用) | 1 列 | 5.77 / 5.60 ms / +3.0% | 7.61 / 6.77 ms / **+12.4%** |
| `animateContentSize` + `animateItem` | 2 列 | 7.51 / 6.29 ms / **+19.4%** | 8.86 / 8.12 ms / +9.2% |

対照は同じ日の同じ端末で、アニメーションの修飾だけを外したビルドを同じ手順で測ったもの。

### 読み

- 項目の配置アニメーション (`animateItem`) を重ねると 2 列の P90 が +19.4% になる。高さの変化だけを
  アニメーションしても押し出される行の移動は段階を踏むため (row-height-animation.md)、
  `animateItem` は採らない
- `animateContentSize` だけでも、2 列の P99 が +10.6% / +12.9%、1 列の P99 が +12.4% となり、
  **合格基準の相対 10% 以内を超える**。同じ手順の再実行でも再現しており、揺れでは説明できない
- 絶対指標は満たしている。フレーム超過時間の P99 は 2 列 -5.46 〜 -5.85 ms、1 列 -6.5 ms で、
  上限 0.0 ms に対して 5 ms 以上の余裕がある。フリックでのフレーム落ちは観測されない
- 上乗せの出どころは、項目ごとに増える測定の割り込みと `animateContentSize` が内側に持つ
  クリップ (項目ごとの描画レイヤ) と見られる。可視項目が多い 2 列グリッドで効きが大きいことと整合する。
  この版の `animateContentSize` にクリップを外す引数は無い

### 決着

「行の高さ変化を既定でアニメーションさせる」というオーナー指示と、相対 10% 以内という合格基準の
両立は、**比較対象にも同じ既定機能を持たせて対等に比べる**ことで解いた (deviation 7 件目)。
相対はラッパーの上乗せの検証として維持し、機能そのもののコストは絶対上限で担保する。
この節の値は、比較対象が素のままだった時点のものとして経緯に残す。条件を揃えて測り直した結果は
本文の「計測結果: スクロール性能」にある。
