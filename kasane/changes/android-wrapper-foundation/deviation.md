# 実装乖離メモ: android-wrapper-foundation

- design Decision 5 (list の区切り線): design では項目の `drawBehind` で描く → review-002 の指摘 (不透明な背景を持つテンプレートでは区切り線が content に隠れ、iOS の前面描画と食い違う) により content の前面 (`drawWithContent` で content 描画後) に描く。理由: iOS (`KsHostingCell`) は区切り線を content の前面に置いており、Sample のセル背景 (#FFFFFF) で両プラットフォームの見え方を揃えるため。spec の Requirement (位置・本数・色・opt-out) は不変 (2026-09-05)
- Requirement「大量件数での仮想化・再利用 (Android)」Scenario「可変行高混在 10,000 件のスクロール」/ design Decision 8: spec では「3 試行すべてで、フレーム時間指標 (P90 / P99) の劣化が 10% 以内、かつ P99 が絶対上限以内」、design では相対指標を `frameOverrunMs` としていた → オーナー判断により、相対判定は `frameDurationCpuMs` (P90 / P99) で行い、`frameOverrunMs` は絶対上限 (P99 ≤ 0.0 ms、Pixel 4a 初回計測で校正) で判定する。判定は試行別ではなく 3 試行の集計に対して行い、超過したときは同じ手順を 1 回やり直して再現するかを見る。理由: `frameOverrunMs` は実測がほぼ全域で負のため比率で劣化を表せず、差が 1 ms 未満の領域では試行別の P90 / P99 が ±14% 揺れる (試行 1 に散発する 1 フレームの外れ値は比較対象側にも出る)。蒸留時に handbook/android/performance-verification.md へ規約化する (2026-09-05)
- android/ADR-0002 (Compose BOM は実装時点の最新安定に載せる / compileSdk は実装時点の最新) / tasks 2.1: 実装は BOM 2026.08.00 (Compose 1.12.0) + compileSdk 37.2 で進めていた → オーナー指示により、Compose 1.11 系の最新安定 BOM に下げ、本体の compileSdk を 36 (minor 指定なし) にする。理由: Compose 1.12.0 の AAR メタデータが利用者アプリに compileSdk 37 (Platform 37.2、直近リリースの minor 版) を要求し、ライブラリを入れるだけで利用者に未普及の SDK Platform のインストールを強いる。ADR-0002 が受容した負の帰結は「利用者の Compose 版の引き上げ」であり、SDK Platform の強制は想定外。「最新安定」は「利用者に未普及の SDK Platform を強いない範囲での最新安定」と読み替える (蒸留時に ADR-0002 の改訂を検討)。Compose 1.11 系はキャッシュ窓 (1.9 以上) と material3 1.4 の要件を満たす (2026-09-05)
- handbook/cross/sample-parity (DSL に渡すパラメータの一致) / Sample「リスト」画面の `touchFeedbackColor`: iOS は `SampleTheme.accent.opacity(0.15)`、Android は `SampleTheme.accent` (不透明) を渡す → 本体の意味論が非対称 (iOS は渡した色をそのまま塗る / Android の material3 `ripple` は渡した色に自前で不透明度をかける) なため、同じ生値を渡すと Android では不可視になる。Sample は描画結果を揃える値を渡し、生値の不一致は本体側の統一課題として記録する (review-004 / second-opinion-code-004 の確定指摘。統一は後続 change で扱う) (2026-09-05)
- tasks 8.3 (再利用の確認: カウンタ + Layout Inspector): Layout Inspector は GUI 操作が前提で固定手順に載らないため実施せず → テンプレート呼び出しの累積数に加えて同時生存数 (最大値・破棄) を測れる debug 限定カウンタで代替し、その結果を evidence に残す (2026-09-05)
- Requirement「セル自己サイズと content の配置 (Android)」/ 検証画面「行の高さ変化」: spec では項目の高さがコンテンツに応じて自動決定されることのみ → オーナー指示により、行の高さが変わるときはアニメーションさせる (展開する項目自身の高さ変化と、それに押される他の項目の移動)。理由: RecyclerView (KsSettingsView) は既定のアニメータで行高変化がアニメーションされ、それを目標にする (オーナー実機確認、2026-09-05)。ライブラリ既定の挙動として入れる。iOS 側は行の高さ変化がアニメーションされることをオーナーが確認済みで、本修正は Android を iOS に揃えるもの。帰結: 補間中に限り content はその時点の行の高さで測り直され (Requirement「content は行の高さに引き伸ばされない」は静定時の契約として不変)、はみ出しはクリップされる。テンプレートの根に高さの制約が渡るため、根が制約を使わない透明な箱だと折りたたみ中に隙間が見える — 利用契約として KDoc と dsl-samples に明記
- design Decision 8 (相対基準の比較対象 = 素の `LazyVerticalGrid`): 行の高さ変化のアニメーション (deviation 6 件目) をライブラリ既定にした結果、素の grid との相対比較が「ラッパーの薄さ」ではなくアニメーション機能のコストを測る形になった (P99 +10.6〜12.9%) → オーナー判断により、比較対象の計測用画面にもライブラリと同じ既定機能 (`animateContentSize`) を付けて対等に比較し、相対 10% 以内はラッパーの上乗せの検証として維持する。機能そのもののコストは絶対上限 (`frameOverrunMs` P99 ≤ 0.0 ms) で担保する (2026-09-05)
- design Decision 4 (`.center` / `.end` は対象を可視化してから `layoutInfo` の項目サイズで `scrollBy` 補正する 2 段階): オーナー実機確認で「Item 50 (Center) が一度行き過ぎてから戻る」と指摘 (design の Risks 節が予告していた「アニメーション中に位置が跳ぶ」の顕在化) → 1 回の `animateScrollToItem(index, scrollOffset)` に集約する。`scrollOffset` は対象の高さの推定値 (可視なら実測、同じ contentType の可視項目の平均、なければ可視項目全体の平均の順) から計算し、到着後の残差はアニメーション時は進行方向と同じ向きかつ 4dp を超えるときだけ詰める (逆向きの補正は入れない)。非アニメーション時は残差をそのまま詰める。4dp は「1 フレームの補正として目に付かない量」として実機で決めた (design の Open Question「補正の許容差」の回収)。clamp・contentPadding 内側基準・到達不能位置の扱いは不変 (2026-09-05)
- (7 件目の補足) 比較対象の「同じ既定機能」は Compose 標準の `animateContentSize` で実現し、ライブラリ側は自前の高さ補間 modifier (`KsAnimatedHeight`) を使う。両者は機能として同等 (高さの補間 + はみ出しのクリップ) だが実装が異なるため、相対基準は「標準の Compose で同じ機能を組んだ場合に対するラッパーの上乗せ」を測るものと読む。ラッパーそのものの純粋な上乗せは、両側からアニメーションを外した対照計測 (evidence/performance-measurement.md の経緯節: P90 +2.3% / P99 +6.0%) で別途押さえている (2026-09-05)
