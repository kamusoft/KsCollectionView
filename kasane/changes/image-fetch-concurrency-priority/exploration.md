# Exploration: image-fetch-concurrency-priority

## 課題 / 動機

画像グリッドで「スクロールを止めてから画像が揃うまで」が遅い。オーナーの手動計測で Android は約 5 秒 (iOS は 2〜3 秒) で、到達点 (メモリまで / ディスクまで / 列幅) による差を感じない。`prefetch-display-size` の実機計測 (tasks 8.5) で内訳を測った結果、主因は画像の取得経路の同時取得数の上限だった (2026-09-24、オーナー指示で起票)。

- **Android の主因**: 取得経路 (OkHttp) の同一ホスト同時取得数 5。この上限だけを 64 にすると、止めてから揃うまでの中央値は 3 到達点とも約 2.3〜3.2 秒 → 0 秒 (最終ビルドでも同じ)。待ちのほぼすべては取得の順番待ちで、通信そのものは約 0.4 秒。止めた時点で 40〜50 件前後が列に並ぶ
- **Android の副因**:
  - 先読みと表示要求に優先度が無く同じ列に並ぶ (止めた時点で先読み 23〜29 件と表示要求 15〜21 件)
  - 取得中の先読みと表示要求の二重取得 (フリングで取得した画像の 29〜38%)。画面に出た時点で先読みがまだ取得中の画像で起きる
  - `prefetch-display-size` で入れた「先読みが取得中の画像は表示要求の開始を画面に出る時点まで遅らせる」(spec「メモリ到達点の後の表示」を満たすため) により、到達点 memory / 列幅で止めてから揃うまでが修正前より 0.25〜0.3 秒長い (6 標本ずつで範囲は重なる)
- **iOS**: Nuke の `dataLoadingQueue` の同時数 6 が同じく主因 (64 で約 1.15 秒 → 約 0.53 秒)。iOS の列が短い (止めた時点 18〜20 件) のは、画面外のセルの表示要求の取り消し・先読みの優先度の低さ・同じ画像の取得の合流があるため
