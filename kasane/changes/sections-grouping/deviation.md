# Deviation: sections-grouping

- [付随修正] iOS の補助ビュー (グループの見出し・ルートのヘッダー / フッター、セルも同じなら含む) の SwiftUI の中身: 一番外側の画面として載せたとき、上端の安全領域に重なった分だけ中身が押し下げられ高さが増える既存の挙動を直す (修正内容は実施後に追記)。理由: 固定中のグループの見出しの見え方と 5.x の検証に関わるため、オーナー判断で同梱 (確認で提示し「同梱」を選択) (2026-09-24)
- [付随修正] iOS の layout 値の `rowSpacing` / `columnSpacing`: 負の値を `groupSpacing` / `headerItemSpacing` と同じく core/ADR-0011 の不正入力の扱い (debug は assertion、release は警告ログを出して 0 で続ける) に揃えた。これまでは debug の assertion だけで release では負の値のまま使われていた。テストで担保。理由: 同じ検知の経路に載り、局所的なため (2026-09-24)
- design Decision 16 (端を表示中の端への挿入、iOS): design では更新後の表示位置を `targetContentOffset(forProposedContentOffset:)` で返す形としていたが、差分の適用ではこの戻り値が使われないことを確認したため、`finalizeCollectionViewUpdates()` の中で表示位置を動かす形で実装した。spec の挙動 (挿入のアニメーションの中で端に留まる) は変えない。アニメーションの見え方は 5.7 のオーナー目視で確かめる (2026-09-24)
- [付随修正] iOS の不正入力の警告ログ (`KsInvalidInput`) の category が `image` のままで、layout 値・グループ・先読みの宣言の警告も画像の category に出ていたのを `input` に直した。テストで担保 (2026-09-24)
- design Decision 10 (Android のスクロールインジケータの全体の長さ): design では「公式の全体の長さ × 数えた行数 ÷ 公式が数えた行数」としていたが、この式では前後の余白まで拡大されて末尾でわずかにずれるため、前後の余白を比の外に出し、行の部分だけを比で補う形で実装した。spec の挙動 (末尾に達したときだけインジケータが下端に届く) は変えない (2026-09-25)
- Requirement「見出しの固定」ほか (全画面に広げた一覧と安全領域、iOS / Android): spec では安全領域での振る舞いの記述なし → 指示により、一覧を全画面に広げた場合 (iOS の `.ignoresSafeArea()`、Android の edge-to-edge) は、固定中の見出しを上端の安全領域の境目 (バーのすぐ下) で止め、行はバーの裏を流れる。コンテンツの先頭 (ルートのヘッダー・最初の見出し) と末尾も初期状態では安全領域の内側に収まる。普通の置き方 (安全領域に重ならない) の見え方は変えない。1 項目めの付随修正 (中身が安全領域の分だけ押し下げられ高さが増える件) はこの中で直す。左右の安全領域 (横向き) は今の挙動のまま。理由: iOS の連絡先アプリと同じ見え方が正解 (オーナーが連絡先アプリのスクリーンショットで提示)。Android の edge-to-edge でも同じ現象が起きるはずで両プラットフォームで揃える (2026-09-25)
- 上の「全画面に広げた一覧と安全領域」の訂正: 指示により、コンテンツの先頭・末尾には安全領域の分の内側余白を足さない。ルートのヘッダーは安全領域に被ってよく、バーの分の大きさは利用者がルートのヘッダーの大きさで調整する (下端のルートのフッター・最後の行も同じ扱い)。ライブラリが安全領域に合わせるのは、固定中のグループの見出しを上端の安全領域の境目より上へ行かせない (バーのすぐ下で止める) ことだけ。付随修正 (中身が安全領域の分だけ押し下げられ高さが増える件) は変わらず直す。理由: ルートのヘッダーの配置は利用者の責任 (オーナー判断) (2026-09-25)
- 1 項目めの付随修正と「全画面に広げた一覧と安全領域」の iOS 側の実施内容: `KsHostingCell` / `KsHostingSupplementaryView` が上下の安全領域を SwiftUI の中身へ渡さないようにした (左右は従来どおり渡す)。固定中のグループの見出しの上端を「表示範囲の上端 + 上端の安全領域」とし、押し上げ・固定中の見出しに覆われた範囲・回転の復元・ID によるスクロール命令も同じ境目を基準にした。`contentInsetAdjustmentBehavior = .never` は変えていない。安全領域に重ならない置き方では追加の値がすべて 0 で従来と同じ。テスト `KsSafeAreaTests` (8 件) で担保 (2026-09-25)
- [付随修正] iOS Sample の `DemoData`: 「大量件数」の項目の作り方を `DemoData.largeItem(_:)` に切り出し、「グループ化」と共有した。「大量件数」の中身は変わらない。理由: 「グループ化」のセルは「大量件数」と同じ見え方 (brief) (2026-09-25)
- design Decision 13 の試作で決める点の確定 (tasks 3.8、Android): オーナーがエミュレータの試作を目視して決定。① `animateItem` は項目と見出しに付ける (付けない選択肢はない) ② 出入りのフェードあり ③ 固定中の見出し (`stickyHeader`) にも付ける ④ `ksAnimatedHeight` との順序は見え方の違いが分からないため、項目の修飾のいちばん外側 (`ksAnimatedHeight` の前) とする。あわせてオーナー指摘: 末尾への挿入のアニメーションが分かりにくく、即反映したように見える → Requirement「端を表示中の端への挿入」(いちばん下での末尾への挿入はアニメーションが見えること) を満たすよう 3.9 / 3.10 で直す (2026-09-25)
- design Decision 13 の「高さ変化の補間と同時に動くときの扱い」(Android、試作では決めていなかった点): 同じ一覧で高さの補間が進んでいる間は、`animateItem` の配置のアニメーションを止める (`placementSpec = null`、出入りのフェードは残す)。理由: 補間で押し出される行を配置のアニメーションが追いかけ、行の間に最大 81dp の帯ができて既存の高さ補間のテストが落ちたため。このため「更新 + 移動」が同時に起きると、補間が動き始めた後の移動はアニメーションしない場面がありうる (2026-09-25)
- android/ADR-0006 の適用範囲 (Android): `animateItem` を項目と見出しに加えて、ルートのヘッダー / フッターにも付けた (内部のキー `KsRootSlotKey`)。理由: 項目だけが動くとフッターが先に飛んで項目と重なるため (2026-09-25)
- tasks 3.10 (Android、端を表示中の端への挿入の末尾側): 末尾への挿入で `requestScrollToItem` を呼ぶと Compose が配置と出現のアニメーションをすべて捨てて 1 フレームで末尾へ飛ぶため (オーナー指摘「即反映に見える」の原因)、挿入のフレームでは位置を要求せず、次のフレームから `animateItem` と同じばねで末尾までなめらかにスクロールする形に改めた。画面外に足された項目は最初に配置されたときに一度だけフェードさせる (2026-09-25)
- 「全画面に広げた一覧と安全領域」の Android 側の実施内容: 安全領域は `WindowInsets.systemBars ∪ displayCutout` から祖先が消費済みの分を除き、一覧と実際に重なっている長さだけを使う。固定中の見出しを境目より下に置き、スクロール命令・列数変化での位置の保持も同じ境目を基準にした。押し上げは、次の見出しを境目で止めた位置から測る (iOS は次の見出しの本来の位置から測る。境目より上 = バーの裏での見え方だけの小さな違い) (2026-09-25)
- [付随修正] Android Sample の `DemoData`: 「大量件数」の項目の作り方を `DemoData.largeItem(id)` に切り出し「グループ化」と共有した (iOS と同じ対応。中身は変わらない)。あわせて `app/build.gradle.kts` の古いコメント「デモ 9 画面」を「デモ画面」に直した (2026-09-25)
- Requirement「グループの値によるグループ化」(表示中のグループの値の取り出し方の切り替え、iOS / Android): spec では切り替えの扱いの記述なし → レビュー (review-001 / second-opinion-code-001 の双方一致の指摘) の裁定により、同じ配列のままキーパス / ラムダを切り替えた場合も、新しいグループの値の列を前回と比べて異なれば組み直し、差分として反映する (Android の KDoc の「表示中に差し替えない前提」は取り除く)。理由: 表示の切り替え (カテゴリ別 / ブランド別など) は利用者の自然な使い方で、iOS では古い境界に新しい見出しが出る不具合になっていた (2026-09-25)
- tasks 5.4 (iOS 16 の Simulator での押し出し中の見出しの薄めと方式 3c の打ち消し): tasks では iOS 16 の Simulator で確かめる → 指示により、手元にある iOS 18.6 の Simulator で代わりに確かめ、iOS 16 は未確認として記録する。理由: この Mac に iOS 16 のランタイムが無く、数 GB のダウンロードを避ける (オーナー判断) (2026-09-25)
- Requirement「グループをまたぐ差分更新」(項目と見出しの移動・挿入・削除は新しい位置へ飛ばずにアニメーションで反映する、iOS): 「グループ化」画面 (10,000 件) の一覧の途中で「並び順を反転」すると、新しく画面に来る項目が遠い元の位置 (約 20 万 pt 先) から動いてくるため約 0.35 秒 (21 フレーム) 画面にセルも見出しも出ず、アニメーションの最後のフレームで見出しとセルが一緒に 222〜278pt 跳ぶ (evidence/ios-verification.md の 5.2 の所見)。見出しとその塊のセルの相対位置は保たれる。指示により、合意済みの妥協として受け入れる。理由: オーナーが iPhone 11 の実機で目視し「気になるが妥協できる」と判断 (2026-09-26)
