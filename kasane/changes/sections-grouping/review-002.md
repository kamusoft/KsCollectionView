## 指摘事項

### 🟡 Minor (優先度高) iOS で取り出し方を切り替えると、消えていく古い見出しに新しいグループの名前が出る

**該当箇所**: `ios/Sources/KsCollectionView/KsCollectionViewController.swift:200-204`、`ios/Sources/KsCollectionView/KsCollectionViewController.swift:753-758`、`ios/Tests/KsCollectionViewTests/KsGroupingEngineTests.swift:760`
**問題点**: `update(configuration:)` は、`self.configuration` を新しい宣言に差し替えた後 (177 行目)、差分の適用 (`apply`) の前に `updateVisibleGroupHeaders()` を呼ぶ (202 行目の条件は、観測する値を宣言しない一覧では毎回成り立つ)。このとき `configureGroupHeader` は、新しい見出しのクロージャ (新しいキーパスで値を取り出す) を、まだ古い `appliedChunkTable` の範囲に当てる。配列が変わる通常の更新では、キーパスが同じなので古い範囲・古い値のまま食い違いは起きない。キーパスを切り替えた更新でだけ、古い境目の見出しに新しいグループの値が入る。
プローブで確かめた。既存のテストと同じ条件 (果物 2 件 + 野菜 3 件を `\.half` に切り替え) で、見出しの組み立ての記録は `["前半:[0, 1]", "前半:[2, 3, 4]", "前半:[0, 1, 2]", "後半:[3, 4]"]` の順になった。はじめの 2 件は古い「果物」「野菜」の見出しのビューで、どちらも「前半」として組み立てられている。この後の snapshot の適用では、古い見出しの塊 (識別子はグループの値を含む) が削除され、アニメーションで消える。その間 (約 0.3 秒)、古い境目に「前半」が 2 つ並ぶ。前回 Major と確定した症状 (古い境目に新しいグループ名が出る) が、アニメーションの間だけ残っている。既存のテストは、最後の組み立てが正しいことだけを待つので通る。
静止画では見えない種類の一時的な不具合なので、目視での確認はしていない。組み立てられた内容はプローブの記録で確定している。
**推奨修正**: 取り出し方が変わった更新 (`groupValueSourceChanged`) では、適用の前の `updateVisibleGroupHeaders()` を呼ばない。適用が完了したときの呼び出し (816 行目) が、新しい塊の表で組み立て直す。塊の表が変わらず snapshot を適用しない場合 (同じ値を返す別のキーパス) は、753 行目の早期の return の前で、`regroupingSections` のときだけ `updateVisibleGroupHeaders()` を呼ぶ。この経路でも見出しは新しいクロージャで組み立て直される。テストは、既存の切り替えのテストに条件を足す。切り替え以降のすべての組み立てが新しい構成の組 (`前半:[0,1,2]` / `後半:[3,4]`) だけであることを確かめる。Android は、構成と見出しを同じコンポジションで読むため、この食い違いは起きない。

## 所見 (指摘ではない)

- Android はラムダの同一性を `remember` のキーにしたので、`by` に渡したラムダが再コンポジションのたびに別のインスタンスになる書き方だと、再コンポジションごとに配列全体からグループを求め直す (O(n)。構成が同じなら適用はしない)。strong skipping の既定のラムダの記憶では、捕捉しない書き方も、同じ値を捕捉する書き方も同じインスタンスのままなので、ふつうの書き方ではこうならない。状態を捕捉したラムダでは、その状態が変わったときに組み直しが起きる (切り替えの意図どおり)。性能の問題があるとすれば 5.x の計測で分かる
- 前回の所見 (android/ADR-0004 と ADR-0006 の関係、proposal.md の「60 件」と spec の 20 件の食い違い、proposed の ADR の確定) は、蒸留で扱う事項としてそのまま残っている

## 確認した観点

- **仕様充足**: 切り替えの扱いは spec に記述がなく、deviation の最後の項目 (レビューの裁定) に沿っている。組み直したときの見出し・境目・塊の件数 (iOS の `[3, 2]`、Android の見出しの位置)、同じ値を返す別の取り出し方で組み直さないこと、無関係な再コンポジションで組み直さないことを、テストで確かめた。tasks.md と足場 (proposal / design / specs) には、前回から変更がない
- **堅牢性**: 取り出し方の切り替えと配列の変化が同時に届いた場合 (通常の差分の経路で新しい宣言から塊の表を作る)、見出しの有無・固定の有無の切り替えとの組み合わせ (レイアウトの無効化の条件は別に立つ)、構成が等しいときに古い `KsGroupResolution` を使い続けても診断が変わらないこと (構成が等しければ値と何回目かも等しい)
- **設計品質**: `KsGroupPlan.equals` / `hashCode` はグループの数に比例する比較で、配列の件数に依らない。構成が等しい間は `groupPlan` の同一性が保たれ、`rows` などの派生の表を作り直さない。`KsPositionKeeper` と先読みの窓は配列の同一性で変化を検知するので、構成の同一性が保たれても挙動は変わらない。`KsGroupingProbe` は既存の `KsTapFeedback` と同じく、テストで観測するための internal な計数
- **テスト**: 追加の 4 件は、切り替え後の状態を条件ベースで待つ (iOS の `waitUntil`、Android の `waitForIdle`)。固定時間の待機はない
