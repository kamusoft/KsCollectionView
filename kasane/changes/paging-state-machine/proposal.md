# Proposal: paging-state-machine

## Why

ロードマップ v1-foundation のゴールに挙げた定型機能のうち、無限スクロール (ページング)・Pull to Refresh・読み込み中の表示は、まだどちらのプラットフォームにも無い。利用者は今、末尾に近づいたことの検出・二重の読み込みの抑止・読み込み中や失敗の表示・Pull to Refresh の接続を画面ごとに自分で書くしかなく、旧 AiForms.CollectionView の `LoadMoreCommand` / `LoadMoreMargin` 相当の機能も欠けている。

公開契約の外形 (利用者の VM が 5 状態を持ち、DSL に状態と次ページ要求を渡す) は phase-1 で決まっている (core/ADR-0005)。phase-5 の議論 (agenda の決定事項) で、状態の細部・発火の条件・多重発火と連鎖の抑止・表示範囲の置き方・Pull to Refresh の接続・標準の表示が確定した (core/ADR-0019〜0024、いずれも proposed。0021 は core/ADR-0018 を、0024 は core/ADR-0005 を一部置き換える)。本提案はそれを実装可能な契約に落とす。

## What Changes

- **ページングの状態**: 5 状態 (待機 / 取り直し中 / 追加読み込み中 / 失敗 / 終端) の公開の列挙を提供する。状態は付属値を持たない (core/ADR-0019)。状態は利用者の VM が持ち、ライブラリは遷移を強制しない (core/ADR-0005)
- **ページングの設定**: 一覧に状態・次ページ要求の処理・しきい値を渡す (Swift は modifier、Kotlin は名前付き引数)。次ページ要求の処理は両プラットフォームとも非同期関数で受ける (core/ADR-0022)
- **発火の条件**: 画面に出ているいちばん後ろの項目より後に残る項目の数が「しきい値 × 画面に出ている項目の数」以下になったら次のページを頼む。しきい値は画面数 (既定 1、0 は最後の項目が画面に入ったら)。スクロール・配列の差し替え・状態の変化・一覧の大きさの変化のたびに判定し直し、項目が空で待機なら初回の読み込みとして頼む (core/ADR-0020)
- **多重発火の抑止**: 頼むのは状態が待機のときだけ。一度頼んだら、処理が終わり、かつ状態か配列が変わるまで次を頼まない (core/ADR-0022)
- **表示範囲の置き方** (ページングを付けた一覧だけ): 差し替えの直前の状態が終端以外なら末尾への挿入でも末尾に留めず、届いたページは今の位置の下に現れる。直前が取り直し中なら差し替えと同時に先頭を表示する (core/ADR-0021、amends core/ADR-0018)
- **Pull to Refresh**: iOS は SwiftUI 標準の `.refreshable { await }` を一覧が受け取り、Android は取り直しの処理を引数で受ける。インジケータは両プラットフォームとも引っ張って始めた取り直しの間だけ出し、状態が追加読み込み中の間は引っ張りを受け付けない (core/ADR-0023)
- **標準の表示**: 項目が並んでいるときにいちばん下の項目のすぐ下に出す 3 つ (次のページの読み込み中 / 失敗 / 終端) と、項目が 1 件もないときに一覧の真ん中に出す 3 つ (最初の読み込み中 / 失敗 / 空) の 6 つ。既定で出すのは 2 つの読み込み中だけ (各プラットフォームの標準のくるくる、文言なし) で、失敗・終端・空は利用者が設定したときだけ出す。6 つそれぞれに差し替え口を用意し、失敗の表示には再試行 (いつも次ページ要求) の操作を渡す。VM が自分で始めた取り直しの間は、項目が並んでいれば何も重ねない (core/ADR-0024・0019)
- **安全領域**: 全画面に広げた一覧でも、Pull to Refresh のインジケータはバーのすぐ下より下に出し、0 件の表示は上下の安全領域を除いた範囲の真ん中に置く (core/ADR-0025、amends core/ADR-0017。提案の自己レビューで ADR-0017 との衝突を検出し、オーナー判断で改訂)
- **不正入力**: しきい値が負の数 (または有限でない数) なら、debug は assertion、release は 0 として扱って警告ログを出す (core/ADR-0011 の方針。議論で「提案時に決める」とした細部)
- **Sample デモ画面「ページング」**: 両プラットフォームに sample-parity 準拠で追加する。全 10,000 件を 1 ページ 50 件・取得の遅延 1 秒 (起動引数で変えられる) で返す決定的な偽の取得元を持ち、list / 2 列グリッドの切り替え、次の読み込みを失敗させる切り替え、中身を 0 件にする切り替え、VM が始める再読み込みの操作、Pull to Refresh を備える。失敗・終端・空の表示を同じ文言で設定して見せ、VM は失敗の状態からの再試行を受け付ける
- **検証**: Scenario ごとの自動テストに加え、「ページング」画面での基準機の体感 (cross/ADR-0006) と、両プラットフォームの標準のくるくるが OS 側の言葉で読み上げられることを evidence/ に残す

影響する能力: collection-paging (新規: 状態・設定・発火・抑止・表示・Pull to Refresh) / collection-core (端を表示中の端への挿入 — ページングを付けた一覧の例外) / samples (検証装置)

## Non-Goals

- 先頭側へのページング (前のページを上に足す。チャットの過去ログ等) — 5 状態 (core/ADR-0005) に前方向の読み込みが無く、位置の保ち方と発火の条件を逆向きに設計し直す必要がある
- 状態遷移の強制 (追加読み込み中の取り直し等、誤った遷移の防止) — core/ADR-0005 (状態は利用者が持つ)
- 失敗の状態へのエラーの値・失敗の種類の付与 — core/ADR-0019
- 標準の表示の文言と翻訳・スケルトン表示・VM が始めた取り直し中の重ね表示 — core/ADR-0024
- タップしたときの色の意味の統一 (phase-3 の申し送り) — テーマが同じ `library-default-colors-dark-mode` に移した (agenda の決定事項)
- 利用者向けガイド (Skill) への記載 — skills/ はまだ無く、配布・ドキュメントのフェーズ (phase-7) が制作する。記載する約束ごと (項目があるときの取り直しの失敗は失敗の状態にしない / 最初の読み込みは VM が始めない / 失敗・空の表示を設定しないときの見え方 / ページの境目でグループが伸びることと並び順の責任 / 次ページ要求の処理から戻る前に状態を追加読み込み中にする・VM が自分で取り直すときは古い読み込みの結果を捨てる) は蒸留時に phase-7 へ申し送る
- Android の相対計測 (素の Lazy グリッドとの比較) — ページングは既定機能ではなく、付けた一覧だけで動く。性能は「ページング」画面の体感で確かめる

## Impact

- 公開 API 追加 (両プラットフォーム): ページングの状態の列挙、ページングの設定 (状態・次ページ要求・しきい値)、6 つの表示の差し替え口、Pull to Refresh の接続 (Android は取り直しの処理の引数、iOS は SwiftUI 標準の `.refreshable` を読む)。破壊的変更なし
- 既存の振る舞いの変更: ページングを付けた一覧だけ、末尾への挿入で末尾に留める条件と、取り直しの差し替えでの位置が変わる (core/ADR-0021)。ページングを付けない一覧は変わらない
- iOS: 一覧の中で SwiftUI の環境値 (`.refreshable` の処理) を読む最初の例になる。スクロールの通知 (`scrollViewDidScroll`) を新たに受ける (ページングを付けたときだけ判定する)
- Android: material3 の Pull to Refresh (有効 / 無効を切り替えられる土台の修飾とインジケータ) を使う。material3 への依存は既存
- リスク: 追加読み込みの差し替えがスクロール中に走る (差分のアニメーションとスクロールの重なり)。「ページング」画面の体感で確かめる
- リスク: iOS は内部の塊の件数が変わる差し替えでアニメーションを切る (ios/ADR-0009・0010)。追加読み込みで 500 件の境目を越えるたびにこの経路を通るため、見え方を確かめる
- リスク: iOS の引っ張りの部品と、全画面の一覧で行をバーの裏に流す作り (core/ADR-0017) の組み合わせ (インジケータの出る位置) は未確認
