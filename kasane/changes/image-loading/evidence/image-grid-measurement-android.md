# Android 画像グリッドの計測 (tasks 7.5)

## 状態

**実施済み・不合格 (一部は未判定)。** 基準機で 4 系統すべてを実行したが、次の 2 点により
**この土俵の性能面の完了とは報告できない**。

1. **到達点ディスク: 絶対基準を満たさない。** `frameOverrunMs` P99 が独立した 2 実行で
   **5.7 ms / 6.2 ms** (合格基準は 0.0 ms 以下)。規約が求めるやり直し 1 回でも再現した
2. **到達点メモリ: 実機でアプリがクラッシュする。** 先読みが載せた元寸の画像を表示の組み立て中に
   縮小する経路が `Config.HARDWARE` のビットマップで落ちる。この到達点のスクロール・メモリの
   両方が**判定不能** (4 系統中 2 系統が未判定)

環境: Pixel 4a / Android 13 (SDK 33) / benchmark 構成 (release と同じ最適化 + profileable、
debug 鍵で署名) / Compose BOM 2026.06.01 (compose 1.11.4) / compileSdk 36。
基準機での実行であり、代替機ではない。

計測は `samples/android/benchmark` の `ImageGridBenchmark` 6 件を**同一実行内で連続**して行った
(所要 1 時間 25 分)。到達点ディスクのスクロールだけは、その前に単独でも 1 実行しており、
下表の「実行 1」がそれにあたる。生の結果ファイル (Macrobenchmark の JSON と Perfetto トレース) は
手元保管で、ここには判定に使った集計値だけを載せている。

## 土俵と入口

| 対象 | 入口 |
|---|---|
| スクロール性能 (到達点ディスク / メモリ) | 計測用の経路 `measurement/image/<件数>/<到達点>`。10,000 件。3 秒のフリックを独立に 3 回 |
| メモリの定常判定 (到達点ディスク / メモリ × 1,000 件 / 10,000 件) | 計測用の経路 `measurement/image-memory/<件数>/<往復上限>/<到達点>`。走査・記録・停止まで画面自身が行う |

相対基準は適用しない (同等機能を持つ比較対象が無いため。絶対基準とメモリで評価する)。
メモリは到達点ごとに 1,000 件と 10,000 件の 2 通りを測る (計 4 系統)。Android 性能検証の規約は
定常値が件数比 (10 倍) に比例しないことまで合格条件にしており、10,000 件だけでは判定材料が
揃わないため。件数は経路で渡し、対象アプリはその件数分だけを作って保持する。

## 固定 fixture

- 画面: Sample「画像グリッド」と同じ土俵を、操作バーだけ外して描く計測専用の経路
- 件数: 10,000 件 (メモリの件数比較では 1,000 件も使う)、3 列、セル間と外周の余白は Sample と同じ
- セル: 正方形の `KsImage` (fill) と「#ID」の文言
- 取得元: ID から決まる公開プレースホルダー画像サービスの URL (400 × 400)
- プリフェッチ: 到達点は経路で選ぶ (ディスクまで / メモリまで)

要素・配置・外周の余白・プリフェッチの宣言は、デモ画面と計測用の画面が同じ宣言元
(`ImageGridFixture`) から取る。土俵が食い違ってもどちらの画面も正常に動いてしまうため、
一致は `ImageGridMeasurementFixtureTest` が両方を実際に描いて確かめている。

「大量件数」の土俵 (固定高・可変行高混在の 2 列) とは別の土俵であり、値を比較しない。

## スクロール性能 (絶対基準) — 不合格

`FrameTimingMetric` の 3 試行の集計値。暖機 1 回 + `CompilationMode.Partial`、実座標のフリック
3 秒 × 独立 3 試行。試行ごとに画像キャッシュを空にしてから開く (cold、下記)。

| 土俵 | 実行 | frameCount (min / median / max) | `frameDurationCpuMs` P50 / P90 / P99 | `frameOverrunMs` P50 / P90 / P99 | 判定 |
|---|---|---|---:|---:|---|
| 到達点ディスク | 実行 1 | 155 / 163 / 164 | 8.2 / 13.3 / 19.8 ms | -3.9 / 0.8 / **5.7** ms | **不合格** |
| 到達点ディスク | 実行 2 | 167 / 171 / 172 | 7.9 / 10.7 / 20.9 ms | -3.8 / 3.6 / **6.2** ms | **不合格** (再現) |
| 到達点メモリ | 実行 2 | 0 / 2 / 3 | 3.6 / 6.5 / 7.3 ms | -12.2 / -9.5 / -8.7 ms | **無効** (下記) |

判定 (到達点ディスク): 合格基準は `frameOverrunMs` P99 が 0.0 ms 以下。**2 実行とも超えており、
規約が求める「やり直して再現するかを見る」でも再現した**。P90 も実行 2 では正 (3.6 ms) で、
フレームの期限超過はこの土俵で常態的に起きている。10,000 件・3 列の画像グリッドを cold から
フリックする条件そのものが重い (取得・デコードがフリング中に走る) が、**合格基準は条件では
なく値で判定する規約であり、超過は超過として記録する**。

**到達点メモリの行は判定に使ってはならない。** frameCount が 0〜3 枚しかなく、これは
「フリック中にほぼ何も描かれていない」ことを意味する。実際にはアプリが起動直後に
クラッシュしており、上の数値は落ちるまでの数フレームを集計しただけである。
**それにもかかわらずこの計測 (`scrollWithMemoryPrefetch`) は成功として緑になった** —
描画が成り立たなかったことを検出する条件が入っていないため。手順の「未判定は緑にならない」
という要求 (メモリ側には入っている) が、スクロール側には無い。

## 到達点メモリの実機クラッシュ

**先読みの到達点をメモリまでにした土俵は、基準機でアプリが落ちるため計測できない。**

- 症状: `java.lang.IllegalArgumentException: can't create mutable bitmap with Config.HARDWARE`
- 位置: 表示の組み立て中の同期縮小 (`KsImageRequestFactory.downscale` → `Image.toBitmap`)。
  先読みがメモリに載せた元寸の画像を、その場で縮小して初回描画に使う経路
- 抜粋: `image-grid-memory-prefetch-crash-android.log`
- 再現手順 (計測の枠組みを介さずに単独でも再現した): 計測用の経路
  `measurement/image/10000/memory` を開き、**フリックする**。画面を開いただけでは落ちない
  (先読みが元寸を載せ、その項目のセルが新しく組み立てられた時点で落ちる)

原因は、ローダーがデコードした画像が実機では `Config.HARDWARE` のビットマップであり、
そこから可変ビットマップを作れないこと。この経路はレビュー 2 周目のオーナー判断で入った形
(deviation「到達点メモリの先読みと表示の継ぎ目」「表示の組み立て中の同期縮小」) にあたる。
既存の単体テストは Robolectric で走るためソフトウェアのビットマップになり、この分岐を
踏まない。エミュレータでの挙動確認 (`image-behavior-observation.md`) でも表面化していない。

影響は計測にとどまらない。**Sample のデモ画面「画像グリッド」でも到達点をメモリまでにすれば
同じ経路を通る**ため、利用者が `KsPrefetchDestination.Memory` を選んだときに落ちる。
これは計測の不備ではなく実装の欠陥であり、直してから測り直す必要がある。

## 先読みの開始・取消件数 (基準機での実測)

性能値ではなく**挙動の量**。計測の枠組みを使わず、基準機で計測用の経路
`measurement/image/10000/disk` を開いて観測した (観測手段と限界は `image-behavior-observation.md`)。

| 操作 | 先読みの開始 | 先読みの取り消し | 表示要求の開始 | 表示要求の取り消し |
|---|---:|---:|---:|---:|
| 画面を開いた直後 (到達点ディスク) | 15 | 0 | 15 | 0 |
| 速いフリック 5 回 (到達点ディスク) | 120 | 90 | 87 | 51 |

可視件数と同数の窓が張られ (基準機の画面では可視 15 件に対し先読み 15 件)、フリング中に窓から
外れた要求が取り消されている。**基準機では回線を絞らなくても取り消しが観測できた**
(エミュレータでの観測では取得が速すぎて回線を絞る必要があった)。フリック直後に数えているため、
開始のうち完了まで至っていないものが残っている (この表は開始と取り消しだけを見る)。

参考として、同じ土俵をエミュレータ (API 35 / Debug 構成) で数えた過去の値は
先読み 12 / 0・表示要求 12 / 0 (画面を開いた直後)、先読み 42 / 8・表示要求 36 / 3
(速いフリック 5 回、回線を絞って観測) だった。可視件数と入力手段が違うため、
上表と件数は一致しない (別実行である)。

**到達点メモリの土俵ではこの表を作っていない。** 落ちるため観測が成り立たないことに加え、
下記の集計規則によりこの土俵では表示要求と先読みを分けて数えられない。

### この表の集計規則

観測ログの種別 (`kind=`) は、要求から本当に分かることだけを名乗る。上の表の列との対応は次のとおり。

| ログの種別 | 意味 | 上の表での扱い |
|---|---|---|
| `prefetch-disk` | 到達点をディスクまでにした先読み。メモリキャッシュを使わない指定で確実に分かれる | 「先読み」の列 |
| `display-or-memory-prefetch` | 表示要求 / 到達点をメモリまでの先読み / ローダー付属のビューの直接表示のいずれか。**要求からは区別できない** | 「表示要求」の列 (下記の条件付き) |

曖昧な種別を「表示要求」として数えてよいのは、**到達点をディスクまでにした土俵に限る**。この
土俵では到達点がメモリまでの先読みが 1 件も出ず、画面もローダー付属のビューを使っていないため、
この種別に入るのは表示要求だけになる。上の表の 2 行はどちらもこの条件を満たしている。

**到達点をメモリまでにした土俵で数えるときは、この列を「表示要求」と読んではならない** —
先読みと表示要求が同じ種別に混ざるため、分けたければログの種別以外の材料 (取得元の URL と
発生順など) で人が切り分ける必要がある。

## 試行ごとのキャッシュ状態

**すべての試行を空の状態 (cold) から測る。** 試行の前処理で計測対象アプリを起動する際に
画像キャッシュの消去を要求し (`ks_reset_image_cache`)、メモリとディスクの両方を空にしてから
画面を開く。空にしないと 2 回目以降の試行はディスクとメモリが温まり、同じ負荷を独立に 3 回
測ったことにならない。

cold を選ぶ帰結として、取得はどの試行でも実際にネットワークへ出る。したがってこの土俵の
結果は実行時の回線状態を含み、回線の違う日の値どうしを比較できない (同じ実行内の 3 試行の
ばらつきは比較できる)。温まった状態 (warm) の値が要るときは、この取り決めを変える判断が
別途要る。

**絶対基準の超過を読むときはこの取り決めが効く。** cold ではフリング中に取得とデコードが
走るため、warm より不利な条件を測っている。ただし合格基準は条件ではなく値で定めてあるため、
基準を緩める・条件を変えるという判断はオーナーの領分であり、この証跡では値をそのまま残す。

## 未判定として残るもの

- 到達点メモリのスクロール性能 (絶対基準) — アプリが落ちるため
- 到達点メモリのメモリ定常化 (1,000 件 / 10,000 件) — 同上
- 件数比の判定 (到達点メモリ側) — 同上
- 到達点メモリの先読み開始・取消件数 — 同上、かつ種別が分かれないため

## 次に必要なこと

1. **到達点メモリの経路のクラッシュを直す** (実装の欠陥。`Config.HARDWARE` のビットマップから
   縮小できない)。直したうえで到達点メモリの 3 系統を測り直す
2. **到達点ディスクの絶対基準の超過をどう扱うか判断する** — 実装を改善して基準に収める、
   基準または土俵の条件 (cold / 件数 / 画像サイズ) を見直す、のいずれもオーナー判断が要る。
   この土俵は既存の「大量件数」とは別物であり、既存の合格線をそのまま当てるのが妥当かを
   含めて決める必要がある
3. **スクロールの計測が描画の成立を確かめていない点を塞ぐ** — 到達点メモリの計測は、
   アプリが落ちてフレームが 0〜3 枚でも緑になった。メモリ側と同じく「未判定は緑にしない」
   条件をスクロール側にも置く
