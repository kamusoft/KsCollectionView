## 固定 fixture

- 画面: Sample「画像グリッド」と、同じデータ・同じ配置を描く計測専用の起動経路
- 件数: 10,000 件、3 列、セル間と外周の余白は Sample と同じ
- セル: 正方形の `KsImage` (fill) と ID の文言
- 取得元: ID から決まる公開プレースホルダー画像サービスの URL (400 × 400)
- プリフェッチ: 到達点はディスクまで (Sample の初期選択と同じ)

要素・配置・外周の余白・セル・プリフェッチの宣言は、デモ画面と計測用の画面が同じ宣言元
(`ImageGridFixture`) から取る。コレクションの組み立てそのものを 1 箇所に集めているため、
両者の土俵が食い違う書き方ができない (Android は宣言元の共有に加えて、両画面を実際に描いて
一致を確かめるテストを持つ。iOS は組み立てが 1 本なのでテストでの確認を持たない)。

取得はネットワークに依存するため、この土俵の結果は実行時の回線状態を含む。
「大量件数」の土俵 (固定高・可変行高混在の 2 列) とは別の土俵であり、値を比較しない。

## メモリ

手順は iOS 性能検証の規約どおり。Release 構成の app を Simulator に入れ、計測専用の起動経路を
自動実行で走らせる (走査・記録・終了まで app 自身が行う)。1 往復は可視範囲の高さの半分ずつ
content offset を送って先頭から末尾、そして先頭へ戻る走査で、各段階は「目的の位置に到達し、
その位置のセルが載った」ことを条件に待つ。

環境: iPhone 17 Pro Simulator (iOS 26.5) / Release 構成。規約はメモリの計測を Simulator で行うと
定めており、判定は定常化 (往復を重ねても増え続けないこと) に限る — Simulator のメモリ絶対値は
実機と異なるため、この土俵の値を絶対量の判定に使わない。

2 回の実行は独立している。実行ごとに app を削除して入れ直し、画像のキャッシュを空の状態から
始めている。

### 実行 1

| 往復 | `phys_footprint` | 1 往復後に対する増分 | 通過項目 |
|---|---:|---:|---:|
| 1 往復後 | 38,455,432 bytes | — | 10,000 / 10,000 |
| 2 往復後 | 39,471,240 bytes | +2.64% | 10,000 / 10,000 |
| 3 往復後 | 40,241,288 bytes | +2.00% | 10,000 / 10,000 |
| 4 往復後 | 40,683,656 bytes | +1.15% | 10,000 / 10,000 |
| 5 往復後 | 41,437,320 bytes | +1.96% | 10,000 / 10,000 |

判定: **定常化を確認した**。4・5 往復目の増分が 1 往復後の値の 2% 以内 (+1.15% / +1.96%) で
2 往復連続して収まり、上限の 10 往復に達する前に打ち切っている。走査は毎往復 10,000 件すべてを
通過した。3 往復目の増分 (+2.00%) は許容差をわずかに上回っており、そこでは定常と判定していない。

### 実行 2

| 往復 | `phys_footprint` | 1 往復後に対する増分 | 通過項目 |
|---|---:|---:|---:|
| 1 往復後 | 38,471,840 bytes | — | 10,000 / 10,000 |
| 2 往復後 | 39,569,568 bytes | +2.85% | 10,000 / 10,000 |
| 3 往復後 | 40,093,856 bytes | +1.36% | 10,000 / 10,000 |
| 4 往復後 | 40,519,840 bytes | +1.11% | 10,000 / 10,000 |

判定: **定常化を確認した**。3・4 往復目の増分が許容差以内 (+1.36% / +1.11%) で 2 往復連続して
収まっている。走査は毎往復 10,000 件すべてを通過した。

### 実行間のばらつき

| 見る値 | 実行 1 | 実行 2 | 差 |
|---|---:|---:|---:|
| 1 往復後の値 | 38,455,432 bytes | 38,471,840 bytes | +0.04% |
| 定常と判定した往復 | 5 往復目 | 4 往復目 | 1 往復 |
| 定常と判定した時点の値 | 41,437,320 bytes | 40,519,840 bytes | 2.26% |

系統としての判定: **合格**。規約が求める独立 2 回の実行のいずれでも、上限の 10 往復に達する前に
定常化した。実行間のばらつきは 1 往復後の値で 0.04%、定常時の値で 2.26% であり、定常化の成否は
どちらの実行でも変わらない。

ただし増分は 0 にはならず、定常と判定した往復でも 1 往復あたり 0.4〜0.8 MB の増加が残っている
(規約の合格線は「増分が 1 往復後の値の 2% 以内」であって「増分が 0」ではない)。この土俵の値は
実行ごとの回線状態を含むため、回線の違う日の値どうしは比較できない。

なお、この変更の以前の便で 1 回だけ実行した記録 (1 往復後 82,168,976 bytes、4 往復目で定常) が
あるが、Simulator の版を記録しておらず、上の 2 回とは環境が揃っていない。合格の判定材料には
使わない。

## プリフェッチの開始・取消件数

Sample「画像グリッド」(プリフェッチはディスクまで) を iPhone 17 Pro Simulator (iOS 26.5) の
Debug 構成で開き、app を削除して入れ直した状態から 4 回の速いフリックを行ったときの件数。
観測手段と限界は `image-behavior-observation.md` に書いたとおりで、到達点がディスクまでの先読みは
ローダー自身の計測記録の側で数えている。

| 対象 | 開始 | 取り消し | 完了 |
|---|---:|---:|---:|
| 元データの取得 (先読みを含む) | 200 | 41 | 159 |
| 表示要求 | 165 | 43 | 122 (失敗 0) |

フリング中に窓から外れた取得が実際に取り消されている。デコードは開始・終了とも 124 件で、
取り消された取得はデコードまで進んでいない。

この表は、`image-behavior-observation.md` の 7.4 に載せた取り消しの観測とは**別の実行**である
(あちらは同じ土俵の以前の実行で、元データの取得 183 / 48 / 135、表示要求 254 / 53 / 201)。
件数はフリックの速さと回線状態で変わるため、2 つの表の数字は一致しない。どちらの実行でも
「開始した取得の一部が取り消され、残りが完了する」という読み取りは同じである。

元データの取得 (200) が表示要求 (165) を上回るのは、この差に先読みが含まれるためである
(到達点がディスクまでの先読みは表示要求として現れない)。ただし**両者の差がそのまま先読みの
件数になるわけではない** — 同じ URL への表示要求と先読みは 1 本の取得にまとめられるため、
この観測から先読みの件数だけを取り出すことはできない。

### この表の集計規則

観測ログの種別 (`kind=`) は、要求から本当に分かることだけを名乗る。上の表の行との対応は次のとおり。

| ログの種別 | 意味 | 上の表での扱い |
|---|---|---|
| `display` | `KsImage` の表示要求。表示枠から決めた縮小の指定を持つのはこれだけ | 「表示要求」の行 |
| `prefetch-or-loader-display` | 到達点がメモリまでの先読みか、ローダー付属のビュー (`LazyImage`) の直接表示のいずれか。**要求からは区別できない** | どちらの行にも数えない (下記) |
| (ログに現れない) | 到達点がディスクまでの先読み。元データの取得として走り割り込み処理へ通知が来ない | 「元データの取得」の行 — ローダー自身の計測記録の側で数える |

この土俵は到達点がディスクまでで、画面もローダー付属のビューを使わない。したがって曖昧な種別に
入る要求は構成上生まれないはずであり、上の表の「表示要求」は `display` の件数だけで足りる。
**この計測では、その曖昧な種別の件数を実際に数え上げて 0 件であることを確かめている** (構成から
導いた推論だけに頼っていない)。**この種別が出る土俵 (到達点をメモリまでにする / 検証画面の
ローダー付属ビューを使う) で数えるときは、その件数を先読みとも表示とも読んではならない。**

完了した表示要求 122 件の取得元は、この実行ではすべてネットワークだった。app を入れ直した直後で
ディスクにもメモリにも何も無い状態から始めているため、この数字を「先読みが効いていない」根拠に
してはならない — 先読みと表示が同じ取得にまとまった場合、その表示は先読みの完了を待って成功し、
取得元はネットワークとして記録される。プリフェッチが効いていることの判定は
`image-behavior-observation.md` の 7.3 の観測 (先読み済みの ID に要求が出ないこと) で行っている。

## スクロール性能 (hitch time ratio)

環境: iPhone 11 (基準機) / iOS 18.7.8 / Release 構成。記録は Instruments の Animation Hitches
テンプレート。操作は Debug の XCTest Runner から Release app を `--screen 画像グリッド` で起動し、
一覧が出てから実座標タッチによる 3 秒間の連続フリックを行う
(`samples/ios/KsCollectionViewSamplesUITests/PerformanceDriverUITests.swift` の
「画像グリッドを3秒間連続フリックスクロールする」)。

3 試行は独立している。試行ごとに app を削除して入れ直し、画像のキャッシュが空の状態から始めている。

### 集計の窓と帰属の決め方

規約は「3 秒間の連続フリック」の hitch time ratio を求める。この計測では窓と帰属を次のように決めた。
どちらも規約が手段まで定めていない部分であり、決め方によって値が変わるので明示する。

- **窓**: 駆動テストはフリックの繰り返しで終わるため、テスト終了時刻の 3.3 秒前から終了時刻までを
  窓とする (3 秒のフリック + 0.3 秒の余裕)。比は 3.0 秒で割る。窓の位置は、記録に現れる app 起動の
  画面遷移 (装置全体側のプロセスの commit) がテスト開始直後に来ることで筋が通ることを確かめた
- **帰属**: 記録は端末全体を対象に取っている (後述)。したがって hitch には Sample 以外のプロセスの
  ものも混じる。各 hitch の commit 段階に現れるプロセスを見て、Sample が含まれるものだけを数えた

### 結果

| 試行 | 窓内でアプリに帰属する hitch | hitch time の合計 | hitch time ratio | 判定 |
|---|---:|---:|---:|---|
| 1 | 0 件 | 0.00 ms | **0.00 ms/s** | 合格 |
| 2 | 3 件 | 150.10 ms | **50.03 ms/s** | **不合格** |
| 3 | 0 件 | 0.00 ms | **0.00 ms/s** | 合格 |

系統としての判定: **不合格**。規約は「3 回すべて 5 ms/s 未満」を求め、平均で合格にしないと定める。
試行 2 が合格線の 10 倍に達しており、平均 (16.68 ms/s) も合格線を超える。

### 試行 2 の内訳

| hitch | 長さ | 種別 | commit 段階に現れたプロセス |
|---|---:|---|---|
| 窓の先頭 +0.33 秒 | 71.42 ms | Expensive Commit(s) - Expensive Rendering | 自動化の重ね表示 (46.66 ms)、Sample (0.25 / 0.53 ms) |
| 同 +0.40 秒 | 16.64 ms | Pre-Commit(s) latency | Sample のみ (2.42 / 1.01 ms) |
| 同 +0.72 秒 | 62.04 ms | Pre-Commit(s) latency | Sample のみ (2.09 / 0.45 ms) |

3 件はいずれもフリック開始から 0.8 秒以内に固まっており、窓の後半 2 秒には 1 件も無い。
最も長い 2 件のうち 62.04 ms の方は commit 段階そのものが 2.87 ms しかなく、遅れは commit 前の
主スレッドの待ちに出ている (Pre-Commit latency)。

**最もアプリに有利に読んでも合格しない**: 計測の足場である自動化の重ね表示が支配的な 1 件目
(71.42 ms) を除いても、残り 2 件で 78.68 ms → **26.23 ms/s** であり合格線を超える。

窓の外にも hitch はあるが、アプリには帰属しない。試行 2 の窓の 0.53 秒後に 33.32 ms が 1 件
(commit は装置全体側のプロセス)、試行 3 の窓の 0.17 秒後と 0.76 秒後に 17.05 ms と 16.67 ms が
各 1 件 (同じく Sample 以外) 出ている。試行 1・3 の窓内は、アプリ・他プロセスとも hitch が 0 件だった。

### この計測が規約の手順と違うところ

規約は「Instruments の Animation Hitches テンプレートを Sample process に接続する」と定めるが、
この便ではプロセスを指定した記録が成立しなかったため、**端末全体を対象にした記録**に替えている。
観測した現れ方は次のとおりで、いずれも記録側の都合であり、アプリの挙動ではない。

| 試したこと | 起きたこと |
|---|---|
| 起動済みの app にプロセス指定で接続し、Runner から前面化してフリック | 前面化の瞬間に「対象 app が終了した」として記録が打ち切られ、フリック区間が入らない |
| プロセス指定のまま app を放置して記録 | hitch 系のどの表にも 1 行も入らない (フリックをしていないので妥当だが、記録が成立していることの裏付けにならない) |
| 端末全体を対象に記録 | 成立した。hitch と、その commit 段階のプロセスまで取れる |

この差し替えには、**計測の足場が測る対象に混じる**という代償がある。上の内訳のとおり、試行 2 の
最も長い hitch は自動化の重ね表示の commit が支配的で、これはプロセス指定の記録なら混じらない
可能性がある。ただし前述のとおり、その 1 件を除いても合格線は超える。

なお、**HID (触った入力) の表は 3 試行とも 0 行だった**。このためフリックの区間を記録側のデータで
直接指すことはできず、窓はテストの終了時刻から逆算している。

### この結果の読み方 (限界)

- 試行間のばらつきが大きい (0.00 / 50.03 / 0.00)。3 試行では「たまたま出た 1 回」なのか
  「一定の割合で出る」のかを分けられない。合否の判定には影響しない (規約は 3 回すべてを求める) が、
  原因を追うには試行数を増やす必要がある
- 土俵はネットワークからの画像取得を含み、各試行はキャッシュが空の状態から始まる。したがって
  この値は回線状態を含む。「大量件数」の土俵 (ネットワークを含まない) の値とは比較しない
- 記録された hitch はいずれもフリック開始直後に固まっている。開始直後は取得・デコードが一斉に
  立ち上がる区間であり、`Pre-Commit(s) latency` (commit 前の主スレッドの待ち) がその 2 件を
  占めることと整合する。ただし**この計測は原因を特定していない** — 主スレッドで何が待っていたかは
  この記録からは分からない

数値抜粋は `scripts/log-sanitize.py` を通し、置換対象がないことを確認した。個体識別子・端末名・
開発者識別子・ローカル絶対パス・生の trace は evidence に保存していない (trace はスクラッチに手元保管)。
