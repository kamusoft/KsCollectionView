# Deviation: image-loading

- [付随修正] `android/gradle/libs.versions.toml` の Compose BOM 版のコメント: 作業文書への裸参照 (`deviation.md を見る`) を削除した。理由: cross/comment-policy.md の「禁止する参照」に該当し、本務で触るファイル内の局所修正で済むため (2026-09-07)
- Requirement「共有キャッシュ」/ Scenario「iOS のディスクキャッシュ有効化」: spec では「iOS はライブラリの初回利用時に、共有パイプラインにディスクキャッシュが設定されていなければ有効化した構成で差し替える (SHALL)」→ オーナー判断により、**利用者が明示的に呼ぶ公開 API を 1 つ設け、呼ばれたときだけ差し替える**。理由: Nuke 13.2.0 は共有パイプラインの割り込み処理 (`delegate`) を外から読めず (宣言が internal)、design Decision 1 が要求する「現在の設定と割り込み処理をそのまま引き継いだ差し替え」が実現できない。設定 (`configuration`) 側だけを引き継ぐ自動差し替えは、リクエスト直前の認証ヘッダ付与を割り込み処理で行うアプリで画像が読めなくなる壊れ方をするため、自動化を取りやめた (2026-09-07)
- 上記の公開 API は `KsImagePipeline.enableSharedDiskCache()` として実装した (iOS のみ。Coil は既定でディスクキャッシュが有効なため Android に対応物は作らない)。既知の副作用が 2 つあり、いずれも公開 doc コメントに明記した上で tasks 8.1 の利用者向け注記に含める: ①差し替えで割り込み処理 (`delegate`) は既定に戻る (Nuke が読み取り手段を公開していないため引き継げない。代替は利用者自身が `dataCache` 付きパイプラインを共有インスタンスに置くこと) ②コレクション表示後に呼んでも既存のコレクションのプリフェッチ経路には反映されない (生成時点の共有パイプラインを捕捉するため。アプリ起動時に一度だけ呼ぶ運用) (2026-09-07)
- tasks 4.4 (Android の統合テスト) の実現手段: design Decision 8 は「カウンタ付き `Fetcher.Factory` / `Decoder.Factory` を登録したテスト用 ImageLoader」→ 取得回数の計測を**カウンタ付きの `NetworkClient` を差した `NetworkFetcher.Factory`** で行う。理由: Coil 3 はディスクキャッシュの読み書きを `NetworkFetcher` の内部に持つため、Fetcher ごと差し替えるとディスクキャッシュ経路を迂回してしまい、Scenario「ディスク到達点の後の表示」が観測できない。「取得層をスタブする」という Decision 8 の趣旨は保っており、`Decoder.Factory` は design どおり (2026-09-07)
- [付随修正] `KsImageCacheContractTest` (本 change 内で作成した Android のテスト) の取得回数・デコード回数カウンタ: 素の `Int` を `AtomicInteger` に変えた。理由: 取得が IO スレッドで走るため可視性の問題で古い値を読むことがあり、2 件同時プリフェッチのテストで間欠失敗が実際に再現したため (2026-09-07)
- Android の `KsImageSource.Resource` の描画経路: design Decision 6 の表では resource も Coil の `AsyncImage` 経由 → Compose の `painterResource` で同期的に描く経路にした。理由: spec の Requirement「KsImage の表示状態」が「リソースは読み込み中を経由せず成功か失敗になる (SHALL)」と定めており、Coil 経由では必ず一瞬読み込み中を経由するため spec を優先した。付随して `KsImageCache.remove(Resource)` は design 表の `memoryCache.remove` ではなく no-op になる (iOS のアセットと対称) (2026-09-07)
- iOS の `fit` の縮小指定: design Decision 5 は「fit は枠に収まる最大寸法 (`maxPixelSize` = 枠の長辺 × 表示倍率)」→ `ImageRequest.ThumbnailOptions` の `.aspectFit` / `.aspectFill` を使う。理由: `maxPixelSize` は正方形以外の枠では短辺方向に枠を超え、spec の Scenario「枠より大きい画像」(fit では枠のサイズを超えない) を満たさないため。design の規範文 (収まる最大 / 覆う最小) には従っている (2026-09-07)
- tasks 5.1 の `imageIdKey`: Nuke 13.2.0 では `ImageRequest.UserInfoKey.imageIdKey` が deprecated → `ImageRequest.imageID` プロパティを使う。世代付き識別子の挙動は変わらない (2026-09-07)
- iOS の `KsImageInvalidation`: design は `@Observable` → `ObservableObject` で実装。理由: `Package.swift` の下限が iOS 16 で `@Observable` (iOS 17 以上) が使えないため (2026-09-07)
- [注記材料] Android の `KsImageCache.remove` のキャッシュ鍵の導出は、リモート以外が best-effort。ファイルのソースはメモリ鍵を完全一致と Coil が file URI に付ける接尾辞の前置一致で拾っており、テストでは担保していない (spec の Scenario がリモートのソースだけを要求しているため)。tasks 8.1 の利用者向け注記の材料 (2026-09-07)
- Android の `KsImageCache` のシグネチャと本体の依存: 実装当初は Coil の共有インスタンス取得に必要な画面のコンテキストを第 1 引数に取る形 (`clear(context, scope)` / `remove(context, source)`) だったが、オーナー判断により **iOS と同じ引数構成に揃える** (`clear(scope)` / `remove(source)`)。application context は `androidx.startup` の Initializer で捕捉する。理由: core/ADR-0002 (accepted) が「パラメータ名を両プラットフォームで 1 対 1」と定めており、Compose を使うアプリには `androidx.startup.InitializationProvider` が既に入っている (Sample の実マニフェストで emoji2 / lifecycle / profileinstaller の 3 件を確認) ため相乗りでき、利用者のアプリに ContentProvider が増えないと確認できたため。本体の依存に `androidx.startup:startup-runtime` が加わる — proposal の Impact に無い追加だが、既に Compose 経由で推移していたものを明示依存にするもので、利用者への新たな推移依存にはならない (2026-09-07)
- [付随修正] `samples/android/.../MemoryRoundTripScreen.kt`: 配置・先読み宣言・1 項目の見た目を引数化した (既定値は従来と同じ)。理由: 画像グリッドの往復計測を既存の走査実装で行うため (2026-09-07)
- tasks 7.1 / 7.5 の「受け口のカウンタ」による計数: 内部の受け口はライブラリ internal で Sample から差し込めないため、**ローダー自身の通知** (iOS = 共有パイプラインの割り込み処理、Android = `ImageLoader` の `EventListener`) と、iOS はローダーの計測記録 (signpost) で数えた。既知の限界を証跡に明記済み: iOS は到達点がディスクまでの先読みが割り込み処理に通知されない (計測記録側で数える)、Android は到達点がメモリまでの先読みを表示要求と区別できない (ディスクまでは `memoryCachePolicy=DISABLED` で区別可) (2026-09-07)
- 計測用の観測コードの入り方がプラットフォーム間で非対称: iOS の観測用コードと検証画面は既存の `--verify-*` 画面と同じく release の Sample にも入る (起動引数でのみ到達)。Android は計測用ソースセットに限定され配布構成には入らない (2026-09-07)
- 縮小手段の選び分け (iOS): design Decision 5 は「`ImageRequest.ThumbnailOptions` を付けて要求する」→ **元寸がメモリにあるかで縮小手段を選び分ける** (元寸あり → デコード後の縮小で再デコードを避ける / 元寸なし → デコード時の縮小で元寸をメモリに展開しない)。理由: 相方レビュー Major 1 で「`ThumbnailOptions` 付きの要求は元寸のメモリ項目を再利用せず再デコードする」ことが再現し、spec の Scenario「メモリ到達点の後の表示」と「枠より大きい画像」を同時に満たすにはこの選び分けが必要だったため。spec の Requirement は両方とも満たす (2026-09-07)
- `clear(.disk)` の実挙動: spec の Requirement「キャッシュのクリア」(消去後は表示中の画像が読み込み中を経て再取得される) を満たすため、`.disk` は元データに加えて**そこから作られたメモリ項目も落とす**。要求の識別子に世代を混ぜてメモリを避ける案は、spec の「消去は共有に影響しない」に反する (ローダー付属ビューと鍵が永久に分かれる) ため採らなかった。結果として消去範囲の `.disk` と `.all` の実挙動が同一になり、`.memory` だけが別挙動になる (2026-09-07)
- キャッシュ消去時のフェンスの限界: `clear` / `remove` は進行中の取得を止めてから消すが、止められるのは取り消しが届く前に完了しきっていない取得まで。取り消しとキャッシュ書き込みが同時に起きた場合の書き戻しは防げない (ローダーが書き込み地点への割り込みを公開していないため)。また消去後、次に可視範囲が動くまで先読みは自動再開しない (spec は再開を要求していない) (2026-09-07)
- 先読み台帳の直列化がプラットフォーム間で非対称: Android は `KsImageCache` が任意のスレッドから呼べるため台帳操作を錠で直列化。iOS は `@MainActor` で保証している (2026-09-07)
- [付随修正] `KsAppContextTest` (Android): 全件実行でクラス実行順に依存して落ちる問題を解消した。理由: androidx.startup は初期化結果を同一 JVM で使い回すため、先に別クラスが初期化していると古い Application を見る。本 change 内で作成したテストの潜在的な順序依存が、テスト追加で表面化したもの (2026-09-07)
- [付随修正] `KsImageCacheContractTests` (iOS): スタブ取得層に応答保留の口を足し、表示レベルのテストの待機を実行ループ + 表示完了の合図を持つ形にして間欠失敗を解消した。理由: Major 3 の再現に保留が必要で、同ファイルの既存テストの間欠失敗も同じ待機の作りが原因だったため (2026-09-07)
- 消去範囲の選択肢: spec の Requirement「キャッシュのクリア」は `clear(.memory / .disk / .all)` の 3 択 → オーナー判断により **「ディスクまで」を廃止し、「メモリだけ」と「全部」の 2 択にする**。理由: 上記のとおり `.disk` と `.all` の実挙動が同一になったため、同じ動きをする選択肢を 2 つ公開すると利用者が違いを期待して誤解する。名前が「ディスクまで」なのにメモリ上の画像も落ちる乖離も併せて解消する (2026-09-07)
- spec 内の 2 文の衝突 (`KsImage` の表示状態): 「枠のサイズが確定するまでは読み込み中の表示を出す (SHALL)」と「メモリキャッシュにあれば読み込み中を経由せず成功になる (SHALL)」が、**サイズ未確定かつメモリに画像がある**局面で衝突する。**後者を優先**し、その局面では読み込み中ではなくキャッシュ済みの画像を描く。理由: 後者の方が具体的で、Scenario「戻ってきたときの再表示」が名指ししているため。「サイズが確定するまで取得を開始しない」側の契約は変えていない (2026-09-07)
- `KsImage` のスロット指定の糖衣がプラットフォーム間で非対称: ラベル付きの指定 (Swift `loading:` / `failure:` ⇔ Kotlin `loading =` / `failure =`) は 1 対 1 だが、**ラベルを省いた末尾クロージャ**は Swift では読み込み中と失敗のどちらにも当たりうるため曖昧になり書けない (Kotlin は末尾ラムダが失敗側に束縛される)。修正前も書けなかったため退行ではない (2026-09-07)
- Android の `KsImage` がメモリ上の画像を直接読むようになった帰結: 表示枠より小さい画像がメモリにあると、ローダーが再デコードを決めるまでの数フレームだけ拡大表示になる。読み込み中を挟むより spec に近いと判断したが、実機での見え方は未確認 (2026-09-07)
- Android のキャッシュ操作の未初期化時: レビュー指摘を受けて例外から「警告ログを出して no-op」へ変更。**core/ADR-0011 の「debug では assertion」は掛けられなかった** — debug 判定が組み込み先アプリのコンテキストから読む作りで、そのコンテキスト自体が無いのがこの局面のため。ライブラリ自身のビルド種別で代用する案は ADR-0011 が明示的に否定している判定軸なので採らず、落とさない側に倒した (2026-09-07)
- `KsAppContext.reset()` (internal) をテスト専用に追加した。理由: 初期化前の状態を作るテストに必要なため。テスト側は finally で元に戻すためクラス実行順への依存は作らない (2026-09-07)
- `KsImagePipeline.enableSharedDiskCache()` のディスクキャッシュ作成失敗経路は、警告を出すところまで実装したが**テストでは踏んでいない**。理由: 検証のために内部 factory の注入口を足しても確かめられるのは「共有パイプラインが差し替わらない」ことだけで、既存テストの裏返しにしかならないため (2026-09-07)
- Android の計測の試行条件: 3 試行すべてを **cold** (試行ごとに画像キャッシュを消してから起動) に決めた。理由: 「独立した 3 試行」を成り立たせるため。帰結として毎試行ネットワークに出るので回線状態のばらつきを拾い、回線の違う日の値どうしは比較できない (証跡に明記済み) (2026-09-07)
- 到達点メモリの先読みと表示の継ぎ目 (両プラットフォーム): レビュー 2 周目で「先読みは寸法なしの鍵で元寸を載せ、表示は縮小指定付きの鍵で探すため一致しない」ことが判明し、iOS は読み込み中を経由 (Requirement「KsImage の表示状態」違反)、Android は鍵の判定を緩めた結果 元寸をそのまま描く (Requirement「KsImage の縮小デコード」違反) と、同じ継ぎ目を逆向きに倒していた。**オーナー判断により両プラットフォームを「元寸を同期で引き当て、その場で縮小して初回描画に使う」形に揃える**。縮小済みの画像は元寸から作り (ネットワーク・ディスクへ取りに行き直さない)、以後は縮小指定付きの鍵で当たる。2 つの Requirement を両方満たすため spec の変更は不要。成立しない場合はどちらの契約を優先するか改めてオーナー判断を仰ぐ (2026-09-07)
- Android の表示要求のキャッシュ鍵: ローダー内部の付随情報名 (`coil#size`) を使って表示サイズを鍵に載せている。理由: ローダーが鍵の表示サイズと要求の表示サイズを突き合わせ食い違う項目を捨てる作りのため、この名前でないと載せた画像が使われずに捨てられる (逆アセンブルで確認)。ローダーの版が上がると壊れ得るが、壊れ方は「再デコードが増える」方向で表示は正しいまま。当てはめ方の区別には自前の名前 (`ks#scale`) を併用する (これが無いと fit の縮小結果が fill でも使われる不具合が出た) (2026-09-07)
- Android の `KsImage` の枠の読み取り: `rememberConstraintsSizeResolver()` → `BoxWithConstraints` に変更。理由: 表示枠を最初の構成で同期に読む必要があるため。画像 1 枚あたり subcomposition が 1 段増える。10,000 件グリッドでの実測は未実施 (実機計測は別タスク) (2026-09-07)
- 縮小済み画像を共有ローダーのメモリへ書く (両プラットフォーム): 1 ソースにつき「表示サイズ × 当てはめ方」の数だけ項目が増える。「ライブラリ独自のキャッシュ領域を持たない」契約は守っている (2026-09-07)
- [付随修正] `KsImageCacheContractTests` (iOS) の間欠失敗を解消した。原因は「合図役に置いた未取得の 1 枚が消去の直後に取り直されるとは限らない」競合で、変更前の形でも 4 回に 1 回落ちることを確認済み。取得の完了を待ってから消す・消去後は検査対象の URL だけを数える・待つ間にレイアウトの機会を促す、の 3 点に変更 (2026-09-07)
- [付随修正] `KsImageCacheContractTests` / `KsImageTests` (iOS) に窓の後始末を追加した。理由: テストをまたいで生き残った表示が、次のテストのパイプラインへ読み込みを出し続けるため (2026-09-07)
- [付随修正] `KsImageCacheContractTest` (Android): 表示の検査を本番の組み立て経由に変更し手書きの複製を廃止した。あわせて共有ローダーを直接使うテストの要求を、ライブラリ独自の鍵を付けない素の要求に直した (「ローダー付属ビューと同じ形」という趣旨に合わせるため) (2026-09-07)
- キャッシュ消去のフェンスの適用範囲 (両プラットフォーム): **対象は先読み層が出した進行中の取得のみ**で、`clear(.memory)` / `clear(.all)` / `remove(source)` のすべてで消す前に止める。**表示中の `KsImage` が出した進行中の取得は対象外**のため、消去の直前に完了した表示要求は消去したのと同じ鍵へ書き戻しうる。理由: iOS は表示要求を止める手段があるが (ローダーが取得ハンドルを渡す)、Android の Coil 3.5.0 には公開の取り消し口が無く、代替 3 案 (再取得を始めてしまう / Compose のメインスレッド前提を破る / 通常の取り消しまで効かなくなる) をいずれも確認済み。iOS だけ入れるとこの change で 2 度 Major になったプラットフォーム間非対称を新たに作るため、両方とも先読み層のみに揃えた。なお `clear(.memory)` は spec が「表示中の画像を置き換えない」と定めるため、そもそも表示要求を止めてはいけない。**この受容はオーナー未確認** — 完了報告で提示する (2026-09-07)
- 先読み宣言のクロージャの呼び出し回数: 台帳の再解決を入れたため、配列更新・先読み通知のたびに台帳に載っている件数分 (可視 + 窓) だけクロージャを呼ぶようになった (配列全長には比例しない)。帰結として、クロージャ自体を差し替えた場合、従来は既存の追跡分に反映されなかったが、今後は次の通知・配列更新の時点で旧 URL を止めて新 URL を取りに行く (spec の「差し替えた場合は以後の新しい取得にだけ反映される」の範囲内と判断) (2026-09-07)
- 計測入口の土俵一致の担保の仕方がプラットフォーム間で非対称: Android は宣言元 (`ImageGridFixture`) をデモ画面と計測画面で共有し、土俵の一致を静的テストで確かめる → **iOS はコレクションの組み立て関数そのものを 1 本に寄せた**ため、土俵が食い違う書き方が型の上で書けない (一致テストは追加していない — iOS Sample に unit test ターゲットが無く追加には project ファイルの変更が要るため)。担保の強さは iOS の方が上だが、作りは非対称 (2026-09-07)
