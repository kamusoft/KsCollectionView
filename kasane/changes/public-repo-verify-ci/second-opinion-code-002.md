## 指摘事項

### [🟡 Minor（優先度: 高）] 行頭以外の `@Test` が検出されず、期待クラス集合から黙って抜ける

**該当箇所**: `scripts/ci/check-android-test-count.py:71`、`scripts/ci/check-android-test-count.py:170`、`scripts/ci/check-android-test-count.py:171`

**問題点**: `TEST_ANNOTATION` は空白の直後に `@Test` がある行だけを認識する。このため、別の注釈を同じ行で先に書いた有効な Kotlin のテストを見落とす。

```kotlin
package example

import org.junit.Test

class ATest {
    @Test fun a() {}
}

class BTest {
    @Suppress("unused") @Test fun b() {}
}
```

コードを静的に追うと、`ATest` は期待集合に入るが、`BTest` のメソッド行は正規表現に一致せず、そのまま読み飛ばされる。`orphans` にも記録されない。結果 XML が `example.ATest` の分だけあり、実行件数が正なら、`BTest` の結果が欠落していても検査は成功する。

また、`class BTest { @Test fun b() {} }` のようにクラスとテストを同じ行に書いた場合も、クラス宣言の処理直後の `continue` により `@Test` が検査されない。

これは verification-ci「Android の検証」の Scenario「一部のクラスの結果しか無いと落ちる」と、design.md の Decision 4 が求める期待集合の縮小防止に反する。追加された孤立 `@Test` の検査も、同じ検出条件に依存しているため、この経路を防げない。

現在のリポジトリのテストが欠落しているという指摘ではない。しかし、前回と同じ失敗形態が有効なソースの書き方で残るため、承認前の修正対象とする。

**推奨修正**: クラス宣言の認識とテスト注釈の認識を同じ行でも行い、先行する注釈があっても `@Test` を検出する。認識できない書き方は黙って除外せず、検査失敗として示す。コメントや文字列中の `@Test` を誤認しないようにする。

上記 2 形式について、通常形式のクラスと混在させ、対象クラスの結果 XML だけを欠落させたときに失敗する回帰テストを追加する。対象クラスの XML がそろった正常系も確認する。

## アクションプラン

1. Android のテスト注釈の検出を補強し、上記の欠落ケースを回帰テストに追加する。
2. ホスト側でスクリプトのテストを実行し、件数・失敗・スキップを証跡に追記する。
3. 修正差分について、期待集合が縮んでも検査を通る経路が残っていないか再レビューする。
