# Exploration: ios-prefetched-cell-content-refresh

## 課題 / 動機

iOS エンジンで、画面外で先行して組み立てられたセル (UICollectionView のセル先行組み立て) は、同値配列の更新や観測する値の変化が届いてもテンプレートの内容が呼び直されない。同値配列の更新でテンプレートを呼び直すのは可視セルだけ (`KsCollectionViewController.reconfigureVisibleCells`、ios/ADR-0006) で、観測する値が変わったときの残存セルの作り直しも可視セルだけが対象 (ios/ADR-0008)。そのため先行組み立て済みのセルは、呼び出し側の古い状態で作られた内容のまま表示に入りうる。ADR-0006 の「同値配列でも表示中のセルは作り直す」の意図から漏れている可能性がある。

コード中のコメント「画面外のセルは表示されるときに最新の構成で作られる」(`ios/Sources/KsCollectionView/KsCollectionViewController.swift` の `reconfigureVisibleCells` の説明と、もう 1 か所) は、テンプレートの内容については先行組み立て済みのセルに当てはまらない。

`ios-separator-update-guard` (S 級) のレビュー 2 回目 (`kasane/changes/ios-separator-update-guard/review-002.md` の Suggestion、2026-09-24) で見つかった既存の制約。同 change はセルが表示に入る時点 (`willDisplay`) で位置依存の表示とタッチ色だけを揃える形を入れたが、テンプレートの内容は扱っていない。同 change の差分で入ったものでも悪化したものでもない。ユニットテストのホストでは先行組み立てが起きないため、実害は実証していない。オーナー判断で別 change として簡易起票した (同梱しないのは、表示に入る時点で内容を作り直すと SwiftUI の作り直しの費用がスクロール中にかかり、直し方と性能の判断が要るため)。

## 未決の論点

**未探索 (簡易起票)** — 深掘りはこのメモを出発点に通常の探索で行う。現時点で見えている疑問:

- 実害の有無: 実機でセル先行組み立てが起きる条件で、同値配列の更新や観測する値の変化の後に古い内容が表示に入るかを確かめる (Simulator のユニットテストでは再現しない)
- 直し方の候補: 表示に入る時点で「前回組み立て以降に構成が変わったセル」だけ内容を作り直す (世代番号の比較等) / 先行組み立て済みのセルを可視セルと同じく作り直しの対象に含める / 既知の制約として ADR-0006・0008 に明記する
- 性能: 表示に入る時点での作り直しをスクロール中に行う費用 (先行組み立ての利点を打ち消さないか)
- コメントの修正: 直し方にかかわらず、上記コメントは実態に合わせる必要がある。`kasane/concepts/ios/architecture/collection-engine.md` の「観測する値の変化だけがテンプレートを呼び直す」の表 (配列が変わる行の「画面外セルは表示時に最新構成で作られるため対象外」) も同じ前提に立っている
