# Deviation: ios-engine-foundation

- [付随修正] iOS 26 のセル登録準備: 初回セル取得の処理中にテンプレート用のセル登録を生成すると実行時例外になるため、snapshot 適用前に使用する全テンプレートキーの登録を準備するよう修正した。理由: 同じ collection-core 能力内の局所的な実行時互換修正で、Sample の起動に必要なため (2026-09-02)
- list の区切り線: spec では「行の間に区切り線を既定で表示」→ 指示により各区切り線を左右端まで描画し、先頭行の上にも区切り線を描画する。理由: オーナーの実機確認で必要なリスト外観として確定したため (2026-09-02)
- list の区切り線の太さ: design では 1 物理ピクセル相当の hairline → 指示により Retina 上でも視認しやすい 1pt で描画する。理由: オーナーの Simulator 確認で hairline が薄すぎて判別しづらかったため (2026-09-02)
- iPhone の対応向き: Sample では逆さま portrait も宣言して検証 → ホームボタンのない iPhone が `portraitUpsideDown` をサポートしないため、iPhone Sample は通常 portrait と左右 landscape の3方向を対象とする。理由: OS 非対応の向きを宣言すると端末外形とアプリ内容の向きが一致しないため (2026-09-02)
- Sample のスペーシングと余白: Slider は 4pt 刻みの固定値 → 指示により刻みを持たない連続値として操作できるようにする。理由: オーナーの Simulator 確認で値が飛び、操作がカクついて感じられたため (2026-09-02)
- list の外周下端: 先頭上端と行間だけに区切り線を描画 → 指示により最終行の Bottom にも全幅の区切り線を描画する。理由: リスト全体の上下境界を同じ線で明示するため (2026-09-02)
- list の区切り線色: ライブラリの semantic color → Sample brief の確定トークン `#D9D9DE` と同じ固定 RGBA をライブラリ内部既定値にする。理由: 公開 API を増やさず、Sample と後続 Android 実装の色比較を同じ実値で成立させるため (2026-09-02)
- 性能検証の基準機: iPhone 11 実機 → 接続可能な iPhone 15 実機で代替計測する。理由: オーナーが代替機での続行を承認したため。iPhone 15 は基準機より高速であり、この結果だけでは iPhone 11 相当の性能保証にならないリスクを受容する (2026-09-02)
- 重複 ID / 重複テンプレートキー: spec は debug assertion のみを定める → release は後勝ち + 警告ログで継続する。理由: オーナー判断。未登録テンプレートキーの release 方針 (空セル + 警告ログ) と揃えるため (2026-09-02)
- 値キーテンプレートの宣言形: core/ADR-0004 と dsl-samples の例は `Template(.message) { item in ... }` (型名を書かない推論形) → 実装ではこの形がコンパイルできず (result builder 文脈で `Item` / `Key` の両方が未確定になり型推論が失敗)、Sample と dsl-samples を `Template(TemplateDemoKind.message) { (item: TemplateDemoItem) in ... }` の明示形に揃えた。理由: 本 change の範囲では API の形を変えずに動く形へ寄せたため。**明示形はオーナーの本意ではなく暫定** — 推論形を成立させる API の見直しと `Template` の接頭辞 (`Ks`) の要否を phase-3 (Android ラッパー基盤) の前に対応する (2026-09-02)
- 差分更新: spec は内容変化の判定を `Equatable` 同値比較と定める → 同値配列でも親の更新が来たら可視セルを再構成する (オーナー判断 案 B)。理由: SwiftUI の親状態を捕捉するテンプレート (選択中 ID で色を変える等) を成立させ、Android と挙動を揃えるため。差分計算と snapshot 適用は同値配列では引き続き省略する (2026-09-02)
- tasks 3.2 の自己サイズ補正: 翻案元の `KsCellViewSupport` に相当する高さ補正 (固定行高契約のためのもの) は行わない → 本ライブラリは固定行高の契約を持たず、`UIHostingConfiguration` と `.estimated` の自己サイズだけで成立するため不要のまま。一方、翻案元の `CustomCellRowPlacement` に相当する中央配置はみ出し対策は実機確認で発現した (行の高さが content のサイズ変化に 1 レイアウトパス遅れる間、ホスト View の既定の中央配置で content が上方向へ 48.667pt はみ出す) ため、`KsRowContentPlacement` として翻案した。実効行高の概念は持ち込まず、基準は content の自然高だけで常に上端へ揃える。既知の帰結: content へ行の高さを提案しない (自己サイズが自己参照になるため) ので、grid で背の低いセルは行高いっぱいに広がらず自然高のまま上端に置かれる — `.frame(maxHeight: .infinity)` や `Spacer()` で行全体に背景を敷く書き方は効かない。証跡: evidence/height-change-after-ab-measurement.md (2026-09-03)
- 行の推定高さ: `.estimated(44)` の固定値 → 実測した行の高さ (直近 32 件の平均) を推定値に使う (`KsEstimatedHeight`)。テンプレートキー別の推定値は成立しない — `NSCollectionLayoutSize.estimated` は item / group の定義単位で index path ごとに変えられず、単一 section にキーが混在しうるため。中央値ではなく平均を採るのは、推定値が行位置の積み上げ (= コンテンツ全体の高さ) の見積もりに使われるため。grid では行の高さが「その行の列のうち最も高いセル」で決まるのに対し実測はセル単位でしか拾えず、行高が混在する grid では平均でもなお小さめに見積もる乖離が残る (固定 44 に対して誤差は約半分)。実測値は測ったときの行の幅と対で保持し、違う幅の実測が来た時点で前の幅の分を捨てる。捨てるのを幅が変わった瞬間ではなく次の実測が来るまで遅らせるのは、幅の変化で走る再レイアウトに既定値を読ませないため (捨てた直後の再レイアウトは実測を 1 件も持たず、推定が 44 へ戻ってしまう)。この遅延により、回転などの直後は新しい幅の実測が入るまで前の幅の平均が使われる。既知の帰結: 保持するのは直近 32 件だけの移動平均のため、大量件数のスクロール中に窓の中身が入れ替わると未計測分の見積もりが動き、コンテンツ全体の高さが揺れうる (長いスクロール中のインジケータ・オフセットの安定性は未測定)。推定値が layout へ反映される契機は section provider の再実行だけなので、幅が変わった後に新しい幅で測り直した平均が効くのは次に invalidateLayout が走るときになる。証跡: evidence/estimated-height-ab-measurement.md (2026-09-03)
- tasks 5.3 の `Template` builder: 「値キー / 型 / 単一クロージャの 3 形」→ 実装は値キーと単一クロージャの 2 形。理由: 型ベースの切り替えは proposal の Non-Goals で v1 の対象外のため (2026-09-02)
- [付随修正] 項目が空のときの初回表示: 空配列では初回の snapshot 適用自体が省略され、header / footer が表示されなかった。初回は section を載せるために必ず適用するよう修正した。理由: 空データでの先頭へのスクロールを成立させる過程で同じ経路に見つかった、同一能力内の局所修正のため (2026-09-02)
- 差分更新: 同値配列の更新では `id:` / `template:` / `Template` の登録集合の変更を反映しない — これらは表示中は不変とする利用者契約とする。理由: キーパスと登録集合は宣言箇所ごとに静的な指定が通常であり、表示中の差し替えを支えるコストに見合わないため (2026-09-02)
- 性能検証のメモリ計測: spec では「リスト全体の 1 往復スクロール」を基準機 (代替: iPhone 15 実機) で計測 → 指示により、全項目を通過する走査での再計測は Simulator で行う (hitch time ratio は iPhone 15 実機の既存計測を維持)。理由: 往復手順の是正を優先し、実機の再接続を待たずに証跡を更新するため。Simulator のメモリ値は実機の絶対値とは異なるが、往復間で増え続けないこと (定常化) の判定には使えるリスクを受容する (2026-09-02)
- 性能検証のメモリ判定: spec の THEN は「1 往復後のメモリ使用量を基準に、さらに 1 往復してもメモリが増え続けない」→ 判定を「増加が止まるまで往復を重ね、連続する 2 往復の増分がいずれも 1 往復後の値の 2% 以内になったら定常とみなす (上限 10 往復。止まらなければ未判定)」で行う。理由: 全 10,000 件を通過する走査では上限のあるキャッシュが数往復かけて埋まり、2〜3 往復目までは数 % の増加が残るため、1 往復の追加だけでは定常化を判定できない。許容差と上限は計測前に決め、証跡に記載している (2026-09-03)
