# 提案の段階の実測 (2026-10-06)

提案が前提にしている外部の部品の挙動を、提案を書く前に実物で確かめた記録 (lessons/spec-review.md [L-002])。測ったのは作業専用に新しく作ったシミュレータ / エミュレータで、終わってから削除した。リポジトリのファイルは書き換えていない (Android は Sample の写しをリポジトリの外に作ってビルドした)。画像と生の結果はリポジトリに残していない。

## 1. iOS の標準の灰色の値

色の表の出どころにした iOS の標準の灰色が、公表値どおりかを確かめた。

- 測り方: 色を外観ごとに解決した成分 (`UIColor.resolvedColor(with:)`) を出す小さな実行ファイルを iOS シミュレータ向けにビルドし、シミュレータの中で実行した。画面の画素を読んだ値ではない
- 環境: Xcode 27.0、iOS 17.5・18.6・26.0・27.0 のシミュレータ (iOS 16 のランタイムは無く、測っていない)
- 条件: 外観のライト / ダーク × コントラストの通常 / 「コントラストを上げる」

4 つの版で同じだった色:

| OS の色 | ライト | ライト (コントラストを上げる) | ダーク | ダーク (コントラストを上げる) |
|---|---|---|---|---|
| systemGray5 | `#E5E5EA` | `#D8D8DC` | `#2C2C2E` | `#363638` |
| systemGray4 | `#D1D1D6` | `#BCBCC0` | `#3A3A3C` | `#444446` |
| systemGray | `#8E8E93` | `#6C6C70` | `#8E8E93` | `#AEAEB2` |

版で違った色 (区切り線の不透明な色 opaqueSeparator):

| 版 | ライト | ダーク |
|---|---|---|
| iOS 17.5・18.6・26.0 | `#C6C6C8` | `#38383A` |
| iOS 27.0 | `#E7E7E8` | `#2A2A2C` |

分かったこと:

- 画像の既定の表示に使う 3 つの灰色 (読み込み中・失敗の下地・失敗の印) は、予定した値と一致し、版による差も無い
- 区切り線のダークの候補 `#38383A` は、iOS 26 までの OS の区切り線の不透明な値である。iOS 27 では OS の値が `#2A2A2C` に変わっている (新しい SDK でビルドした場合)。ライブラリは固定値で持つので OS の版には左右されないが、「iOS の今の区切り線と同じ色」ではない
- 「コントラストを上げる」では 3 つの灰色とも別の値になる。固定値で持つと、この切り替えには追随しない (core/ADR-0036 の負の帰結のとおり)

## 2. Android の波紋が、渡した色の不透明度をどう扱うか

「渡した色の不透明度は捨てられ、波紋の標準の濃さに置き換わる」という実装の読み取り (探索メモ) と、過去の記録「半透明の色を渡すと Android では見えなくなる」が食い違っていたので、画素で確かめた。

- 環境: Android 16 (API 36) のエミュレータ (1080×2400)、表示モードはライト、Compose BOM 2026.06.01 (material3 1.4.0)。API 29・30 のシステムイメージは無く、測っていない
- 画面: Sample のデモ画面「リスト」。下地は白、渡す色はアクセント (ライトの値)
- ケース A: 不透明なアクセント色を渡す (今の Sample のまま)
- ケース B: アクセント色の 15% を渡す (iOS の Sample と同じ値。Sample の写しの該当行だけを書き換えてビルド)
- 操作: 3 行目を 5 秒押し続け、押し始めから 0.3・1.0・2.5・4.0 秒で撮った。A・B とも 2 回ずつ
- 測り方: 押している行の、文字や線が無い下地の画素を、押す前の同じ位置の画素と比べ、重なっている色の不透明度を逆算した

押し始めから 1.0・2.5・4.0 秒 (波紋が広がりきった後)。A の 2 回・B の 2 回とも同じ値だった:

| 測った位置 | 重なっている色の不透明度 (赤 / 緑の成分から逆算) |
|---|---|
| 行の中央 (押した点・左右・上下) | 約 8.7% / 約 8.3% |
| 行の左右の端の近く | 約 6.7〜7.2% / 約 6.9% |
| 隣の行 (対照) | 0% |

- 押している行の全画素 (約 19 万 6 千個) が、1.0・2.5・4.0 秒のどの時点でも A と B で完全に一致した
- 押した直後 (0.3 秒) の中央は、A・B とも約 10%。端は波紋の広がり具合で回ごとにばらつき、A と B の差とは言えない
- 長押しで見た目が変わるのは押した行だけで、離して 2 秒後は押す前と一致した

分かったこと:

- この条件では、アクセント色の 15% を渡しても、不透明なアクセント色を渡したときと同じ濃さで見える。「半透明の色を渡すと見えなくなる」は再現しなかった
- 渡した色の不透明度は見え方に効かない。濃さは、押した直後の中央で約 10%、落ち着くと中央で約 8〜9%、端で約 7%
- 測っていない条件: API 29・30、ダーク、15% 以外の不透明度、実機、押してすぐ離す短いタップ。不透明度を置き換える処理は Compose のライブラリの側にあり (探索メモの調査)、OS の版には左右されない見込みだが、API 29・30 の濃さの値は実測していない

## 3. iOS で、表示モードで変わる色を SwiftUI の色として使ったときの追随

新しい実測はしていない。同じ仕組み (ライト用とダーク用の値を持つ `UIColor` を SwiftUI の色に包む) を Sample の配色 (`samples/ios/KsCollectionViewSamples/SampleTheme.swift` の `adaptive`) が既に使っており、一覧のセルの中の色が外観の切り替えにその場で追随することは `sample-dark-mode-toggle` のオーナーの目視で確かめられている。ライブラリの画像の既定の表示が同じように追随することは、実装のテストと視覚照合で確かめる (tasks 1.5・4.1)。

## 4. iOS で、外観で値の変わる色を SwiftUI の色から UIKit の色へ変換したときの保たれ方

相方の提案レビューの指摘 (利用者が指定した外観で値の変わる色の扱いが曖昧) を受けて、約束を書く前に確かめた。ライブラリの色の設定 (区切り線の色・タップしたときの色・読み込み中の表示の色) は、SwiftUI の色を受け取って UIKit の色へ変換している。

- 測り方: ライト用とダーク用の値を持つ UIKit の色を SwiftUI の色に包み、それを UIKit の色へ変換し直してから、ライト / ダークの外観で解決した値を出す小さな実行ファイルを、シミュレータの中で実行した (アプリの画面の中ではなく、単体の実行ファイル)
- 環境: iOS 17.5・18.6・26.0・27.0 のシミュレータ (作業専用に作り、終わってから削除した)

| 版 | ライトの外観で解決 | ダークの外観で解決 |
|---|---|---|
| iOS 17.5 | ライト用の値 | **ライト用の値のまま** (変わり方が保たれない) |
| iOS 18.6・26.0・27.0 | ライト用の値 | ダーク用の値 (保たれる) |

- iOS 17.5 では、変換する時点の外観をダークにしておいても、結果はライト用の値に固定された。OS の色 (SwiftUI の標準の文字色) を変換した場合も同じだった
- 不透明度を掛けた色も同じ結果だった (色みの変わり方だけが失われ、不透明度は保たれる)
- 対照として、UIKit の色のまま (SwiftUI を通さない) なら、どの版でも外観ごとの値に解決された。ライブラリの既定の色は UIKit の色として持つので、この影響を受けない

分かったこと:

- iOS 17.5 では、外観で値の変わる色を色の設定に渡すと、ライト用の値に固定される見込みである (単体の実行ファイルでの結果で、アプリの画面の中では確かめていない。iOS 16 はランタイムが無く測っていない)
- これは利用者が指定した色の今の挙動で、この変更では変えない。デルタスペックは「指定した色にライブラリは手を加えない」とだけ約束し、外観で値の変わる色の追随は約束しない
- Sample は外観で値の変わる色 (配色のアクセントなど) を色の設定に渡している。iOS 17 以前のダークでは、Sample の区切り線「アクセント」・タップの色・読み込み中の色がライトの配色の値で出る可能性がある。視覚照合は iOS 18 以降で行う (tasks 4.1)
