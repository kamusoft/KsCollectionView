title: 配列を内部で固定件数の塊 (内部セクション) に分けて配置し、レイアウトの再解決の費用を配列の件数から切り離す
status: proposed
date: 2026-09-16

## Context

iOS エンジンは 1 つの配列を diffable の単一セクション (`KsSectionID.main`) に載せ、compositional layout の `.estimated` 高さでセルを自己サイズにしている (ios/ADR-0001、ios/ADR-0003)。compositional layout は推定高さと違う高さに測られたセルが現れるたびに、そのセクションの配置を解き直す (`_UICollectionLayoutSectionEstimatedSolver`)。解き直しの費用はセクションの件数に比例するため、10,000 件を 1 セクションに載せた Sample「大量件数」(2 列、固定高と 7 件ごとの長文の混在) は、基準機 iPhone 11 での手動フリックで体感不合格になった (主スレッドの 55%)。

推定高さを直近の実測の最頻値にして多数派のセルが解き直しを起こさないようにする対策 (performance-criteria-review の Decision 1) は、不一致率を 0.032 まで下げ solver の占有率を 35.9% に減らしたが、少数派の行が可視になるたびに 10,000 件を解き直す費用が残り、10,000 件の体感は不合格のまま、占有率は 2,000 件の 4.1 倍と件数に比例した。画像グリッド (全セル同じ高さ) では solver が一度も走らず体感合格。

phase-4 (セクション / グループ化) の利用者向けの論理セクションはまだ無い。区切り線はセルのサブビューで描き、`NSCollectionLayoutDecorationItem` は将来のセクション装飾のために使っていない。

前提: compositional layout の estimated 高さの解き直しがセクション単位であること (profile からの推論。試作の実機計測で確かめる)。利用者の宣言に現れない内部構造をライブラリが自由に持てること (core/ADR-0006 の単一コンポーネント)。

## Decision

- 1 つの配列を内部で**固定件数の塊 (内部セクション)** に分けて diffable のセクションに載せ、塊の境界に列数に満たない行を作らない。
- 塊の境界は見た目に現れない。塊の分け方は `internal` に閉じ、公開 API・DSL・Android には現れない。
- 表示位置の維持とスクロール命令は項目 ID から indexPath を解決する既存の仕組みに任せ、塊の境界に依存する状態を持たない。
- 推定高さは 1 コレクション 1 値のまま全塊に渡す (塊ごとの推定値は再訪案)。

塊の件数は基準 500 件を列数の候補の最小公倍数の倍数へ切り上げた値とする。候補は固定列数と向き別列数では宣言された列数すべて、列数が表示領域の幅で決まる adaptive では直近に解決した列数で、組み直すのは列数の変化または layout 値の変更で現在の塊の件数が新しい列数で割り切れなくなったときだけ。最小公倍数がオーバーフローするか基準の 4 倍を超える向き別列数は、現在の列数の倍数に縮退して回転で組み直す。

境界を見た目に出さないとは: 行間は塊の境界でも他と同じ、内側余白は配列全体の上下だけ、ルートのヘッダー / フッターは先頭と末尾の塊にだけ付け、区切り線の先頭の上線は配列全体の先頭にだけ出す。空配列でも 1 塊を載せてヘッダー / フッターを表示する。項目だけの追加・削除・並べ替えでの表示位置の動きは塊が無い場合と同じとし、位置を項目に固定する契約は足さない。

## Alternatives Considered

- **推定高さの最頻値化だけで済ませる**: 却下。実機計測で少数派の行の解き直しが残り、費用が件数に比例したまま (上記)。最頻値化自体は残す (解き直しの回数を減らす効果は独立にある)。
- **`.absolute` 高さの併用 (テンプレート単位で高さを宣言し、自己サイズを止める)**: 今は採らない。`.estimated` は item 定義単位で index path ごとに変えられず、DSL の語彙の拡張 (レイアウト指定は layout 値 1 つ、core/ADR-0006) が要る。塊分割が効かなかった場合の再訪案として、改訂案のコストと並べて提示する。
- **FlowLayout / 完全自前レイアウト (高さを自前でキャッシュ)**: 今は採らない。ios/ADR-0003 (全レイアウトを自前 compositional セクションで統一) の改訂が要り、コストが特大。同じく再訪案。
- **fixture の件数を減らす (2,000 件)**: 却下。問題を隠すだけで、利用者の大量件数では再現する (cross/ADR-0006 の帰結として件数は 10,000 のまま)。
- **塊の所属を項目に固定して件数を可変にする**: 却下。挿入・削除で塊の件数が列数の倍数でなくなり、境界に不完全な行ができる。
- **常に現在の列数だけで塊を組み、列数が変わるたびに組み直す**: 却下。向き別列数で回転するたびに全件の差分適用が起き、アンカー復元と重なる。最小公倍数で組めば回転で組み直さずに済む。
- **`NSCollectionLayoutDecorationItem` で塊の境界の見た目を埋める**: 却下。将来のセクション装飾と座を取り合う (concepts の禁止事項)。

## Consequences

- 正: 1 回の解き直しの費用の上限が塊の件数で決まり、配列全体の件数に比例しない。
- 正: 利用者の語彙・公開 API・Android の実装は変わらない。
- 正: 表示位置の維持・スクロール命令・prefetch・選択は項目 ID 経由の既存の仕組みのまま動く。
- 負: phase-4 の論理セクションは「論理セクション × 内部の塊」の 2 段を前提に設計する。sticky ヘッダは内部の塊の境界で止まらず論理セクション全体を覆うこと、列数に合わない分割で不完全な行を作らないこと、先頭挿入で塊の所属が変わるときの差分更新と位置維持、の 3 条件を満たす必要がある。
- 負: 塊の境界の見た目 (行間・余白・区切り線・ヘッダー / フッター) をライブラリが自前で保守する。
- 負: adaptive で列数が変わると塊を組み直す差分適用が発生する (固定列数・向き別列数では発生しない)。
- 負: 先頭への挿入・削除で、塊の境界の項目が隣の塊へ移る差分が毎回発生する (件数 / 塊の件数 の項目数)。
- 負: 塊ごとの推定値を使わないため、少数派の行の解き直しは塊の中で残る。

## Revisit When

- 試作の実機計測で、解き直しの費用が塊の件数ではなく全セクションに比例すると分かったとき (前提が崩れる。`.absolute` 併用または自前レイアウトの改訂案へ)
- phase-4 で論理セクションを入れるとき (2 段構造の責務を確定する)
- UIKit が estimated 高さの解き直しの費用を件数に依らない形にしたとき
