## Context

iOS エンジンは 1 つの配列を diffable の単一セクションに載せ、compositional layout の `.estimated` 高さでセルを自己サイズにしている (ios/ADR-0001、ios/ADR-0003)。compositional layout は、渡した推定高さと違う高さに測られたセルが現れるたびに、そのセクションの配置を解き直す (`_UICollectionLayoutSectionEstimatedSolver`)。10,000 件を 1 セクションに載せた Sample「大量件数」(2 列、固定高と 7 件ごとの長文の混在) は、基準機 iPhone 11 の手動フリックで体感不合格になり、解き直しが主スレッドの 55% を占めた。

推定高さを直近の実測の最頻値にして多数派のセルが解き直しを起こさないようにする対策 (change `performance-criteria-review` で先に実装) は、推定と実測の不一致率を 0.032 まで下げ、解き直しの占有率を 35.9% に減らした。それでも少数派の行が可視になるたびに 10,000 件を解き直す費用が残り、10,000 件の体感は不合格のまま、占有率は 2,000 件の 4.1 倍と件数に比例した。全セルが同じ高さの Sample「画像グリッド」では解き直しが一度も走らず、体感は合格だった。

利用者向けの論理セクションはまだ無い (ロードマップ v1-foundation の後続の機能「セクション / グループ化」で導入する)。区切り線はセルのサブビューで描き、`NSCollectionLayoutDecorationItem` は将来のセクション装飾のために使っていない。

前提: 解き直しの費用はセクション単位で、そのセクションの件数に比例する。これは profile からの推論で一次資料は無く、Apple Forums には件数が増えると全セクションが再計算されるという報告もある。そのため本決定は、配列を塊に分けるだけの試作を基準機で計測し、件数比例が消えることを確かめてから境界の処理を実装する手順と対で採った。もう 1 つの前提は、利用者の宣言に現れない内部構造をライブラリが自由に持てること (core/ADR-0006 の単一コンポーネント)。

## Decision

1 つの配列を内部で**固定件数の塊 (内部セクション)** に分けて diffable のセクションに載せる。塊の境界に列数に満たない行を作らず、境界は見た目に現れない。塊の分け方は `internal` に閉じ、公開 API・DSL・Android には現れない。表示位置の維持とスクロール命令は項目 ID から indexPath を解決する既存の仕組みに任せ、塊の境界に依存する状態を持たない。推定高さは 1 コレクション 1 値のまま全塊に渡す。

塊の件数は、基準 500 件を列数の候補の最小公倍数の倍数へ切り上げた値とする。候補は、固定列数と向き別列数では宣言された列数すべて、列数が表示領域の幅で決まる adaptive では直近に解決した列数である。塊を組み直すのは、列数の変化または layout 値の変更で、現在の塊の件数が新しい列数で割り切れなくなったときだけとする。最小公倍数がオーバーフローするか基準の 4 倍 (2,000) を超える向き別列数は、現在の列数の倍数に縮退し、回転で組み直す。

境界を見た目に出さないとは、次をいう。行間は塊の境界でも他と同じにし、内側余白は配列全体の上下だけに付ける。ルートのヘッダー / フッターは先頭と末尾の塊にだけ付け、区切り線の先頭の上線は配列全体の先頭にだけ出す。空配列でも 1 塊を載せてヘッダー / フッターを表示する。項目の追加・削除・並べ替えでの表示位置の動きは塊が無い場合と同じとし、位置を項目に固定する契約は足さない。

## Alternatives Considered

### 解き直しの費用への対策

- **推定高さの最頻値化だけで済ませる**: 却下。少数派の行の解き直しが残り、費用が件数に比例したまま (Context)。最頻値化自体は解き直しの回数を減らす効果が独立にあるので残す。
- **`.absolute` 高さの併用 (テンプレート単位で高さを宣言し、自己サイズを止める)**: 今は採らない。`.estimated` は item 定義単位で index path ごとに変えられず、DSL の語彙の拡張 (レイアウト指定は layout 値 1 つ、core/ADR-0006) が要る。塊分割が効かなくなった場合の再訪案とする。
- **FlowLayout / 完全自前レイアウト (高さを自前でキャッシュ)**: 今は採らない。ios/ADR-0003 (全レイアウトを自前 compositional セクションで統一) の改訂が要り、コストが特大。同じく再訪案。
- **fixture の件数を減らす (2,000 件)**: 却下。問題を隠すだけで、利用者の大量件数では再現する (cross/ADR-0006 で件数は 10,000 のまま)。
- **塊ごとに異なる推定高さを渡す**: 今は採らない。sectionProvider の仕組み上は可能だが、最頻値化で不一致率が 0.032 まで下がっており、必要性が示されていない。

### 塊の組み方と境界の扱い

- **塊の所属を項目に固定して件数を可変にする**: 却下。挿入・削除で塊の件数が列数の倍数でなくなり、境界に不完全な行ができる。
- **常に現在の列数だけで塊を組み、列数が変わるたびに組み直す**: 却下。向き別列数で回転するたびに全件の差分適用が起き、位置の復元と重なる。最小公倍数で組めば回転で組み直さずに済む。
- **塊を 200 件にする**: 採らない。再解決の上限はさらに下がるが、塊の数が 2.5 倍になり境界の処理が増える。500 件の試作で件数比例が消えたため、下げる理由が無い。
- **`NSCollectionLayoutDecorationItem` で塊の境界の見た目を埋める**: 却下。将来のセクション装飾と座を取り合う。
- **全塊にヘッダー / フッターを付け、先頭と末尾以外を空にする**: 却下。空の supplementary view が塊の数だけ生成され、ホスティングの費用が無駄になる。
- **塊の組み直しで `reloadData` する**: 却下。位置が飛び、可視セルが作り直される。

## Consequences

- 正: 1 回の解き直しの費用の上限が塊の件数で決まり、配列全体の件数に比例しない。
- 正: 利用者の語彙・公開 API・Android の実装は変わらない。
- 正: 表示位置の維持・スクロール命令・prefetch・選択は、項目 ID を経由する既存の仕組みのまま動く。
- 負: セクション / グループ化機能の論理セクションは「論理セクション × 内部の塊」の 2 段を前提に設計する。sticky ヘッダが塊の境界で止まらず論理セクション全体を覆うこと、列数に合わない分割で不完全な行を作らないこと、先頭挿入で塊の所属が変わるときの差分更新と位置維持、の 3 条件を満たす必要がある。
- 負: 塊の境界の見た目 (行間・余白・区切り線・ヘッダー / フッター) をライブラリが自前で保守する。
- 負: `indexPath.item` は塊ごとに 0 から始まり、配列全体の順番を表さない。全体の順番が要る箇所 (区切り線の先頭判定・計測の通過件数・テスト) は塊の位置を含めて数える必要がある。
- 負: adaptive で列数が変わると、塊を組み直す差分適用が発生する。向き別列数でも、最小公倍数が上限を超えて縮退する組み合わせでは回転で発生する。
- 負: 列数は配置を解いて初めて決まるため、adaptive の組み直しは列数の変化より遅れる。その間は塊の境界に列数に満たない行が出うる。
- 負: 先頭への挿入・削除で、塊の境界の項目が隣の塊へ移る差分が毎回発生する (件数 / 塊の件数 の項目数)。
- 負: 塊ごとの推定値を使わないため、少数派の行の解き直しは塊の中で残る。

## Revisit When

- 件数を変えた基準機の計測で、解き直しの費用が塊の件数ではなく配列全体の件数に比例していると分かったとき (前提が崩れる。`.absolute` 併用または自前レイアウトの改訂案へ)
- セクション / グループ化機能で利用者の論理セクションを入れるとき (2 段構造の責務を確定する)
- UIKit が推定高さの解き直しの費用を件数に依らない形にしたとき
