## Context

iOS エンジンはセルを `UIHostingConfiguration` でホスティングする (ios/ADR-0001)。セルが画面外に出て再利用されるとき、セル内の SwiftUI ビューが持つ内部 state (`@State` — 展開状態・入力途中など) をどう扱うかを決める必要があった。SwiftUI には再利用をまたいで `@State` を退避・復元する公式の口がない。先行実装 KsSettingsViewUI は再利用のたびにホスティング階層を作り直す方針で、そのコストは実測で許容と確認されている。

## Decision

セル再利用時はホスティングを作り直し、セル内の SwiftUI 内部 state は保持されない仕様とする。スクロールで画面外に出ても残したい状態は、利用者がデータモデル側に持たせて復元する (コレクションの状態モデル core/ADR-0003 — プレーンな配列 + 安定 ID — の帰結)。この挙動は利用者向けドキュメントに明記する。

## Alternatives Considered

- **再利用をまたいで内部 state を保つ独自機構を設ける**: 却下。公式 API がなく独自機構になり、再利用バグの温床。状態の正がセルとデータに分裂する余地が生まれ、core/ADR-0003 の思想 (状態の正はデータ側) と衝突する

## Consequences

- 正: 実装が単純で、先行実装で実証済みのコスト特性を継承できる
- 正: 状態の正がデータモデルに一本化され、挙動が予測しやすい
- 負: セル内だけの一時状態 (展開・入力途中など) はスクロールで失われる。残したい場合は利用者がデータに反映する設計上の負担が生じ、ドキュメントでの明示が必須
