## Context

ios/ADR-0002 は、セルが再利用されるときにホスティングを作り直し、セル内の SwiftUI の内部 state (`@State` など) を保持しないと決めた。作り直しの費用は、先行実装 KsSettingsViewUI での実測で許容と確認されていた。

大量件数の一覧では、この作り直しが主スレッドの費用として現れる。並べ替え機能の基準機 (iPhone 11) の体感ゲートで hitch の数値が悪かった原因を切り分けたところ、操作中の主スレッドの標本のうち hosting view の解放が 10.5% を占めていた。Simulator の計数 (10,000 件、下向きに 450 フレーム) では、セルの生成が 9 件なのに対し、ホスティングの生成と解放は表示に入る項目ごとに 1 回ずつ (399 回と 390 回) 起きていた。体感ゲートそのものはオーナーの体感で合格している (cross/ADR-0006)。

再利用のときに中身を外さず、同じ型の `UIHostingConfiguration` を当て直すと、ホスティングは使い回される (同じ計数で生成が 9 回・解放が 0 回)。このとき state を誰が戻すかは OS の版で変わる。

- iOS 18 のリリースノートには、`UIHostingConfiguration` のルートの state をセルが表示される前に戻すよう直したとある。iOS 18.6・26.0・27.0 の Simulator では、ライブラリが何もしなくても、再利用が起きる距離を往復したテンプレートの state は初期値へ戻った
- iOS 17.5 の Simulator では戻らなかった。state はセルに付いて回り、state を変えたセルを再利用した別の項目すべてに出た
- iOS 16 のランタイムは手元に無い。対応 OS の下限は iOS 16 である

ライブラリ自身が state を戻す形 (再利用のたびに変わる識別の値を中身に付ける) も試した。OS が戻す版では二重の戻しになり、iOS 18.6 の Simulator で効果が作り直す場合と区別できなかった (主スレッドの CPU 時間の中央値で 2.6〜6.4% の減。識別の値を付けない形は 8.6〜27.3% の減)。OS が戻さない iOS 17.5 では state は正しく戻ったが、表示から外れた項目の `onAppear` と `.task` が余分に 1 回動いた。

前提:

- セルのホスティングは `UIHostingConfiguration` で続ける (ios/ADR-0001)
- 同じ型の構成を当て直したとき、UIKit は中身のビューを作り直さずに使い回す
- iOS 18 以降は、再利用されたセルが表示される前に、OS がルートの state を初期値へ戻す

## Decision

ios/ADR-0002 の決定のうち「セル再利用時はホスティングを作り直す」を、iOS 18 以降について本決定で置き換える。iOS 18 より前の版では ios/ADR-0002 のまま作り直す。「セル内の SwiftUI の内部 state は再利用をまたいで保持されず、残したい状態は利用者がデータモデル側に持たせる」は、どの版でも維持する。

iOS 18 以降では、セルが再利用されるとき、中身を載せるホスティングは捨てずに使い回す。利用者のテンプレートが持つ内部 state を初期値へ戻すことは OS に任せ、ライブラリは戻すための処理を持たない。表示中のセルの作り直し (ios/ADR-0006・0008) は再利用ではないので、state を残す。

理由: 効果が出るのは、ライブラリが戻す処理を持たない形だけで、その形で契約を保てるのは OS が state を戻す版だけである。OS が戻さない版は今の作りのままにすれば、利用者から見える動きがどの版でも変わらない。

含まないもの: グループの見出しとルートのヘッダー / フッターのホスティング (どの版でも再利用のたびに作り直すまま)。

## Alternatives Considered

- **どの版でも、再利用のたびにホスティングを作り直す (ios/ADR-0002 のまま)**: 却下。体感ゲートは合格しており正当な選択だが、ホスティングの解放だけで主スレッドの 1 割を占めており、なくせば利用者が重いセルを書いたときや遅い端末での余裕になる (オーナー判断: 軽いにこしたことはない)。
- **どの版でもホスティングを使い回し、ライブラリが state を戻す**: 却下。経路は 1 本で済むが、iOS 18.6 の Simulator で効果が作り直す場合と区別できなかった。識別の値を付ける位置を変えても同じだった。
- **どの版でもホスティングを使い回し、state は OS に任せる**: 却下。iOS 17.5 で、state を変えたセルを再利用した別の項目すべてに state が出た。対応 OS の下限が iOS 16 である間は、利用者に見える不具合になる。
- **iOS 18 より前の版でもホスティングを使い回し、その版だけライブラリが state を戻す**: 却下。iOS 17.5 で state は戻ったが、表示から外れた項目の `onAppear` と `.task` が余分に 1 回動き、利用者から見える動きが今と変わる。その版での効果も小さい。

## Consequences

- 正: iOS 18 以降では、表示に入る項目ごとのホスティングの生成と解放がなくなる
- 正: 利用者から見える動きがどの版でも変わらないので、利用者のコードと、利用者向けドキュメントに書く内容を変えずに済む
- 正: iOS 18 より前の版は今の経路のままなので、確かめられない版 (iOS 16) でも動きが変わらない
- 負: iOS 18 より前の版では効果が無い
- 負: 再利用のときの扱いが OS の版で 2 通りになり、両方の版でテストを流す必要がある
- 負: iOS 18 以降は state が戻ることを OS の挙動に頼る。OS の版が変わるたびに、状態が初期値へ戻るテストで確かめ続ける必要がある
- 負: iOS 18 以降では、前の項目の中身が残ったホスティングへ次の項目を当てるので、前の見た目・高さの計測・読み上げの操作を次の項目へ持ち越さないことを、ライブラリが個別に保証する必要がある (作り直しでは何もしなくても持ち越さなかった)
- 負: セルとグループの見出しで、再利用のときのホスティングの扱いが違う形になる

## Revisit When

- 新しい OS の版で、状態が初期値へ戻るテストが失敗したとき (OS が戻さなくなった)
- 対応 OS の下限を iOS 18 以上へ上げるとき (版の分岐を外せる)
