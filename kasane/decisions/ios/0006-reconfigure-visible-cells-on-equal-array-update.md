## Context

差分更新のデルタスペックは、内容変化の判定を `Equatable` の同値比較と定めていた。この定義では、配列が前回と同値なら何もしないのが自然な実装になる。しかし SwiftUI では「選択中 ID を親の状態に持ち、テンプレートの中でその ID と比較して色を変える」のような、配列の外にある親の状態をテンプレートが捕捉する書き方が普通にあり、その状態だけが変わったときも表示を更新する必要がある。Android (Compose) では親の状態変化で自然に再コンポーズされるため、両プラットフォームの挙動を揃える観点でも同値配列の扱いを決める必要があった。

同時に、`id:` / `template:` のキーパス指定と `Template` の登録集合を表示中に差し替えられるかも決める必要があった。

## Decision

- 利用者の配列が前回と同値でも、親 View の更新がライブラリに届いたら**可視セルの内容を再構成する** (`reconfigureItems` 相当)。差分計算と snapshot 適用は同値配列では省略する (挿入・削除・移動が無いことは分かっているため)。
- `id:` / `template:` のキーパス指定と `Template` の登録集合は**表示中は不変**とする利用者契約とし、同値配列の更新ではこれらの変更を反映しない。

## Alternatives Considered

- **同値配列では何もしない (スペックの定義どおり)**: 却下。親の状態を捕捉するテンプレート (選択中 ID で色を変える等) が成立せず、Android との挙動差が生じる。
- **キーパス指定と登録集合の表示中差し替えを支える**: 却下。キーパスと登録集合は宣言箇所ごとに静的な指定が通常であり、表示中の差し替えを検知・反映するコストに見合わない。

## Consequences

- 正: 親の状態を捕捉するテンプレートが、配列を作り直さなくても表示に反映される (両プラットフォームで同じ書き方が成立する)。
- 正: 同値配列では差分計算と snapshot 適用を省略するため、可視セルの再構成だけのコストで済む。
- 負: この決定は「親 View の更新がライブラリに届く」ことを前提にしている。テンプレートのクロージャの中でしか読まれない親の `@State` は SwiftUI の依存グラフに載らず、その変化では親 View の body が再評価されないため更新が届かない (実装結果: 2026-09-03 のライブ調整で観測。利用者側の回避策は、その状態を body 側でも読むこと)。前提の成立条件と根本的な解き方は別の変更 (template-parent-state-observation) で扱う。
- 負: 可視セルの再構成では `UIHostingConfiguration` が差し替わるため、中身の変化は SwiftUI のアニメーションとして扱われず瞬時に切り替わる (テンプレート内部の状態変化はアニメーションする)。
- 負: 表示中にキーパスや登録集合を差し替えても反映されないことを、利用者向けドキュメントに明記する必要がある。
