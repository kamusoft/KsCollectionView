## Context

ページングの公開契約では、末尾に近づいたときに次ページ要求のコールバックを呼ぶのはライブラリの責務である (core/ADR-0005)。何をもって「末尾に近い」とするかは決まっていなかった。

旧 AiForms.CollectionView の `LoadMoreMargin` は「表示中のいちばん後ろの項目より後の残りが N 件以下」という件数の意味で、Android 版は件数のまま、iOS 版は件数を距離に換算して判定していた。既定値は 0 だった。項目が現れたことを契機にする方式は、Compose が画面外の項目を前もって組み立てるため成り立たない。一方、画面に実際に出ている項目の範囲は両プラットフォームで取れる (画像の先読みが既に使っている)。Android の Lazy 系は、まだ並べていない項目の高さを知らない。layout 値は向きで列数が変わるグリッドを一級に扱う (core/ADR-0006)。スクロールしたときだけ判定すると、1 ページが画面に満たない一覧はスクロールできないまま止まる。項目が空で状態が待機のときは残りが 0 件なので、このまま判定すると初回の読み込みもライブラリが頼むことになる。

前提: ページの件数と次のページの取得にかかる時間は、利用者 (VM・アプリの API) だけが知っていて、ライブラリは知らない。

## Decision

- 「末尾に近い」は、画面に出ているいちばん後ろの項目より後に残っている項目の数で測る。数えるのは項目だけで、グループの見出し・ルートのヘッダー / フッターは数えない。画面に実際に出ている項目で数え、画面外で前もって組み立てられた項目は数えない
- 残りの項目の数が「しきい値 × 今画面に出ている項目の数」以下になったら、次ページ要求のコールバックを呼ぶ
- しきい値は「何画面分手前で頼むか」を表す画面数で、利用者が指定できる公開の設定とする。既定は 1 画面分
- しきい値 0 は、最後の項目が画面に入ったら頼む (底に着いてから読み込む) ことを表す
- 判定し直すのは、スクロール・配列の差し替え・状態の変化・一覧の大きさの変化のとき
- 項目が空で状態が待機なら頼む。初回の読み込みも次ページ要求のコールバックで始まり、VM は最初の読み込みを自分で始めなくてよい

## Alternatives Considered

- **末尾までの残りの距離で測る**: 却下。Android の Lazy 系はまだ並べていない項目の高さを知らないため、末尾が近づくまで距離が見積もりになり、両プラットフォームで同じ意味にならない。
- **末尾が見えたら頼む (しきい値を持たない)**: 却下。毎ページ、末尾で読み込み中の表示を待たせる。
- **既定を固定の件数 (例: 5 件) にする**: 却下。列数・向き・項目の大きさで発火の位置が大きく変わる (4 列なら末尾の 1 行強手前、半画面のカードなら 2.5 画面手前)。
- **既定を 0 件 (旧 AiForms の既定) にする**: 却下。毎ページ読み込みを待たせる。
- **既定をページの件数ぶん手前 (Paging 3 の既定) にする**: 却下。ページの件数をライブラリは知らない。
- **しきい値を公開しない**: 却下。取得の遅い API のアプリで、読み込み中の表示が見えるのを手当てできない。
- **しきい値を件数で指定させる**: 却下。旧 `LoadMoreMargin` の値をそのまま移せるが、指定した時点で列数・項目の大きさによる発火の位置のずれが戻る。
- **項目が空のときは頼まず、初回の読み込みは VM が始める**: 却下。二重の読み込みや空のページでの頼み続けは起きないが、VM に「画面を開いたら読み込む」を書かせる必要があり、書き忘れると空のままになる。
- **項目が空のときは取り直しとして頼む**: 却下。初回の読み込みが取り直しの意味になり全体の読み込み表示とつながるが、二重の読み込みと空のページでの頼み続けは空でも頼む案と同じで、取り直しの処理を渡していない一覧のための規則が別に要る。

## Consequences

- 正: 既定でも、しきい値を変えても、発火は列数・向き・項目の大きさによらず末尾の同じ画面数手前になる。
- 正: 画面外の項目を前もって組み立てても発火の判定は変わらず、両プラットフォームで同じ意味で測れる。
- 正: 取得の遅い API のアプリは、しきい値を増やして読み込み中の表示を見せにくくできる。
- 正: VM は最初の読み込みを書かなくてよく、次ページ要求の処理だけで一覧が始まる。1 ページが画面に満たないときも、配列の差し替えで判定し直して続きを頼み、画面が埋まる。
- 負: 発火する残りの件数は画面の大きさと項目の大きさで変わり、件数で予測・検証しにくい。
- 負: 旧 `LoadMoreMargin` の値はそのまま移せず、画面数に読み替える必要がある。
- 負: 両プラットフォームにしきい値の公開の設定が 1 つ増え、利用者向けドキュメント (en/ja) とテストがそのぶん増える。単位を後から変えると利用者のコードを壊す。
- 負: VM が自分でも最初の読み込みを始めると、状態の書き換えが遅れた場合に二重に読み込む。
- 負: 続きありのまま空のページが返ると、終端になるまで頼み続ける。項目が 0 件の一覧は、VM が終端にしたときにだけ空の表示になる。
