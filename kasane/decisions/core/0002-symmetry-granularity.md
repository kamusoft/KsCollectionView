## Context

core/ADR-0001 は「同じ書き味の対称性は公開 DSL の層で担保する」と決めたが、DSL 層のどこまでを揃えるかは未定義だった。本ライブラリの主読者は KMP アプリ量産時に「片方のプラットフォームで書いた画面をもう片方に書き写す人」である (cross/ADR-0001)。

## Decision

対称性の粒度を次のとおり定める:

- **揃えるもの**: コンポーネント名・パラメータ名・宣言構造 (何を・どんな名前で・どんな順で宣言するか)。両プラットフォームで1対1対応させる
- **各プラットフォームの流儀に残すもの**: modifier 記法、状態保持の仕組み (`@State` / `remember` 等)、非同期処理

揃えるのは宣言の「頭の中のモデル」であり、記法まで独自 DSL 化しない。

## Alternatives Considered

- **記法まで完全対称の独自 DSL**: 却下。SwiftUI / Compose の標準機能 (modifier・状態管理) との接続を遮り、独自記法の学習コストを課し、独自層2つ分の実装保守コストが跳ねる
- **機能セットだけ揃え API は独立設計**: 却下。書き写し時に機能の探し直しが発生し、KMP 量産時の UI 記述コスト削減という主目的に反する

## Consequences

- 正: 片方で書いた画面宣言を、もう片方へ機械的に書き写せる
- 正: modifier・状態管理・非同期処理はプラットフォーム標準のまま使えるため、ネイティブ開発者に違和感がなく、標準の進化を自動で享受する
- 負: 命名・宣言構造の設計時に常に両プラットフォームの制約を同時に満たす必要があり、片方だけなら自然な API を諦める場面が生じる
