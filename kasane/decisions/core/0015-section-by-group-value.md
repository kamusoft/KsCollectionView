## Context

グループ化機能 (ロードマップ v1-foundation) で、利用者がグループをどう宣言するかを決める。KsCollectionView は利用者のプレーンな配列と安定 ID を受け取り、差分計算とアニメーションはライブラリが担う (core/ADR-0003)。並べ替えはデータ層で行い、ライブラリは差分の移動アニメーションを出すだけで、並べ替えの DSL は持たない。旧 AiForms.CollectionView はグループのコレクションを渡す形で、語彙は `IsGroupingEnabled` / `GroupHeaderTemplate` / `IsGroupHeaderSticky` だった (core/ADR-0009 で議論素材として申し送り)。

API 設計の判断軸として、項目のモデルに手を入れないこと、配列を 1 種類の型に保つこと、KMP の共有モデルを改造せずに使えることを置いている。公開 API は両プラットフォームで語彙と構造を 1 対 1 に揃え、記法は各流儀に従う (core/ADR-0002)。iOS エンジンの内部では、compositional layout のセクション (内部の塊) を「セクション」と呼んでいる (ios/ADR-0009)。

Swift の初期化子は ID の指定 × テンプレートの切り替えで 4 つある。Kotlin は省略可能な引数の型を、渡された値から推論する。Android の Compose Lazy 系は項目のキーを状態保存 (Bundle) に載せるため、キーは保存可能な型でなければならない (core/ADR-0011 の Android 固有の不正入力)。

前提: 空のグループ (項目が 0 件のグループ) の見出しを出す必要がある画面は、決定の時点で挙がっていない。

## Decision

### グループの値

利用者は今までどおり平らな配列を渡し、各項目の「どのグループか」を表す値 (グループの値) をキーパス / ラムダで指す。ライブラリは配列の順に、同じグループの値が続く項目をまとめて 1 つのグループにする。グループの識別はグループの値で行う。

同じグループの値が配列の離れた位置に再び現れる入力 (並べ替え忘れ) は不正入力として扱う (core/ADR-0011 の方針)。利用者アプリの debug ビルドでは assertion で知らせ、release では配列の順のまま別々のグループとして表示を続け、警告ログを出す。同じ値をわざと何度も使う用途 (送信者ごとの連続したメッセージのまとまりなど) は、グループの値に何番目のまとまりかを含めて表す。

Android では、グループの値は項目の `key` と同じく状態保存に載せられる型でなければならない (利用契約)。ライブラリはグループの見出しに、グループの値を内部の型で包んだ lazy のキーを付け、見出しがグループの並べ替えや項目の移動で項目と一緒に動くようにする。内部の型で包むのは、項目のキーとグループの値が偶然一致したときの衝突を避けるためである。載らない値は、項目の `key` と同じ扱い (core/ADR-0011 の Android 固有の不正入力) にする。

グループの値の取り出し方 (キーパス / ラムダ) は表示中に差し替えてよい。同じ配列のまま差し替えた場合も、新しいグループの値の並びが前回と異なればグループを組み直し、差分として反映する。並びが同じなら組み直さない。

グループごとに layout 値を持たせる入れ物は無く、layout 値はコレクション全体で 1 つのまま (core/ADR-0006) とする。

### 見出し

グループの見出しは任意の View / Composable で書ける。宣言のクロージャには、そのグループの値と、そのグループに入る項目が渡される。高さは中身から自動で決まり、高さの指定は持たない (旧 `GroupHeaderHeight` は継承しない)。グリッドでは全幅を占める。グループが持つのは見出しだけで、グループのフッターは持たない。見出しは省略でき、そのときグループはグループ間の間隔と区切り線 (core/ADR-0016) の単位としてだけ働く。

見出しは既定でスクロール時に上端へ固定し、設定 1 つ (`pinnedHeaders: false`) で固定を外せる (区切り線の既定表示・opt-out と同じ形)。

### 公開 API の形

グループの値・見出し・固定の有無を 1 つの宣言にまとめる。Swift は modifier `.groups(by:pinnedHeaders:header:)`、Kotlin は `KsCollectionView` の引数 `groups` に `KsGroups` 型の値を渡す。グループの値の型は Swift が `Hashable`、Kotlin が型引数で、見出しのクロージャは型を保ったまま値を受け取る。`KsGroups` は Kotlin だけの公開型で、Swift の modifier に当たる (Kotlin の `template(key)` に Swift の `KsTemplate` が当たるのと同じ非対称)。見出しと固定の設定は省略できる。

項目型 `Product` の `category` をグループの値にし、見出しに「カテゴリ名 (件数)」を出す例:

```swift
KsCollectionView(products) { product in ProductRow(product) }
    .groups(by: \.category) { category, productsInGroup in
        Text("\(category) (\(productsInGroup.count))")
    }
```

```kotlin
KsCollectionView(
    items = products,
    key = { it.id },
    groups = KsGroups(by = { it.category }) { category, productsInGroup ->
        Text("$category (${productsInGroup.size})")
    },
) { template { product -> ProductRow(product) } }
```

公開の語彙は group に揃え、section は使わない。`groupBy` という名前は避け、続いた範囲だけがグループになることを利用者向けドキュメントと debug の assertion で示す。

### 間隔

グループとグループの間の間隔 `groupSpacing` と、見出しとそのグループの先頭行の間の間隔 `headerItemSpacing` を、行間と同じく layout 値の引数で宣言する (いずれも既定 0。core/ADR-0006 の「間隔は layout 値で宣言する」)。`headerItemSpacing` は旧 `GroupFirstSpacing` に当たる。グループ間の間隔は前のグループの最終行の後、次のグループの見出しの前に入り、リストの先頭と末尾には入らない (端は `contentPadding` が受け持つ)。

行間は行と行の間にだけ入り、グループの見出しの前後にも、ルートのヘッダー / フッターの前後にも入らない。`contentPadding` はルートのヘッダーの上とフッターの下に入る (ヘッダー / フッターもスクロールするコンテンツの一部。core/ADR-0006 の意味論)。

## Alternatives Considered

### 宣言の形

- **グループの配列を渡す (各グループが見出しの情報と項目の配列を持つ。旧 AiForms と同じ形)**: 却下。項目とは別にグループの型が要り、配列が 1 種類の型でなくなる。共有モデルが平らな配列を返す場合は VM でグループに組み直す必要がある。並べ替えをデータ層に置く決定 (core/ADR-0003) に対して、グループ分けを利用者が組み直す手間が残る。
- **両方の入口を用意する**: 却下。公開 API の入口が 2 つになり、両プラットフォームの実装・テストと利用者向けドキュメント (en/ja の Skill) がそれぞれ倍になる。

### 公開 API の形と名前

| 案 | 却下理由 |
|---|---|
| Swift の初期化子にグループの値の引数を足す | 初期化子が 8 つになり、今後の引数追加でさらに倍になる。modifier ならどの初期化子とも組み合わさる |
| Kotlin でグループの値と見出しを別々の省略可能な引数にする | 見出しを省いた呼び出しでグループの値の型が決まらず、見出しの値が `Any` になる |
| 固定の有無を独立した modifier / 引数にする | グループの宣言と離れた場所に置けてしまい、グループなしで指定されたときの意味が無い。固定の有無は見出しに属する設定である |
| 公開の語彙を section にする (`.sections(by:)` / `KsSections` / `sectionSpacing`) | 利用者の言葉 (「グループ化」「グループの値」) と旧 AiForms の語彙からずれ、iOS エンジンの内部の「セクション」(内部の塊) と同じ言葉になって取り違えやすい |
| 見出しの下の間隔を `groupHeaderSpacing` / `groupHeaderToItemsSpacing` / `spacingBelowGroupHeader` / `groupHeaderBottomSpacing` と名付ける | `groupHeaderSpacing` は見出しの上か下か、何と何の間かが読めない。残りは長い、語順がほかの間隔と違う、「下端」がどちらの下端か曖昧、のいずれか。layout 値で間隔を持つ見出しはグループの見出しだけなので `group` を外し、`rowSpacing` / `columnSpacing` と同じ作りの `headerItemSpacing` にした |

### 同じグループの値が離れて現れる入力

- **離れて現れた同じ値を 1 つのグループに集める**: 却下。並べ替え忘れを黙って直すため気づけず、画面の並び順が配列の順とずれてスクロール命令や位置の指定と食い違う。
- **離れて現れた同じ値を正当な入力として別々のグループにする**: 却下。並べ替え忘れに気づけない。同じ値が複数あるとグループの識別が「値 + 何回目か」になり、あいだに別のまとまりが入ると番号がずれて見出しの差分アニメーションが崩れやすい。

### Android の見出しのキー (グループの値の制約を避ける案)

- **見出しのキーをグループの先頭の項目のキーから作る**: 却下。先頭の項目が入れ替わるたびに見出しが作り直され、見出しの移動アニメーションが成り立たない。
- **見出しのキーをグループの値を `toString()` した文字列にする**: 却下。異なる値が同じ文字列になると衝突し、重複キーで落ちる。

### グループの値の取り出し方の差し替え

- **表示中に差し替えない前提にする**: 却下。カテゴリ別 / ブランド別のような表示の切り替えは利用者の自然な使い方で、前提にすると同じ配列のまま切り替えたときに古い境界のままになる (iOS では古い境界に新しい見出しが出た)。

### 見出しと余白

- **グループのフッターも用意する (ルートのヘッダー / フッターと揃える)**: 却下。旧 AiForms でも実績のある用途でも使うのは見出しだけで、フッターは後から宣言を足しても既存の利用者コードを壊さない。フッターがあると固定ヘッダーの押し出しやグループ末尾の区切り線・余白の組み合わせが増える。
- **見出しを既定では固定せず、指定したときだけ固定する**: 却下。ロードマップのゴールと実績のある用途は固定される見出しが前提で、毎回 1 行を書かせることになる。iOS 標準の plain なリストも既定で固定する。
- **見出しを常に固定し、設定を持たない**: 却下。見出しを大きな帯やバナーとして使い、固定したくない画面を作れない。
- **グループ間の余白の設定を持たず、見出しの View の余白で作る**: 却下。固定された見出しが余白ごと上端に貼り付き、見出しの上に空白の帯が残る。見出しの無いグループの間を空けられない。
- **グループの後ろの余白を持つ (`GroupLastSpacing` 相当)**: 却下。前のグループの最終行と次の見出しの間はグループ間の間隔が受け持ち、リストの末尾は `contentPadding` が受け持つ。
- **見出しの上下にも行間を入れる (見出しを行と同じに扱う)**: 却下。見出しと先頭行の間だけを行間と別の値にできない。
- **見出しと先頭行の間を見出しの View の余白で作る**: 却下。固定された見出しが余白ごと上端に貼り付き、見出しの下に空白の帯が残る。
- **ルートのヘッダー / フッターの余白を両プラットフォームで違うまま残す**: 却下。Sample のプラットフォーム間の見え方 (cross/ADR-0004) が一致せず、グループの見出しとルートのヘッダーで規則が違う。

## Consequences

### 宣言の形

- 正: 既存の API に modifier / 引数 1 つと layout 値の引数を足すだけで、項目のモデル・配列の型・KMP の共有モデルに手を入れずにグループ化できる。
- 正: データ層で並べた順がそのままグループになり、項目を別グループへ動かすのはグループの値を変えるだけで済む。
- 正: 正しい入力ではグループの識別がグループの値そのものになり、並べ替え忘れには開発中に気づける。
- 正: グループの値の型が見出しのクロージャまで保たれ、見出しを省いても型が `Any` に落ちない。
- 負: 項目が 0 件のグループは存在できず、その見出しも出せない。
- 負: 同じ値を何度も使う用途では、利用者がグループの値に何番目のまとまりかを含める手間を負う。release で不正な入力を受けた間は同じ見出しが複数回表示され、ライブラリはその間だけ同じ値のグループを内部で区別する。
- 負: 取り出し方を差し替えるたびに、グループの値の列を前回と比べる費用がかかる。
- 負: 旧 AiForms (グループのコレクション) からの移行では、利用者がデータの形を平らに直す必要がある。

### 見出しと間隔

- 負: 見出しに出せる情報は、グループの値そのもの (構造体でもよい) とグループ内の項目から取れるものに限られる。
- 負: 一覧の中でグループごとに list とグリッドを切り替えることはできない。
- 負: グループ末尾の「もっと見る」や小計の行は、グループの最後の項目のテンプレートに含めて作ることになる。後からフッターを足すときは、グループ末尾の区切り線と余白の規則を見直す。
- 負: ルートのヘッダー / フッターの前後の余白が、グループを宣言しない既存の画面でも変わる (iOS は `contentPadding.top` の位置、Android はヘッダーの下の行間)。

### プラットフォーム間

- 負: Android ではグループの値の型が状態保存に載る型に限られ、iOS (`Hashable` であればよい) より狭い。
- 負: Swift は modifier、Kotlin は `KsGroups` 型の値と、宣言の置き場所が両プラットフォームで非対称になる。
- 負: 固定あり / なしの 2 通りを、両プラットフォームで同じ見え方に揃えて保守する。
