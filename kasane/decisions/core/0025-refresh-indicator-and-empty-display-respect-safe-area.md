## Context

一覧を全画面に広げて置いた場合、ライブラリが安全領域に合わせるのは固定中のグループの見出しの位置だけで、行はバーの裏を流れる (core/ADR-0017)。安全領域を使う箇所を絞った理由は、利用者の余白の指定 (`contentPadding`) と二重にならないためだった。

ページングの導入で、ライブラリが一覧に重ねて描くものが 3 つ増える。Pull to Refresh のインジケータ (各プラットフォームの標準の部品。core/ADR-0023)、項目が 0 件のときに一覧の真ん中に出す表示、項目が並んでいるときに見えている範囲の下端に重ねる次のページの読み込み中の表示 (core/ADR-0024) である。どれも中身の一部ではないため、中身の周りの余白である利用者の余白の指定 (`contentPadding`) は効かない。利用者は一覧の上に重ねた自前のもの (浮いた操作パネル等) を避けるために、下端の余白を大きく取ることがある。iOS の一覧は行をバーの裏に流すために安全領域を自動では空けない設定 (`contentInsetAdjustmentBehavior = .never`) で、標準の引っ張りの部品をそのまま付けると、全画面の一覧ではインジケータがナビゲーションバーの裏に出る。SwiftUI 標準の `List` + `.refreshable` では、インジケータはバーの下に出る。0 件の表示をバーの裏も含めた範囲の真ん中に置くと、見えている範囲からは上寄りに見える。

前提: 全画面の一覧でも、Pull to Refresh のインジケータはバーの下に見え、0 件の表示は見えている範囲の真ん中に出るのが自然な形である (オーナー判断)。

## Decision

core/ADR-0017 の決定のうち「ライブラリが安全領域に合わせるのは、固定中のグループの見出しの位置だけ」とする範囲を本決定で置き換え、安全領域に合わせる箇所に次の 3 つを足す。行はバーの裏を流れること、コンテンツの先頭・末尾に安全領域の分の余白を足さないこと、項目・見出し・ルートのヘッダー / フッターの中身を押し下げないこと、左右の安全領域を対象外とすることは維持する。

- Pull to Refresh のインジケータは、上端の安全領域の境目 (バーのすぐ下) より下に出す
- 項目が 0 件のときの表示は、上下の安全領域を除いた、一覧の見えている範囲の真ん中に置く
- 次のページの読み込み中の表示は、下端の安全領域の境目 (ナビゲーションバー・ホームインジケータのすぐ上) より上に置き、利用者の余白の指定 (`contentPadding`) では位置を変えない
- 安全領域に重ならない置き方では、追加の値はすべて 0 で見え方は変わらない

## Alternatives Considered

- **Pull to Refresh のインジケータだけを安全領域に合わせる**: 却下。改訂の範囲は最小になるが、全画面の一覧では 0 件の表示がバーの分だけ上寄りに見える (iPhone で 30pt 前後)。
- **次のページの読み込み中の表示を、下端の余白の指定 (`contentPadding` の下) の分も上げて置く**: 却下。一覧の上に重ねた別のもののために取った余白で、ライブラリが重ねる表示の位置が動く (オーナー判断: 本体以外の影響で位置がずれるのは重大な欠点)。`contentPadding` は中身と一緒にスクロールする余白で、重ねる表示の置き場は決めない。
- **core/ADR-0017 のまま、どちらも安全領域に合わせない**: 却下。改訂は要らないが、iOS の全画面の一覧では、引っ張ってもインジケータがバーの裏に隠れて見えない。

## Consequences

- 正: 全画面に広げた一覧でも、Pull to Refresh のインジケータがバーの下に見え、0 件の表示が見えている範囲の真ん中に出て、次のページの読み込み中の表示がナビゲーションバーの上に見える。
- 正: 次のページの読み込み中の表示の位置は、利用者が中身のために取った余白に左右されない。
- 正: 行がバーの裏を流れる作りと、利用者の余白の指定の意味は変わらない。
- 負: 安全領域を読む箇所が、両プラットフォームで固定の上端のほかに 3 つ増え、それぞれで安全領域の求め方を保守する。
- 負: 利用者が一覧の下端に自前のもの (浮いたボタン等) を重ねて安全領域として渡していないと、次のページの読み込み中の表示がそれに重なる。
- 負: iOS は標準の引っ張りの部品の位置を、ライブラリが安全領域の分だけ調整する必要がある。
