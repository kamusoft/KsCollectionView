## Context

Pull to Refresh はライブラリが一覧に接続し、ページングの取り直し中の状態と連動させる (core/ADR-0005)。iOS は SwiftUI 標準の `.refreshable { await }` を付けると、その処理を環境値として受け取れる。Android は非同期関数の取り直しの処理を引数で受け、material3 の `PullToRefreshBox` で一覧を包み、インジケータは「処理の実行中、または状態が取り直し中」に出す外形が先に決まっていた。対称性は語彙と構造でそろえ、記法や非同期処理は各プラットフォームの流儀に残す (core/ADR-0002)。

引っ張っていないのに状態が取り直し中になるのは、VM が自分で取り直したとき (絞り込みの変更・再読み込みのボタン等) である。初回の読み込みは追加読み込みの処理で始まるため (core/ADR-0020)、これには当たらない。

追加読み込みを頼むのは状態が待機のときだけなので (core/ADR-0022)、取り直し中に追加読み込みが始まることはない。逆向きは残る。追加読み込みの途中で利用者が先頭まで戻って Pull to Refresh をすると、取り直しで一覧が新しくなった後に古い追加読み込みの結果が遅れて届き、新しい一覧の後ろに古いページが混ざる (ID が重なれば不正入力の警告も出る)。取り直しが始まったら追加読み込みを取り消す手当ては、VM が取り消しを失敗として拾うと取り直し中の状態を失敗で上書きして壊れ (Swift の `catch`・Kotlin の `runCatching` は取り消しも拾う)、VM のスコープで起動した読み込みにはライブラリの取り消しが届かない。material3 1.4.0 の `PullToRefreshBox` には引っ張りを受け付けない設定が無く、その土台の修飾 (`Modifier.pullToRefresh`) には有効 / 無効の引数がある。

前提: Pull to Refresh のインジケータは、iOS・Android とも引っ張ったときだけ出るのがプラットフォームの自然な形である (オーナー判断)。追加読み込みにかかる時間は短く (1〜2 秒程度)、その間だけ引っ張れなくても実害は小さい。

## Decision

- Pull to Refresh のインジケータは、両プラットフォームとも引っ張って始めた取り直しの間だけ出す。VM が自分で始めた取り直し (引っ張っていないのに状態が取り直し中) では出さない
- 引っ張って始めた取り直しでは、取り直しの処理が終わっても、状態が取り直し中の間はインジケータを出し続ける (VM の処理がすぐ戻る書き方のため)
- ページングの状態が追加読み込み中の間と、ライブラリが頼んだ次ページ要求の処理が実行中の間は、両プラットフォームとも Pull to Refresh の引っ張りを受け付けない。どちらでもなくなったら、また引っ張れるようにする

## Alternatives Considered

- **状態が取り直し中ならいつでもインジケータを出す**: 却下。VM が始めた取り直しにもインジケータが出るのは、両プラットフォームとも Pull to Refresh の自然な形ではない。途中までスクロールしていると、Android は一覧の上端に重ねて見え、iOS は引っ張りの部品がコンテンツの上の外側にあるため見えず、先頭にいてもプログラムから出すには位置の調整が要る。
- **取り直しが始まったら先頭へ戻してインジケータを出す**: 却下。どこにいても両方で見えるが、取り直しの開始で読んでいた場所を離れ、失敗したときも元の場所に戻れない。
- **取り直しが始まったら、実行中の追加読み込みの処理をライブラリが取り消す**: 却下。いつでも引っ張れるが、VM が取り消しを失敗として拾うと取り直し中の状態を失敗で上書きして壊れ、VM のスコープで起動する書き方には取り消しが届かず古いページが混ざる。
- **追加読み込みとの競合でライブラリは何もせず、古い結果を見分けて捨てるのを VM に任せる**: 却下。ライブラリは単純だが、防ぐ責任がすべて VM にかかる。

## Consequences

- 正: Pull to Refresh は両プラットフォームとも、利用者が見慣れた標準の一覧と同じく引っ張ったときだけインジケータが出る。iOS でプログラムからインジケータを出すときの位置の調整が要らない。
- 正: 状態を追加読み込み中にしてから処理から戻る書き方と、処理の中で取得を待つ書き方では、Pull to Refresh の取り直し後の一覧に古いページが混ざらない。VM に取り消しの扱いを求めない。
- 負: VM が自分で始めた取り直しには、ライブラリの Pull to Refresh のインジケータが出ない。取り直し中であることは、別の表示部品かアプリで見せる必要がある。
- 負: 追加読み込みが遅いと、終わる (または失敗する) まで Pull to Refresh で更新できない。
- 負: 次ページ要求の処理から戻った後に状態を追加読み込み中にする書き方では、戻ってから書き換えるまでの間に引っ張れ、その取り直しには古いページが混ざりうる。VM が自分で始める取り直し (引っ張らない再読み込み) と読み込みの競合も、ライブラリは防がない。どちらも VM が古い結果を捨てる必要がある。
- 負: Android は `PullToRefreshBox` では引っ張りを止められないため、有効 / 無効を切り替えられる土台の修飾とインジケータで組む。
- 負: Pull to Refresh の接続が、ページングの状態 (取り直し中・追加読み込み中) を読むようになる。
