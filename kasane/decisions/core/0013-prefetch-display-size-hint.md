## Context

core/ADR-0008 は先読み宣言を「アイテム → URL 配列」のクロージャと定めた。画像ロード統合の詳細設計 (v1-foundation ロードマップの画像ロードのフェーズの agenda、2026-09-05) は、宣言にサイズヒントを付けて縮小鍵まで合わせる案を、利用者に `KsImage` とのサイズ一致責任を負わせること・Android では列幅を利用者が自前計算しなければならないことを理由に却下した。image-loading の設計も、列幅をライブラリが計算して `KsImage` に渡す案と、利用者に縮小サイズを指定させる案を却下した。その帰結として到達点 `memory` の先読みは「URL だけの鍵で元寸をメモリに載せ、表示側 (`KsImage`) が元寸を同期で枠サイズに縮小して初回描画に使う」形になった。

この形は Android の実機で成立しない。先読みが載せた元寸はハードウェアビットマップ (GPU 側) になり CPU から画素を読めないため、初回表示は読み込み中を経由してディスクから表示サイズで再デコードする。到達点 `memory` は `disk` に対して元寸のデコードとメモリ保持の費用だけ余分に払い、「メモリ到達点の後の表示はネットワークもデコードのやり直しもしない」という契約が破れ、iOS (UIImage は常に読める) との非対称が生じている。ハードウェア支援を切る回避策 (`allowHardware(false)`) は描画のたびに画素の転送費用が乗り、基準機で frameOverrun P99 18〜21 ms を出したためオーナー方針で不採用とした。

前提:

- 表示側の鍵は「URL + 枠の実サイズ + 当てはめ方」の完全一致で、メモリにある項目を「近い大きさなら使う」判定は無い
- ローダーに近い大きさの項目を引き当てる手段が無い。Nuke 13 の `ImagePipeline.cache` は鍵単位の参照だけで、近似の引き当ても鍵の列挙も無い。Coil 3 の `Precision.INEXACT` は「要求以上の大きさなら有効」(下限 1.0・上限なし) で、少し小さい項目を許す下限も大きすぎる項目を退ける上限も表せない
- Nuke / Coil とも、メモリキャッシュからの追い出しを通知する API を持たない
- 呼び出し元 (iOS `KsCollectionViewController`、Android `KsCollectionView`) にはレイアウト値・コンテナ幅・余白が揃っていて列幅を解ける

## Decision

**表示 (`KsImage`) は鍵の完全一致をやめ、同じ URL でメモリにある項目の実物の寸法と枠を比べて、許容範囲の内側なら使い、描画時に枠へ合わせる。** 判定には、項目を枠に当てはめるのに必要な拡大率 `s` を使う。`fill` は `max(枠幅/幅, 枠高/高)`、`fit` は `min(枠幅/幅, 枠高/高)` で、`s` が [1/上限, 1/下限] の内側なら使う。範囲内の項目が複数あれば、`s` が 1 に最も近い項目を選ぶ。下限は小さすぎる項目を拡大してぼやけるのを防ぎ、上限は極端に大きい項目 (GPU 縮小のざらつき・テクスチャ上限) を避ける。許容範囲は公開 API にせず、ライブラリ内部の定数 1 か所に置く (初版は下限 0.5・上限 4、実機の見た目で調整する)。判定は宣言の値ではなく実物の寸法で行う。

**範囲内の項目があれば、`KsImage` はローダーへ取得の要求を出さず、その項目を表示の完了状態として描く。** 範囲外の項目しか無ければ使わず、枠の実サイズで縮小デコードする (読み込み中を経由する)。CPU で画素を読む同期縮小は行わないので、ハードウェアビットマップのままで成立する。

**先読み宣言の要素を `KsResource` (URL + 任意の幅 `KsWidth`) にする。** 入口は `prefetchResources` 1 本のままで、URL だけの配列 (`[URL]` / `List<String>`) は廃止する (配布前の破壊的変更)。core/ADR-0008 の決定のうち、先読み宣言の戻り値を URL 配列とする外形を本決定で置き換える。クロージャで宣言する形・同じキャッシュを見る `KsImage` と対にする形・データ型に準拠を課さない形は維持する。

幅の種類は 2 つだけにする。**列幅** はライブラリが先読みの時点で画面幅・列数・余白から解き、グリッドの幅いっぱいに置く画像に使う。**固定値** は Swift pt / Kotlin dp の 1 値で、セル内の固定サイズ配置に使う。高さ・縦横比・当てはめ方は宣言に持たない (当てはめ方は View の仕事)。幅のある要素は、幅 × 幅の正方形を覆う最小の大きさに縮小デコードして (元がそれより小さければそのまま、拡大しない) メモリに載せる。短辺を宣言幅にそろえるので、縦長・横長どちらの画像でも正方形以下の枠に `fill` で当てはめられる。概算でよく、大きめに書く運用を前提とする。到達点 `disk` では幅を使わない。

**幅を省略した要素は、到達点 `memory` では原寸をデコードしてメモリに載せる。** 表示は上と同じ許容範囲の引き当てで原寸を使う。1 つの宣言の中で幅あり・幅なしを混ぜてよい。書き口は Swift `KsResource(url, width: .column)` / `.fixed(40)` / `KsResource(url)`、Kotlin `KsResource(url, width = KsWidth.Column)` / `KsWidth.Fixed(40.dp)` / `KsResource(url)`。

表示から学んで先読みに使う方式 (A-2) は本決定では採らず、宣言で書けないケースが出たときに足す (却下ではなく見送り)。

## Alternatives Considered

| 案 | 却下理由 |
|---|---|
| 表示から学ぶ (A-2: 同じコレクションで `KsImage` が要求した寸法を覚えて以後の先読みに使う。相談役の推奨は宣言との併用 A-3) | 学習表・レイアウト世代・窓の再評価・一意に絞れないときの扱いが要り、実装の重い部分がここに集中する。概算 + 許容範囲で宣言の負担が軽くなったため、宣言で書けるケースを先に解く。見送り (実例が出たら追加) |
| 宣言と学習の併用を今回一気に (A-3) | 上と同じ理由で学習部分を切り離した |
| 鍵の完全一致のまま、サイズを一定の刻みに丸めて先読みと表示で同じ鍵にする (バケット化) | 概算と実寸が刻みをまたぐと外れて `disk` に落ちる。「概算でよい」を成立させる力が弱い |
| 先読みした項目があれば枠より小さくても必ず使う (下限なし) | 概算を大きく外した画面が全部ぼやける事故を防げない |
| 枠より小さい項目は使わず必ず縮小デコードし直す (下限 = 1.0) | 「概算はやや大きめに」を利用者に強いる。少し小さいだけで読み込み中を経由する |
| 上限を持たず、原寸は常にそのまま使う | 4000 px 級の写真を小さな枠に描くと GPU 縮小のざらつきとテクスチャ上限の問題が出る |
| 幅だけで判定する (宣言と同じ軸) | 縦長の枠に `fill` する画像で高さが足りず、拡大ぼやけになる |
| 許容範囲を公開 API にして利用者が調整する | `KsImage` に縮小の個別引数を持たせない画像ロードの agenda の決定と衝突し、値の意味を利用者に説明する負担に見合わない |
| 範囲内の項目でもローダーへ要求を出し、ローダーの判定 (`Precision.INEXACT`) に寄せる | Coil の下限が 1.0 で「概算は少し小さくてもよい」が成立せず、上限は判定されない。Nuke にはそもそも近似の判定が無い |
| Coil の鍵の全走査で同じ URL の項目を探す (Android)、iOS は候補サイズの総当たり | 走査は件数に比例し、10,000 件のグリッドで毎セル O(n) になる。総当たりは候補が無限 |
| ライブラリ独自のメモリキャッシュを持つ | core/ADR-0012 (ローダーの共有インスタンスをそのまま共有キャッシュにする) と衝突する |
| 幅を長辺の上限にする (`maxPixelSize` 相当) | 縦長の画像で幅が宣言値より小さくなり、`fill` で拡大ぼやけになる |
| 宣言に幅と高さ (または縦横比) と当てはめ方を持たせる | 当てはめ方は View の仕事で宣言の責務ではない。先読みの目標は幅だけで足り、幅だけで困る唯一のケース (画像より縦長の枠に fill) は表示側の実物判定で弾かれて `disk` と同じ動きに落ちる |
| セル幅からライブラリが一律に画像枠を推定して先読みに使う (image-loading の設計で却下した「列幅をライブラリが計算して `KsImage` に渡す案」の再来) | `KsImage` がセル全体を占めるとは限らない。本決定はこれを利用者が明示的に選ぶ「列幅」の宣言に限定し、枠がセルより小さい場合は許容範囲で大きめの項目を使う |
| 別名の入口 (`prefetchImages` 等) を足して URL だけの配列を残す | 「画像」と「リソース」で区別がつかない。幅あり・幅なしの混在ができず、同時宣言の不正入力の扱いが要る |
| `[URL]` と `[KsResource]` のオーバーロード | Kotlin の `KsCollectionView` は引数の多い 1 つの Composable で、複製になる。Swift だけ残すと非対称 |
| 列幅をファクトリ (`KsResource.column(url)`)、固定値をコンストラクタにする / 幅を `Dp` の番兵値で表す | コンストラクタとファクトリが混ざって読みにくい / 番兵への計算を防げない。型 (`KsWidth`) で表す方が直感的 (オーナー判断) |
| 先読みにハードウェア支援を使わない指定を付けて同期縮小を成立させる | 描画のたびに画素の転送費用が乗る (基準機で P99 18〜21 ms)。オーナー方針で不採用 |

## Consequences

- 正: 到達点 `memory` は幅の有無に関わらず、両プラットフォームで初回表示が読み込み中もデコードのやり直しも経由しない。CPU で画素を読まないので Android のハードウェアビットマップでも成立し、iOS との非対称が消える
- 正: 幅を書いた要素は元寸をメモリに載せないため、メモリ量が縮小済みの分だけになる。幅を省略した要素は原寸を持つ (利用者の選択)
- 正: 概算が実寸と一致しなくても、大きめなら当たり、外れても壊れず `disk` と同じ動きに落ちる
- 負: 公開 API の破壊的変更 (配布前): `prefetchResources` の戻り値が `[KsResource]` になる。画像ロードの agenda の「サイズヒント付き宣言は却下」と、image-loading の設計の「列幅をライブラリが計算して渡す案」「利用者に縮小サイズを指定させる案」の却下の前提は本決定で改訂される
- 負: 表示に使う項目の寸法は枠と一致しなくなる。枠より大きい項目は描画時に縮み、枠より小さい項目 (下限まで) は軽く拡大されるため、概算を小さく書くと見た目がわずかに甘くなる
- 負: 大きめの概算はその分メモリを余分に食う。許容範囲の値と概算の書き方は利用者向け注記が要る
- 負: ローダーに近似の引き当ても鍵の列挙も追い出しの通知も無いため、両プラットフォームともライブラリが URL ごとに「メモリへ載せるよう要求した鍵」の索引を持つ。索引は寸法も画像も持たない手掛かりで、実在と寸法の正はローダーのキャッシュに置く (core/ADR-0012 の「独自のキャッシュ領域を持たない」と両立させるため)
- 負: 索引は上限つきで、索引から外れた項目はメモリにあっても引き当てられず、通常の縮小要求に落ちる
- 負: 先読み台帳は URL 単位から取得単位 (`disk` は URL、`memory` は URL + 幅 px) に変わる。列幅は回転・列数変更で変わるため、以後の先読みは新しい幅で出て、古い項目は許容範囲の判定に任せる
- 負: ローダー付属ビュー (`LazyImage` / `AsyncImage`) を直接使う利用者は、この引き当てを通らないため縮小済みの項目に当たらない (共有キャッシュによる再ダウンロードなしは維持)

- 宣言で書けないケース (テンプレートやレイアウトが実行時にしか決まらない等) が実例として出たとき (A-2 の追加を検討)
- 許容範囲の引き当てが Coil / Nuke の版更新で成立しなくなったとき
