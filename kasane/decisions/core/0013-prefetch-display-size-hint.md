## Context

core/ADR-0008 は先読み宣言を「アイテム → URL 配列」のクロージャと定め、phase-8 の agenda (2026-09-05) は「サイズヒント付き宣言で縮小鍵まで合わせる案」を、利用者に `KsImage` とのサイズ一致責任を負わせること・Android では列幅を利用者が自前計算しなければならないことを理由に却下した。その帰結として到達点 `memory` の先読みは「URL だけの鍵で元寸をメモリに載せ、表示側 (`KsImage`) が元寸を同期で枠サイズに縮小して初回描画に使う」形になった (image-loading の design Decision 5 と deviation 2026-09-07)。

この形は Android の実機で成立しない。先読みが載せた元寸はハードウェアビットマップ (GPU 側) になり CPU から画素を読めないため、初回表示は読み込み中を経由してディスクから表示サイズで再デコードする。到達点 `memory` は `disk` に対して元寸のデコードとメモリ保持の費用だけ余分に払い、spec「メモリ到達点の後の表示 (ネットワークもデコードのやり直しもなし)」が破れ、iOS (UIImage は常に読める) との非対称が生じている。ハードウェア支援を切る回避策 (`allowHardware(false)`) は描画のたびに画素の転送費用が乗り、基準機で frameOverrun P99 18〜21 ms を出したためオーナー方針で不採用 (image-loading deviation 2026-09-08)。

前提: 表示側の鍵は「URL + 枠の実サイズ + 当てはめ方」の完全一致 (iOS は `ThumbnailOptions`、Android は自前の `coil#size` / `ks#scale` extras) で、メモリにある項目を「近い大きさなら使う」判定は無い。先読みの台帳は URL → 参照数のみ。呼び出し元 (iOS `KsCollectionViewController`、Android `KsCollectionView`) にはレイアウト値・画面幅が揃っていて列幅を解ける (探索 2026-09-22 の調査)。

## Decision

**表示 (`KsImage`) は鍵の完全一致をやめ、同じ URL でメモリにある項目の実物の寸法と枠を比べて、許容範囲 (下限・上限) の内側なら使い、描画時に枠へ合わせる。** 下限は小さすぎる項目を拡大してぼやけるのを防ぎ、上限は極端に大きい項目 (GPU 縮小のざらつき・テクスチャ上限) を避ける。範囲外の項目しか無ければ使わず、枠の実サイズで縮小デコードする (読み込み中を経由)。判定は宣言の値ではなく実物の寸法で行う。CPU で画素を読む同期縮小は行わない (ハードウェアビットマップのままで成立する)。

**先読み宣言の要素を `KsResource` (URL + 任意の幅 `KsWidth`) にする。** 入口は `prefetchResources` 1 本のままで、URL だけの配列 (`[URL]` / `List<String>`) は廃止する (配布前の破壊的変更)。幅の種類は 2 つだけ: **列幅** (ライブラリが先読みの時点で画面幅・列数・余白から解く。グリッドの幅いっぱいに置く画像向け) と **固定値** (Swift pt / Kotlin dp の 1 値。セル内の固定サイズ配置向け)。高さ・縦横比・当てはめ方は宣言に持たない (当てはめ方は View の仕事)。先読みはその幅になるよう縮小デコードして (元が小さければそのまま、拡大しない) メモリに載せる。概算でよく、大きめに書く運用を前提とする。

**幅を省略した要素は、到達点 `memory` では原寸をデコードしてメモリに載せる。** 表示は上と同じ許容範囲の引き当てで原寸を使う。1 つの宣言の中で幅あり・幅なしを混ぜてよい。書き口: Swift `KsResource(url, width: .column)` / `.fixed(40)` / `KsResource(url)`、Kotlin `KsResource(url, width = KsWidth.Column)` / `KsWidth.Fixed(40.dp)` / `KsResource(url)`。

表示から学んで先読みに使う方式 (A-2) は本決定では採らず、宣言で書けないケースが出たときに足す (却下ではなく見送り)。

## Alternatives Considered

| 案 | 却下理由 |
|---|---|
| 表示から学ぶ (A-2: 同じコレクションで `KsImage` が要求した寸法を覚えて以後の先読みに使う。相談役の推奨は宣言との併用 A-3) | 学習表・レイアウト世代・窓の再評価・一意に絞れないときの扱いが要り、実装の重い部分がここに集中する。概算 + 許容範囲で宣言の負担が軽くなったため、宣言で書けるケースを先に解く。見送り (実例が出たら追加) |
| 宣言と学習の併用を今回一気に (A-3) | 上と同じ理由で学習部分を切り離した |
| 鍵の完全一致のまま、サイズを一定の刻みに丸めて先読みと表示で同じ鍵にする (バケット化) | 概算と実寸が刻みをまたぐと外れて `disk` に落ちる。「概算でよい」を成立させる力が弱い |
| 先読みした項目があれば枠より小さくても必ず使う (下限なし) | 概算を大きく外した画面が全部ぼやける事故を防げない |
| 枠より小さい項目は使わず必ず縮小デコードし直す (下限 = 1.0) | 「概算はやや大きめに」を利用者に強いる。少し小さいだけで読み込み中を経由する |
| 上限を持たず、原寸は常にそのまま使う | 4000 px 級の写真を小さな枠に描くと GPU 縮小のざらつきとテクスチャ上限の問題が出る |
| 宣言に幅と高さ (または縦横比) と当てはめ方を持たせる | 当てはめ方は View の仕事で宣言の責務ではない。先読みの目標は幅だけで足り、幅だけで困る唯一のケース (画像より縦長の枠に fill) は表示側の実物判定で弾かれて `disk` と同じ動きに落ちる |
| セル幅からライブラリが一律に画像枠を推定して先読みに使う (Decision 5 の却下案 A の再来) | `KsImage` がセル全体を占めるとは限らない。本決定はこれを利用者が明示的に選ぶ「列幅」の宣言に限定し、枠がセルより小さい場合は許容範囲で大きめの項目を使う |
| 別名の入口 (`prefetchImages` 等) を足して URL だけの配列を残す | 「画像」と「リソース」で区別がつかない。幅あり・幅なしの混在ができず、同時宣言の不正入力の扱いが要る |
| `[URL]` と `[KsResource]` のオーバーロード | Kotlin の `KsCollectionView` は引数の多い 1 つの Composable で、複製になる。Swift だけ残すと非対称 |
| 列幅をファクトリ (`KsResource.column(url)`)、固定値をコンストラクタにする / 幅を `Dp` の番兵値で表す | コンストラクタとファクトリが混ざって読みにくい / 番兵への計算を防げない。型 (`KsWidth`) で表す方が直感的 (オーナー判断) |
| 先読みにハードウェア支援を使わない指定を付けて同期縮小を成立させる | 描画のたびに画素の転送費用が乗る (基準機で P99 18〜21 ms)。オーナー方針で不採用 |

## Consequences

- 正: 到達点 `memory` は幅の有無に関わらず、両プラットフォームの実機で初回表示が読み込み中もデコードのやり直しも経由しない。iOS と Android の非対称が消え、`Unreadable` の分岐 (CPU での同期縮小) が不要になる
- 正: 幅を書いた要素は元寸をメモリに載せないためメモリ量が縮小済みの分だけになる。幅を省略した要素は原寸を持つ (利用者の選択)
- 正: 概算が実寸と一致しなくても、大きめなら当たり、外れても壊れず `disk` と同じ動きに落ちる
- 負: 公開 API の破壊的変更 (配布前): `prefetchResources` の戻り値が `[KsResource]` になる。core/ADR-0008 の「URL 配列」の外形を amends する。phase-8 agenda の「サイズヒント付き宣言は却下」と image-loading design Decision 5 の却下案 A / C の前提は本決定で改訂される
- 負: 大きめの概算はその分メモリを余分に食う。許容範囲の値と概算の書き方は利用者向け注記が要る
- 負: spec は「縮小デコードは枠のサイズを超えない」を「許容範囲の項目を使う」に、到達点の Requirement を「メモリにある項目を許容範囲で引き当てる」に書き換える。`KsImage` の鍵から当てはめ方 (`ks#scale`) が外れる
- 負: 先読み台帳は URL 単位から「取得単位 (`disk` は URL、`memory` は URL + 幅 px) 」に変わる。列幅は回転・列数変更で変わるため、以後の先読みは新しい幅で出て、古い項目は許容範囲の判定に任せる
- 負: 許容範囲の引き当ては Nuke に無いため、iOS はライブラリが URL ごとに載っている寸法の索引を持つ。Android は Coil の `Precision.INEXACT` で近い挙動が得られる見込みだが、上限の判定は自前になる可能性があり実物での裏取りが要る
- 負: ローダー付属ビュー (`LazyImage` / `AsyncImage`) を直接使う利用者は、この引き当てを通らないため縮小済みの項目に当たらない (共有キャッシュによる再ダウンロードなしは維持)

## Revisit When

- 宣言で書けないケース (テンプレートやレイアウトが実行時にしか決まらない等) が実例として出たとき (A-2 の追加を検討)
- 許容範囲の引き当てが Coil / Nuke の版更新で成立しなくなったとき
- 到達点 `memory` で表示待ちの体感が改善しないと計測で分かったとき (別要因: 画像 1 枚ごとの subcomposition、cold の取得)
