## Context

ページングの公開契約では、末尾に近づいたときの次ページ要求と、その多重発火の抑止はライブラリの責務である (core/ADR-0005)。発火の判定は残りの項目の数としきい値で行う (core/ADR-0020)。ライブラリが頼むのは状態が待機のときだけだが、VM が状態を追加読み込み中に書き換えるのが遅れる書き方 (VM のスコープに起動した処理の中で、待ってから書き換える等) では、その間も待機に見えるため、スクロールのたびに二重に頼んでしまう。

DSL の利用形の試案では、頼む処理は Swift が非同期のクロージャ、Kotlin が普通の関数だった。Pull to Refresh の Kotlin 側は、Swift の `.refreshable { await }` と同じ「非同期処理が終わるまでインジケータを出す」意味論にするため非同期関数 (`suspend`) で受ける形に決まっている。非同期処理は各プラットフォームの流儀で書く (core/ADR-0002)。

前提: Kotlin では、非同期関数の型の引数に普通の関数を渡せる (ラムダでも関数参照でも)。

## Decision

- 追加読み込みを頼む処理は、Swift は非同期のクロージャ、Kotlin は非同期関数 (`suspend`) の型で受ける。Pull to Refresh と同じ形にする
- ライブラリは、状態が待機で末尾に近いときだけ頼む
- 一度頼んだら、頼んだ処理が終わり、かつ頼んだ時点から状態か配列が変わるまで、次を頼まない

## Alternatives Considered

- **Kotlin は普通の関数のまま受け、状態か配列が変わるまで次を頼まない**: 却下。二重に頼まない点は同じだが、頼む処理の形が Swift と Pull to Refresh からずれ、VM の書き方が起動してすぐ戻る形に寄り、Kotlin では実行中の処理をライブラリがつかめないため取り直しのときの取り消しの手段が無い。
- **状態だけで判断し、頼んだ後に待たない**: 却下。いちばん単純だが、VM が状態の書き換えを遅らせるとスクロールのたびに二重に頼み、VM 側で必ず弾いてもらう必要がある。

## Consequences

- 正: VM が処理の中で待つ書き方でも、VM のスコープに起動してすぐ戻る書き方でも、二重に頼まない。
- 正: 頼む処理の形が両プラットフォームと Pull to Refresh でそろい、VM の普通の関数もそのまま渡せる。
- 正: 実行中の処理をライブラリがつかんでいるため、取り直しが始まったときに追加読み込みを取り消す設計を選べる。
- 負: 処理の中で待つ書き方の読み込みは、ライブラリが一覧の表示の中で実行するため一覧の寿命に結びつき、一覧が破棄される (一覧を含む画面を閉じる等) と取り消される。続けたい読み込みは VM のスコープで起動する必要がある。
- 負: VM が頼みを無視して状態も配列も変えないと、スクロールしても、状態か配列が変わるまで次を頼まない。
