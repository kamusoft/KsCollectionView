## Context

テストは 4 系統ある。iOS 本体、iOS Sample (ユニットテストと、実際の操作を通す UI テスト)、Android 本体、Android Sample である。iOS の 2 系統は、ユニットテストも含めてすべて Simulator の上で走る。Android の 2 系統は JVM の上で動き、エミュレータを使わない。

このほかに、端末が要る確認が 2 種類ある。Android 本体には、画像のデコードが端末の上でどう振る舞うかを確かめる、端末をつないで走らせるテストが数件ある。性能検証は基準機で行い、合否はオーナーの体感で決める (cross/ADR-0006)。

完了判定では、手元で 4 系統を絞り込みなしで全件流す (cross/ADR-0008)。検証 CI は `develop` への push の後と `main` 宛ての Pull Request で走り、後者では必須の検査になる (cross/ADR-0010)。

GitHub の標準のランナーの Simulator は、手元より遅い。検証 CI に iOS 本体のテストを全件載せて初めて走らせた回で、手元では通るテストが 1 件落ちた。セルの再利用を、スクロールを小刻みに送りながら確かめるテストで、手元では 5 秒で終わるものが 150 秒かかっていた。兄弟ライブラリ KsSettingsView にも、CI の Simulator の負荷でテストが一度タイムアウトした記録がある。

GitHub の組織には、自前のランナー (Mac mini) が 1 台登録されている。

前提: 手元の完了判定で 4 系統を全件流す決まりが続くこと。性能の合否をオーナーの体感で決める決まりが続くこと。GitHub の標準のランナーの Simulator が、手元より遅い状態が続くこと。

## Decision

検証 CI では、Simulator・エミュレータ・実機の上で走るテストを 1 件も走らせない。CI が使うのは、GitHub が提供する標準のランナーだけとする。

- iOS は、本体と本体のテストのコード、Sample のアプリと Sample のテストのコードが、ビルドできることだけを確かめる。
- Android は、JVM で走る本体と Sample のユニットテストを全件走らせ、Sample のアプリを組み立てる。

iOS のテストの実行 (本体の全件、Sample のユニットテストと UI テスト)、端末をつないで走らせるテスト、性能検証は、手元の完了条件に残す。

CI の緑が保証するのは、iOS がビルドできることと、Android の JVM のテストが全件通ることまでとする。iOS のテストが通ることは、CI の緑からは言えない。

理由は次のとおり。遅い Simulator の上では、手元で通るテストが時間に依って落ちる。落ちるたびにテストを直す運用は、CI に特有の不安定さに付き合い続けることになり、`main` 宛ての Pull Request の必須の検査が、コードの誤りではない理由で止まる。iOS のテストは手元の完了判定で毎回全件が流れているので、CI から外しても検出の場所は残る。ビルドの確認は Simulator を起動せずに済み、時間に依らない。

## Alternatives Considered

- **iOS 本体のテストを Simulator で全件走らせ、Sample はビルドとユニットテストまでを走らせる**: 却下。CI の緑が、iOS のロジックのテストの通過まで意味するようになる。しかし最初の実行で、手元では通るテストが落ちた。落ちたテストを 1 件ずつ CI に合わせて直しても、別のテストで同じことが起き得る。
- **4 系統をすべて走らせる**: 却下。CI の緑が手元の完了判定と同じ意味になる。しかし上の案の不安定さに、1 件ごとにアプリを起動する UI テストの分が加わり、macOS のランナーを使う時間もいちばん長い。
- **iOS を CI に載せない**: 却下。macOS のランナーを使わずに済む。しかし iOS のコードがビルドできなくなっても、CI では気付けない。
- **端末をつないで走らせるテストだけ、CI のエミュレータで走らせる**: 却下。毎回走るようになる。しかしエミュレータが実機と同じ振る舞いをするかを確かめておらず、エミュレータの起動で CI の時間が延びて不安定さの元になる。
- **組織の自前のランナーに基準機をつないで CI に載せる**: 今は採らない。端末のテストが実機で毎回走り、Android の性能は自動で計測できる。しかし基準機の常時接続と端末の状態の管理が要る。public のリポジトリに自前のランナーをつなぐので、動かせる人と workflow の絞り込みも要る。iOS の性能は体感が合否なので、合否は出ない。

## Consequences

- 正: `main` 宛ての Pull Request の必須の検査が、ランナーの Simulator の遅さで止まらない。
- 正: iOS のコードと Sample がビルドできなくなったことには、CI で気付ける。
- 正: Android は、手元の完了判定と同じテストが CI でも全件走る。
- 正: CI が GitHub の標準のランナーだけで動き、維持する機材が無い。macOS のランナーを使う時間も短い。
- 負: iOS のテストの失敗は、CI では 1 件も見つからない。手元の完了判定の全件実行を省くと、検出する場所が無くなる。
- 負: プラットフォームで CI の緑の意味が違う。Android の緑はテストの通過を意味し、iOS の緑はビルドの成功しか意味しない。
- 負: 端末をつないで走らせるテストの流し忘れを、CI は止めない。関係する変更のときに手元で流す決まりに頼る。
- 負: CI で性能の退行を検出できないままになる。
