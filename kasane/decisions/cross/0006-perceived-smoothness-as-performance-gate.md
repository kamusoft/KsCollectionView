## Context

iOS / Android の性能検証規約 (`handbook/ios/performance-verification.md` / `handbook/android/performance-verification.md`) は、固定 fixture (10,000 件の 2 列グリッド) を自動駆動でフリックし、iOS は hitch time ratio が 3 秒窓で 5 ms/s 未満、Android は `frameOverrunMs` P99 が 0.0 ms 以下、という数値を合否にしていた。image-loading (L 級) の実機計測 (2026-09-08) で、この基準の土台が弱いことが分かった。

- iOS の 5 ms/s は Apple の Animation Hitches の目安を持ち込んだ値だが、3 秒窓に当てると「1 フレームも落とさない」と同値になる。基準機 iPhone 11 で有効に計測した値は一度も存在しない (foundation は代替機かつ hitch を検出できない接続手順だった)
- Android の 0.0 ms は foundation 時点の文字だけのグリッドを基準機で測った実測に合わせた退行検出線であり、利用者体感の閾値ではない。画像グリッドでは到達点 disk でも P99 6 ms で満たせない
- 自動駆動 (XCUITest) が主スレッドの 20〜37% を占め、体感を測る土俵そのものを汚していた。座標駆動に変えても指を離した後の静止待ちで 3 秒窓にフリックは 1 回しか入らない
- 10,000 件は仮想化とメモリ定常化のための件数で、スクロールの滑らかさとは無関係

つまり従来の規約は「体感の目安」と「自分の過去値への退行検出」が混ざり、新機能 (画像) を足すたびに基準に合わない値が出て deviation に残る構造だった。

## Decision

1. スクロール性能の完了判定が保証するものは**「基準機で、その種類の画面をフリックしてもカクつきを感じないこと」(利用者体感)** とする。foundation 時点の実測値への退行検出は合否のゲートにしない。同一 fixture の前回証跡との比較は証跡に記録するに留める。
2. 合否は**オーナーが基準機を手動でフリックして下す**。その操作中に計測器 (iOS は Instruments、Android は Perfetto 等) をプロセス指定で接続しておき、数値は証跡として残す。数値はゲートではなく、合否の説明と次回との比較材料である。
3. worker の役割は、基準機に Release 構成を入れ、計測器を接続してオーナーに渡し、操作後に trace を回収して数値と判定を証跡に書くこと。
4. Android の相対基準 (素の Compose に対するラッパーの薄さ、android/ADR-0001 の検証) は目的が別なので、本決定の対象外として別系統に残す (残し方の詳細は本 change の論点 4 で扱う)。
5. 自動駆動による計測は捨てるのではなく、CI の受け皿ができた時点で再訪する事項として適用範囲に残す。

## Alternatives Considered

- **退行検出だけをゲートにする**: 却下。有効な基準値が iOS に存在せず作り直しになる上、fixture を変えるたびに校正し直しが要る。過去値が偶然良いと新機能が永久に不合格になる (今回の Android の絶対基準がこれ)。
- **体感の保証と退行検出の両方をゲートにする (現状に近い)**: 却下。校正し直しが常態化し、image-loading で起きた「作って計測して基準に合わず deviation に残す」を再演する。
- **手動操作だけで数値を残さない**: 却下。体感ゲートは不合格を言うには強いが合格の再現性が弱く、数値が無いと後日「合格だった状態」を参照できず、不合格時に worker が原因を追えない。
- **自動駆動を残して足場 (XCTest 以外の駆動) を直す**: 今は採らない。駆動手段の調査から始まり遅く、足場の汚染もゼロにはならない。CI 再訪時の候補として残す。

## Consequences

- 正: 合否が「利用者が感じるか」に直結し、新機能 (画像・セクション) を足すたびに基準を合格できる値へ寄せる誘惑が消える。
- 正: 手動操作中の記録はそれ自体が「自動化なしの対照計測」であり、image-loading で未特定だった大量件数の超過が足場由来かエンジン由来かを切り分けられる。
- 負: 完了判定のたびにオーナーの操作が要る。worker だけでは性能面の完了を報告できない。
- 負: 体感は日や個体で揺れる。証跡に残す数値と参考スケールの取り方 (本 change の論点 3・4) で補う。
- 帰結: 両 handbook の合格基準・固定 fixture・手順の節を書き直す。fixture は機能ごとの Sample デモ画面 (エンジンの土台に触る変更は文字だけの「大量件数」、機能の変更はその機能のデモ画面) とし、件数は 10,000 件のまま保持する。件数を減らす案 (2,000 件) は、本決定の手順を初めて適用した計測で主因が「セクション内の件数に比例する estimated 高さの solver」と分かり、件数を減らすと問題が隠れるため採らない。メモリの「1,000 件と 10,000 件の定常値の件数比」の系統は廃止し、仮想化の証明はテンプレート呼び出しカウンタと自動テストに任せる。
- 帰結: 手動操作の記録が初めて適用された計測 (2026-09-08、iPhone 11) で、自動駆動の足場が主因でないことと、エンジン側の主因 (estimated 高さの solver) が同時に判明した。数値を証跡に残す設計 (決定 2) が原因の帰属を可能にした実例。

## Revisit When

- CI で実機を駆動できる受け皿ができ、自動駆動の足場汚染を測って無視できる水準と分かったとき
- 体感の合否がオーナー以外の判断者に広がり、再現性の担保が数値側に必要になったとき

## 実装後の補足 (2026-09-17)

本決定の手順を出典の変更 (performance-criteria-review) で 3 回運用した (最頻値化のみ 2026-09-15 / 内部セクション分割の試作 2026-09-16 / 最終ビルド 2026-09-17)。proposed の間に確かめられたことを、Context の前提と Consequences の別に記す。

### Context の前提がどう確かめられたか

「自動駆動が体感を測る土俵を汚す」「手動操作 + 計測器の接続なら原因を帰属できる」という前提は 3 回の運用で成り立った。1 回目は体感を不合格と判定して実装を止め、原因をエンジン側 (推定高さの解き直し) に帰属させて提案の改訂へ送り、2 回目 (試作) と 3 回目 (最終) が同じ手順で改訂の効果を確かめている。決定 2 の「数値は合否の説明と次回との比較材料」が、判定ではなく改訂の意思決定に効いた形である。

一方で「合否はオーナーが下す」は 3 回とも守られ、worker が合否を宣言した記録は無い。負の帰結に書いた「完了判定のたびにオーナーの操作が要る」は、実際には 1 回の不合格が change の提案改訂を引き起こす形で現れ、オーナーの操作が判定だけでなく設計の分岐にも乗ることが分かった。

### 運用して分かったこと (帰結ではなく観測)

次の 4 点は実装と計測を通して初めて分かったことで、決定からは導けない。手順としての正は規約 (`kasane/handbook/cross/scroll-performance-gate.md` と platform 別の文書) にあり、ここには本決定の運用実績としてだけ残す。

- 合図の手順 (接続成立を確認してから合図し、オーナーの合図を受けて操作に入る) は 3 回とも成立し、記録窓が操作列を収めきれなかった記録は出なかった
- 起動引数が効いていることを画面の件数表示でオーナーに目視確認してもらう手順が要る。fixture の件数を取り違えた記録は数値ごと無効になるため、合図の前に挟むことにした
- 未判定条件を数値だけでは外せない場合がある。trace に到達件数が残らず、「2,000 件が初回区間で末尾に達したか」は 2 回ともオーナーへの口頭確認で外した
- 体感と数値の食い違いは 3 回とも残った (体感は全段階で引っかかりなし、数値には High の hitch が出る)。決定 1・2 のとおり体感を合否の主語とし、食い違いは証跡にそのまま書いて解消したことにしていない

### 非接続の対照を行わなかった経緯

判定規則 (規約の「判定の 3 状態と再試行」) は、体感に迷ったとき**または体感と数値が食い違ったとき**に計測器を接続しない対照を 1 回行うとしている。3 回の計測でオーナーが体感に迷った場面は無く、食い違いは毎回あったが、非接続の対照は一度も行っていない。試作の申し送りは「最終ビルドでの再計測 (同じ fixture・同じ手順) で兼ねる」とし、最終の記録はその再計測として体感側の再現を確かめたが、計測器を外した走行ではない。

規則の文言と運用がここで離れている。体感が全段階で合格のとき食い違いだけを理由に対照を要求するか、要求するなら誰が発火させるかは、本決定の proposed の間には決まっていない。
