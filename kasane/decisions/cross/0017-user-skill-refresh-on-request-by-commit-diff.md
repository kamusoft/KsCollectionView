## Context

利用者向け Skill (`skills/`) は、`kasane/` とコード・テストから利用者向けに翻訳した派生物である。手で直接育てず、源泉の変更に追従させる (cross/ADR-0005)。cross/ADR-0005 は、追従を担う仕組みの具体を後の決定に委ね、兄弟ライブラリの運用 (対象の一覧・対応表の形・起動の決まり) をそのまま持ち込まないと決めている。

兄弟ライブラリ KsSettingsView の追従は、次の形である。

- 対応表が、源泉の concepts のファイルごとのハッシュと、Skill のファイルへの対応を持つ
- プロジェクト内の専用の Skill が手順を持ち、オーナーが頼んだときだけ動く。CI は、Skill が源泉からずれていることを検査しない
- concepts を分割・改名したときは、対応表のハッシュを手で合わせる。記録済みのハッシュがいつの内容かを知るために、git の履歴と突き合わせた経緯がある
- 検査のスクリプトにテストが無い

本リポジトリの現状は、次のとおりである。

- 源泉になる利用者向けの concepts は 6 枚で、Skill の `references/` の 5 枚とほぼ 1 対 1 に対応する
- `develop` は強制 push を禁じ、`main` へのマージは merge commit だけなので、commit の ID は変わらずに残る
- 作業の手順は handbook のガイドに、機械で行う部分は `scripts/` に置き、スクリプトのテストは検証 CI で流している
- 検証 CI は、`main` 宛ての Pull Request のときだけ走る検査を持てる (cross/ADR-0016)。開発の記録だけを変えた `develop` への push では、検証 CI は起動しない

前提: `develop` の履歴を書き換えない運用が続くこと。源泉と Skill が、変わった分をまとめて追従できる規模であること。兄弟ライブラリが、オーナーの依頼で追従させる運用を続けていること。手順を handbook に、機械で行う部分を `scripts/` に置く置き方が続くこと。

## Decision

利用者向け Skill の追従は、オーナーが頼んだときにだけ行う。検証 CI は、Skill が源泉からずれていることを検査しない。

頼まれたときは、前回追従した commit から今までの、源泉のパスの差分を git で出し、変わった分をまとめて追従させる。覚えておくのは、前回追従した commit の ID 1 つとする。源泉のファイルごとのハッシュは持たない。

手順は handbook のガイドに、差分を出す部分と検査する部分は `scripts/` のスクリプトに置く。プロジェクト内の専用の Skill は作らない。

理由は 3 つある。頼んだときだけにするのは、追従をいつ動かすかの運用を兄弟ライブラリと揃えるためである。commit からの差分を使うのは、源泉のどこがどう変わったかが出るので直す範囲を絞れ、分割・改名を git が追うので記録を手で合わせる作業が起きないためである。handbook と `scripts/` に置くのは、ほかの手順と同じ置き方になり、機械で行う部分が今のスクリプトのテストに乗るためである。

公開 API の名前が Skill から漏れていないことの確かめ方、英語版と日本語版の一致の守り方、Skill の外への参照の扱いは、この決定の外に置く。

## Alternatives Considered

- **`main` 宛ての Pull Request の検査で止める**: 却下。古い Skill のままリリースされることを機械が防げ、日々の push は止まらない。しかし兄弟ライブラリの運用と揃わない。検査を 1 つ作り、機械が合否を出せる形の記録を保つ必要があり、Pull Request を出してから落ちると出し直しになる。
- **`develop` への push ごとに止める**: 却下。蒸留のたびに 2 言語・2 つの Skill を直すことになり、検証 CI の起動の条件も変える必要がある。`develop` は事後に検証する決まり (cross/ADR-0010) と逆向きになる。
- **源泉のファイルごとのハッシュを対応表に持つ (兄弟ライブラリの形)**: 却下。1 枚ごとに追従を進められ、兄弟ライブラリの検査の道具を手直しして使える。しかし分かるのは変わったことだけで、中身は git で見ることになる。源泉を分割・改名したときに、ハッシュと対応を手で合わせる作業が要る。
- **何も覚えず、頼まれるたびに全部の源泉と Skill を突き合わせる**: 却下。毎回すべての枚数ぶんの作業になり、変わっていない文面も揺れやすい。
- **プロジェクト内の専用の Skill に手順をまとめる (兄弟ライブラリの形)**: 却下。名前で呼べるので起動は確実で、兄弟ライブラリと揃う。しかし手順の置き場が 1 つ増え、Skill の中のスクリプトは今のスクリプトのテストの対象の外になる。

## Consequences

- 正: 作るものが追従の手順とスクリプトだけで済み、検証 CI に検査が増えない。
- 正: 追従をいつ動かすかの運用が、兄弟ライブラリと揃う。
- 正: 追従のときに、源泉のどこがどう変わったかが差分で分かる。
- 正: 源泉を分割・改名しても、記録を手で合わせる作業が起きない。
- 正: 追従のスクリプトが、ほかのスクリプトと同じテストで確かめられる。
- 負: 頼み忘れると、古い Skill のままリリースされ得る。機械は止めない。
- 負: 一部だけを追従させて、残りを次回に回すことができない。
- 負: 追従には git の履歴が要る。履歴を持たない写しや、浅い clone では動かない。
- 負: 記録の形と手順の置き場が兄弟ライブラリと違うので、兄弟ライブラリの道具をそのまま使い回せない。
- 負: 名前で呼ぶ専用の Skill に比べて、手順が読まれないまま作業される余地が残る。
