## Context

利用者向け Skill (`skills/`) は、`kasane/` とコード・テストから利用者向けに翻訳した派生物である。手で直接育てず、源泉の変更に追従させる (cross/ADR-0005)。

追従の仕組みは、cross/ADR-0017 が次のように決めていた。追従はオーナーが頼んだときにだけ行い、検証 CI はずれを検査しない。前回追従した commit からの源泉の差分で、変わった分を見分ける。手順は handbook のガイドに、差分を出す部分と検査する部分は `scripts/` のスクリプトに置き、プロジェクト内の専用の Skill は作らない。専用の Skill を却下した理由は、手順の置き場が増えることと、Skill の中のスクリプトがスクリプトのテストの対象の外になることだった。名前で呼べないことによる起動の不確かさは、`skills/` を触る作業でガイドが必ず読まれるようにして補うとしていた。

その後に確かめたところ、次のことが分かった。

- handbook の索引を作業の前に開く決まりがあるのは、コード・テストに触れるワーカー (実装・UI の実装・レビュー・ライブ調整) だけである。オーナーの依頼を受けるメインのセッションには、その決まりが無い。AGENTS.md・追従の記録・道具のスクリプトにも、ガイドを指す記述が無い。追従を頼んでも、手順にたどり着く保証が無い
- どの作業をどのワーカーに任せるかを決めるのは、メインのセッションである。ワーカーのモデルは、ハーネスの器の定義が決め、呼ぶ側は器を選ぶ。メインに読まれない handbook のガイドは、この任せ方を持てない。今のガイドも、ワーカーへの任せ方を書いていない
- 兄弟ライブラリ KsSettingsView の追従の Skill は、メインのセッションでは機械的な確かめだけを行い、Skill の書き直しを低コストのモデルのワーカーに、1 つの Skill の英語版と日本語版をまとめて任せている。Skill の実体は 1 つの置き場に置き、もう 1 つの CLI の置き場からはリンクで指している
- 専用の Skill を却下した 2 つの理由は、実体を 1 つにしてリンクで指す置き方と、スクリプトを `scripts/` に置いたまま Skill から呼ぶ形で、どちらも小さくできる

前提: `develop` の履歴を書き換えない運用が続くこと。源泉と Skill が、変わった分をまとめて追従できる規模であること。兄弟ライブラリが、オーナーの依頼で追従させる運用を続けていること。メインのセッションが、器を指定してワーカーを呼べる実行環境であること。

## Decision

cross/ADR-0017 の決定を、全体として本決定で置き換える。

利用者向け Skill の追従は、オーナーが頼んだときにだけ行う。検証 CI は、Skill が源泉からずれていることを検査しない。頼まれたときは、前回追従した commit から今までの、源泉のパスの差分を git で出し、変わった分をまとめて追従させる。覚えておくのは、前回追従した commit の ID 1 つとし、源泉のファイルごとのハッシュは持たない。

追従は、プロジェクト内の専用の Skill から始める。Skill は、メインのセッションが行う進め方と、Skill の書き直しのような実作業をどの器のワーカーに任せるかを持つ。ワーカーのモデルは、ハーネスの器の定義に従う。差分を出す部分と検査する部分は、`scripts/` のスクリプトに置き、Skill から呼ぶ。

専用の Skill にするのは、名前で呼べるので頼んだときに手順にたどり着けるためと、ワーカーへの任せ方を持てるので実作業をメインより低コストのモデルの器に任せられるためである。頼んだときだけにするのは、追従をいつ動かすかの運用を兄弟ライブラリと揃えるためである。commit からの差分を使うのは、源泉のどこがどう変わったかが出るので直す範囲を絞れ、源泉を分割・改名しても、ファイルごとのハッシュを合わせ直す作業が起きないためである。スクリプトを `scripts/` に置くのは、スクリプトのテストに乗せ続けるためである。

Skill が持つのは、進め方とワーカーへの任せ方までとする。道具の出力の読み方・直し方・確かめ方の基準といった手順の中身と、利用者向け Skill の書き方の決まりは、handbook に置き、Skill はそれを読ませる。開発者向けの規範・手順を handbook に置く決まり (cross/ADR-0005) を保つためである。

どのワーカーに何を任せるかは、この決定の外に置く。公開 API の名前が Skill から漏れていないことの確かめ方、英語版と日本語版の一致の守り方、Skill の外への参照の扱いも、この決定の外に置く。

## Alternatives Considered

- **手順を handbook のガイドに置き、専用の Skill は作らない (cross/ADR-0017 の形)**: 却下。ほかの手順と同じ置き方で、スクリプトはテストに乗る。しかしメインのセッションには handbook を読む決まりが無く、頼んでも手順にたどり着く保証が無い。ガイドはワーカーの呼び分けを持てず、実作業を低コストのモデルに任せられない。
- **AGENTS.md に、追従のガイドを指す 1 行を足す**: 却下。AGENTS.md はセッションの始めに読まれるので、手順にはたどり着ける。しかしワーカーの呼び分けは、ガイドに置くのと同じく持てない。
- **`main` 宛ての Pull Request の検査で止める**: 却下。古い Skill のままリリースされることを機械が防げ、日々の push は止まらない。しかし兄弟ライブラリの運用と揃わない。検査を 1 つ作り、機械が合否を出せる形の記録を保つ必要があり、Pull Request を出してから落ちると出し直しになる。
- **`develop` への push ごとに止める**: 却下。蒸留のたびに 2 言語・2 つの Skill を直すことになり、検証 CI の起動の条件も変える必要がある。`develop` は事後に検証する決まり (cross/ADR-0010) と逆向きになる。
- **源泉のファイルごとのハッシュを対応表に持つ (兄弟ライブラリの形)**: 却下。1 枚ごとに追従を進められ、兄弟ライブラリの検査の道具を手直しして使える。しかし分かるのは変わったことだけで、中身は git で見ることになる。源泉を分割・改名したときに、ハッシュと対応を手で合わせる作業が要る。
- **何も覚えず、頼まれるたびに全部の源泉と Skill を突き合わせる**: 却下。毎回すべての枚数ぶんの作業になり、変わっていない文面も揺れやすい。

## Consequences

- 正: 追従の手順を名前で呼べ、頼んだときに手順にたどり着ける。
- 正: Skill の書き直しのような実作業を、低コストのモデルの器に任せられる。そのモデルは、Skill を変えずに器の定義で変えられる。
- 正: 追従をいつ動かすかの運用と、手順を専用の Skill に置く形が、兄弟ライブラリと揃う。
- 正: 追従のときに、源泉のどこがどう変わったかが差分で分かる。源泉を分割・改名しても、ハッシュを合わせ直す作業は起きない (名前の変わった源泉の記録のパスは、追従のときに直す)。
- 正: 検証 CI に検査が増えず、追従のスクリプトは、ほかのスクリプトと同じテストで確かめられる。
- 負: 手順の置き場として Skill が 1 つ増え、2 つの CLI から呼べるようにする手当てが要る。
- 負: 頼み忘れると、古い Skill のままリリースされ得る。Skill にしても、頼まれなければ動かず、機械も止めない。
- 負: 一部だけを追従させて、残りを次回に回すことができない。
- 負: 追従には git の履歴が要る。履歴を持たない写しや、浅い clone では動かない。
- 負: 記録の形が兄弟ライブラリと違うので、兄弟ライブラリの道具をそのまま使い回せない。
