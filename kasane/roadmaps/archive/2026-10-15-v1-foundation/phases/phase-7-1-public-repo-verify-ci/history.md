## 2026-10-08: 論点 0 — このフェーズを分けるか

論点が 7 つになり、申し送りの中の決めごとを数えると分割を検討する目安 (8 個) に届いたため、中身の議論より先に諮った。

| 案 | 内容 | 評価 |
|---|---|---|
| A: 今分ける (採用) | 決定事項が無いうちに ksn-split で分ける | 配り直すのが論点だけで済む。進める順番を行順で表せる |

採用の理由は、決定事項がまだ 0 件で今がいちばん安く分けられること、進める順番 (公開の前提と検証 CI が先、配布がその次、ドキュメントの本体は並行) がはっきりしていること、1 フェーズ = 1 変更の原則に収まらないことの 3 つ。分け方の見立ては「公開の準備と検証 CI / 配布とリリース / 利用者ドキュメント」で、分割・昇格・整理のどれにするかは ksn-split が判定する。ADR には当たらない (作業の進め方の決定)。

## 2026-10-08: 論点 1-a — 今の履歴をそのまま公開するか

公開の前提を、履歴の扱い (1-a)・ブランチの役割 (1-b)・外部からの PR の扱い (1-c) に分けて順に諮ることにし、まず 1-a を決めた。

翻案元は公開リポジトリを新しく作り、作業ツリーを最初の 1 commit にした (`../KsSettingsView/kasane/decisions/cross/0021-public-repository-fresh-start.md`)。理由は、履歴に個人のメールアドレスと約 1,000 行のローカル絶対パスが残っていたことである。同じ理由がこのリポジトリにあるかを実測した。

| 確かめたこと | 結果 |
|---|---|
| 規模 | 73 commit、pack 約 30 MB |
| 作者・コミッターのメールアドレス | noreply の 1 種類だけ |
| 履歴の中身 (最初の commit の次から先頭まで) を `scripts/git-gate-lint.py --range` で検査 | 違反 0 件 |
| 最初の commit の中身と、全コミットメッセージのローカル絶対パス・メールアドレス | 0 件 |
| 履歴に残る証跡の画像 | 約 100 件・33 MB (`kasane/changes/` 配下。作業ツリーには無い) |
| gitleaks 8.30.1 で履歴全体を走査 (決定の後に試した) | 70 commit を走査して検出 0 件 |

| 案 | 内容 | 評価 |
|---|---|---|
| A: そのまま公開 (採用) | remote を足して push する | 経緯が公開側に残り、作業が最小。過去の証跡の画像は公開されるので、事前の目視が要る |
| B: 作り直して 1 commit で公開 | 翻案元と同じ | 画像は公開されず、兄弟ライブラリと揃う。経緯が公開側から辿れず、開発の場所を移す作業が要る |
| C: 画像だけ履歴から除いて公開 | 履歴を書き換える | 画像は公開されず、経緯も残る。書き換えの確認が要り、commit の ID が変わる |

オーナーは A を選び、あわせて gitleaks の導入を指示した。A を推した理由は、翻案元が作り直した理由がここでは 0 件であること、最初の commit から公開前提の検査が入っていること、証跡の画像は今後も履歴に入り続けるので過去の分だけ除いても性質が変わらないことの 3 つ。

gitleaks の導入は、公開の直前に履歴全体へ掛けることと、公開後も検査として使い続けることの両方と受け取った (後者は議論側の解釈)。置き場所 (CI の検査・手元の hook) は検証 CI の構成の論点で決める。翻案元は CI の lint の中で、追跡中の内容だけを取り出して走査している。

そのまま公開すると、追跡中のすべて (`kasane/`・`.claude/settings.json`・`.codex/hooks.json`・`.githooks/` を含む) が公開される。ADR は cross/ADR-0009 を proposed で起票した。ライセンスの種類が未決だったので、論点 1-d として足した。

## 2026-10-08: 論点 1-b — ブランチの役割

今は `main` の 1 本だけで、作業用のブランチを手元で `main` にマージしている。翻案元は `develop` (日々の開発。直接 push、検証は事後) と `main` (`develop` からの PR だけ。リリースの起動元) の 2 本で、当初の「どちらにも PR と検証」が 1 マージあたり macOS ランナー約 54 分だったため整理した (`../KsSettingsView/kasane/decisions/cross/0028-ci-triggers-by-branch-role.md`)。翻案元の GitHub 上の既定ブランチは `main` (GitHub の API で確認)。

| 案 | 内容 | 評価 |
|---|---|---|
| A: `develop` と `main` の 2 本 (採用) | 翻案元と同じ | `main` 宛ての PR がリリースの節目になる。日々の push は待たない。workflow と手順を流用できる。`develop` を作る切り替えが要る |
| B: `main` 1 本 | 開発もリリースも `main` | 今の運用のまま。節目が無く、壊れた状態が `main` に載り得る。トリガーとリリースノートの作り方を作り直す |
| C: `main` 1 本で PR 必須 | 自分の PR を必須にする | 壊れた状態は載らない。PR ごとに検証を待ち、節目として細かすぎる |

オーナーは A を選んだ。ADR は cross/ADR-0010 を proposed で起票した。`main` 宛ての PR で何を確かめ、何をリリースノートの材料にするかは、検証 CI・配布・リリースの各論点で決める。

## 2026-10-08: 論点 1-c — 外部からの PR の扱い

翻案元は外部からの PR を受け付けず、貢献を Issue で受けている (`../KsSettingsView/kasane/decisions/cross/0024-contributions-via-issues-no-external-pull-requests.md`)。理由は AI が生成した粗い提案の流入防止とレビューの負荷で、PR を完全に無効にしないのはオーナー自身の `main` 宛て PR が作れなくなるため。

| 案 | 内容 | 評価 |
|---|---|---|
| A: 受けずに Issue で受ける (採用) | PR を作れる人を共同作業者に限る | 変更フローの外から実装が入らない。1-b の決定がそのまま成り立つ。コードで貢献したい人の道は無い |
| B: 外部の PR を受ける | 通常の OSS の形 | 貢献の道がある。文脈の無い実装のレビューと、`develop` 宛ての PR と検証が要る |
| C: README で断るだけ | GitHub の設定は変えない | 来た PR をその都度閉じる手間が残る |

オーナーは A を選んだ。細部は翻案元のまま (Issue のフォームは英語で 3 本、貢献の案内は英日 2 枚、Discussions は開かない) を既定として示し、変更の指示は無かった。ADR は cross/ADR-0011 を proposed で起票した。

公開の前提に、リポジトリをいつ public にするか (1-e) が残っていたので論点に足した。

オーナーは A を選んだ。ADR は cross/ADR-0012 を proposed で起票した。

## 2026-10-08: 論点 1-e — リポジトリをいつ public にするか

| 案 | 評価 |
|---|---|
| A: 最初から public で作る (採用) | `main` の保護が最初から使え、標準のランナーは無料。README が無い期間も見える。公開前の確認は最初の push の前に済ませる |
| B: 非公開で作り、後で切り替える | 準備中の姿は見えない。public にするまで `main` の保護が使えず、検証 CI が利用枠を使う。切り替えのときに設定を入れ直す |

## 2026-10-08: 論点 3-a — CI が走らせる範囲

検証 CI の論点を、走らせる範囲 (3-a)・実機が要るテストと性能計測の受け皿 (3-b)・macOS のランナーと Xcode の版 (3-c)・lint の中身 (3-d)・構成とトリガーの細部 (3-e) に分けた。

テストは 4 系統で、手元の完了判定では毎回すべてを流す (cross/ADR-0008)。iOS Sample はユニットテスト 37 件と UI テスト 11 件。翻案元は CI の緑が保証する範囲を「ロジックの全件通過と配線のコンパイル」までとし、アプリを起動する確認を CI に載せていない (`../KsSettingsView/kasane/decisions/cross/0026-ci-guarantee-logic-and-wiring-not-e2e.md`)。

| 案 | 評価 |
|---|---|
| A: 4 系統すべて | CI の緑が手元の完了判定と同じ意味になる。UI テストが CI で止まると `main` 宛ての PR が進まない。ランナーの時間がいちばん長い |
| B: 本体は全件、Sample は UI テスト以外 (採用) | Sample のビルドとモデルの崩れは CI で気付ける。画面の操作の崩れは手元で気付く |
| C: 本体の 2 系統だけ | ランナーの時間はいちばん短い。Sample が壊れても CI では気付けない |

オーナーは B を選んだ。ADR は cross/ADR-0013 を proposed で起票した。3-b の結論が保証範囲に掛かる場合は、同じ ADR に書き足す。

## 2026-10-08: 論点 3-b — 実機が要るテストと性能計測の受け皿

phase-8 の申し送り (実機が要るテストの受け皿を CI に含めるか) と phase-2 の申し送り (性能計測の CI での自動化の再訪) を、同じ論点として扱った。

対象は 3 つ。Android の端末で走らせるテスト (`android/kscollectionview/src/androidTest/` の画像のデコードの 4 件。申し送りの時点では 3 件)、iOS の性能検証 (基準機をオーナーが手で操作し、体感で合否)、Android の性能検証 (基準機で人の操作なしに計測できる)。性能の合否は体感で決め、数値に合格線を置かない (cross/ADR-0006)。翻案元は CI でエミュレータも実機も使わない。

| 案 | 評価 |
|---|---|
| A: CI には載せない (採用) | 維持するものが無く、初回リリースに影響しない。端末のテストの流し忘れを CI は止めない |
| B: 端末のテストだけ CI のエミュレータで | 毎回走る。エミュレータが実機と同じ振る舞いをするかは未確認で、起動が不安定さの元になる |
| C: 組織の Mac mini に基準機をつなぐ | 実機で毎回走り、Android の性能は自動で測れる。基準機の常時接続と、public のリポジトリに自前のランナーをつなぐための絞り込みが要る |

オーナーは A を選んだ。cross/ADR-0013 (proposed) を書き直して、この結論を含めた (タイトルを「端末を使わないライブラリのテスト」に改めた)。申し送りの 2 項目は論点から外した。

確かめて分かったこと: 端末のテストの流し方は handbook に書かれていない (書かれているのは計測用の `:benchmark:connectedBenchmarkAndroidTest` だけ)。手元の完了条件に残すと決めたので、流し方と流す時点を handbook に書くことを TODO に足した。

## 2026-10-08: 論点 3-c — macOS のランナーと Xcode の版

GitHub の標準のランナーは `xcode-27` (Xcode 27、iOS 27.0 の Simulator だけ、public preview) と `macos-26` (Xcode 26.0.1〜26.6、正式提供)。手元は Xcode 27.0 だけ (Swift 6.4) で、Simulator の OS は iOS 17.5 / 18.6 / 26.0 / 27.0 がある。翻案元は開発機が替わって Xcode 27 だけになったため、2026-10-04 に `xcode-27` へ揃えた。

議論側は、パッケージの定義が Swift 6.2 のツールから使えると宣言している (`ios/Package.swift`) のに、Xcode 26 でのビルドを誰も確かめていない点を挙げた。

| 案 | 評価 |
|---|---|
| A: Xcode 27 だけ (採用) | 手元と同じ環境で、macOS のジョブは 1 本。Xcode 26 の利用者がビルドできるかは確かめない |
| B: Xcode 27 でテスト、Xcode 26 でビルドだけ | Xcode 26 のビルドを毎回確かめる。ジョブが 2 本になり、初回に通らない可能性がある |
| C: Xcode 26 だけ | 正式提供のランナーだけで済む。手元と違うので、CI だけで落ちると再現できない |

議論側の推奨は B だったが、オーナーは A を選んだ (理由の言及は無い)。ADR にはしていない (ランナーの選び方は設定で、後から変えられる)。Xcode 26 を確かめないので、対応する Xcode をどう案内するかが配布物の形と README の議論に残る。

## 2026-10-08: 論点 3-d・3-e — lint の中身と、構成・トリガーの細部

どちらも、ここまでの決定 (ブランチの役割・CI が走らせる範囲・ランナー) と翻案元の形から決まり、案の間で比べる軸が残らなかったため、選択肢を諮らずに議論側の既定として決定事項に書いた。オーナーには既定として報告し、見直すかどうかをフェーズの終わり方とあわせて尋ねた。

gitleaks の置き場所について確かめたこと: 手元の commit 時の hook (`.githooks/pre-commit`) は Kasane の標準で、gitleaks が入っていればステージした内容を走査する。この clone では `core.hooksPath` が `.githooks` で、gitleaks 8.30.1 が入っているので、既に動いている。したがって新しく足すのは CI の lint のジョブだけになる。1-a で「gitleaks による検査は未実施」と報告したのは履歴全体の走査のことで、commit 時の走査は別に動いていた。

翻案元の lint のジョブは 19 step で、うち本フェーズに当たるのは 5 つ (PR の head の検査・gitleaks・ローカル絶対パス・識別子・コメント規約)。残りは README の例の検査 (利用者ドキュメントのフェーズ) と、配布・リリースのスクリプトのテスト (配布物の形・リリースのフェーズ) で、それぞれのフェーズが足す。

検証 CI の構成 (再利用 workflow と入口、リリースからも同じ検証を呼ぶ) は ADR の候補だが、オーナーが既定を確かめていないので起票していない。
