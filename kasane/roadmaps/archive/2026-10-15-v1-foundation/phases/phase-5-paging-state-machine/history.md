## 2026-09-26: 論点の統合

元の 6 論点と各フェーズ (phase-1・phase-3・phase-4) の申し送りを合わせると 9 前後になるため、固定番号の 7 論点 (状態の契約の細部 / 追加読み込みの発火条件 / 多重発火と連鎖の抑止 / Pull to Refresh の接続 / 標準の表示部品の範囲 / グループとの組み合わせ / タップのフィードバック色の意味論) に統合した。元の論点「Paging 3 依存か自前か」は core/ADR-0005 (accepted) の帰結として自前が既定路線のため、状態の契約の論点の中で確認する。端への挿入による連鎖 (phase-4 申し送り) は多重発火の抑止と同じ仕組みで扱うため同じ論点にまとめた。発火・抑止・Pull to Refresh・表示部品はいずれも状態の意味に依存するため、状態の契約の細部を先に扱う。

## 2026-09-26: 状態の契約の細部 — 失敗の中身

ライブラリが見分けて出し方を変える場面は、初回の読み込み中・初回の読み込みの失敗・空・追加読み込みの失敗・項目があるときの取り直しの失敗。選択肢: A 失敗は中身を持たず、状態と項目が空かどうかでライブラリが出し方と再試行の行き先を決める / B 失敗に「取り直し / 次のページ」のどちらの失敗かを持たせる / C 失敗にエラーの値を持たせる。判断の軸は、VM が失敗時に書くもの、再試行の行き先、項目があるときの取り直しの失敗の扱い、エラーの中身の表示、状態の比較と Kotlin の型、KMP の共有 VM からの写しやすさ、core/ADR-0005 との関係。B は項目があるときの取り直しの失敗を末尾に出すしかなく不自然さが残るため、失敗の状態にしないガイドはどのみち要る。C は Swift で状態どうしの比較が自動で成り立たなくなり、エラーの型の橋渡しが要る。どちらも Kotlin は enum ではなくなる。

採用: A (オーナー決定)。エラーの文言は差し替えたテンプレートが VM から読む。ADR: core/ADR-0019 (proposed)。

元の論点「Paging 3 依存か自前か」は、core/ADR-0005 が却下した「ライブラリがページング全体を内包する」案の理由 (データの所有がライブラリに移り、KMP の共有 VM と組み合わせにくい) が今も成り立つため、選択肢を出さずに「Paging 3 には依存しない」と記録した (オーナーに報告)。論点 1 はこれで完了。

## 2026-09-26: 追加読み込みの発火条件 — 「末尾に近い」の測り方

旧 AiForms の `LoadMoreMargin` は「表示中のいちばん後ろの項目より後の残りが N 件以下」の件数の意味 (Android 版は件数、iOS 版は件数を距離に換算。既定値は 0)。今のコードは画像の先読みで、画面に実際に出ている項目の範囲を両プラットフォームで取っており (Android は見出し・フッターを除いた項目の添字)、画面外を前もって組み立てる影響を受けない。選択肢: A 残りの項目数 / B 末尾までの残りの距離 / C 末尾が見えたら。判断の軸は、両プラットフォームで同じ意味で測れるか、画面外を前もって組み立てる影響、旧 `LoadMoreMargin` との対応、グリッドの列数による違い、読み込み中の表示が見える頻度、見出し・フッターの影響。B は Android の Lazy 系がまだ並べていない項目の高さを知らず、末尾が近づくまで見積もりになる。C は毎ページ読み込み中を見せる。

採用: A (オーナー決定)。ADR は、しきい値の既定値と公開の有無が決まってから 1 本にまとめる (数え方だけならライブラリ内部の可逆な選択で、しきい値を公開するとその単位が公開契約になるため)。

## 2026-09-26: 追加読み込みの発火条件 — しきい値の既定値

しきい値の役目は読み込み中の表示を見せずに次のページを間に合わせることで、効くのは末尾の手前どれだけの距離で発火するか。ページの件数ぶん手前 (Paging 3 の既定) はページの件数をライブラリが知らないため対象外。選択肢: A 1 画面分 (今画面に出ている項目の数) / B 固定の件数 (例: 5 件) / C 0 件 (旧 AiForms の既定、最後の項目が見えたら)。判断の軸は、列数・向き・項目の大きさが変わったときの発火の位置、読み込み中の表示が見える頻度、説明と予測のしやすさ、旧 AiForms からの移行。B は 4 列なら末尾の 1 行強手前、半画面のカードなら 2.5 画面手前と、発火の位置が大きく変わる。C は毎ページ読み込みを待たせる。

採用: A (オーナー決定)。向き可変のグリッド (core/ADR-0006) でも発火の位置がずれない。

## 2026-09-26: 追加読み込みの発火条件 — しきい値の公開

既定の 1 画面分でたいていは足りるが、次のページの取得にかかる時間はアプリの API ごとに違いライブラリには分からない。旧 AiForms (`LoadMoreMargin`) と Paging 3 (`prefetchDistance`) はどちらもこの値を公開している。選択肢: A 公開しない / B 画面数で指定できる / C 件数で指定できる。判断の軸は、取得の遅い API のアプリへの手当て、指定したあとの列数・向きの影響、旧 `LoadMoreMargin` からの移行、公開 API・ドキュメント・テストの増え方、後から変えるときのコスト。C は旧の値を移せるが、指定した時点で固定の件数と同じ弱点 (列数・項目の大きさで発火の位置がずれる) が戻る。

採用: B (オーナー決定)。オーナーの補足: 0 だと底に到達してから読み込む。測り方に当てはめて「最後の項目が画面に入ったら頼む」と記録した (ルートのフッターは数えないため、フッターが見える少し前に発火する)。発火条件 (測り方・既定値・公開) をまとめて ADR: core/ADR-0020 (proposed) を起票した。論点 2 はこれで完了。

## 2026-09-26: 多重発火と連鎖の抑止 — 末尾への追従との関係

core/ADR-0018 (accepted) をそのまま適用すると、一番下で読み込み中の表示を見ているところへ次のページが届いたとき、表示範囲が新しい末尾まで送られて届いたページを飛ばし、また末尾にいるので最後のページまで読み込みが連鎖する。末尾への追従は両プラットフォームとも「差し替えの直前に末尾にいて末尾に項目が入ったか」を 1 か所で判定しており、例外を足す費用は小さい。ADR の衝突時の手順に従い、従う案と改訂案を並べた。選択肢: A 続きがあるうちは (差し替えの直前の状態が終端以外なら) 末尾に追従しない / B ページングを付けたら末尾の追従を一切しない / C 追加読み込みで足された項目だけ追従しない / D ADR-0018 のまま。判断の軸は、末尾にいるときに届いたページの見え方、読み込みの連鎖、一覧がそろった後に末尾へ足した項目、続きがある間の読み込み以外の末尾への追加、判定の確かさ、改訂の費用。B はそろった一覧の末尾への追加が下に外れて見えない。C は VM が配列と状態を書き換える順番やタイミングで見分けを誤る。D はページを飛ばして連鎖する。

採用: A (オーナー決定)。直前の状態で判定するため、最後のページが届くのと同時に終端になっても飛ばさない。先頭側は変えない。ADR: core/ADR-0021 (proposed、amends ADR-0018)。

## 2026-09-26: 多重発火と連鎖の抑止 — 頼んだ後の待ち方

ライブラリは待機で末尾に近いときだけ頼むが、VM が状態を追加読み込み中に書き換えるのが遅れる書き方 (VM のスコープに起動した処理の中で待ってから書き換える等) では、その間も待機に見えて二重に頼む。DSL サンプルでは頼む処理が Swift は非同期のクロージャ、Kotlin は普通の関数でずれており、Pull to Refresh の Kotlin 側は phase-3 で非同期関数にそろえてある。選択肢: A 頼む処理を両方とも非同期関数にし、処理が終わるまでと状態か配列が変わるまでの両方を待つ / B Kotlin は普通の関数のまま、状態か配列が変わるまで待つ / C 状態だけで判断し待たない。判断の軸は、VM が状態の書き換えを遅らせたとき、頼む処理の形、VM の書き方の自由、取り直しで追加読み込みを取り消す手段、VM が頼みを無視したとき、画面を離れたとき。B は Swift・Pull to Refresh と形がずれ、Kotlin に取り消しの手段が無い。C は VM 側で必ず弾く必要がある。

採用: A (オーナー決定)。Kotlin は普通の関数もそのまま渡せるため VM の書き方を縛らない。ADR: core/ADR-0022 (proposed)。議論の過程で、DSL サンプルの VM が待機のときだけ読み込むため失敗の状態で再試行を押しても何も起きないことに気づき、Sample の VM を直す TODO を積んだ。

## 2026-09-26: 多重発火と連鎖の抑止 — 判定し直すきっかけと初回の読み込み

判定し直すきっかけは、スクロールだけだと 1 ページが画面に満たない一覧が止まるため、スクロール・配列の差し替え・状態の変化・一覧の大きさの変化とする (選ぶ余地のない前提として記録)。すると項目が空で待機のときは残り 0 件で発火条件を満たす。選択肢: A 空でも頼む (初回の読み込みも追加読み込みの処理で始まる) / B 空のときは頼まず、初回の読み込みは VM が始める / C 空のときは取り直しとして頼む。判断の軸は、VM が書くこと、VM が自分でも最初の読み込みを始めたとき、続きありのまま空のページが返ったとき、空の表示を出す状態、取り直しの処理を渡していない一覧。B を推奨した (VM が状態の持ち主で普通のアプリは画面を開いたときに読み込む、A は二重の読み込みと空のページでの頼み続けが起きうる)。

採用: A (オーナー決定)。VM は最初の読み込みを書かずに済む。二重の読み込みと空のページでの頼み続けは利用者向けガイドで注意する (TODO)。新しい ADR は起こさず、発火条件の一部として core/ADR-0020 (proposed) を書き直して含めた。初回の読み込みが追加読み込みの処理で始まるため、取り直しの処理を渡していない一覧で空で失敗したときの再試行の行き先 (core/ADR-0019 は取り直しとした) を論点 5 に積んだ。

## 2026-09-27: 多重発火と連鎖の抑止 — 取り直しと追加読み込みの競合

取り直し中は状態が待機でないため追加読み込みは始まらない (core/ADR-0022)。残るのは、追加読み込みの途中で先頭へ戻って Pull to Refresh をしたとき、取り直し後の一覧に古いページが遅れて混ざる向き。選択肢: A 追加読み込みの間は Pull to Refresh を受け付けない / B 取り直しが始まったら追加読み込みを取り消す / C ライブラリは何もせず VM に任せる。判断の軸は、古いページが混ざるか、VM に求めること、利用者の操作、実装。B は VM が取り消しを失敗として拾うと (Swift の `catch`・Kotlin の `runCatching`) 取り直し中の状態を失敗で上書きして壊れ、VM のスコープで起動する書き方には届かない。C は防ぐ責任がすべて VM にかかる。ぶつかる時間は追加読み込みの 1〜2 秒程度で、その間引っ張れなくても実害は小さい。事前に material3 1.4.0 を確かめ、`PullToRefreshBox` には引っ張りを止める設定が無く、土台の修飾 `Modifier.pullToRefresh` には有効 / 無効の引数があることを確認した。

採用: A (オーナー決定)。Android は phase-3 で決めた外形 (`PullToRefreshBox` で包む) を改め、土台の修飾とインジケータで組む。ADR: core/ADR-0023 (proposed)。core/ADR-0022 (proposed) の footer に関連行を足した。

## 2026-09-27: 多重発火と連鎖の抑止 — 取り直しのときの表示範囲の位置

Pull to Refresh は先頭で引っ張るので core/ADR-0018 の先頭側の留め方で先頭が見え続ける。問題は途中までスクロールしているときに VM が取り直し (絞り込みの変更・再読み込みのボタン等) をした場合で、一覧が 1 ページ目に差し替わると、iOS はコンテンツの位置を保って新しい末尾に張り付き、Android は見ていた項目が無ければ同じ番号の位置 (末尾寄り) に寄り、どちらもすぐ追加読み込みが始まる。見ていた項目が残っていれば、Android は項目を、iOS は位置を保ち、見える場所がずれる。選択肢: A 差し替えの直前の状態が取り直し中なら先頭を表示する / B 各プラットフォームの既定のまま (先頭に戻したいアプリはスクロール制御で戻す) / C 見ていた項目が残っていれば保ち、無ければ先頭。判断の軸は、途中で取り直したときに見える場所、末尾に張り付いてすぐ読み込みが始まるか、Pull to Refresh のとき、位置を保ちたい VM、予測のしやすさ、実装。B は両プラットフォームで結果がずれ、末尾に張り付くことがある。C は留まるか戻るかがページの境目しだいで予測しにくく、iOS に項目を基準に位置を保つ仕組みが要る。

採用: A (オーナー決定)。見える形の取り直しは「最初から見直す」意味で、位置を保ちたい VM は状態を取り直し中にせず配列だけを差し替える。新しい ADR は起こさず、同じく ADR-0018 を amends する core/ADR-0021 (proposed) を「ページングを付けた一覧では、差し替えの直前の状態で表示範囲の置き方を決める」ADR に書き直してまとめた (ファイル名も改めた)。論点 3 はこれで完了。

## 2026-09-27: Pull to Refresh の接続 — 引っ張っていない取り直しのインジケータ

iOS は SwiftUI 標準の `.refreshable { await }` を環境値として受け取り、ライブラリが引っ張りの部品を付ける (選ぶ余地なし)。決めどころは phase-3 で Android に決めた「インジケータは処理の実行中、または状態が取り直し中なら出す」の後半で、引っ張っていないのに取り直し中になるのは VM が自分で取り直したとき。途中までスクロールしていると、Android はインジケータが一覧の上端に重ねて見え、iOS は引っ張りの部品がコンテンツの上の外側にあるため見えない (先頭でもプログラムから出すには位置の調整が要る)。選択肢: A 取り直し中ならいつでも出す (phase-3 のまま) / B 引っ張ったときだけ出す / C 取り直しが始まったら先頭へ戻して出す。B を推奨した (両プラットフォームでそろい、iOS の癖を避けられる)。

オーナーの応答: Pull to Refresh はプラットフォームの自然な形のままでよく、ここまで無理にそろえると不自然。これを「iOS は引っ張ったときだけ、Android は VM が始めた取り直しでも上端に出す」と受け取って確認したところ、オーナーは「そういうことなら違う」とし、確認の選択肢から「Android も引っ張ったときだけ出るのが自然な形」を選んだ。

採用: 両プラットフォームとも引っ張って始めた取り直しの間だけインジケータを出す (結果は B と同じ。理由は両プラットフォームの自然な形であること)。引っ張った後は、VM の処理がすぐ戻る書き方でも状態が取り直し中の間は出し続ける (B で示した細部。phase-3 の後半の条件を狭めて残す)。VM が始めた取り直しの見せ方は論点 5 に積んだ。ADR は、追加読み込みの間は引っ張れない決定と合わせて core/ADR-0023 (proposed) を「Pull to Refresh とページングの状態の連動」に書き直してまとめた (ファイル名も改めた)。論点 4 はこれで完了。

## 2026-09-27: 標準の表示部品 — 何も指定しないときに用意する表示の範囲

最初の提示で「末尾」「全体」という言い方をしたところ、オーナーから意味が分からないと指摘があり、画面のイメージ (項目が並んでいるときはいちばん下の項目のすぐ下に小さく出る 3 つ、項目が 1 件もないときは一覧の真ん中に大きく出る 3 つ) を描いて言い直した (artifacts/standard-displays.md)。選択肢: A 6 つ全部を用意する / B 項目が並んでいるときの 3 つだけ用意する (0 件のときはその小さな表示が上端に出る) / C 読み込み中と失敗の 4 つだけ用意する (終端と空は渡したときだけ。何も渡さないと 0 件の一覧は真っ白で、core/ADR-0005 の終端の表示も改める)。判断の軸は、何も指定しないときの見え方、終端の表示、翻訳が要る文言の数、ADR-0005 との関係、実装とテストの量。スケルトン表示はライブラリがセルの形を知らないため、どの案でも用意しない。

採用: A (オーナー決定)。どれも差し替えられる。ADR は論点 5 の残り (VM が始めた取り直しの見せ方・再試行の行き先・差し替えの形・文言) が決まってから 1 本にまとめる。

## 2026-09-27: 標準の表示部品 — VM が自分で取り直している間の表示

Pull to Refresh のインジケータは VM が始めた取り直しでは出さないと決めたため (core/ADR-0023)、項目が並んだまま待っている間にライブラリが何か出すかを、画面のイメージを描いて比べた。選択肢: A 何も出さない / B 一覧の上端に小さな「読み込み中」を重ねる / C 項目の上に半透明の「読み込み中」を重ねる。判断の軸は、標準の一覧らしさ、取り直し中だと分かるか、待っている間に古い項目を触れるか、用意する表示の数。A を推奨した (標準の一覧にこの場面の表示は無く、きっかけはアプリの画面にあるので見せたいならアプリが出すほうが文脈に合う)。項目が 1 件もないときは最初の読み込みと同じ真ん中の表示を出す前提とした。

採用: A (オーナー決定)。

## 2026-09-27: 標準の表示部品 — 項目が 1 件もない画面の再試行

真ん中に出る「読み込めませんでした + 再試行」に来るのは、最初の読み込みの失敗・0 件の一覧での Pull to Refresh の失敗・VM が自分で取り直した失敗の 3 つで、どれも再試行で最初のページを読み直したい。VM の次のページを頼む処理は項目が空なら最初のページを読むため、どちらの処理を呼んでも結果は同じ。core/ADR-0019 は「空なら取り直し」としていたが、Pull to Refresh を付けていない一覧には取り直しの処理が無い。選択肢: A 再試行はいつも次のページを頼む処理を呼ぶ / B 取り直しの処理があればそれを、なければ次のページの処理を呼ぶ。判断の軸は、規則の数、最初の読み込みの失敗と 0 件での Pull to Refresh の失敗をどの処理でやり直すか、VM に求めること、ADR-0019 との関係。

採用: A (オーナー決定)。core/ADR-0019 (proposed) を書き直し、agenda の論点 1 の決定の表も今の決定に合わせた。

## 2026-09-27: 標準の表示部品 — 差し替えの形

いちばん多い使い方 (「項目がありません」をアプリの言葉に替えるだけ) で何を書くかを、仮の名前のコードで比べた。選択肢: A 6 つの表示それぞれに差し替え口を用意する / B 「いちばん下」と「0 件のとき」の 2 つにまとめ、中で状態によって出し分ける / C 1 つにまとめ、状態と場所の両方を受け取る。判断の軸は、1 つだけ替えるときに書くもの、公開の差し替え口の数、6 つの表示との対応、全部を作り直すとき、今の DSL との揃い方。B と C は 1 つだけ替えるときも分岐と「残りは標準を呼ぶ」を書く必要があり、標準の表示を呼ぶ公開の部品も要る。どの形でも、失敗の表示の差し替えにはライブラリの再試行を呼ぶ操作を渡す。

採用: A (オーナー決定)。

## 2026-09-27: 標準の表示部品 — 文言と言語

ライブラリは iOS・Android ともリソース (文言のファイル) を持っておらず、標準の表示に文言を入れるには両プラットフォームにリソースの仕組みを足す必要がある。前例として KsSettingsView は日付の表示を OS で選ばれた言語に従わせている (KsSettingsView の core/ADR-0035)。選択肢: A 英語と日本語の文言を持ち、OS で選ばれた言語で切り替える / B 英語だけ持つ / C 文言を持たずアイコンだけで見せる。判断の軸は、日本語アプリで何も指定しないときの見え方、英語・日本語以外のアプリ、読み上げ、ライブラリに足すもの。A を推奨した (主な利用者が日本語アプリで、英語だけでは毎回差し替えることになる)。

オーナーの決定: 「アイコンのみ。読み込み失敗、Empty、これ以上ありません。の部品は既定では空。必要なら利用者が設定する。」これにより、先に決めた「6 つ全部を用意する」を改め、既定で出すのは 2 つの読み込み中 (標準のくるくる、文言なし) だけとし、失敗 (2 か所)・終端・空は既定では何も出さない。6 つそれぞれの差し替え口はそのまま。core/ADR-0005 (accepted) の「失敗 → 再試行ボタン / 終端 → 終端の表示」を置き換えるため、論点 5 の決定をまとめた ADR を amends 0005 として起票した: core/ADR-0024 (proposed)。オーナーには、失敗の表示を設定しないと再試行の手段が出ない (Pull to Refresh が無ければ止まる) ことを帰結として伝え、ガイドの注意と Sample での設定を TODO に積んだ。論点 5 はこれで完了。

## 2026-09-27: グループとの組み合わせ — ページの境目でグループが伸びることの扱い

はじめ「ページングのデモに切り替えを付けて、見出しの件数が増える様子を見せる」を推奨したところ、オーナーから「グループの件数はライブラリ側が数えているのか」と確認があった。コードで確かめ、ライブラリは見出しのクロージャにグループの値とそのグループの項目の配列を渡すだけで (iOS `header: (Group, [Item])`、Android `header = { group, items -> }`)、「N 件」は Sample の見出しが配列の数から出していると答えた。あわせて、「最後のグループに項目が続けて足されるのは試したことのない道筋」は言いすぎで、Sample の「差分更新」画面 (グループ化オン + 末尾に挿入) で 1 件ずつ伸びる動きはすでに確かめられると訂正し、推奨をガイドにだけ書く案に変えた。さらに「グループが伸びる」が分からないとの指摘を受け、日付でグループ分けしたメッセージの例 (1 ページ目の最後の 9/26 のグループに 2 ページ目の 9/26 の項目が続き 2 件 → 5 件になる、同じ日付が離れて現れる並びは不正入力) を図にして説明した (artifacts/group-extends-across-pages.md)。

選択肢: A ページングのデモに「グループ化」の切り替えを付け、ガイドにも書く / B 利用者向けガイドにだけ書く / C 何もしない。判断の軸は、新しく実物で確かめられること、並び順の責任に利用者が気づけるか、Sample の手間。採用: B (オーナー決定)。ライブラリの振る舞いは変わらないため ADR は起こさない。論点 6 はこれで完了。

## 2026-09-27: タップの色の意味の違い — 扱う場所

phase-3 からの申し送り (`touchFeedbackColor` は iOS が渡された色をそのままセル全面に塗り、Android の ripple が渡された色に自前で不透明度を掛けるため、Sample は iOS にアクセント色の 15%、Android にアクセント色そのものを渡している) を、中身を決める前にどこで扱うかを決めた。phase-3 が phase-5 に送った理由は「両プラットフォームの DSL に同時に触る」だったが、ページングの change はタップの色のコードに触らない。選択肢: A 既定の色のダーク対応の change (`library-default-colors-dark-mode`、簡易起票済み。探索メモの参考にも iOS のタップの反応の色と Android の既定の ripple が挙がっている) に移す / B ページングの change に同梱する / C 独立した小さな change として起票する。判断の軸は、テーマのまとまり、ページングの change の焦点、決着までの時間、Sample の値の食い違いの追跡。

採用: A (オーナー決定)。`kasane/changes/library-default-colors-dark-mode/exploration.md` の未決の論点に、経緯と出典つきで積んだ。論点 7 はこれで完了し、フェーズの論点はすべて決定した。
