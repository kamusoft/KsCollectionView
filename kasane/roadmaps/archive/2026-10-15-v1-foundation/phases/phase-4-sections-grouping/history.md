# 議論履歴

## 2026-09-24: 論点の統合

旧 5 論点と各フェーズ (phase-1〜3・performance-criteria-review・android-scrollbar-parity) の申し送りを合わせると 11 前後になり、分割トリガー (8 論点) に達した。どの論点も「論理セクションとは何か」に依存し単独完了できないため、分割・別ロードマップへの独立は該当せず、agenda の整理として固定番号の 7 論点 (セクションモデル / 論理セクションと内部の塊 / 固定ヘッダー / セクション境界の見た目 / 差分更新とソート連携 / 向き可変との組み合わせ / スクロールインジケータの全体長さ) に統合した。申し送りでオーナーが最初の論点に挙げた塊の懸念 (論点 2・3) は、セクションの識別の形が決まらないと定まらないため、セクションモデルを先に扱う。

## 2026-09-24: セクションモデル — グループの宣言の形

選択肢: A 平らな配列 + 項目の「どのグループか」を表す値を指す / B グループの配列 (各グループが見出しの情報と項目の配列を持つ。旧 AiForms と同じ形) を渡す / C 両方の入口を用意する。

判断の軸は、配列の型が 1 種類でモデルに手を入れないこと、KMP の共有モデルをそのまま使えること、見出しに出せる情報、空のグループの見出し、並べ替えとの相性 (core/ADR-0003)、旧 AiForms との近さ、新たに決める不正入力、公開 API の広さ。A は空のグループを出せない代わりに、モデル・配列の型・共有モデルを変えずに済み、データ層で並べた順がそのままグループになる。B はグループの型が別に要り、平らな共有モデルでは VM で組み直しが要る。C は入口が 2 つになり実装・テスト・en/ja の Skill が倍になる。

採用: A (オーナー決定)。空のグループの見出しが必要になったら B の入口を後から足す。オーナーの確認に答えて、セクションヘッダーは任意の View / Composable で書け、クロージャにグループの値とセクション内の項目が渡され、高さは中身から自動 (ルートのヘッダーと同じ考え方) とした。ADR: core/ADR-0015 (proposed)。

## 2026-09-24: セクションモデル — セクションのフッター

選択肢: ヘッダーだけ / ヘッダーとフッターの両方。判断の軸は使う場面、ルートのヘッダー / フッターとの揃い方、固定ヘッダー・区切り線・余白で決める組み合わせの数、iOS の塊との関係 (フッターは論理セクションの最後の塊だけに付ける処理が要る)、逆の判断をしたときのコスト。

採用: ヘッダーだけ (オーナー決定)。旧 AiForms でも実績のある用途でも使うのは見出しだけで、フッターは後から足しても利用者コードを壊さない。「もっと見る」や小計は最後の項目のテンプレートで作れる。後から足すときは区切り線・余白の規則を見直す。ADR は起こさず core/ADR-0015 (proposed) に追記した (可逆で局所的なため単独の ADR にはしない)。

## 2026-09-24: セクションモデル — 同じグループの値が離れて現れる入力

選択肢: A 並べ替え忘れとして不正入力に扱う (debug は assertion、release は別々のセクションで表示継続 + 警告ログ) / B 離れていても 1 つのセクションに集める / C 正当な入力として別々のセクションにする。判断の軸は並べ替え忘れに気づけるか、画面の並び順と配列の順の一致、同じ値をわざと何度も使う用途、セクションの識別の安定性、core/ADR-0011 との一貫性。B は画面の順が配列とずれてスクロール命令と食い違う。C は識別が「値 + 何回目か」になり差分アニメーションが崩れやすい。

採用: A (オーナー決定)。同じ値をわざと何度も使う用途は、値に何番目のまとまりかを含めて表す。core/ADR-0015 (proposed) に追記。

## 2026-09-24: セクションモデル — セクションごとの layout 値

グループの値でまとめる宣言にはセクションの入れ物が無く、ロードマップの非ゴール「セクションごとに異なるレイアウトの混在」とも一致するため、どちらを選んでも同じ結論になるとして選択肢を出さずに「layout 値はコレクション全体で 1 つ」と記録した (オーナーに報告済み)。core/ADR-0006 の Consequences の「セクションごとに layout 値を付与する拡張」は採らない。accepted の本文は変えず、蒸留時に footer の関連行で示す (TODO に積んだ)。論点 1 はこれで完了。

## 2026-09-24: 論理セクションと内部の塊の重ね方

iOS の現行は配列全体を塊に区切り、塊の順番 (`KsSectionID.chunkIndex`) で識別している。core/ADR-0015 と重ねると形はほぼ一択として提示した: 塊は論理セクションごとに区切る (ヘッダーとピン留めは compositional layout のセクション単位なので、塊が論理セクションをまたぐと見出しを置けない)。識別は「グループの値 + セクション内の塊の順番」(配列全体の塊の順番のままだと、グループの並べ替えで見出しがその場で書き換わり項目だけが飛ぶ)。release の同値の重複は何回目のまとまりかで区別。塊の件数は全セクション共通で最後の塊は端数でよい。位置の維持は項目 ID のアンカーのまま。オーナーは構造に異論なし。ios/ADR-0009 の Revisit When に該当するため、ios/ADR-0010 (proposed、amends 0009) を起票した。

残る不確実性は、グループ数がそのまま iOS のセクション数になるため、小さいグループが多いデータでの費用 (ios/ADR-0009 の Context に全セクション再計算の報告がある)。

## 2026-09-24: グループ化の性能を確かめる画面

選択肢: A 大きいグループと小さいグループを混ぜた 1 画面 / B 大きいグループだけと小さいグループだけの 2 画面 / C 実際のアプリに近い 1 種類 (20 件前後のグループ)。判断の軸は、塊に割れる論理セクションを通るか、セクション数の多さを通るか、不合格時の切り分けやすさ、オーナーの計測回数、Sample の保守。C は塊に割れるセクションを通らない。B は切り分けやすいが計測と保守が倍。

採用: A (オーナー決定)。たたき台は 10,000 件・2 列、1,200 件前後の大きいグループ 2〜3 個と 5〜30 件の小さいグループ多数 (数字は提案化で詰める)。可逆なため ADR にはしない。論点 2 はこれで完了 (セクションをまたぐ挿入・削除でのアンカーの確認は design の TODO に積んだ)。

## 2026-09-24: 固定ヘッダー — 既定と宣言の形

選択肢: A 既定で固定・設定 1 つで外せる / B 既定は固定せず指定したときだけ固定 / C 常に固定 (設定なし)。判断の軸は実績のある用途、固定したくない画面 (大きな帯・バナーの見出し)、既存の語彙との揃い方 (A は区切り線、B は SwiftUI の `pinnedViews` や Compose の `stickyHeader`、C はスクロールインジケータ)、公開 API、テストの通り数。C は固定したくない画面を作れない。

採用: A (オーナー決定)。ロードマップのゴールと実績用途は固定される見出しが前提で、iOS 標準の plain なリストも既定で固定する。既定の変更は利用者の見た目を変えるため覆すコストが高く、core/ADR-0015 (proposed) に追記した。塊に割れたグループでのピン留め (iOS) は残りの論点。

## 2026-09-24: 固定ヘッダー — 塊に割れたグループの試作の時期

申し送りの候補「全塊に同じ見出しを付けてピン留め」には、見出しがセクション内で自分の高さの場所を取るためグループの途中に隙間が出る (重ねる設定では先頭行にかぶる) リスクと、塊の境目で見出しが押し出されて入れ替わる動きが見えるリスクがある。代わりの方式 (ライブラリが固定見出しを自分で重ねて描く等) は作業量が大きく、試作の結果で提案の中身と規模が変わる。

選択肢: A 提案化の前に使い捨ての試作 / B 提案に「試作 → オーナー確認 → 本実装」を書き実装の最初のタスクにする (performance-criteria-review と同じ順)。判断の軸は提案の中身 (方式が 1 つか 2 通りを抱えるか)、規模の見積もり、流れの数、オーナーの確認の時期。

採用: A (オーナー決定)。方式が決まってから提案を書ける。試作は議論の場では行わず、ライブ調整か使い捨てのブランチで行い証跡を artifacts/ に残す (TODO)。論点 4〜7 は並行して議論する。

## 2026-09-24: セクション境界の見た目 — 区切り線

core/ADR-0010 の「先頭行の上端・行の間・最終行の下端」はリスト全体の上下境界を示す規則で、見出しが入ると位置を決め直す必要がある。

選択肢: A セクションごとに閉じる (各セクションを小さなリストとして同じ規則を当てる) / B 見出しの下には引かない (iOS 標準の plain な表に近い)。判断の軸は今の規則からの変わり方、背景色の無い見出しの見え方、線の数、見慣れた見た目、見出しを宣言しないときの二重線。B は最初のセクションに見出しがあると先頭の上線の位置が他とずれ、例外規則が要る。A は見出し未宣言のとき境目で二重線になるため「2 つめ以降の上線を出さない」規則が要る。

採用: A (オーナー決定)。塊の境目に線を出さないこととグリッドに描かないことは変わらない。accepted の core/ADR-0010 の位置の決定を一部置き換えるため core/ADR-0016 (proposed、amends 0010) を起票した。

## 2026-09-24: セクション境界の見た目 — セクション間の余白

選択肢: A 設定を持たず見出しの View の余白で作る / B セクション間の間隔を 1 つ / C 旧語彙と同じく前・後ろの余白を別々に。判断の軸は固定された見出しの見え方、見出しの無いセクションの間を空けられるか、公開 API の数、旧語彙からの移し替え、間隔が入る場所。A は固定見出しが余白ごと貼り付き空白の帯が残り、見出しの無いセクションの間を空けられない。C はリストの端を `contentPadding` が受け持つため 2 つにする理由が無い。

採用: B (オーナー決定)。行間と同じく layout 値の引数で宣言し (core/ADR-0006)、既定 0、先頭・末尾には入らず、塊の境目にも入れない。見出しと先頭行の間は見出しの View の下側の余白で作る。可逆な API 追加のため単独の ADR にはせず core/ADR-0015 (proposed) に追記した。

## 2026-09-24: セクション境界の見た目 — 背景装飾

旧 AiForms.CollectionView のソースにグループの背景・角丸の語彙は無かった。選択肢: A v1 では用意しない / B 背景色と角の丸みを設定できる板を用意する。判断の軸は作れる見た目、実績とゴール、iOS の作業 (塊ごとの角の丸め分け・固定見出しとの重なり)、Android の作業 (標準の仕組みが無く項目ごとに板の一部を描き分け、余白と板の端を合わせる)、後から足すときのコスト。

採用: A (オーナー決定)。可逆なため ADR にはしない。論点 4 はこれで完了。

## 2026-09-24: 差分更新とソート連携

グループの値が変わった項目の移動、グループの並べ替えで見出しが項目と一緒に動くこと、空になったグループの見出しの消滅、Android で full reset をやめキーで差分を取ることは、core/ADR-0003・core/ADR-0015・ios/ADR-0010 から導けるため選択肢を出さずに報告した (オーナー異論なし)。

確かめる場所の選択肢: A 「グループ化」の画面に操作ボタンを載せる / B 動きを見るための小さな画面 (数十件) を別に作る。判断の軸は Sample の画面数、動きの見やすさ、大量件数での並べ替えアニメーションの確認、性能計測との干渉。採用: A (オーナー決定)。ボタンは「グループの並び順を反転」「見えている項目を 1 つ別のグループへ移す」を候補とし提案化で詰める。可逆なため ADR にはしない。論点 5 はこれで完了。

## 2026-09-24: 向き可変グリッドとの組み合わせ

ios/ADR-0009・0010 から、回転で塊を組み直さないこと・端数の行が各グループの終わりにだけ出ることが導けるため、選択肢を出さずに報告した。回転時の位置の復元は、固定見出しがあるとき控えた項目を見出しのすぐ下へ戻す (表示範囲の先頭では見出しの裏に隠れる)。確かめる場所は「グループ化」の画面の列数を縦 2・横 4 にして兼ねる (縦向きの計測条件は「大量件数」と同じ)。可逆なため ADR にはしない。論点 6 はこれで完了。

## 2026-09-24: スクロールインジケータの全体の長さ (Android)

Android のバーは Compose 公式の `scrollIndicatorState` の全体の長さ (可視行の平均の高さ × 「項目数 ÷ 列数」行) を使っており、全幅の見出しを 1 ÷ 列数 行と数える。「グループ化」画面のたたき台 (10,000 件・2 列・約 370 グループ) では本当の約 5,550 行に対し約 5,185 行で 6〜7% 短く、末尾の 600 件ほど手前でバーが下端に着く。

選択肢: A ライブラリが全体の行数 (見出し 1 行・各グループの端数の行 1 行) を数え直して長さを補う / B 公式の見積もりのまま受け入れる。判断の軸は画面での見え方、グループ数への依存、作業 (位置の補正との組み合わせの確認を含む)、concepts の契約の書き方、iOS との揃い方。

採用: A (オーナー決定)。残る誤差は行の高さのばらつきだけになり、ルートの見出し / フッターのずれも消える。Android 内部の可逆な選択のため ADR にはしない。位置の補正との組み合わせは design の TODO に積んだ。論点 7 はこれで完了。残る論点は固定見出しの塊またぎ (試作待ち) のみ。

## 2026-09-24: 固定ヘッダー — 試作の進め方

選択肢: A 使い捨てのブランチ (worktree でワーカーが試作し、オーナーが Simulator で目視、証跡だけを artifacts/ に残す) / B ライブ調整 (ksn-live、change と独立レビューが残る)。判断の軸は残るもの、見た目を直すときの流れ、手間、向いている場面 (方式の見極めか本実装への育成か)。

## 2026-09-24: 固定ヘッダー — 試作 1 周目の結果とオーナーの目視

試作 (iOS Simulator、2 列・行間 8・セル高 56・見出し高 40、グループ A 40 件 / B 1,200 件 = 3 塊 / C 40 件) の数値 ([証跡](artifacts/sticky-header-chunk-prototype-2026-09-24.md)): 方式 1 (全塊に通常の見出し) はグループの途中に 40pt の帯が挟まり塊の境目で押し上げと薄れが出る。方式 2 (2 つめ以降は場所を取らない) は 32pt のかぶりと 8pt の横ずれ。2b (固定まで隠す) は帯がまるごと消える瞬間が出る。UIKit は塊単位で見出しを押し出すため、1・2・2b では塊の境目の切り替わりを消せない。方式 3 (ライブラリが見出しを重ねて描く) と 3b (位置を書き換えてグループ全体で 1 つとして固定) は塊の境目の隙間・かぶり・動き・帯の欠けがすべて 0。ワーカーの推奨は 3b (UIKit の部品と標準の押し出しに乗れ、作業は中)。未確認: 指で弾く計測、実機・Release、追加・削除のアニメーション中の位置、VoiceOver、塊が多いときの費用。

オーナーの目視: グループの境目で押し出されるアニメーションは 3b (UIKit 標準の押し上げ + 薄れ) より 3 のほうが自然、それ以外は 3b で良い。これを受けて 3b を基本に押し出しだけ 3 に揃える変種 3c を試作 2 周目で確かめることにした。

同じ目視で、見出しの上下の余白が揃っていないとの指摘があった (グループ A は見出しと先頭行が 0、B・C は 8pt、最終行と次の見出しの間は 0)。原因は試作のエンジンが塊の境目を見せないために 2 つめ以降の塊の上端へ行間を入れており、B・C の先頭の塊にもそれが入ったこと。本番の規則が未決のため論点 4 (見出しの上下の余白) を追加した (論点 4 は背景装飾まで決定済みで一度消していた番号を再利用)。

## 2026-09-24: 固定ヘッダー — 試作 2 周目 (方式 3c)

3 と 3b のグループの境目の押し出しは、位置と速さ (スクロールと 1:1) が同じで、違いは透明度だけだった。3b では UIKit が押し出し量に応じて見出しを薄め (α = 1 − 押し出し量 / 15、iOS 26.5 Simulator で観測)、後半 12 フレームは見出しが見えず上端に最大 24pt の見出しの無い帯ができていた。3 は押し出しの間 α 1。

3b を基本に表示中の見出しを常に α 1 にした変種 3c は、グループの境目 (A→B・B→C) の押し出しが 3 の記録と同じ contentOffset どうしで全フレーム一致し、塊の境目の 4 項目 (隙間・かぶり・動き・帯の欠け) も 0 のままだった。残る差は作り (3 は別の View を重ねる、3c は UIKit の固定見出し 1 つ) による VoiceOver の見え方 (未確認) と、UIKit が α 以外で薄める版では効かないという版への依存。1 周目からの未確認 (追加・削除のアニメーション中の位置・VoiceOver・塊が多いときの費用・基準機の体感) は変わらない。オーナーの目視は未実施 (Simulator で 3c を開いたまま起動済み)。

## 2026-09-24: セクション境界の見た目 — 見出しの上下の余白

試作の目視で見出しの上下の余白が揃っていない指摘を受けて議論した。提示した選択肢: A 見出しを行と同じに扱い上下にも行間を入れる / B 上下は 0 のまま、見出しの View の余白とセクション間の余白で作る (前の決定のまま)。判断の軸は既定の見え方、Android の並べ方 (項目どうしに一律の行間)、iOS の作業、見出しの下だけを別の値にできるか、固定見出しの見え方。

採用: オーナーの案。旧 AiForms が `GroupFirstSpacing` を持っていたのはこの制御のためで、セクション間の余白があるので `GroupLastSpacing` 相当は不要、見出しの下の余白には専用の設定を足す。既定は他の間隔と同じ 0 (core/ADR-0006)、行間は見出しの上下に入れない。A は見出しの下だけを別の値にできず、View の余白は固定見出しに空白の帯ごと貼り付くため採らない。前の決定の「見出しと先頭行の間は見出しの View の余白で作る」を置き換え、core/ADR-0015 (proposed) を書き直した。Android は `Arrangement.spacedBy` の一律の行間を見出しの前後で外す工夫が要るため design の TODO に積んだ。

## 2026-09-24: 固定ヘッダー — 塊に割れたグループの見出しの方式

オーナーが Simulator で 3 と 3c を見比べ、3c で確定した。3c は見え方が 3 と一致し、見出しを UIKit の部品のまま扱えて差分の適用と再利用を UIKit に任せられる。弱点は UIKit が押し出し中に透明度以外で薄める版では効かないことと、VoiceOver が未確認なこと。iOS の内部の作りだが UIKit の振る舞いに依存し後の変更を縛るため、ios/ADR-0010 (proposed) の決定に組み込み、試作で退けた方式 (1・2・2b・3・3b) と理由を Alternatives に書いた。未確認 4 点は実装・計測の TODO。試作のブランチはマージせず、実装時の参考に残す。これで論点はすべて決定した。

## 2026-09-24: Android の差分の移動アニメーション (提案作成時)

ksn-propose の自己レビューで、論点 5 の導いた契約「グループをまたぐ移動・グループの並べ替えをアニメーションで見せる」が、android/ADR-0004 (accepted) の「`animateItem` は重ねない」と衝突していることを検出した。Compose で移動・挿入・削除を見せる手段は `animateItem` だけで、今の Android は配列の差し替えで項目が新しい位置へ飛ぶ。論点 5 で選択肢を出さずに導いたときに ADR-0004 を見落としていた。

選択肢: A ADR-0004 に従い、Android の移動のアニメーションは D&D 並べ替え (phase-6) に申し送る / B ADR-0004 を一部改訂し、この change で Android も `animateItem` でアニメーションさせる。判断の軸は Android の見え方、Sample のプラットフォーム間の一致、性能のリスク (ADR-0004 の却下理由は高さ補間に重ねたときの P90 +19.4% で、移動を見せる目的では未検討)、作業量、phase-6 との関係。

採用: B (オーナー決定)。D&D の実装時期は分からず、どうせ解決しなければならないので先送りする意味がない。android/ADR-0006 (proposed、amends 0004) を起票した。付け方・フェードの有無・高さ補間との重なりは使い捨ての試作 (Android エミュレータ、`animateItem` なし / ありの切り替え) のオーナー目視で決め、性能は相対基準で確かめる。

## 2026-09-24: 提案化 (change `sections-grouping`)

ksn-propose で L 級の提案一式 (proposal / design の Decision 15 件 / デルタスペック 3 能力 / ui の brief・mock / tasks) を作成した。提案作成中の追加の決定: Android の差分の移動アニメーション (上の節、android/ADR-0006)、ルートのヘッダー / フッターの余白を両プラットフォームで揃える (core/ADR-0006 の `contentPadding` の意味論の適用。今は iOS と Android で位置が違う)、Sample に「差分更新」画面を足す (オーナー指示。今の Sample には配列を差し替える操作が無かった)、両画面の操作は下部バー (モック案 B、オーナー承認)。相方 (codex) の提案レビューの Major 4 件 (セクションありのシャッフルが不正入力になる / iOS の見出しの内容の更新が未定義 / Android の性能比較の条件が handbook と衝突 / 作り直さない保証の範囲) をすべて採用して反映した。

## 2026-09-24: 差分のアニメーションの見比べ (提案作成時)

Android の試作 (エミュレータ) と iOS の試作 (Simulator) を同じ操作で作り、オーナーが見比べた。Android はいちばん上で先頭に挿入すると挿入した項目が表示範囲の上に外れて見えない (NG) → 先頭を表示中なら先頭に留める契約を両プラットフォームに足した (design Decision 16)。末尾・中間の挿入と削除も無いと網羅できない → 「差分更新」画面の操作を 位置 (先頭 / 中ほど / 末尾) × 挿入 / 削除 / 更新 / 移動 に広げ、件数は 60 件では多すぎるため 20 件にした。グリッドで列をまたぐ移動は iOS も斜めにまっすぐ動くと分かり、オーナーは両プラットフォームとも標準のままを選択。オーナーから「試作は propose でやることではない」と指摘があり、以後は提案の仕上げに戻した。`animateItem` を付ける位置・フェードの有無・高さの補間との重なりは実装のタスク (3.8) で決める。

## 2026-09-24: 公開の語彙を group に揃える (提案作成後)

オーナーが design Decision 1 の `section` という名前は用途と一致しないと指摘した。選択肢: A 公開の語彙を Group に揃える / B Section のまま。判断の軸は利用者と議論の言葉 (「グループ化」「グループの値」)、旧 AiForms の語彙 (`GroupHeaderTemplate` 等) との連続、iOS エンジン内部の「セクション」(内部の塊) との取り違え、SwiftUI の `Section` との近さ、`groupBy` から「離れた同じ値も集める」と誤解されるおそれ。採用: A (オーナー決定)。`.groups(by:)` / `KsGroups` / `groupSpacing` とし、`groupBy` の名は避けて続いた範囲だけがグループになることをドキュメントと assertion で示す。

見出しの下の間隔の名前は `groupHeaderSpacing` ではどこの間隔か分からないとの指摘で、短い候補 (`headerItemSpacing` / `headerToItemsSpacing` / `belowHeaderSpacing` / `headerSpacing`) から `headerItemSpacing` を採用 (オーナー決定)。layout 値で間隔を持つ見出しはグループの見出しだけなので `group` を外した。提案一式・ADR 4 件の本文で利用者の語彙の意味の「セクション」を「グループ」に揃え、iOS 内部の意味 (内部セクション・compositional layout のセクション) は残した。

## 2026-09-24: 端を表示中の端への挿入 (提案作成後)

オーナーが design Decision 16 (Android でいちばん上での先頭への挿入を先頭に留める) を Android に限定しないよう指示した。いちばん上での先頭への挿入、いちばん下での末尾への挿入は、両プラットフォーム・list / グリッドの両方でアニメーションが見えることを必須とし、画面外でひっそり足されないように工夫する。表示範囲の外での挿入は見えないので考慮不要。これで提案時の未決 (先頭以外を表示中の、表示範囲より前への挿入での位置の保ち方の違い) も決着した。スペックの Requirement を「端を表示中の端への挿入」に広げ、design Decision 16 を両プラットフォームの方式 (iOS の末尾は差分のアニメーションの中で `contentOffset` を下げる、Android は先頭・末尾とも差し替えと同じフレームでスクロールを要求) に書き直し、tasks に iOS (2.11) と目視確認 (5.7) を足した。
