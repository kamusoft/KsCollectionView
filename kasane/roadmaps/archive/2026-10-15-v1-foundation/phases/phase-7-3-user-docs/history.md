## 2026-10-10: 論点 2-b — 変わった源泉の見分け方

頼まれたときに動く手順が、「前回の追従から変わった源泉」を何で見分けるかを諮った。

確かめたこと: 翻案元は concepts のファイルごとのハッシュを対応表に持つ。concepts を分割・改名したときに手でハッシュを合わせる必要があり、記録済みのハッシュがいつの内容かを知るために、git の履歴の各版をハッシュにして突き合わせていた (`../KsSettingsView/kasane/lessons/inbox/manifest-hash-left-stale-when-restructure-has-unconsumed-diffs.md`)。自リポジトリの `develop` は強制 push を禁じ、マージは merge commit だけなので、commit の ID は変わらずに残る (handbook の `cross/branch-and-github-settings.md`)。

| 案 | 覚えておくもの | 評価 |
|---|---|---|
| A: ファイルごとのハッシュ | concepts の 1 枚ごとのハッシュ (翻案元と同じ) | 「変わった」ことだけが分かり、中身は git で見る。分割・改名は手で合わせる。1 枚ごとに追従を進められる。兄弟ライブラリと同じ形で、検査の道具を手直しして使える |

## 2026-10-10: 追従の仕組みの ADR の起票

追従の仕組みの 3 つの決定 (ずれの見つけ方・変わった源泉の見分け方・手順の置き場所) を、1 本の ADR にまとめて起票した。cross/ADR-0005 が本フェーズに委ねた決定で、今後の源泉の変更すべてがこの仕組みに頼るため、選別基準に当たる。

起票の前に、ずれの見つけ方でオーナーが議論側の推奨 (`main` 宛ての Pull Request の検査で止める) と違う案を選んだ理由を確かめた。候補として、作るものを最小にしたい・リリースの Pull Request を文書の遅れで止めたくない・追従させるかどうかは人が決めたい・兄弟ライブラリと運用を揃えたい、の 4 つを示した。オーナーの答えは「兄弟ライブラリと運用を揃えたい」だった。

揃えるのは、追従をいつ動かすかの運用である。記録の形 (commit の ID) と手順の置き場所 (handbook と `scripts/`) は、それぞれの論点で兄弟ライブラリと違う形を選んでおり、ADR にはその両方を書いた。

ADR は cross/ADR-0017 (proposed)。status は、変更の蒸留のときに上げる。

## 2026-10-10: 論点 3 — インストール例の版の書き方

インストール例が載るのは 6 か所 (ルートの README 2 枚と、各 Skill の `SKILL.md` の導入の節 4 部)。書く値は決まっており (handbook の `cross/public-identifiers.md`)、決まっていないのは版のところだけだった。

翻案元は、具体の版を書いていて実在しない版が残り、リリースのたびに置き換える仕組みを作って対象を広げた 5 日後に、仕組みごと撤去して `{version}` に変えた (翻案元の 0029)。

| 案 | 起きること | 評価 |
|---|---|---|
| A: 版を書かず `{version}` を置く (採用) | 利用者が自分で置き換える。最新の版は Release の一覧で確かめる | 例の版が古くならない。貼ってそのままでは動かないので、置き換えの説明を添える。リリースの工程に何も要らない。兄弟ライブラリと同じ |
| B: 具体の版を書き、リリースの工程が毎回置き換える | 例はいつも最新の版 | 貼ればそのまま動く。リリースのたびに 6 か所を書き換える道具と commit が要る。リリースの工程が Skill を書き換える道ができ、「追従は頼んだときだけ」(cross/ADR-0017) と別の経路になる。翻案元が撤去した形 |
| C: 具体の版を書き、手で直す | 直し忘れると古い版が残る | 何も作らずに済む。翻案元で、実在しない版が残ることが実際に起きた |

オーナーは A を選んだ。A を推した理由は、例の中に版が無ければ古くなりようが無いことと、リリースの工程が Skill や README を書き換える道を作らずに済むこと。

A の帰結として 2 つが残る。最新の版の確かめ先を `SKILL.md` に URL で書くなら、cross/ADR-0005 の閉世界性の条項に掛かる (論点 6)。案内先の Release の形は phase-7-4 が決める (申し送りの候補として TODO に足した)。ADR は、論点 6 の結論とあわせて起票する。

## 2026-10-10: 論点 6 — cross/ADR-0005 の閉世界性の条項

論点 3 でインストール例に版を書かないと決めたので、番号の順を飛ばして論点 6 を先に扱った。

cross/ADR-0005 (accepted) は、`SKILL.md` と `references/` が Skill の外のファイル・URL への参照を持たないと決めている。この文面のままでは、SwiftPM のインストール例 (依存に書く値が Package URL) と、最新の版の確かめ先が書けない。条項は翻案元から引き継いだもので、翻案元は引き継ぎの後に、文面が実態と合っていないことを理由に、境界を「URL があるかどうか」から「何のための参照か」に改めている (翻案元の 0029)。accepted の ADR なので、従う案と改める案を並べて諮った。

| 案 | 起きること | 評価 |
|---|---|---|
| A: 改める (採用) | 知識を外に委ねる参照は持たない。操作の対象の URL (依存に書く Package URL・最新の版の確かめ先・不具合の報告先・配布元) は書いてよい | 決定と実物が食い違わない。利用者のエージェントが最新の版に URL で行ける。線引きは機械で確かめられず、人が見る。要る作業は ADR 1 本で、`skills/` がまだ無いので直す実物は無い。兄弟ライブラリと同じ線引き |
| B: 従う | 案内の URL を書かず、最新の版は言葉で案内する。Package URL だけは読み替えで書く | URL が無いことは機械で確かめやすい。Package URL を書いた時点で文面と食い違い、読み替えは ADR に書かれていない。エージェントは言葉から場所を推測する |

オーナーは A を選んだ。frontmatter の配布元の URL の項目は、論点 1-c で保留にしていたが、書いてよいものに入るので、翻案元と同じく持つことにした (議論側の既定)。

ADR は 2 本起票した (どちらも proposed)。cross/ADR-0018 はインストール例の版の書き方 (論点 3 の決定)、cross/ADR-0019 は条項の改訂で、cross/ADR-0005 の一部だけを置き換える形にした。cross/ADR-0005 の側の印 (一部が改められたことの記載) は、cross/ADR-0019 を accepted に上げるときに付ける。翻案元は 2 つを 1 本の ADR にまとめているが、決定ごとに分ける今の決まりに合わせた。

## 2026-10-10: 論点 4-a — README の最小コード例を何と一致させるか

論点 4 (README の中身と検査) を、最小コード例 (4-a)・インストール例の検査 (4-b)・必要な環境の案内 (4-c) に分けた。phase-7-2 が「利用者役のソースは最小の利用例として書く。README の例と一致させる検査はこのフェーズで扱う」と送ってきているので、検査を持たない案は候補から外した。

確かめたこと: 翻案元は、README の最小コード例を利用者役の画面のファイル全体と完全一致で比べる。翻案元の利用者役のファイルにはコメントが無く、Android は package の宣言も無い。自リポジトリの利用者役は、日本語の説明コメントがあり、iOS はモデルと画面が 2 ファイルに分かれ、Android は利用者役のアプリの package の宣言で始まる。

| 案 | 起きること | 評価 |
|---|---|---|
| A: 利用者役のファイル全体と完全一致 (採用) | 利用者役の画面のソースを、README に載せる形に書き直す | README の例が、import まで含めてビルドで確かめたコードそのものになる。比べ方は文字列の一致だけ。利用者役のソースは README の見せ方に縛られ、コメントを書けない。兄弟ライブラリと同じ |
| B: 印で囲んだ範囲と一致 | 利用者役のソースに印の行を入れ、その間だけを比べる | 利用者役のソースは今のままでよい。import を印の外に置くと、例だけ貼っても動かない。印を読み取る処理が要る |

オーナーは A を選んだ。利用者役のソースから日本語の説明コメントが消える点は、handbook の利用者役のガイド (`cross/consumer-build-check.md`) がファイルの役割を説明しているので、そちらに任せる。あわせて示した既定 (検査は今の CI のスクリプトのテストに足す・比べる相手は README の英日 2 枚とも・各 Skill の「最小の動く例」は対象にしない) に、変更の指示は無かった。

## 2026-10-10: 論点 4-b — インストール例の検査

phase-7-2 の申し送りが方向 (利用者役と一致させる検査を作る) を決めており、翻案元の検査の中身 (`{version}` であること・最新の版への案内があること・英語版と日本語版の一致) と合わせると、比べる軸が残らなかった。選択肢を諮らずに、議論側の既定として決定事項に書いた。

翻案元と変えた点は 1 つ。翻案元は、例の形をスクリプトの中の決まりと比べるだけで、例の値が利用者役と同じかは見ない。こちらは、phase-7-2 の申し送りに合わせて、値を利用者役と突き合わせる。

`SKILL.md` を対象に入れることは、Skill のずれを検証 CI で検査しない決定 (cross/ADR-0017) と別の話として扱った。cross/ADR-0017 が検査しないと決めたのは源泉とのずれで、翻案元で実在しない版が残ったのは Skill の導入の節だったためである。

## 2026-10-10: 論点 4-c — 必要な環境の案内と、スクリーンショット

必要な環境の案内は、比べる軸が無かったので、議論側の既定として報告した。「対応プラットフォーム」の節に翻案元と同じ形の表を 1 枚置き、翻案元に無い Xcode の行を足す (Xcode 27 以上は phase-7-2 の決定)。値の正はビルドの設定で、追従のときに差分を出す対象のパスに、ビルドの設定を入れる。

諮ったのは、スクリーンショットの節である。cross/ADR-0005 が挙げた README の節 (9 つ) には無いが、翻案元の README は同じ並びの中に持っている (両プラットフォームの画面 4 枚を `assets/` に置き、表で並べる)。README を利用者の入口に絞る決定の範囲内で、足しても cross/ADR-0005 とぶつからないと読んだ。

| 案 | 起きること | 評価 |
|---|---|---|
| A: 載せる (採用) | 概要の次に節を置き、両プラットフォームの代表の画面を数枚、Sample から撮って置く | 初めて見る人に、何ができる部品かが画面で伝わる。撮る画面を選ぶ・撮る・置き場を作る・写り込みを確かめる作業が増える。見た目を変えたら撮り直すが、古くなっても機械は気付けない。兄弟ライブラリと同じ |

オーナーは A を選んだ。A を推した理由は、一覧やグリッドの部品は画面のほうが早く伝わることと、Sample に両プラットフォームで揃えた画面が既にあること。どの画面を何枚撮るかは、提案のときに決める。

論点 4 はこれで空になったので、論点の一覧から外した。ADR にはしていない (README の中身で、後から変えられる)。

## 2026-10-10: 論点 5-a — Skill 自身の整合の検査の置き場所

論点 5 (守り方) を、Skill 自身の整合の検査 (5-a)・公開 API の名前の網羅の確かめ方 (5-b)・初回の制作で検収の前に確かめること (5-c) に分けた。

| 案 | 起きること | 評価 |

| B: CI のスクリプトのテストでも毎回流す (採用) | 追従の手順に加えて、push のたびと `main` 宛ての Pull Request でも走る | 崩れに、その push の回で気付く。`skills/` を触らない push では落ちない。同じスクリプトを CI のテストからも呼ぶだけで済む。cross/ADR-0017 とはぶつからない。兄弟ライブラリとは違うが、README の検査とは揃う |

## 2026-10-10: 論点 5-b — 公開 API の名前の網羅の確かめ方

翻案元で、concepts から Skill へ移すときに API の名前が脱落した件 (iOS で 33 件) の守り方を扱った。基準 (名前が Skill のどこかに一度は現れる)・結果の扱い (報告だけで、載せるか外すかはオーナーが判断し、外す名前は一覧に残す)・流す場所 (追従の手順の中だけ) は、翻案元と同じで比べる軸が無かったので、既定として示した。諮ったのは、漏れを数える元である。

| 案 | 漏れを数える元 | 評価 |

## 2026-10-10: 論点 5-c — 初回の制作で、検収の前に確かめること

| 案 | 確かめ方 | 評価 |
