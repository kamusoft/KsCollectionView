## 2026-09-29: 並べ替えの結果の受け渡し — 知らせるタイミングと仮の並びの持ち主

論点 1 を 2 段に分け、前半としてドラッグ中の並びを誰が持ち、利用者にいつ知らせるかを決めた。

選択肢: A 指を離したときに 1 回だけ知らせ、ドラッグ中の仮の並びはライブラリが持つ / B 項目が入れ替わるたびに知らせ、VM がその都度配列を並べ替えて渡す / C ライブラリが利用者の配列を直接書き換える (Binding / 書き換えられるリスト)。判断の軸は、配列が唯一の正であること (core/ADR-0003)、KMP の共有 VM の配列をそのまま使えるか、保存のタイミング、保存に失敗したときの戻し方、各 OS の慣習。

採用: A (オーナー決定)。配列が唯一の正のまま保て、ドラッグ中に共有 VM とやり取りせず、知らせを受けたときがそのまま保存の契機になる。SwiftUI の List の並べ替えと iOS 27 の標準の並べ替えも同じ時機で、iOS の利用者が知っている形である。B は VM の処理が 1 段ごとに走って KMP では反映が指に遅れうるうえ、保存のためにドラッグの終わりの知らせが別に要る。C は core/ADR-0003 を改めることになり、KMP の共有モデルをそのまま使えない。調査で、両プラットフォームとも A で作れること (Android は OSS を使う場合もラッパー内部に仮の並びを持って包む) を確かめた。

A の負の面として、利用者が配列を並べ替えなかったときに表示を元に戻す仕組みが別に要る (`StateFlow` は同じ値を流さないため、配列を渡し直すだけでは戻せない)。これを論点 1 の後半として続けて決める。core/ADR-0026 を proposed で起票した。

## 2026-09-29: 並べ替えの結果の受け渡し — 受け入れなかったとき・保存に失敗したときの戻し方

論点 1 の後半。core/ADR-0026 (置いたときに 1 回知らせ、仮の並びはライブラリが持つ) の負の面として、利用者が配列を並べ替えなかったときに表示を戻す仕組みを決めた。扱う場面は 3 つ: ① 置いてみて初めて業務ルールで受け入れられないと分かる、② 受け入れた後で保存に失敗する、③ KMP の `StateFlow` の値が Swift 側へ遅れて届く。③ があるため、一定時間配列が来なければ戻す形は使えない (一度戻ってまた動く)。

選択肢: A 知らせる処理がその場で受け入れたかを返す / B 保存が終わるまで待つ非同期関数で結果を返す (core/ADR-0022 と同じ形) / C 何も返さず、置いた後に届く配列だけに従う。判断の軸は、3 つの場面それぞれの戻り方、仮の並びが残る時間 (ドラッグ中の配列の差し替えの扱いに響く)、VM の書き方。

採用: A (オーナー決定)。受け入れないならすぐアニメーションで戻し、受け入れたなら置いた並びのまま配列を待つ。保存の失敗は、受け入れた時点で配列を並べ替えている VM が元の並びの配列を渡し直せば、値が違うので `StateFlow` でも届いて戻る。時間の決め打ちなしで 3 つの場面を扱え、戻り方も配列が決めるので配列が唯一の正のまま。B は保存の間ずっと仮の並びが残り、次のドラッグや配列の差し替えの扱いが増えるうえ、VM が先に並べ替える書き方では待つ意味がない。C は受け入れない KMP の VM が配列を変えないと表示と配列がずれたまま戻らない。

A の負の面: 受け入れたと返したのに配列を並べ替えないと次に配列が届くまでずれる (利用契約としてガイドに書く)。受け入れの判断は同期なので、サーバーに問い合わせないと分からない可否は保存の失敗として扱う。置く前に止める手段は論点 2 の「置き先の制限」で別に決める。core/ADR-0027 を proposed で起票し、core/ADR-0026 の「含まないもの」から参照を張った。

## 2026-09-29: 動かせる範囲 — グループをまたぐ移動

論点 2 を ① グループをまたぐか → ② list / グリッドの両方か → ③ 項目ごとの可否と置き先の制限 → ④ 行き先の表し方、の順に扱うことにし、① を決めた。

前提として示した事実: グループは項目から読み取るグループの値が同じものが続く範囲なので (core/ADR-0015)、グループをまたぐ移動は項目の属性の書き換えを伴い、VM がグループの値を書き換えて配列を渡すまで確定しない。書き換え忘れは「同じ値が離れた位置に現れる」不正入力になる。空のグループは表示できないため、空のグループへは移せない。

選択肢: A このフェーズはグループの中だけにし、知らせの形は「どのグループのどこへ」で作ってグループ間を後から足せるようにする / B グループ間の移動もこのフェーズで提供する。判断の軸は、区分を移す用途が叶うか、新しく決めることの量 (境目に置いたときの所属・見出しの消え方・書き換え忘れ)、VM の書き方、後から足せるか、フェーズの規模。推奨は A (区分を移す用途は移し先が空になりうるため今の契約では中途半端にしか叶わず、決めることが増え、必要になるか自体が未確定) だった。

採用: B (オーナー決定。理由の言及はなし)。空のグループへは移せない制約は core/ADR-0015 のまま引き継ぐ。グループの値の書き換えは利用者の VM が行う (ライブラリは利用者のモデルを書き換えない — core/ADR-0026)。ADR は、行き先の表し方 (④) が決まってから、グループ間の移動の契約として 1 本にまとめて起票する。

## 2026-09-29: 動かせる範囲 — list とグリッド (既決事項から導出)

② は選択肢を出さずに既決事項から導いた: list / グリッドの両方で提供する。両プラットフォームとも list を 1 列のグリッドとして扱い (ios/ADR-0003・android/ADR-0001)、データやテンプレートの宣言を変えずに layout 値だけを差し替えられる契約 (core/ADR-0006) なので、並べ替えも layout によらず同じに効かせる。片方だけにすると、layout を差し替えたときに並べ替えが消える。

## 2026-09-29: 動かせる範囲 — 行き先の表し方

論点 2 の ④。③ (項目ごとの可否と置き先の制限) は ④ で決める行き先の形を使うため、順番を入れ替えて先に扱った。

選択肢: A 項目で表す (動かした項目と「この項目の前 / このグループの末尾」、グループを宣言しているときは行き先のグループの値) / B 位置で表す (何番目から何番目へ、行き先のグループの値を足す) / C 置いた後の並びを丸ごと渡す。判断の軸は、グループの境目の区別 (前のグループの末尾と次のグループの先頭は配列では同じ位置)、置いてから処理までの配列の変化への強さ (KMP で画面の配列と VM の最新の配列がずれうる)、VM の書き方、大量件数、既存の契約と慣習。

採用: A (オーナー決定)。境目を区別でき、配列がずれても行き先の意味が変わらず、スクロール命令 (core/ADR-0007) や状態モデル (core/ADR-0003 で位置ベースを却下) と同じく項目で指す形にそろう。iOS 27 の SwiftUI 標準の並べ替えも同じ表し方。B は VM の書き方が最短 (SwiftUI の `onMove`・Compose の OSS と同じ) だが、配列のずれで別の場所へ動き、「何番目」の数え方で間違えやすい。C は大量件数で重く、その間の配列の変化を消し、保存のため動かした項目を VM が割り出す必要がある。項目はタップと同じく配列の要素そのものを渡す想定で、型・名前・配列に当てはめる補助関数は提案で設計する。

ADR は、グループ間の移動と 1 本にまとめる予定だったが、行き先を項目で表す決定はグループが無くても成り立つ独立した決定なので、2 本に分けて起票した: core/ADR-0028 (行き先を項目で表す) と core/ADR-0029 (グループをまたぐ移動を提供し、グループの値は VM が書き換える)。0029 の却下案 (グループの中だけ) は、オーナーから却下の理由が述べられていないため「オーナー判断」とし、推奨側の理由を併記した。

## 2026-09-29: 動かせる範囲 — 項目ごとの可否と置き先の制限

論点 2 の ③。業務ルールで動かしてはいけない項目 (広告・先頭に固定したい項目) や置いてはいけない場所 (特定のグループ、グループの外) をどう伝えるかを決めた。

選択肢: A 「動かせるか」(項目ごと) と「ここに置けるか」(ドラッグ中に行き先ごと、行き先は core/ADR-0028 の形) の 2 つの判定を任意で渡せる / B 「動かせるか」だけ持ち、置き先は置いた後の受け入れで弾く / C 判定を持たず、すべて置いた後の受け入れで弾く。判断の軸は、動かせない項目と置けない場所の見え方、グループ間の移動を止める書きやすさ、API の量、判定の呼ばれ方。

採用: A (オーナー決定)。動かせない項目は持ち上がらず、置けない場所にはそもそも入らない。グループ間の移動を止めたいアプリは「行き先のグループが元と同じなら置ける」の判定 1 つで書ける。UIKit にはドラッグ中に置けないことを返す標準の口があり、Android はラッパーが仮の並びを持つので置けない場所で並びを変えなければよい。B・C は置けない場所にいったん入ってから戻る見た目になる。「ここに置けるか」はドラッグ中に何度も呼ばれるため軽い判定にしてもらう (ガイドに書く)。置いた後の受け入れ (core/ADR-0027) は最後の砦として残す。core/ADR-0030 を proposed で起票した。

## 2026-09-29: 動かせる範囲 — グループをまたぐときの細部 (既決事項から導出)

論点 2 の残りの細部は、選択肢を出さずにここまでの決定から導いた。

- 境目に置いたときの所属は、置いた見た目の位置で決まる。見出し (見出しが無ければグループの間の間隔) より上なら前のグループの末尾、下なら次のグループの先頭。行き先を項目とグループの値で表す (core/ADR-0028) ので、どちらかは知らせで区別される
- 見出しの無いグループでも同じ規則にする。間隔 0 などで境目が見えず紛らわしい一覧は、利用者が「ここに置けるか」(core/ADR-0030) でグループ間の移動を止められる
- 最後の 1 件を持ち出しても、ドラッグ中は元のグループの見出しを残す。ドラッグ中に消すと表示が見出しの分だけ詰まって跳ね、元のグループへ戻せなくなる (空のグループへは移せない — core/ADR-0029)。確定して VM の配列が届いた時点で、空になったグループは見出しごと消える (core/ADR-0015)。受け入れられずに戻ったときは、グループがそのまま残る

これで論点 2 を閉じた。

## 2026-09-29: 開始の操作 — 持ち上げ方

論点 3 を ① どうやって持ち上げるか → ② 既存の長押し (`onItemLongTap`) との関係 → ③ 端での自動スクロール → ④ アクセシビリティの移動操作、の順に扱うことにし、① を決めた。

選択肢: A 項目のどこでも長押しで持ち上げ、ハンドルは持たない / B ハンドルだけ (テンプレートの中の部品に印を付け、そこをつかむとすぐ動く) / C 両方 (既定は長押し + 任意のハンドル)。判断の軸は、標準の操作との一致、テンプレートへの手の入れ方、既存の長押しとの取り合い、並べ替えできることへの気づきやすさ、実装の重さ。

採用: A (オーナー決定)。両 OS のコレクションの標準の操作 (写真アプリ・ホーム画面、UIKit のコレクションビュー標準のドラッグ) と同じで、テンプレートに手を入れずに動き、いちばん軽い。B・C はハンドルの印を付ける語彙が両プラットフォームに増え、iOS ではハンドルからすぐ動かす経路が標準のドラッグと別になって重くなる見込み (未調査)。ハンドルは後から足しても今の書き方を壊さない。負の面として並べ替えできることに気づきにくく、既存の長押しと取り合う (② で決める)。「編集」ボタンで並べ替えを有効にする作り方は論点 4 の有効 / 無効で書ける。ADR は ② と合わせて開始の操作の契約として起票する。

## 2026-09-29: 開始の操作 — 既存の長押しとの関係

論点 3 の ②。長押しで持ち上げると決めたため、長押しが成立した瞬間に呼ばれる既存の長押しの知らせと取り合う。動かせる項目で並べ替えと長押しの知らせを両方宣言したときの振る舞いを決めた。

提示した選択肢: A 動かさずに指を離したら長押しの知らせを呼ぶ (両方を同時に使える。両方あるときは知らせが指を離すまで遅れる) / B 動かせる項目では長押しは並べ替えだけ / C 長押しの成立時に知らせを呼び、そのまま動かせばドラッグにもする (知らせで出したメニューの下でドラッグが始まるなど崩れやすい)。推奨は A だった。

採用: オーナー提案の案 (B に有効 / 無効のスイッチを足した形)。一覧に並べ替えのスイッチ (仮称「UseDragSort」、名前は提案で設計) を持たせ、有効の間は長押しがハンドルの代わりになり、ふだんの長押しの知らせは呼ばない。並べ替えは「編集」のように必要なときだけ有効にする使い方に応え、常に有効にする一覧は長押しの知らせが使えないと割り切る (オーナーの言葉)。スイッチで長押しの意味が 1 つに決まり、知らせの時機も変わらない。

解釈として記録したこと (オーナーの「通常のロングタップは無効」をそのまま読んだもの): 有効の間は、動かせない項目 (core/ADR-0030) も含めて長押しの知らせを呼ばない。タップの知らせはスイッチによらず変わらない。スイッチの既定は無効 (必要なときだけ有効にする使い方が主のため、並べ替えを宣言しただけで長押しの知らせが止まらないようにする)。

持ち上げ方 (①) と合わせて、開始の操作の契約として core/ADR-0031 を proposed で起票した。スイッチは論点 4 (ソートとの関係) の「有効 / 無効の切り替え口」でもある。

## 2026-09-29: 開始の操作 — 端での自動スクロール (既決事項から導出)

論点 3 の ③ は選択肢を出さずに導いた: 端での自動スクロールは両プラットフォームで付ける。調査では iOS は UIKit のドラッグ & ドロップの経路なら標準で付き、Android の OSS (`sh.calvin.reorderable`) も持っている。速さと反応する範囲は各 OS の自然な形 (iOS は UIKit 標準、Android はそれに近い既定) に任せ、公開の設定は持たない。「自然な形」はここでの推測なので、実装後に実機で見て確かめる。

## 2026-09-29: 開始の操作 — アクセシビリティの移動操作

論点 3 の ④。VoiceOver / TalkBack の利用者が並べ替える手段を決めた。材料: iOS は UIKit のドラッグ & ドロップで VoiceOver の操作が自動で付くとされる (経験則で未確認)、Android の TalkBack には自動で付かない、ライブラリは文言のファイルを持たず読み上げの文言は利用者から受け取る (`KsImage`)、英日の文言をライブラリが持つ案は core/ADR-0024 で翻訳の保守を理由に却下済み。

選択肢: A ライブラリが「前へ移動 / 後ろへ移動」の操作を出し、文言は利用者が渡す (渡さなければ出さない) / B 操作と英日の文言をライブラリが持つ / C iOS は標準任せ、Android は利用者がテンプレートで付ける / D 両 OS とも利用者が付ける。判断の軸は、何も書かなくても使えるか、文言の持ち方、両 OS のそろい方、読み上げで動かしたときに知らせと判定の契約を通るか、実装量。

採用: A (オーナー決定)。iOS の標準に頼らず両 OS で同じ操作を出せ、読み上げで動かしてもドラッグと同じ知らせ・判定・受け入れを通り、文言は `KsImage` と同じく利用者から受け取るのでライブラリに翻訳の保守を持ち込まない。負の面は、文言を渡し忘れると読み上げで並べ替えられないこと (ガイドで案内)。操作の種類 (先頭へ・末尾へ) とグループの境目での動き方は提案で設計する。core/ADR-0032 を proposed で起票した。これで論点 3 を閉じた。

## 2026-09-29: ソートとの関係

初期の agenda は「ソート中は並べ替えを止めるか、並べ替えたら手動の並びに切り替えるか、どちらかを契約にする」としていたが、その後の決定で前提が変わった: ライブラリはソートを知らない (phase-1 の既決。ソートの指定を持つと並びの正が 2 つになり D&D とぶつかる)、並べ替えの有効 / 無効のスイッチがある (core/ADR-0031)、置いたときの知らせに VM がその場で受け入れを返せる (core/ADR-0027)。

選択肢: A ライブラリの契約にはせず、VM の書き方としてガイドに両方載せる (ソート中はスイッチを無効にする / 知らせを受けたら VM がソートを手動に切り替えて並べ替え、受け入れを返す) / B ライブラリに「ソート中」の印を足し、印がある間は並べ替えを止める。判断の軸は、phase-1 の既決との整合、並びの正の数、公開の口、アプリが選べる振る舞い。

採用: A (オーナー決定)。公開の口を増やさず、どちらの振る舞いもアプリが選べる。B は phase-1 で避けた「ライブラリがソートを知る」形になり、スイッチと役割が重なる。既決事項と既存の口からの帰結で新しい方向を足さないため、ADR は起票しない。Sample の並べ替え画面でソートの切り替えも見せるかは提案で決める。

## 2026-09-29: ドラッグ中の配列の差し替え

論点 7 は両プラットフォーム共通の契約で、iOS / Android の実装方式 (論点 5・6) がこれを実装するため、5・6 より先に扱った。前半としてドラッグ中に配列が届いたとき (自動スクロールで末尾に近づいてページングの追加が届く、VM が別の理由で配列を更新する) を決めた。

選択肢: A ドラッグ中は反映を保留して最新の 1 つを持ち、指を離してから反映する (受け入れたら保留分を捨てて VM の配列を待つ、受け入れなければ保留した最新の配列へ戻す) / B 反映しながらドラッグを続ける / C ドラッグを取り消して反映する。判断の軸は、ドラッグ中の見た目、末尾まで運んだときのページングの追加、ドラッグ中の項目が消えたとき、実装の重さ。

採用: A (オーナー決定)。ドラッグ中の見た目が安定し、知らせは項目で表すので (core/ADR-0028) VM の配列が新しくても意味が変わらず、両 OS ともドラッグの途中でデータを入れ替えずに済む。B は指の下で周りが動き、仮の並びに新しい配列を混ぜる実装が重い。C は自動スクロールでページングの追加が届くたびにドラッグが切れる。負の面は、ドラッグ中は届いた変化が見えず、末尾まで運んでも一覧が指を離すまで伸びないこと。

後半 (受け入れた後に並べ替えを含まない配列が先に届いたとき、core/ADR-0027 で持ち越した分) は A から導いた: 受け入れる前に届いていた配列 (保留分) は受け入れた時点で捨てるので古い配列で一度戻るちらつきは起きず、受け入れた後に届いた配列には core/ADR-0027 のとおりそのまま従う (受け入れた後に並べ替えを含まない配列が届くのは VM が受け入れた後で並びを変えたときで、それに従うのが正しい)。core/ADR-0033 を proposed で起票し、core/ADR-0027 の「含まないもの」から参照を張った。これで論点 7 を閉じた。

## 2026-09-29: iOS の実装方式

ここまでの契約 (core/ADR-0026〜0033) を iOS のエンジン (UICollectionView + 差分データソース + 自前のレイアウト、内部の塊) でどう作るかを決めた。

選択肢: A UIKit 標準のドラッグ & ドロップの delegate で作り、差分データソースの並べ替えハンドラは使わない / B 差分データソースの並べ替えハンドラ (`reorderingHandlers`) / C 対話的な移動 (`beginInteractiveMovementForItem`) を自前の長押しで駆動する。判断の軸は、自前のレイアウトで動くか、端での自動スクロール、読み上げのドラッグ操作、長押しの取り合い、持ち上げの見た目、未確認のこと。

採用: A (オーナー決定)。仮の並び (プレースホルダ)・置けない場所を返す口・塊をまたぐ移動・自動スクロール・持ち上げの見た目・VoiceOver のドラッグ操作が標準で揃い、契約にいちばん素直に当てはまる。スイッチが有効の間はドラッグを有効にして長押しの認識器を止め、無効の間はその逆にするので取り合いが起きない。ドラッグの始まりと終わりの間は配列の適用を待たせる (core/ADR-0033)。B は自前のレイアウトで呼ばれない報告 (FB9753149) があり頼れない。C は自動スクロールと持ち上げの見た目が自前になり、読み上げのドラッグ操作も付かない。自前の見出しの固定との干渉は実機で確かめる (TODO)。iPhone ではドラッグを明示的に有効にし、iPad ではアプリの外への持ち出しを止めることは提案の設計に書く。ios/ADR-0011 を proposed で起票した。

## 2026-09-29: Android の実装方式

`sh.calvin.reorderable` の規模・依存・動きの模型・保守を ksn-scout に追加で調べさせ、[artifacts/reorderable-oss-assessment-2026-09-29.md](artifacts/reorderable-oss-assessment-2026-09-29.md) に保存した。要点: グリッドに要る部分は約 1,500 行、実験的・内部の API は使わない、置けない場所で並びを変えないとドラッグ中の項目が指からずれて固まる作り (推測)、span の異なるグリッドでつかみが切れる不具合 (#93) が未解決、依存にすると `org.jetbrains.compose.*` が利用者の依存に加わる、保守はほぼ作者 1 人で 2026 年のコミットは 2 件。

選択肢: A OSS に依存する / B 自前で作る / C OSS のグリッド向けのソースを取り込み、手を入れて自分で持つ。判断の軸は、置けない場所 (core/ADR-0030) を満たせるか、既知の弱点に当たったときに直せるか、自動スクロール・位置飛び・持ち上げを解き直すか、利用者の依存、自分で持つコードの量、上流の修正の取り込み、ライセンスとコメント規約の手当て。推奨は C だった (小さな改変で置けるかの判定を足せる、難所は解いてあるものを使える、当たった不具合を自分で直せる、iOS のエンジンもコードを取り込んで持った前例 — ios/ADR-0001)。

採用: B (オーナー決定。理由の言及はなし)。OSS には依存も取り込みもせず、Compose の公開 API の上に自前で作る。契約を最初から作り込め、利用者の依存も第三者のライセンスの手当ても要らない。負の面は、自動スクロール・先頭の項目を動かしたときの位置飛び・持ち上げ・移動直後の表示のつなぎを一から解くこと (難所と知られた回避策は [artifacts/platform-reorder-research-2026-09-29.md](artifacts/platform-reorder-research-2026-09-29.md) の「公式 API と自前実装」)。android/ADR-0007 を proposed で起票し、却下した C は「オーナー判断」として推奨側の理由を併記した。

これで論点がすべて決まった。提案で設計・確認することを agenda の「提案への申し送り」にまとめた。
