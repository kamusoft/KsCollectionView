## 2026-10-14: 版の付け方と、兄弟ライブラリの踏襲による決定

A1 の最初の問いとして、両プラットフォームで版を 1 つにするかを聞いた。README と 4 つの `SKILL.md` は、版が 1 つの前提 (同じ `{version}` と、1 つの確かめ先) で書かれていて、Android の本体は開発中の版を `-SNAPSHOT` にし、リリースの版を外から渡す作りになっている。

- 選択肢:
  - 1 つの版 (推奨): 6 つのファイルがそのまま使え、兄弟ライブラリと揃う。変わっていない側にも新しい版が出て、片方の失敗で全体が止まる
  - プラットフォームごとの版: 変わった側だけ出せる。確かめ先が分かれ、6 つのファイルと許可する URL の一覧を書き直すことになり、本リポジトリの tag に接頭辞が要る
- オーナーの決定: 1 つの版。あわせて「以降の論点は兄弟ライブラリを踏襲するで決めてもらって OK」と指示した
- 踏襲で決めた範囲: A1 の残り (tag の形・プレリリースの形・初回の版)・A2・A3・A4・B1。決めた内容は agenda の決定事項にあり、ADR cross/0021〜0024 を proposed で起票した
- 兄弟ライブラリと違えた所:
  - NuGet と MAUI の工程を持たない
  - 利用者役に、リリースの工程が作った成果物を受け取る形を足す (今の利用者役は持たない)
  - iOS のテストは、検証 CI で走らせない決まり (cross/ADR-0013) のまま、各変更の完了判定に任せる
- リリースの手順の置き場は、最初、cross/ADR-0017 が利用者向け Skill の追従で専用の Skill を却下した理由を当てはめ、専用の Skill を作らない方向で考えた
  - 同じ日に別のセッションで、変更 `user-skill-refresh-skill` が始まっていて、cross/ADR-0017 を置き換える cross/ADR-0020 (追従を専用の Skill で行う) を proposed で起票していた。手順のガイドがメインのセッションに読まれる保証が無い、という理由である
  - そこで兄弟ライブラリの形 (手順の正は handbook、入口に専用の Skill、Skill は handbook を読むだけ) に戻した。置き方はその変更に揃える
  - 番号が重なったので、起票した ADR を 0021〜0024 に付け直した
- 兄弟ライブラリに決まりが無かったもの: B1 の節目の基準は、兄弟ライブラリと同じく置かないことにした。B2 (管理者が保護を迂回してよい条件) と B3 (secret を検出したときの手順) は、踏襲する先が無いので、オーナーに聞く

## 2026-10-14: 管理者が保護を迂回してよい条件 (B2)

`main` の保護は必須の検査が 5 つで、管理者には強制していない。利用者役の 2 つの検査は外部の依存 (Nuke・Maven の依存) を取得するので、コードの誤りでない理由で止まり得る。兄弟ライブラリには決まりが無く、CI に迂回の権限を持たせる案は却下している。

- 選択肢:
  - 迂回しない (推奨): 再実行して通るまで待つ
  - 外部の取得の失敗に限って迂回してよい: 原因の見分け方と理由の残し方を手順に書く
  - 決まりを置かない
- 推奨の理由: リリースの workflow も公開の前に同じ検証と利用者役の確認を流し、同じ外部の依存を取得するので、迂回してもリリースは早まらない。得られるのは、検査の通っていない commit が `main` に入ることだけ。待つのは、リリース以外の `main` 宛て (文書の修正など) が障害の間に入れられないことだけになる
- オーナーの決定: 迂回しない。保護の設定は今のまま (管理者に強制しない) にし、手順で決める
- ADR にしない。手順の決まりで、いつでも戻せる (選別基準のどれにも当たらない)

## 2026-10-14: secret を検出したときの手順 (B3)

最初の提示は、検出の仕組み 4 つ (commit の前の gitleaks・push の保護・検証 CI の検査・GitHub の secret の検査) の表から始めたため、オーナーに伝わらなかった。「パスワードや鍵をうっかり commit したら、どうするか」を、GitHub に送る前に気づいた場合と、送った後に気づいた場合の 2 通りで言い直した (教訓 `open-exploration-with-plain-problem-summary` の 3 回目として捕捉した)。

- 選択肢:
  - 送ったかどうかで分ける (推奨): 送る前なら手元の commit から消すだけ、送った後なら無効化して取り替える
  - いつも取り替える: 迷わないが、送る前でも署名の鍵を作り直す手間がかかる (新しい公開鍵の登録し直しが要る)
  - 取り替えて、履歴からも消す: 公開済みの写しや fork から消えず効き目が薄い。`develop` の強制 push の禁止と、履歴をそのまま公開する決まり (cross/ADR-0009) にぶつかる
- オーナーの決定: 送ったかどうかで分ける
- ADR にしない。手順の決まりで、いつでも戻せる (選別基準のどれにも当たらない)
- これで論点がすべて決まった。誤検出の扱いは提案で決める

## 2026-10-14: リリースの Skill の中身 (A3 の補い)

オーナーから「兄弟ライブラリにあるリリーススキルの対応は含まれてたっけ?」と問われた。決定事項にあったのは、専用の Skill を入口に置き、手順の正を handbook にすることと、置き方を揃えることだけで、Skill の中身は議論していなかった (調査でも本文を読んでいなかった)。

- 兄弟ライブラリの Skill を読んだ。自分で持つのは 3 つだけ: 変更の節の下書きの作り方、確認を版と文面の 1 回にまとめてあとは公開まで止まらずに進める境界、止まる条件。ほかに、CI を自分で見張ること、自分からは起動しないこと
- 兄弟ライブラリにある Pull Request のひな形 (変更の節の書き方) が、本リポジトリには無いと分かった
- 「以降の論点は兄弟ライブラリを踏襲する」の指示の範囲として、中身も同じにする決定を足した。確認の 1 回の後に、Pull Request のマージ・本番の起動・tag の作成まで進めてよいとする境界は、取り消せない公開を含むので、報告でオーナーに示した
