# 利用者ドキュメント

skills/ と README を制作し、源泉 (kasane/ とコード) に追従させる仕組みを決める。

## 論点

論点 1〜7 はすべて決定済みで、決定事項に移した (2026-10-10)。方針 (2 Skill × en/ja・README はルートの 2 枚) は [cross/ADR-0005](../../../../decisions/cross/0005-user-docs-as-agent-skills-and-root-readme.md) で accepted 済み。以下は、制作のときに載せる事項の申し送りである。

### phase-8 からの申し送り (2026-09-08)

- 利用者ドキュメント (skills/ 方式) に画像ロードの運用を含める。原料は concepts `core/core-model/image-loading.md` の責務境界と「してはいけないこと」。含める項目は次の表

| 項目 | 要点 |
|---|---|
| 先読みに宣言する URL | グリッドにはサムネイル用途の寸法で配信される URL を宣言する |
| iOS のディスクキャッシュ | 起動時に `KsImagePipeline.enableSharedDiskCache()` を一度呼ぶ。delegate を使うアプリは自分でパイプラインを組む |
| iOS の `remove` | 消したソースはローダー付属ビューとキャッシュを共有しなくなる |
| Android のキャッシュ操作 | androidx.startup の初期化が前提。無効化した構成では警告だけで何もしない |

### phase-8 からの申し送り (2026-09-24、prefetch-display-size)

- 利用者ドキュメントの画像ロードの項目に、先読みの要素 `KsResource` の幅と任意キーの運用を足す。原料は concepts `core/core-model/image-loading.md` の「先読みの幅」「任意キー」の節と「してはいけないこと」。足す項目は次の表

| 項目 | 要点 |
|---|---|
| 先読みの幅 | グリッドの幅いっぱいの画像は列幅、セル内の固定サイズの画像は固定値。概算でよく、大きめに書く (小さめだと引き当てに外れるか見た目が甘くなる)。幅は取得とディスクの量を減らさない |
| 任意キー | 署名付き URL のように URL が変わる画像に使う。先読みの要素とセルの `KsImage` の 2 か所に同じキーを書き (モデルから両方を作る関数を 1 つ用意すると食い違わない)、違う画像に同じキーを付けない |
| キー付きの画像の削除とローダー付属ビュー | `KsImageCache.remove` には同じキーを付けたソースを渡す。キー付きの項目はローダー付属ビュー (`LazyImage` / `AsyncImage`) とキャッシュを共有しない |

### phase-4 からの申し送り (2026-09-26、sections-grouping)

利用者ドキュメントに載せる事項 (原料は concepts `core/core-model/collection-items.md` / `core/styling/collection-layout.md`):

- グループの宣言 (iOS `.groups(by:pinnedHeaders:header:)` / Android `KsGroups`) と、同じグループの項目を配列の中で続けて並べる責任が利用者にあること (離れて現れる同じ値は不正入力)
- 全画面に広げた一覧 (iOS `.ignoresSafeArea()` / Android edge-to-edge) では、ルートのヘッダーは安全領域に被ってよく、バーの分の大きさは利用者がルートのヘッダーで調整すること。ライブラリが合わせるのは固定中の見出しだけ (core/ADR-0017)
- Android のグループの値は状態保存に載る型 (Bundle に入る型) であること
- グループの値の取り出し方 (キーパス / ラムダ) は表示中に切り替えてよいこと

### phase-5 からの申し送り (2026-09-29、paging-state-machine)

ページング・Pull to Refresh の利用者向けガイド (Skill) に書く約束ごと。出典は ../../../../changes/archive/2026-09-29-paging-state-machine/deviation.md と core/ADR-0019〜0025、公開契約の現在の形は concepts/core/core-model/collection-paging.md。

- 項目があるときの取り直しの失敗は失敗の状態にせず元の状態に戻し、知らせはアプリが出す (core/ADR-0019)
- 最初の読み込みはライブラリが頼むので VM は自分で始めない (始めるなら状態を先に書き換える)。続きありのまま空のページで待機に戻すと頼み続ける (core/ADR-0020)
- 失敗・終端・空は既定で出ない。失敗の表示を設定しないと再試行の手段が出ず (Pull to Refresh が無ければ止まる)、空の表示を設定しないと 0 件の一覧は真っ白 (core/ADR-0024)
- 続きのページが同じグループの値で始まればそのグループが伸び、並び順を崩さないのは利用者の責任 (素材: phases/phase-5-paging-state-machine/artifacts/group-extends-across-pages.md)
- 状態と配列は同じ回に書き換える。次ページ要求の処理から戻る前に状態を追加読み込み中にする。VM が自分で取り直すときは古い読み込みの結果を捨てる (core/ADR-0021・0022・0023 の負の帰結)
- VM が自分で始める取り直しを先頭から見せたいときは、取り直し中が一覧に届いてから差し替えるか、差し替えと一緒に先頭へのスクロール命令 (`scrollToStart`) を出す。Pull to Refresh の取り直しはライブラリが先頭を表示する (core/ADR-0021)
- 差し替えた「次のページの読み込み中」の表示は、その範囲のタップを止め、範囲から始めたドラッグは一覧のスクロールになる。既定の表示はタッチを受けない
- Pull to Refresh の取り直しのインジケータを出している間にスクロールして失敗し配列を変えずに状態を戻すと、iOS は先頭へ戻り、Android はその位置に残る (両プラットフォームの差として受け入れ済み)
- Android では `onLoadMore` / `onRefresh` が投げた例外 (取り消し以外) をライブラリは握りつぶさず、コルーチンと同じく伝える

### phase-6 からの申し送り (2026-10-01、drag-reorder)

並べ替えの利用者向けガイド (Skill) に書く約束ごと。出典は ../../../../changes/archive/2026-10-01-drag-reorder/deviation.md と core/ADR-0026〜0034・ios/ADR-0011・android/ADR-0007、公開契約の現在の形は concepts の core/core-model/collection-reorder.md。

#### ガイドに書く約束ごと (drag-reorder)

- 受け入れたら配列を並べ替えて渡す。受け入れたのに並べ替えないと、次に配列が届くまで表示と配列がずれる。保存の失敗は元の並びの配列を渡し直して表す (core/ADR-0027)
- 行き先は項目で届く。行き先の項目が配列から消えていたら受け入れないと返す (core/ADR-0028)
- グループをまたぐときは、VM が動かした項目のグループの値を書き換える。空のグループへは移せない (core/ADR-0029)。グループの宣言を付け外しできる画面では、外している間に動かした項目のグループの値も隣の項目に合わせる
- 「ここに置けるか」はドラッグ中に何度も呼ばれるので、軽い同期の判定にする (core/ADR-0030)
- 並べ替えのスイッチが有効の間は長押しの知らせが呼ばれない。常に有効にする一覧では長押しの知らせを使えない (core/ADR-0031)
- 読み上げの移動操作は、文言を渡さないと出ない (core/ADR-0032)。iOS は、文言を渡した一覧で並べ替えのスイッチが有効の間、行の組み立ての負荷が増える (Simulator で主スレッドの CPU 約 5〜8%)
- ドラッグ中に届いた配列は指を離すまで表示に出ず、ドラッグ中は追加読み込みも始まらない (core/ADR-0033・0034)
- ソート中の 2 つの書き方: ソート中は並べ替えのスイッチを無効にする / 置いたときの処理で手動の並びへ切り替える
- 両プラットフォームで動きが違う点: iOS は UIKit 標準の並べ替えの動きに従う (隙間は指を止めてから動く・別のグループの末尾へはいったん手前に入れてから最後の項目の上で止める・受け入れないときは置いた位置に収まってから戻る・取りやめは指を離したときに戻る・一覧の外ではプレビューが小さくなる)。Android は指の位置で決まり、見出しより上なら前のグループの末尾に直接置ける
- Android は、テンプレートの根が背景を塗らないと、持ち上げた項目の影が透けて見える

### phase-7-2 からの申し送り (2026-10-09、package-distribution)

## 決定事項

### Skill の `references/` の分け方 (2026-10-10)

- 利用者のやりたいことで 5 枚に分ける。iOS と Android の Skill は同じ 5 枚を持つ (能力マップを揃える。cross/ADR-0005)
- ファイル名は提案のときに決める
- ADR にはしていない (cross/ADR-0005 の方向の中での形で、分け直しは変更フローで行える)

| 枚 | 載せる範囲 | 源泉の concepts |
|---|---|---|
| 一覧を出す | 配列・ID・テンプレートの切り替え・タップと長押し・スクロール制御・配列の差し替え・不正入力の挙動 | `core/core-model/collection-items.md`・`collection-interaction.md` |
| 並べ方と見た目 | リストとグリッド・列数・余白・区切り線・ヘッダーとフッター・グループと固定見出し・安全領域 | `core/styling/collection-layout.md` (グループの宣言は `collection-items.md`) |
| ページングと Pull to Refresh | 5 つの状態・次のページの要求・6 つの表示・VM が守る書き方 | `core/core-model/collection-paging.md` |
| 並べ替え | 並べ替えのスイッチ・置いたときの処理・グループをまたぐ移動・読み上げの移動操作 | `core/core-model/collection-reorder.md` |
| 画像 | 先読み・`KsImage`・キャッシュの操作 | `core/core-model/image-loading.md` |

### 相手のプラットフォームとの差の書き方 (2026-10-10)

- 動きが違う機能と、片方にしか無い指定は、その機能を説明している場所に 1〜2 文で書く。相手のプラットフォームのコードは載せない
- 差をまとめた節は作らない。相手の Skill に触れるときは名前だけにする (cross/ADR-0005)
- 載せる差は、源泉の concepts と申し送りから拾う (並べ替えの動き・Pull to Refresh が失敗したときの位置・親の状態を渡す指定・ディスクキャッシュの準備など)
- ADR にはしていない (書き方の決まりで、提案のときに規約 (handbook) の候補として扱う)

### `SKILL.md` の節立てと `references/` の書き方 (2026-10-10、議論側の既定)

翻案元と同じ並びを既定にした (比べる軸が無いので、選択肢を諮っていない)。

- `SKILL.md` の節は 5 つ: 何のライブラリか (見出しの直下の 1 段落)・できること (やりたいことから `references/` の 1 枚への表)・導入 (依存の宣言と必要な環境)・最小の動く例・`references/` の一覧
- `references/` の各 1 枚は、やりたいことを見出しにして、動くコードと約束ごとを並べる
- frontmatter は `name`・`description`・`license`・`metadata.language`・`metadata.source` (配布元の URL。「Skill の外への参照の扱い」で、書いてよいと決めた)
- en と ja は、見出しの並びとコードブロックを一致させる (cross/ADR-0005 の翻訳ロックステップ)

### 追従のずれの見つけ方 (2026-10-10)

- Skill が源泉からずれていないかは、オーナーが頼んだときだけ確かめる (翻案元と同じ)。CI では止めない
- 頼み忘れると、古い Skill のままリリースされ得る (機械は止めない)
- 理由は、追従をいつ動かすかの運用を兄弟ライブラリと揃えるため (オーナーの判断)
- 追従の仕組みの 3 つの決定 (ずれの見つけ方・変わった源泉の見分け方・手順の置き場所) は、[cross/ADR-0017](../../../../decisions/cross/0017-user-skill-refresh-on-request-by-commit-diff.md) (proposed) にまとめた

### 変わった源泉の見分け方 (2026-10-10)

- 前回追従した commit の ID を 1 つ覚えておき、その commit から今までの、源泉のパスの差分を git で出す。ファイルごとのハッシュは持たない
- 追従は、変わった分をまとめて行う (一部だけ直して残りを次回に回す形は取らない)
- 源泉と Skill の 1 枚との対応は、「Skill の `references/` の分け方」の表を出発点にする。覚えておく場所と形は、提案のときに決める
- 公開 API の名前が Skill から漏れていないかの確認は、これとは別の物差しで、論点 5 で扱う

### 追従の手順の置き場所 (2026-10-10)

- 手順は handbook のガイド 1 枚に書き、差分を出す部分と検査する部分は `scripts/` のスクリプトにする。プロジェクト内の専用の Skill は作らない
- ガイドは、`skills/` を触る作業で必ず読まれるようにする (handbook の「適用のきっかけ」にパスを書く)
- スクリプトのテストは、今の CI のスクリプトのテストに乗せる
- ハーネス (Kasane) 側に共通の追従の道具を持つ案は、このリポジトリの変更では作れないので扱っていない

### インストール例の版の書き方 (2026-10-10)

- インストール例には具体の版を書かず、`{version}` を置く。置き換えることと、そのままでは依存の解決に失敗することを、例のそばに書く
- 対象は 6 か所 (ルートの README 2 枚と、各 Skill の `SKILL.md` の導入の節 4 部)
- リリースの工程は、README と Skill の版を書き換えない (置き換えの仕組みを持たない)
- 最新の版は Release の一覧で確かめてもらう。案内先の Release をどこにどう作るかは phase-7-4 が決め、URL はその決定を待つ
- SwiftPM の例は、handbook の `cross/public-identifiers.md` と利用者役と同じ、版を 1 つに決める書き方 (`exact:`) で書く
- ADR は [cross/ADR-0018](../../../../decisions/cross/0018-install-examples-without-concrete-version.md) (proposed)

### Skill の外への参照の扱い (2026-10-10)

- cross/ADR-0005 の条項「Skill の外のファイル・URL への参照を持たない」を、何のための参照かで分ける形に改める
- ADR は [cross/ADR-0019](../../../../decisions/cross/0019-skill-external-references-by-purpose.md) (proposed。cross/ADR-0005 の一部だけを置き換える)
- 持たないもの: 知識を Skill の外に委ねる参照 (README・索引・相手の Skill・リポジトリの中の文書へ、続きをそちらで読ませる形)
- 書いてよいもの: 操作の対象の URL (依存に書く Package URL・最新の版の確かめ先・不具合の報告先・配布元を示す frontmatter の項目)
- 線引きは機械では確かめられない。守り方は論点 5 で決める

### README の最小コード例の検査 (2026-10-10)

- README の最小コード例は、利用者役の画面のファイル全体と完全一致させる (翻案元と同じ)。README に載る例が、CI でビルドされているファイルそのものになる
- 利用者役の画面のソースを、README に載せる形に書き直す (コメントを消す・モデルと画面を 1 ファイルにする・Android は package の宣言を持たない置き方にする)
- 検査は、今の CI のスクリプトのテストに足す (検査の名前は増えない)。比べる相手は README の英日 2 枚とも
- 各 Skill の「最小の動く例」は、この一致の検査の対象にしない (翻案元と同じ)
- ADR にはしていない (利用者役でビルドを確かめる決定 cross/ADR-0016 の中での形)

### インストール例の検査 (2026-10-10、議論側の既定)

phase-7-2 が「README のインストール例と利用者役を一致させる検査をこのフェーズで扱う」と送ってきており、比べる軸が残らなかったので、選択肢を諮っていない。

- 対象は、インストール例が載る 6 か所 (README の英日 2 枚と、各 Skill の `SKILL.md` の 4 部)
- 例の値 (SwiftPM の Package URL・package の名前・product の名前、Maven の座標) が、利用者役が公開済みの配布物を取るときに使う値と同じであること
- 版の位置が `{version}` で、具体の版が書かれていないこと。最新の版の確かめ先の案内が、同じファイルにあること (cross/ADR-0018)
- 英語版と日本語版で、例の種類と数が同じであること
- 検査は、今の CI のスクリプトのテストに足す

### README の対応プラットフォームの案内とスクリーンショット (2026-10-10)

- README にスクリーンショットの節を置く (概要の次。翻案元と同じ)。両プラットフォームの代表の画面を数枚、Sample から撮って `assets/` に置く。どの画面を何枚撮るかは、提案のときに決める
- スクリーンショットの節は cross/ADR-0005 が挙げた節には無いが、README を利用者の入口に絞る決定の範囲内として足す
- 画像は追従の仕組みの対象の外。見た目を変えたときの撮り直しは、人が気付いて行う
- 必要な環境は、「対応プラットフォーム」の節の表 1 枚で案内する (議論側の既定)。翻案元の形に Xcode の行を足し、Android は、利用者に求める下限と、ライブラリのビルドに使った版を分ける
- 必要な環境の値の正は、ビルドの設定。追従のときに差分を出す対象のパスに、ビルドの設定を入れる (議論側の既定)

### Skill 自身の整合の検査 (2026-10-10)

源泉を見なくても `skills/` の中だけで合否が決まる検査を、追従の手順の中に加えて、CI のスクリプトのテストでも毎回流す。README の英日の見出しの一致を CI で確かめている今の形を、`skills/` に広げる。

| 検査 | 守る決まり |
|---|---|
| 英語版と日本語版で、ファイルの集合・見出しの並び・コードブロックが同じ | 翻訳ロックステップ (cross/ADR-0005) |
| frontmatter の項目 (name が英日で同じ・言語が置き場と合う) | 同上 |
| Skill の外のファイルへのリンクが無い | 閉世界性 (cross/ADR-0019) |
| Skill の中の URL が、許可した一覧にあるものだけ | 同上。許可する URL を一覧で持ち、一覧に足すときに人が判断する |
| 決めた内部の用語 (ADR の番号・開発の記録の言葉など) が無い | リポジトリ内部の用語を漏らさない (cross/ADR-0005) |

- 源泉と比べる検査 (公開 API の名前の網羅・必要な環境の値) は、CI には置かない。追従の手順の中だけで流す (cross/ADR-0017)
- ADR にはしていない (検査の置き場所で、後から変えられる。手順と一覧は、提案のときに handbook の候補として扱う)

### 公開 API の名前の網羅の確かめ方 (2026-10-10)

- 基準は、公開 API の名前が Skill のどこかに一度は現れること。詳しい説明やコード例までは求めない (翻案元と同じ)
- 漏れを数える元は、各プラットフォームのコードの公開の宣言にする (concepts に書かれた名前とは比べない)。拾う名前の粒度 (引数の名前まで拾うか) は、提案のときに決める
- 結果は報告だけで、自動では直さない。載せるか外すかはオーナーが判断し、外すと決めた名前は一覧に残す
- 流すのは追従の手順の中だけ (CI には置かない)
- ADR にはしていない (確かめ方の形。基準と外す一覧は、提案のときに handbook の候補として扱う)

### 初回の制作で、検収の前に確かめること (2026-10-10)

- 変更フローのレビューに加えて、配った先を再現した確認を行う。Skill の 1 ディレクトリだけを渡した、リポジトリを知らない新しいエージェントを使う
- 読ませる確認: 分からない言葉・足りない説明・冒頭に「これは何か」があるかを挙げさせる
- 使わせる確認: 決めた課題を Skill だけを頼りに書かせ、利用者役と同じ形でビルドが通ることを確かめる。課題は `references/` の 1 枚に 1 つを目安にし、中身は提案のときに決める
- 使わせる確認で落ちたときは、Skill の欠けか、エージェントの書き損じかを仕分ける。つまずいた箇所は記録に残す
- 追従のときは、機械の検査・差分のレビュー・オーナーの承認までとする。構成を大きく変えるときは、初回と同じ確かめ方をする (議論側の既定)

### 変更の切り方 (2026-10-10)

フェーズは分けず、1 つの変更でやりきる (L 級の見込み)。作るものは次の 4 つのまとまりである。

| まとまり | 作るもの |
|---|---|
| README まわり | ルートの README 2 枚 (スクリーンショットの節を含む)・スクリーンショットの撮影・利用者役のソースの書き直し・最小コード例の検査・インストール例の検査 |
| Skill まわり | Skill の文書 24 枚 (2 Skill × 英日 × `SKILL.md` と `references/` 5 枚)・索引 2 枚・Skill 自身の整合の検査 5 つ・許可する URL と内部の用語の一覧 |
| 追従まわり | 追従の手順 (handbook)・差分を出す道具・前回追従した commit の記録・公開 API の名前を拾う道具 (Swift と Kotlin)・外す名前の一覧 |
| 確かめ | 配った先を再現した確認 (読ませる・使わせる) |
