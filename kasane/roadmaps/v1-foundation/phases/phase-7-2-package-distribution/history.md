## 2026-10-09: 論点 1-a — SwiftPM をどこから配るか

SwiftPM は git のリポジトリのルートにあるマニフェストしか解決できず、今の `ios/Package.swift` のままでは配れない。ルートにマニフェストを置かないことは cross/ADR-0002 が決めている。SwiftPM の利用者は、依存するリポジトリを履歴ごと取得する (翻案元の 0018 の Context)。

| 案 | 内容 | 評価 |
|---|---|---|
| A: 配信用の別リポジトリから配る (採用) | `KsCollectionView-SPM` に `ios/` の本体の写しを置き、リリースのたびに CI が送る | 利用者が取得するのは 1 MB 前後の見込み (兄弟の実績は 0.4〜0.8 MB)。既存の決定とマニフェストを変えない。兄弟と揃う。2 つ目のリポジトリと書き込み用の鍵が要り、利用者が見る場所が 2 か所になり、package の名前が `KsCollectionView-SPM` になる |
| B: このリポジトリから直接配る | ルートにマニフェストを置く | 場所は 1 か所で、名前も製品名のまま。利用者が開発の記録と証跡の画像ごと (約 30 MB、増え続ける) 取得する。cross/ADR-0002 の改訂が要り、マニフェストを 2 枚持つか、開発の入口を移すことになる |
| C: ビルド済みのバイナリで配る | xcframework を配る | 利用者の側のビルドが速くなる。リリースのたびのビルドと照合値の管理、Swift の版の縛り、Nuke への依存の包みが増える |

オーナーは A を選んだ。推した理由は、利用者が取得する量の差、既存の決定と開発の形を変えずに済むこと、兄弟 2 つが同じ形で運用中で道具と手順を翻案できることの 3 つ。リポジトリ名は兄弟と同じ形の `KsCollectionView-SPM` を既定として示し、変更の指示は無かった。ADR は cross/ADR-0015 を proposed で起票した。

Android の経路は Maven Central で、cross/ADR-0003 が前提にしているため、選択肢を諮っていない (議論側の既定)。

## 2026-10-09: 論点 1-c — 対応する Xcode の宣言と案内

マニフェストは Swift 6.2 のツール (Xcode 26.0 以降) から使えると宣言しているが、確かめているのは手元も検証 CI も Xcode 27.0 (Swift 6.4) だけである。phase-7-1 は、Xcode 26 でビルドできるかを CI で確かめないと決め、案内の書き方をこのフェーズに残した。マニフェストは書き換えずに写すので (1-a)、この宣言がそのまま利用者に届く。

確かめたこと: 本体のソースの版の分岐は iOS 18 の 1 か所だけで、iOS 26・27 だけの API を使い分ける箇所は無い。Swift 6.3・6.4 で入った書き方を使っているかは、手元に Xcode 26 が無く確かめていない。翻案元は宣言が Swift 5.10 のままで、確認は Xcode 27 だけ、README に Xcode の版は書いていない。

| 案 | 内容 | 評価 |
|---|---|---|
| A: 宣言を確かめた版に上げる (採用) | 宣言を Swift 6.4 に上げ、Xcode 27 以上と案内する | 宣言と確認が一致する。Xcode 26 の利用者は使えないが、依存を解決する時点で理由が分かる。後から下げても利用者を壊さない |
| B: 宣言はそのまま、案内で断る | Swift 6.2 の宣言を残し、確認は Xcode 27 だけと案内する | Xcode 26 でも入れられる。ビルドできるかは利用者が試すまで分からず、後の変更で壊れても気付けない |
| C: Xcode 26 でも確かめる | 利用者の立場のビルドの確認を、Xcode 26 のランナーでも走らせる | Xcode 26 を対応と言える。phase-7-1 の決定を改め、macOS のジョブが 1 本増える |

オーナーは A を選んだ。推した理由は、確かめる手段の無い版を使えると宣言しなくて済むこと、利用者のつまずき方が解決の時点の分かりやすいものになること、宣言は後から下げる向きなら利用者を壊さないことの 3 つ。ADR にはしていない (宣言は設定で、下げる向きには後から変えられる)。

## 2026-10-09: 論点 2-a — 利用者の立場のビルドの確認の形

公開物を利用者の立場で確かめる仕組みは無い。Sample は両プラットフォームともソースを参照している (iOS はプロジェクトのファイルに固定したローカル参照、Android は composite build の明示の置き換え)。Sample のビルドが通っても、写しの入れ漏れ・発行物の依存の宣言の漏れ・配信用リポジトリのルートでのマニフェストの解決は確かめられない。

| 案 | 内容 | 評価 |
|---|---|---|
| A: 専用の小さな利用者役を置く (採用) | `verification/` の最小のプロジェクトが、利用者と同じ書き方で公開前の成果物を参照してビルドする | 入れ漏れ・依存の宣言の漏れ・マニフェストの誤りが見つかる。利用者の書き方を確かめられ、公開の後の確認にも同じ利用者役を使える。小さなソース 2 つと準備のスクリプトを維持する |
| B: Sample を公開物の参照に切り替える | 利用者役を別に持たない | 見つかる壊れ方は A と同じ。Sample に参照の切り替えが要り、Android の「置き換えが外れたら必ずエラー」の安全策に抜け道ができる。利用者の書き方は確かめられない |
| C: 中身の照合だけにする | 写しのファイルと発行物の依存を照合し、ビルドしない | 数秒で終わる。利用者の側でコンパイルできない壊れ方は見つからない |

オーナーは A を選んだ。推した理由は、利用者と同じ書き方で確かめられること、Sample の安全策を崩さないこと、公開の後の確認に使い回せることの 3 つ。翻案元の実測は iOS 1 分 21 秒・Android 2 分 48 秒 (成果物を受け取る形) で、自リポジトリでは未計測。

ADR は起票していない。確かめる範囲と必須の検査に足すかの結論 (2-b) とあわせて、検証 CI が保証する範囲の決定として起票するかを判断する。

2-b は判断が 2 つ (どこまで確かめるか・必須の検査に足すか) あるため、2-b-1 と 2-b-2 に分けて順に諮ることにした。

## 2026-10-09: 論点 2-b-1 — 利用者役で確かめる範囲

phase-7-1 が「ビルドまでにするか、実行まで確かめるか」を申し送った論点。利用者役を CI の上で起動して確かめる案は、cross/ADR-0013 が同じ理由 (ランナーの遅さと不安定さで、必須の検査がコードの誤りと関係なく止まる) で外した案に当たるため、選択肢に入れなかった。

確かめたこと:

| 確かめたこと | 結果 |
|---|---|
| コード縮小 (R8) を有効にしたアプリで動かした実績 | 無い。Sample のリリースの設定もコード縮小が無効 (`samples/android/app/build.gradle.kts`) |
| 起動時の初期化のクラスが残るか | `androidx.startup` (startup-runtime 1.1.1) の配布物の中の規則が、初期化のクラスとその引数なしのコンストラクタを残す |
| 本体が名前から引くクラス | 見当たらない |
| 翻案元 | ビルドまで。コード縮小は無効で、規則の不足は検出できないと明記している |

| 案 | 内容 | 評価 |
|---|---|---|
| A: ビルドまで | コード縮小は無効のまま組み立てる (翻案元と同じ) | 入れ漏れと依存の宣言の漏れは見つかる。コード縮小に関わる壊れ方は CI では見つからない |
| B: ビルドまで、Android はコード縮小あり (採用) | Android の利用者役は R8 を有効にして組み立てる | A に加えて、コード縮小の途中で見つかる不整合が CI で止まる。組み立てが少し長くなる (未計測) |
| C: B に加えて、節目ごとに手元で起動 | リリース候補にする節目ごとに、手元で利用者役を起動する | 起動して落ちる壊れ方まで毎回見つかる。手元の確認が 1 つ増える |

オーナーは B を選んだ。推した理由は、利用者の本番に近い形を毎回通せること、CI の決まり (起動しない) を変えないこと、起動の確認は今回の実装で 1 回行えば足り、節目ごとに置くかはリリースの基準で決められることの 3 つ。「実装のときに手元で 1 回起動して確かめる」は、どの案でも行う既定として示した。

## 2026-10-09: 論点 2-b-2 — 必須の検査に足すか

`main` 宛ての Pull Request の必須の検査は `lint`・`ios / verify`・`android / verify` の 3 つで、`develop` への push でも同じ 3 つが走る。`main` 宛ての Pull Request はリリースの節目である (cross/ADR-0010)。翻案元は、利用者の立場の確認を `main` 宛ての Pull Request のときだけ走らせて必須にしている (以前は毎回走らせ、1 回のマージで macOS のランナーを約 54 分使っていた)。

| 案 | 内容 | 評価 |
|---|---|---|
| A: `main` 宛てで走らせて必須 (採用) | `main` 宛ての Pull Request のときだけ走り、落ちたらマージできない | 配布物の壊れが、リリースを起動する前の節目で止まる。節目ごとにランナーを数分使い、`main` の保護に検査の名前を 2 つ登録する |
| B: `main` 宛てで走らせるが参考だけ | 落ちてもマージできる | 保護の設定を変えずに済む。壊れたまま `main` に入る道が残る |
| C: `develop` への push でも毎回 | push のたびに走り、`main` 宛てでは必須 | いちばん早く気付ける。push ごとに macOS のランナーを数分使う |
| D: リリースのときだけ | 検証 CI には足さず、リリースの workflow の中だけで確かめる | Pull Request の検査は軽いまま。気付くのがリリースを起動したときになる |

オーナーは A を選んだ。推した理由は、配布物の壊れをリリースを起動する前に止められること、配布の経路は本体のコードを変えるたびには壊れにくく push のたびに走らせる価値が低いこと、必須にしないと落ちたまま入る道が残ることの 3 つ。検査の名前は、兄弟と同じ `consumer-ios / verify`・`consumer-android / verify` を既定として示し、変更の指示は無かった。

2-a・2-b-1・2-b-2 の結論をまとめて、cross/ADR-0016 を proposed で起票した。コード縮小の有無と、節目ごとに手元で起動する案は、同じ方向の中の形の違いなので、ADR の却下案には入れていない (この history に残る)。cross/ADR-0014 が固定した 3 つの検査の名前は変えず、必須の検査を 2 つ足す形になる (同 ADR の Context が、この確認を足す予定を書いている)。

論点が空になった。phase-3 と phase-7-1 の申し送りは、答えを決定事項の表に移して論点の節から外した。

## 2026-10-09: フェーズの終わり方 — 提案化へ

論点が空になり、TODO が提案の中で確かめる・決める作業だけになったので、終わり方を諮った。案は、提案化する / 既定にした細部 (配布物の中身・検査の名前・起動の確認を 1 回にすること) を見直す / ここで止める、の 3 つ。オーナーは提案化を選んだ。既定にした細部は見直しの指示が無かったので、そのまま提案の前提として持ち込む。

翻案元は同じ範囲を 3 つの変更 (SwiftPM の配布・Maven の配布・利用者の立場の確認) に分けて進めた。自リポジトリは product も Android のモジュールも最初から 1 つなので、それぞれは小さく済む見込みと伝え、変更の大きさの判定は提案を作るときに行うことにした。
