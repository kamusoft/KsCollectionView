# ページング状態機械

無限スクロール・Pull to Refresh・ローディング/エラー/empty 表示を統一した状態モデルで提供する。両プラットフォーム。

### phase-1 からの申し送り (2026-09-01)


公開契約は core/ADR-0005 で確定: 5状態 enum `KsPagingState` を利用者 (VM) が所有し、DSL に状態 + `onLoadMore` を渡す。ライブラリはトリガー発火・多重発火抑止・標準フッター (差し替え可)・Pull to Refresh 接続。利用形は [dsl-samples.md](../phase-1-symmetric-dsl-spec/artifacts/dsl-samples.md) シナリオ3

- 論点「Paging 3 依存か自前か」は ADR-0005 の帰結として自前が既定路線 (状態機械はライブラリ内包でなく利用者所有のため Paging 3 のデータ所有モデルと不整合)
- 残課題: `failed` にエラー内容を持たせるか / 発火しきい値 (旧 `LoadMoreMargin` 相当) を paging 設定に持つか

### phase-3 からの申し送り (2026-09-04)

Pull to Refresh の Compose 側の流儀を確認済み (phase-3 agenda「決定事項」論点 6)。Android の外形は `onRefresh: (suspend () -> Unit)?` 引数で、Swift の `.refreshable { await }` と同じ「非同期処理が終わるまでインジケータを出す」意味論。ライブラリが `LazyVerticalGrid` を material3 `PullToRefreshBox` (1.4 系で stable) で内包し、`isRefreshing` は「`onRefresh` 実行中」または `KsPagingState.Refreshing`。`onRefresh` 未指定なら挟まない。利用者側で包む形は非対称のため不採用。実装は本フェーズで両プラットフォーム同時に行う。

### phase-3 からの申し送り (2026-09-05 実装結果)

`touchFeedbackColor` の意味論が両プラットフォームで非対称: iOS は渡された色をそのままセル全面の塗りにし、Android は material3 の `ripple` が渡された色に自前で不透明度を掛ける (android/ADR-0003 の帰結)。同じ生値を渡すと Android では不可視になるため、Sample「リスト」は描画結果を揃える別の生値を渡している (iOS は accent の 15%、Android は accent そのまま — `kasane/changes/archive/2026-09-05-android-wrapper-foundation/deviation.md` 4 件目)。本フェーズは両プラットフォームの DSL に同時に触るため、ここで統一の方向 (iOS が不透明度を掛ける側に寄せる / Android が生値をそのまま塗る / 語彙を分ける) を決めて sample-parity の生値一致を回復する。

### phase-4 からの申し送り (2026-09-26 実装結果)

- 端を表示中の端への挿入 (core/ADR-0018): いちばん下を表示中に末尾へ項目を足すと、表示範囲は末尾へ送られて末尾に留まる。末尾への追加読み込みでこれがそのまま働くと、フッター (末尾ローディング) が見え続けて次の読み込みが連鎖しうる。追加読み込みの反映を「端への挿入」として扱うか (発火の抑止・フッターを含めた末尾の定義) を本フェーズで決める
- グループとの組み合わせ: 追加読み込みで末尾のグループと同じグループの値の項目が続くと、既存のグループが伸びる (見出しの件数が変わる)。グループの値の不連続は不正入力 (core/ADR-0015) なので、ページの境目でグループが割れない順に並べる責任は利用者にある。この前提と見出しの件数の見え方を、Sample と利用者ドキュメントで扱うかを決める
- 実装の実際: `kasane/changes/archive/2026-09-26-sections-grouping/deviation.md`、Android は末尾への送りを `KsPositionKeeper` の `followEnd` が行う

## 決定事項

- Paging 3 には依存せず、状態機械は自前で持つ (2026-09-26、論点 1)。core/ADR-0005 が却下した「ライブラリがページング全体を内包する」案の理由 (データの所有がライブラリに移り、KMP の共有 VM と組み合わせにくい) が今も成り立つため

### 失敗の状態は中身を持たず、出し方と再試行の行き先は状態と項目が空かどうかで決める (2026-09-26、論点 1)

5 状態は付属値のない列挙のまま (エラーの値も、どの読み込みの失敗かも持たない)。ライブラリが知りたいのは、エラーをどこに出すかと再試行で何を呼ぶかだけで、どちらも状態と項目が空かどうかの組み合わせで決まる。

| 状態 | 項目 | エラーを出す場所 | 再試行で呼ぶもの |
|---|---|---|---|
| 失敗 | 空 | 一覧の真ん中 | 次のページ |
| 失敗 | あり | いちばん下の項目のすぐ下 | 次のページ |

項目があるときの取り直し (Pull to Refresh) の失敗は、失敗の状態にせず元の状態に戻し、知らせるのはアプリ側で行う、と利用者向けガイドに書く。エラーの文言は、差し替えたテンプレートが VM から読む。再試行の行き先は、2026-09-27 に論点 5 で「項目が空でも、いつも次のページ」に改めた (初回の読み込みが次のページの処理で始まり、Pull to Refresh を付けていない一覧には取り直しの処理が無いため)。ADR: core/ADR-0019 (proposed)。初回の読み込み中・空の表示をどの部品で出すかは論点 5、初回の読み込みを誰が始めるかは論点 2・3 で決める。

### 追加読み込みの発火条件 — 残りの項目の数で測り、しきい値は画面数 (既定 1 画面分) (2026-09-26、論点 2)

残りが N 件以下になったら次のページを頼む。旧 `LoadMoreMargin` と同じ意味。数えるのは項目だけで、グループの見出し・ルートのヘッダー / フッターは数えない。画面に実際に出ている項目で数えるため、Compose が画面外の項目を前もって組み立てても影響を受けない (画像の先読みが使う表示中の範囲と同じ取り方)。末尾までの距離で測る案は、Android の Lazy 系がまだ並べていない項目の高さを知らず末尾が近づくまで見積もりになるため、末尾が見えたら頼む案は毎ページ読み込み中の表示を見せるため、採らない。グリッドでは列が多いほど、件数で指定した場合の発火が末尾の手前何行かが縮む。

既定のしきい値は 1 画面分 (今画面に出ている項目の数) とする。列数・向き・項目の大きさが変わっても発火が末尾のおよそ 1 画面手前に保たれ、向き可変のグリッド (core/ADR-0006) でも発火の位置がずれない。固定の件数 (例: 5 件) は列数と項目の大きさで発火の位置が大きく変わり、0 件 (旧 AiForms の既定) は毎ページ読み込みを待たせるため採らない。ページの件数ぶん手前 (Paging 3 の既定) は、ページの件数を VM だけが知っていてライブラリは知らないため採れない。

しきい値は「何画面分手前で頼むか」の画面数で利用者が指定できる公開の設定とし、既定は 1 画面分、0 は最後の項目が画面に入ったら (底に着いてから) 頼む。取得の遅い API のアプリが読み込み中の表示を見せにくくする手段が要り、画面数なら指定しても既定と同じく列数・向きに左右されない。件数での指定は旧 `LoadMoreMargin` の値を移せるが、指定した時点で発火の位置のずれが戻るため採らない。ADR: core/ADR-0020 (proposed)。

### ページングを付けた一覧では、終端に達するまで末尾への追従をしない (2026-09-26、論点 3)

core/ADR-0018 をそのまま適用すると、一番下で読み込み中の表示を見ているところへ次のページが届いたとき、表示範囲が新しい末尾まで送られて届いたページを飛ばし、また末尾にいるため最後のページまで読み込みが連鎖する。終端に達するまでの末尾は仮の端とみなし、差し替えの直前の状態が終端以外なら末尾への挿入でも表示範囲を留めない (届いたページは今の位置の下に現れる)。終端なら ADR-0018 のとおり留める。直前の状態で判定するため、最後のページが届くのと同時に終端になっても飛ばさない。先頭側 (Pull to Refresh で先頭に足された項目) は変えない。ADR: core/ADR-0021 (proposed、amends ADR-0018)。

### 追加読み込みを頼む処理は非同期関数で受け、終わるまでと変わるまで次を頼まない (2026-09-26、論点 3)

頼む処理は Swift は非同期のクロージャ、Kotlin は非同期関数 (`suspend`) で受け、Pull to Refresh と同じ形にする (Kotlin は普通の関数もラムダ・関数参照でそのまま渡せる)。ライブラリは待機で末尾に近いときだけ頼み、一度頼んだら、頼んだ処理が終わり、かつ頼んだ時点から状態か配列が変わるまで次を頼まない。VM が状態の書き換えを遅らせる書き方でも二重に頼まず、実行中の処理をライブラリがつかむので取り直しのときの取り消しを選べる。処理の中で待つ書き方の読み込みは画面を離れると取り消される (続けたいなら VM のスコープで起動する)。ADR: core/ADR-0022 (proposed)。

### 判定し直すきっかけと初回の読み込み — 空で待機ならライブラリが頼む (2026-09-26、論点 3)

「末尾に近いか」はスクロール・配列の差し替え・状態の変化・一覧の大きさの変化のたびに判定し直す (スクロールだけだと 1 ページが画面に満たない一覧が止まるため、選ぶ余地のない前提)。項目が空で待機のときも頼み、初回の読み込みも追加読み込みの処理で始まる。VM は最初の読み込みを書かなくてよい。引き受ける弱点は、VM が自分でも最初の読み込みを始めて状態の書き換えが遅れると二重に読み込むことと、続きありのまま空のページが返ると終端になるまで頼み続けること。空の表示は空で終端のときに出る。空のときは VM が始める案 (推奨していた) と、空のときは取り直しとして頼む案は採らない。ADR: core/ADR-0020 (proposed) に含めた。

### 追加読み込みの間は Pull to Refresh を受け付けない (2026-09-27、論点 3)

取り直し中は状態が待機でないため追加読み込みは始まらない (core/ADR-0022)。逆向き (追加読み込みの途中で引っ張る) は、取り直し後の一覧に古いページが遅れて混ざるため、状態が追加読み込み中の間は両プラットフォームとも引っ張りを受け付けない。取り直しで追加読み込みを取り消す案は、VM が取り消しを失敗として拾うと取り直し中を上書きして壊れ、VM のスコープで起動する書き方には届かないため採らない。Android は material3 1.4.0 の `PullToRefreshBox` に引っ張りを止める設定が無いため、phase-3 で決めた外形 (`PullToRefreshBox` で包む) を改め、有効 / 無効を切り替えられる土台の修飾 (`Modifier.pullToRefresh`) とインジケータで組む。ADR: core/ADR-0023 (proposed)。

### 見える形の取り直しの結果は先頭を表示する (2026-09-27、論点 3)

途中までスクロールしているときに VM が取り直しで一覧を 1 ページ目に差し替えると、iOS は位置を保って新しい末尾に張り付き、Android は見ていた項目が無ければ同じ番号の位置に寄り、どちらもすぐ追加読み込みが始まる (見ていた項目が残れば両プラットフォームで見える場所がずれる)。差し替えの直前の状態が取り直し中なら、差し替えと同時に表示範囲を先頭にする。見える形の取り直しは「最初から見直す」意味で、位置を保ちたい VM は状態を取り直し中にせず配列だけを差し替えれば各プラットフォームの既定の保ち方になる。Pull to Refresh は先頭で引っ張るので変わらない。見ていた項目が残れば保つ案は、留まるか戻るかがページの境目しだいで予測しにくく iOS に新しい仕組みが要るため採らない。ADR: core/ADR-0021 (proposed) を「差し替えの直前の状態で表示範囲の置き方を決める」ADR に書き直してまとめた。

### Pull to Refresh のインジケータは引っ張って始めた取り直しの間だけ出す (2026-09-27、論点 4)

Pull to Refresh は各プラットフォームの自然な形に従い、インジケータは両プラットフォームとも引っ張ったときだけ出す。VM が自分で始めた取り直し (引っ張っていないのに状態が取り直し中) では出さない。引っ張った後は、VM の処理がすぐ戻る書き方でも、状態が取り直し中の間は出し続ける (phase-3 の「処理の実行中、または状態が取り直し中なら出す」を、引っ張って始めた取り直しの間に狭めて残す)。iOS は SwiftUI 標準の `.refreshable { await }` を付けると処理を環境値として受け取れるので、ライブラリがそこから引っ張りの部品を一覧に付ける (選ぶ余地のない受け方)。VM が始めた取り直しの見せ方は論点 5 で扱う。ADR: 追加読み込みの間は引っ張れない決定と合わせて core/ADR-0023 (proposed) にまとめた。

### 既定で出すのは読み込み中の 2 つだけ (アイコン)、失敗・終端・空は設定したときだけ (2026-09-27、論点 5)

| 項目が並んでいるとき (いちばん下の項目のすぐ下) | 項目が 1 件もないとき (一覧の真ん中) | 既定 |
|---|---|---|
| 次のページを読み込み中 | 最初の読み込み中 | 標準のくるくる (アイコンだけ) |
| 次のページの読み込みに失敗 + 再試行 | 最初の読み込みに失敗 + 再試行 | 何も出さない |
| 最後まで読み終えた (終端) | 読み込んだら 0 件 (空) | 何も出さない |

6 つとも差し替え口で設定でき、失敗・終端・空は利用者が設定したときだけ出る。ライブラリは文言と翻訳を持たない。はじめは「6 つ全部を用意する」を選んだが、文言と言語を決める段でオーナーが「アイコンのみ。読み込み失敗・Empty・これ以上ありませんの部品は既定では空。必要なら利用者が設定する」と改めた。英日の文言を持つ案は文言のファイルと翻訳の保守が要り、英語だけは日本語アプリが毎回差し替えることになり、全部アイコンは意味が伝わりにくいため採らない。何も設定しないと、失敗しても再試行の手段が出ず (Pull to Refresh が無ければ止まる)、0 件の一覧は真っ白になる。スケルトン表示は用意せず、最初の読み込み中を差し替えて利用者が作る。図: [artifacts/standard-displays.md](artifacts/standard-displays.md)。ADR: core/ADR-0024 (proposed、amends ADR-0005)。

### VM が自分で取り直している間、項目が並んでいるときは何も出さない (2026-09-27、論点 5)

絞り込みの変更や再読み込みボタンなどで VM が自分で取り直している間 (Pull to Refresh のインジケータは出ない。core/ADR-0023)、項目が並んでいれば古い項目をそのまま見せ、ライブラリは何も重ねない。届いたら先頭から表示し直す (core/ADR-0021)。iOS・Android の標準の一覧にこの場面の表示は無く、取り直しのきっかけはアプリの画面にあるため、見せたいアプリが自分で出す。項目が 1 件もなければ、最初の読み込みと同じ真ん中の「読み込み中」を出す。上端に小さく重ねる案と、項目の上に半透明で重ねる案は、ライブラリ独自の表示が 1 つ増えるため採らない。

### 再試行は、項目が空でもいつも次のページを頼む処理を呼ぶ (2026-09-27、論点 5)

項目が 1 件もない画面の再試行も、次のページを頼む処理を呼ぶ。最初の読み込みはこの処理で始まり、VM のこの処理は項目が空なら最初のページを読むため、Pull to Refresh の失敗も含めて読み込まれる中身は取り直しと同じになる。規則が 1 つで、Pull to Refresh を付けたかどうかで振る舞いが変わらない。取り直しの処理があればそれを呼ぶ案は、規則が 2 段になり、VM が両方の処理で失敗からの呼び出しを受け付ける必要があるため採らない。core/ADR-0019 (proposed) を書き直した。

### 差し替えは 6 つの表示それぞれに口を用意する (2026-09-27、論点 5)

替えたい表示の分だけ書けばよい形にする (Swift は `.pagingEmpty { }` のような modifier、Kotlin は `KsPaging(empty = { })` のような名前付き引数。名前は仮で提案時に決める)。6 つの表示と 1 対 1 で対応し、今の DSL の `.header { }` / `header =` と同じ書き方になる。失敗の表示の差し替えには、ライブラリの再試行を呼ぶ操作を渡す。「いちばん下」と「0 件のとき」の 2 つにまとめる案と、1 つにまとめる案は、1 つだけ替えるときも分岐と標準の表示の呼び出しを書く必要があり、標準の表示を呼ぶ公開の部品も別に要るため採らない。 ADR: core/ADR-0024。

### ページの境目でグループが伸びることは、利用者向けガイドにだけ書く (2026-09-27、論点 6)

続きのページの先頭が最後のグループと同じ値なら、そのグループの続きとして下に足され (グループが伸びる)、ライブラリは伸びた項目の配列で見出しのクロージャを呼び直す。ライブラリは件数を数えず、「N 件」はアプリの見出しが配列の数から出す。同じ値が離れて現れるのは不正入力で、ページの境目で並び順を崩さないのは利用者の責任。この約束ごとは利用者向けガイドにだけ書き、ページングのデモは平らな一覧にする。グループが伸びて見出しが呼び直される動きは、Sample の「差分更新」画面 (グループ化オン + 末尾に挿入) ですでに確かめられる。図: [artifacts/group-extends-across-pages.md](artifacts/group-extends-across-pages.md)。

### タップしたときの色の意味の違いは、既定の色のダーク対応の change に移す (2026-09-27、論点 7)

phase-3 からの申し送り (iOS は渡された色をそのまま塗り、Android の ripple は渡された色を自分で薄くするため、Sample が別々の値を渡している) は、このフェーズでは扱わない。phase-3 が phase-5 に送った理由は「両プラットフォームの DSL に同時に触る」だったが、ページングの change はタップの色のコードに触らない。ライブラリの既定の色を両プラットフォームで見直す `library-default-colors-dark-mode` とテーマが同じなので、その探索メモの未決の論点に移した。ページングの change に同梱する案は無関係な公開 API の変更が混ざり、独立した change にする案は同じ場所に触る change が 2 つに分かれるため採らない。
