# 画像ロード統合

画像の遅延ロード・キャンセル・キャッシュ・プリフェッチをリスト/グリッドの性能要件として成立させる。実行順は基盤 (phase-2/3) の直後・機能フェーズの前 (セル API の形を縛るため後付け不可)。

## 論点

- プリフェッチのリソース宣言: プリフェッチ時点ではセルの View が存在しないため、View 走査ではなく**アイテムから画像 URL を申告させるデータ層 hook** (`prefetchResources` 的な宣言) を DSL に持たせる方向。宣言の形・複数 URL・優先度
- iOS: `UICollectionViewDataSourcePrefetching` とローダーの接続 (prefetch 開始 / `cancelPrefetching` でのキャンセル)。ローダーは Kingfisher / Nuke のどちらを推奨するか
- Android: Coil + Lazy の合成ライフサイクルで遅延・キャンセルは概ね自動 — 追加でデータ層 prefetch (キャッシュ温め) を提供するか、`LazyLayoutCacheWindow` の先読みで足りるか
- ローダー依存の持ち方: 直接依存 / `ImageProvider` 抽象 + アダプタ提供 / 統合ポイントのみ提供 (本体は無依存)
- 専用画像コンポーネント (`KsImage` 相当) を提供するか: セル再利用時の定型処理・**セルサイズからのダウンサンプリング既定値** (グリッドのメモリ対策)・両プラットフォーム同名の一貫性。使わなくても成立する薄い推奨部品とする方向
- 標準 API の限界の確認: SwiftUI `AsyncImage` はキャッシュ制御・ダウンサンプリング・重複統合なし / Compose は標準ローダー自体なし (Coil が公式推奨) — 自前実装はしない
- 検証: 画像入りグリッド大量件数での実機計測 (メモリ・フリング時のキャンセル動作)

### phase-1 からの申し送り (2026-09-01)

- DSL 外形は core/ADR-0008 で確定: `prefetchResources` クロージャ (アイテム → リソース列挙、データ型への準拠要求なし) + 同一ローダ・キャッシュを見る専用 `KsImage` の対。利用形は [dsl-samples.md](../phase-1-symmetric-dsl-spec/artifacts/dsl-samples.md) シナリオ5
- `KsImage` は「提供するか」から「外形確定済み」に進んだ — 本フェーズの論点は機能範囲 (ダウンサンプリング既定値等) とローダー選定・依存の持ち方
- `KsImage` を使わない画像コンポーネントとのキャッシュ連携口を設けるかは本フェーズで判断 (ADR-0008 の負の帰結)
