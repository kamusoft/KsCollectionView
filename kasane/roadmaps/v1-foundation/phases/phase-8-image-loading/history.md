# 議論履歴

## 2026-09-05: ローダー依存の持ち方

ksn-explore で起動後、フェーズの論点なので ksn-agenda に切り替え。ksn-scout に iOS ローダー (Nuke / Kingfisher)・Coil 3・Compose Foundation の先読み API・隣接リポジトリの前例・本リポジトリの内部配線・依存分離パターンを調査させた。

前提の把握: iOS 本体には `UICollectionViewDataSourcePrefetching` → アイテム単位の prefetch / cancel を内部プロトコル (`KsPrefetching` / `KsAnyPrefetcher`) へ流す配線が既にあるが中身は空 (`prefetcher: nil` 固定、公開 API なし)。Android 側に対応物なし。隣接リポジトリに画像ローダー採用の前例なし (旧 AiForms は本体無依存 + FFImageLoading 推奨)。

選択肢:
- A. 本体がローダーへ直接依存 (`KsImage` とプリフェッチ接続を内蔵)
- B. 本体は無依存、統合部品を同一パッケージの別 product / 別モジュールで同梱 (Nuke・Coil 自身が採る分割の型)
- C. ローダー抽象 (`ImageProvider`) + アダプタ

判断軸: 利用者の手間 / 画像を使わない利用者への影響 / 他の画像部品とのキャッシュ共有 / 実装・保守コスト / 将来のローダー差し替え / ADR-0008 との整合。

採用: A。理由は (1) ADR-0008 の「外部依存推奨を `KsImage` として内蔵化」に最も素直、(2) ローダーの共有インスタンス自体が共有キャッシュになるので、`KsImage` を使わない画像部品とのキャッシュ連携 (ADR-0008 の負の帰結) がほぼ無料で解ける、(3) 主目的が自社 KMP アプリ量産 (cross/ADR-0001) で利用者に統合手順を課す価値が薄い。負の面「画像を使わない利用者にもローダーが付く」は Android では Coil が標準的、iOS では Nuke が MIT・活発で受容できると判断。覆すコストが高いため core/ADR-0012 を proposed で起票。

## 2026-09-05: ローダーの選定

ADR-0012 (直接依存) を受け、どのローダーに依存するかを決めた。Android は Coil 3 一択 (Compose の事実上の標準、制約からのデコード縮小が既定、`enqueue` でプリフェッチ可、Apache-2.0、minSdk 23。Glide の Compose 統合は beta)。実質の判断は iOS の Nuke 13.2 vs Kingfisher 8.12。

判断軸: プリフェッチのキャンセル単位 / 優先度・宛先指定 / Swift 6 strict concurrency / SwiftUI ビュー / ダウンサンプリング / 重複統合 / 最低 OS / ライセンス・保守。

採用: A (iOS は Nuke、Android は Coil 3)。理由は (1) Nuke の `ImagePrefetcher` は URL 単位で開始・停止でき、本体の内部配線 (アイテム単位の prefetch / cancel) にそのまま繋がる。Kingfisher はインスタンス単位の `stop()` しかなく、フリング中の細かなキャンセルを表現できない、(2) Nuke は 13 系でパイプライン全体を Swift Concurrency に移行済み。Kingfisher は README の対応表明と Package.swift の宣言 (tools 5.1・言語モード指定なし) に乖離があり未検証、(3) 重複統合と優先度指定を持つ。懸念: Nuke 次期 14 系は iOS 16 / Swift 6.2 要求で本リポジトリと一致するが、将来さらに上がれば追随できない可能性 (ADR-0012 の Revisit When)。却下案 B (Kingfisher、キャンセルは画面単位に丸める) は選ばれず。決定は proposed の ADR-0012 に畳み込んだ。

## 2026-09-05: プリフェッチの宣言と到達点

論点 1 (宣言の形・複数 URL・優先度) は `KsImage` の縮小とキャッシュ鍵の関係が決まらないと形が決まらないため、「プリフェッチが何をキャッシュに載せるか」と一緒に扱った。ksn-scout に Nuke 13 / Coil 3 のキャッシュ鍵とサイズ照合、NukeUI `LazyImage` の縮小機能、本リポジトリで列幅を出せるかを調査させた。

分かったこと: Nuke のメモリ鍵は縮小処理を含むが、元寸がメモリにあれば表示時の縮小付き要求はそれを再利用する。Coil は変換なし要求の鍵がサイズ非依存で、元寸のメモリ画像は `AsyncImage` の制約付き要求 (INEXACT) にヒットする一方、プリフェッチ側で小さく縮小すると要求より小さい場合にミスする。ディスク鍵は両者とも実質 URL。`LazyImage` に自動縮小はなく processors 指定が要る。iOS はプリフェッチ時点で列幅を計算できる材料が揃うが、Android は列幅計算もプリフェッチ機構も存在しない。Nuke のディスクキャッシュ (DataCache) は既定で無効。

選択肢: A. 元寸でメモリまで載せる (スクロール中は最軽量、元寸がメモリに載る) / B. ディスク (元データ) までに留め、表示時にデコード・縮小 (メモリ最小、表示時にデコードが走る、iOS はディスクキャッシュ有効化が前提) / C. 宣言にサイズヒントを足し縮小鍵までプリフェッチ (利用者が `KsImage` とサイズを合わせる責任、Android は列幅の自前計算)。いずれも宣言は URL 配列のまま (優先度は Coil に無く対称にできないため持たせない)。

エージェントの推奨は A だったが、オーナーは B を採用 (メモリ圧を避ける側を優先)。決定は覆すコストが低い (プリフェッチの内部到達点で公開 API に影響しない) ため ADR にはせず決定事項のみ。TODO に iOS のディスクキャッシュ有効化設計と利用者ドキュメント (サムネイル URL の申告) を追加。

## 2026-09-05: プリフェッチの到達点の改訂 — メモリまでも選べるようにする

オーナーから「B (ディスクまで) を既定にしつつ、メモリキャッシュまで載せる指定も選べるようにしたい」と追加要望。宣言に任意引数を足す形で記録 (Swift `.prefetchResources(destination: .memory) { }` / Kotlin `prefetchDestination = KsPrefetchDestination.Memory`、既定は disk)。ADR-0008 の外形への任意引数の追加であり衝突なし。Nuke は `ImagePrefetcher` の宛先指定をそのまま使え、Coil は `memoryCachePolicy` の切替 (ディスクのみならデコード省略も併用) で表現できる。

## 2026-09-05: Android のプリフェッチ機構

Android 側に iOS の内部配線に相当する機構が無い状態から、ADR-0008 (両プラットフォームに `prefetchResources`) を満たす実現方法を決めた。

選択肢: A. 可視範囲の観測からライブラリ自身が先読み窓を作り、アイテム単位で Coil に取得を投げ、窓から外れたら取り消す / B. Compose Foundation の先読み窓 (`LazyLayoutCacheWindow`) に任せる / C. Android はデータ層プリフェッチなし。

判断軸: iOS との契約の対称性 / 使う API の安定性 / 先読み量の制御 / 実装コスト / メモリ。

採用: A。理由は (1) iOS と同じアイテム単位の契約になり concepts に共通の契約として書ける、(2) 安定 API (`LazyGridState.layoutInfo`、Coil `enqueue` / `Disposable`) のみで済む。B は本リポジトリの BOM (2026.06.01 = foundation 1.11.4) で experimental (stable 化は 1.13 系) であることに加え、セルを先に合成する機構なので `KsImage` の表示読み込みが走り、到達点 (ディスク / メモリ) の指定を守れない。C は ADR-0008 の改訂が要る。窓幅の既定値は提案の設計で決める。ADR 化はしない (プラットフォーム内部の実現方法で公開 API に影響せず、覆すコストも低い)。

## 2026-09-05: `KsImage` の機能範囲

前提: NukeUI `LazyImage` には自身のレイアウトサイズへの自動縮小がなく、縮小処理を明示しないと元寸でデコードされる。Coil `AsyncImage` は制約から縮小するのが既定。

選択肢: A. 最小 (URL + 当てはめ方のみ、縮小既定あり) / B. A + 読み込み中・失敗時の表示スロット / C. ローダー付属ビューの薄い別名 (縮小既定なし)。判断軸: グリッドのメモリ対策 / セル内の見た目の制御 / 両プラットフォームの語彙の一致 / 実装・保守コスト / 「使わなくても成立」。

採用: B。縮小の既定は自身のレイアウトサイズ (論点 1 の「ディスクからの表示時デコード」とグリッドのメモリ対策を両立)。当てはめ方と表示スロットを両プラットフォーム同じ語彙で持ち、縮小サイズの手動指定・演出・ローダー設定の露出は持たない。ADR 化はしない (公開部品の機能範囲だが、追加は後から可能で覆すコストが低い)。

続けてオーナーから「ファイルやリソースも渡せるようにしたいがそうなっているか」と確認。ADR-0008 とサンプルはリモート URL のみで、ローカルファイル・バンドル済みリソースは未決定と回答し、論点 8「画像ソースの種類」として agenda に追加した。

## 2026-09-05: 画像ソースの種類

前提: Nuke はリモート URL と `file://` URL を同じ経路で扱えるがアセットカタログは守備範囲外。Coil は文字列・URI・ファイル・リソース ID をそのまま受ける。判断軸に KMP 共有モデルの純粋性 (モデルにライブラリの型を持ち込まない) を含めた。

選択肢: A. 画像ソース型を導入 (`KsImageSource`: remote / file / asset・resource)、`KsImage(url)` は便宜初期化子として残す / B. 種類ごとの初期化子 / C. URL のみ (`file://` 含む)。判断軸: バンドル済みリソースの扱い / 項目ごとにソース種別が変わるケース / 語彙の一致 / モデルの純粋性 / `prefetchResources` との関係 / 実装コスト。

採用: A。1 つの項目が状況によってリモートとローカルを切り替えるケースを 1 値で表現できテンプレートの分岐が不要。`prefetchResources` はリモート URL 配列のまま。ADR 化はしない (公開型の追加だが ADR-0008 の外形の内側)。

続けてオーナーから「種類ごとにメモリかディスクかを選べるとなお良い」と追加要望。論点 8 を「ソース種別ごとのキャッシュ方針」に差し替えて継続。

## 2026-09-05: ソース種別ごとのキャッシュ方針

「種類ごとにメモリ / ディスクを選べる」要望に対し、指定の粒度 (A. 全体設定で種別ごとの既定 / B. `KsImage` 個別 / C. 両方) と既定案 (リモート = ディスク、ファイル・リソース = メモリ) を提示。オーナーは「ファイルやリソースはディスクに載せる意味がないのでメモリ固定でよい」と応答し、選択式ではなく種別ごとの固定に着地。リモートはディスク既定 (メモリまでは論点 1 のプリフェッチ宛先指定)、ファイル・リソースはメモリ固定。設定は設けない。

## 2026-09-05: 表示後の画像のメモリ保持 (キャッシュ方針の整理)

オーナーから「リモートをディスクにした場合、メモリにも載るのか」と確認。表示のために読み込んだ縮小済み画像はローダーの通常経路でメモリキャッシュに載る (ディスク指定が効くのはプリフェッチ段階のみ) と回答。これにより「ファイル・リソースはメモリ固定」も特別扱いではなくローダー既定に乗るだけと整理し、ライブラリの調整点はプリフェッチの到達点だけという単純な形に着地。「表示後もメモリに残さない」案 (毎回再デコード) は性能面で非推奨とし、オーナーはローダー既定のままで了承。決定事項の見出しと本文を差し替えた。

## 2026-09-05: iOS のプリフェッチ接続と決着済み 2 項目の閉鎖

論点 2 (iOS 接続の既定値: 宛先は宣言指定・優先度は Nuke 既定の低で非露出・Android と同じ契約を concepts へ)、「標準 API の限界の確認」(調査で裏付け、ADR-0012 で決着)、申し送り「キャッシュ連携口」(共有インスタンスで自動、別ローダーとの連携口は設けない) を、先行決定の帰結としてまとめて決定事項へ移すことをオーナーが了承。続けて「キャッシュのクリアの口を作っておきたい」と追加議題があり、論点 9 として agenda に追加。

## 2026-09-05: キャッシュのクリアの口

選択肢: A. 同名の入口 (範囲付き全消去 + URL 単位の削除) / B. 全消去のみ / C. 入口なし (ローダー直叩きをドキュメント案内)。判断軸: 語彙の一致 / 同じ URL で画像が差し替わる場面 / 共有インスタンスの巻き添え (全案で不可避) / 実装コスト / 「本体を入れるだけで済む」利点。

採用: A に、オーナーの追加要望「ファイル単位のクリアも可能か」を受けて URL 単位を**ソース単位** (`remove(source: KsImageSource)`) に一般化。ファイル・リソースも表示時にローダーのメモリへ載るため同じ薄い包みで消せる。iOS のアセットは Nuke を通らないため no-op。ADR 化はしない (公開 API の追加だが ADR-0012 の帰結)。

## 2026-09-05: 検証方法

選択肢: A. Sample の実機計測のみ / B. 配線の自動テスト + 実機計測 1 回 / C. 数値目標を決めて CI で継続計測。判断軸: 契約の退行検知 / メモリ・フリングの体感 / 継続コスト / 実装コスト。採用: B。契約 (アイテム単位の開始 / 取消) は自動テストで守り、メモリとフリングの体感は一度確かめれば十分な性質のため実機で 1 回計測して history に残す。これで論点が出尽くし、提案化 (ksn-propose) へ進める状態になった。

## 2026-09-05: 提案化 (ksn-propose) と依存の要求値の追加調査

論点が出尽くしたため change `image-loading` (L 級、domain: cross) を起こした。提案の Decision 2 のために ksn-scout に Coil / Nuke が利用者へ要求する値を調査させた結果: Coil 3.6.0 以降は Compose 1.12.0 / compileSdk 37 でビルドされ、推移依存の `androidx.compose.foundation:foundation:1.12.0` が利用者アプリに compileSdk 37 を要求する。compileSdk 36 で収まる最新は 3.5.0 (Compose 1.11.1、推移 foundation 1.11.2 は本体 BOM の 1.11.4 に吸収)。ネットワーク取得には `coil-network-okhttp` (OkHttp 4.12.0 が推移) が必須。Nuke 13.2.0 は swift-tools 6.0 / iOS 15+ / 外部依存なし。Coil は 3.5.0 に固定して提案に反映した。

## 2026-09-06: 提案のセカンドオピニオン (codex) と反映

相方レビュー (second-opinion-spec-001) は NEEDS_DISCUSSION (Major 7・Minor 1)。全件を採用して提案を修正: 共有パイプラインの差し替えは既存構成と delegate を引き継ぐ / iOS の縮小は `ThumbnailOptions` で fit・fill の目標寸法を定義 / プリフェッチは台帳 + URL 参照数の寿命モデル / `KsImageCache` は上限付き台帳 + 世代番号で表示中ビューを無効化 / 公開シグネチャを固定し当てはめ方は共通の `KsImageContentMode` / 性能検証は handbook の全系統を既存 fixture で回帰計測 / 実ローダーの統合テストを追加。agenda 決定「キャッシュのクリアの口」のソース単位削除は、iOS ではライブラリの台帳に残る鍵に限る保証へ狭めた (オーナー確認事項)。agenda 決定「検証方法」の「実機計測 1 回」は handbook の rule (Android の全系統計測) が上位のため、その範囲で読み替えた。

## 2026-09-06: `remove` の保証範囲の確定 — 世代付きキャッシュ識別子

オーナーから「台帳から消えたものは再読み込みになるか」と確認。上限付き台帳案では台帳から落ちた鍵のメモリ項目が残り古い画像が出得る、と回答し、Nuke の `imageIdKey` でソースごとの世代を識別子に含める案 (B) を提示。判断軸: `remove` 後に古い画像が出る可能性 / 追加で持つ状態 / ローダー付属ビューとの共有 / 実装の複雑さ。オーナーは B を採用 (消去の確実さを、消したソースに限った共有の喪失より優先)。design Decision 7・spec・tasks・proposal を更新。
