# iOS 性能検証の手順

この文書は、iOS エンジンの変更を性能面で検証するための**土俵・機材・手順**を定める。読むと、何を fixture にし、どの機材でどう計測器を接続し、どの数値を取り出すかが分かる。

**合否の判定規則はここでは定めない。** スクロール性能の合否・操作列・証跡の形式は [スクロール性能の体感ゲート](../cross/scroll-performance-gate.md) に従う。判定をオーナーの体感に置く理由は [ADR-0006](../../decisions/cross/0006-perceived-smoothness-as-performance-gate.md) にある。

## 計測する 2 系統

| 系統 | 駆動 | 取り出すもの | 判定 |
|---|---|---|---|
| スクロール性能 | オーナーの手動フリック (固定の操作列) | Instruments Animation Hitches の hitch 指標と time profile の帰属 | オーナーの体感 (cross の体感ゲート) |
| メモリ | Simulator の計測専用 launch 経路による自動往復 | 往復ごとの `phys_footprint` と通過した項目数 | 定常化したか / 未判定 |

メモリの定常判定は「全項目を通過する往復を重ね、連続する 2 往復の増分がいずれも 1 往復後の値の 2% 以内になったら定常」とする。上限 10 往復で止まらなければ未判定として報告する。

## 固定 fixture

土俵は**機能ごとの Sample デモ画面**とする。エンジンの土台に触る変更は文字だけの「大量件数」、特定機能の変更はその機能のデモ画面 (画像なら「画像グリッド」) を使う。

「大量件数」は件数 10,000、2 列グリッド、固定高と 7 件ごとの長文による可変行高の混在、整数 ID による決定的な生成 (同じバイナリでは項目ごとの内容が常に一致する)。件数は起動引数で変えられる (対策の効果を件数間で比べるときに使う) が、既定は 10,000 のまま保持する。fixture を変えた計測は過去の結果と比較しない。

## 機材

基準機は iPhone 11 相当、構成は Release。基準機を接続できないときは代替機で計測してよいが、**代替の前にオーナー承認を得て**、代替機が基準機より速いか遅いかに関わらず「基準機の保証にならない」旨を証跡に明記する。Simulator は絶対値が実機と異なるため、メモリの定常化の判定にだけ使う。

推定高さと自己サイズの一致の計数 (不一致率) は Debug 構成にしか載せない。計測のための仕組みを製品構成へ持ち込まないためである。したがって滑らかさの計測は**2 つの走行**からなる: 体感と time profile は Release 構成、不一致率は Debug 構成で同じ操作列を 1 回なぞって読む。2 つの数値は同じ走行のものではないため、証跡の「限界」にその旨を書く。

## スクロール性能の手順

1. Sample を Release 構成で基準機にインストールする。キャッシュ状態を揃えるときは削除してから入れ直す
2. 対象のデモ画面を起動引数 (`--screen <画面名>`) で直接開く
3. Instruments の Animation Hitches テンプレートを**プロセス名指定**で接続する (`xctrace record --template 'Animation Hitches' --attach <プロセス名>`)。pid 指定は「見つからない」で失敗することがある
4. 「Starting recording」が出て記録が始まったことを確認してからオーナーに合図し、オーナーの合図を受けて固定の操作列に入る
5. 操作列の終了を確認してから記録を閉じ、数値を取り出して証跡に書く
6. 不一致率を採るときは、同じ端末に Debug 構成の Sample を入れ、同じ画面・同じ操作列をもう 1 回なぞる。操作の直前に帯の「数え直す」で区間を切り、操作を止めてから「読む」で値を読む (スクロール中は読み直さない)

接続は「アプリを先に起動し、記録を後から張る」順序で行う。起動済みのアプリに接続してから駆動側で前面化すると、前面化の瞬間に対象アプリが終了したものとして記録が打ち切られる。

`xctrace record --attach` はプロセス名指定でも端末の認識が揺れてタイムアウトすることがある。その場合は「Starting recording」が出るまで再試行する。失敗した試行でオーナーが操作した分は、キャッシュ状態を揃え直すために入れ直してからやり直す。

### 取り出す数値

- hitch 件数 (High / Moderate / Low)、hitch time ratio (記録窓の実長で割った値と、10 秒ごとの推移)、最長 hitch、hitch の種類の内訳
- 描画の surface swaps / 秒、主スレッドの稼働率
- time profile (inclusive、主スレッド標本比) による帰属: `CA::Transaction::commit` 配下の内訳、セルの生成、hosting の計測と描画、`_UICollectionLayoutSectionEstimatedSolver`
- 不一致率 (自己サイズを返したセルのうち、そのセルに渡されていた高さと違う高さに測られた割合): **Debug 構成の走行**で、件数を指定して開いた「大量件数」画面の帯から読む (件数を指定した起動でだけ帯が出る)。Release 構成では読めない

占有率は操作列の区間の標本で計算する。区間を指定せず記録全体で割った値は、無操作の時間を含むため他の記録と比較できない。

実機のログは `log stream` では追えず `log collect` は root を要するため、必要なら Instruments の Logging テンプレート (`xctrace record --template Logging --attach <プロセス名>`) で採る。端末全体を対象にすると行が落ちるためプロセス指定にする。

## メモリの手順

1. Sample を Release 構成で Simulator にインストールし、計測専用 launch 経路を自動実行モードで起動する (走査・記録・終了まで app 自身が行う)
2. 1 往復は、先頭から末尾まで可視範囲の高さの半分ずつ content offset を送り、同じ刻みで先頭へ戻る走査とする。可視範囲より粗い刻みでは間の項目のセルが作られず、コストが計上されない
3. 1 段階ごとに「目的の位置に到達し、その位置のセルが載った」ことを条件に待つ。各段階の可視セルの項目番号を集合に記録し、往復ごとに全項目を通過したことを件数で確かめる
4. 往復ごとに `phys_footprint` を記録し、定常判定まで往復を重ねる。同じ手順を独立に 2 回実行し、実行間のばらつきも記録する

計測ドライバはこのメモリの自動往復だけを持つ。自動フリックによるスクロール性能の駆動は持たない (体感ゲートで使わない足場を残さないため)。

### 保持対象の解放の確認

メモリの定常化とは別に、ライブラリが**項目単位**で持つ対象 (セルとそのホスティング) の解放をエンジンテストで確かめる。Debug 構成の同時生存セル数のカウンタを使い、(a) 全件往復した後に配列を別の内容へ置換したとき同時生存が可視セル数の 4 倍未満に戻ること、(b) コレクションへの強参照を手放したときエンジンへの弱参照が nil になること、の 2 点を見る。破棄後は同じインスタンスのカウンタを読めないため、(b) は弱参照プローブで確かめる。

## 証跡

計測結果は change の `evidence/` に、[体感ゲート](../cross/scroll-performance-gate.md)の雛形で残す。数値の抜粋は `scripts/log-sanitize.py` を通し、個体識別子・端末名・ローカル絶対パス・生の trace を含めない。生の trace は退避先 (スクラッチ) にのみ置く。

## なぜ

メモリの判定を「1 往復追加で増えないこと」にしないのは、上限のあるキャッシュが数往復かけて埋まる間は数 % の増加が残り、1 往復の追加では定常化を判定できないため (実測: 4〜5 往復目で定常)。

Simulator でメモリを測るのは、往復の自動化が足場の汚染なしに成立し、判定したいのが絶対値ではなく定常化だからである。

## 適用範囲

- 対象: セルの生成・再利用・自己サイズ・レイアウト生成・snapshot 適用の経路に触れる変更、および大量件数を扱う新機能 (セクション・ページング・画像ロード)
- 対象外: 公開 API の形だけの変更、Sample の文言・配色の変更
- CI での自動化は実機の受け皿ができた時点で再訪する ([ADR-0006](../../decisions/cross/0006-perceived-smoothness-as-performance-gate.md) の Revisit When)
