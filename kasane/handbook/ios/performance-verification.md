# iOS 性能検証の手順と合格基準

この文書は、iOS エンジンの変更を「性能面で完了」と判定する条件を定める。読むと、何を土俵に、どの機材と操作で計測し、どの数値なら合格かが分かる。手順は ios-engine-foundation の実装で実測して検証し (証跡: `kasane/changes/archive/2026-09-04-ios-engine-foundation/evidence/performance-early-measurement.md`)、スクロール性能の接続手順は image-loading の基準機での計測で立て直したもの (証跡: `kasane/changes/archive/2026-09-08-image-loading/evidence/image-grid-measurement-ios.md`)。

## 規約

エンジンの描画・再利用・レイアウト経路に触れる変更は、次の 2 系統を計測し、両方を満たすまで性能面の完了と報告しない。

| 系統 | 指標 | 合格基準 |
|---|---|---|
| スクロール性能 | Instruments Animation Hitches の hitch time ratio | 3 秒間の連続フリックを独立に 3 回記録し、**3 回すべて** 5 ms/s 未満。平均値だけで合格にしない |
| メモリ | `TASK_VM_INFO.phys_footprint` の往復推移 | 全項目を通過する往復を重ね、連続する 2 往復の増分がいずれも 1 往復後の値の 2% 以内になったら定常とみなす。上限 10 往復で止まらなければ「未判定」として報告する |

## 固定 fixture

Sample「大量件数」画面と、同じデータを使う計測専用の launch 経路を土俵にする。件数 10,000、2 列グリッド、固定高と 7 件ごとの長文による可変行高の混在、整数 ID による決定的な生成 (同じバイナリでは項目ごとの内容が常に一致する)。fixture を変えた計測は過去の結果と比較しない。

## 手順

### スクロール性能

1. Sample を Release 構成で実機へインストールする。Release の Runner は UI Automation の初期化がタイムアウトするため、駆動は Debug の XCTest Runner から行い、Release app へ実座標のフリックだけを入力する。
2. 駆動テスト自身が Release app を起動し (計測窓を `os_signpost` 区間で示す起動引数 `--signpost-scroll-window` を付ける)、その後に Instruments の Animation Hitches テンプレートをプロセス指定で接続する。
3. 先頭へ戻し、実座標タッチによる 3 秒間の連続フリックを行う。駆動はフリックの座標を区間に入る前に確定し、区間中に要素の走査 (アクセシビリティのスナップショット) を行わない。区間は締切 (3.000 秒) で閉じ、hitch time の合計は区間の実測長で割る。これを独立に 3 回記録し、各試行の hitch time ratio を個別に記録する。
4. 実機のログは `log stream` では追えず `log collect` は root を要するため、必要なら Instruments の Logging テンプレート (`xctrace record --template Logging --attach <pid>`) で採る。端末全体を対象にすると行が落ちるためプロセス指定にする。

接続の順序を逆にしない。起動済みのアプリに接続してから駆動側の `activate()` で前面化すると、前面化の瞬間に対象アプリが終了したものとして記録が打ち切られ、フリック区間が入らない。

計測の足場の限界を証跡に明記する: 座標による press-drag も指を離した後の静止まで待って戻るため、3 秒の区間に入るフリックの投入は 1 回になり、区間内に無操作の時間が残る。区間中も XCTest ランナーがアクセシビリティの走査を続け、主スレッドの一部を占める。

基準機は iPhone 11 相当。接続できない場合は代替機で計測してよいが、代替機が基準機より高速なら「基準機相当の保証にならない」旨を証跡に明記する。

### メモリ

1. Sample を Release 構成で Simulator へインストールし、計測専用 launch 経路を自動実行モードで起動する (走査・記録・終了まで app 自身が行う)。
2. 1 往復は、先頭から末尾まで可視範囲の高さの半分ずつ content offset を送り、同じ刻みで先頭へ戻る走査とする。可視範囲より粗い刻みでは間の項目のセルが作られず、コストが計上されない。
3. 1 段階ごとに「目的の位置に到達し、その位置のセルが載った」ことを条件に待つ。各段階の可視セルの項目番号を集合に記録し、往復ごとに全項目を通過したことを件数で確かめる。
4. 往復ごとに `phys_footprint` を記録し、定常化の判定 (上表) まで往復を重ねる。同じ手順を独立に 2 回実行し、実行間のばらつきも記録する。

Simulator のメモリ絶対値は実機と異なる。この手順で判定できるのは定常化 (往復で増え続けないこと) だけであり、絶対値の判定に使わない。

## 証跡

計測結果は change の `evidence/` に、環境 (機種・OS・構成)、fixture、各試行の値、判定を表で残す。数値の抜粋は `scripts/log-sanitize.py` を通し、個体識別子・端末名・ローカル絶対パス・生の trace を含めない。

## なぜ

XCTest の自動性能テストは実機 + Instruments の hitch 計測と同精度にならず、初版では再現手順の固定 (機種・操作・回数) が計測の信頼性を担う。メモリの判定を「1 往復追加で増えないこと」にしないのは、上限のあるキャッシュが数往復かけて埋まる間は数 % の増加が残り、1 往復の追加では定常化を判定できないため (実測: 4〜5 往復目で定常)。

## 適用範囲

- 対象: セルの生成・再利用・自己サイズ・レイアウト生成・snapshot 適用の経路に触れる変更、および大量件数を扱う新機能 (セクション・ページング・画像ロード)
- 対象外: 公開 API の形だけの変更、Sample の文言・配色の変更
- CI での自動化 (XCUITest + `XCTOSSignpostMetric`) は実機の受け皿ができた時点で再訪する (design Decision 6 の代替案)
