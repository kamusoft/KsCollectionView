# Sample のプラットフォーム間一致

この文書は、`samples/` 配下の Sample アプリを iOS と Android でどこまで一致させるかの規約を定める。読むと、Sample に画面や文言を追加・変更するときに何を揃えなければならないか、どんな差異なら許されるかが分かる。

## 目的

KsCollectionView は、リスト・グリッドの定型機能を SwiftUI と Jetpack Compose で同じ書き味で提供することを製品目的とする。Sample はその対称性が実際に成立しているかを実行・目視で確認する検証装置を兼ねる。

Sample 自体がプラットフォーム間でばらばらだと、画面上の差異が「本体の仕様差 (= バグ)」なのか「Sample の書き方の差」なのか判別できず、検証装置として機能しない。そこで Sample は**両プラットフォームで一字一句同じ文言・同じ画面構成**で実装する ([cross/ADR-0004](../../decisions/cross/0004-sample-cross-platform-parity.md))。

内部の描画エンジンは iOS と Android で非対称であり、公開 DSL の対称性はビルドシステムからもコンパイラからも強制されない。Sample はその強制されない部分を人が見て確かめるための唯一の装置である。

## 保証すること

一致の単位は「対応するデモ画面」。画面同士の対応は画面タイトル (= ルートメニューの文言) で取る。`samples/ios` と `samples/android` の両方で以下を揃える。揃っていないと、目視検証がプラットフォーム間比較として成立しない。

- **画面の集合**: デモ画面とルートメニュー項目は両プラットフォームに同一の構成で存在する
- **表示文言の完全一致**: 画面タイトル・メニュー項目・セクションのヘッダ / フッタ・セルの表示フィールド・デモデータ (件数・初期値・選択肢の文言) を一字一句一致させる
- **表記ゆれも不一致**: 大文字小文字の違いや「〜デモ」の有無のような表記ゆれも、上記の完全一致に対する違反として扱う
- **画面構成の一致**: セクション数・アイテム数・並び順と、DSL に渡すパラメータ (列数、グリッドの間隔、ページサイズ、初期選択、ソート順、色等) を一致させる
- **色はプラットフォーム固有の semantic color や UI フレームワークの既定のテーマ色に任せない**: 実値がプラットフォーム間でずれるため、Sample が自分で描く色は同一の RGBA を Sample 共通の定義 (`SampleTheme`) に置いて両プラットフォームから参照する
- **メニューと画面タイトルの一致**: ルートメニューのリンク文言と遷移先画面自身のタイトルは同一文字列にする (別々に定義される二重管理が表記ゆれの主要因)

表示モード (ライト / ダーク) への対応は、両プラットフォーム同値の 2 組の配色を、Sample の中の同じ切り替え (ルートメニューの「外観」) で選ぶ形でだけ行う ([cross/ADR-0007](../../decisions/cross/0007-sample-light-dark-within-parity.md))。`SampleTheme` はライトとダークの 2 組を持ち、Sample に色を足すときは 2 組とも足す (項目の内容を表す色のように外観で変えない色は、2 組に同じ値を置く)。OS の semantic color に任せて表示モードに追随させることはしない。プラットフォームらしさは、同じ宣言内容が OS 標準の chrome の中でどう描かれるかという形で確認する。

## 収束の境界

一致は**収束状態**への要求であり、常時同時である必要はない ([cross/ADR-0004](../../decisions/cross/0004-sample-cross-platform-parity.md))。境界は次のとおり。

- 各プラットフォームの基盤実装 (iOS エンジン基盤 / Android ラッパー基盤) は、各自の Sample scaffold (`SampleScreen` / `SampleTheme` / メニュー構造) と対向プラットフォームへの追随タスクを責務とする
- 両基盤の完了時点が最初のパリティ収束ゲートであり、そこで初めて全デモ画面の一致を検査する
- 以降の機能追加の変更は「デモ画面を両プラットフォームの Sample に本規約準拠で追加」を完了条件に含める

## 許容される差異

- OS 標準のナビゲーション chrome や既定フォント・描画差など、プラットフォームの見た目そのもの (例: iOS は `NavigationStack`、Android は `TopAppBar` を持つ共通ラッパーで画面を包む)
- 本体公開 API のプラットフォーム命名差に由来する、画面文言に出ないコード上の差 (引数名・型名・リソース指定方法)
- Sample が明示的に渡していないパラメータの、**本体既定値のプラットフォーム差**。Sample 側で値を明示すると「既定のデモ」という意図が壊れるため解消できない
- **実装順序による一時的な片側先行**。変更がプラットフォーム別に分かれる場合など、先行側だけにデモ画面・文言変更が存在する期間は許容する

本体既定値のプラットフォーム差は規約違反としては扱わないが、本体の統一課題として change 配下の deviation.md に記録して追跡する。片側先行も恒久化させないこと — 未追随プラットフォームへの追随を tasks / 後続 change として残し、追跡できる状態を保つ (追跡が切れた片側限定の差異は、この規約の違反になる)。

## 例外: デモ対象の公開 API が存在しないプラットフォーム

デモ画面の一致対象は、**デモ対象の公開 API がそのプラットフォームに存在する場合に限る**。存在しないプラットフォームには当該画面を作らない (作れない)。この例外に該当する画面は片側先行の追跡対象に数えない。

対称 DSL を製品価値とする以上、この例外は原則として発生しない。発生しうるのは、非対称な描画エンジンの都合が公開 API に出る場合に限られる。例外画面を作るときは、対称 DSL に載せられない理由を根拠 (ADR または deviation.md) として残す。

デモの主対象がそのプラットフォーム固有の公開 API と意味論である場合は、確認項目の一部に対向の対応概念があってもページ全体をプラットフォーム固有画面としてよい。固有画面はルートメニュー上で「iOS 固有」のような区分に置き、パリティ対象のデモ画面と明確に区別する。

## 例外: プラットフォーム固有の技術検証画面

本体を経由しない生の UI フレームワーク挙動を確かめるような、プラットフォーム固有の技術検証画面は一致の対象外として許容する。ただし:

- ルートメニュー上でデモ画面と明確に区別する (「検証」など、ライブラリのデモとは別物だと分かる表記にする)
- 対向プラットフォームへの移植義務は負わないが、デモ画面の集合には数えない

## してはいけないこと

- 片側だけの文言・構成・デモデータの変更を**追跡なしで放置しない**。同一変更内で両プラットフォームを揃えるのが原則で、片側が先行する場合は追随の予定を残す
- プラットフォームごとに独自の「改善」(セクションの統合、プレビュー UI の追加、デモデータの増減) をしない。改善は両プラットフォーム一斉に行う
- 本体公開 API のプラットフォーム差で一致が不可能な箇所を黙認しない。一致できない理由を deviation.md に記録し、本体側の統一課題として扱う
- この規約を製品契約と混同しない。Sample の表示文字列やデモデータは利用者向けの製品契約ではなく、変更しても破壊的変更ではない

追随の予定は、進行中の変更ディレクトリ `kasane/changes/<change-id>/` の tasks.md / deviation.md (実装が仕様・計画から逸れた点を記録するメモ)、または後続 change に残す。追跡が残っている一時的な不一致は違反ではない。本規約は「プラットフォーム間で互いに揃える」内部の検証規約であり、製品契約とは別軸で両立する。
