# 実行時挙動の検証規約

この文書は、実行時挙動が絡む不具合修正の**完了判定**を定める。読むと、どの種類の不具合でユニットテストだけの検証が「完了」にならないか、代わりに何を確認するかが分かる。

## 規約

実行時挙動 — スクロール・セルの再利用・アニメーション・フォーカス・IME・スレッドやフレームのタイミング・OS サービスとの連携 — が絡む不具合の修正は、次の 3 点を満たすまで完了と報告しない。

1. **修正前に実環境で症状を再現する。** 実環境とは実機・エミュレータ / Simulator と実物の依存先の組み合わせを指す。再現できた操作手順が、そのまま解消確認の手順になる
2. **修正後に同一手順で解消を確認する。** 可能なら修正前後の A/B (修正を外したビルドで症状が出る / 入れたビルドで出ない) まで取ると、修正が原因に効いた証明になる
3. **証跡 (スクリーンショット・ログ等) を change 配下に残す。** レビューと蒸留が「解消した」の主張を検証できる形にする

原因分析の段階でも同じ規律を適用する: **コード読解だけで原因仮説を「真因」と断定しない**。仮説は実環境の観測 (再現・計測・A/B) で裏取りしてから修正に進む。

### 実行環境で実体が変わる資源を扱う分岐

不具合修正に限らず、新規実装でも次を適用する。画像のデコード構成 (ハードウェアビットマップ)・GPU 資源・センサ・権限・ファイルシステムの権限モデルのように、**実行環境によって実体が変わる資源**を扱う分岐は、単体テストの実行環境 (Robolectric / Simulator) で緑になっても完了としない。テスト環境が代替実装 (ソフトウェアのビットマップ・モックのセンサ) を提供している場合、緑は「代替実装では動く」ことしか意味しない。

その分岐に対応する Scenario は、**実機で踏む経路 (実機で走るテスト) を 1 本用意するか、実機での確認を証跡に残すまで「未検証」として扱う**。実装・レビュー・検証のどの段階でも、公開 API の選択肢が実機だけで落ちる可能性をテストの緑で否定しない。レビュアーは、こうした資源に触れる変更で実機の経路も証跡も無いときは、その Scenario を「未検証」として判定に書く。

## なぜ

ユニットテストは「実装した通りに動く」ことしか守れない。原因仮説そのものが誤っていれば、仮説に沿ったテストが全て green でも不具合は 1 ミリも直らない。

実行時挙動は、JVM 上のテスト環境や macOS 上のテスト環境では再現しない要素 (実スクロールに伴う行の生成・再利用、アニメーションの実挙動、フレーム間タイミング、実 IME の composing 等) を含むため、テスト環境の green は実機の動作を保証しない。

リスト・グリッドを扱う本ライブラリでは、大量件数での仮想化・再利用の成立そのものが必須要件であり、その検証は動くホストアプリでしか成立しない。

## 適用範囲

- **対象**: 症状が実行時にしか現れない不具合。目安は「ユニットテストでその症状自体を再現できるか」— できないなら本規約の対象
- **対象外**: 純ロジックの不具合 (ユニットテストで症状を再現できるもの)。この場合は失敗するテストの作成が再現手順を兼ね、テストの green が解消確認になる

ユニットテストが不要になる規約ではない。実環境の再現確認に**加えて**、修正の意図を固定する回帰テストは通常どおり書く。

## 目視確認の観測点

実環境での確認は、確認する結果を観測点として事前に言語化してから行う。「見た感じ問題ない」は証跡にならない。

観測点の一覧 (どのデモ画面で何を確認するか) は、Sample のデモ画面が生まれる時点でこの節へ追記する。iOS エンジン基盤 / Android ラッパー基盤の実装時が最初の追記機会になる。追記の際は次を守る。

- 観測点表は正典ではない。画面の文言・構成は各 Sample の画面実装が正であり、表はそれを見る観点を与えるだけである
- 観測点は両プラットフォームで同じ表現にする。プラットフォーム間比較として成立させるための条件である ([Sample のプラットフォーム間一致](sample-parity.md))
- 不具合修正の完了証跡に使う場合は、上の一般規約どおり修正前後で同じ操作と観測点を使う

| デモ画面 | 観測点 |
|---|---|
| リスト | 区切り線の既定表示と ON/OFF、タップ feedback、通常タップと長押しの排他 |
| グリッド (固定列) | list ⇄ grid の切替後に全可視セルの列幅が揃い、表示の乱れが無いこと (切替時のアンカー保持は本体の統合テストで担保する) |
| グリッド (adaptive) | コンテナ幅に応じた列数と最小幅、列間の均等配置 |
| 向きで列数変更 | 対応する縦向きと左右横向きで、コンテナ縦横比に対応する列数へ変わる |
| テンプレート切り替え | 値キーごとのセル表示と、スクロールによる再利用後の内容 |
| ルートヘッダー/フッター | 一緒にスクロールし、データ更新後の動的内容が表示中でも更新される |
| スクロール制御 | ID・先頭・末尾への到達と、データ追加直後の末尾命令が新しい末尾へ到達すること。Center / End 指定のアニメーションが行き過ぎてから戻らず一方向で着地すること (最終位置だけでなく動きの過程を見る) |
| スペーシングと余白 | Slider の連続ドラッグ中に配置が追従し、スクロールインジケータ位置は余白に寄らないこと |
| 大量件数 | 固定高・可変行高混在のスクロール、再利用後の内容、性能計測条件 |
| 画像グリッド | プリフェッチの 3 択を切り替えたときのスクロール中の絵の出方。フリングで画面外へ出たセルの読み込みが取り消され、戻ってきたセルが読み込み中を経ずに出ること。キャッシュを消去した後は表示中のセルが読み込み中を経て取得し直されること |
| 検証: 画像の挙動 | 先読みで取り込んだ画像がローダー付属のビューの表示にも効くこと (要求が起きない / ディスクから返る)、読み込み中の既定の表示、取得できない画像での失敗の既定の表示 |
| 検証: 行の高さ変化 (iOS 固有) | 展開・折りたたみで本文が行の上端より上へ出ないこと、遷移直後の 1 タップ目から開閉すること |
| 検証: 行の高さ変化 (Android 固有) | 展開・折りたたみで行の高さが中間フレームを通ってアニメーションし、押し出される行も追従すること。折りたたみの途中で行の中身と区切り線の間にページ背景の帯が出ないこと。展開した行を可視範囲と先読み分を超えて送って戻すとテンプレート内の状態が初期値に戻ること |

「検証:」で始まる 3 行は技術検証画面であり、デモ画面の集合には数えない ([Sample のプラットフォーム間一致](sample-parity.md) の例外枠)。「行の高さ変化」の 2 行はプラットフォーム固有で、両プラットフォームで同じ表現にする要求は掛からない。「画像の挙動」は両プラットフォームに同じ観点で置くが、Sample のメニューには出さず、iOS は起動引数、Android は計測できる構成の経路からだけ開く。
