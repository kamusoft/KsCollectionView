# 利用者向け Skill と README の書き方

この文書は、利用者向けの文書 (`skills/` の Agent Skill と、ルートの `README.md`・`README_ja.md`) を書く・直すときに守ることを定める。源泉が変わったときに Skill を追従させる流れは、[利用者向け Skill の追従](user-skill-refresh.md) にある。

利用者向けの文書をこの 2 つで提供すると決めた理由は、[cross/ADR-0005](../../decisions/cross/0005-user-docs-as-agent-skills-and-root-readme.md) にある。Skill の主な読み手は、利用者の手元の AI エージェントである。エージェントの手元には、Skill の 1 ディレクトリしか無い。この文書の決まりの多くは、その前提から出ている。

守れたかどうかの一部は、検査が確かめる (`scripts/ci/check-skills.py`・`scripts/ci/check-readme-examples.py`。検証 CI でも、スクリプトのテストを通して流れる)。決まりを持つ節の終わりに、検査が見るものと、見ないものを分けて書く。

## この文書の言葉と、決まりの当たる範囲

| 言葉 | 意味 |
|---|---|
| 利用者役 | 配布物を利用者と同じ書き方で取る、最小のプロジェクト (`verification/ios/`・`verification/android/`)。検証 CI がビルドする ([利用者の立場のビルドの確認](consumer-build-check.md)) |
| 源泉 | Skill の内容の元になるもの (概念の文書 `kasane/concepts/`・ビルドの設定・本体の公開の宣言) |
| 追従 | 源泉が変わった後に、Skill を今の源泉に合わせて直す作業。オーナーが頼んだときに行う |
| 初回の制作 | Skill と README を最初に作った変更 `user-docs` (2026-10-10)。この文書の「初回の制作では」は、そのときの実績を指す |
| オーナー | リポジトリの持ち主である開発者 |
| 検証 CI | GitHub Actions で、`develop` への push と `main` 宛ての Pull Request のときに走る検査 ([検証 CI](verification-ci.md)) |
| 簡易起票 | 別の作業の途中で見つけた課題を、後で扱うために `kasane/changes/<名前>/exploration.md` に書き留めたもの |
| 作業の報告 | 作業者が、作業の終わりに指揮側 (作業を任せた側) へ返す報告。追従では、オーナーの承認のときに見せるものに入る |
| 同じ回 | 1 回の直しの作業。同じ回に直したものは、同じ commit に入れる |

決まりの当たる範囲は、節で違う。

| 節 | Skill (`skills/` の 4 つ) | ルートの README |
|---|---|---|
| 構成 | 当たる (小節「Skill」「SKILL.md」) | 当たる (小節「README」「対応プラットフォームの値」) |
| 英語版と日本語版を同じ回に直す | 当たる | 当たる。ただし、検査が README について見るのは、見出しの深さの並び・9 つの節・最小コード例・インストール例だけである |
| コード例・インストール例 | 当たる | 当たる |
| 相手のプラットフォームとの差・公開の宣言の名前・書くときの勘どころ | 当たる | 当たらない (README は、両プラットフォームを 1 枚で扱う概要である) |
| Skill の外への参照 | 当たる | 当たらない。README はリポジトリの中の文書なので、リポジトリの中のファイル (ライセンス・貢献の案内・Skill) へ相対のリンクを張る。URL の一覧と内部の言葉の検査 (`scripts/ci/check-skills.py`) は、`skills/` だけを見る |
| スクリーンショット | 当たらない | 当たる |

内部の言葉を README に書かないことは、決まりとしては定めていない。2026-10-10 時点の README の 2 枚に、内部の言葉の一覧の言葉は現れない。

## 構成

### Skill

```
skills/
├── README.md / README_ja.md          索引
├── .manifest.json                    追従の記録
└── {en,ja}/kscollectionview-{ios,android}/
    ├── SKILL.md
    └── references/
        ├── basics.md                 一覧を出す
        ├── layout.md                 並べ方と見た目
        ├── paging.md                 ページングと Pull to Refresh
        ├── reorder.md                並べ替え
        └── images.md                 画像
```

- 4 つの Skill のディレクトリは、同じ 6 枚を持つ。ファイルを足す・名前を変えるときは、4 つに同じ変更をする
- `references/` は、利用者のやりたいことで 5 枚に分ける。源泉の概念の文書の分け方には合わせない
- 新しい機能は、今の 5 枚のどれかに入れる。どれにも入らないときだけ、1 枚を足す (足したら、`SKILL.md` の表と一覧・Skill の索引・追従の記録の `sources` を同時に直す)
- `references/` の各 1 枚は、やりたいことを見出しにして、動くコードと約束ごとを並べる
- iOS の Skill と Android の Skill の見出しは、同じ機能なら同じ言い方にする。違えてよいのは、プラットフォームの固有の名前 (読み上げの機能の名前・画像ローダーの名前) と、片方にしか無い手順の節だけである

### SKILL.md

| 部分 | 決まり |
|---|---|
| 節 | 順に 5 つ: 何のライブラリか (見出しの直下の 1 段落)・できること (やりたいことから `references/` の 1 枚への表)・導入・最小の動く例・`references/` の一覧 |
| 冒頭の 1 段落 | この段落だけを読んで、これが何のライブラリかが分かるように書く |
| frontmatter の項目 | `name` (ディレクトリの名前と同じ)・`description`・`license` (`MIT`)・`metadata.language` (`en` か `ja`)・`metadata.source` (配布元。本リポジトリの URL) の 5 項目だけにする |
| frontmatter の値 | **項目ごとに 1 行で書く** (検査は、複数行の値と折り返しを読めず、違反にする)。日本語版の `description` は、日本語の本文に英語のキーワードを添える |

frontmatter の形 (今の `skills/ja/kscollectionview-ios/SKILL.md`。`description` は、ここでは省いて書いた)。`metadata` の 2 項目は、1 段だけ字下げして書く。

```yaml
---
name: kscollectionview-ios
description: <1 行で書く。日本語の本文に、英語のキーワードを添える>
license: MIT
metadata:
  language: ja
  source: https://github.com/kamusoft/KsCollectionView
---
```

5 つの節の見出しの文面は、今の 4 つの `SKILL.md` で次のとおりである。5 つの節に入らない内容は、右の列の場所に置いてある。新しく足すときも、同じ場所に置く。

| 節 | 英語版の見出し | 日本語版の見出し | この節に置いてある、ほかの内容 |
|---|---|---|---|
| 何のライブラリか | `# KsCollectionView for iOS` / `# KsCollectionView for Android` (見出しの直下の 1 段落) | 英語版と同じ | 相手の Skill の名前 (段落の末尾) |
| できること | `## What you can do` | `## できること` | 提供していない機能 (表の下に 1 段落) |
| 導入 | `## Setup` | `## 導入` | 必要なものと下限の表・Android の、下限を示していないものについての 1 文・一緒に入る依存と、利用する側が書くもの・不具合の報告先 |
| 最小の動く例 | `## Minimal working example` | `## 最小の動く例` | 例の後に: どの使い方にも当たる決まり・「この Skill が使う言葉」(言葉の説明)・例の書き方の断り (Android は、Material 3 の無いモジュールでの読み替え方を含む) |
| `references/` の一覧 | `## References` | `## リファレンス` | — |

### README

ルートの README は、英日とも次の 9 つの節 (深さ 2 の見出し) を、この順で持つ。見出しの文面は、スクリプトのテストが持つ一覧と同じにする。

| 順 | `README.md` | `README_ja.md` |
|---|---|---|
| 1 | Overview and key features | 概要と特徴 |
| 2 | Screenshots | スクリーンショット |
| 3 | Supported platforms | 対応プラットフォーム |
| 4 | Installation | インストール |
| 5 | Minimal code examples | 最小コード例 |
| 6 | Skills | Skill |
| 7 | Repository structure | リポジトリ構成 |
| 8 | Contributing | 貢献 |
| 9 | License | ライセンス |

- **最小コード例の節の見出しの文面 (`Minimal code examples`・`最小コード例`) を変えない。** 検査は、この文面で節を見つける。変えるときは、検査 (`scripts/ci/check-readme-examples.py`) とテストの一覧を同時に直す
- Skill への導線の節は、自分の言語の 2 つの `SKILL.md` と、自分の言語の索引だけを指す

### 対応プラットフォームの値

- 対応プラットフォームの表の値は、ビルドの設定 (`ios/Package.swift`・`android/gradle/libs.versions.toml`・`android/kscollectionview/build.gradle.kts`) から拾う。覚えている値で書かない
- 表の列は、最低の OS・利用する側のビルドに必要なもの・ライブラリのビルドに使っているもの、の 3 つである。iOS は、最低の OS と、利用する側に要る Xcode の版 (マニフェストが宣言する Swift tools の版から決まる) を載せる
- Android は、利用者に求める下限と、ライブラリのビルドに使った版を分けて書く
- **確かめていない下限を、下限として載せない。** メタデータから読んだだけで、その版でビルドして確かめていない値は、利用する側の下限に書かない。ライブラリのビルドに使っている版として書く
- Android の利用する側の下限は、minSdk と compileSdk だけを示す (2026-10-10 時点の値は minSdk 29・compileSdk 36。値は、上のビルドの設定から拾う)。Android Gradle Plugin と Kotlin の下限は、その組でビルドして確かめていないので示さない (2026-10-10 のオーナーの決定)
- README の 2 枚と Android の 2 つの `SKILL.md` は、Android Gradle Plugin と Kotlin の下限を示していないことと、確かめてある版の組を、1 文で断っている

検査が見るもの: 4 つの Skill のファイルの集合が英日で同じこと・frontmatter の 5 項目・README の 9 つの節の並び・導線のリンクの先の実在。
検査が見ないもの: 4 つの Skill が同じ 6 枚であること (iOS と Android の間)・`SKILL.md` の節の並び・対応プラットフォームの値が今のビルドの設定と合っていること。

## 英語版と日本語版を同じ回に直す

- **1 枚を直すときは、英語版と日本語版を同じ回に直す。** 片方を先に仕上げてから訳さない。新しく書くときも、1 枚ごとに 2 言語を一緒に書く
- 「同じ回」は、1 回の直しの作業のことで、英日の直しを同じ commit に入れる。検査が見るのは、commit された状態で英日が揃っていることである。片方だけを直した commit を push すると、見出しかコードブロックが違っていれば、検証 CI が落ちる
- 見出しの深さの並びを、英日で同じにする。片方にだけ見出しを足さない
- コードブロックの中身 (言語の名前を含む) と順番を、英日で同じにする
- 本文は、同じ事実を同じ順で書く。片方にだけ注意書きを足さない
- iOS と Android で同じ書き方をしている箇所を直すときは、もう片方のプラットフォームの同じ箇所も見て、当たるなら直す

検査が見るもの: 見出しの深さの並び・コードブロックの中身と順番。
検査が見ないもの: 見出しの文面の対応・本文の内容。本文だけを片方で直しても、検査は落ちない。

## コード例

- **コード例には、原則としてコメントを書かない。** 要るかどうかの線は決めていない。本文で説明できることは、本文に書く。書くときは英語で書く。日本語版のコードブロックにも、日本語のコメントを書かない (英日でコードブロックが同じでなくなり、片方だけを直したことを機械で見つけられなくなる)
- 説明は、コードブロックの前後の本文に書く
- 例の中の文字列 (画面に出す文言・読み上げの文言) も、英日で同じにする (英語で書く)
- Android の `references/` の例は `import` を省いている。省いた import のうち、推測しにくいものは、本文に書く (初回の制作では、`by mutableStateOf` に要る `getValue`・`setValue` と、コルーチンの取り消しを表す例外 `CancellationException` の import が推測になった)
- 例が、利用者のモジュールに無いかもしれない依存 (Android の Material 3 など) を使うときは、無いモジュールでの読み替え方を `SKILL.md` に書く
- 見本の URL は `https://example.com/` で始める。ほかのホストを例に書かない

### 最小コード例は、利用者役の画面のファイルと同じにする

README の最小コード例と、各 `SKILL.md` の最小の動く例は、利用者役の画面のファイルの全体と同じ内容にする。

| プラットフォーム | 利用者役の画面のファイル |
|---|---|
| iOS | `verification/ios/Sources/VerificationApp/ItemListScreen.swift` |
| Android | `verification/android/app/src/main/kotlin/ItemListScreen.kt` |

- 例を変えるときは、利用者役の画面のファイルを先に変え、README の 2 枚と 4 つの `SKILL.md` に同じ内容を写す。利用者役のファイルは、検証 CI の利用者の立場のビルドの確認がビルドする ([利用者の立場のビルドの確認](consumer-build-check.md))
- 利用者役の画面のファイルには、コメントと、利用者に関係の無い行 (package の宣言・`public`) を書かない。そのまま README に載るためである

### コード例を確かめる

`references/` のコード例と、本文の中の 1 行の断片は、どの検査もビルドしない。コードブロックか断片を変えた・足したときは、リポジトリの外の作業用の置き場でコンパイルして確かめる。リポジトリのファイルは変えない。コンパイルして確かめることは決まりで、下の表のやり方は、初回の制作で行った一例である (同じことを確かめられれば、別のやり方でよい)。

| プラットフォーム | やり方 (初回の制作で行った形) |
|---|---|
| iOS | 本体 (`ios/` のマニフェストとソース) の写しに依存する作業用の Swift パッケージを作り、英語版のコードブロックを取り出して置く (1 枚を 1 つの target にし、先頭に `import SwiftUI` と `import KsCollectionView` を足す)。行き先を機種を決めない形 (`generic/platform=iOS Simulator`) にしてビルドする。Swift 6 の言語モードで確かめる |
| Android | `android/` と `verification/android/` の写しを作り、写しの本体を作業用の Maven のディレクトリへ発行して、写しの利用者役のアプリから利用者と同じ 1 行の依存で取る。英語版のコードブロックを取り出して、1 枚を 1 つのファイルにして置く (先頭に package の宣言と import を足す。例が Material 3 を使うなら、写しのアプリにその依存を足す)。Kotlin のコンパイルのタスクを流す |
| どちらも (1 つの画面で確かめたいとき) | 作業ツリーを作業用の置き場に写して使い捨ての git のリポジトリにし、写しの中の利用者役の画面のファイルを入れ替えて、確認のスクリプトを `local` で流す。利用者と同じ依存の届き方で確かめられる |

- 日本語版のコードブロックは、検査が英語版と同じ内容だと確かめているので、英語版だけをビルドすればよい
- 本文の中の 1 行の断片も、コンパイルできる形にして一緒に通す
- ビルドが例のソースを読んでいることを、最初に 1 回確かめる (存在しない名前を呼ぶファイルを足すと落ち、消すと通る)
- 確かめられるのは、コンパイルが通ることまでである。例を起動して動きを見てはいないことを、作業の報告に書く

検査が見るもの: README の最小コード例が利用者役の画面のファイルと同じこと・コードブロックが英日で同じこと・一覧に無い URL が無いこと。
検査が見ないもの: `SKILL.md` の最小の動く例が利用者役と同じこと (追従の道具が、利用者役の変更を「変わった源泉」として出す)・`references/` の例がコンパイルできること・コメントの有無と言語。

## 相手のプラットフォームとの差

「片方にしか無いもの」と「無い機能」は、何が無いのかで、書く場所が違う。

| 書くもの | 書く場所 | 書き方 (今の Skill の例) |
|---|---|---|
| 両方にある機能の、動きの差 | 両方の Skill の、**その機能を説明している場所に 1〜2 文** | それぞれの側から書く (タッチ中の色: 「Android の同じ設定は、色みだけを使い…」/「iOS の同じ設定は、渡した色を…そのまま…塗ります」) |
| 相手にだけある機能・指定・手順 | こちらの Skill の、同じ用途を説明している場所に 1 文 | こちらでは要らない・無いことを書き、相手のものは役割で呼ぶ (Android の Skill: 「このために宣言するものはありません。(iOS では、こうした状態を専用の modifier で一覧に渡す必要があります…)」) |
| こちらにだけある機能・指定・手順と、こちらにだけ当たる約束ごと | こちらの Skill にだけ、ふつうの説明として書く。相手の Skill には、上の行の 1 文だけが載る | こちらにしか無いことを 1 文で断る (iOS の Skill: 「この modifier は iOS にしかありません」「この手順は iOS にしかありません」) |
| ライブラリが、どちらのプラットフォームでも提供していない機能 | `SKILL.md` の「できること」の表の下に、1 か所にまとめる | 「次のものには、ライブラリの API がありません」で始まる 1 段落 |

- 差をまとめた節や 1 枚を作らない
- 相手のプラットフォームのコードを載せない。iOS の Skill に Kotlin のコードブロックを、Android の Skill に Swift のコードブロックを置かない。本文の中でも、相手のプラットフォームの modifier や関数の呼び出しを書かない
- 相手のものは、役割で呼ぶ (「同じ設定」「対応するコールバック」「専用の modifier」「同じ命令」)。今の Skill が相手の名前を出しているのは、名前の違いそのものを説明している 1 か所 (テンプレートの登録。型の名前と関数の名前が違う) だけである
- 相手の Skill に触れるときは、名前 (`kscollectionview-ios`・`kscollectionview-android`) だけを書く。リンクを張らない。触れるのは `SKILL.md` の冒頭の 1 か所で足りる
- 相手のプラットフォームの動きを書くときは、相手の本体のコードか、相手の Skill の文面と突き合わせて、合っていることを確かめる。初回の制作では、iOS の Skill が Android の動きに触れる 16 行を、Android の実物と突き合わせた

検査が見るもの: Skill の外へのリンクが無いこと。
検査が見ないもの: 相手のプラットフォームのコードブロックが無いこと・差の記述が合っていること。

## Skill の外への参照

この節の決まりは、Skill にだけ当たる (README には当たらない)。Skill は、1 ディレクトリを単体でコピーして使われる。Skill の外への参照は、何のための参照かで分ける ([cross/ADR-0019](../../decisions/cross/0019-skill-external-references-by-purpose.md))。

| 参照 | 扱い |
|---|---|
| 知識を Skill の外に委ねる参照 (README・Skill の索引・相手の Skill・リポジトリの中の文書へ、続きをそちらで読ませるもの) | 書かない。Skill の外のファイルへのリンクは、すべてこれに当たる |
| 操作の対象になる URL (依存に書く Package URL・最新の版の確かめ先・不具合の報告先・frontmatter の `metadata.source`) | 書いてよい。許可する URL の一覧にあるものだけ |
| 同じ Skill の中の 1 枚へのリンク | 書いてよい。リンクの先が実在すること |
| 依存しているライブラリの文書への誘導 | URL は書かない。「そのライブラリの文書に従う」と言葉で書き、Skill が扱わない範囲であることを明記する |

- Skill だけで読み切れるように書く。Skill の外を見ないと分からないことを残さない
- リポジトリの内部の言葉を書かない。ADR の番号・開発の記録の言葉・利用者役など、利用者の知らない言葉が当たる。内部の言葉の一覧は `scripts/ci/user-docs-rules.json` の `internalTerms` にある
- HTML で書いたリンクと画像も、同じ扱いである。検査は、Markdown の書き方のほかに、HTML の `href`・`src` の値もリンクの先として見る。HTML のほかの属性 (`srcset` など) と、属性の名前と値を改行で分けた書き方は、検査が見ない (限界)

### URL と内部の言葉の一覧に足すとき

許可する URL と内部の言葉は、`scripts/ci/user-docs-rules.json` に置いてある。

| 項目 | 中身 | 足すとき |
|---|---|---|
| `allowedUrls` | 完全一致で許可する URL。役割 (`role`)・URL・何の URL か (`note`) を持つ。今は 4 つ (Package URL・本リポジトリ・最新の版の確かめ先・不具合の報告先) | 操作の対象になる URL だけを足す。知識を委ねる先 (文書のページ・ブログ) は足さない。役割 `latest-version` の URL は、インストール例の検査が「最新の版の確かめ先」として読むので、役割の名前を変えない |
| `sampleUrlPrefixes` | 前方一致で許可する、見本の URL の前置き。今は `https://example.com/` | 原則として足さない。例は、今の前置きで書く |
| `internalTerms` | Skill に現れてはいけない言葉。大文字と小文字を区別せずに探す。言葉の端が英数字のときは、ほかの単語の一部を数えない | 新しい内部の言葉 (ハーネスの道具の名前・内部のディレクトリやターゲットの名前) が Skill に入り得ると分かったときに足す。足す前に、その言葉が Skill の正しい文面に現れないことを、4 つの Skill で探して確かめる (一般の英単語と重なる言葉を足すと、正しい文面が落ちる) |

一覧を変えたら、スクリプトのテストを流す (`python3 scripts/ci/run-tests.py`)。

検査が見るもの: Skill の外へ出るリンク (Markdown の書き方と、HTML の `href`・`src`)・一覧に無い URL・内部の言葉 (本文とコードブロックの両方)。
検査が見ないもの: 言葉だけで Skill の外へ誘導する文・Skill だけで読み切れるか・HTML の `href`・`src` のほかの属性に書いた先・属性の名前と値を改行で分けて書いた先。

## インストール例

インストール例は、6 つのファイル (README の 2 枚と、4 つの `SKILL.md`) にある。

- **版の位置には `{version}` を置く。具体の版を書かない** ([cross/ADR-0018](../../decisions/cross/0018-install-examples-without-concrete-version.md))。リリースのときにも、書き換えない
- 例のそばに、次の 3 つを、同じファイルの中に書く: `{version}` を、利用者が使う版の番号に置き換えること・置き換えないと依存の解決に失敗すること・最新の版の確かめ先の URL
- Package URL・package の名前・product の名前・Maven の座標は、[公開識別子と配布座標](public-identifiers.md) の値を書く。検査は、利用者役が公開済みの配布物を取るときに使う値と比べる
- README は SwiftPM と Gradle の両方の例を、iOS の `SKILL.md` は SwiftPM の例を、Android の `SKILL.md` は Gradle の例を持つ。英語版と日本語版で、例の種類と数を同じにする
- 配布物をまだ公開していないことの 1 文は、README のインストールの節の冒頭にだけ書く。Skill には書かない (利用者が Skill を手にするのは、公開の後である)。この 1 文は、初回のリリースのときに外す
- Skill の索引 (`skills/README.md`・`skills/README_ja.md`) には、ライブラリの版を書かない

最新の版の確かめ先 (本リポジトリの Release の一覧) は、仮の値である。リリースの工程が別の場所に決めたら、例のある 6 つのファイルと、許可する URL の一覧を同時に直す。

### 依存の宣言の行の形

**依存の宣言の行は、コードブロックの中に、次の形で 1 行ずつ書く。** 検査は、コードブロックの中のこの形の行だけを、インストール例として数える。文の中に書いた同じ字面は数えない。

```text
.package(url: "<Package URL>", exact: "{version}")
.product(name: "<product>", package: "<package>")
implementation("<group>:<artifact>:{version}")
```

コードブロックの中で、本ライブラリの Package URL か Maven の座標に触れる行は、上の形のとおりに書く。形の違う行は、版の位置を読み取れないので、検査が行そのものを違反にする。違反の文面は「本ライブラリの Package URL (…) に触れている行が、決めた形 … でない」で始まる (Maven の座標のときは「本ライブラリの Maven の座標 (…)」)。

| 違反になる書き方 (コードブロックの中) | 理由 |
|---|---|
| 行末にコメントを足した行 | 決めた形に当たらない |
| 別の書き方 (Groovy の書き方・`api(...)` など) | 同上 |
| Package URL の行を、複数行に分けた宣言 | 同上 |

座標を分けて書く形は、検査が拾えない。group・name・version を別々に書く宣言と、version catalog の書き方が当たる。行の中に座標 (`<group>:<artifact>`) の字面が現れないので、この形に具体の版を書いても、検査は気付かない (限界)。

検査が見るもの: 値が利用者役の値と同じこと・版が `{version}` であること・最新の版の確かめ先の URL が同じファイルにあること・例の種類と数・コードブロックの中で Package URL か座標に触れる行が、決めた形であること。
検査が見ないもの: 置き換えの説明の文面・文の中に書いた版・座標を分けて書く形に書いた具体の版。

## 公開の宣言の名前

- **本体の公開の宣言の名前 (型・関数と modifier・プロパティ・列挙の値) は、外すと決めたものを除いて、そのプラットフォームの Skill の英語版と日本語版のそれぞれに、一度は現れるようにする**
- 名前は、その機能を説明している 1 枚に、使い方と一緒に載せる。名前だけを並べた一覧の節を作って数を合わせない
- 外してよいのは、利用者が自分のコードに書かない名前だけである (コンパイラが呼ぶ関数・DSL の組み立てに使う印など)。利用者が書けるが勧めない名前は、外さずに、勧めない理由と一緒に載せる
- 外す名前は、書き手が決めない。候補と理由を一覧にして、オーナーに諮る。決まった名前と理由を、追従の記録 (`skills/.manifest.json`) の `apiExclusions` に、プラットフォームごとに書く
- 外す名前を、文書の表だけに書かない。道具が読む記録に書かないと、毎回報告され、同じ判断を聞き直すことになる
- 提供していない機能は、`SKILL.md` の「できること」の表の下に、1 か所にまとめて書く。書く前に、公開の宣言を読んで、無いことを確かめる

今、外している名前 (2026-10-10 のオーナーの決定。正は `skills/.manifest.json` の `apiExclusions`):

| プラットフォーム | 名前 | 外す理由 |
|---|---|---|
| iOS | `buildExpression`・`buildBlock` | テンプレートを並べて書くブロック (`KsTemplateBuilder`) を、コンパイラが組み立てるときに自動で呼ぶ関数。利用者は自分のコードに書かない |
| Android | なし | — |

確かめ方: `python3 scripts/docs/check-api-coverage.py` (漏れが無ければ終了コード 0)。追従のときと、Skill から名前を消したときに流す ([利用者向け Skill の追従](user-skill-refresh.md))。

検査が見るもの: なし (検証 CI では流れない。上の道具を、人が流す)。
検査が見ないもの: 名前が Skill に現れていること・名前が使い方と一緒に載っていること。

## 書くときの勘どころ

この節は、決まりではなく助言である。守れたかを検査も成果物も判定できないものを含む。ただし、「コードで確かめていない動きを、事実として書かない」ことは、「してはいけないこと」にある決まりである。

初回の制作で、リポジトリの中のレビューをすべて通った後に、Skill だけを渡したエージェントの確認 (読ませる・使わせる) で挙がったことから拾った。

- **事実は、本体のコードで確かめてから書く。** 源泉の概念の文書や、覚えている動きから書かない。宣言の形 (引数の型・既定値・付いている属性)・呼ばれるスレッド・既定の色・依存の届き方は、宣言とビルドの設定の実物を読む
- **コードから決められないことは、書かない。** 掛かる時間・依存しているライブラリの内部に任せている動き・テストも決まりも無い入力の扱いが当たる。書かなかったことと理由を、作業の報告に残す
- 実行して確かめていないことを、確かめたように書かない。コードを読んで決めた動きは、読んで決めたと報告に書く
- **提供していない機能を、明記する。** エージェントは、書かれていない API を探し続けるか、推測で書く。「ライブラリに API が無い」と書けば、そこで止まる
- **例を写したときの落とし穴を、例の直後に断る。** 例が簡単のために省いたことを書く。初回の制作で、例の直後に断ったものは 3 つある: 保存の間の変更を巻き戻すこと・例のモデルが、ソートの並びへ戻す手段を持たないこと・例の例外の型が、代わりの型であること。エージェントは、例をそのまま写す
- **例のどの部分が任意かを書く。** 複数の機能を受け持つ例 (状態を持つモデルなど) は、機能ごとに要る部分を 1 文で示す
- 型の宣言の事実と、実行時の事実を分けて書く。「メインスレッドで呼ばれる」は実行時の話で、クロージャの宣言に何が付いているかは、別に書かないと分からない (Swift 6 の言語モードでは、宣言が分からないと書き方が決まらない)
- 二通りに読める言い回しを避ける。同じものを指す言葉は、Skill の中で 1 つに決め、`SKILL.md` に言葉の説明を置く
- 「できること」の表の行から、行き先の 1 枚の見出しが見つけられるように書く。表から辿れない見出しを作らない
- 1 枚が膨らむ直しは、足す前に、足す量を見積もる (量の上限は決めていない)。例を別の書き方でもう 1 つ足すより、読み替え方を 1〜2 文で書く

検査が見るもの: なし。
検査が見ないもの: この節のすべて。

## スクリーンショット

README のスクリーンショットは、`assets/` の 6 枚である。3 つの画面 (リスト・グリッド (固定列)・グループ化) を、両プラットフォームで撮る。

| 画面 (Sample の名前) | ファイル |
|---|---|
| リスト | `assets/ios-list.png`・`assets/android-list.png` |
| グリッド (固定列) | `assets/ios-grid.png`・`assets/android-grid.png` |
| グループ化 | `assets/ios-grouping.png`・`assets/android-grouping.png` |

### 撮り方

- Sample の今の画面を撮る。**撮るために Sample を変えない**
- 作業専用の Simulator とエミュレータを新しく作って使い、終わったら削除する。操作のたびに、作った端末の識別子を指定する。既存の Simulator・AVD・つながっている実機には触らない
- ライトの表示で撮る。開いた直後 (スクロールしていない・操作していない) の状態で撮る
- ステータスバーを固定の表示にする。初回は、iOS は Simulator の機能で時刻 9:41・電波と電池を固定の表示にし、Android はシステムのデモ表示で時刻 9:41・通知のアイコンなし・電池 100% にした
- 撮る機種と OS は、決めていない。初回は、iPhone 17 (iOS 27.0) と Pixel 8 (Android 16・API 36) で撮った。使った機種と OS を、証跡に残す
- 両プラットフォームで、同じ画面を同じ状態で撮る
- 外から取得した画像が写る画面 (画像グリッド) は撮らない。権利の確認が別に要る

画面の開き方は、戻るボタンの出方が揃うように、プラットフォームで分ける。

| プラットフォーム | 開き方 | 理由 |
|---|---|---|
| Android | Sample の起動の引数で、画面を直接開く | 直接開いても、画面の上のバーに戻る矢印が出る |
| iOS | Sample のメニューからたどって開く | 起動の引数で直接開くと、画面の上のバーに戻るボタンが出ない。メニューからたどって開いた状態で撮ると、Android と揃う |

### 今の 6 枚の、揃っていない点

今の 6 枚 (2026-10-10 に撮ったもの) には、次の 2 点が残っている。オーナーの決定で、今の 6 枚のまま載せている。

| 対象 | 揃っていない点 |
|---|---|
| Android の 3 枚 | 上端の時刻とアイコンが白で描かれていて、明るい背景の上でほとんど見えない。Sample の今の表示である |
| iOS の 3 枚 | 起動の引数で直接開いて撮ったので、戻るボタンが写っていない。Android の 3 枚には、戻る矢印が写っている |

撮り直しは、簡易起票 `kasane/changes/android-sample-status-bar-contrast/exploration.md` に、後で行う作業として書き留めてある。Android の Sample の上端の表示を直した後に、6 枚を上の撮り方で撮り直す。

### 保存する前と後に確かめること

- **保存する前に、1 枚ずつ開いて、外から取得した画像と、個人を特定する情報 (端末の名前・アカウント・通知・通信事業者の名前) が写っていないことを確かめる。** 画像のファイルに、位置や機種の名前の埋め込みが無いことも確かめる
- 撮った後に、Sample をビルドしたことで、git が追跡しているファイルが変わっていないことを確かめる (`git status` に、`samples/` の下の行が出ない)
- README からは、相対パスで参照する。ブランチの名前を含む URL で参照しない
- 環境と、写っているものの確かめの結果を、撮った変更の証跡に残す。初回の記録は、`kasane/changes/archive/2026-10-10-user-docs/evidence/readme-and-screenshots.md` にある

### 撮り直すきっかけ

スクリーンショットが古くなったことは、機械では分からない。次の変更をしたときに、撮り直すかを判断する。

- 撮っている 3 つの画面の、Sample のデモデータ・文言・並べ方を変えた
- ライブラリの既定の見た目 (区切り線・間隔・グループの見出しの固定) を変えた
- Sample の画面の上のバー・操作のパネルの見た目を変えた
- README に載せる画面を足す・入れ替える

撮り直すときは、6 枚を同じ回に撮る (片方のプラットフォームだけを撮り直すと、機種と OS の版がずれる)。

検査が見るもの: README のスクリーンショットの節が、`assets/` の 6 枚を 1 回ずつ指し、6 枚が実在すること。
検査が見ないもの: 画像の中身・大きさ・今の画面と合っているか。

## してはいけないこと

- 英語版か日本語版の片方だけを直して終える
- インストール例に、具体の版を書く
- 確かめていない下限を、利用する側の下限として載せる
- Skill に、Skill の外のファイルへのリンク・一覧に無い URL・内部の言葉を書く
- 相手のプラットフォームのコードを載せる
- コードで確かめていない動きを、事実として書く
- 外す名前を、オーナーに諮らずに `apiExclusions` に足す
- 検査を通すために、検査の一覧 (`user-docs-rules.json`) や、検査が読む見出しの文面を、理由を残さずに変える (理由は、作業の報告に書く)
- ライブラリの不足や不具合を、Skill の文面で取り繕う (オーナーに諮る)。追従の途中に限らない

最後の箇条の線: 無い機能を「無い」と書くこと、例が省いたことを断ることは、事実を事実として書くことで、求められている。禁じているのは、不具合や不足を、決めた仕様であるかのように書いて隠すことと、回避のためのコードを例に足して埋めることである。
