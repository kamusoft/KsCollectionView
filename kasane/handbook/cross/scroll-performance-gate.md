# スクロール性能の体感ゲート

この文書は、スクロール性能を「完了」と判定する共通の規則を定める。読むと、誰が何を根拠に合否を決めるか、どの操作で測るか、証跡に何を残すかが分かる。判定の根拠と経緯は [ADR-0006](../../decisions/cross/0006-perceived-smoothness-as-performance-gate.md) にある。機材・計測器の接続手順・数値の取り出し方は platform 別の文書 ([iOS](../ios/performance-verification.md) / [Android](../android/performance-verification.md)) が持つ。

## 規約

スクロール性能の完了判定が保証するのは「基準機で、その種類の画面をフリックしてもカクつきを感じないこと」だけである。次を守るまで性能面の完了と報告しない。

1. **合否はオーナーが基準機を手動でフリックして下す。** worker は合否を宣言しない
2. **体感による滑らかさの合否に、絶対数値の合格線を置かない。** 数値は合否の説明・原因の帰属・次回との比較材料として証跡に残す。これは体感ゲートの規則であり、**ラッパーの上乗せの薄さを比較対象との相対で見るゲート** (Android の相対計測) は目的も判定者も別の系統である — そちらが数値の基準を持つことはこの規則と矛盾しない
3. **判定が未判定のままでは完了と報告しない。** 未判定は不合格ではないが、完了でもない

worker の役割は、基準機に指定の構成を入れ、計測器を接続してオーナーに渡し、操作後に記録を回収して数値と判定を証跡に書くことである。

## 固定の操作列

手動フリックは次の 4 段階を順に行う。段階を飛ばした記録は他の記録と比較しない。

| 段階 | 操作 |
|---|---|
| 初回 | 先頭から下向きに 10 秒連続フリック (未訪問の範囲を通る) |
| 休止 | 3 秒静止 |
| 再訪 | 上向きに 5 秒 (既に通った範囲) |
| 連続 | 下向きに 10 秒 (未訪問の範囲へ) |

速度は「いつもの感覚」でよい。速度を指定しない代わりに、開始位置・方向・各段階の所要・到達範囲を証跡に残す。

## 判定の 3 状態と再試行

判定は **合格 / 不合格 / 未判定** の 3 状態とする。独立試行は 1 回を基本とし、再試行は次の条件でのみ行う。

- オーナーが体感に迷った、または体感が不合格だったときは、計測器を接続せずに同じ操作列を 1 回行って対照とする。計測器をつないだ負荷が体感を悪くしていないかを確かめるためである
- 体感が迷いなく合格で、数値だけが悪い (体感と数値が食い違う) ときは対照を行わない。計測器を外せば負荷は減る向きなので、対照しても合否は変わらない。食い違いは証跡の「判定」に書く
- 対照でも迷うときは未判定とする。迷った結果を合格側に寄せない
- 記録窓が操作列を収めきれなかった (合図の往復が窓に食い込んだ等) 記録は破棄し、判定に使わない

## 合図の手順

記録の開始はオーナーの準備の合図を待つ。起動と同時に記録を始めない。

1. 基準機に指定の構成を入れ、キャッシュ状態 (入れ直しの有無) を揃える
2. 計測器をプロセス指定で接続し、記録が実際に始まったことを確認する
3. 接続成立を確認してからオーナーに合図し、オーナーの開始の合図を受けてから操作列に入る
4. 操作列の終了を確認してから記録を閉じ、回収する

記録窓が固定長 (`dumpsys gfxinfo` の reset から取得まで、`xctrace` の時間指定) の場合、合図の往復がそのまま窓を食う。窓長は操作列 (合計 28 秒) に往復と余裕を足した長さにする。

## 証跡に残す項目

証跡は change の `evidence/` に、次の 6 節で残す。節を欠いた記録は次回との比較に使えない。

| 節 | 残すもの |
|---|---|
| 環境 | 機種・OS・ビルド構成・fixture・駆動 (手動)・記録手段と記録窓の実長・熱状態 |
| 操作条件 | 開始位置・方向・段階ごとの所要・到達範囲・文字サイズ・キャッシュ状態 |
| オーナーの体感 | 段階ごと (初回 / 再訪 / 連続) の体感とムラの有無。**数値を見る前に**聞き取って記録する |
| 数値 | 計測器から取り出した値。指標名と取得源と単位を明示する |
| 判定 | 合格 / 不合格 / 未判定、体感と数値の一致・不一致、前回との比較可否 |
| 限界 | その記録で分からないこと (操作量の揺れ・未記録の条件・記録回数) |

熱状態は観測した事実の形で書く。「override が無い」ことを「熱制限が無かった」と書き換えない。

### 比較と悪化の記載義務

- 操作条件が前回と揃わないときは「比較不能」と書く。「前回と同等」とは書かない
- 体感の一致と数値の一致は別の文で書く。数値が悪くても体感が合格なら、両方をそのまま書く
- 前回より数値が悪化しているときは、原因仮説・再確認の有無・受容する理由を書く。悪化を黙って通さない

### 参考スケールの扱い

iOS の hitch time ratio には WWDC20「Eliminate animation hitches with XCTest」の推奨値 (5 ms/s 未満 Good、10 ms/s 以上 Critical) を、資料名つきで参考として添えてよい。「Apple の目安」と一括せず、引用元の資料を特定する。Android のフレーム時間には公式の出所を持つ参考スケールが無いため添えない。

参考スケールは合否に読み替えない。窓長も操作量も違う記録の間で、参考スケールを基準にした優劣を書かない。

## 画像の表示待ちは別の観測点

このゲートが判定するのは滑らかさだけである。スクロールを止めてから画像が揃うまでのテンポは別の観測点であり、合否に混ぜない。証跡には体感の節に「画像の出方」として別項目で残し、扱いは画像の能力の spec に委ねる。

## 区切り線が密に見えるのは合否に混ぜない

区切り線のある一覧を速くフリックすると、線がブレて、行が実際より細かく並んで見える。この見え方は滑らかさの合否に混ぜない。オーナーがこの見え方に触れたら、証跡の体感の節に「区切り線の見え方」として別項目で残す。

混ぜない根拠は次の 2 つである (2026-10-06 に確認。条件と数値は [探索メモ](../../changes/archive/2026-10-06-list-separator-blur-on-fast-scroll/exploration.md) と [コマごとの確認](../../changes/archive/2026-10-06-list-separator-blur-on-fast-scroll/evidence/simulator-frame-check.md))。

- 描画は正しい。iOS の Simulator で速いフリックを録画・連写したところ、どのコマでも線は正しい位置・本数・太さで描かれていた
- OS 標準の一覧と同じくらいである。基準機 iPhone 11 で「設定」アプリの一覧を同じ速さでフリックして見比べ、オーナーがそう判定した

見え方の仕組みは、60Hz の画面で等間隔の線が 1 コマに行の半分以上進み、目が直前の数コマを重ねて見るためとみている (実機では未確認)。Android (Pixel 4a) でも iOS より弱く出るが、Android ではコマの確認も OS 標準の一覧との見比べも行っていない。

次のどちらかに当たったら、同じ機体で OS 標準の一覧 (iOS は「設定」アプリ) を同じ速さでフリックして見比べ、結果を証跡の体感の節に書く。OS 標準より目立つときは、合否には混ぜず、区切り線の見た目の変更として起票する。

- オーナーが「OS 標準の一覧より目立つ」または「前回より目立つ」と述べた
- 区切り線の既定の太さ・色を変えた

## 自動駆動の再訪条件

自動駆動 (UI テストによるフリック) はこのゲートでは使わない。駆動の足場が主スレッドを占め、体感を測る土俵そのものを汚すためである。CI で実機を駆動できる受け皿ができ、足場の占有を測って無視できる水準と分かったときに再訪する ([ADR-0006](../../decisions/cross/0006-perceived-smoothness-as-performance-gate.md) の Revisit When)。

## 適用範囲

- 対象: スクロール・セルの生成・再利用・自己サイズ・レイアウト経路に触れる変更、および大量件数を扱う新機能 (セクション・ページング・画像ロード) の完了判定
- 対象外: 公開 API の形だけの変更、Sample の文言・配色の変更
- メモリの定常化と保持対象の解放は本ゲートの対象外 (手順は platform 別の文書)
