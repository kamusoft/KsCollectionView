# テスト実行規約

この文書は、各プラットフォームのテストを「実際に全件走らせる」ための規律と、**実行や検証が黙って空振りする範囲**の扱いを定める。読むと、何をもって検証したと言えるか、どんな書き方が「待ったつもり」になるかが分かる。

本文書の現行規範は、プラットフォーム非依存の 3 節と、実構成で確認済みの iOS / Android の実行手順である。

## 実行件数の確認までが検証

テストが 1 件も実行されなくてもコマンド自体は成功で終わるため、終了コードだけでは検証したことにならない。**実行件数を確認するところまでが検証**であり、テスト結果を報告するときはプラットフォームを問わず実行件数 (`N tests / M failures`) を併記する。

- 件数の得方はビルドシステムごとに異なる。コンソールに出ないビルドシステムでは、結果ファイル (XML / HTML レポート) の集計まで行って初めて件数を得たことになる
- 「テスト全 pass」とだけ報告しない。件数を言えない状態は、空振りしていないことを確認していない状態と同じである
- 絞り込み実行 (特定ターゲット・特定クラスのみ) は反復中の手段であり、**完了判定には絞り込みなしの全件実行を使う**
- 検証 CI は、iOS のテストを 1 件も実行しない (ビルドできることだけを確かめる。[検証 CI](verification-ci.md))。iOS 本体と iOS Sample のテストは、手元で流さなければどこでも走らない。CI の緑を、iOS のテストが通った根拠にしない

## 全系統の合計は 10 分以内

テストは 4 系統ある (iOS 本体・iOS Sample・Android 本体・Android Sample)。4 系統を順に流したときの、コマンド開始から結果が出るまでの待ち時間の合計を、ビルド込みで 10 分以内に保つ ([cross/ADR-0008](../../decisions/cross/0008-test-suite-ten-minute-budget.md))。ビルドは差分ビルドの状態で数える。完了判定に全件実行を使う決まりは変えず、全件を流しても収まる状態をテストの側で保つ。

テストを足すときは、置く層を次の基準で選ぶ。

| 確かめたいこと | 置く層 |
|---|---|
| ライブラリの振る舞い | 本体のテスト |
| Sample のモデル・起動引数の解釈・メニューの並びなど、画面を起動せずに確かめられること | Sample のユニットテスト |
| 実際の指の操作と本物のアプリを通さないと確かめられないこと | Sample の UI テスト |

- Sample の UI テストは 1 件ごとにアプリを起動し、最低でも数秒かかる。本体のテストが確かめている振る舞いを UI テストに重ねない
- 本体のテストはタップ・ドラッグ・スクロールを関数の直呼びで確かめる。機能ごとに、実際の操作を通す UI テストを 1 件ずつ持つ
- テストの追加・変更で合計が伸びる見込みのときは、4 系統を順に流して壁時計の合計を測り、件数とあわせて報告する
- 10 分を超えたら、その変更の中で収める (重なるテストを本体かユニットテストへ寄せる、準備の長い UI テストを短くする)

## 収束を待つアサーション

非同期に反映される状態を検証するテストは、待ちたい**完了条件そのもの**を観測する条件ベース待機で書く。固定時間の待機を繰り返して「静止した」ことにしない。通常時は無駄に待ち、実行機が混んでいるときは待ち足りずに落ちる。

待機は次の 3 つをすべて満たす形で書く。いずれを欠いても「待ったつもり」になる。

- 上限は**実時間の deadline** で区切る。反復回数で区切ると、対象がバックグラウンドにある間にループが燃え尽きる
- ループ内で待機対象へ実行機会を譲る (`Thread.sleep(1)` 等)。CPU が飽和した状況では、OS へのヒントに留まる譲り方 (`Thread.yield()` 等) は譲れる保証がない
- deadline 超過時は黙って戻らず、その時点の実測値をメッセージに載せて失敗させる

黙って戻る待機は収束前の状態を検証したことにされ、「実装が壊れた」と「待機が足りない」も区別できなくなる。この誤りは CPU が競合したときだけ落ちるため、手元では常に緑で、並列実行や CI の混雑時に間欠的に落ちる flaky として表面化する。**手元で通ることは、この形で書けている根拠にならない。**

リスト・グリッドの検証はこの誤りに特に当たりやすい。行の生成・再利用、差分適用、レイアウトの反映はいずれも呼び出した時点では完了せず、フレームまたはバックグラウンドスレッドをまたいで確定するためである。

## プラットフォーム別の実行手順

実測していない手順を確定した手順として書かない。iOS・Android とも本プロジェクトで確認済みである。末尾の小節「Android: 端末をつないで走らせるテスト」だけは、今のコードで確かめていない部分を含む。その部分は、小節の中で「確かめていないこと」として分けてある。

### iOS: Simulator で SwiftPM 全件を実行する

- Swift Package のテストのうち `#if canImport(UIKit)` でガードされたものは、macOS 上の `swift test` では**コンパイル対象から外れ、失敗ではなく最初から存在しないものとして扱われる**
- UIKit のセル・レイアウト・Renderer に関わる検証はガードされた側に集まるため、`swift test` だけで完了と判断すると変更の中核が 1 件も検証されないまま「全 pass」と報告されうる
- `ios/` で `xcodebuild test -scheme KsCollectionView -destination 'platform=iOS Simulator,name=<利用可能な機種名>,OS=<利用可能な版>' -configuration Debug` を実行する
- Release は `ENABLE_TESTABILITY=YES` を付ける。付けないと `@testable import KsCollectionView` を解決できず、テストバンドルのコンパイル前に失敗する
- 新しく作った Simulator でテストが失敗すると、`xcodebuild` が診断の収集で約 10 分待つことがある (成功時は待たない)。失敗の中身を早く見たいときは `-collect-test-diagnostics never` を付ける
- 実行件数は `xcodebuild` 出力末尾の `Executed N tests, with M failures` で確認できる。Simulator の機種名は `xcrun simctl list devices available` で得る

### iOS: Sample のテストと計測ドライバを分けて実行する

Sample (`samples/ios/`) のテストは、ユニットテスト (`KsCollectionViewSamplesTests`) と UI テスト (`KsCollectionViewSamplesUITests`) の 2 つのターゲットに分かれる。UI テストのターゲットには、計測のために動かすドライバが同居する。ドライバを通常の検証に混ぜると、実行時間が伸びるうえ、計測のための固定待機を含むテストが通常の検証の緑の一部として数えられる。

- 通常の検証は `xcodebuild test -project KsCollectionViewSamples.xcodeproj -scheme KsCollectionViewSamples` で実行する。このスキームはユニットテストと UI テストを流し、計測ドライバを除外する
- 計測ドライバは `-scheme KsCollectionViewSamplesPerformance` でのみ実行する。実行そのものが計測手順の一部である
- 計測スキームにユニットテストのターゲットを入れない
- どちらのスキームも実行件数を報告する。通常スキームの件数は、ユニットテストと UI テストの内訳で書く。通常スキームの件数に計測ドライバが含まれていないことが、分離が効いている確認になる

計測ドライバの合否の持ち方は 2 種類あり、実行件数の読み方が変わるため取り違えない。

- **観測のための駆動** (画像の読み込みのように、記録側のログと画面の印を突き合わせて読むもの) は判定を持たない。緑は「駆動が最後まで動いた」ことしか意味せず、合否は証跡の側で決める
- **判定を持つドライバ** (メモリの往復のように、定常化したかを app 側の規則で判定するもの) は、判定に届かなかった走行を**失敗**させる。未判定は証跡に使えない結果であり、緑として通すと「確かめた」ことにされてしまうためである
- したがって**計測スキームの成功件数には判定つきのテストが含まれる**。件数を報告するときは、そのうちどれが判定を持つドライバかまで書く

### Android: 差分なし再実行と Robolectric の描画限界

本体とテストは 2 つのビルドルートに分かれている。完了判定にはどちらも回す。

- 本体は `android/` で `./gradlew :kscollectionview:testDebugUnitTest --rerun-tasks`
- Sample は `samples/android/` で `./gradlew :app:testDebugUnitTest --rerun-tasks`
- 既定の JDK が 17 より古い環境では `JAVA_HOME=$(/usr/libexec/java_home -v 17+)` を前置きする (ビルドは JDK 17 以上のどれでも動く)

件数の得方と落とし穴は次のとおり。

- Gradle は up-to-date なテストタスクをスキップするため、**差分なしの再実行は「テスト 0 件で BUILD SUCCESSFUL」になり得る**。全件を回し直して件数を確認するときは `--rerun-tasks` を付ける
- 実行件数はコンソールに出ない。`build/test-results/<タスク名>/TEST-*.xml` の `tests` / `failures` 属性の合計、または `build/reports/tests/<タスク名>/index.html` で確認する
- ディレクトリ名は variant 名ではなく**タスク名**であり、読み替えを誤ると集計対象が 0 件になる
- XML はクラスごとに 1 ファイルできる。集計はクラス単位の内訳まで出し、期待するクラスがすべて現れていることを確かめる (1 クラスだけ走った状態も「0 件ではない」ため終了コードでは見分けられない)

Robolectric の既定 (legacy graphics モード) では一部の描画処理が実行されず、描画結果を見るアサーションが空振りする。**実描画を要する検証はクラスへ `@GraphicsMode(GraphicsMode.Mode.NATIVE)` を付ける。**

NATIVE モードは実 Skia を動かすため起動コストが増えるが、区切り線の色・タップフィードバックの伝播・content の配置はこれ無しでは検証層に載らないため採用する。ヒープは既定では足りず、`testOptions` で `maxHeapSize = "2g"` を与えている。

### Android: 端末をつないで走らせるテスト

Android 本体には、端末の上でしか確かめられないテストがある (`android/kscollectionview/src/androidTest/`)。2026-10-08 時点では `KsImageDeviceDecodeTest` の 4 件で、画像のデコードが画素をグラフィックス側に置いたときの振る舞いを確かめる。JVM 上のテスト環境では、画素は常にソフトウェア側に置かれるので、この経路はユニットテストでは踏めない ([実行時挙動の検証規約](runtime-behavior-verification.md) の「実行環境で実体が変わる資源」に当たる)。

このテストは、テスト 4 系統に入っておらず、検証 CI も流さない ([cross/ADR-0013](../../decisions/cross/0013-ci-runs-no-simulator-or-device-tests.md))。流し忘れを止める仕組みは無いので、次の時点で手元で流す。

流す時点: Android 本体の、画像のデコードに触る変更をしたとき。画像の取得・デコードする大きさ・メモリに載せた画像の引き当て・先読みが載せる大きさのどれかを変えたら、完了の判定の前に流す。

流し方は 2 つあり、どちらも実機で流した記録がある。端末は minSdk 29 (Android 10) 以上の実機を使う。

| 流し方 | 実行の記録 |
|---|---|
| `android/` で `./gradlew :kscollectionview:connectedDebugAndroidTest` を実行する | テストが 3 件だった時点で、実機で 3 件 / 0 失敗 |
| `android/` で `./gradlew :kscollectionview:assembleDebugAndroidTest` でテストの APK を組み立て、実機に入れて、`am instrument -w -r -e class jp.kamusoft.kscollectionview.KsImageDeviceDecodeTest` で流す | テストが 4 件になった後に、実機で 4 件成功・スキップ 0 |

結果の読み方:

- 実行件数・失敗の件数に加えて、**スキップの件数**を報告する
- 画素がグラフィックス側に置かれることを前提にするテストは、その前提が成り立たなかった実行を、失敗ではなくスキップとして残す。スキップがあった実行は、その契約を確かめたことにならない
- 前提が成り立つかどうかは端末とローダーの判断で、実機でも常には成り立たない (端末の資源が逼迫していると成り立たないことがある)

確かめていないこと (2026-10-08 時点):

| 確かめていないこと | 分かっていること |
|---|---|
| テストが 4 件になった後に、Gradle のタスクで流した結果 | タスクがあることと、テストの APK が組み立てられることは 2026-10-08 に確かめた。端末には流していない |
| Gradle のタスクで流したときに、実行件数とスキップの件数がどこに出るか | 記録が無い。件数の確認までが検証である決まり (上の「実行件数の確認までが検証」) は、このテストにも当たる |
| 2 つ目の流し方の、APK を入れるコマンドと `am instrument` の引数の全体 | 記録にあるのは上の表に書いた部分までである |
| 端末が複数つながっているときに、1 台に絞る指定 | 流した記録が無い |
| エミュレータで流したときの結果 | エミュレータが実機と同じ振る舞いをするかは確かめていない |
