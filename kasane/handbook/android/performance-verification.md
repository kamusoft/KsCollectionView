# Android 性能検証の手順

この文書は、Android ラッパーの変更を性能面で検証するための**土俵・機材・手順**と、相対基準が何を測っているかを定める。読むと、何を fixture にし、どの機材でどう計測し、どの数値を取り出すかが分かる。

**スクロール性能の合否の判定規則はここでは定めない。** 合否・操作列・証跡の形式は [スクロール性能の体感ゲート](../cross/scroll-performance-gate.md) に従う。判定をオーナーの体感に置く理由は [ADR-0006](../../decisions/cross/0006-perceived-smoothness-as-performance-gate.md) にある。

## 計測する 3 系統

| 系統 | 駆動 | 取り出すもの | 判定 |
|---|---|---|---|
| スクロール性能 | オーナーの手動フリック (固定の操作列) | `dumpsys gfxinfo` のフレーム時間分布と Perfetto トレース | オーナーの体感 (cross の体感ゲート) |
| 相対 (ラッパーの上乗せ) | Macrobenchmark の自動計測 | `FrameTimingMetric` の `frameDurationCpuMs` P90 / P99 (3 試行の集計値) | 事後検証スクリプト |
| メモリ | 計測用の入口による自動往復 | 往復ごとの PSS 合計・`MemoryUsageMetric`・テンプレート呼び出しカウンタ | 定常化したか / 未判定、解放されたか |

絶対値の合格線は置かない。フレーム時間そのものの良し悪しは体感ゲートが判定する。

メモリの定常判定は「全項目を通過する往復を重ね、連続する 2 往復の増分がいずれも 2% 以内になったら定常」とする。上限 10 往復で止まらなければ未判定として報告する。増分は符号つきで見る (開いた直後の一時的な確保が回収される往復があるため、減少は定常に含める)。

## 固定 fixture

土俵は**機能ごとの Sample デモ画面**とし、計測用の入口から同じ内容を描く。エンジンの土台に触る変更は文字だけの「大量件数」、特定機能の変更はその機能のデモ画面 (画像なら「画像グリッド」) を使う。

「大量件数」は件数 10,000、2 列グリッド (行間 / 列間 1dp。1 列の比較では 1 列リスト、行間 1dp)、固定高と 7 件ごとの長文による可変行高の混在、整数 ID による決定的な生成。fixture (件数・列数・混在規則・生成) は iOS と同じとする。fixture を変えた計測は過去の結果と比較しない。件数を変えた比較のための試行は持たない。

## 機材

基準機は Pixel 4a (参考機 Pixel 6a)。エミュレータでは計測しない。基準機を接続できないときは代替機で計測してよいが、オーナー承認を得て、証跡に「基準機の保証にならない」旨を明記する。app は benchmark ビルド種別 (release と同じ最適化 + profileable、debug 鍵で署名)。

## 手動フリックの手順

1. app を benchmark 構成で基準機に入れる。キャッシュ状態を揃えるときは削除してから入れ直す
2. 対象の画面を Intent の追加情報 (`ks_start_route=demo/<画面>`) で直接開く
3. `dumpsys gfxinfo <package> reset` で窓を開き、必要なら `perfetto` のトレースも同時に開始する
4. reset の直後にオーナーへ合図し、オーナーの合図を受けて固定の操作列に入る
5. `dumpsys gfxinfo <package> framestats` で回収し、reset から取得までの**時刻差 (記録窓の実長)** も記録する

窓の実長を記録しないと、描画フレーム数が vsync に対して密かどうかを言えない。合図の往復が窓に食い込んだ記録は破棄してやり直す。

### 取り出す数値

- 描画フレーム数と記録窓の実長、janky frames の件数と割合、期限超過 (Frame deadline missed) の件数
- フレーム時間の P50 / P90 / P95 / P99 とヒストグラムの山、Missed Vsync / Slow UI thread / Slow issue draw の内訳

`dumpsys gfxinfo` のフレーム時間 (描画 1 フレームの所要時間の分布) と Macrobenchmark の指標は、取得源も集計対象も別物である。証跡には指標名と取得源と単位を書き、両者を並べて比較しない。Perfetto のトレースは原因の帰属に使い、`evidence/` には集計値だけを載せる。

## 相対計測の手順

計測は Sample と同じビルドルートの Macrobenchmark モジュール (`samples/android/benchmark`) が自動実行する。人の操作を挟まない。

1. 計測モジュールが、計測用の入口へ直接遷移する指定つきでアプリを起動する
2. 目的の画面が載ったこと (画面ごとの semantics の印の出現) を実時間の上限つきで待ってから計測に入る。起動の完了だけで測り始めると遷移途中のフレームが混ざる
3. 実行時コンパイルの状態を試行間で揃える (`CompilationMode.Partial`、暖機 1 回)。起動時間は測らない (`StartupMode` は使わない)
4. 実座標のフリックを 3 秒間続ける試行を独立に 3 回行う
5. 同じ手順をライブラリ側と比較対象側の両方で行い、結果を事後検証スクリプトに掛ける

### 比較対象と、それが測るもの

比較対象は、まったく同じ件数・間隔・行の見た目・安定 ID・再利用種別を、ライブラリを通さず素の Compose で描いた画面 (多列は `LazyVerticalGrid`、1 列は `LazyColumn`)。Sample の計測用ソースセットに置き、release には含めない。

**比較対象には、ライブラリの既定機能と同じ機能を同じ位置に付ける。** 現時点の既定機能は次の 3 つである。

| 既定機能 | 付ける位置 | 比較対象での実現 |
|---|---|---|
| 行の高さ変化のアニメーション ([android/ADR-0004](../../decisions/android/0004-animate-row-height-change-by-default.md)) | 項目の content を包む箱 | Compose 標準の `animateContentSize` |
| 縦のスクロールインジケータ | グリッド / リストの前面 | Compose に標準の描画が無いため、ライブラリと同じ描画 (見た目・表示の契機・位置の求め方) を計測用ソースセットに複製する |
| 配列の差し替えによる移動・挿入・削除のアニメーション ([android/ADR-0006](../../decisions/android/0006-animate-item-placement-on-diff.md)) | 項目とグループの見出しの修飾のいちばん外側 | Compose 標準の `Modifier.animateItem()` (出入りのフェードあり) |

既定機能を付けないと、相対の差は「ラッパーの上乗せ」ではなく既定機能そのもののコストを表す。既定機能を増やしたときは、比較対象にも同じ機能を付けてから測る。

**既定機能を増やした変更では、その機能そのものの費用を相対基準とは別に測る。** 比較対象にも同じ機能が付くため、機能の費用は相対の差に現れない。ライブラリで機能を「付けない / 付ける」の 2 通りを同じ fixture・同じ端末で測り、上乗せ (P90 / P99 の差) を証跡に残す。機能の経路を既存の fixture が通らない場合 (例: 高さが変わらない画面での高さ変化のアニメーション) は、経路を通す一時的な計測画面を足して測り、計測後に取り除く。上乗せの合否に数値の閾値は置かず、基準機の体感のゲート ([cross/ADR-0006](../../decisions/cross/0006-perceived-smoothness-as-performance-gate.md)) で決める。体感で経路を通す画面 (既存の Sample 画面) も触ってもらい、その結果を上乗せの数値と並べて記録する。

この相対基準が測るのは「標準の Compose で同じ機能を組んだ場合に対するラッパーの上乗せ」であり、実装は揃えない (ライブラリは自前の高さ補間、比較対象は `animateContentSize`)。`animateContentSize` は常時の合成レイヤを持ち、ライブラリは補間中だけ描画時に切り取るため、アニメーションが走っていないフリックの計測では比較対象だけがレイヤのコストを負う。**この条件では相対の 10% はラッパーの上乗せより緩い側にある。** ラッパーそのものの薄さを主張するときは、両側からアニメーションを外した対等条件の対照計測を別に採って証跡に載せる。

### 事後検証スクリプト

判定は `samples/android/benchmark/scripts/verify-fling-results.py` が行う。人が結果を目で突き合わせて合否を言わない。契約は次のとおり。

| 観点 | 規則 |
|---|---|
| 入力 | 最新 1 実行の結果 JSON だけを読む。古い結果が混在したら入力不正 |
| 対応付け | `benchmarks[].name` でライブラリ側と比較対象側を対応付ける。片側しか無ければ入力不正 |
| 環境照合 | JSON の `context` (機種・OS・ビルド構成) が両側で一致しなければ入力不正 |
| 計測成立 | 各試行の `frameCount` が 90 以上。割れた試行があれば未判定 |
| 相対判定 | `frameDurationCpuMs` の P90 / P99 (3 試行の集計値) の劣化が 10% 以内なら合格、超えたら不合格 |
| 終了コード | 合格は 0。不合格・未判定・入力不正 (欠損 metric・破損 JSON・重複・片側のみ・環境不一致) は種別ごとに別の非 0 |

比較対象を持たない fixture (画像グリッド) は計測成立だけを判定し、相対の判定はしない。フレーム数の下限 90 は基準機 60 Hz × 3 秒のフリックの理論上限 180 の 50% として固定した値であり、結果を見て動かさない。

## メモリの手順

1. 計測モジュールが自動往復の画面へ直接遷移する指定つきでアプリを起動し、画面が載ったことを待つ。走査・記録・停止まで画面自身が行う
2. 1 往復は、先頭から末尾まで可視範囲の半分程度 (16 項目 = 8 行刻み) 位置を送り、同じ刻みで先頭へ戻る走査。可視範囲より粗い刻みでは間の項目が作られず、コストが計上されない
3. 1 段階ごとに送り先の項目が実際に載ったことを条件に次へ進む (実時間の上限つき)。フレーム数で進めると命令が追い越されて間の項目が作られず「メモリが増えない = 合格」の向きに誤る
4. 往復のたびに通過した項目の識別子を数え、全項目を通過したことを確かめる。両端には刻みと別に明示して到達する
5. 往復ごとに PSS 合計を記録し、定常判定まで往復を重ねる。定常判定に使うのはこのアプリ自身の往復ごとの記録である
6. 定常に達した走査は、続けて下記の「保持対象の解放の確認」の段階 (配列の置換 → 画面離脱) に入る。`MemoryUsageMetric` は計測区間の終わり (離脱の後) の値になるため、定常値としてではなく離脱後の水準として証跡に載せる

到達できなかった・間の項目を飛ばした・上限まで定常にならなかった、はいずれも未判定であり、計測側が実測値つきでテストを失敗させる。緑にはならない。

### 保持対象の解放の確認

メモリの定常化とは別に、ライブラリが**項目単位**で持つ対象 (項目のコンポジション) の解放を確かめる。数えるのは計測用の入口と同じソースセットに置いたテンプレートの呼び出しと破棄で、同時生存は「累計 − 破棄」で読む。カウンタは画面ではなくプロセスに属し、画面を離れた後の値も読める (画面の中に数を持つと、離脱後に読む相手が画面と一緒に消えてしまう)。デモ画面の確認に使う呼び出し回数のカウンタとは別に持つ — あちらは呼び出しごとにログを出すため、計測の構成には載せない。

計測用の入口の自動走査は、10,000 件の通過に続けて「配列の置換 → 画面離脱 (結果画面への遷移)」の段階を持つ。置換する配列は同じ件数で識別子が重ならないものにする (識別子が重なるとテンプレートが作り直されず、解放を見られない)。同時生存の上限は、走査中に観測した最大の**可視件数** (項目の矩形と土俵の矩形の重なりで数える) の 4 倍とする — 同じ走査で観測した同時生存そのものを上限にすると、走査中からすでに多すぎた場合を素通りさせるため、上限は別の観測から独立に決める。係数は固定値であり、結果を見て動かさない。走査中の最大の同時生存と置換後の同時生存がともにこの上限を超えないこと、離脱後の同時生存が 0 であることを、結果画面の進捗の印から読んで計測モジュールが判定する。印の形は `steady:<往復> peak:<最大同時生存> visible:<最大可視件数> replaced:<置換後> left:<離脱後>` で、読めない・可視件数が 0・上限を超えた・離脱後が 0 でないはいずれも失敗させる。置換後の待機は数が動かなくなったことではなく「置換前の項目が 1 つも載っていないこと」を条件にする。Layout Inspector は GUI 操作が前提で固定手順に載らないため使わない。カウンタと計測用画面は release の APK に含めない (ソースセットの差し替えで空実装にし、APK の識別子で確認する)。

## 実行後の後始末

- benchmark の実行後は対象アプリの APK が端末から消える。件数観測など端末上の確認を続けるときは、先に再インストールする
- 生の結果 (Macrobenchmark の JSON と Perfetto トレース) は Gradle の出力に残らず実行ごとに入れ替わる。事後解析に使うなら実行ごとに退避する (置き場は `~/.kasane/` かスクラッチ)

## 証跡

計測結果は change の `evidence/` に、[体感ゲート](../cross/scroll-performance-gate.md)の雛形で残す。相対計測の証跡には環境 (機種・OS・構成・Compose 版・compileSdk)、比較対象の条件、スクリプトの判定を載せる。数値の抜粋は `scripts/log-sanitize.py` を通し、個体識別子・端末名・ローカル絶対パス・生の結果ファイルを含めない。機種は機種名で表す。

## なぜ

相対基準を置くのは、ラッパーが薄いこと ([android/ADR-0001](../../decisions/android/0001-unified-lazy-grid-rendering.md)) を候補実装だけの計測 (循環) ではなく素の Compose との差で検証するためである。この目的は体感ゲートとは別で、自動駆動の汚染は両側に等しく乗るため自動計測のままでよい。

判定を試行別ではなく 3 試行の集計に対して行うのは、差が 1 ms に満たない領域では試行別の P90 / P99 が ±14% 揺れ、試行 1 つの比を判定にすると実装の差ではなく揺れを測ることになるため。集計値が基準を超えたときは同じ手順を 1 回やり直し、再現するかを見る。

判定をスクリプトに載せるのは、人が突き合わせる限り「未判定が緑になる」穴が残るためである。フレーム数の下限を実測で校正しないのは、合否線を結果の観測後に動かせてしまうためである。

## 適用範囲

- 対象: 項目の生成・再利用・自己サイズ・高さ補間・区切り線・タップ領域・スクロール命令の経路に触れる変更、および大量件数を扱う新機能 (セクション・ページング・画像ロード)
- 対象外: 公開 API の形だけの変更、Sample の文言・配色の変更
- CI での自動実行は実機の受け皿ができた時点で再訪する
