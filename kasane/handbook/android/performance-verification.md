# Android 性能検証の手順と合格基準

この文書は、Android ラッパーの変更を「性能面で完了」と判定する条件を定める。読むと、何を土俵に、どの機材と手順で計測し、どの数値なら合格か、そして相対基準が何を測っているかが分かる。手順と合格線は android-wrapper-foundation の実装で基準機により実測して校正したもの (証跡: `kasane/changes/archive/2026-09-05-android-wrapper-foundation/evidence/performance-measurement.md`)。

## 規約

項目の描画・再利用・レイアウト経路に触れる変更は、次の 3 系統を計測し、すべて満たすまで性能面の完了と報告しない。

| 系統 | 指標 | 合格基準 |
|---|---|---|
| 相対 (ラッパーの上乗せ) | `FrameTimingMetric` の `frameDurationCpuMs` P90 / P99。比較対象 (下記) に対する劣化 | 3 試行の集計値で P90・P99 とも劣化 10% 以内 |
| 絶対 (フレーム落ち) | `frameOverrunMs` P99 | 3 試行の集計値で 0.0 ms 以下 (基準機の初回計測で校正した値) |
| メモリ | 往復ごとの PSS 合計 (アプリ自身の記録) と `MemoryUsageMetric` | 連続する 2 往復の増分がいずれも 2% 以内で定常。上限 10 往復で止まらなければ「未判定」。1,000 件と 10,000 件の定常値が件数比 (10 倍) に比例しない |

判定は試行別ではなく 3 試行の集計に対して行う。差が 1 ms に満たない領域では試行別の P90 / P99 が ±14% 揺れ、試行 1 つの比を合否にすると実装の差ではなく揺れを測ることになる。集計値が基準を超えたときは同じ手順を 1 回やり直し、再現するかを見る。差が小さい判定 (相対の符号が固まらないとき) は同じ手順を独立に 2 回実行して両方を証跡に載せる。

比率での比較は `frameOverrunMs` に使わない。実測がほぼ全域で負 (期限に対して余裕がある) であり、負値どうしの比は劣化の大小を表さない。相対は CPU 時間で、超過時間は絶対値で判定するのはこのため。

メモリの定常判定は増分を符号つきで見る。減少は「増え続けていない」として定常に含める (開いた直後の一時的な確保が回収される往復がある)。

## 固定 fixture

Sample「大量件数」画面と同じ内容を描く計測用の入口を土俵にする。件数 10,000 (メモリの件数比較では 1,000 も使う)、2 列グリッド (行間 / 列間 1dp。1 列の比較では 1 列リスト、行間 1dp)、固定高と 7 件ごとの長文による可変行高の混在、整数 ID による決定的な生成。件数ごとにその件数分だけを生成して保持する (最大件数を作り置きして切り出すと 1,000 件の計測でも 10,000 件分の入力データが保持され、件数間の差を測れない)。fixture を変えた計測は過去の結果と比較しない。

## 相対基準の比較対象と、それが測るもの

比較対象は、まったく同じ件数・間隔・行の見た目・安定 ID・再利用種別を、ライブラリを通さず素の Compose で描いた画面 (多列は `LazyVerticalGrid`、1 列は `LazyColumn`)。Sample の計測用ソースセットに置き、release には含めない。

**比較対象の項目には、ライブラリの既定機能と同じ機能を同じ位置に付ける。** 現時点の既定機能は行の高さ変化のアニメーション (android/ADR-0004) で、比較対象は Compose 標準の `animateContentSize` を項目の content を包む箱に付ける。既定機能を比較対象に付けないと、相対の差は「ラッパーの上乗せ」ではなく既定機能そのもののコストを表す (実測: 素のままの比較対象に対して P99 +10.6〜12.9%)。機能そのもののコストは絶対基準で担保する。

この相対基準が測るのは「標準の Compose で同じ機能を組んだ場合に対するラッパーの上乗せ」であり、実装は揃えない (ライブラリは自前の高さ補間、比較対象は `animateContentSize`)。`animateContentSize` は常時の合成レイヤを持ち、ライブラリは補間中だけ描画時に切り取るため、アニメーションが走っていないフリックの計測では比較対象だけがレイヤのコストを負う。**この条件では相対 10% はラッパーの上乗せより緩い側にある。** ラッパーそのものの薄さを主張するときは、両側からアニメーションを外した対等条件の対照計測 (実測: 2 列で P90 +2.3% / P99 +6.0%) を別に採って証跡に載せる。10% を素直な合格基準として読まない。

## 手順

計測は Sample と同じビルドルートの Macrobenchmark モジュール (`samples/android/benchmark`) が自動実行する。人の操作を挟まない。app は benchmark 構成 (release と同じ最適化 + profileable、debug 鍵で署名)。

### スクロール性能

1. 計測モジュールが、計測用の入口へ直接遷移する指定つきでアプリを起動する
2. 目的の画面が載ったこと (画面ごとの semantics の印の出現) を実時間の上限つきで待ってから計測に入る。起動の完了だけで測り始めると遷移途中のフレームが混ざる
3. 実行時コンパイルの状態を試行間で揃える (`CompilationMode.Partial`、暖機 1 回)。起動時間は測らない (`StartupMode` は使わない)
4. 実座標のフリックを 3 秒間続ける試行を独立に 3 回行う
5. 同じ手順をライブラリ側と比較対象側の両方で行い、集計値を突き合わせる

### メモリ

1. 計測モジュールが自動往復の画面へ直接遷移する指定つきでアプリを起動し、画面が載ったことを待つ。走査・記録・停止まで画面自身が行う
2. 1 往復は、先頭から末尾まで可視範囲の半分程度 (16 項目 = 8 行刻み) 位置を送り、同じ刻みで先頭へ戻る走査。可視範囲より粗い刻みでは間の項目が作られず、コストが計上されない
3. 1 段階ごとに送り先の項目が実際に載ったことを条件に次へ進む (実時間の上限つき)。フレーム数で進めると命令が追い越されて間の項目が作られず「メモリが増えない = 合格」の向きに誤る
4. 往復のたびに通過した項目の識別子を数え、全項目を通過したことを確かめる。両端には刻みと別に明示して到達する
5. 往復ごとに PSS 合計を記録し、定常判定 (上表) まで往復を重ねる。終了時点で `MemoryUsageMetric` からも記録する
6. 同じ手順を 1,000 件でも行い、定常値を件数間で突き合わせる

到達できなかった・間の項目を飛ばした・上限まで定常にならなかった、はいずれも未判定であり、計測側が実測値つきでテストを失敗させる。緑にはならない。

### 再利用の確認

Sample の debug 構成に置いたテンプレート呼び出しカウンタで、累計の呼び出し回数と同時生存数 (現在値・最大値・破棄回数) を読む。10,000 件を渡して初期表示で評価されるのが可視範囲の項目数だけであること、フリックで数百項目を通過しても同時生存の最大が可視範囲 + 先読み分に留まること、累計 − 破棄 = 現在値が成り立つことを確かめる。Layout Inspector は GUI 操作が前提で固定手順に載らないため使わない。カウンタと計測用画面は release の APK に含めない (ソースセットの差し替えで空実装にし、APK の識別子で確認する)。

## 機材

基準機は Pixel 4a (参考機 Pixel 6a)。エミュレータでは計測しない。基準機を接続できないときは代替機で計測してよいが、オーナー承認を得て、証跡に「基準機の保証にならない」旨を明記する。

## 証跡

計測結果は change の `evidence/` に、環境 (機種・OS・構成・Compose 版・compileSdk)、fixture、各試行 (または実行) の値、比較対象の条件、判定を表で残す。数値の抜粋は `scripts/log-sanitize.py` を通し、個体識別子・端末名・ローカル絶対パス・生の結果ファイルを含めない。機種は機種名で表す。

## なぜ

手動計測 (Perfetto / `dumpsys gfxinfo`) は再現性が人の操作に依存する。Macrobenchmark は iOS の「計測専用 launch 経路 + 固定手順」と同じ再現性を公式の枠組みで得られ、将来 CI にも載る。相対基準を置くのは、ラッパーが薄いこと (android/ADR-0001) を候補実装だけの計測 (循環) ではなく素の Compose との差で検証するため。

## 適用範囲

- 対象: 項目の生成・再利用・自己サイズ・高さ補間・区切り線・タップ領域・スクロール命令の経路に触れる変更、および大量件数を扱う新機能 (セクション・ページング・画像ロード)。ライブラリの既定機能を増やしたときは比較対象にも同じ機能を付けてから測る
- 対象外: 公開 API の形だけの変更、Sample の文言・配色の変更
- CI での自動実行は実機の受け皿ができた時点で再訪する
