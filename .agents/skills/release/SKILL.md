# release — リリースの入口

KsCollectionView のリリース (版を入力してリリースの workflow を起動し、両プラットフォームの配布物を同じ版で公開して、tag と Release を作る) を、手順の文書に従って進める。この Skill は入口であり、段の順序もコマンドも持たない。

## 手順の正

リリースの手順の正は、次の 1 枚である。

```
kasane/handbook/cross/release-procedure.md
```

- 起動のたびに、この文書を先頭から本文まで読む。前回の記憶や要約で代えない (手順は変わっていることがある)
- 以降は、この文書に書かれた順とコマンドのとおりに進める。依頼の種類 (本番・試し・失敗した実行の続き) ごとにどこから始めるかも、この文書の「この文書の使い方」にある
- この文書が無いときは、何も実行せずに止まり、次の趣旨を伝える

  ```
  リリースの手順の文書 kasane/handbook/cross/release-procedure.md がありません。
  release の Skill は、この文書に書かれた順とコマンドのとおりに進める前提で、手順を自分では持ちません。
  今回は、何も実行していません (push・Pull Request・workflow の起動をしていません)。
  ```

- この文書の前提と手元の状態が違うとき・書かれていない状況に当たったときは、手順を補わずに止まる (下の「止まる条件」)。この Skill は、手順の文書を書き換えない

この Skill が自分で持つのは、次の 3 つだけである。

1. 変更の節の下書きの作り方 (下の「変更の節の下書き」)
2. オーナーへの確認を 1 回にまとめる境界 (下の「確認は 1 回」)
3. 自動の進行を止める条件 (下の「止まる条件」)

## この Skill の中の言葉

| 言葉 | 意味 |
|---|---|
| 手順の文書 | 上の `kasane/handbook/cross/release-procedure.md` |
| オーナー | リポジトリの持ち主である開発者。リリースを頼み、版と変更の節の文面を確定する |
| 対象の commit | 事前の確認を終えた時点の `origin/develop` の先端。リリースの Pull Request で `main` に入れ、公開する commit |
| 変更の節 | `main` 宛ての Pull Request の本文の `## Changes` の節。リリースノートの材料になる。行の書き方は `.github/pull_request_template.md` の注釈にある |
| リリースの Pull Request | 対象の commit を `develop` から `main` へ入れる Pull Request |
| 確定 | オーナーが、確認のメッセージに対して、版と変更の節の文面を決めて答えたこと |

## 頼まれたときだけ動く

- オーナーが明示して、リリース・その試し (dry-run)・失敗した実行の続きのどれかを頼んだときだけ動く
- 別の作業 (変更の実装・蒸留・追従など) が終わった流れで、自分からリリースを始めない。Pull Request の作成も workflow の起動もしない
- 試しを頼まれたときは、その依頼を、試しの起動の承認として扱う (版が依頼に無ければ聞く)。試しは外へ何も送らない
- 失敗した実行の続きを頼まれたときは、手順の文書の失敗したときの節に従う。再実行の形をオーナーが選んでいなければ、選べる形を示して答えを待つ

## 事前の確認で満たすこと

確認のメッセージを出す前に、手順の文書の事前の確認の段を流し、次が満たされていることを確かめる。確かめ方のコマンドは手順の文書にある。

- 手元の `develop` と `origin/develop` の関係: 手元が先行していれば push し、その先端の検証 CI の完了を待つ。手元が遅れている・分かれているときは、push せずに止まる
- 対象の commit の検証 CI が成功している。失敗しているとき・待っても終わらないときは、確認のメッセージを出さずに止まり、失敗した検査を示す
- 対象の commit に検証 CI の記録が無いときは、push した直後なら手順の文書の上限まで読み直し、それでも無ければ、直近で検証 CI が成功した commit の成功で代えられるかを確かめる (下の段落)
- 利用者向け Skill の追従が要るか: 追従の Skill `docs-refresh` の確かめるだけの使い方 (引数 `check`) で調べ、結果を確認のメッセージに添える。追従そのものはしない (追従はオーナーが頼むもの)

対象の commit に検証 CI の記録が無いのは、`develop` への push で検証 CI を起動しないパスだけを変えた commit が先端にあるときである。このときは、直近で検証 CI が成功した commit から対象の commit までの変更が、検証 CI を起動しないパスだけなら、その成功で代えて進む。それ以外の変更があれば止まり、変わったパスを示す。起動しないパスかどうかは、自分で判断せず、手順の文書のコマンドの結果で決める。

## 確認は 1 回

オーナーに確認するのは、1 回のメッセージだけである。段ごとに「進めてよいか」を聞かない。

確認のメッセージに並べるもの:

| 項目 | 内容 |
|---|---|
| 対象の commit | ID と、その検証 CI の run。直近の成功で代えたときは、代えた run と、その commit から対象の commit までに変わったパス |
| 版 | 依頼にあればその版。無ければ候補 (前回の版と、下書きに `breaking` があるかを判断の材料に添える) |
| 変更の節の下書き | 下の「変更の節の下書き」で作ったもの |
| 下書きから外した commit | commit と、外した理由 |
| 事前の確認の結果 | push したか・検証 CI の結果 (直近の成功で代えたかを含む) |
| 利用者向け Skill の追従 | 要るか (`docs-refresh` の確かめるだけの結果) |

- 確定の前に、公開を伴う操作 (リリースの Pull Request のマージ・本番の起動・tag の作成) をしない。確定していない下書きを、Pull Request の本文に書き込まない
- 確定したら、それを対象の commit についての以降の承認として扱う。手順の文書のとおり、リリースの Pull Request の作成とマージ・本番の起動・公開の後の確認まで、段ごとに聞かずに進める (起動に伴う tag と Release の作成も、この確定で承認済みである)
- マージは、リリースの Pull Request の先端が対象の commit と同じときだけ行う。確定の後に `origin/develop` が進み、先端が対象の commit と違っていたら、マージせずに止まり、先端が変わったことを示す
- CI と workflow の完了は、自分で見張る (オーナーに「終わったら教えて」と頼まない)。待ちはバックグラウンドで流し、完了したら、成功・失敗をジョブごとに読み直してから次の段へ進む。見張り方のコマンドは手順の文書にある
- 段を 1 つ終えるたびに、手順の文書のその段の到達状態と突き合わせる。達していないまま次の段へ進まない。進み具合は 1〜2 行で流し、応答は求めない
- 最後に、完了の報告を 1 回出す

```
リリース <版> 完了
- 各段の到達状態: 段ごとに 1 行 (根拠にした run・Pull Request・URL)
- 公開物: 配信用リポジトリの tag・本リポジトリの tag・Release・Maven Central の版 (確かめた先)
- 気になる点: <あれば。無ければ「なし」>
```

## 変更の節の下書き

範囲は、これから作るリリースの Pull Request が `main` へ新しく持ち込む commit だけである。前回のリリースからのすべての変更を範囲にしない (すでに `main` に入った変更は、それを持ち込んだ Pull Request の変更の節が持っていて、ノートに二重に載る)。範囲の commit を出すコマンドは、手順の文書にある。

- 利用者から見える変化 (公開 API・配布物・利用者向けの文書) だけを載せる。ハーネス・CI・テストの整備や、内部の作り直しは載せない
- 1 項目 1 行で、`.github/pull_request_template.md` の注釈の書き方 (行の形・種類・言語) に合わせる。説明は英語で、利用者の言葉で書く。commit のメッセージの言い回しや、内部の識別子をそのまま持ち込まない
- 複数の commit が 1 つの利用者向けの変化にまとまるなら、1 項目にまとめる
- 載せるものが無ければ、`- none` の 1 行だけにする
- 変更の節は、次の `## ` で始まる見出しか、本文の終わりまで続く。Pull Request の本文で、変更の節の後ろに何かを書くとき (本文の末尾に付ける署名の行など) は、`## ` で始まる見出し (`## Notes` など) を置いてから書く。`###` などほかの水準の見出しでは変更の節が終わらない。見出しを置かずに足すと、その行が変更の節の読めない行になり、リリースが止まる
- 下書きは下書きのままオーナーに示し、種類の割り当てと文面の確定を委ねる (確認は上の 1 回で行う)

## 止まる条件

次のときに自動の進行を止め、何が起きたか・手順の文書の該当箇所・選べる対応 (推奨を先頭に) を、1 回のメッセージで示す。

| 止まるとき | 示すもの |
|---|---|
| 検証や実行が失敗したとき (事前の確認の検証 CI・リリースの Pull Request の検査・リリースの workflow) | 失敗した位置 (ジョブと step とログのエラーの行)。手順の文書の失敗したときの記述のうち、その位置に当たるもの。当たる記述が無ければ「該当なし」と書く (似た別の記述で埋めない) |
| 手順の文書に書かれていない状況に当たったとき (前提と手元の状態が違う・コマンドが書かれていない結果を返す) | 何が違うかと、手順の文書の該当箇所 |
| 確定した版や文面のままでは進めないと分かったとき | 進めない理由と、確定し直す必要がある項目 |

- 再実行するか・どの形で再実行するか・中止するかは、オーナーが決める。この Skill は自分では再実行しない
- 版の番号と変更の節の文面は、オーナーが決める (確認の 1 回で決める)

## やらないこと

- 自分から起動しない。起動と公開は取り消せない操作なので、オーナーの明示の依頼から始める
- 手順の文書を読まずに実行しない。手順の文書に無い手順を足さない・端折らない
- 確定の前に、公開を伴う操作をしない。確定していない下書きを Pull Request の本文に書き込まない
- secret の値を扱わない (登録・差し替えはオーナーが行う)
- `main` を `develop` へ取り込み直さない
- 削除は `rm` ではなく `trash` を使う
